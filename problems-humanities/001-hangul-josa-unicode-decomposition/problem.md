# #001 [고객님, '아이폰을' 받으세요: 유니코드 한글 음절 분해와 종성(받침) 판별 동적 조사 교정 엔진 (Hangul Syllable Unicode Decomposition & Dynamic Josa Correction Engine)]

## 1. 장애 및 실무 시나리오

국내 최대 규모의 패션·테크 이커머스 플랫폼의 CRM 마케팅 자동화 팀은 매일 수백만 건의 주문 확인 카카오톡 알림톡, 결제 영수증 이메일, 이벤트 당첨 푸시 메시지를 발송하고 있습니다.

최근 생성형 AI와 바이브 코딩(Vibe Coding) 도구를 활용해 고객 맞춤형 알림 템플릿 엔진을 서둘러 배포했으나, 고객센터로 사용자들의 불만과 조롱이 쏟아지기 시작했습니다:

```
[잘못 발송된 실제 고객 알림 메시지]
- "고객 민준는 주문하신 맥북 프로 16를 서울으로 배송했습니다."   (X)
- "이벤트에서 스타벅스 아메리카노을 수령하여 부산로 보냈습니다."    (X)
- "길동야, 토끼과 함께 엑스칼리버을 들고 모험을 떠나자!"          (X)
- "추천 도서 『어린 왕자』은 생텍쥐페리가 집필한 명작입니다."       (X)
```

### 왜 이런 참사가 발생했을까요?
1. **문과적 감수성과 국어 문법의 부재**:
   - 영어는 `"{user} ordered {item}"`처럼 단순 변수 치환으로 문장이 완성되지만, **한국어는 교착어(Agglutinative Language)**이므로 앞 단어의 끝소리(종성/받침)에 따라 결합하는 조사(이/가, 은/는, 을/를, 과/와, 으/로)가 완전히 달라집니다.
   - AI가 짠 단순 템플릿 치환 코드는 단어 뒤에 무조건 `"(이/가)"`, `"(을/를)"`을 괄호째 붙이거나, 받침을 고려하지 않고 고정된 조사를 붙여 브랜드 이미지를 심각하게 실추시켰습니다.
2. **'ㄹ' 받침의 특수 예외 (으로 vs 로)**:
   - 받침이 있는 단어 뒤에는 매개모음 '으'가 붙어 `'으로'`가 되는 것이 기본이지만, **'ㄹ' 받침으로 끝나는 단어(예: "서울", "3개월", "Model-R")** 뒤에는 '으로'가 아니라 **'로'**가 붙어야 합니다("서울로", "3개월로", "Model-R로").
3. **숫자와 외래어(알파벳) 발음 종성 무시**:
   - "맥북 프로 16"의 마지막 글자는 숫자 `'6'`이며, 한국어 발음은 **'육'(종성 'ㄱ')**이므로 "16을"이 맞습니다.
   - 단순 문자 검사만으로는 숫자나 영어 끝소리의 받침 유무를 판별할 수 없어 오탈자가 양산되었습니다.

마케팅 총괄 이사와 브랜드 경험(BX) 팀은 "우리 플랫폼의 언어적 품격을 지키기 위해, 모든 템플릿 변수를 문법에 맞게 100% 자동 교정하는 유니코드 조사 해결 엔진을 전사 공통 라이브러리로 구축하라"고 명령했습니다.

## 2. 컴퓨터 과학 원리: 한글 유니코드 3차원 음절 블록 (U+AC00 ~ U+D7A3)

현대 한글 11,172자는 유니코드에서 초성(19개) $\times$ 중성(21개) $\times$ 종성(28개, 받침 없음 포함)의 직교 곱(Cartesian Product) 구조로 완벽하게 수학적으로 인코딩되어 있습니다.

```
+-------------------------------------------------------------------------+
|                  한글 유니코드 음절 인코딩 수학 공식                     |
|                                                                         |
|  코드 = 0xAC00 + (초성 인덱스 * 21 + 중성 인덱스) * 28 + 종성 인덱스     |
+-------------------------------------------------------------------------+
                                    │
                                    ▼ 역산 (종성 인덱스 도출)
+-------------------------------------------------------------------------+
|                종성 인덱스 = (ord(문자) - 0xAC00) % 28                  |
|                                                                         |
|  * 종성 인덱스 == 0 : 받침 없음 (예: '사', '바', '가')                   |
|  * 종성 인덱스 > 0  : 받침 있음 (예: '산', '밥', '달')                   |
|  * 종성 인덱스 == 8 : 'ㄹ' 받침 (예: '달', '울', '월') -> '로' 예외 규칙!|
+-------------------------------------------------------------------------+
```

## 3. 입력 사양 (Input Specification)

표준 입력(stdin)으로 하나의 JSON 객체가 주어집니다:

```json
{
  "template": "고객 {user}(이/가) 주문하신 {item}(을/를) {dest}(으/로) 배송합니다.",
  "variables": {
    "user": "민준",
    "item": "맥북 프로 16",
    "dest": "서울"
  }
}
```

### 지원해야 하는 조사 패턴:
1. `(을/를)` 또는 `(을)를`: 받침 있으면 `을`, 없으면 `를`
2. `(은/는)` 또는 `(은)는`: 받침 있으면 `은`, 없으면 `는`
3. `(이/가)` 또는 `(이)가`: 받침 있으면 `이`, 없으면 `가`
4. `(와/과)` 또는 `(과/와)`: 받침 있으면 `과`, 없으면 `와`
5. `(으/로)` 또는 `(으)로`:
   - 받침이 없거나, **받침이 'ㄹ'인 경우**: `로` (예: "서울로", "대구로", "1로", "Model-R로")
   - 그 외의 받침이 있는 경우: `으로` (예: "부산으로", "수박으로", "3호선으로")
6. `(이나/나)` 또는 `(이)나`: 받침 있으면 `이나`, 없으면 `나`
7. `(이라/라)` 또는 `(이)라`: 받침 있으면 `이라`, 없으면 `라`
8. `(아/야)`: 받침 있으면 `아`, 없으면 `야` (호격 조사)

### 처리 규칙:
1. **변수 치환 조사 (`{var}(조사)`)**:
   - `{var}`의 치환값 문자열의 실질적인 마지막 글자를 분석하여 올바른 조사로 교정합니다.
2. **정적 단어 조사 (`단어(조사)`)**:
   - 템플릿 내에 변수가 아닌 일반 텍스트 뒤에 붙은 `사과(와/과)` 같은 패턴도 동일하게 분석하여 `사과와`로 교정합니다.
3. **특수기호 무시 (역추적)**:
   - 단어 끝에 닫는 따옴표(`"`, `'`, `”`, `’`), 괄호(`)`, `]`, `}`), 낫표(`』`) 등이 붙어있는 경우, 이를 건너뛰고 바로 앞의 실질 문자(한글, 숫자, 영문)를 기준으로 종성을 판별합니다 (예: `『어린 왕자』(은/는)` $\rightarrow$ `'자'` 분석 $\rightarrow$ `『어린 왕자』는`).
4. **숫자 발음 매핑 (0~9)**:
   - 0(영, ㅇ받침), 1(일, **ㄹ받침**), 2(이, 무받침), 3(삼, ㅁ받침), 4(사, 무받침), 5(오, 무받침), 6(육, ㄱ받침), 7(칠, **ㄹ받침**), 8(팔, **ㄹ받침**), 9(구, 무받침).
5. **영문 알파벳 발음 매핑**:
   - `L`, `l`, `R`, `r`: **'ㄹ' 받침** 인정 (예: `Model-R` $\rightarrow$ `로`, `Level-L` $\rightarrow$ `을`).
   - `M`, `m`: **'ㅁ' 받침** 인정.
   - `N`, `n`: **'ㄴ' 받침** 인정.
   - 그 외 알파벳(예: `BTS`의 `S`, `Apple`의 `e`): 받침 없음으로 간주.
