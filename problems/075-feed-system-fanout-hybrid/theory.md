# CS 백서: SNS 피드 타임라인 아키텍처와 하이브리드 팬아웃 (Feed Timeline Fan-out-on-Write vs Hybrid Fan-out)

> **"팔로워 1,000만 명 연예인이 사진 한 장 올렸는데 왜 전사 데이터베이스와 레디스(Redis)가 20분 동안 뻗어버리나요?!"**  
> — 소셜 네트워크 서비스를 출시하자마자 유명 인플루언서 가입으로 백엔드 인프라가 전소된 스타트업 개발팀의 절규

---

## 1. 현실 비유: 아파트 단지 우편배달원과 관리소장님의 비극

1만 세대가 모여 사는 초대형 아파트 단지가 있습니다.  
이 단지에는 주민들 사이의 소식을 전하는 우편배달 시스템이 있습니다.

```
[동네 친구 철수 (팔로워 5명)] ────(편지 작성)────▶ 배달원이 5명 우편함에 직접 배달 (Push: 5초 완료!)

[관리소장님 (팔로워 10,000명)] ───(공지 작성)────▶ 배달원이 10,000가구 우편함에 전수 배달?! (Push: 8시간 탈진!)
```

1. **쓰기 시점 배달 (Fan-out-on-Write / Push 방식)**:
   - 동네 친구 철수가 편지를 쓰면, 집배원은 철수를 팔로우하는 친구 5명의 집을 찾아가 우편함(Inbox)에 편지를 꽂아둡니다. 5가구만 돌면 되니 5초 만에 끝납니다. 친구들은 아침에 우편함만 열면 바로 편지를 읽을 수 있습니다.
   - 그런데 어느 날, **단지 전체 1만 세대가 팔로우하는 관리소장님(슈퍼스타/인플루언서)**이 "내일 단수됩니다"라는 공지문을 작성했습니다.
   - 집배원이 이 공지문을 1만 장 인쇄하더니, 101동 101호부터 110동 2504호까지 **1만 개 우편함을 하나하나 찾아다니며 공지문을 꽂기 시작합니다.**
   - 배달원은 반도 못 돌고 탈진하여 쓰러지고, 그동안 다른 일반 주민들의 편지 배달까지 모조리 중단됩니다! (쓰기 팬아웃 폭증으로 메시지 큐와 DB 락 발생)

2. **읽기 시점 배달 (Fan-out-on-Read / Pull 방식)**:
   - 배달원의 비극을 보고 관리사무소는 방식을 완전히 바꿨습니다. "앞으로 편지는 우편함에 배달하지 않는다. 각자 관리사무소에 와서 자기가 팔로우하는 사람들의 편지를 직접 모아서 읽어라!"
   - 배달원은 편해졌지만, 아침마다 1만 명의 주민이 관리사무소 창구로 몰려와 "내가 팔로우하는 50명의 편지 묶음을 다 찾아서 날짜순으로 정렬해 주세요"라고 요구합니다.
   - 창구는 마비되고 주민들은 편지 한 번 읽으려고 30분씩 줄을 서야 합니다 (읽기 시점 Merge Sort 디스크 I/O 병목).

3. **해결책: 하이브리드 배달 시스템 (Hybrid Fan-out)**:
   - **일반 주민(팔로워 적음)**의 편지: 배달원이 팔로워들의 우편함(Inbox)에 즉시 배달 (**Push**).
   - **관리소장님(팔로워 $\ge$ 임계값)**의 공지문: 우편함에 일일이 넣지 않고, 단지 중앙 엘리베이터 입구 게시판(Outbox)에 딱 1장만 게시 (**Pull**)!
   - **주민이 편지를 읽을 때**: 내 우편함(Inbox, 친구들 편지) + 엘리베이터 게시판(Outbox, 관리소장님 공지) 2곳만 쓱 확인하여 합쳐서 읽음!
   - 배달원도 쓰러지지 않고, 주민들도 기다림 없이 번개처럼 최신 피드를 볼 수 있습니다!

## 2. 컴퓨터 과학 이론: 피드 시스템(Feed System)의 3대 아키텍처

트위터(X), 인스타그램, 페이스북 같은 소셜 네트워크 서비스의 핵심은 **"내가 팔로우하는 사람들의 최신 포스트를 시간 역순으로 모아 보여주는 홈 타임라인(Home Timeline)"**입니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. Fan-out-on-Write (Push Model)                            │
│    포스트 작성 시 ─▶ 팔로워 N명의 타임라인 캐시에 전부 복사    │
│    장점: 읽기 $O(1)$ 초고속                                  │
│    단점: 쓰기 $O(N)$ 폭증 (셀럽 문제: Celebrity Problem)     │
├─────────────────────────────────────────────────────────────┤
│ 2. Fan-out-on-Read (Pull Model)                             │
│    포스트 작성 시 ─▶ 작성자 보관함에만 저장                     │
│    장점: 쓰기 $O(1)$ 가벼움                                  │
│    단점: 읽기 $O(K \log K)$ 다중 조회 병합 오버헤드, 지연 심함   │
├─────────────────────────────────────────────────────────────┤
│ 3. Hybrid Fan-out Model (트위터/인스타그램의 실제 해법)       │
│    - 팔로워 수 < Threshold: Push (팔로워 인박스 배달)          │
│    - 팔로워 수 >= Threshold: Pull (셀럽 아웃박스 보관)        │
│    - 유저 피드 조회: 본인 인박스 + 팔로우한 셀럽 아웃박스 병합  │
└─────────────────────────────────────────────────────────────┘
```

### 1) Push Model (Fan-out-on-Write)의 치명적 병목
- 대부분의 사용자는 글을 쓰는 빈도보다 남의 글을 읽는 빈도가 수십~수백 배 높습니다 (Read-Heavy 워크로드).
- 따라서 유저가 피드를 열 때마다 매번 DB를 뒤져서 합치기보다는, 글이 작성될 때 미리 팔로워들의 캐시(Redis Sorted Set)에 넣어두면 읽기 속도가 극대화됩니다 ($O(1)$).
- **그러나 셀럽(Celebrity / Hotspot)이 등장하면 붕괴합니다**:
  - 팔로워가 5,000만 명인 사용자가 트윗 1개를 쓰면, 백엔드는 즉시 5,000만 개의 Redis ZADD 명령을 날려야 합니다.
  - 카프카(Kafka) 파티션에 수천만 개의 메시지가 쌓이고, 컨슈머 렉(Lag)이 치솟으며, 몇 분 동안 다른 일반 유저의 알림과 피드가 멈춰 버립니다.

### 2) Pull Model (Fan-out-on-Read)의 한계
- 셀럽 문제를 피하고자 글을 쓸 때 아무 데도 복사하지 않고 작성자의 테이블에만 저장합니다 ($O(1)$).
- 하지만 사용자가 홈 화면을 열 때마다, 내가 팔로우하는 500명의 유저의 최신 글 수천 건을 디스크에서 긁어모아 시간순으로 정렬(K-way Merge Sort)해야 합니다.
- 캐시 히트율이 급감하고 데이터베이스 CPU가 100%로 치솟아 전체 읽기 API가 지연됩니다.

### 3) 하이브리드 팬아웃 (Hybrid Fan-out)의 우아함
트위터 엔지니어링 팀이 고안하여 전 세계 표준이 된 아키텍처입니다:
1. **팔로워 수 기준 분류**:
   - `len(followers) < CELEBRITY_THRESHOLD` (예: 500명): **일반 유저**
   - `len(followers) >= CELEBRITY_THRESHOLD`: **인플루언서 (Celebrity)**
2. **포스팅 시 (`POST`)**:
   - 일반 유저의 글 $\to$ 팔로워들의 `inbox`에 즉시 Push. (팔로워가 적으므로 부담 제로)
   - 인플루언서의 글 $\to$ 푸시하지 않고, 인플루언서의 `outbox`에만 1건 기록! (쓰기 부하 $O(1)$로 완전 제거)
3. **피드 조회 시 (`READ_FEED`)**:
   - 사용자의 개인 `inbox` (일반 친구들의 푸시된 글들)를 가져옵니다.
   - 사용자가 팔로우하고 있는 **인플루언서 목록**의 `outbox` 최신 글들만 가져옵니다.
   - 소수의 인플루언서 글들과 `inbox`를 시간순으로 병합하여 상위 `FEED_LIMIT`개를 반환합니다.

## 3. 시뮬레이션 모델 명세

### 1) 비용 모델
- **쓰기 연산 (`WRITE_OPS`)**:
  - Naive Engine: 작성자의 팔로워 수 $N$만큼 발생 (`N`).
  - Hybrid Engine:
    - 일반 유저: 팔로워 수 $N$만큼 발생 (`N`).
    - 셀럽 유저: 작성자 Outbox에 1건만 기록 (`1`).
- **읽기 연산 (`READ_OPS`)**:
  - Naive Engine: 본인 Inbox 1회 읽기 (`1`).
  - Hybrid Engine: 본인 Inbox 1회 + 내가 팔로우하는 셀럽 수 $C$회 읽기 (`1 + C`).

### 2) 결과 일관성 (Feed Consistency)
- Naive Engine과 Hybrid Engine이 생성하여 사용자에게 반환하는 최신 피드 목록(`post_ids`)과 순서는 **100% 완벽히 일치**해야 합니다.
- Hybrid 방식은 결과의 왜곡 없이 대규모 쓰기 I/O만을 획기적으로 제거합니다.
