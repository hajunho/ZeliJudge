# [배경 이론] 악성 IP 1만 개 차단했더니 왜 서버 패킷 처리가 100배 느려지고 CPU가 100% 찍어요?!: 리눅스 iptables 선형 탐색($O(N)$) vs ipset 해시 테이블($O(1)$) 패킷 필터링

## 1. 현실 비유: 10,000줄짜리 종이 명단 vs 바코드 스캐너

클럽 정문에서 가드(방화벽)가 입장객(네트워크 패킷)을 검사합니다.

- **iptables 방식 (10,000줄짜리 종이 블랙리스트)**:
  - 이 클럽은 유명해서 블랙리스트에 오른 진상 손님(악성 IP)이 **10,000명**이나 됩니다.
  - 가드는 이 10,000명의 이름이 적힌 **두꺼운 종이 명부(연결 리스트)**를 들고 있습니다.
  - 손님이 1명 올 때마다, 가드는 명부의 1번째 줄부터 10,000번째 줄까지 **눈으로 하나하나 순서대로 비교($O(N)$)**합니다!
  - 1초에 손님이 1,000명씩 몰려오면? 가드는 1초에 무려 **$1,000 	imes 10,000 = 1,000만 번** 종이를 넘겨보다가 뇌 과열(CPU 100%)로 쓰러지고, 정문 앞 대기열(네트워크 지연)은 수 킬로미터로 늘어납니다!

- **ipset 방식 (바코드 스캐너 / 해시 테이블)**:
  - 가드가 종이 명부를 버리고 **바코드 스캐너(해시 테이블, $O(1)$)**를 손에 쥡니다.
  - 블랙리스트에 손님이 10명 있든, 10,000명 있든, 100만 명 있든 상관없습니다.
  - 손님이 오면 신분증을 바코드 기계에 "삑!" 하고 단 **1번 스캔(Hash Lookup)**하여 0.001초 만에 입장/퇴출을 즉시 판정합니다!
  - 가드는 힘 하나 들이지 않고 초당 수만 명의 손님을 지연시간 0초로 가뿐하게 처리합니다.

## 2. 왜 iptables는 룰이 많아지면 폭사하는가?

리눅스 커널의 기본 패킷 필터링 도구인 `iptables`는 Netfilter 프레임워크를 기반으로 동작합니다.  
하지만 iptables의 내부 자료구조는 **단순 연결 리스트 (Linked List)**입니다.

```
[iptables의 O(N) 선형 탐색 체인]
패킷 유입 ──► [Rule 1: Drop 1.1.1.1?] (불일치)
               └──► [Rule 2: Drop 1.1.1.2?] (불일치)
                     └──► ...
                           └──► [Rule 10000: Drop 1.2.3.4?] (불일치)
                                 └──► [Default: ACCEPT] (10,000번 비교 후 통과!)
```

정상적인 사용자 패킷은 블랙리스트에 없기 때문에, 체인에 걸린 **모든 룰(10,000개)을 끝까지 전부 비교하고 나서야** 통과 판정을 받습니다!
- 차단 룰 $N = 1,000$개 $\implies$ 패킷당 1,000회 비교
- 차단 룰 $N = 10,000$개 $\implies$ 패킷당 10,000회 비교
- 초당 수만 패킷 유입 $\implies$ 리눅스 커널 인터럽트 데몬(`ksoftirqd`)이 CPU 100%를 독점하며 네트워크 마비!

> **쿠버네티스(K8s)의 역사적 교훈**:  
> 쿠버네티스 초기에는 모든 Service 라우팅을 `iptables`로 구현했습니다.  
> 하지만 클러스터 내 서비스가 5,000개를 넘어서자 iptables 룰이 수만 개로 불어나 패킷 지연이 수십 배로 폭증하고 CPU가 고갈되는 심각한 성능 한계(iptables Scale Limit)에 부딪혔습니다.  
> 결국 K8s 팀은 이를 해결하기 위해 해시 기반의 **IPVS (IP Virtual Server)** 모드를 표준으로 도입했습니다.

## 3. 구원 투수: ipset (커널 인메모리 해시 테이블)

`ipset`은 리눅스 커널 내부에서 수만~수백만 개의 IP, 네트워크 대역(CIDR), 포트 번호를 **해시 테이블(Hash Table) 및 이진 탐색 트리(rbtree)**로 관리하는 초고속 동반자 도구입니다.

### iptables와 ipset의 결정적 차이

| 구분 | iptables 단독 | iptables + ipset 조합 |
|:---:|:---:|:---:|
| **내부 자료구조** | 단순 연결 리스트 (Linked List) | **해시 테이블 (Hash Table)** |
| **패킷 평가 복잡도** | **$O(N)$ (룰 개수에 비례하여 선형 증가)** | **$O(1)$ (룰이 100만 개여도 1회 고정)** |
| **등록 방식** | IP마다 `iptables -A` 룰 1만 개 등록 | 룰은 **단 1개** (`-m set --match-set`) 등록 |
| **CPU 점유율** | 룰 증가 시 100% 포화 | **0~1% 수준 극도로 경량** |
| **동적 갱신** | 룰 추가 시 전체 체인 재파싱/락 경합 | 커널 메모리 해시 셋에 $O(1)$ 원자적 삽입 |

### 단 1줄로 100만 개 IP를 차단하는 마법
```bash
# 1. 커널에 해시 셋 생성
ipset create blacklist hash:ip

# 2. iptables에는 단 '1개'의 룰만 등록! (O(1) 해시 룩업 매칭)
iptables -A INPUT -m set --match-set blacklist src -j DROP

# 3. 차단할 IP는 ipset에 O(1)으로 마구 추가해도 패킷 처리 속도 영향 0!
ipset add blacklist 198.51.100.1
ipset add blacklist 198.51.100.2
... (100만 개를 추가해도 0ms 지연)
```

이처럼 단순한 알고리즘 자료구조의 차이(연결 리스트 $O(N)$ vs 해시 테이블 $O(1)$)가 대규모 네트워크 인프라에서는 서버가 살고 죽는 거대한 차이를 만들어냅니다.\n
