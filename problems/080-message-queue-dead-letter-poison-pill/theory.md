# 메시지 큐의 독약 알약(Poison Pill)과 데드 레터 큐(Dead Letter Queue, DLQ)

## 1. 분산 메시징의 악몽: 독약 알약 (Poison Pill)

### 1.1 우체국 컨베이어 벨트에 떨어진 독극물 편지 한 통의 비극
하루 10만 통의 우편물을 분류하는 대형 우체국 자동화 센터를 상상해 봅시다.  
컨베이어 벨트를 타고 편지들이 초당 100통씩 바코드 스캐너를 통과하고 있습니다.  
그런데 누군가 실수로 주소란에 정체불명의 화학 약품을 쏟아 바코드가 타버린 불량 편지 한 통이 스캐너에 도착했습니다.

스캐너는 "삐-익! 판독 오류!"를 울리며 벨트를 멈춥니다.

```text
❌ [단순 재시도 시스템 (Naive Retry without DLQ)]
"오류 났네? 다시 읽어봐!" -> 1초 뒤 재시도 -> "삐-익! 판독 오류!"
"또 오류네? 다시 읽어봐!" -> 1초 뒤 재시도 -> "삐-익! 판독 오류!"
... (무한 반복) ...
```

이 단 한 통의 불량 편지 때문에 컨베이어 벨트 전체가 영구 정지(Head-of-Line Blocking)됩니다.  
뒤에 줄 서 있던 10만 통의 정상 우편물(수능 합격 통지서, 법원 등기, 병원 검사 결과)은 단 1통도 배송되지 못하고, 우체국 바깥까지 트럭들이 수 킬로미터 줄을 서며 우체국이 완전 마비됩니다.

이것이 바로 Apache Kafka, AWS SQS, RabbitMQ 등 메시지 큐 시스템에서 가장 악명 높은 **독약 알약(Poison Pill)**과 **헤드 오브 라인 블로킹(Head-of-Line Blocking)** 참사입니다.

## 2. 왜 일반적인 에러 처리로는 해결할 수 없는가?

### 2.1 일시적 장애(Transient Error) vs 영구적 결함(Poison Pill)
네트워크 순단이나 DB 락 타임아웃 같은 **일시적 장애**는 몇 초 뒤 재시도하면 대부분 성공합니다.  
하지만 **독약 메시지**는 다음과 같은 영구적 결함을 내포하고 있습니다:
- **역직렬화(Deserialization) 실패**: 깨진 JSON, 호환되지 않는 Protobuf/Avro 스키마
- **데이터 무결성 위반**: 필수 필드 누락(`null`), 외래키 위반, 0으로 나누기
- **비즈니스 로직 예외**: 미지원 통화 코드, 존재하지 않는 상품 ID

이러한 메시지는 100만 번을 다시 시도해도 **영원히 100% 실패**합니다.

### 2.2 메시지 큐의 엄격한 순서 보장과 오프셋 커밋(Offset Commit)의 함정
메시지 큐(Kafka 파티션, SQS FIFO 등)는 메시지의 엄격한 순차 처리를 보장합니다.  
컨슈머가 메시지를 성공적으로 처리해야만 오프셋(Offset)을 다음 번호로 전진(Commit)시킵니다.  
만약 메시지 처리에 실패하여 트랜잭션이 롤백되면:
1. 오프셋이 커밋되지 않음 (NACK / Uncommitted).
2. 컨슈머는 다음 폴링(Poll) 때 **똑같은 오프셋의 실패한 메시지를 다시 읽어옴**.
3. 다시 예외 발생 $\to$ 컨슈머 크래시(CrashLoopBackOff) $\to$ 재시작 후 다시 읽어옴...
4. **결과**: 뒤에 쌓인 수백만 건의 정상 메시지들이 단 한 걸음도 전진하지 못하는 **영구 컨슈머 랙(Consumer Lag 폭발)** 발생!

## 3. 데드 레터 큐(Dead Letter Queue, DLQ) 아키텍처

AWS, Netflix, Uber 등 글로벌 테크 기업들은 이 문제를 **Dead Letter Queue (DLQ, 사장된 편지함 / 격리 병동)** 패턴으로 해결합니다.

```
[메인 메시지 큐 (Main Queue)]
 ──> [정상 메시지 1] ──> [독약 메시지 (Poison)] ──> [정상 메시지 2] ──> [정상 메시지 3] ──>
                               │
                      (최대 3회 실패 시 격리)
                               │
                               ▼
               ┌───────────────────────────────┐
               │   Dead Letter Queue (DLQ)     │
               │   - 에러 원인/스택트레이스 기록  │
               │   - 알림(Slack/PagerDuty) 발송   │
               └───────────────────────────────┘
                               │
                      (버그 수정 후 재주입)
                               │
                               ▼
                     [Redrive / Replay 파이프라인]
```

### 3.1 Redrive Policy (재구동 정책)
1. **`max_retries` (최대 재시도 허용 횟수)**:
   - 메시지마다 실패 횟수(`retries`)를 카운트합니다.
   - 일시적인 네트워크 순단에 대비해 $N$회까지는 재시도를 허용합니다.
2. **격리(Quarantine) 및 오프셋 전진**:
   - 재시도 횟수가 `max_retries`에 도달하면, 더 이상 메인 큐를 붙잡고 있지 않고 메시지를 **DLQ로 전송(오프로딩)**합니다.
   - 메인 큐에는 **성공(ACK / Commit)**을 보고하여 오프셋을 즉시 다음 정상 메시지로 넘깁니다!
   - 이로써 HOL 블로킹이 해소되고 뒤의 10만 건 정상 메시지들이 즉시 지연 없이 처리됩니다.
3. **진단 메타데이터 주입 (Metadata Injection)**:
   - DLQ로 보낼 때 원본 페이로드와 함께 `x-death-reason`, `failed-at-timestamp`, `exception-class`, `original-topic` 등의 디버깅 정보를 첨부합니다.
4. **Redrive (Replay) 파이프라인**:
   - 엔지니어가 버그를 픽스하거나 스키마를 패치한 후, DLQ에 보관되어 있던 메시지들을 메인 큐로 안전하게 재주입(Redrive)하여 **단 1건의 데이터 유실도 없이(Zero Data Loss)** 복구합니다.

## 4. 실무 프로덕션 권장 수칙

1. **알림 및 모니터링 (Alerting on DLQ Ingress)**:
   - DLQ에 메시지가 1건이라도 인입되면 즉시 개발팀 Slack이나 PagerDuty로 경보를 울려야 합니다. DLQ는 쓰레기통이 아니라 '중환자실'입니다.
2. **DLQ 메시지 보존 기한 (Retention Period)**:
   - 버그 분석 및 패치 시간을 확보하기 위해 DLQ의 TTL은 메인 큐보다 훨씬 길게(예: 14일) 설정해야 합니다.
3. **지수 백오프와 결합**:
   - 재시도 시 즉시 재시도하지 않고 1초, 2초, 4초 지수 백오프(Exponential Backoff)를 두어 다운스트림 DB나 외부 API의 부하를 완화해야 합니다.
