# [분산 트랜잭션 아키텍처: 2PC의 한계와 사가 패턴(Saga Pattern) 및 보상 트랜잭션]

## 1. 모놀리스에서 MSA로: ACID의 종말과 BASE의 등장

단일 데이터베이스에서는 RDBMS의 강력한 트랜잭션 엔진이 **원자성(Atomicity)**을 보장했습니다.
하지만 마이크로서비스 아키텍처(MSA)에서는 각 서비스가 독립적인 데이터베이스(Database-per-Service)를 소유하므로, 여러 서비스에 걸친 비즈니스 트랜잭션에서 전통적인 로컬 ACID는 작동하지 않습니다.

대신 분산 시스템에서는 CAP 정리와 **BASE 원칙 (Basically Available, Soft state, Eventual consistency - 최종 일관성)**을 따르게 됩니다.

---

## 2. 왜 2PC (Two-Phase Commit)를 실무에서 쓰지 않는가?

분산 원자성을 달성하는 고전적인 컴퓨터 과학 프로토콜로 **2단계 커밋(2PC, Two-Phase Commit)**이 있습니다:
1. **Prepare Phase**: 코디네이터가 모든 참여 노드에게 "커밋할 준비가 되었는가?" 묻고, 모든 노드는 리소스 락을 잡은 채 준비 완료 응답.
2. **Commit Phase**: 모든 노드가 OK를 보내면 일제히 영구 커밋.

### 실무 마이크로서비스에서 2PC가 기피되는 이유:
1. **블로킹 락과 가용성 파괴 (Blocking Coordinator)**:
   - Prepare 단계부터 Commit 단계까지 모든 데이터베이스 행 락(Row Lock)이 풀리지 않고 유지됩니다.
   - 코디네이터가 네트워크 지연이나 장애로 멈추면 전사 시스템의 DB 락이 영구 동결됩니다.
2. **이기종 NoSQL 및 메시지 큐 미지원**:
   - Kafka, Redis, MongoDB, DynamoDB 등 최신 데이터 스토어는 XA/2PC 인터페이스를 지원하지 않습니다.
3. **성능 병목**:
   - 네트워크 RTT가 수십 ms에 달하는 클라우드 환경에서 2PC의 처리율(TPS)은 단일 DB 대비 1/100 이하로 곤두박질칩니다.

## 3. 해결책: 사가 패턴 (Saga Pattern)

1987년 헥터 가르시아-몰리나(Hector Garcia-Molina) 교수가 제안한 **사가(Saga)**는 분산 트랜잭션을 **여러 개의 독립적인 로컬 트랜잭션($T_1, T_2, \dots, T_n$)의 연속된 체인**으로 분할하여 실행하는 패턴입니다.

### 핵심: 보상 트랜잭션 (Compensating Transaction)
- 각 로컬 트랜잭션 $T_i$는 즉시 커밋되어 락을 오래 쥐지 않습니다.
- 만약 $T_k$ 단계에서 비즈니스 검증 실패나 시스템 오류가 발생하면, 시스템은 **이미 커밋 완료된 이전 단계들($T_{k-1}, \dots, T_1$)의 비즈니스 효과를 무효화하는 보상 트랜잭션($C_{k-1}, \dots, C_1$)을 역순으로 실행**하여 결과적인 최종 일관성(Eventual Consistency)을 달성합니다.

| 단계 | 전진 트랜잭션 ($T$) | 실패 시 보상 트랜잭션 ($C$) |
|:---:|:---|:---|
| 1 | 주문 생성 (`PENDING`) | 주문 상태 변경 (`CANCELLED`) |
| 2 | 고객 카드 결제 승인 | 카드 결제 승인 취소 (환불) |
| 3 | 창고 재고 차감 | 재고 원상 복구 (재고 +1) |
| 4 | 택배 배송 접수 | 택배 배송 접수 취소 |

## 4. 사가 구현의 두 가지 접근법: 코레오그래피 vs 오케스트레이션

### (1) 코레오그래피 (Choreography - 이벤트 기반)
- 중앙 관리자 없이, 서비스들이 도메인 이벤트(Kafka Topic)를 발행하고 서로를 구독하여 반응합니다.
- **장점**: 단순하고 서비스 간 결합도가 낮음.
- **단점**: 트랜잭션이 복잡해지면 "누가 이벤트를 받고 어디로 가는지" 파악하기 어려운 스파게티 의존성이 생김.

### (2) 오케스트레이션 (Orchestration - 중앙 조율자)
- **사가 오케스트레이터(Saga Orchestrator)**라는 전담 상태 머신(State Machine)이 서비스들에게 명령(Command)을 내리고 응답을 수집합니다.
- (예: Temporal, Camunda, AWS Step Functions)
- **장점**:
  1. 전체 분산 워크플로우의 상태(State)와 진행률을 한눈에 추적 및 모니터링 가능.
  2. 장애 발생 시 보상 트랜잭션의 역순 실행을 오케스트레이터가 완벽히 통제.
  3. 순환 의존성(Cyclic Dependency) 제거.
