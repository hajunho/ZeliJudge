# [배경 이론] 실시간 채팅에 Redis Pub/Sub 썼더니 왜 메시지가 몽땅 증발하고 서버가 터져요?!: Redis Pub/Sub의 소방호수 함정(Buffer Overflow) vs Redis Streams 신뢰성 큐(PEL & XACK)

## 1. 현실 비유: 확성기 방송 vs 등기우편 장부

마을에 중요한 공지사항(메시지)을 전달해야 합니다.

- **Redis Pub/Sub (확성기 방송 / 소방호수)**:
  - 이장이 확성기를 켜고 소리를 지릅니다: *"지금 마을회관으로 모이세요!"*
  - 그 순간 **귀를 열고 듣고 있던 주민(온라인 구독자)**만 소리를 듣습니다.
  - 마침 화장실에 가 있거나 잠시 잠이 들었던 주민(오프라인/네트워크 순단)은 방송을 영영 듣지 못합니다. 확성기 소리는 공중으로 흩어져 **영구 증발**합니다!
  - 게다가 이장이 소방호수로 물을 뿜듯 분당 1,000마디씩 말을 쏟아내는데, 한 어르신(Slow Consumer)이 말을 다 알아듣지 못하고 귀가 막히면(출력 버퍼 포화), 이장은 *"너 때문에 방송 지연된다!"*며 그 어르신의 집 전선을 가위로 싹둑 잘라버립니다(`CLIENT_OUTPUT_BUFFER_LIMIT_EXCEEDED` 강제 퇴출).

- **Redis Streams (등기우편 장부 / Append-Only Log)**:
  - 이장이 마을 우체국에 **날짜와 일련번호가 적힌 공식 장부(Stream Log)**를 만듭니다.
  - 주민이 화장실에 가 있든 며칠 여행을 떠났든 상관없습니다. 장부에 영구히 기록되어 있으므로 언제든 돌아와서 **"내가 지난번에 4번까지 읽었으니 5번부터 읽을게!"** 하고 오프셋을 이어서 읽을 수 있습니다.
  - 집배원(워커)이 편지를 배달하러 가져가면 장부의 **보류 목록(PEL, Pending Entries List)**에 체크됩니다.
  - 배달을 마치면 주민에게 서명(`XACK`)을 받아 장부에서 지웁니다.
  - 만약 집배원이 배달 도중 오토바이 사고(워커 프로세스 크래시)를 당해 30분이 지나도록 감감무소식이라면? 다른 건강한 집배원이 장부를 보고 **"어? 이 편지 배달 안 됐네? 내가 대신 배달할게!"(`XCLAIM`)** 하고 편지를 가로채 배달을 100% 완수합니다!

## 2. 왜 Redis Pub/Sub을 신뢰성 큐로 쓰면 망하는가?

수많은 주니어/비전공자 개발자들이 "실시간 채팅"이나 "비동기 작업 큐"를 만들 때 이름이 그럴싸해 보이는 `Redis Pub/Sub`을 무지성으로 도입했다가 서비스 오픈 첫날 대참사를 겪습니다.

### 1) At-Most-Once (최대 1회 전송 = 유실 가능)
- Pub/Sub은 메시지를 메모리나 디스크 어디에도 보관하지 않습니다.
- 발행 시점에 네트워크 지연, 배포로 인한 서버 재시작 등으로 구독자가 연결되어 있지 않았다면, 그 메시지는 **우주에서 영구히 사라집니다.**

### 2) 느린 소비자의 저주와 강제 퇴출 (`client-output-buffer-limit`)
- Redis는 싱글 스레드 이벤트 루프로 동작하므로, 특정 구독자가 메시지를 느리게 읽는다고 해서 Redis 전체가 멈춰 기다려줄 수 없습니다.
- 따라서 각 구독자 소켓마다 메모리 송신 버퍼를 둡니다.
- 만약 구독자가 무거운 DB 작업 등으로 메시지 소비를 지체하여 버퍼 한도(예: 32MB)를 넘기면, Redis는 메모리 고갈을 막기 위해 **해당 클라이언트 연결을 가차 없이 끊어버립니다(Kill/Evict)!**

## 3. Redis Streams의 구원: 고성능 + 무유실 분산 큐

Redis 5.0에서 도입된 **Redis Streams**는 Apache Kafka의 장점(Log 기반 보존, 오프셋, 컨슈머 그룹)을 Redis 특유의 초고속 인메모리 성능과 완벽히 결합했습니다.

### 1) 시간 기반 고유 ID와 지속성 (Append-Only Log)
- 모든 메시지는 `밀리초타임스탬프-순번` (예: `1526972795262-0`) 형태의 단조 증가 ID를 부여받고 스트림에 안전하게 추가됩니다.
- 클라이언트는 언제든지 `XREAD stream 0-0`을 통해 과거 메시지를 처음부터 다시 읽거나(Replay), 중단된 지점부터 이어 읽을 수 있습니다.

### 2) 컨슈머 그룹 (Consumer Group)과 부하 분산
- 동일한 그룹에 속한 여러 워커(컨슈머)가 단일 스트림의 메시지를 겹치지 않게 병렬로 분산 소비(`XREADGROUP`)합니다.

### 3) PEL (Pending Entries List)과 XACK, 그리고 XCLAIM의 장애 복구
```
[Redis Streams의 신뢰성 보장 흐름]
1. 프로듀서: XADD mystream * message "결제요청"
2. 워커 1: XREADGROUP group1 worker1 count 1
   -> 메시지가 워커 1에게 전달됨과 동시에 그룹의 PEL(보류 목록)에 등록!
3-A. 정상 처리 시:
   -> 워커 1이 결제 처리 후 `XACK mystream group1 <msg_id>` 전송!
   -> PEL에서 메시지가 삭제되며 완전 처리 완료!
3-B. 비정상 크래시 시:
   -> 워커 1의 서버가 다운되어 XACK를 영영 보내지 못함!
   -> 관리자/워커 2가 `XPENDING`을 조회하여 오랫동안 방치된 고아 메시지 발견!
   -> 워커 2가 `XCLAIM mystream group1 worker2 min_idle_time <msg_id>`로 소유권 탈취!
   -> 메시지 유실 0%, 완벽한 결제 처리 완수!
```

이 메커니즘 덕분에 Redis Streams는 카프카보다 훨씬 가볍고 빠르면서도, 결제나 주문 같은 미션 크리티컬한 시스템에서도 단 한 건의 메시지도 유실 없이 100% 안전하게 처리할 수 있습니다.\n
