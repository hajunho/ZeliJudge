# HTTP/2 다중화와 L4 vs L7 gRPC 로드밸런싱의 비극

> "마이크로서비스 간 REST API 지연을 줄이기 위해 초고속 바이너리 프로토콜인 **gRPC (HTTP/2 기반)**를 전격 도입했습니다.  
> 쿠버네티스에 백엔드 서버 파드를 4대 띄우고 기본 ClusterIP 서비스(L4 로드밸런서)로 묶은 뒤 성능 테스트를 돌렸는데...  
> **Server 01 혼자 CPU 100%를 찍고 OOM으로 사망했고, 나머지 Server 02, 03, 04는 CPU 0%로 완벽하게 놀고 있었습니다!**  
> 똑같은 라운드로빈 로드밸런서 뒤에 있는데, 도대체 왜 트래픽이 1대에만 100% 몰빵된 걸까요?!"

---

## 1. gRPC와 HTTP/2의 혁명: 단일 TCP 다중화(Multiplexing)

전통적인 **HTTP/1.1 REST API** 환경에서는 브라우저나 클라이언트가 서버로 요청을 보낼 때:
1. 요청마다 새로운 TCP 3-Way Handshake를 맺거나,
2. Keep-Alive 커넥션 풀을 열어 여러 개의 독립적인 TCP 소켓(예: 10~20개 소켓)을 병렬로 운용했습니다.

하지만 **HTTP/2를 기반으로 동작하는 gRPC**는 연결 맺기 비용을 극단적으로 줄이기 위해 **단일 장기 지속 TCP 연결(Single Long-Lived TCP Connection)** 아키텍처를 채택했습니다.

```
[HTTP/1.1 REST 통신]
Client  ====== TCP Connection 1 (Req 1 -> Res 1) ======> Server A
Client  ====== TCP Connection 2 (Req 2 -> Res 2) ======> Server B
Client  ====== TCP Connection 3 (Req 3 -> Res 3) ======> Server C

[HTTP/2 gRPC 통신]
Client  ====== 단 1개의 TCP Connection =================> Server A (영구 핀닝!)
               ├── Stream 1 (RPC Call #1)
               ├── Stream 2 (RPC Call #2)
               ├── Stream 3 (RPC Call #3)
               └── Stream 10000 (RPC Call #10000)
```

클라이언트는 서버와 최초에 TCP 연결을 단 1개만 맺고, 그 연결 위에 **수천 개의 가상 양방향 스트림(Stream)**을 띄워 데이터를 프레임(Frame) 단위로 쪼개어 동시에 주고받습니다.  
이로 인해 TCP 핸드셰이크 지연과 TLS 협상 비용이 사라져 엄청난 고성능을 냅니다.

## 2. L4 로드밸런서의 치명적 맹점: "커넥션 밸런싱" vs "요청 밸런싱"

문제가 발생하는 지점은 바로 **L4(전송 계층) 로드밸런서**입니다.
쿠버네티스의 기본 `ClusterIP Service` (iptables/IPVS 모드), AWS NLB(Network Load Balancer), Linux LVS 등은 모두 **L4 로드밸런서**입니다.

### L4 로드밸런서의 동작 방식
L4 로드밸런서는 TCP 패킷 헤더의 `IP:Port`만 봅니다.
- 클라이언트가 최초로 TCP 3-Way Handshake(`SYN` 패킷)를 보낼 때, L4 로드밸런서는 백엔드 서버 목록 중 하나(예: `Server 01`)를 골라 연결을 매핑합니다.
- **그 후 데이터 교환 단계(`ACK`, `PSH`)에서는 L4가 패킷의 내용을 들여다보지 않고, 처음에 정한 `Server 01`로 바이트 스트림을 그대로 전달하기만 합니다.**

### gRPC를 만났을 때 터지는 대참사 (Connection Pinning)
1. 클라이언트 Pod가 부팅되면서 gRPC 채널을 초기화합니다.
2. L4 로드밸런서로 `SYN` 패킷 1개를 보냅니다.
3. L4는 이를 `Server 01`에 연결해 줍니다.
4. **끝입니다!** 이후 클라이언트는 이 단 하나의 TCP 연결을 끊지 않고 유지합니다.
5. 클라이언트에서 초당 1,000건, 10,000건의 gRPC RPC 요청(Stream)을 쏟아붓습니다.
6. 하지만 L4 로드밸런서 입장에서는 **"어? 새로운 TCP 연결 요청(SYN)은 안 들어왔고, 아까 맺어진 커넥션에서 패킷만 계속 흐르네?"**라고 판단하여 10,000건의 요청을 **100% 전부 `Server 01`로만 전송**합니다!
7. 결과: `Server 01`은 과부하로 CPU 100% 및 큐 포화로 사망하고, `Server 02, 03, 04`는 할 일이 없어 하품만 하게 됩니다!

## 3. 세 가지 실무 구원 아키텍처

이 문제를 해결하기 위해서는 **"TCP 연결"이 아니라 HTTP/2 "스트림(요청)" 단위로 부하를 분산**해야 합니다.

```
+-------------------------------------------------------------------------------+
|                            gRPC 부하 분산 3대 해법                            |
+-----------------------+-----------------------+-------------------------------+
| 1. L7 프록시 분산     | 2. 클라이언트 사이드  | 3. Max Connection Age         |
| (Envoy / ALB)         | (gRPC Subchannel RR)  | (주기적 재연결 완충책)        |
+-----------------------+-----------------------+-------------------------------+
| 프록시가 HTTP/2 스트림| 클라이언트가 모든 파드| 서버가 GOAWAY로 연결 종료     |
| 디코딩 후 파드별 라운 | 와 서브채널 맺고 직접 | 클라이언트가 L4 통해 재연결   |
| 드로빈 전송           | 스트림 분산           | 맺으며 다음 서버로 순환       |
+-----------------------+-----------------------+-------------------------------+
```

### (1) L7 프록시 로드밸런싱 (Proxy Load Balancing)
- **원리**: 클라이언트와 백엔드 서버 사이에 **Envoy Proxy**, **AWS ALB**, 또는 **Nginx(gRPC 모듈)** 같은 L7 리버스 프록시를 배치합니다.
- **동작**:
  - 프록시가 클라이언트와의 HTTP/2 연결을 종단(Terminate)합니다.
  - 프록시 내부에서 들어오는 각각의 gRPC 스트림 프레임을 파싱하여, 백엔드 서버 풀(`Server 01, 02, 03, 04`)로 스트림별 라운드로빈(`ROUND_ROBIN`) 또는 최소 활성 요청(`LEAST_CONCURRENT`) 방식으로 분산합니다.
- **장점**: 클라이언트 코드 수정이 전혀 필요 없고, 쿠버네티스 Istio/Envoy 서비스 메시(Service Mesh)를 쓰면 자동으로 해결됩니다.
- **단점**: 중간에 프록시 홉(Hop)이 추가되어 수 밀리초의 레이턴시 오버헤드와 프록시 서버 CPU/메모리 비용이 발생합니다.

---

### (2) gRPC 클라이언트 사이드 로드밸런싱 (Client-Side Load Balancing)
- **원리**: 중간 프록시 없이, 클라이언트 애플리케이션의 gRPC 라이브러리 자체가 백엔드 서버들의 주소를 모두 알고 직접 분산합니다.
- **동작**:
  - 쿠버네티스 **Headless Service** (`clusterIP: None`)나 Consul, DNS SRV 레코드를 통해 백엔드 파드 4개의 개별 IP(`10.0.1.10`, `10.0.1.11`, `10.0.1.12`, `10.0.1.13`)를 모두 조회(Name Resolution)합니다.
  - 클라이언트의 gRPC 채널은 각 파드와 **1:1로 독립적인 TCP 서브채널(Subchannel)**을 4개 연결합니다.
  - 클라이언트 내부의 `round_robin` 로드밸런서 정책이 동작하여, 애플리케이션이 `stub.call()`을 날릴 때마다 Subchannel 1 $	o$ 2 $	o$ 3 $	o$ 4로 번갈아가며 요청(Stream)을 쏩니다!
- **장점**: 중간 프록시 홉이 전혀 없어 **가장 빠른 극상의 속도(Ultra Low Latency)**와 0의 프록시 인프라 비용을 자랑합니다.
- **단점**: 클라이언트가 서비스 디스커버리 로직을 내장해야 하며, 백엔드 파드가 1,000대면 클라이언트 1대가 1,000개의 TCP 소켓을 유지해야 하므로 대규모 클러스터에서는 연결 폭발(Connection Explosion)을 주의해야 합니다.

---

### (3) 서버 주기적 커넥션 에이징: `grpc.max_connection_age_ms` (GOAWAY 재연결)
- **원리**: L4 환경을 당장 바꿀 수 없을 때 적용하는 서버 측 완화책입니다.
- **동작**:
  - 백엔드 서버 설정에 `max_connection_age_ms: 60000` (예: 1분)을 줍니다.
  - 1분이 지나면 서버는 클라이언트에 **`HTTP/2 GOAWAY`** 프레임을 보내 "이 연결은 곧 닫힐 예정이니 더 이상 새 스트림을 열지 말고, 현재 진행 중인 스트림만 마치고 연결을 끊으라"고 통보합니다.
  - 클라이언트는 기존 연결을 Graceful하게 닫고, L4 로드밸런서로 **새로운 TCP 3-Way Handshake(SYN)**를 겁니다.
  - 이때 L4 로드밸런서가 라운드로빈으로 다음 서버(`Server 02`)로 새 연결을 맺어줍니다!
- **장점**: L4 인프라나 클라이언트 코드를 갈아엎지 않고도 트래픽이 한 서버에 영구 핀닝되는 현상을 크게 완화할 수 있습니다.

## 4. 로드 불균형 지수 (Load Imbalance Ratio)

부하가 얼마나 심각하게 쏠렸는지를 정량화하기 위해 다음 불균형 지수를 사용합니다:

$$	ext{Imbalance Ratio} = rac{\max(	ext{Received}) - \min(	ext{Received})}{\max(	ext{Avg}(	ext{Received}), 1.0)}$$

- **`SERVER_OVERLOAD_HOTSPOT_FAILURE`**: 특정 서버에 부하가 집중되어 수용 한도(`max_capacity`)를 초과하고 요청이 거절(`REJECTED_OVERLOADED`)된 상태.
- **`SEVERE_LOAD_IMBALANCE`**: 거절은 없었으나 불균형 지수가 $1.0$ 이상으로 극심하게 한 서버로 쏠린 상태 (L4 환경에서 단일 클라이언트 유입 시 전형적).
- **`MODERATE_LOAD_IMBALANCE`**: 불균형 지수가 $0.5$ 이상 $1.0$ 미만인 상태.
- **`BALANCED`**: 불균형 지수가 $0.5$ 미만으로 모든 서버에 고르게 요청이 분산된 상태.
