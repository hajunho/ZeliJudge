# [배경 이론] 리눅스 CFS 스케줄러와 CPU 스로틀링의 저주 (Linux CFS Quota & Throttling)

## 1. 현실 비유: 매달 1일 충전되는 200분 통화 요금제와 8명의 비서

회사에서 여러분에게 **"월 200분 무료 통화가 제공되는 스마트폰 요금제"**를 지급했다고 가정해 봅시다.  
한 달(CFS 주기, Period)은 100일로 환산되고, 매월 1일에 200분의 통화량(CFS 쿼터, Quota = 2.0 코어)이 충전됩니다.

- **상황 1: 혼자서 전화할 때 (스레드 1개)**
  - 100일 동안 하루에 1분씩 총 100분을 썼습니다.
  - 통화량이 100분이나 남았으므로 한 번도 끊기지 않고 쾌적하게 사용합니다.

- **상황 2: 8명의 비서를 고용해서 동시에 전화할 때 (멀티스레드 8개)**
  - 월초(1일)에 고객 문의가 폭주하여 8명의 비서가 동시에 수화기를 들고 통화를 시작했습니다.
  - 8명이 동시에 통화하므로, **1시간에 8시간분의 무료 통화가 빛의 속도로 소진**됩니다!
  - 결국 $200 \div 8 = 25$일 만에 한 달 치 무료 통화 200분이 0분으로 바닥나 버렸습니다!
  - 통신사(리눅스 커널)는 26일 아침이 되자마자 **전화선을 강제로 끊어버립니다(CPU Throttling)**.
  - 나머지 75일(26일~100일) 동안 8명의 비서는 아무 일도 하지 못하고 멍하니 손가락만 빨고 있어야 합니다.
  - 전화는 먹통이 되고, 고객들은 "왜 응답이 없냐"며 항의(타임아웃, 504 Gateway Timeout)를 쏟아냅니다.
  - 101일(다음 달 1일)이 되어서야 통화량이 재충전되어 전화가 복구됩니다.

> **충격적인 사실**: 100일 동안 쓴 총 통화량은 고작 200분이므로, 한 달 전체로 보면 **평균 통화량 사용률은 20%에 불과**했습니다!  
> 평균 CPU 사용률이 20%인데도 75%의 시간 동안 서버가 얼어붙어 있었던 것입니다.

## 2. 쿠버네티스와 리눅스 CFS (Completely Fair Scheduler)의 대역폭 제어

쿠버네티스에서 파드(Pod)에 `resources.limits.cpu: "2"`를 설정하면, 리눅스 커널은 이를 내부적으로 Cgroup CFS 대역폭 제어 파라미터로 변환합니다.

```
cpu.cfs_period_us = 100000   (주기: 100,000 us = 100ms)
cpu.cfs_quota_us  = 200000   (할당량: 2코어 × 100ms = 200,000 us = 200ms)
```

리눅스 커널의 CFS 스케줄러는 **100ms(Period)마다 카운터를 리셋**하며 다음 규칙으로 컨테이너를 감시합니다:

```
[100ms 주기(Period) 타임라인]
0ms                                     25ms                                100ms
├────────────────────────────────────────┼───────────────────────────────────┤
│   8개 스레드 동시 실행                   │   모든 스레드 강제 동결(Freeze)       │
│   (총 200ms CPU 쿼터 소진)               │   (CPU Throttled! 응답 불가)        │
│   Rate: 8us CPU / 1us Wall-clock       │   남은 75ms 동안 CPU 사용 불가        │
└────────────────────────────────────────┴───────────────────────────────────┘
                                         ▲
                                    쿼터 조기 고갈!
```

1. 매 100ms 주기 시작 시, 컨테이너에 200ms의 CPU 런타임 쿼터가 주어집니다.
2. 컨테이너 내부의 모든 스레드가 CPU를 사용할 때마다 쿼터에서 실시간으로 차감됩니다.
3. **만약 주기 중간에 쿼터가 0이 되면?**
   - 커널은 해당 컨테이너 내부의 **모든 스레드를 즉시 스케줄링 큐에서 제외하고 강제 동결(Throttle)**시킵니다.
   - 주기가 끝날 때까지 단 1마이크로초의 CPU도 할당받지 못합니다.
   - 이것이 바로 **평균 CPU 사용률이 낮은데도 p99 응답 지연이 100ms씩 튀는 주원인**입니다!

## 3. 실무 지표: `/sys/fs/cgroup/cpu/cpu.stat`

리눅스 커널은 CPU 스로틀링 통계를 Cgroup 가상 파일 시스템에 실시간 기록합니다:

- `nr_periods`: 지금까지 경과한 총 CFS 주기의 수
- `nr_throttled`: 쿼터 고갈로 인해 스로틀링이 발생한 주기의 수
- `throttled_time`: 스레드들이 쿼터 고갈로 멈춰서 기다린 누적 시간 (us / ns)
- **스로틀링 비율**: $\text{Throttled Rate} = \frac{\text{nr\_throttled}}{\text{nr\_periods}} \times 100\%$

---

## 4. 리눅스 5.14+의 구원 투수: CFS Burst (`cpu.cfs_burst_us`)

이 끔찍한 조기 고갈 문제를 완화하기 위해 리눅스 5.14 커널부터 **CFS Burst** 기능이 도입되었습니다.

- **원리**: 이전 주기에서 다 쓰지 못하고 남은 쿼터(`unused_quota`)를 버리지 않고 **버스트 풀(Burst Pool, 최대 `burst_us`까지)**에 저축해 둡니다.
- 다음 주기에 트래픽 버스트가 발생하여 쿼터를 초과하더라도, 저축해 둔 버스트 풀을 끌어다 써서 **스로틀링 없이 일시적인 스파이크를 부드럽게 넘길 수 있습니다**.

---

## 5. 실무 엔지니어링 권장안

1. **스레드 풀 크기 튜닝**: CPU 리밋이 2코어라면 톰캣/워커 스레드 풀을 200개로 두지 말고, 코어 수에 맞게 제한합니다.
2. **K8s CPU Limit 재검토**: 레이턴시가 극도로 민감한 API 서버는 `limits.cpu`를 제거하고 `requests.cpu`만 설정하거나(Guaranteed/Burstable), 리밋을 충분히 넉넉하게 잡습니다.
3. **CFS Burst 활성화**: 최신 커널 환경에서 버스트 버퍼를 켜서 순간 트래픽 스파이크를 흡수합니다.
