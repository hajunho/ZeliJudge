# Raft 합의 알고리즘과 리더 리스(Leader Lease): 선형성 보장, 클록 드리프트와 Stale Read 방어 아키텍처

## 1. 개요: 분산 시스템의 선형성(Linearizability)과 읽기 경로의 딜레마

현대 분산 데이터베이스(Spanner, CockroachDB, TiKV, etcd)는 일관성 모델 중 가장 강력한 **선형성(Linearizability, Strong Consistency)**을 제공해야 합니다.
선형성이란 단일 시스템 이미지(Single-System Image) 모델로서, **"어떤 쓰기(Write) 연산이 성공적으로 완료(Commit)된 이후에 시작된 모든 읽기(Read) 연산은 반드시 그 쓰기 값 또는 그 이후에 갱신된 최신 값을 반환해야 한다"**는 실시간 인과율(Real-Time Precedence)을 요구합니다.

Raft 합의 알고리즘에서 모든 데이터 쓰기는 반드시 과반수(Quorum, $\lfloor N/2 \rfloor + 1$) 노드의 복제와 커밋을 거칩니다.
그러나 **"읽기(Read) 연산은 어떻게 처리해야 하는가?"**라는 질문은 분산 시스템 엔지니어링에서 가장 까다로운 트레이드오프를 낳습니다.

## 2. 분리 리더(Partitioned Leader)와 나이브 로컬 읽기의 붕괴

가장 직관적인 방법은 "리더 노드는 항상 최신 상태 머신을 쥐고 있으므로, 로컬 메모리에서 즉시 읽어서 클라이언트에게 응답하는 것"입니다.
하지만 이는 비대칭 네트워크 단절(Asymmetric Network Partition) 상황에서 **치명적인 선형성 위반(Stale Read)**을 초래합니다:

```
[클라이언트 A] -------- Write(x = 100) --------> [구 리더: Node 1] (네트워크 고립!)
                                                        | (과반수 통신 불가)
[과반수 노드: Node 2, 3] (Node 1 타임아웃 감지)          |
       |                                                |
       v (Term 2 선출 완료)                             |
[신규 리더: Node 2] <--- Write(x = 200) 커밋!            |
       |                                                |
[클라이언트 B] -------- Read(x) ------------------------+
       |
       v (Node 1이 로컬에서 구 값 응답!)
  결과: x = 100  <---- [대재앙: x = 200이 이미 완료되었는데 100이 반환됨!]
```

구 리더(Node 1)는 자신이 네트워크 파티션으로 인해 폐위되었다는 사실을 모른 채, 클라이언트의 조회 요청에 로컬의 낡은 데이터(Stale Data)를 반환하게 됩니다.

## 3. 전통적 해법: ReadIndex 프로토콜의 한계

Diego Ongaro 박사의 Raft 원논문(Section 6.4)은 이를 해결하기 위해 **ReadIndex** 프로토콜을 제시했습니다:

1. 리더가 읽기 요청을 받으면 현재 자신의 커밋 인덱스를 `read_index`로 기록합니다.
2. 리더가 자신이 여전히 정당한 리더인지 확인하기 위해 과반수 팔로워에게 빈 하트비트(Heartbeat `AppendEntries`)를 전송합니다.
3. 과반수의 ACK를 받아 리더십이 재확인되면, 상태 머신이 `read_index`까지 적용(Apply)되기를 기다립니다.
4. 상태 머신에서 데이터를 읽어 클라이언트에게 반환합니다.

### ReadIndex의 치명적 단점: 네트워크 RTT 지연
ReadIndex는 선형성을 100% 보장하지만, **단 1건의 단순 조회 요청마다 데이터센터 내부 또는 대륙 간 왕복 지연시간(1 RTT, $15\sim50\,\text{ms}$)**이 무조건 발생합니다.
읽기 트래픽이 전체의 90% 이상을 차지하는 웹 서비스에서 모든 읽기에 네트워크 RTT를 지불하는 것은 엄청난 성능 저하입니다.

## 4. 리더 리스(Leader Lease)와 클록 드리프트(Clock Drift)의 역습

### 4.1 리더 리스 (Leader Lease) 원리
팔로워들이 리더에게 하트비트를 승인할 때, **"향후 $L$시간(예: $500\,\text{ms}$) 동안은 절대로 새로운 리더 선출 투표를 시작하지 않겠다"**는 약속(Lease)을 부여합니다.
리더는 리스가 유효한 기간 동안에는 새로운 리더가 선출될 수 없음을 수학적으로 확신할 수 있으므로, **과반수 하트비트 확인 없이 로컬 메모리에서 즉시 0ms 지연시간으로 읽기를 처리**할 수 있습니다.

### 4.2 물리 시계(Physical Clock)의 배신
문제는 컴퓨터의 물리 시계(Quartz Oscillator)가 결코 완벽하지 않다는 점입니다:
- **클록 드리프트 (Clock Drift)**: 서버 하드웨어의 온도 변화나 발진기 오차로 인해 하루에 수십~수백 밀리초씩 시계가 어긋납니다.
- **NTP 스텝 조정**: NTP 데몬이 시계를 동기화하는 과정에서 과거 시간으로 점프(Backward Step)할 수 있습니다.
- **가상화 정지 (Hypervisor / VM Freeze)**: 클라우드 환경에서 라이브 마이그레이션이나 호스트 CPU 경합으로 VM이 수백 밀리초 동안 일시 동결(Freeze)될 수 있습니다.
- **GC Stop-The-World (STW)**: Java/Go 런타임의 가비지 컬렉션으로 프로세스가 $500\,\text{ms}$ 동안 멈출 수 있습니다.

```
[Wallclock 시간축] 0ms -------------- 500ms -------------- 600ms
[팔로워 시계]     0ms -------------> 500ms (리스 만료!) -> 600ms (Node 2를 Term 2 새 리더로 선출!)
                                                            |
                                                            v (새 쓰기: x = 5000 커밋)
[구 리더 Node 1]
  - 400ms 시점에 시계가 느려져 150ms 뒤처짐 (Node 1의 체감 시간 = 450ms)
  - 600ms 벽시계 순간, Node 1의 시계는 고작 450ms를 가리킴!
  - Node 1: "내 시계는 450ms니까 500ms 리스가 아직 50ms나 남았군!"
  - 클라이언트 조회 시 로컬의 x = 1000 응답! (Stale Read 발생!)
```

## 5. 산업계의 선형성 사수 기법 (Spanner & TiKV Bounded Lease)

### 5.1 엄격한 단조 시계 사용 (`CLOCK_MONOTONIC_RAW`)
절대로 `gettimeofday()`나 `System.currentTimeMillis()` 같은 시스템 월클록을 사용해서는 안 됩니다. 시스템 시간이 NTP에 의해 뒤로 점프할 수 있기 때문입니다. 리눅스에서는 NTP 스텝의 영향을 받지 않고 단조 증가만 하는 하드웨어 타임스탬프 카운터(`CLOCK_MONOTONIC_RAW`)를 사용해야 합니다.

### 5.2 클록 불확실성 상한선과 바운디드 리스 (Bounded Lease)
Google Spanner의 TrueTime API와 PingCAP TiKV는 클록의 최대 불확실성 드리프트 비율($\text{drift\_rate}$, 보통 $200\,\mu\text{s/sec}$)과 네트워크 지연 상한선($\epsilon$)을 정의합니다:

$$\text{안전 유효 리스 기간} = \text{Lease Duration} - (2 \times \epsilon)$$

1. **안전 마진 차감**: 팔로워가 $500\,\text{ms}$의 리스를 승인하더라도, 리더는 오차 안전 마진($2\epsilon = 100\,\text{ms}$)을 뺀 **$400\,\text{ms}$까지만 로컬 리스 읽기를 허용**합니다.
2. **선제적 ReadIndex 폴백**:
   - 로컬 시간이 $400\,\text{ms}$를 초과하거나, 하드웨어 클록 오차 경보가 발생하면, 리더는 즉시 로컬 읽기를 중단하고 **`ReadIndex` 쿼럼 하트비트 모드로 자동 전환**합니다.
3. 이로 인해 어떤 극단적인 클록 왜곡이나 리더 교체 레이스 컨디션에서도 **Stale Read 선형성 위반 확률을 물리적으로 0%**로 완벽히 차단합니다.
