# 동기식 로깅의 디스크 I/O 블로킹과 Log4j2 LMAX 디스럽터 링 버퍼

> "대형 프로모션 도중 결제 주문 흐름을 실시간으로 추적하기 위해 API 메서드 진입점에 `log.info(\"Order requested: {}\", orderId);`를 딱 한 줄 추가했습니다.  
> 로컬 노트북에서는 SSD 덕분에 몇 나노초 만에 넘어가길래 안심하고 배포했는데...  
> **배포 1분 만에 톰캣 워커 스레드 200개가 전멸하고 전사 API 응답 시간이 10초를 넘기며 504 Gateway Timeout 참사가 터졌습니다!**  
> 단지 로그 한 줄 찍었을 뿐인데, 도대체 왜 전사 시스템이 멈춰버린 걸까요?!"

---

## 1. 동기식 로거(Synchronous Logger)의 치명적 덫

우리가 흔히 쓰는 전통적인 `log.info(...)` (SLF4J + Logback 기본 설정)는 **동기식(Synchronous)**으로 동작합니다.

```
[클라이언트 요청] ──► [톰캣 워커 스레드]
                           │
                           │ 1. 비즈니스 로직 처리 (1ms)
                           │
                           ▼
                   log.info("결제 완료");
                           │
                           ├──► [Appender 공유 락(Lock) 획득 대기] 🔒 (스레드 간 락 경합!)
                           │
                           └──► [디스크 write() / fsync() 시스템 콜 호출] 💾
                                (디스크 I/O 지연: 10ms ~ 50ms 대기!)
                           │
                           ▼
                    [워커 스레드 블로킹 해제 및 응답 반환]
```

### 왜 서버가 멈출까?
1. **락 경합 (Lock Contention)**:  
   로그 파일(`app.log`)은 하나의 물리적 파일입니다. 여러 스레드가 동시에 파일에 글을 쓰면 내용이 뒤섞여 깨지므로, 로깅 프레임워크의 Appender는 내부적으로 **`synchronized` 또는 `ReentrantLock`**을 걸고 단 하나의 스레드만 파일에 쓰도록 통제합니다.
2. **디스크 I/O 블로킹 (Disk I/O Latency)**:  
   고객 요청을 빠르게 처리해야 하는 톰캣 워커 스레드가 비즈니스 로직 처리를 멈추고, **직접 OS 커널의 디스크 I/O 시스템 콜(`write`, `flush`)을 블로킹으로 대기**합니다.
3. **스레드 풀 고갈 (Thread Pool Starvation)**:  
   클라우드 가상화 환경(EBS, 클라우드 디스크)에서 순간적인 I/O 지연 스파이크(예: 20ms)가 발생하면, 초당 수천 건의 요청을 처리하던 200개의 워커 스레드가 전부 로그 찍는 줄에서 락을 쥔 채 멈춰 섭니다. 신규 요청을 받을 스레드가 단 1개도 남아있지 않아 시스템이 완전히 마비됩니다!

## 2. LMAX 디스럽터(Disruptor) 혁명: 락 프리 링 버퍼

이 비극을 해결하기 위해 2011년 영국의 금융 거래소 LMAX의 마틴 톰슨(Martin Thompson) 팀은 초당 600만 건의 주문을 마이크로초 단위로 처리하는 **LMAX Disruptor**를 발표했습니다.  
Apache Log4j2는 이 아키텍처를 도입하여 **세계에서 가장 빠른 비동기 로거(Async Logger)**를 완성했습니다.

```
[비즈니스 워커 스레드들] (Producer)
      │       │       │
      ▼       ▼       ▼
┌───────────────────────────────────────────────┐
│     LMAX Disruptor Lock-Free Ring Buffer      │  ◄── 락(Lock) 없는 원형 큐!
│  [Slot 0] [Slot 1] [Slot 2] ... [Slot N-1]   │      비트 연산: seq & (size - 1)
└──────────────────────┬────────────────────────┘
                       │ (배치 꺼내기)
                       ▼
         [단 1개의 백그라운드 I/O 전용 스레드] (Consumer)
                       │
                       ▼ (일괄 배치 디스크 플러시!)
             [disk.write(Batch 100건)]
```

### LMAX Disruptor의 4대 핵심 원리
1. **원형 링 버퍼 (Circular Ring Buffer)**:
   - 링 버퍼의 크기는 항상 **$2^N$ (2의 거듭제곱)**입니다.
   - 나눗셈/모듈로 연산(`%`) 대신 초고속 비트 마스킹 **`sequence & (buffer_size - 1)`**을 사용하여 나노초 단위로 슬롯 위치를 찾습니다.
2. **사전 메모리 할당 (Pre-allocated Event Objects)**:
   - 링 버퍼의 모든 슬롯 객체(`LogEvent`)를 서버 기동 시 미리 힙 메모리에 할당해 둡니다.
   - 로그를 찍을 때 새 객체를 `new`하지 않고 슬롯의 기존 객체에 데이터만 덮어쓰므로 **가비지 컬렉션(GC) 발생률이 0에 수렴**합니다.
3. **거짓 공유 방지 (Cache Line Padding)**:
   - CPU 캐시 라인(64바이트) 단위로 변수들이 서로 다른 코어에 의해 캐시 무효화(False Sharing)되지 않도록 더미 변수(Padding)를 채워 L1/L2 캐시 적중률을 극대화합니다.
4. **책임 분리와 배치 쓰기 (Batching Consumer)**:
   - 비즈니스 워커 스레드는 링 버퍼 슬롯에 데이터만 던져두고 **즉시 0ms 만에 복귀**하여 다음 고객 요청을 처리합니다.
   - 디스크 I/O는 백그라운드의 단 1개 전용 I/O 스레드가 담당하며, 링 버퍼에 쌓인 로그들을 50개, 100개씩 한 번에 묶어 **배치 디스크 쓰기(Batch Flush)**를 수행하므로 시스템 콜 횟수가 수십 분의 1로 급감합니다.

## 3. 버퍼 포화 시 백프레셔(Backpressure) 3대 정책

하지만 디스크 I/O 속도보다 훨씬 더 빠른 속도로 대규모 트래픽 버스트가 몰아치면, 링 버퍼(예: 크기 262,144개) 역시 가득 차는 **버퍼 포화(Buffer Saturation)** 상황에 직면합니다.  
Log4j2는 이때 시스템 붕괴를 막기 위해 세 가지 백프레셔 정책을 제공합니다:

```
+-----------------------------------------------------------------------------------+
| 링 버퍼 포화 시 백프레셔 정책 비교                                               |
+---------------------+-------------------------------+-----------------------------+
| 정책                | 동작 방식                     | 트레이드오프                |
+---------------------+-------------------------------+-----------------------------+
| 1. BLOCK            | 빈 슬롯이 생길 때까지 워커    | 로그 유실 0건 보장.         |
|                     | 스레드가 대기 (기본값)        | 하지만 동기 로거처럼 워커   |
|                     |                               | 스레드 지연 폭증 위험!      |
+---------------------+-------------------------------+-----------------------------+
| 2. DISCARD_LOW_     | 버퍼 사용률이 임계점(75% 등)  | 중요한 ERROR/WARN은 100%    |
|    PRIORITY         | 에 도달하면 DEBUG, INFO 폐기  | 보존하면서 워커 스레드      |
|                     | WARN, ERROR만 슬롯 진입 허용  | 블로킹 완전 회피 (실무 권장)|
+---------------------+-------------------------------+-----------------------------+
| 3. SYNCHRONOUS_     | 버퍼가 꽉 차면 워커 스레드가  | 버퍼 대기열을 우회하지만    |
|    FALLBACK         | 직접 디스크에 동기식으로 기록 | 해당 워커는 일시적 지연     |
|    (Caller Runs)    |                               | 발생                        |
+---------------------+-------------------------------+-----------------------------+
```

### DISCARD_LOW_PRIORITY의 실무적 가치
- 장애 발생 순간에는 수많은 `INFO` 로그(예: "요청 수신", "장바구니 조회")가 쏟아져 버퍼를 채웁니다.
- 정작 장애의 근본 원인을 담고 있는 `ERROR` 로그(예: "DB 커넥션 타임아웃", "NullPointerException")가 버퍼에 들어가지 못하고 유실되거나, `BLOCK` 정책 때문에 전사 스레드가 멈추는 악순환이 발생합니다.
- `DISCARD_LOW_PRIORITY` 정책은 버퍼 수위가 높아지면 사소한 `INFO/DEBUG`를 조기에 과감히 버림으로써, **서비스 가용성(Latency 0ms)과 치명적 에러 로깅(ERROR 100% 보존)** 두 마리 토끼를 모두 잡는 업계 표준 해법입니다.

## 4. 로깅 성능 및 상태 진단 지표

- **`max_worker_blocked_ms`**: 고객 요청을 처리하는 워커 스레드가 로깅으로 인해 대기한 최대 시간. 50ms 이상이면 위험 수준.
- **`avg_worker_latency_ms`**: 워커 스레드의 평균 로깅 오버헤드. 비동기 환경에서는 0ms에 수렴해야 함.
- **`overall_verdict`**:
  - `SYNC_LOGGING_THREAD_STARVATION`: 동기식 로거로 인해 워커 스레드가 락과 디스크 I/O에 묶여 심각한 지연 발생.
  - `ASYNC_RING_BUFFER_OVERFLOW_BLOCKED`: 비동기 로거였으나 BLOCK 정책으로 인해 버퍼가 차서 워커가 블로킹됨.
  - `ASYNC_DISCARD_UNDER_BURST`: 버스트 발생 시 정책에 따라 저위험 로그를 폐기하여 워커 블로킹을 방어함.
  - `ASYNC_HIGH_THROUGHPUT_OPTIMAL`: 버퍼 오버플로우 없이 워커 대기 0ms로 완벽하게 비동기 처리됨.
