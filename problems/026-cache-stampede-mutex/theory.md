# [ZeliJudge 백서 #026] 캐시가 만료된 그 1초, DB가 폭발했다: 캐시 스탬피드(Cache Stampede)와 뮤텍스 방어

> **"캐시 히트율 99%에 안심하지 마세요. 진짜 재앙은 캐시가 만료되는 바로 그 1%의 순간, 수천 개의 요청이 동시에 DB로 돌진할 때 일어납니다."**

---

## 1. 💡 비전공자 바이브 코더를 위한 현실 비유: "공용 화장실 휴지 참사"

대형 경기장 화장실을 상상해 보세요:

```text
[평화로운 상황: 캐시 히트 (Cache Hit)]
벽에 두루마리 휴지(캐시)가 걸려 있습니다.
손님들은 0.1초 만에 휴지를 뜯어 쓰고 나갑니다. (창고 갈 일 없음)

[참사의 순간: 캐시 만료 (TTL Expiration)]
휴지가 딱 떨어진 바로 그 순간, 화장실에 100명이 동시에 들어왔습니다!
100명이 동시에 빈 휴지걸이를 보고 일제히 외칩니다:
"어? 휴지가 없네? 내가 창고 가서 새 휴지 박스(무거운 DB 쿼리) 가져와야지!"
──> 100명이 좁은 창고 문으로 한꺼번에 돌진하여 창고 문이 박살 나고 압사 사고 발생!
──> 이것이 바로 캐시 스탬피드(Cache Stampede / Dogpiling)입니다!
```

- **상식적인 해결책 (Mutex / Singleflight)**:
  - 첫 번째 손님이 창고 열쇠(Mutex)를 쥐고 창고로 가고,
  - 나머지 99명은 화장실에서 10초만 기다립니다.
  - 첫 번째 손님이 새 휴지를 걸어두는 순간, 기다리던 99명은 창고에 갈 필요 없이 그 휴지를 편안하게 쓰고 나갑니다!
  - 창고 방문 횟수: **100번 ──> 단 1번!**

---

## 2. 🔍 컴퓨터 과학적 원리: 캐시 스탬피드 발생의 3대 요소

캐시 스탬피드는 다음 세 가지 조건이 결합할 때 필연적으로 발생합니다:

1. **높은 동시성(High Concurrency)**: 초당 수백~수천 건의 읽기 트래픽
2. **무거운 연산 비용(Expensive Computation)**: 실행하는 데 50ms~1초 이상 걸리는 복잡한 JOIN/집계 쿼리
3. **순간적인 캐시 만료(Hard TTL Expiry)**: 특정 시점에 캐시가 완전히 사라짐

### 💥 연쇄 사망 사이클 (Cascading Failure)
더 무서운 것은 캐시 스탬피드가 시작되면 **DB가 영원히 살아나지 못한다는 점**입니다:
1. 수백 개의 쿼리가 몰려 DB CPU가 100%가 됨.
2. 쿼리 응답 속도가 50ms에서 5초로 느려짐.
3. 그 5초 동안 새로운 수천 개의 요청이 또 DB로 쏟아짐.
4. 캐시가 채워지기도 전에 DB 커넥션 풀이 터져서 서버 전체가 영구 사망!

## 3. 🛡️ 구원의 기술 3대장

### 1) 뮤텍스 락 / 싱글플라이트 (Singleflight)
가장 정석적인 방법으로, 캐시 미스 발생 시 **오직 1개의 스레드만 락을 얻어 DB를 조회**하고 나머지는 대기시킵니다:

```python
# Redis 분산 락을 활용한 싱글플라이트 예시
data = redis.get("key")
if not data:
    # 락 획득 시도 (SET key val NX EX)
    if redis.set("lock:key", "1", nx=True, ex=10):
        try:
            data = db.query_heavy()
            redis.set("key", data, ex=100)
        finally:
            redis.delete("lock:key")
    else:
        # 다른 스레드가 쿼리 중이므로 0.05초 대기 후 캐시 재조회
        time.sleep(0.05)
        data = redis.get("key")
return data
```

### 2) 확률적 조기 만료 (XFetch / Probabilistic Early Expiration)
- 캐시가 완전히 만료되기 직전에, 들어오는 요청 중 **확률적으로 1개의 요청이 백그라운드에서 캐시를 미리 갱신**합니다.
- 사용자는 항상 캐시 히트를 누리며, TTL이 끝나서 캐시가 비는 순간 자체가 영원히 사라집니다!

### 3) 헌 데이터 우선 반환 (Stale-While-Revalidate)
- 캐시가 만료되었더라도, 에러를 내거나 사용자를 기다리게 하지 않고 **약간 낡은 데이터(Stale Data)를 즉시 반환**합니다.
- 그리고 백그라운드 비동기 워커가 새로운 데이터를 DB에서 긁어와 캐시를 조용히 갈아치웁니다.
