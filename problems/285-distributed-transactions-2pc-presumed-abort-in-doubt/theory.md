# 이론적 배경: 분산 2단계 커밋(2PC), Presumed Abort 및 블로킹 문제의 해결

## 1. 분산 트랜잭션과 원자성 보장의 난제

분산 시스템에서 여러 노드에 걸쳐 분할된 데이터에 대해 단일 트랜잭션을 실행할 때, 모든 노드가 함께 커밋(Commit)하거나 함께 롤백(Abort)해야 하는 **원자성(Atomicity)**을 만족해야 합니다.

1978년 짐 그레이(Jim Gray)가 제안한 **2단계 커밋(Two-Phase Commit, 2PC)**은 합의를 도출하기 위한 표준 프로토콜입니다.

### 고전적 2PC의 메시지 흐름과 비용
1. **Prepare 단계**: 코디네이터 $\to$ 참여자 ($N-1$개 메시지)
2. **Vote 응답**: 참여자 $\to$ 코디네이터 ($N-1$개 메시지, 참여자 로컬 fsync 1회)
3. **Commit/Abort 결정**: 코디네이터 디스크 fsync 1회
4. **Commit/Abort 브로드캐스트**: 코디네이터 $\to$ 참여자 ($N-1$개 메시지)
5. **ACK 응답 및 완료**: 참여자 $\to$ 코디네이터 ($N-1$개 메시지), 코디네이터 완료 fsync 1회

- 총 메시지 수: $4(N-1)$개
- 총 왕복 지연: 2 RTT + 최소 2회 이상의 디스크 강제 동기화(fsync)

---

## 2. Presumed Abort (PA) 최적화

고전적 2PC의 가장 큰 낭비는 **트랜잭션이 중단(Abort)될 때에도 코디네이터가 디스크에 로그를 쓰고 ACK를 기다려야 한다는 점**이었습니다.

1986년 C. Mohan, B. Lindsay, R. Obermarck는 논문 「Transaction Management in the R* Distributed Database Management System」에서 **Presumed Abort (PA)**를 제안했습니다:

| 구분 | 고전적 2PC (Classic 2PC) | Presumed Abort (PA) |
| :--- | :--- | :--- |
| **Commit 시 코디네이터 WAL** | `COMMIT` 기록 (강제 fsync) | `COMMIT` 기록 (강제 fsync) |
| **Abort 시 코디네이터 WAL** | `ABORT` 기록 (강제 fsync) | **기록하지 않음 (fsync 없음, 0비용)** |
| **Abort 시 참여자 ACK** | 모든 참여자 ACK 필수 | **ACK 불필요 (메모리에서 즉시 삭제)** |
| **재부팅 시 미확인 트랜잭션** | 명시적 로그 없으면 오류 | **로그가 없으면 무조건 Abort로 간주** |

- **효과**: 트랜잭션 실패나 충돌로 인한 롤백 시 코디네이터의 디스크 쓰기가 완전히 생략되어 처리량이 비약적으로 향상됩니다.

## 3. 의문 상태(In-Doubt State)와 2PC 블로킹 문제

2PC의 가장 치명적인 약점은 **블로킹(Blocking)**입니다.

- 참여자가 1단계에서 `VOTE_COMMIT`을 보내면, 그 즉시 **의문 상태(In-Doubt State)**에 들어갑니다.
- 왜냐하면 코디네이터가 다른 참여자의 거부로 인해 `GLOBAL_ABORT`를 내렸을 수도 있고, 모두 찬성하여 `GLOBAL_COMMIT`을 내렸을 수도 있기 때문입니다.
- 이때 코디네이터가 2단계 결정을 전달하기 직전에 크래시되면, 참여자는 혼자서 커밋할 수도(만약 코디네이터가 abort했다면 일관성 붕괴), 롤백할 수도(코디네이터가 commit했다면 일관성 붕괴) 없는 진퇴양난에 빠집니다.

### 협조적 종결 프로토콜 (Cooperative Termination Protocol, CTP)
참여자는 코디네이터가 살아날 때까지 마냥 기다리지 않고 다른 참여자 노드들과 통신하여 결정을 유추합니다:
1. 동료 중 한 명이라도 `COMMITTED` 상태라면 $\to$ 코디네이터가 커밋을 결정했음이 100% 확실하므로 커밋.
2. 동료 중 한 명이라도 `ABORTED` 상태이거나 1단계에서 `VOTE_ABORT`를 던졌다면 $\to$ 결코 커밋될 수 없으므로 중단.
3. **독립적 블로킹 상황**: 만약 연락 가능한 모든 참여자가 `PREPARED` 상태라면, 코디네이터가 결정을 내리고 죽었는지 내리기 전에 죽었는지 알 수 없으므로 블로킹됩니다. (이것이 2PC의 한계이며, 이를 극복하기 위해 Paxos/Raft 복제 기반 커밋이나 3PC가 연구되었습니다.)

## 4. 현대 분산 데이터베이스(Spanner, CockroachDB)에서의 발전

현대 NewSQL 데이터베이스는 2PC의 코디네이터 SPOF와 블로킹 문제를 다음과 같이 해결합니다:
- **각 샤드 및 코디네이터 자체를 단일 노드가 아닌 Paxos / Raft 복제 그룹(Replication Group)으로 구성**:
  - 코디네이터 노드가 죽더라도 Raft 쿼럼(Quorum)에 의해 새로운 리더가 즉시 선출되어 2PC 상태 머신을 이어받으므로, 코디네이터 단일 장애로 인한 영구 블로킹이 발생하지 않습니다.
- **TrueTime API / HLC (Hybrid Logical Clock)**:
  - 분산 락 타임아웃과 트랜잭션 충돌을 최소화하여 2PC의 락 점유 시간을 마이크로초 단위로 단축합니다.
