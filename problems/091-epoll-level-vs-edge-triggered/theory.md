# [CS 백서 #091] epoll로 고성능 비동기 서버를 짰더니 CPU 100% 찍거나 패킷이 증발해요?!: Level-Triggered (LT) vs Edge-Triggered (ET)

> **"Nginx와 Redis처럼 초당 수만 건을 처리하는 비동기 서버를 만들려고 Linux `epoll`을 도입했습니다. 그런데 어떤 때는 CPU가 100%를 찍으며 무한 루프를 돌고, 어떤 때는 클라이언트가 보낸 데이터 절반이 감쪽같이 증발해 서버가 멈춰버립니다!"**  
> 고성능 네트워크 프로그래밍에 입문한 개발자들이 가장 혹독하게 치르는 통과의례입니다.  
> 원인은 바로 **Linux epoll의 2대 통지 모드인 Level-Triggered (LT)와 Edge-Triggered (ET)** 의 동작 원리를 제대로 이해하지 못했기 때문입니다!

## 1. 현실 세계 비유: 문 앞의 택배 상자와 2가지 알림 방식

현관문 앞(소켓 수신 버퍼)에 택배 기사(클라이언트)가 상자(데이터)를 배달합니다. 집주인(서버 애플리케이션)에게 배달을 알리는 방법에는 2가지가 있습니다:

### 방식 A. 시끄러운 초인종 (Level-Triggered, 수평 통지)
- **규칙**: 문 앞에 택배 상자가 **1개라도 남아있는 한(버퍼 > 0)**, 초인종이 1초도 쉬지 않고 계속 딩동딩동 울려댑니다.
- **개발자의 실수 (CPU 100% 비지 루프)**:
  - 택배 상자 10개가 배달되었습니다.
  - 집주인이 일단 상자 1개만 집 안으로 들여놓고(부분 읽기, Partial Read), 나머지는 나중에 치우려고 문을 닫았습니다.
  - 하지만 문 밖에 상자 9개가 여전히 남아있으므로, 초인종이 1초에 수십만 번씩 미친 듯이 딩동딩동 울려댑니다!
  - 집주인은 다른 일을 전혀 못 하고 초인종 소리에 시달려 쓰러집니다(**CPU 100% 무한 비지 루프, Busy Loop**).

### 방식 B. 깜빡이는 1회용 LED 전등 (Edge-Triggered, 에지 통지)
- **규칙**: 택배가 새로 도착하는 **'그 순간(상태 전이, Edge)'** 에만 문 앞의 LED 전등이 딱 한 번 깜빡이고 꺼집니다.
- **개발자의 실수 (데이터 고립 및 무한 먹통, Starvation)**:
  - 택배 상자 10개가 새로 도착하여 LED가 한 번 반짝였습니다.
  - 집주인은 무심코 상자 5개만 집 안으로 들여놓고 문을 닫았습니다.
  - 문 밖에는 상자 5개가 남아있지만, **새로운 택배가 도착하지 않았으므로 LED 전등은 다시 켜지지 않습니다!**
  - 집주인은 "더 이상 택배가 없구나" 생각하고 소파에 눕고, 문 밖의 상자 5개는 비를 맞으며 영원히 방치됩니다(**데이터 고립, Marooned Data**).
  - 클라이언트는 남은 5개 상자에 대한 응답을 받지 못해 영구 타임아웃에 빠집니다!

## 2. 컴퓨터 과학 원리: Linux epoll의 내부 동작

Linux의 `epoll`은 `select`나 `poll`의 $O(N)$ 전수 순회 한계를 극복하기 위해, 커널의 레드-블랙 트리(RB-Tree)와 준비 큐(Ready List)를 기반으로 **$O(1)$ 이벤트 기반 I/O**를 제공합니다.

```text
[네트워크 패킷 도착] ──► 소켓 수신 버퍼(Kernel Buffer)에 데이터 적재
                              │
            ┌─────────────────┴─────────────────┐
            ▼                                   ▼
[Level-Triggered (LT)]                [Edge-Triggered (ET)]
- 버퍼에 데이터가 남아있으면           - 상태가 변경되는 '순간'에만
  epoll_wait 호출 시마다 계속 반환!      준비 큐에 딱 1번 추가!
- 다 안 읽으면 다음 루프에서 또 깨어남!  - epoll_wait으로 꺼내면 큐에서 즉시 제거!
```

---

### (1) Level-Triggered (LT)의 특징과 함정
- **동작**: 소켓 버퍼의 데이터 크기가 0보다 크면, `epoll_wait()`은 해당 FD를 계속 "준비 완료(Ready)" 상태로 보고합니다.
- **장점**: 개발이 안전합니다. 데이터를 일부만 읽어도 다음 루프에서 또 알려주므로 데이터가 유실될 위험이 없습니다.
- **치명적 함정**:
  - 만약 애플리케이션이 1,000바이트 중 100바이트만 읽고 다음 `epoll_wait()`을 호출하면, 버퍼에 900바이트가 남아있으므로 `epoll_wait()`이 블로킹되지 않고 **즉시(0초 만에) 반환**됩니다.
  - 이를 반복하면 루프가 쉬지 않고 초당 수백만 번 헛돌며 **CPU 점유율이 100%** 로 치솟습니다(**Busy-Waiting Spin**).

---

### (2) Edge-Triggered (ET)의 특징과 황금 룰

- **동작**: 빈 버퍼에 새 데이터가 들어오거나 새로운 연결이 맺어지는 **'상태의 변화(Edge)'** 가 일어날 때만 준비 큐에 1회 등록됩니다.
- **장점**: 불필요한 중복 이벤트 통지가 없어 시스템 콜 오버헤드가 극도로 적으며, Nginx 같은 고성능 프록시 서버의 기본 모드입니다.
- **치명적 함정**:
  - 한 번 통지를 받은 후, 버퍼의 데이터를 남겨둔 채 다음 `epoll_wait()`으로 넘어가면 **두 번 다시 통지가 오지 않습니다.**

#### ET 모드의 황금 룰 (The Golden Rule of ET):
> **"소켓을 반드시 Non-Blocking 모드로 열고, `read()` 시스템 콜이 `EAGAIN` (또는 `EWOULDBLOCK`)을 반환할 때까지 `while` 루프로 끝까지 퍼내라(Drain)!"**

```c
// [ET 모드의 올바른 배수(Drain) 패턴]
while (true) {
    ssize_t bytes_read = read(fd, buf, sizeof(buf));
    if (bytes_read > 0) {
        process_data(buf, bytes_read);
    } else if (bytes_read == -1) {
        if (errno == EAGAIN || errno == EWOULDBLOCK) {
            // 버퍼를 완전히 다 비웠음! 이제 안전하게 epoll_wait으로 복귀
            break;
        }
        // 실제 소켓 에러 처리
        break;
    } else {
        // EOF: 클라이언트가 연결을 닫음
        close(fd);
        break;
    }
}
```

## 3. 실무 아키텍처 비교 요약

| 구분 | Level-Triggered (LT) | Edge-Triggered (ET) |
| :--- | :--- | :--- |
| **통지 조건** | 버퍼에 데이터가 **남아있는 동안 내내** | 버퍼 상태가 **변화하는 순간 1회** |
| **기본값 여부** | Linux epoll의 **기본 모드** (`EPOLLET` 미지정) | `EPOLLET` 플래그 명시 필요 |
| **버퍼 부분 읽기 시** | 다음 루프에서 또 알려줌 (안전) | **남은 데이터가 영구 고립됨 (치명적 버그)** |
| **주의해야 할 참사** | 잔여 데이터 방치 시 **CPU 100% 비지 루프** | 루프 미적용 시 **패킷 증발 및 응답 먹통** |
| **권장 패턴** | 간단한 네트워크 앱, 블로킹 방지 | 고성능 서버 (Nginx, Netty) + **EAGAIN 루프 배수** |
