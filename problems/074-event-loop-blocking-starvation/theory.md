# CS 백서: 싱글 스레드 이벤트 루프 블로킹과 기아 현상 (Single-Threaded Event Loop Blocking & Task Starvation)

> **"비동기 프레임워크니까 수만 명도 버틴다면서요?! 왜 비밀번호 하나 암호화했다고 전사 API가 10초 동안 먹통이 되나요?!"**  
> — Node.js / FastAPI 서버에 `bcrypt.hashSync` 한 줄 넣었다가 서비스 전체 504 게이트웨이 타임아웃을 겪은 신입 백엔드 엔지니어의 절규

## 1. 현실 비유: 단 하나의 계산대만 있는 초스피드 편의점

서울 도심 한복판, 출근길에 손님이 1초에 수십 명씩 몰려드는 초대형 편의점이 있습니다.  
이 편의점의 계산대에는 신의 손이라 불리는 엄청나게 빠른 점원(싱글 스레드 이벤트 루프) 딱 한 명만 일하고 있습니다.

```
[출근길 손님들 줄서기] ─────────▶ [단 1개의 초고속 계산대 (이벤트 루프)]
  (손님 A: 삼각김밥 1개 - 0.1초)       │
  (손님 B: 커피 1캔 - 0.1초)           ▼ [비동기 I/O 선반 (백그라운드)]
  (손님 C: 도시락 데우기 - 전자레인지 위임) ───▶ 전자레인지 2분 조리 (점원은 다음 손님 받음!)
```

1. **정상적인 비동기(Non-blocking I/O) 흐름**:
   - 손님이 삼각김밥이나 음료수를 가져오면 0.1초 만에 바코드를 찍고 다음 손님을 받습니다 (경량 요청 처리).
   - "도시락을 데워주세요"라는 요청(I/O 요청)이 오면, 점원은 전자레인지에 도시락을 넣고 시작 버튼을 누른 뒤 손님에게 진동벨을 건넵니다. 그리고 **전자레인지가 돌아가는 2분 동안 멍하니 서서 기다리지 않고**, 즉시 뒤에 선 다른 손님 100명의 계산을 0.1초마다 척척 해치웁니다!
   - 2분 뒤 전자레인지가 "삐-" 하고 울리면(I/O 완료 인터럽트), 점원은 계산 사이사이에 틈을 내어 도시락을 건네줍니다(콜백 처리).
   - 이것이 바로 **Node.js와 Python asyncio가 자랑하는 싱글 스레드 논블로킹 I/O의 마법**입니다.

2. **비극의 시작: 계산대에서 발생한 블로킹(Event Loop Blocking)**:
   - 그런데 어느 날, 손님 X가 계산대에 오더니 엄청난 요구를 합니다:
     > *"점원님! 제가 가져온 A4 용지 5,000장을 한 장씩 복사해서, 스탬프를 찍고, 코팅한 뒤 호치키스로 묶어주세요!"* (`bcrypt.hashSync(cost=14)` / 동기 CPU 연산 / `fs.readFileSync`)
   - 점원은 이 작업을 뒤편 작업실로 넘기거나 거절하지 않고, **계산대 정중앙에서 직접 종이를 한 장 한 장 복사하기 시작합니다.**
   - 점원이 복사기를 돌리는 10분 동안 계산대는 완전히 정지합니다.
   - 뒤에 줄 서 있던 손님 A(물 한 병), 손님 B(껌 한 통) 수백 명은 계산대 앞을 지나가지도 못하고 10분 동안 꼼짝없이 갇힙니다.
   - 1분이 지나자 화가 난 손님들이 물건을 내던지고 편의점을 뛰쳐나갑니다 (**Request Timeout / 504 Gateway Timeout**).
   - 편의점 밖을 감시하던 배달 플랫폼 본사는 "이 지점 점원이 10분 동안 응답이 없으니 망한 지점이다"라며 배달 주문 목록에서 이 편의점을 강제로 퇴출시켜 버립니다 (**K8s Liveness Probe 실패로 인한 파드 강제 재부팅 & 연쇄 폭사**)!

## 2. 컴퓨터 과학 이론: 이벤트 루프(Event Loop)의 구조와 동작

### 1) 이벤트 루프란 무엇인가?
Node.js(V8 + libuv), Python(asyncio), 브라우저 JavaScript 런타임 등은 모두 **단일 메인 스레드(Single Main Thread)**에서 동작하는 이벤트 기반 아키텍처를 채택하고 있습니다.

```
┌─────────────────────────────────────────────────────────────┐
│                    Call Stack (Main Thread)                 │
│   단 1개의 실행 컨텍스트: 한 번에 단 1개의 함수만 실행 가능!     │
└──────────────────────────────▲──────────────────────────────┘
                               │ (Tick: 작업 꺼내기)
┌──────────────────────────────┴──────────────────────────────┐
│                    Event Loop (루프 스케줄러)                │
└──────────────────────────────▲──────────────────────────────┘
                               │
       ┌───────────────────────┴───────────────────────┐
       │             Task Queue (FIFO 대기열)          │
       │   [Task 1] ◀─ [Task 2] ◀─ [Task 3] ◀─ ...     │
       └───────────────────────────────────────────────┘
```

이벤트 루프의 1주기(Tick)는 대단히 단순한 무한 루프입니다:
1. **Call Stack 확인**: 현재 메인 스레드에서 실행 중인 코드가 있는지 확인합니다.
2. **Task 인출 및 실행**: Call Stack이 비어있으면 `Task Queue`에서 가장 오래 대기한 작업을 꺼내 Call Stack에 올리고 실행합니다.
3. **완료 및 반복**: 해당 작업이 끝날 때까지 기다렸다가, 끝나면 다음 작업을 꺼냅니다.

### 2) "Don't Block the Event Loop!": 블로킹의 치명성
이벤트 루프 아키텍처는 **"모든 개별 태스크가 아주 짧은 시간(수 마이크로초~수 밀리초) 안에 CPU를 양보(Yield)한다"**는 신뢰에 기반합니다.

만약 어떤 개발자가 메인 스레드에서 다음과 같은 코드를 실행하면 어떻게 될까요?
- **동기 CPU 바운드 연산**:
  - 비밀번호 단방향 해싱: `bcrypt.hashSync(password, 14)` (약 1,000ms 소요)
  - 대용량 데이터 직렬화: `JSON.parse(hugeString_500MB)`
  - 복잡한 정규식(ReDoS): 취약한 정규식 매칭으로 지수 시간($O(2^N)$) 소모
- **동기 블로킹 I/O**:
  - 파일 읽기: `fs.readFileSync('/large/file')`
  - 동기 HTTP 호출: Python `requests.get()` in `async def`

**결과: Event Loop Lag 폭증 & 태스크 기아(Starvation)**
- 해당 작업이 Call Stack을 독점하는 동안 Call Stack이 비워지지 않으므로, 이벤트 루프는 다음 Tick으로 전진할 수 없습니다.
- 뒤따라온 수천 건의 `GET /health`, `GET /users`, 웹소켓 핑/퐁 패킷 등 초경량 작업들이 Task Queue에 갇혀 실행 기회를 얻지 못하는 **기아 현상(Starvation)**이 발생합니다.
- 클라이언트와 로드밸런서는 타임아웃(예: 3초)을 감지하고 요청을 끊어버립니다.

## 3. 해결책: 워커 스레드 오프로딩과 논블로킹 I/O

현대 고성능 비동기 시스템은 무거운 작업을 메인 스레드에서 격리하기 위해 3가지 전략을 사용합니다.

```
                              [신규 작업 유입]
                                     │
                 ┌───────────────────┴───────────────────┐
                 │ 작업 성격 판별 (Task Classification)   │
                 └───────────────────┬───────────────────┘
                                     │
           ┌─────────────────────────┼─────────────────────────┐
           ▼                         ▼                         ▼
   [경량 CPU / 웹 라우팅]      [무거운 CPU 연산]          [네트워크 / 디스크 I/O]
           │                         │                         │
           ▼                         ▼                         ▼
 [메인 이벤트 루프 스레드]    [워커 스레드 풀 오프로딩]    [OS 비동기 논블로킹 커널]
   즉시 1 Tick 처리 완료!     (Worker Thread Pool /      (epoll, kqueue, IOCP)
                              run_in_executor)           완료 시 콜백만 큐에 등록!
```

### 1) 무거운 CPU 연산 $\to$ 워커 스레드 풀 오프로딩 (Worker Thread Pool)
- 메인 이벤트 루프는 요청을 접수하자마자 백그라운드 워커 스레드 풀(`worker_threads`, `ThreadPoolExecutor`)로 작업을 넘깁니다 (`loop.run_in_executor()`).
- 메인 스레드는 작업을 던져두고 즉시 다음 틱으로 넘어가 다른 요청들을 지연 없이 처리합니다.
- 워커 스레드가 연산을 마치면 결과를 콜백 형태로 Task Queue에 넣어 메인 스레드가 최종 반환하도록 합니다.

### 2) 동기 I/O $\to$ 비동기 논블로킹 I/O 전환 (epoll / kqueue)
- `fs.readFileSync` 대신 `fs.promises.readFile`을 사용합니다.
- Python에서는 동기 라이브러리인 `requests` 대신 `httpx`나 `aiohttp`를 사용합니다.
- I/O 대기 시간 동안 스레드가 멈추지 않고 OS 커널이 하드웨어 레벨에서 비동기 완료 통지를 보냅니다.

### 3) 틱 쪼개기 (Chunking / Yielding via `setImmediate` or `asyncio.sleep(0)`)
- 100만 건의 배열을 순회해야 한다면, 1,000건마다 `await asyncio.sleep(0)` 또는 `setImmediate()`를 호출하여 제어권을 이벤트 루프에 일시 양보합니다. 이렇게 하면 대기 중인 다른 급한 요청들이 중간중간 끼어들어 처리될 수 있습니다.

## 4. 시뮬레이션 모델 설계

본 문제에서는 동일한 작업 스트림에 대해 두 가지 엔진의 성능을 시뮬레이션합니다:

### 1) Naive Engine (블로킹 메인 루프)
- 모든 태스크(경량, 비동기, 무거운 CPU, 동기 I/O)를 단일 메인 스레드에서 순차 실행합니다.
- 블로킹 작업이 실행되는 동안 루프의 가상 시간(Tick)이 작업 소요 시간만큼 일거에 건너뛰며, 뒤에 대기 중이던 태스크들의 대기 시간(`wait_ticks`)이 누적됩니다.
- 대기 시간이 최대 허용 시간(`MAX_WAIT_TICKS`)을 초과하면 해당 태스크는 **타임아웃 드롭(`TIMEOUT_DROP`)** 처리됩니다.

### 2) Tuned Engine (논블로킹 + 워커 풀 오프로딩)
- `LIGHT_TASK`: 메인 루프에서 즉시 처리 (소요 시간 1 Tick).
- `ASYNC_IO_TASK`: OS 커널 위임 후 1 Tick 콜백 완료.
- `BLOCKING_CPU_TASK` & `BLOCKING_SYNC_IO`: 메인 루프를 점유하지 않고 `WORKER_POOL_SIZE`개의 백그라운드 워커 스레드로 즉시 오프로딩.
- 메인 이벤트 루프의 Lag이 최소화되어 뒤따르는 경량 요청들이 타임아웃 없이 전원 정상 완료됩니다.
