# 📘 [CS 이론 #005] 문자열 덧셈의 늪: 불변 객체(Immutable)와 메모리 복사 지옥

> **"문자열 10만 개 합치는데 왜 1시간이나 걸릴까? 리스트 합치기는 0.01초인데?"**  
> 불변성(Immutability)의 철학과 가비지 컬렉터(GC)를 울리는 $O(N^2)$ 메모리 복사의 비밀.

---

## 1. 겉보기엔 우아한 `+=` 연산자의 배신

파이썬, 자바스크립트, 자바, C# 등 대부분의 현대 언어에서 문자열을 합칠 때 우리는 너무나 자연스럽게 `+` 연산자를 씁니다:

```python
report = ""
for line in error_lines:
    report += line + "\n"   # <- 1시간 동안 서버를 멈추게 만든 주범
```

루프가 10번 돌 때는 아무 문제가 없습니다. 100번 돌 때도 눈 깜짝할 사이에 끝납니다.  
하지만 **루프가 10만 번을 넘어서는 순간, 컴퓨터는 거북이처럼 기어가기 시작하고 CPU 사용률이 100%로 치솟습니다.**

도대체 컴퓨터 안에서 무슨 일이 벌어지고 있는 걸까요?

---

## 2. 왜 문자열은 '불변(Immutable)'일까?

리스트(`list`)는 `append()`를 하면 기존 메모리 뒤에 쏙쏙 새 데이터를 붙일 수 있습니다.  
하지만 **파이썬의 문자열(`str`)은 한 번 메모리에 생성되면 죽을 때까지 내용이 절대 바뀌지 않는 '불변 객체(Immutable Object)'**입니다.

```python
text = "hello"
text[0] = "H"  # TypeError: 'str' object does not support item assignment!
```

> **언어 설계자들은 왜 문자열을 불변으로 만들었을까요?**  
> 1. **해시 키(Hash Key) 무결성**: 딕셔너리(`dict`)나 집합(`set`)의 키로 문자열을 쓸 때, 내용이 바뀌면 해시 테이블이 완전히 깨져버립니다. 불변이어야만 안전하게 키로 쓸 수 있습니다.
> 2. **스레드 안전성(Thread-Safety)**: 여러 스레드가 동시에 같은 문자열을 읽더라도, 내용이 변하지 않으므로 복잡한 락(Lock) 없이 안전합니다.
> 3. **문자열 인턴(String Interning)**: 똑같은 문자열 리터럴(`"hello"`)이 수천 번 등장해도 메모리에는 단 1개만 올려두고 포인터만 공유하여 RAM을 대폭 절약할 수 있습니다.

## 3. `report += message`의 숨겨진 실체: 1,500억 번의 바이트 복사!

문자열이 불변이라는 것은 **"기존 메모리 방 뒤에 새로운 글자를 이어붙이는 것이 물리적으로 불가능하다"**는 뜻입니다.

따라서 `report += message`를 실행할 때마다 컴퓨터는 내부적으로 다음과 같은 미친 짓을 반복합니다:

```
[ 루프 1회차: 길이 30바이트 ]
1. 30바이트 크기의 새 메모리 할당
2. message를 복사 (30바이트 복사)

[ 루프 2회차: 길이 60바이트 ]
1. 60바이트 크기의 새 메모리 할당
2. 이전 report(30바이트) + 새 message(30바이트) 복사 (총 60바이트 복사!)
3. 이전 30바이트 메모리는 쓰레기(Garbage)로 버려짐

...

[ 루프 100,000회차: 길이 3,000,000바이트 ]
1. 3MB 크기의 새 메모리 할당
2. 이전 report(2,999,970바이트)를 통째로 복사!
3. 새 message(30바이트) 복사
4. 이전 2,999,970바이트 메모리는 또 버려짐!
```

### 총 복사 연산량 계산:
각 라인의 길이가 약 30바이트라고 할 때, $N=100,000$번 동안 복사되는 바이트 수는 다음과 같습니다:

$$\text{총 복사량} = 30 \times (1 + 2 + 3 + \dots + N) = 30 \times \frac{N(N+1)}{2} \approx 30 \times 5,000,000,000$$
$$= \mathbf{150,000,000,000 \text{ 바이트 (1,500억 번의 메모리 복사!)불변}}$$

겨우 3MB짜리 텍스트 결과를 만들겠다고, **CPU가 1,500억 번 동안 메모리를 복사하고 있었던 것**입니다!  
시간 복잡도로 따지면 명백한 **$O(N^2)$**입니다.

게다가 루프를 돌 때마다 버려진 수만 개의 임시 문자열 쓰레기를 치우느라 **가비지 컬렉터(Garbage Collector)가 수시로 프로그램을 일시 정지(Stop-the-World)**시키니 1시간이 걸려도 끝나지 않는 것이 당연합니다.

## 4. 구원투수: 가변 버퍼(Mutable Buffer)와 `join()`의 마법

이 문제를 해결하는 엔지니어의 정석 코드는 단 2줄입니다:

```python
# [올바른 엔지니어링 코드]
buffer = []
for line in error_lines:
    buffer.append(line)          # 1. 가변 리스트에 포인터만 추가 (O(1))

report = "\n".join(buffer) + "\n" # 2. 마지막에 C-레벨 단 1회 결합 (O(N))
```

### 왜 `join()`은 번개처럼 빠를까요?
파이썬 CPython 인터프리터 내부의 `join()` 구현은 다음과 같이 동작합니다:
1. **1단계 (크기 사전 계산)**: 리스트 내부 문자열들의 길이를 훑어, 최종 결과물에 필요한 총 바이트 수를 정확히 계산합니다.
2. **2단계 (단 1번의 메모리 할당)**: 딱 필요한 크기(예: 3MB)만큼의 메모리를 운영체제로부터 **단 1번만 할당(Single Allocation)**받습니다.
3. **3단계 (고속 C 메모리 복사)**: 각 문자열의 내용을 목표 메모리에 차례대로 딱 1번씩만 복사합니다.

중간에 버려지는 임시 객체가 단 1개도 없으며, 각 바이트는 정확히 1번만 복사되므로 **시간 복잡도는 완벽한 $O(N)$**이 됩니다.

$$\text{1시간 동안 뻗어있던 작업} \xrightarrow{\quad \text{join() 적용} \quad} \mathbf{단\ 0.02초(20밀리초) 만에 완료!}$$

## 5. 다른 언어들에서는 어떻게 해결할까?

이 문제는 모든 현대 언어 개발자가 겪는 공통 과제이므로 언어마다 가변 버퍼 도구를 제공합니다:

| 언어 | 비효율 코드 ($O(N^2)$) | 고성능 가변 버퍼 ($O(N)$) |
|---|---|---|
| **Python** | `s += chunk` | `list.append()` 후 `"".join(list)` |
| **Java** | `str += chunk` | `StringBuilder sb = new StringBuilder(); sb.append()` |
| **C#** | `str += chunk` | `System.Text.StringBuilder` |
| **C++** | `std::string s; s += c;` | `s.reserve(total_size);` 후 `append` |
| **Go** | `s += chunk` | `strings.Builder` |
