## 1. TCP의 두 가지 연결 종료 방식: FIN vs RST

TCP는 신뢰성 있는 양방향 전이중(Full-Duplex) 통신 프로토콜입니다.
연결을 닫는 방식 역시 두 가지로 극명하게 나뉩니다.

### 1) 신사적인 작별 인사: FIN (4-Way Handshake & Graceful Teardown)
정상적인 연결 종료는 서로에게 "더 이상 보낼 데이터가 없다"는 사실을 확인하는 4단계 작별 인사입니다:
1. **Client -> Server (FIN)**: "저는 할 말을 다 끝마쳤습니다 (더 이상 보낼 데이터 없음)."
2. **Server -> Client (ACK)**: "네, 당신의 말이 끝난 것을 확인했습니다."
3. **Server -> Client (FIN)**: "저도 당신에게 보낼 데이터를 모두 전송했고, 할 말이 끝났습니다."
4. **Client -> Server (ACK)**: "네, 확인했습니다. 안녕히 계세요!"

- **TIME_WAIT 상태의 필연성**: 마지막 ACK를 보낸 주체(Active Close)는 네트워크에 늦게 도착할지 모르는 패킷(지연 패킷)이 새로운 연결을 오염시키는 것을 막기 위해 **2MSL(기본 60초)** 동안 `TIME_WAIT` 상태로 소켓을 유지합니다.

---

### 2) 일방적인 수화기 패대기: RST (Abrupt Reset & Connection Reset by Peer)
RST(Reset)는 신사적인 작별 인사가 아니라 **"지금 당장 모든 통신을 강제로 폭파하라!"**는 커널 레벨의 비상 명령어입니다:
- 상대방에게 작별 인사를 묻지 않고 단 1개의 RST 패킷을 던져 연결을 파괴합니다.
- 송신 버퍼와 수신 버퍼에 남아있던 모든 데이터는 **즉시 폐기(Drop)**됩니다.
- RST를 받은 상대방 애플리케이션은 읽기/쓰기 시도시 `ECONNRESET (Connection reset by peer)` 예외를 맞고 강제 중단됩니다.
- 가장 중요한 특징: **`TIME_WAIT` 상태를 거치지 않고 즉시 소켓이 닫힙니다.**

---

## 2. 실무에서 RST가 폭발하는 3대 원인과 참사

### 1) 수신 버퍼 미처리 데이터(Unread Data) 상태에서의 `close()` (가장 흔한 실무 버그!)
- 클라이언트가 10KB 데이터를 소켓에 썼습니다.
- 서버 애플리케이션이 앞부분 1KB만 `read()`하고 비즈니스 로직을 마친 뒤 `close()`를 호출했습니다.
- **커널의 판단**: "어? 아직 애플리케이션이 읽지 않은 데이터 9KB가 수신 버퍼에 남아있는데 소켓을 닫네?! 이건 데이터 유실(Data Loss)이다! 정상 종료(FIN)를 보내면 상대방이 데이터가 다 잘 전달된 줄 착각하겠어!"
- **결과**: 커널은 FIN 대신 **즉시 RST 패킷**을 상대방에게 쏘아 보냅니다! 클라이언트는 정상 응답 대신 `ECONNRESET` 에러를 맞고 폭사합니다.

---

### 2) `SO_LINGER` 옵션을 이용한 꼼수와 부작용 (Zero Linger)
TIME_WAIT 소켓이 많이 생겨 임시 포트가 고갈될까 봐 두려워진 일부 개발자들이 다음과 같은 치명적인 코드를 작성합니다:
```c
struct linger sl = { .l_onoff = 1, .l_linger = 0 }; // Zero Linger
setsockopt(sock_fd, SOL_SOCKET, SO_LINGER, &sl, sizeof(sl));
close(sock_fd);
```
- `l_onoff = 1, l_linger = 0`으로 설정하면, `close()`를 호출할 때 송신 버퍼에 아직 상대방에게 다 안 날아간 데이터가 남아있더라도 **모두 내던져 버리고 강제로 RST를 날려 TIME_WAIT를 회피**합니다.
- TIME_WAIT는 안 생기지만, 상대방은 잘 가던 데이터가 중간에 끊기고 `ECONNRESET` 에러를 맞게 됩니다.

---

### 3) 닫혀 있는 포트 접근 (Port Closed / Connection Refused)
- 서버의 특정 포트(예: 8080)에서 리슨(`listen()`)하고 있는 프로세스가 없는데, 클라이언트가 SYN 패킷을 보내면 커널은 즉시 RST/ACK 패킷을 응답하여 `Connection refused (ECONNREFUSED)` 에러를 냅니다.

---

## 3. 실무 아키텍처 베스트 프랙티스

1. **수신 버퍼 드레인(Drain) 후 종료**:
   - 소켓을 닫기 전에는 반드시 상대방이 보낸 데이터를 EOF(`read() == 0`)가 나올 때까지 끝까지 비워내거나, `shutdown(sock, SHUT_WR)`을 사용하여 내 쪽의 송신만 먼저 닫는 **Half-Close** 패턴을 사용해야 합니다.
2. **`SO_LINGER` 남용 금지**:
   - TIME_WAIT는 적이 아니라 TCP의 신뢰성을 지켜주는 수호천사입니다. TIME_WAIT를 피하겠다고 `l_linger = 0`으로 강제 RST를 날리는 것은 데이터 파손과 클라이언트 에러를 유발하는 안티패턴입니다.
3. **HTTP Keep-Alive 커넥션 재사용**:
   - TIME_WAIT 고갈 문제는 `SO_LINGER` 꼼수가 아니라, 커넥션 풀링(Keep-Alive)을 통해 불필요한 단기 연결 생성/종료 자체를 최소화함으로써 우아하게 해결해야 합니다.
