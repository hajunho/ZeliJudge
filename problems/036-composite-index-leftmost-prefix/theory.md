# 📚 기술 백서: 복합 인덱스(Composite Index)와 Leftmost Prefix의 저주

> **"인덱스 괄호 안에 컬럼 이름을 다 적어두었다고 해서, DB가 마법처럼 모든 조건을 한 번에 빠르게 찾아주는 것은 아닙니다."**

현대 웹 애플리케이션의 성능 장애 중 80% 이상은 **잘못 설계된 데이터베이스 인덱스**에서 비롯됩니다.
특히 AI 코딩 어시스턴트에게 "이 쿼리 빨라지게 인덱스 짜줘"라고 부탁하면, AI는 `WHERE` 절에 등장하는 컬럼들을 아무 생각 없이 나열한 복합 인덱스를 생성해 주기 일쑤입니다.

하지만 운영 환경에 배포하는 순간, 특정 쿼리는 0.001초 만에 실행되지만 다른 쿼리는 **CPU 100%를 찍으며 슬로우 쿼리 폭탄**을 터뜨립니다.
이 미스터리를 풀기 위해서는 RDBMS(MySQL, PostgreSQL 등)의 심장인 **B-Tree 인덱스의 물리적 정렬 원리**와 **Leftmost Prefix 법칙**을 반드시 이해해야 합니다.

---

## 1. 현실 비유: 10만 명 학교 출석부와 전화번호부

데이터베이스의 복합 인덱스 `INDEX (학년, 반, 번호, 이름)`는 학교 교무실에 비치된 **10만 명 학생 출석부**와 똑같습니다.

출석부는 다음과 같이 철저하게 **사전식 순서(Lexicographical Order)**로 정렬되어 있습니다:
```text
1학년 -> 1반 -> 1번 -> 강호동
1학년 -> 1반 -> 2번 -> 김철수
...
1학년 -> 2반 -> 1번 -> 박영희
...
2학년 -> 1반 -> 1번 -> 나코딩
```

이제 교장 선생님이 여러 가지 심부름을 시킵니다:

### 시나리오 A: "2학년 3반 15번 학생 출석부 가져와!"
* 사서는 출석부를 펼쳐 [2학년] 섹션으로 바로 갑니다 ($O(\log N)$).
* 그 안에서 [3반]으로 바로 갑니다 ($O(\log N)$).
* 그 안에서 [15번]을 단 0.001초 만에 딱 집어냅니다!
* **결과**: 완벽한 **Index Seek**! 읽은 페이지 수 = 단 1장!

### 시나리오 B: "이름이 '나코딩'인 학생 다 찾아와!" (Leftmost Prefix 누락)
* 출석부에는 분명히 '이름'이 적혀 있습니다.
* 하지만 출석부의 대분류는 **[학년]**이고, 중분류는 **[반]**, 소분류는 **[번호]**입니다.
* 사서는 1학년 1반 1번부터 3학년 마지막 반 끝 번호까지 **10만 명의 이름을 처음부터 끝까지 눈으로 다 넘겨봐야** 합니다!
* **결과**: 끔찍한 **Table Full Scan**! 출석부 10만 장을 전부 넘기느라 손목이 나가고 10분이 걸립니다.

### 시나리오 C: "2학년에서 1반부터 3반까지 학생 중 번호가 '5번'인 학생 찾아와!" (Range 조건의 단절)
* [2학년]은 바로 찾습니다.
* [반]은 '1반부터 3반까지' 범위입니다.
* 이제 사서는 1반, 2반, 3반 학생 목록을 펼쳐봅니다.
* 그런데 1반의 5번, 2반의 5번, 3반의 5번은 **출석부 상에서 한곳에 모여 있지 않고 뿔뿔이 흩어져 있습니다!**
* 따라서 사서는 1반~3반의 모든 학생(수백 명)을 일단 다 읽으면서 그중 5번인 학생을 하나하나 필터링해야 합니다.
* **결과**: 범위 조건(`반 BETWEEN 1 AND 3`) 뒤에 오는 `번호 = 5`는 **탐색 범위를 좁히는 Seek Key로 전혀 쓰이지 못하고 단순 필터(Filter)로 격하**됩니다!

## 2. B-Tree 복합 인덱스의 물리적 저장 구조

RDBMS의 B-Tree 인덱스 리프 노드(Leaf Node)에는 인덱스를 구성하는 컬럼값들이 **단방향 튜플 형태로 정렬**되어 저장됩니다.

```text
INDEX idx_test (C1, C2, C3)
```

인덱스의 정렬 기준은 수학적으로 다음과 같습니다:
1. $C_1$ 기준으로 먼저 전체 정렬된다.
2. **$C_1$의 값이 완벽히 동일한 경우에 한해서만**, $C_2$ 기준으로 정렬된다.
3. **$C_1$과 $C_2$의 값이 모두 완벽히 동일한 경우에 한해서만**, $C_3$ 기준으로 정렬된다.

```text
  (C1, C2, C3)
+---------------+
| ('A', 10, 100)|
| ('A', 10, 200)|  <-- C1='A', C2=10 일치하므로 C3 순서로 정렬됨
| ('A', 20,  50)|
| ('B',  5, 300)|
| ('B', 10, 100)|
+---------------+
```

이 물리적 구조로부터 데이터베이스 튜닝의 가장 중요한 법칙이 파생됩니다.

## 3. Leftmost Prefix (최좌측 접두사) 법칙

> **"복합 인덱스의 첫 번째 컬럼이 조건에 없으면, B-Tree 탐색(Seek)은 불가능하다!"**

인덱스가 `(A, B, C)`로 생성되어 있을 때:
* `WHERE A = 1 AND B = 2 AND C = 3`: **A, B, C 모두 Seek Key**로 사용 ($O(\log N)$ 완벽한 인덱스 탐색)
* `WHERE A = 1 AND B = 2`: **A, B 모두 Seek Key**로 사용
* `WHERE A = 1`: **A만 Seek Key**로 사용
* `WHERE B = 2 AND C = 3`: **인덱스 사용 불가 (TABLE_FULL_SCAN)**!
  * 첫 번째 컬럼 `A`가 없으므로 B-Tree 루트부터 분기할 수 없습니다.
* `WHERE C = 3`: **인덱스 사용 불가 (TABLE_FULL_SCAN)**!

## 4. 등치(`=`) vs 범위(`RANGE`) 조건의 결정적 차이

실무에서 가장 많은 주니어/바이브 코더들이 걸려 넘어지는 함정입니다.

### 왜 범위 조건 뒤의 컬럼은 Seek Key가 되지 못할까?
예를 들어 `INDEX (status, price, created_at)` 인덱스가 있다고 가정해 봅시다.

쿼리:
```sql
WHERE status = 'SALE' AND price >= 10000 AND created_at = '2026-01-01';
```

1. `status = 'SALE'`:
   * B-Tree에서 `status = 'SALE'`인 연속된 블록의 시작점을 정확히 찾아갑니다. (**Seek Key**)
2. `price >= 10000`:
   * `status = 'SALE'` 블록 내부에서 `price`는 정렬되어 있습니다!
   * 따라서 `price = 10000`인 시작점을 B-Tree로 찾고, 그 뒤로 스캔을 시작합니다. (**Seek Key**)
3. `created_at = '2026-01-01'`:
   * **여기서 비극이 발생합니다.**
   * `price >= 10000`인 레코드들은 `price = 10000`, `price = 15000`, `price = 20000` 등 가격이 제각각입니다.
   * `created_at`은 **가격이 정확히 같을 때만 정렬**되어 있습니다!
   * 가격이 10000원인 상품들의 날짜, 15000원인 상품들의 날짜가 따로따로 정렬되어 있으므로, B-Tree 전체에서 `created_at = '2026-01-01'`이 한곳에 뭉쳐 있지 않습니다!
   * 결국 DB 엔진은 `price >= 10000`에 해당하는 **수천~수만 건의 인덱스 레코드를 하나하나 다 읽어가며 `created_at`이 2026-01-01인지 일일이 검사(Filter)**해야 합니다!

> **핵심 원리 요약:**  
> 복합 인덱스에서 **첫 번째 범위 조건(`<, >, BETWEEN, LIKE 'abc%'`)을 만나는 순간, 그 뒤에 나오는 모든 컬럼은 인덱스 탐색(Seek Key) 능력을 상실**하고 단순 필터(Index Condition Pushdown / Filtering)로 전락합니다!

## 5. 복합 인덱스 컬럼 배치 3대 황금률

실무에서 쿼리 성능을 100배~10,000배 끌어올리는 복합 인덱스 설계 공식입니다:

```text
[등치(=) 조건 컬럼들 (카디널리티 높은 순)] + [범위(RANGE) 조건 컬럼 (가장 좁은 범위 1개)]
```

### 규칙 1: 등치(`=`) 조건 컬럼을 무조건 인덱스 앞쪽에 몰아넣어라!
* `WHERE status = 'SALE' AND created_at >= '2026-01-01'`
* 나쁜 인덱스: `(created_at, status)` $\to$ `created_at`이 범위이므로 `status`는 필터로 전락!
* 좋은 인덱스: `(status, created_at)` $\to$ 등치 `status`로 범위를 확 줄이고 `created_at` 범위 스캔 시작!

### 규칙 2: 범위 조건 컬럼은 등치 컬럼들 뒤에 배치하라!
* 범위 조건은 인덱스에서 단 1개만 유효 Seek Key로 동작합니다.
* 여러 개의 범위 조건이 쿼리에 있다면, **데이터를 가장 많이 걸러내는(Selectivity가 가장 작은) 핵심 범위 컬럼 1개를 앞쪽에 배치**해야 스캔 행 수를 최소화할 수 있습니다.

### 규칙 3: 등치 조건들 사이에서는 카디널리티(고유값 수)가 높은 컬럼을 우선하라!
* 예: `tenant_id`(고유값 1,000개, 선택도 0.1%) vs `is_deleted`(고유값 2개, 선택도 50%)
* `(tenant_id, is_deleted)` 순서로 배치하면, 다른 쿼리에서 `tenant_id` 단독 조건만 들어오더라도 Leftmost Prefix를 만족하여 재사용성이 극대화됩니다.

## 6. 실무 안티패턴: 인덱스를 걸어놓고도 스스로 파괴하는 3대 실수

인덱스를 완벽한 순서로 걸어두었더라도, 쿼리 작성 시 다음 실수를 범하면 옵티마이저는 인덱스를 포기하고 풀스캔을 선택합니다:

1. **인덱스 컬럼 변형/가공 (Column Expression)**:
   ```sql
   -- ❌ 인덱스 파괴 (함수로 컬럼값을 감싸면 B-Tree 정렬 기준 상실)
   WHERE SUBSTRING(phone, 1, 3) = '010';
   WHERE DATE(created_at) = '2026-01-01';

   -- ⭕ 인덱스 활용 (컬럼을 가공하지 않고 범위로 표현)
   WHERE phone LIKE '010%';
   WHERE created_at >= '2026-01-01 00:00:00' AND created_at < '2026-01-02 00:00:00';
   ```

2. **앞부분 와일드카드 LIKE (`%keyword`)**:
   ```sql
   -- ❌ 인덱스 파괴 (사전에서 뒷글자가 '길동'인 단어를 찾으라는 꼴)
   WHERE name LIKE '%길동';

   -- ⭕ 접두사 검색만 B-Tree Index Seek 가능
   WHERE name LIKE '홍%';
   ```

3. **묵시적 형변환 (Implicit Type Conversion)**:
   ```sql
   -- user_id가 VARCHAR(20) 문자열 컬럼인 경우:
   -- ❌ 인덱스 파괴 (DB가 내부적으로 TO_NUMBER(user_id) = 12345 로 컬럼을 형변환함)
   WHERE user_id = 12345;

   -- ⭕ 정상 인덱스 사용
   WHERE user_id = '12345';
   ```

## 7. 결론: 인덱스는 마법이 아니라 물리적 정렬이다

B-Tree 인덱스는 데이터를 가상의 정렬된 종이 장부에 적어둔 것에 불과합니다.
* **첫 장(Leftmost)부터 찾지 않으면** 목차는 쓸모가 없습니다.
* **물결표(~) 범위 검색을 시작하는 순간**, 그 뒤에 적힌 세부 목차는 정렬이 흐트러집니다.

이 물리적 법칙을 머릿속에 시각화할 수 있을 때, 비로소 AI가 추천해 주는 엉터리 인덱스를 교정하고 수억 건의 대용량 트래픽 앞에서도 0.001초 만에 응답하는 탄탄한 백엔드 시스템을 구축할 수 있습니다.
