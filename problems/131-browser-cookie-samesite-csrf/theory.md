# 브라우저 쿠키 보안 3대 플래그와 SameSite & CSRF 참사

> "2020년 2월 어느 날 아침, 출근하자마자 커머스 서비스의 결제 승인 콜센터가 폭발했습니다.  
> 사용자가 카드사 결제창에서 비밀번호를 다 누르고 결제 승인을 마쳤는데, 우리 쇼핑몰로 돌아오자마자 **'로그인이 만료되었습니다'**라며 장바구니가 비어버리고 결제가 튕겨버린 것입니다!  
> 우리 서버 코드는 어제 한 줄도 배포하지 않았는데, 도대체 무슨 일이 벌어진 걸까요?"

---

## 1. 쿠키(Cookie)의 탄생과 웹 세션

HTTP 프로토콜은 본래 **무상태(Stateless)** 구조입니다. 즉, 클라이언트가 보낸 첫 번째 요청과 두 번째 요청 사이에 서버는 동일 인물인지 기억하지 못합니다.  
이를 극복하기 위해 넷스케이프(Netscape)에서 고안한 것이 바로 **쿠키(Cookie)**입니다.

1. 사용자가 ID/PW로 로그인 성공 $	o$ 서버가 응답 헤더에 `Set-Cookie: SESSIONID=xyz123`를 실어 보냄.
2. 브라우저는 이 쿠키를 로컬 쿠키 저장소(Cookie Jar)에 보관.
3. 이후 브라우저가 해당 도메인으로 요청을 보낼 때마다 요청 헤더에 자동으로 `Cookie: SESSIONID=xyz123`를 첨부.

하지만 이 "브라우저가 알아서 자동으로 쿠키를 첨부해 준다"는 편리함이 **웹 역사상 최악의 보안 취약점 두 가지(XSS와 CSRF)**를 잉태하게 됩니다.

---

## 2. 브라우저 쿠키의 3대 핵심 보안 플래그

브라우저는 쿠키를 보호하기 위해 세 가지 강력한 방어 무기를 진화시켜 왔습니다.

```
+-------------------------------------------------------------------------------+
|                             쿠키 3대 보안 방패                                |
+-----------------------+-----------------------+-------------------------------+
| 1. HttpOnly           | 2. Secure             | 3. SameSite (Lax/Strict/None) |
| 자바스크립트 접근 차단| HTTPS 채널에서만 전송 | 다른 사이트에서의 쿠키 전송   |
| (XSS 쿠키 탈취 방어)  | (패킷 감청 스니핑 방어)| 제한 (CSRF 공격 원천 방어)    |
+-----------------------+-----------------------+-------------------------------+
```

### (1) HttpOnly 플래그
- **목적**: XSS(Cross-Site Scripting, 악성 스크립트 삽입) 공격 발생 시 해커가 `document.cookie`로 세션 쿠키를 훔쳐가지 못하도록 원천 차단합니다.
- **동작**:
  - `HttpOnly`가 설정된 쿠키는 브라우저 내부 네트워크 통신(HTTP 요청)에는 정상적으로 전송되지만, 웹페이지 내의 자바스크립트 엔진(`document.cookie`)에는 **아예 보이지 않습니다(보이지 않는 유령)**.
  - 비전공자가 자주 하는 실수: "로그인 토큰을 프론트엔드 `localStorage`에 저장하자!" $	o$ XSS 공격 한 번에 모든 토큰이 해커 서버로 털립니다. 세션 토큰은 반드시 `HttpOnly; Secure` 쿠키로 다루어야 안전합니다.

### (2) Secure 플래그
- **목적**: 암호화되지 않은 평문 HTTP 프로토콜을 통해 쿠키가 네트워크에 노출(패킷 스니핑)되는 것을 방지합니다.
- **동작**:
  - `Secure` 플래그가 붙은 쿠키는 오직 **`https://`** 프로토콜로 통신할 때만 전송되며, `http://` 요청 시에는 브라우저가 전송을 거부합니다.

### (3) SameSite 플래그
- **목적**: 내가 머물고 있는 사이트(Initiator Origin)가 아닌, **다른 사이트(Cross-Site)에서 발생한 요청에 이 쿠키를 함께 실어 보낼 것인가?**를 제어합니다.
- 이 플래그가 바로 **CSRF(Cross-Site Request Forgery)** 공격을 막아내는 현대 브라우저의 최전선 방어선입니다.

## 3. Site vs Origin (eTLD+1의 마법)

많은 개발자들이 **Origin(출처)**과 **Site(사이트)**의 차이를 혼동합니다. SameSite를 이해하기 위해서는 이 둘을 반드시 구분해야 합니다.

```
Origin = Scheme(프로토콜) + Host(호스트) + Port(포트) (완전 일치해야 Same-Origin)
Site   = eTLD + 1 (유효 최상위 도메인 + 직전 도메인 1개)
```

| 구분 | A 주소 | B 주소 | Same-Origin? | Same-Site? (eTLD+1) |
|---|---|---|---|---|
| 서브도메인 차이 | `https://shop.com` | `https://api.shop.com` | ❌ (Host 다름) | **O (shop.com으로 동일)** |
| 포트 차이 | `https://shop.com:443` | `https://shop.com:8080` | ❌ (Port 다름) | **O (shop.com으로 동일)** |
| 2단 TLD (한국) | `https://a.co.kr` | `https://b.co.kr` | ❌ | ❌ (`co.kr`은 eTLD이므로 각각 `a.co.kr`, `b.co.kr`) |
| 2단 서브도메인 | `https://pay.a.co.kr` | `https://shop.a.co.kr` | ❌ | **O (a.co.kr로 동일)** |
| 완전 다른 사이트 | `https://evil.com` | `https://bank.com` | ❌ | ❌ (`evil.com` vs `bank.com`) |

> **핵심**: 서브도메인이 달라도(`service.naver.com` $	o$ `nid.naver.com`) 같은 회사 도메인이면 **Same-Site**로 인정됩니다!

## 4. CSRF(크로스 사이트 요청 위조) 공격의 실체

사용자가 인터넷 뱅킹(`bank.com`)에 로그인한 상태라고 가정해 봅시다.
브라우저에는 `bank.com`의 로그인 세션 쿠키가 저장되어 있습니다.

이때 사용자가 피싱 이메일의 링크를 눌러 해커의 사이트(`evil.com`)에 접속했습니다.
해커의 사이트 HTML에는 몰래 다음과 같은 코드가 숨겨져 있었습니다.

```html
<!-- evil.com 페이지 내부 -->
<form id="hackForm" action="https://bank.com/api/transfer" method="POST">
    <input type="hidden" name="to_account" value="hacker_1234" />
    <input type="hidden" name="amount" value="10000000" />
</form>
<script>
    document.getElementById("hackForm").submit();
</script>
```

사용자는 영문도 모른 채 `evil.com`을 보고 있었을 뿐인데, 브라우저는 폼을 전송하면서:
- "어? 목적지가 `bank.com`이네? 내가 가지고 있는 `bank.com` 세션 쿠키를 알아서 붙여서 보내야지!"
- 은행 서버 입장에서는 정상적인 로그인 세션 쿠키가 실려왔으므로, 해커 계좌로 1,000만 원 송금을 승인해 버립니다!

이것이 바로 **CSRF(교차 사이트 요청 위조)** 공격입니다.

## 5. SameSite 3총사의 동작 모드

SameSite 플래그는 이 Cross-Site 전송 규칙을 어떻게 정의할지에 따라 3가지 옵션을 제공합니다.

```
+-----------------------------------------------------------------------------------+
| SameSite 정책 비교                                                                |
+---------+--------------------+--------------------------------+-------------------+
| 정책    | Same-Site 요청     | Cross-Site Top-Level GET 탐색 | Cross-Site POST / |
|         |                    | (링크 클릭, GET 리다이렉트)    | Subresource (img) |
+---------+--------------------+--------------------------------+-------------------+
| Strict  | ✅ 쿠키 전송       | ❌ 쿠키 차단                   | ❌ 쿠키 차단      |
| Lax     | ✅ 쿠키 전송       | ✅ 쿠키 전송                   | ❌ 쿠키 차단      |
| None    | ✅ 쿠키 전송       | ✅ 쿠키 전송                   | ✅ 쿠키 전송 (*)  |
+---------+--------------------+--------------------------------+-------------------+
(*) Chrome 80+에서는 SameSite=None 설정 시 반드시 Secure 플래그가 붙어있어야만 수락됩니다!
```

1. **`SameSite=Strict`**:
   - 가장 엄격합니다. 사용자가 이메일이나 카카오톡 링크(`https://mail.com`)에서 은행 링크(`https://bank.com`)를 클릭해서 들어와도(Top-level GET), Cross-Site 탐색이므로 세션 쿠키를 보내지 않습니다. 사용자는 매번 새로 로그인해야 하는 불편함이 생깁니다.
2. **`SameSite=Lax` (현대 브라우저의 기본 표준)**:
   - "안전한 탐색(GET/HEAD 최상위 이동)은 봐주되, 위험한 상태 변경(POST나 비동기 fetch, img 태그)은 가차없이 차단한다!"
   - 사용자가 링크를 클릭해서 다른 사이트로 넘어갈 때는 세션이 유지되어 로그인 상태가 보존됩니다.
   - 하지만 해커 사이트에서 날리는 `<form method="POST">`나 `fetch(..., {method: 'POST'})`는 Cross-Site POST이므로 쿠키가 전송되지 않아 CSRF가 원천 차단됩니다!
3. **`SameSite=None`**:
   - 모든 Cross-Site 요청에 제약 없이 쿠키를 전송합니다.
   - 외부 위젯(유튜브 임베드 플레이어, PG 결제 팝업 등)이 필수적으로 세션을 공유해야 할 때 사용합니다.

## 6. 2020년 2월 Chrome 80 대참사: 결제 승인 후 세션 증발 사건

과거 크롬 79까지는 개발자가 `SameSite`를 명시하지 않으면(`Unspecified`) 브라우저가 이를 **`SameSite=None`**으로 취급했습니다.

하지만 구글 크롬 팀은 2020년 2월 **Chrome 80 업데이트**를 통해 두 가지 메가톤급 보안 정책을 강제 적용했습니다:
1. **Lax by Default**: `SameSite`를 지정하지 않은 모든 쿠키는 기본값을 **`Lax`**로 강제 승격한다!
2. **None Must Be Secure**: `SameSite=None`으로 명시한 쿠키는 반드시 **`Secure`** 플래그(HTTPS)가 함께 붙어있어야 하며, 그렇지 않으면 브라우저가 쿠키 자체를 거부한다!

### 이로 인해 터진 PG 결제 콜백 참사의 원리
대한민국의 수많은 PG 결제(KG이니시스, 나이스페이 등) 및 글로벌 결제 게이트웨이는 다음과 같은 흐름으로 동작했습니다:

```
[사용자 브라우저]                  [쇼핑몰 서버 (shop.com)]         [결제사 PG (pg-pay.com)]
       |                                     |                                   |
       | 1. 주문서 작성 및 결제 요청         |                                   |
       |------------------------------------>| (세션 발급: SESSIONID)            |
       | 2. PG사 결제창 팝업/리다이렉트      |                                   |
       |------------------------------------------------------------------------>|
       | 3. 카드 번호 입력 및 결제 승인 완료 |                                   |
       |                                     |                                   |
       | 4. PG사가 브라우저를 통해 쇼핑몰로 폼 전송 (Cross-Site Top-Level POST!) |
       |    <form method="POST" action="https://shop.com/checkout/callback">     |
       |    <input name="tx_id" value="TX_999"/>                                |
       |------------------------------------>|                                   |
       |                                     |                                   |
```

- 문제 발생:
  - PG사 도메인은 `pg-pay.com`이고 목적지는 `shop.com`입니다 $	o$ **Cross-Site 요청**!
  - 전송 방식은 `<form method="POST">`입니다 $	o$ **POST 요청**!
  - Chrome 80 이전: 쇼핑몰의 세션 쿠키가 정상 첨부되어 "아, 홍길동 고객님의 주문이 결제 완료되었구나!" 처리.
  - **Chrome 80 이후**: 쇼핑몰 세션 쿠키가 `SameSite` 미지정이었기 때문에 브라우저가 **`Lax`**로 처리 $	o$ **Cross-Site POST이므로 쿠키 첨부 전격 차단!**
  - 쇼핑몰 서버는 결제 결과 POST를 받았지만 세션 쿠키가 전혀 없어서 **"너 누구세요? 로그인 안 하셨는데요?"**라며 결제 실패 페이지를 띄우거나 로그인 페이지로 튕겨버린 것입니다!

### 실무 해결책
1. **GET 방식 리다이렉트 전환**: PG사 결제 콜백을 POST 대신 1회성 토큰을 쿼리스트링에 담아 302 리다이렉트(GET)로 복귀시킵니다. (`Lax`는 Top-level GET에서 쿠키를 전송하므로 안전하게 세션 복구).
2. **콜백 전용 쿠키 분리**: 결제 세션 식별 전용 임시 쿠키를 `SameSite=None; Secure`로 발급합니다.
3. **무상태 트랜잭션 토큰 바인딩**: 결제 요청 시 발급한 암호화된 주문 트랜잭션 ID(`order_token`)를 PG사에 파라미터로 넘겨주고, 콜백 바디로 돌려받아 세션 쿠키 없이도 DB에서 주문자를 찾아 매핑합니다.

## 7. 실무 아키텍처 점검표

| 보안 위험 요소 | 올바른 설정 및 대응책 |
|---|---|
| 세션 쿠키 자바스크립트 탈취 (XSS) | `HttpOnly` 필수 설정 (`document.cookie`로 읽기 불가) |
| 평문 통신 중 세션 도청 (Sniffing) | `Secure` 필수 설정 (오직 HTTPS 연결에서만 전송) |
| 폼 제출/비동기 호출 위조 (CSRF) | 세션 쿠키에 `SameSite=Lax` (기본값) 적용 + 민감 POST 요청에는 서버 발급 CSRF 토큰(Double Submit Cookie or Hidden Field) 교차 검증 |
| 외부 결제/OAuth POST 콜백 유실 | 전용 임시 토큰 쿠키에 `SameSite=None; Secure` 적용 또는 302 GET 리다이렉트 전환 |
