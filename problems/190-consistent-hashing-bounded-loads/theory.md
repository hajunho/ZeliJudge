# 분산 캐시 로드 밸런싱: Google Bounded Loads 일관된 해싱과 핫스팟 방어 심층 분석

## 1. 개요: 일관된 해싱(Consistent Hashing)의 기원과 한계

일관된 해싱(Consistent Hashing)은 1997년 David Karger 등에 의해 제안된 이후, 대규모 분산 캐시(Memcached, Redis), 분산 키-값 저장소(Amazon DynamoDB, Apache Cassandra), 그리고 CDN 프록시 라우팅의 핵심 근간으로 자리 잡았습니다.

### 1.1 Karger 해시 링과 최소 키 이동 보장
전통적인 모듈로 해싱($\text{hash}(key) \pmod N$)은 노드 수 $N$이 하나만 변경되어도 대부분의 키 매핑이 뒤바뀌어 대규모 캐시 미스 폭풍(Cache Miss Storm)을 유발합니다. 반면 일관된 해싱은 $0$부터 $2^{32}-1$까지의 원형 해시 공간(Hash Ring)을 구성하고, 노드가 추가되거나 제거될 때 오직 $O(K/N)$개의 키만 이동하도록 보장합니다.

가상 노드(Virtual Nodes, vnodes)를 노드당 수십~수백 개씩 배치함으로써 노드 간의 공간 점유율을 통계적으로 균등화할 수 있습니다.

### 1.2 표준 일관된 해싱의 아킬레스건: 핫키(Hot Key)와 무한 부하 편향
하지만 표준 일관된 해싱은 **"부하(Load)에 대한 상한선(Bound)이 전혀 없다"**는 치명적인 구조적 결함을 안고 있습니다.

현실의 인터넷 트래픽은 균등 분포가 아닌 **지프(Zipfian) 분포 또는 멱법칙(Power-law)**을 따릅니다:
- 상위 1%의 인기 콘텐츠(월드컵 생중계, 초대형 할인 상품, 바이럴 뉴스)가 전체 트래픽의 80~90%를 차지합니다.
- 가상 노드가 링 전체에 아무리 완벽하게 퍼져 있어도, 특정 핫키 $k_{hot}$의 해시값 $\text{hash}(k_{hot})$은 **오직 하나의 1차 노드($S_{hot}$)로만 모든 요청을 전송**합니다.
- 결과적으로 노드의 하드웨어 처리 한계(Network Bandwidth, CPU, Memory)를 초과하게 됩니다.

## 2. 핫스팟 캐스케이딩 연쇄 붕괴 (Cascading Failure Collapse)

핫키 트래픽이 단일 노드 $S_{hot}$에 집중되면 다음과 같은 연쇄 파멸 사이클이 작동합니다:

```text
[Hot Key Surge: 50,000 RPS]
            │
            ▼
┌───────────────────────┐
│     Node S_hot        │ ──> CPU 100% 포화 / OOM 발생 ──> [CRASH / DEAD]
│ (Max Capacity: 20,000)│
└───────────────────────┘
            │
            ▼ (해시 링에서 S_hot 제거됨)
┌───────────────────────┐
│     Node S_next       │ <── S_hot의 기존 부하 50,000 RPS가 고스란히 유입!
│ (Max Capacity: 20,000)│ ──> 1초 만에 CPU 100% 포화 ──> [CRASH / DEAD]
└───────────────────────┘
            │
            ▼ (해시 링에서 S_next 제거됨)
┌───────────────────────┐
│     Node S_third      │ ──> 연쇄 폭사 (Cascading Failure)
└───────────────────────┘
            │
            ▼
[전체 클러스터 전멸 & 백엔드 오리진 DB 직격 참사]
```

이 연쇄 붕괴는 노드가 다운될수록 남은 노드들이 감당해야 할 핫키 부하 밀도가 기하급수적으로 증가하기 때문에 발생합니다.

## 3. Google Research: Bounded Loads Consistent Hashing (Mirrokni et al. 2017)

Google Research의 Vahab Mirrokni, Mikkel Thorup, Morteza Zadimoghaddam 연구팀은 이 문제를 해결하기 위해 2017년 ACM ICDCN에서 **"Consistent Hashing with Bounded Loads"** 알고리즘을 발표했습니다.

### 3.1 수학적 상한선 정의 (Bounded Capacity)
클러스터 내 총 활성 요청량을 $M$, 활성 노드 수를 $N$이라 할 때, 평균 부하는 $L_{avg} = \frac{M}{N}$입니다.
시스템 관리자는 허용 오차 계수 $\epsilon \ge 0$ (예: $\epsilon = 0.25$, 즉 25% 초과 허용)을 지정합니다.

각 노드가 수용할 수 있는 최대 요청 상한선 $C$는 다음과 같이 정의됩니다:

$$C = \left\lceil (1 + \epsilon) \cdot \frac{M}{N} \right\rceil$$

어떤 상황에서도 개별 노드의 부하 $L(S)$는 $C$를 초과할 수 없습니다:

$$\forall i \in [1, N], \quad L(S_i) \le (1 + \epsilon) \cdot \frac{M}{N} + 1$$

### 3.2 스필오버(Spillover) 라우팅 메커니즘
요청 $(req\_id, key)$가 유입되었을 때의 라우팅 절차:
1. 키 $k$의 해시값 $\text{hash}(k)$를 계산하여 링 상의 첫 번째 시계 방향 노드 $S_0$을 조회합니다 (1차 소유 노드).
2. $S_0$의 현재 부하 $L(S_0)$이 $C$ 미만이면 즉시 $S_0$에 할당합니다 ($S_0$에 캐시 적중).
3. 만약 $L(S_0) \ge C$라면, $S_0$는 포화 상태이므로 요청을 수용하지 않습니다.
4. 해시 링을 시계 방향으로 계속 전진하면서 다음 가상 노드의 물리 노드 $S_1, S_2, \dots$를 순회합니다:
   - 만난 노드 중 $L(S_i) < C$를 만족하는 첫 번째 노드에 요청을 할당합니다 (**Spillover 발생**).
5. 만약 링 전체를 한 바퀴 돌았는데도 모든 노드가 포화 상태라면, 현재 부하가 가장 적은 노드($\arg\min_i L(S_i)$)에 최소 부하 우선 할당합니다.

### 3.3 수학적 보장과 로컬리티(Locality) 특성
- **최대 부하 상한 보장**: 어떤 노드도 $(1+\epsilon) \times \text{평균}$을 초과하지 않으므로, 핫키가 아무리 몰려도 단일 노드가 과부하로 쓰러지지 않습니다.
- **최적의 캐시 지역성 보존**: 오직 $(1+\epsilon)$을 초과하는 잉여 트래픽만이 링의 인접 노드로 완충 분산되며, 나머지 기본 트래픽은 여전히 1차 노드에 집중되어 높은 캐시 적중률을 유지합니다.
- **최소 키 이동 보장**: 노드가 추가되거나 제거될 때도 기존 일관된 해싱의 $O(1/N)$ 재배치 성질이 보존됩니다.

## 4. 업계 적용 사례: Envoy Proxy와 Vimeo CDN

### 4.1 Vimeo 엣지 프록시의 대전환
Vimeo 엔지니어링 팀은 비디오 스트리밍 캐시 클러스터에서 핫스팟으로 인해 노드가 연쇄 폭사하던 고질적 장애를 해결하기 위해 Google Bounded Loads 알고리즘을 도입했습니다.
- 결과: 단일 노드 CPU 포화 및 캐스케이딩 장애 0건 달성.
- 캐시 적중률: 단순 로드밸런싱 대비 80% 이상의 높은 적중률 복원.

### 4.2 Envoy Proxy의 `hash_balance_factor`
Vimeo와 Google의 연구 결과는 클라우드 네이티브 표준 L7 프록시인 **Envoy Proxy**에 공식 채택되었습니다:
- 클러스터 설정의 `ring_hash` 로드 밸런서에서 `hash_balance_factor` 파라미터로 제공됩니다.
- `hash_balance_factor: 125`로 설정 시 $\epsilon = 0.25$ (평균 부하의 125% 상한선)가 적용되어, 상한선 초과 시 해시 링을 시계 방향으로 스필오버 탐색합니다.
