# [CS-110] 연결 1개 들어왔는데 왜 워커 100개가 동시에 깨어나서 CPU 100%를 찍어요?!: 리눅스 천둥 치는 무리(Thundering Herd)와 `EPOLLEXCLUSIVE` & `SO_REUSEPORT`

> **"선생님! 멀티코어를 활용하려고 워커 프로세스를 32개 띄우고 리슨 소켓 하나를 공유했거든요? 그런데 초당 연결이 몇천 개 들어오자마자 CPU가 100% 치솟고 서버가 먹통이 돼요! 연결 1개 들어올 때마다 32개 워커가 동시에 깨어나서 발작을 일으키는데 왜 이러죠?!"**
> 
> 고성능 HTTP 서버를 개발하던 주니어 시스템 프로그래머 하준이는 멀티프로세스 모델을 적용했습니다.
> 메인 프로세스가 `socket()`과 `bind()`, `listen()`을 수행한 뒤, `fork()`를 호출하여 32개의 워커 프로세스를 생성했습니다.
> 모든 워커는 동일한 리슨 소켓을 각자의 `epoll`에 등록하고 `epoll_wait()`를 돌렸습니다.
> 
> 하지만 벤치마크 툴(wrk)로 부하를 거는 순간, 서버는 마비되었습니다.
> 클라이언트 연결 1개가 들어올 때마다 32개의 워커 프로세스가 일제히 비명을 지르며 깨어났습니다.
> 32개 프로세스가 동시에 `accept()`를 호출해 난투극을 벌였고, 단 1개만 연결을 낚아채고 나머지 31개는 `EAGAIN (Resource temporarily unavailable)` 에러를 맞고 다시 잠들기를 무한 반복했습니다!
> 
> "연결 1개에 왜 32개가 다 깨어나서 싸우죠?!"  
> 시니어 커널 엔지니어는 씩 웃으며 리눅스 커널 소스코드를 가리켰습니다.
> "하준 씨, 컴퓨터 과학 역사상 가장 유명한 '천둥 치는 무리(Thundering Herd)'의 덫에 걸리셨군요. 들판에 먹이 1개를 던져놓고 100마리 소 떼를 동시에 깨우면 들판이 초토화되는 법입니다."

---

## 1. 천둥 치는 무리 문제(Thundering Herd Problem)란?

동일한 자원(예: 포트 80 리슨 소켓)을 여러 프로세스나 스레드가 공유하여 대기하고 있을 때, **단 하나의 이벤트(신규 연결 1개)가 발생했음에도 커널이 대기 중이던 모든 프로세스를 한꺼번에 깨워버리는 현상**을 의미합니다.

```
[클라이언트 SYN 인입 (연결 1개)]
             │
             ▼
      [리슨 소켓 (Listen Socket)]
             │
   ┌─────────┼─────────┬─────────┐
   │         │         │         │  🚨 커널이 모든 대기 프로세스를 동시 기상!
   ▼         ▼         ▼         ▼
[워커 1]   [워커 2]   [워커 3]   [워커 32]
 (깨어남)   (깨어남)   (깨어남)   (깨어남)
   │         │         │         │
   │ accept()│ accept()│ accept()│ accept()
   ▼         ▼         ▼         ▼
 [성공!🎉]  [EAGAIN❌] [EAGAIN❌] [EAGAIN❌]
```

### 참사의 결과:
1. **극심한 컨텍스트 스위칭(Context Switching)**: 1개의 연결을 맺기 위해 32번의 기상, 스케줄링, 수면 사이클이 강제됩니다.
2. **CPU 캐시 스래싱 (Cache Thrashing)**: 모든 코어가 동시에 깨어나 커널 락을 잡으려고 경합하면서 CPU L1/L2 캐시가 전멸합니다.
3. **처리량 붕괴**: 실제 네트워크 I/O는 얼마 되지도 않는데, CPU가 '일어났다 다시 자는 헛짓'에 100% 소모되어 서버가 다운됩니다.

## 2. 역사적 진화와 3대 해결책

### 1) Nginx의 유저 공간 해결책: `accept_mutex`
- 리눅스 초기, Nginx는 커널의 문제를 피하기 위해 공유 메모리 기반의 유저 락인 **`accept_mutex`**를 도입했습니다.
- 오직 락을 쥔 단 1개의 워커만 리슨 소켓을 자신의 epoll에 등록하고, 나머지는 등록을 해제하여 1명만 깨어나도록 강제했습니다.
- **한계**: 연결이 들어올 때마다 유저 레벨에서 락을 획득/반환하는 오버헤드가 발생했습니다.

---

### 2) 커널 레벨의 단일 기상 보장: `EPOLLEXCLUSIVE` (Linux 4.5+)
- 리눅스 4.5 커널에서 도입된 혁신적인 epoll 플래그입니다.
- 워커가 리슨 소켓을 등록할 때 `EPOLLEXCLUSIVE` 플래그를 설정하면:
  ```c
  struct epoll_event ev;
  ev.events = EPOLLIN | EPOLLEXCLUSIVE;
  epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);
  ```
- **원리**: 연결이 들어오면 커널이 대기 중인 여러 epoll 인스턴스 중 **정확히 1개(또는 소수)만 선별하여 깨웁니다.**
- **결과**: 나머지 31개 워커는 꿀잠을 자며, 불필요한 기상과 `EAGAIN` 에러가 0이 됩니다!

---

### 3) 완전한 소켓 격리와 커널 부하 분산: `SO_REUSEPORT` (Linux 3.9+)
- 가장 현대적이고 완벽한 아키텍처입니다.
- 여러 워커가 1개의 리슨 소켓을 공유하지 않고, **각 워커 프로세스가 독립적인 소켓을 열어 동일한 포트(80)에 바인드**합니다:
  ```c
  int opt = 1;
  setsockopt(listen_fd, SOL_SOCKET, SO_REUSEPORT, &opt, sizeof(opt));
  bind(listen_fd, ...);
  ```
- **원리**: 각 소켓마다 독립적인 수신 큐(Listen Queue)가 생성되며, 리눅스 커널이 클라이언트의 IP/Port 해시(4-Tuple Hash)를 기반으로 **직접 분산하여 해당 워커의 큐에만 패킷을 넣어줍니다.**
- **결과**: 락 경합이 원천적으로 0이며, Nginx 1.9.1+부터 `reuseport` 옵션을 켜면 성능이 2~3배 이상 수직 상승합니다!
