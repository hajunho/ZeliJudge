# 로드 밸런싱의 함정과 라운드 로빈 vs 최소 활성 연결 (Round Robin vs Least Connections)

## 1. 로드 밸런싱의 치명적 함정: 요청 비용의 비대칭성 (Cost Heterogeneity)

### 1.1 마트 계산대의 비극: 카트 5개 손님과 껌 1개 손님
대형 마트에 계산대 3곳이 열려 있습니다.  
안내 직원이 손님들을 질서정연하게 1명씩 번갈아 가며 계산대로 안내합니다.
> **"1번 손님은 1번 계산대, 2번 손님은 2번 계산대, 3번 손님은 3번 계산대, 4번 손님은 다시 1번 계산대..."**

이것이 바로 가장 널리 쓰이는 기본 로드 밸런싱 알고리즘인 **라운드 로빈 (Round Robin)**입니다.

```text
[손님들의 장바구니 현황]
- 손님 A: 라면 1봉지 (계산 시간: 1초)
- 손님 B: 껌 1통 (계산 시간: 1초)
- 손님 C: 카트 5개에 가득 담은 업소용 식자재 500개 (계산 시간: 60초)
- 손님 D: 카트 5개에 가득 담은 업소용 식자재 500개 (계산 시간: 60초)
```

만약 우연히 1번 계산대로 카트 5개짜리 손님(C, D)들이 연달아 배정된다면 어떻게 될까요?
- **1번 계산대**: 앞 손님 계산이 2분 넘게 안 끝나서 뒤에 줄 선 손님 20명이 멱살을 잡고 폭동을 일으킵니다 (CPU 100%, 스레드 풀 고갈, 타임아웃).
- **2번, 3번 계산대**: 라면 1봉지 손님을 1초 만에 보내고 점원이 하품하며 텅텅 놀고 있습니다.

안내 직원은 **"손님 수를 3개 계산대에 똑같이 1:1:1로 나눴으니 완벽하게 공평하다"**고 생각했지만,  
실제로는 **1번 계산대만 과부하로 터져나가고 마트 전체의 평균 대기 시간과 P99 지연시간이 폭발**했습니다.

## 2. 왜 실무 웹 서비스에서 라운드 로빈은 위험한가?

### 2.1 현실의 모든 HTTP 요청은 처리 비용이 제각각이다
초보 개발자나 비전공자는 "서버 3대에 트래픽을 33%씩 똑같이 나누면 부하도 33%씩 균등하겠지?"라고 착각합니다.  
하지만 실무 백엔드 시스템에 인입되는 API 요청의 소요 시간(Duration)은 극단적으로 비대칭적입니다:

| 요청 유형 | 소요 시간 | 자원 점유 (CPU / Memory / DB) |
|:---|:---:|:---|
| 단순 헬스체크 (`/healthz`) | 1ms | 거의 없음 |
| 유저 프로필 단순 조회 (`/users/me`) | 5ms | DB 인덱스 1회 조회 |
| 월간 매출 엑셀 다운로드 (`/reports/export`) | 3,000ms | 대량 DB 풀스캔 + 메모리 OOM 유발 |
| AI 문서 임베딩 & PDF 변환 (`/ai/process`) | 5,000ms | CPU 멀티코어 100% 점유 |

### 2.2 라운드 로빈의 맹점
라운드 로빈은 **"모든 요청의 실행 시간($Duration$)이 동일하다"**는 비현실적인 가정하에만 유효합니다.  
서버가 이전 요청을 처리하느라 헐떡이고 있는지, 아니면 이미 일을 끝내고 유휴(Idle) 상태인지 **서버의 내부 상태를 전혀 보지 않는 무상태(Stateless) 라우팅**이기 때문에 필연적으로 특정 서버에 무거운 요청이 겹치는 **핫스팟(Hotspot / Convoy Effect)**을 유발합니다.

## 3. 해결책: 최소 활성 연결 (Least Connections / Least In-Flight)

AWS ALB, Nginx, Envoy, HAProxy 등 엔터프라이즈 로드 밸런서는 이 문제를 **Least Connections (최소 활성 연결)** 알고리즘으로 해결합니다.

```
                  [클라이언트 요청 인입]
                           │
                           ▼
                 ┌───────────────────┐
                 │   Load Balancer   │
                 └───────────────────┘
               /           │           \
     (in_flight: 5)  (in_flight: 0)  (in_flight: 1)
            /              │              \
      [Server 0]      [Server 1]      [Server 2]
     (무거운 작업 중)   (완전 유휴)    (가벼운 작업 중)
                           ▲
                           │
             ★ 새 요청은 in_flight가 가장 적은
               Server 1로 자동 라우팅!
```

### 3.1 동작 원리
1. 로드 밸런서는 각 백엔드 서버가 현재 처리 중인 **활성 요청 수(`in_flight`)**를 실시간으로 추적합니다.
   - 요청을 보낼 때: `in_flight += 1`
   - 요청 완료 응답을 받을 때: `in_flight -= 1`
2. 새로운 요청이 도착하면, **현재 `in_flight`가 가장 작은 서버**를 선택하여 라우팅합니다.
   - 만약 최소 활성 연결 수를 가진 서버가 여러 대라면(Tie), 서버 번호(ID)가 가장 작은 서버를 우선 선택합니다 (결정론적 Tie-breaker).
3. **자가 적응적 부하 평탄화 (Self-Balancing)**:
   - 3초짜리 무거운 엑셀 다운로드를 배정받은 서버는 오랫동안 `in_flight`가 높게 유지되므로, 로드 밸런서는 해당 서버로 추가 요청을 보내지 않습니다.
   - 1ms짜리 가벼운 조회를 빠르게 끝낸 서버들은 즉시 `in_flight = 0`이 되므로, 신규 요청들이 자연스럽게 유휴 서버들로 집중됩니다.
   - 결과적으로 클러스터 전체의 동시 활성 요청 수(Peak In-Flight)가 최소화되고, 서버 간 부하 편차가 드라마틱하게 사라집니다!

## 4. 시뮬레이터 아키텍처 및 메트릭

### 4.1 이산 틱(Discrete Tick) 라이프사이클
한 틱(`current_tick`)에서의 이벤트 발생 순서:
1. **신규 인입 요청 라우팅 (Arrival & Routing)**:
   - 해당 틱에 도착한 요청 `Request(id, duration)`을 전략(RR vs LC)에 따라 백엔드 서버에 배정합니다.
   - 배정된 서버: `in_flight += 1`, `peak_in_flight = max(peak_in_flight, in_flight)`.
   - 완료 예정 틱: `finish_tick = current_tick + duration`.
2. **틱 전진 및 요청 완료 (Tick Step & Completion)**:
   - `STEP 1`이 호출되면 `current_tick += 1`로 시간이 흐릅니다.
   - 전진한 새로운 시각 `current_tick`에 `finish_tick == current_tick`을 만족하는 모든 완료 요청들을 종료 처리합니다:
     - `in_flight -= 1`
     - `completed_requests += 1`

### 4.2 핵심 지표 (Metrics)
- `PEAK_IN_FLIGHT`: 시뮬레이션 전 기간 동안 **어떤 단일 서버라도 기록한 순간 최대 활성 연결 수**.
  - 시스템의 스레드 풀 크기나 메모리 한계치(OOM)를 결정짓는 핵심 지표.
  - Round Robin에서는 핫스팟으로 인해 치솟고, Least Connections에서는 낮게 억제됨.
- `SERVER_ALLOCATIONS`: 각 서버에 누적 배정된 총 요청 수 `[s0, s1, ...]`.
- `ACTIVE_IN_FLIGHT`: 현재 클러스터 전체에서 실행 중인 총 활성 요청 수.
