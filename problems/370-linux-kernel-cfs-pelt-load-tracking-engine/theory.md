# Linux Kernel CFS PELT (Per-Entity Load Tracking) 아키텍처 및 수학적 모델링 심층 분석

## 1. 개요 및 배경

멀티코어/SMP 시스템에서 운영체제 스케줄러의 두 가지 핵심 임무는 다음과 같습니다:
1. **부하 분산(Load Balancing)**: 모든 코어가 균등하게 일하도록 스레드를 적절히 분배.
2. **동적 전압 및 주파수 스케일링(DVFS / Energy-Aware Scheduling)**: 워크로드 크기에 맞추어 CPU 클록 주파수를 최적화하여 전력 소모 최소화.

이를 위해서는 "이 스레드가 얼마나 많은 CPU 파워를 필요로 하는가?"와 "이 CPU 코어가 얼마나 바쁜가?"를 정밀하게 측정해야 합니다.

과거 리눅스는 런큐에 매달린 태스크의 개수(nr_running)나 슬립 시간 평균을 보았으나, 1초 동안 100% 도는 단 1개의 태스크와 1초에 1ms씩만 도는 10개의 태스크를 구별하지 못해 심각한 스케줄링 왜곡이 발생했습니다.

리눅스 3.8에서 폴 터너(Paul Turner)에 의해 제안되고 뱅상 기토(Vincent Guittot)에 의해 완성된 **PELT(Per-Entity Load Tracking)**는 각 스케줄링 엔티티(`struct sched_entity`)와 런큐(`struct cfs_rq`)마다 고유한 지수 감쇠 누적기를 부여하여 이 문제를 해결했습니다.

## 2. 수학적 모델: 32ms 반감기 지수 감쇠

PELT는 시간을 $P = 1024\,\mu	ext{s}$ 단위의 주기로 이산화(Discretization)합니다.
연속적인 시간 $t$에서의 부하 $L(t)$는 다음 미분 방정식으로 표현됩니다:

$$rac{dL}{dt} = -rac{\ln 2}{T_{1/2}} L + u(t)$$

여기서 $T_{1/2} = 32 	imes 1024\,\mu	ext{s} = 32768\,\mu	ext{s} pprox 32.768\,	ext{ms}$ 입니다.

이산 주기 $k$에 대한 감쇠율 $y$는:
$$y = 2^{-1/32} pprox 0.97857206$$

따라서 $n$개 주기가 지난 후의 값은:
$$L_{n} = L_0 	imes y^n + \sum_{i=0}^{n-1} u_i \cdot y^{n-1-i}$$

지속적으로 100% CPU를 사용하는 태스크의 최대 누적값은 무한 등비급수 합 공식에 의해 유계(Bounded)됩니다:
$$	ext{MAX\_SUM} = rac{1024}{1 - y} pprox 47742$$

## 3. 3대 신호의 분리

| 신호 | 정의 | 반영 요소 | 주요 사용자 |
| :--- | :--- | :--- | :--- |
| **`util_avg`** | 실제 CPU 코어를 점유한 시간 비율 ($0 \sim 1024$) | 우선순위(Weight) 무관, 순수 실행 시간만 | **`schedutil` CPUFreq 거버너** |
| **`load_avg`** | 런큐 대기 시간 + 실행 시간 $	imes$ 우선순위 가중치 | 태스크 nice 값에 따른 비례 가중치 | **CFS 로드 밸런서 (`load_balance`)** |
| **`runnable_avg`** | 런큐 대기 시간 + 실행 시간 ($0 \sim 1024$) | 우선순위 무관, 큐 체류 전체 시간 | **EAS (Energy-Aware Scheduling) 과포화 판정** |

### 3.1 왜 `util_avg`는 우선순위와 무관한가?
Nice 값이 -20인 고우선순위 태스크라도 실제 CPU를 10%만 쓴다면 CPU 주파수를 100%로 올릴 필요가 없습니다. CPU 클록은 순수한 시간 점유율(`util_avg`)에 비례해야 에너지를 절약할 수 있습니다.
반면 부하 분산(`load_avg`)은 고우선순위 태스크가 머무는 코어에 더 많은 가중치를 부여해야 공정한 CPU 시간 배분이 가능합니다.

## 4. `schedutil` 거버너와의 연동

리눅스 기본 CPU 주파수 스케일러인 `schedutil`은 인터럽트 컨텍스트에서 직접 PELT의 `util_avg`를 읽어 목표 CPU 용량을 결정합니다:

$$	ext{target\_cap} = \min\left(1024, 	ext{util\_avg} 	imes 1.25ight)$$

$1.25$배(25% 마진)를 두는 이유는 태스크의 부하가 갑자기 치솟을 때 CPU 주파수가 한 발 앞서 상승하여 지연 시간(Latency) 스파이크를 방지하기 위함입니다.
