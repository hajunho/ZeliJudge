# [대용량 데이터베이스 파티셔닝(Table Partitioning)과 파티션 프루닝(Partition Pruning) 아키텍처]

## 1. 대용량 테이블에서 B-Tree 인덱스가 무너지는 이유

단일 RDBMS 테이블의 행 수가 수천만~수억 건을 넘어가면 다음과 같은 물리적 한계가 발생합니다:
1. **인덱스 비대화와 버퍼 풀(Buffer Pool) 스와핑**:
   - 데이터가 1억 건이면 인덱스 크기만 수십 GB에 달합니다.
   - 인덱스 리프 페이지가 메모리에 다 올라가지 못하므로, 조회가 발생할 때마다 디스크 랜덤 I/O가 폭증합니다.
2. **락 경합과 동시성 저하**:
   - B-Tree의 깊이(Depth)가 깊어지고 페이지 분할(Page Split)이 빈번해져 인덱스 래치(Latch) 경합이 심화됩니다.
3. **대량 데이터 폐기(Retention) 시의 재앙**:
   - 3년 지난 오래된 로그 1,000만 건을 지우기 위해 `DELETE FROM logs WHERE created_at < ...`을 실행하면 수 시간 동안 Undo Log와 Redo Log가 폭발하고 테이블 락이 걸립니다.

이를 근본적으로 해결하는 기법이 바로 물리적 분할 저장인 **테이블 파티셔닝(Table Partitioning)**입니다.

---

## 2. 테이블 파티셔닝의 유형과 장점

### (1) 레인지 파티셔닝 (Range Partitioning)
- 특정 컬럼(날짜, ID 등)의 연속적인 값 범위를 기준으로 파티션을 나눕니다.
- 시계열 로그, 결제 내역 등 날짜 기반 데이터 관리에 가장 널리 사용됩니다.

### (2) 리스트 파티셔닝 (List Partitioning)
- 국가 코드, 지역, 부서 ID 등 불연속적인 이산 값 목록을 기준으로 분할합니다.

### (3) 해시 및 키 파티셔닝 (Hash / Key Partitioning)
- 특정 컬럼의 해시 함수를 통해 데이터를 파티션에 균등 분산시킵니다.

### 🌟 파티셔닝의 최대 장점: 0초 만에 끝나는 대용량 데이터 삭제 (Drop Partition)
- `DELETE` 구문 대신 파티션 자체를 날리는 `ALTER TABLE logs DROP PARTITION p2023_01;`을 실행하면, 파일 시스템 레벨에서 해당 파티션 물리 파일만 `rm` 처리하므로 **1,000만 건의 데이터도 단 0.1초 만에 흔적도 없이 삭제**할 수 있습니다.

---

## 3. 핵심 원리: 파티션 프루닝 (Partition Pruning)

파티셔닝의 존재 이유이자 성능의 핵심은 **파티션 프루닝(Partition Pruning, 가지치기)**입니다.

```text
[클라이언트 쿼리: WHERE created_at BETWEEN '2026-08-01' AND '2026-08-15']
                             │
                             ▼
                [SQL 옵티마이저 (CBO)]
       파티션 정의 분석: 8월 데이터는 오직 p2026_08에만 존재!
                             │
            ┌────────────────┼────────────────┐
            ▼ (스킵!)        ▼ (스캔!)        ▼ (스킵!)
       [p2026_07]       [p2026_08]       [p2026_09]
        (파일 미열림)     (물리 I/O 발생)    (파일 미열림)
```

- 옵티마이저는 쿼리의 `WHERE` 절을 분석하여 조회 대상 데이터가 절대 존재할 수 없는 파티션은 실행 계획에서 완전히 배제합니다.
- 100개 파티션 중 1개만 스캔한다면, I/O 비용은 즉시 1/100로 격감합니다.

## 4. 실무에서 빈번한 '파티션 프루닝 실패' 3대 함정

### 함정 1: 파티션 키 컬럼에 가공 함수 사용 (Non-SARGable)
```sql
-- ❌ 프루닝 실패: DATE() 함수로 인해 컴파일 시점에 파티션 식별 불가 -> 전 파티션 풀 스캔!
SELECT * FROM payment_logs WHERE DATE(created_at) = '2026-08-15';

-- ⭕ 프루닝 성공: 원본 컬럼을 유지하고 범위를 지정
SELECT * FROM payment_logs 
WHERE created_at >= '2026-08-15 00:00:00' AND created_at < '2026-08-16 00:00:00';
```

### 함정 2: 암시적 형변환 (Implicit Type Conversion)
- 파티션 키가 문자열인데 숫자로 넘기거나, 정수인데 문자열로 넘기면 DB 엔진이 내부적으로 `CAST(col AS ...)`를 호출하여 인덱스와 프루닝이 모두 파괴됩니다.

### 함정 3: 파티션 키 없는 검색
- `WHERE user_id = 12345`처럼 파티션 키(`created_at`)가 조건에 없으면, 유저 12345가 어느 월에 결제했을지 알 수 없으므로 모든 월의 파티션을 다 뒤져야 합니다.
- **실무 해결책**: 이 경우 글로벌 세컨더리 인덱스(Global Secondary Index) 또는 역방향 조회 테이블(Mapping Table)을 별도로 구성해야 합니다.
