# HTTP/2 멀티플렉싱의 역설과 TCP Head-of-Line 블로킹 & HTTP/3 QUIC

## 1. 고속도로의 비극: 6개 차선을 1개로 합쳤더니 생긴 일

### 1.1 앞차 1대 펑크 났다고 뒤따르던 100대가 멈춰 선 참사
서울에서 부산으로 향하는 고속도로를 상상해 봅시다.

```text
[HTTP/1.1 고속도로 (6개 독립 차선)]
차선 1: [차량 A (HTML)] ──> 펑크 발생! (지연)
차선 2: [차량 B (CSS)]  ──────────────> 씽씽 달림 (정상 도착)
차선 3: [차량 C (JS)]   ──────────────> 씽씽 달림 (정상 도착)
차선 4: [차량 D (IMG1)] ──────────────> 씽씽 달림 (정상 도착)
차선 5: [차량 E (IMG2)] ──────────────> 씽씽 달림 (정상 도착)
차선 6: [차량 F (IMG3)] ──────────────> 씽씽 달림 (정상 도착)
=> 차량 A 1대만 늦고, 나머지 5대는 제시간에 도착!

[HTTP/2 고속도로 (단 1개의 좁은 단일 차선에 6대를 줄줄이 비엔나로 엮음)]
단일 차선: ──> [차량 F] ─> [차량 E] ─> [차량 D] ─> [차량 C] ─> [차량 B] ─> [차량 A (펑크!)]
=> 앞서가던 차량 A 1대가 멈추자, 아무 문제 없던 B, C, D, E, F까지 모조리 멈춰 섬!
   (TCP 계층의 Head-of-Line Blocking 참사)
```

2015년 등장한 **HTTP/2**는 브라우저가 수많은 TCP 연결을 맺는 오버헤드를 없애기 위해,  
**"단 1개의 TCP 연결 위에 모든 요청/응답 스트림을 멀티플렉싱(Multiplexing)하여 한 줄로 전송"**하는 혁신을 도입했습니다.

유선 광랜처럼 패킷 손실이 거의 없는 쾌적한 환경에서는 HTTP/2가 압도적으로 빠릅니다.  
하지만 **지하철, 엘리베이터, 불안정한 카페 Wi-Fi, 모바일 LTE/5G**처럼 패킷 손실률이 1~2%만 발생하는 환경에 진입하면 경악스러운 일이 벌어집니다.  
**"HTTP/2가 구버전인 HTTP/1.1보다 훨씬 더 느려지는 역전 현상"**이 발생하는 것입니다!

## 2. 왜 HTTP/2는 패킷 1개 유실에 전체가 마비되는가?

### 2.1 전송 계층(TCP)의 엄격한 순서 보장 (In-Order Delivery)
TCP는 신뢰성 있는 통신을 보장하기 위해 **"바이트 스트림의 순서가 단 1바이트도 틀어지지 않고 순서대로 도착해야만 수신 버퍼에서 애플리케이션(브라우저)으로 데이터를 올려보낸다"**는 철칙을 가집니다.

```
[HTTP/2 단일 TCP 스트림 패킷 인터리빙]
송신 순서: [Stream 1-P0] [Stream 2-P0] [Stream 3-P0] [Stream 4-P0] ...
               │
          (네트워크에서 유실!)
               ▼
커널 수신 버퍼: [유실 구멍] [Stream 2-P0 도착] [Stream 3-P0 도착] [Stream 4-P0 도착]
               │
               ▼
OS 커널 TCP 스택의 판정:
"Stream 1-P0이 아직 안 왔으니, 그 뒤에 도착한 Stream 2, 3, 4 패킷들은
 애플리케이션(브라우저)에 절대 넘겨줄 수 없다! 버퍼에 대기하라!"
```

- **결과**: `Stream 1`의 패킷 1개가 유실되었을 뿐인데, 정상적으로 도착한 `Stream 2`의 CSS, `Stream 3`의 JavaScript, `Stream 4`의 폰트 파일까지 모조리 OS 커널 버퍼에 갇혀 **전체 페이지 렌더링이 영구 동결(TCP Head-of-Line Blocking)**됩니다.
- 패킷 재전송(Retransmission, RTT)이 완료되어 유실된 조각이 채워질 때까지 무관한 모든 스트림이 통째로 멈춰 섭니다.

## 3. 해결책: HTTP/3와 UDP 기반 QUIC 프로토콜

구글과 IETF는 이 문제를 TCP 위에서는 영원히 해결할 수 없다는 것을 깨닫고,  
OS 커널에 굳어진 TCP 대신 **UDP 위에서 독립된 스트림 제어를 구현한 QUIC (HTTP/3)**을 발표했습니다.

```
[HTTP/3 QUIC의 독립 스트림 구조 (UDP 기반)]
Stream 1 (UDP): [P0 유실! 재전송 대기...] ──────────> (Stream 1만 지연)
Stream 2 (UDP): [P0 도착] ──────────────────────────> ★ 즉시 브라우저로 전달 (0초 지연!)
Stream 3 (UDP): [P0 도착] ──────────────────────────> ★ 즉시 브라우저로 전달 (0초 지연!)
Stream 4 (UDP): [P0 도착] ──────────────────────────> ★ 즉시 브라우저로 전달 (0초 지연!)
```

### 3.1 QUIC의 독립 스트림 (Independent Byte Streams)
1. QUIC은 단일 연결을 공유하지만, **각 스트림마다 독립된 패킷 번호와 흐름 제어**를 적용합니다.
2. `Stream 1`의 패킷이 유실되어 재전송 중이더라도, `Stream 2, 3, 4`의 정상 도착 패킷은 **TCP처럼 다른 스트림을 기다리지 않고 즉시 브라우저 애플리케이션으로 전달**됩니다.
3. 따라서 패킷 유실률이 5%에 달하는 열악한 무선 네트워크 환경에서도 HTTP/3는 다른 스트림의 HOL 블로킹 없이 **초고속 웹 로딩 속도를 유지**합니다.

## 4. 3대 프로토콜 비교 요약

| 프로토콜 | 전송 계층 | 연결 수 | 패킷 1개 유실 시 영향 | HOL 블로킹 수준 |
|:---|:---:|:---:|:---|:---|
| **HTTP/1.1** | TCP | 6개 병렬 연결 | 해당 연결 1개만 지연 (나머지 5개 정상) | 연결 단위 HOL 블로킹 |
| **HTTP/2** | TCP | 1개 단일 연결 | **연결에 묶인 모든 스트림 동시 마비** | **치명적 TCP 계층 전체 HOL 블로킹** |
| **HTTP/3 (QUIC)** | UDP | 1개 단일 연결 | **유실된 스트림 1개만 지연 (나머지 즉시 완료)** | **HOL 블로킹 완전 면역 (0%)** |
