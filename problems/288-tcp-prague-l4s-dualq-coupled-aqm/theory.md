# 인터넷 전송 계층의 혁명: L4S (Low Latency, Low Loss, Scalable Throughput), DualQ Coupled AQM, 그리고 TCP Prague 이론 백서

## 1. 버퍼블로트(Bufferbloat)와 고전적 혼잡 제어의 근본적 한계

1986년 반 제이콥슨(Van Jacobson)이 고안한 TCP Reno 이래, 인터넷의 혼잡 제어 알고리즘(AIMD, CUBIC)은 **패킷 손실(Packet Loss)** 또는 RFC 3168의 **단일 비트 ECN(Explicit Congestion Notification)**을 유일한 혼잡 피드백 신호로 사용해 왔습니다.

```
[고전적 CUBIC의 톱니파 진동 (Sawtooth Oscillation)]
혼잡 윈도우 (cwnd)
  ▲
  │       /│      /│      /│
  │      / │     / │     / │   <-- 패킷 드롭 / CE 마킹 시 cwnd를 30~50% 급격히 삭감
  │     /  │    /  │    /  │
  │    /   │   /   │   /   │
  │   /    │  /    │  /    │   <-- 삭감 후 대역폭 미달을 막기 위해 라우터에
  │  /     │ /     │ /     │       거대한 버퍼(Bufferbloat, 100~500ms)가 축적됨!
  └──┴─────┴─┴─────┴─┴─────┴──► 시간
```

### 버퍼블로트의 딜레마
1. **극심한 지연시간(Queuing Delay)**: 라우터 버퍼가 수백 패킷씩 쌓이면서 왕복 시간(RTT)이 10ms에서 300ms 이상으로 치솟아 화상 회의 및 실시간 게이밍이 마비됩니다.
2. **지연과 처리량의 트레이드오프**: 버퍼 크기를 줄이면(Shallow Buffer), CUBIC이 윈도우를 30% 줄이는 순간 파이프가 비어 링크 이용률이 50% 이하로 추락합니다.

## 2. L4S 아키텍처의 3대 기둥 (RFC 9330)

IETF는 2023년 인터넷의 패러다임을 바꿀 **L4S (Low Latency, Low Loss, Scalable Throughput)** 표준을 확정했습니다:

```text
+-------------------------------------------------------------------------+
|                        L4S 종단간 아키텍처                              |
+-------------------------------------------------------------------------+
| 1. 송신자 (TCP Prague / QUIC L4S)                                       |
|    - IP 헤더 ECN 필드: ECT(1) = 0b01 마킹                               |
|    - AccECN: RTT당 정밀 마킹 비율(f) 피드백 수신                        |
|    - 스케일러블 백오프: cwnd = cwnd * (1 - alpha/2)                     |
+-------------------------------------------------------------------------+
                                    │ IP 패킷 (ECT(1))
                                    ▼
+-------------------------------------------------------------------------+
| 2. 병목 라우터: DualQ Coupled AQM (RFC 9332)                            |
|                                                                         |
|   +-----------------------+     +-----------------------+               |
|   | L4S Queue (ECT(1))    |     | Classic Queue (기타)  |               |
|   | - 목표 지연 < 1ms     |     | - 목표 지연 15~20ms   |               |
|   | - 즉각 스텝 마킹(Step)|     | - PIE/CoDel 완충 드롭 |               |
|   +-----------┬-----------+     +-----------┬-----------+               |
|               │                             │                           |
|               └──────────────┬──────────────┘                           |
|                              ▼                                          |
|            [결합 마킹 엔진: p_L = k * sqrt(p_C)]                         |
|            - CUBIC과 Prague 간 1:1 대역폭 공정성 완벽 보장              |
+-------------------------------------------------------------------------+
```

## 3. DualQ 라우터: 왜 큐를 둘로 나누어야 하는가?

하나의 큐에 CUBIC과 Prague를 섞어 넣으면, CUBIC이 뿜어내는 수십 개의 패킷 때문에 Prague 패킷까지 강제로 수십 밀리초의 대기열에 갇히게 됩니다.
따라서 DualQ는 **IP 헤더의 ECN 코드포인트**를 기준으로 패킷을 물리적으로 분리합니다:
* `ECT(1) (0b01)` $\implies$ **L4S 큐**: 즉각적인 얕은 스텝 마킹(예: 800μs / 2패킷)을 적용하여 큐 대기열을 항상 1ms 미만으로 유지.
* `ECT(0) (0b10)` 또는 `Not-ECT (0b00)` $\implies$ **Classic 큐**: 전통적인 깊은 버퍼와 PIE/CoDel AQM을 적용.

### 결합 마킹(Coupled Marking)의 수학적 원리
고전적 CUBIC의 정상 상태 처리량은 $T_C \propto rac{1}{\sqrt{p_C}}$에 비례합니다.
반면 L4S 스케일러블 알고리즘의 처리량은 마킹 확률 $p_L$에 선형적으로 반비례합니다: $T_L \propto rac{1}{p_L}$.

두 흐름이 동일한 병목에서 대역폭을 $1:1$로 공평하게 나누어 가지려면 ($T_C = T_L$), 라우터는 다음 결합 공식을 만족해야 합니다:
$$p_L = k \cdot \sqrt{p_C} \quad \left(	ext{또는 } p_C = \left(rac{p_L}{k}ight)^2ight)$$
이 결합 마킹 덕분에, Classic 큐에 트래픽이 몰려 $p_C$가 상승하면 L4S 큐의 마킹 확률 $p_L$도 연동되어 상승하므로, L4S 흐름이 대역폭을 독점하지 않고 CUBIC과 완벽하게 공존합니다.

## 4. TCP Prague: 스케일러블 혼잡 제어의 메커니즘

TCP Prague는 전통적인 30% 삭감 대신, **최근 1 RTT 동안 발생한 CE 마킹의 비율($f$)**을 정밀하게 측정합니다 (AccECN):

1. **지수 이동 평균 ($lpha$) 갱신**:
   $$lpha = (1 - g)lpha + g \cdot f \quad \left(g = rac{1}{16}ight)$$
2. **비례적 부드러운 감속**:
   $$	ext{cwnd} \leftarrow 	ext{cwnd} \cdot \left(1 - rac{lpha}{2}ight)$$
   - 예컨대 패킷 100개 중 2개만 CE 마킹되었다면 ($f = 0.02, lpha pprox 0.02$), 윈도우는 단 **1%만** 감속됩니다!
   - 윈도우가 미세하게 진동하므로, 라우터 큐가 텅 비지 않고 항상 링크 용량을 100% 포화 상태로 유지합니다.

결과적으로 L4S와 TCP Prague는 **지연시간 1ms 이하, 패킷 손실 0%, 링크 이용률 100%**라는 네트워크 전송 공학의 이상향을 동시에 달성합니다.
