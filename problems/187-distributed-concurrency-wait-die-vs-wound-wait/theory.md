# 분산 트랜잭션 동시성 제어: Wait-Die vs Wound-Wait 교착상태 회피(Deadlock Avoidance)와 Google Spanner 아키텍처

## 1. 개요: 분산 데이터베이스에서 대기 그래프(WFG)의 한계

단일 노드 RDBMS(MySQL InnoDB, PostgreSQL)에서는 데이터베이스 엔진 내부의 메모리 테이블에서 락 대기 상태를 중앙 집중적으로 관리합니다. 트랜잭션 $T_1$이 $T_2$의 자원을 기다릴 때 $T_1 \to T_2$ 간선을 그리고, 백그라운드 스레드가 DFS(깊이 우선 탐색)로 사이클($O(V+E)$)을 찾아 한 트랜잭션을 희생자(Victim)로 롤백시킵니다.

그러나 샤딩된 분산 데이터베이스(Google Spanner, CockroachDB, TiKV)에서는 데이터가 전 세계 리전의 서로 다른 샤드(Shard/Tablet)에 분산되어 있습니다.
- $T_1$은 샤드 A(도쿄)에서 락을 쥐고 샤드 B(서울)의 락을 기다립니다.
- $T_2$는 샤드 B(서울)에서 락을 쥐고 샤드 A(도쿄)의 락을 기다립니다.

이러한 **분산 교착상태(Distributed Deadlock)**를 감지하려면:
1. **중앙 집중식 WFG 수집**: 모든 샤드가 주기적으로 네트워크를 통해 락 대기 목록을 마스터 노드로 전송해야 합니다. 네트워크 트래픽 폭발과 코디네이터 단일 장애점(SPOF)이 발생합니다.
2. **분산 에지 추적 (Edge-Chasing / Chandy-Misra-Haas 알고리즘)**: 대기 프로브 메시지(Probe Message)를 샤드 간에 핑퐁으로 전달해야 합니다. 메시지가 도착하는 도중 트랜잭션이 이미 완료되었는데도 헛된 데드락으로 오인하여 멀쩡한 트랜잭션을 롤백시키는 **유령 교착상태(Phantom Deadlock)** 문제가 빈번합니다.

따라서 최신 분산 데이터베이스는 데드락을 **"발생한 뒤 탐지(Detection)"**하는 대신, **"발생 자체를 수학적으로 원천 차단(Avoidance)"**하는 방식을 채택합니다.

## 2. 타임스탬프 기반 교착 회피: Rosenkrantz 정리 (1978)

1978년 D. J. Rosenkrantz, R. E. Stearns, P. M. Lewis II는 트랜잭션 시작 시 단조 증가하는 논리적 타임스탬프($ts$)를 부여하여 교착상태를 완벽하게 회피하는 두 가지 비대칭 알고리즘을 발표했습니다.

> **기본 공리**: $ts(T)$가 작을수록 먼저 시작된 **연장자(Older)**이며 높은 우선순위를 가집니다. $ts(T)$가 클수록 나중에 시작된 **연하(Younger)**입니다.

### 2.1 Wait-Die (비선점형 기법)
요청자 $T_{req}$가 점유자 $T_{holder}$의 자원을 요구할 때:
- **$ts(T_{req}) < ts(T_{holder})$ (Older requests Younger)**:
  - **연장자는 기다린다 (Older Waits)**. $T_{req}$가 대기 큐에 들어갑니다.
- **$ts(T_{req}) > ts(T_{holder})$ (Younger requests Older)**:
  - **연하는 죽는다 (Younger Dies)**. $T_{req}$는 대기하지 못하고 **즉시 자결(Abort/Rollback)**합니다.

#### 사이클 부존재의 수학적 증명
Wait-Die 규칙에서 대기 간선($T_i \to T_j$)은 오직 $ts(T_i) < ts(T_j)$인 경우에만 생성됩니다.
만약 사이클 $T_1 \to T_2 \to \dots \to T_k \to T_1$이 존재한다면:
$$ts(T_1) < ts(T_2) < \dots < ts(T_k) < ts(T_1)$$
이는 모순($ts(T_1) < ts(T_1)$)이므로, **대기 그래프는 항상 방향성 비순환 그래프(DAG)**가 되며 데드락이 100% 불가능합니다.

---

### 2.2 Wound-Wait (선점형 기법 - Google Spanner 채택)
요청자 $T_{req}$가 점유자 $T_{holder}$의 자원을 요구할 때:
- **$ts(T_{req}) < ts(T_{holder})$ (Older requests Younger)**:
  - **연장자가 연하를 상처 입힌다 (Older Wounds Younger)**.
  - $T_{holder}$를 즉시 선점(Preempt)하여 강제 롤백시키고, $T_{req}$가 즉시 락을 가로챕니다!
- **$ts(T_{req}) > ts(T_{holder})$ (Younger requests Older)**:
  - **연하는 기다린다 (Younger Waits)**.
  - $T_{req}$가 대기 큐에 평화롭게 진입합니다.

#### 사이클 부존재의 증명
Wound-Wait 규칙에서 대기 간선($T_i \to T_j$)은 오직 $ts(T_i) > ts(T_j)$인 경우(연하가 연장자를 기다리는 경우)에만 생성됩니다.
사이클이 형성되려면 $ts(T_1) > ts(T_2) > \dots > ts(T_1)$이어야 하므로 역시 모순이며, 데드락이 원천 봉쇄됩니다.

## 3. 심층 비교: 왜 Google Spanner는 Wound-Wait를 선택했는가?

| 비교 항목 | Wait-Die (비선점형) | Wound-Wait (선점형, Google Spanner) |
|---|---|---|
| **기본 철학** | "연장자는 기다려주고, 연하가 알아서 죽는다" | "연장자는 거침없이 전진하고, 연하는 기다린다" |
| **선점 여부** | 비선점 (실행 중인 트랜잭션을 강제 종료하지 않음) | **선점형** (연장자가 락을 요구하면 연하 점유자를 즉시 타격) |
| **연장자 대기 시간** | 연하의 작업이 끝날 때까지 연장자가 블로킹됨 | **0ms** (연하를 즉시 쫓아내고 락 획득) |
| **트랜잭션 롤백 횟수** | **매우 높음 (Abort Churn)** | **매우 낮음 (최소 롤백)** |
| **기아(Starvation) 위험** | 연하가 재시도할 때마다 연장자에게 막혀 반복 사망 위험 | 극히 낮음 (연하도 시간이 흐르면 연장자가 됨) |

### Google Spanner의 설계 결단
1. **선점(Wounding)의 유리함**:
   - Spanner 논문("Spanner: Google's Globally-Distributed Database", OSDI 2012, Section 4.1.1):
   - *"Spanner uses wound-wait for deadlock avoidance."*
2. **작업 완료 가속화**:
   - 이미 수많은 연산과 네트워크 I/O를 수행한 오래된 트랜잭션(Older Tx)은 시스템 자원을 많이 소비한 상태입니다. 이 연장자에게 최우선권을 주어 빠르게 커밋시켜야 시스템 전체의 락 점유 시간이 줄어듭니다.
3. **불필요한 취소 최소화**:
   - Wait-Die에서는 연하 트랜잭션이 연장자의 락을 건드리는 순간 무조건 자결해야 합니다.
   - 반면 Wound-Wait에서는 연하는 연장자를 기다리기만 하면 되며, **오직 연장자가 연하의 락을 실제로 필요로 할 때만 선점**되므로 실제 발생하는 롤백 횟수가 훨씬 적습니다.

---

## 4. 실무 재시도 불변식: 원래 타임스탬프의 보존

Wait-Die든 Wound-Wait든 트랜잭션이 롤백되어 재시도(Retry)할 때 가장 중요한 엔지니어링 원칙이 있습니다:

> **핵심 원칙**: 트랜잭션이 롤백 후 재시도할 때는 **새로운 타임스탬프를 발급받지 않고, 최초 시작 당시의 원래 타임스탬프($ts$)를 그대로 유지**해야 합니다.

만약 재시도할 때마다 새로운 타임스탬프를 받으면 영원히 가장 어린(Younger) 트랜잭션으로 남아 무한 롤백(Starvation)을 겪게 됩니다. 원래 타임스탬프를 유지하면 시간이 흐름에 따라 상대적으로 나이가 많은 연장자(Older)가 되어 결국 무조건 락을 쟁취하고 완주할 수 있습니다.
