# 리눅스 로드 애버리지(Load Average)와 D 상태(TASK_UNINTERRUPTIBLE) 프로세스의 비밀

> **"top을 켜보니 CPU 사용률은 5%밖에 안 되는데, 왜 서버 응답이 멈추고 Load Average는 80을 찍을까요?! 그리고 왜 `kill -9`를 쳐도 프로세스가 죽지 않을까요?!"**  
> 리눅스 서버를 운영하는 수많은 엔지니어들이 마주치는 가장 미스터리하고 공포스러운 순간입니다. 넷플릭스의 성능 분석 대가 브렌던 그레그(Brendan Gregg)가 *"Linux Load Averages: Solving the Mystery"*라는 유명한 글을 남겼을 정도로, 로드 애버리지와 D 상태 프로세스는 시스템 엔지니어링의 핵심 지식입니다.

---

## 1. Load Average는 "CPU 사용률"이 아니다!

많은 주니어 개발자들이 **"Load Average = CPU 사용률(%)"**이라고 오해합니다.  
하지만 이 둘은 완전히 다른 개념입니다:

- **CPU 사용률 (CPU Utilization)**: 특정 순간에 CPU 코어가 유저 코드나 시스템 코드를 실행하느라 얼마나 바쁜지를 나타내는 **순간 비율 (%)**.
- **로드 애버리지 (Load Average)**: CPU 코어에서 실행 중이거나, 실행을 기다리거나, **하드웨어 I/O 완료를 기다리는 활성 프로세스들의 총 수요(Demand)**를 나타내는 **지수 이동 평균 값**.

```
[비유: 은행 창구와 대기 줄]
- CPU 코어 4개 = 은행 창구 4개
- 창구 직원이 키보드를 치는 속도 = CPU 사용률 (5%)
- 창구 앞에 줄 서 있는 사람 + 대출 서류 도장을 기다리는 사람의 수 = Load Average (80)
```
창구 직원이 놀고 있어도(CPU 5%), 대출 서류를 확인해 주는 본사 전산망(NFS/디스크)이 멈춰서 고객 80명이 창구 앞에 멍하니 서 있다면, 은행 전체의 처리율(Load)은 80으로 폭발하는 것입니다!

---

## 2. 1993년 리눅스 토발즈의 역사적 결정: D 상태의 편입

전통적인 오리지널 유닉스(Solaris, BSD 등)에서는 오직 **CPU를 쓰고 있거나 CPU를 기다리는 프로세스(`TASK_RUNNING`, R 상태)**만 로드 애버리지에 포함했습니다.

하지만 1993년, 리눅스 창시자 **리눅스 토발즈(Linus Torvalds)**는 리눅스 커널 0.99.14에서 매우 독특하고 중요한 패치를 적용했습니다:
> *"디스크 I/O나 스토리지 응답을 기다리느라 멈춰 있는 프로세스(`TASK_UNINTERRUPTIBLE`, D 상태)도 시스템 자원을 기다리고 있는 것이므로 명백히 시스템 부하(Load)로 보아야 한다!"*

이 결정으로 인해, 리눅스에서는 **CPU가 0% 놀고 있더라도 디스크나 NFS가 느려지면 로드 애버리지가 100, 200으로 치솟는 현상**이 발생하게 되었습니다.

## 3. 프로세스 4대 핵심 상태와 D 상태의 정체

리눅스 커널에서 프로세스는 `task_struct`의 `state` 필드로 관리되며, 대표적으로 다음 4가지 상태가 있습니다:

| 프로세스 상태 | 표기 | 이름 | 설명 | 시그널 수신 여부 |
|---|:---:|---|---|:---:|
| **`TASK_RUNNING`** | `R` | 실행/준비 | CPU에서 코드를 실행 중이거나 런큐(Runqueue)에서 대기 중 | 수신 가능 |
| **`TASK_INTERRUPTIBLE`** | `S` | 인터럽트 가능 수면 | 소켓 수신 대기, 타이머(`sleep`) 대기 중인 정상 대기 상태 | 수신 즉시 깨어남 |
| **`TASK_UNINTERRUPTIBLE`** | `D` | **무인터럽트 수면** | **디스크 블록 읽기/쓰기, NFS RPC, 커널 락 대기 중** | **모든 시그널 무시!** |
| **`EXIT_ZOMBIE`** | `Z` | 좀비 | 프로세스가 종료되었으나 부모 프로세스가 `wait()`를 부르지 않음 | 이미 죽은 상태 |

## 4. 왜 D 상태 프로세스는 `kill -9`로도 절대 안 죽을까?!

개발자가 터미널에서 `kill -9 <PID>` (`SIGKILL`)를 날렸을 때:
- `S` 상태인 프로세스는 커널이 즉시 깨워서 시그널을 전달하고 프로세스를 종료시킵니다.
- **하지만 `D` 상태인 프로세스는 `kill -9`를 쳐도 절대 반응하지 않고 계속 살아 있습니다!**

### 왜 커널은 SIGKILL조차 막을까?
`TASK_UNINTERRUPTIBLE` 상태는 프로세스가 **커널 내부 디바이스 드라이버나 파일시스템 계층의 크리티컬 섹션**에 진입해 있음을 뜻합니다:
1. 디스크 컨트롤러(NVMe/SATA)가 DMA로 물리 메모리 버퍼에 데이터를 전송하는 중이거나,
2. 파일시스템의 inode 저널링 메타데이터 락을 쥐고 대기 중입니다.

만약 이때 프로세스를 강제로 사살(`kill`)해 버리면:
- 하드웨어가 방금 해제된 쓰레기 메모리 주소에 데이터를 덮어쓰거나,
- 파일시스템 락이 풀리지 않아 파일시스템이 영구 손상(`Filesystem Corrupted`)되거나,
- 커널 패닉(Kernel Panic)이 발생하여 서버 전체가 블루스크린/패닉으로 뻗어버립니다!

따라서 리눅스 커널은 **"하드웨어 I/O가 끝날 때까지는 신(God)이 와도 이 프로세스를 인터럽트하지 못하게 보호"**하는 것입니다.

## 5. 로드 애버리지 계산 공식: 지수 감쇠 이동 평균 (EMA)

리눅스 커널(`kernel/sched/loadavg.c`)은 타이머 인터럽트를 통해 **정확히 매 5초($\Delta t = 5$)마다** 활성 태스크 수를 샘플링하여 지수 감쇠 이동 평균(Exponentially Damped Moving Average)으로 로드 애버리지를 계산합니다:

$$n = 	ext{count}(R) + 	ext{count}(D)$$

$$	ext{load}_	au(t) = 	ext{load}_	au(t - \Delta t) 	imes e^{-\Delta t / 	au} + n 	imes (1 - e^{-\Delta t / 	au})$$

- $	au = 60$초 (1분 로드 평균): 감쇠 계수 $c_1 = e^{-5/60} pprox 0.920044$
- $	au = 300$초 (5분 로드 평균): 감쇠 계수 $c_5 = e^{-5/300} pprox 0.983471$
- $	au = 900$초 (15분 로드 평균): 감쇠 계수 $c_{15} = e^{-5/900} pprox 0.994460$

### 1분, 5분, 15분 수치 비교를 통한 추세 분석
- `load1 > load5 > load15`: 최근 1분 사이에 부하가 급상승 중 (스파이크 발생).
- `load1 < load5 < load15`: 시스템 부하가 점차 감소하며 회복 중.
- `load15 >> 코어 수`: 장기적으로 시스템 용량을 초과하는 만성 과부하 상태.

## 6. 실무 트러블슈팅 가이드

1. **CPU 사용률 vs I/O Wait 판별**:
   - `top`의 `%Cpu(s)` 행에서:
     - `us + sy`가 높으면 $	o$ **CPU 연산 병목** (무한 루프, 암호화, 정규식 등).
     - `wa`(I/O Wait)가 높고 `id`(Idle)가 높다면 $	o$ **스토리지/디스크 병목** (D 상태 프로세스 급증).
2. **D 상태 프로세스가 멈춘 커널 위치 확인**:
   ```bash
   cat /proc/<PID>/wchan    # 프로세스가 대기 중인 커널 함수 이름 출력 (예: nfs_wait_on_request, io_schedule)
   cat /proc/<PID>/stack    # 커널 콜 스택 전체 출력
   ```
3. **NFS 행(Hang) 대응**:
   - 원격 NFS 서버 장애 시 로컬 프로세스들이 무한히 D 상태에 갇히는 참사를 막기 위해, 마운트 옵션에 `intr`(인터럽트 허용) 또는 적절한 `timeo`, `retrans`를 적용합니다.
