# #056 C10K 문제와 Thread-per-Client vs I/O Multiplexing (Epoll / Reactor) 완벽 가이드

---

## 1. 개요: "서버 사양이 좋은데 왜 동시 접속자 1만 명에서 서버가 뻗나요?"

1999년 소프트웨어 엔지니어 댄 케겔(Dan Kegel)은 전 세계 개발자 커뮤니티에 충격적인 질문을 던졌습니다:

> "현재 하드웨어는 기가비트 이더넷(1,000Mbps)을 지원하고 수 기가헤르츠의 멀티코어 CPU를 탑재했습니다.  
> 하드웨어 스펙상으로는 초당 수만 개의 패킷을 처리할 능력이 충분한데,  
> **왜 현존하는 웹 서버들은 동시 접속자 10,000개($C = 10,000$)를 감당하지 못하고 쓰러질까요?**"

이 질문이 바로 컴퓨터 과학과 인터넷 인프라 역사를 영원히 바꾼 **C10K 문제(The C10K Problem)**입니다.  
당시 웹 서버 점유율 1위였던 아파치(Apache 1.x / 2.x)와 전통적인 자바 소켓 서버는 왜 1만 명의 동시 접속을 버티지 못했을까요?  
그리고 Nginx, Node.js, Netty, Redis는 어떻게 이 문제를 해결하고 세상을 장악했을까요?

---

## 2. 전통적인 블로킹 스레드 모델 (Thread-per-Connection)의 2대 치명적 한계

전통적인 네트워크 프로그래밍에서는 소켓 연결 1개마다 OS 스레드 1개를 할당했습니다:
```java
// 고전적인 Thread-per-Connection 서버 코드
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket socket = server.accept();
    new Thread(new ClientHandler(socket)).start(); // 🚨 클라이언트마다 스레드 생성!
}
```

이 구조는 동시 접속자가 1,000명을 넘어서는 순간 두 가지 물리적 벽에 부딪힙니다:

### 1) 스레드 스택 메모리 폭발 (OOM - Out Of Memory)
- 운영체제의 스레드는 독립적인 함수 호출 콜 스택(Call Stack)을 유지하기 위해 고정 메모리를 예약합니다:
  - Linux 기본: `ulimit -s` = 8MB
  - Java JVM 기본: `-Xss` = 1MB
- 만약 클라이언트 10,000명이 동시에 접속한다면?
  $$10,000 \times 1\text{MB} = 10\text{GB} \text{ 메모리 소모!}$$
- 실제 손님들이 데이터를 주고받는 시간은 1% 미만이고, 99%의 시간은 아무것도 안 하고 연결만 유지하고 있습니다(Keep-Alive / WebSocket 유휴 상태).
- **아무 일도 안 하는 10,000개의 스레드가 멍하니 메모리 10GB를 점유**하다가 `OutOfMemoryError: unable to create new native thread`를 뿜으며 서버 프로세스가 폭사합니다.

### 2) 컨텍스트 스위칭(Context Switching) 지옥
- CPU의 물리적 코어는 보통 4개~16개에 불과합니다.
- 코어 8개가 10,000개의 스레드를 번갈아 실행하려면, OS 스케줄러가 매 밀리초마다 CPU 레지스터, 스택 포인터, TLB(가상 메모리 캐시)를 갈아 끼워야 합니다.
- **CPU 사용률의 90% 이상이 '실제 비즈니스 로직'이 아니라 '스레드 바꿔 끼우는 오버헤드(Thrashing)'에 낭비**되어 서버 전체가 얼어붙습니다.

## 3. 현대적 구원투수: I/O Multiplexing과 epoll / Reactor 패턴

현대 아키텍처의 발상은 단순하고도 위대합니다:  
**"소켓 1개당 스레드 1개를 두지 말고, 스레드 1개가 수만 개의 소켓을 한꺼번에 감시하자!"**

```text
[전통적 블로킹 스레드 모델]
 클라이언트 1 ──> [스레드 1 (1MB)] ──(블로킹 대기)
 클라이언트 2 ──> [스레드 2 (1MB)] ──(블로킹 대기)
 ...
 클라이언트 10,000 ──> [스레드 10,000 (10GB 메모리 폭발!)]

[I/O 다중화 & epoll Reactor 모델 (Nginx, Netty, Node.js)]
 클라이언트 1 ──┐
 클라이언트 2 ──┼──> [리눅스 커널 epoll 이벤트 큐] <── [단 1개의 이벤트 루프 스레드!]
 ...            │         (I/O Ready 알림)             (벨 울린 소켓만 논블로킹 처리)
 클라이언트 10,000 ─┘
 * 메모리 소모: 소켓 FD당 8KB x 10,000 = 80MB! (99% 절감)
```

### 리눅스 I/O 다중화 시스템 콜의 진화:
1. **`select()` ($O(N)$)**:
   - 최대 소켓 수 1,024개 한계 (`FD_SETSIZE`).
   - 데이터가 왔는지 확인하기 위해 매번 1,024개 소켓 전체를 처음부터 끝까지 루프 돌며 선형 스캔.
2. **`poll()` ($O(N)$)**:
   - 1,024개 제한은 풀었으나, 여전히 $N$개의 소켓 전체를 매번 루프 돌며 검사하여 성능 저하.
3. **`epoll()` (리눅스) / `kqueue()` (BSD/macOS) ($O(1)$) - ⭐ 궁극의 혁신**:
   - 커널 내부의 레드블랙 트리(RB-Tree)로 관심 소켓들을 관리.
   - 네트워크 카드(NIC)에 패킷이 도착하여 하드웨어 인터럽트가 발생하면, 커널이 **준비 완료된 소켓만 '준비 리스트(Ready List)'에 추가**합니다.
   - 10만 개 소켓 중 단 1개에서만 패킷이 도착해도, 이벤트 루프 스레드는 $O(1)$로 즉시 그 소켓만 꺼내서 논블로킹으로 처리합니다!

## 4. 실무 아키텍처 대전환과 현대 기술 스택

| 구분 | Thread-per-Connection | I/O Multiplexing (Event-Driven) |
| :--- | :--- | :--- |
| **대표 기술** | Apache HTTP Server (prefork), 구형 Tomcat | **Nginx, Node.js, Netty, Redis, Envoy** |
| **연결당 메모리** | **1MB ~ 8MB** (스레드 스택) | **4KB ~ 8KB** (소켓 버퍼 / 커널 FD) |
| **동시 연결 한계** | 1,000 ~ 2,000개에서 OOM | **수십만 ~ 100만 개 (C1000K)** |
| **적합한 작업** | CPU 연산 집약적 작업 (동영상 인코딩) | **I/O 집약적 작업 (채팅, 웹소켓, API 게이트웨이)** |

### Java 21 Virtual Threads (가상 스레드 / Project Loom)의 등장
최근 Java 21에서 도입된 가상 스레드(Virtual Thread)는  
기존의 복잡한 논블로킹/리액티브 비동기 코드(`CompletableFuture`, `Mono/Flux`)를 작성하지 않고도,  
**동기식 코드 스타일 그대로 작성하면서 내부적으로는 캐리어 스레드가 epoll 기반으로 수백만 개의 가상 스레드를 경량 스케줄링**하여 C10K 문제를 완전히 정복했습니다.
