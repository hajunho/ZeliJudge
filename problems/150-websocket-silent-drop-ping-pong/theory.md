# 웹소켓 침묵의 유휴 커넥션 드롭(Silent Connection Drop)과 WebSocket Ping/Pong 하트비트 vs TCP Keep-Alive

## 1. 개요 및 실무 장애 시나리오: "가만히 놔뒀을 뿐인데 왜 웹소켓이 뚝뚝 끊겨요?!"

실시간 가상자산 거래소 '젤리익스체인지'의 프론트엔드/백엔드 개발팀은 사용자가 호가창을 켜두고 잠시 다른 탭을 보다가 돌아왔을 때, 매수 주문 버튼을 누르면 화면이 멈추고 다음과 같은 에러가 발생하는 장애를 지속적으로 제보받았습니다:

```
WebSocket connection to 'wss://api.zeli.io/ws/order' failed: 
WebSocket is already in CLOSING or CLOSED state. (Code 1006 Abnormal Closure)
```

이상한 점은 **클라이언트도, 서버도 연결을 끊으라고 `close()`를 호출한 적이 없었다는 것**입니다.  
서버의 소켓 로그를 확인해 보면 더 기괴했습니다:
* 클라이언트 브라우저는 12:00:00부터 12:02:00까지 자신이 정상적으로 연결되어 있는 줄(`readyState === WebSocket.OPEN`) 알고 있었습니다.
* 하지만 12:02:00에 사용자가 주문 메시지를 전송하려는 순간, 즉시 커넥션이 폭사(`Connection Reset by Peer / Broken Pipe`)하며 1006 비정상 종료가 터졌습니다.

분명 3-Way Handshake를 맺고 연결을 유지하고 있었는데, **아무런 FIN 패킷도 오가지 않은 상태에서 도대체 누가 연결을 끊어버린 것일까요?**

---

## 2. 침묵의 암살자: L4 로드밸런서와 방화벽의 유휴 커넥션 소각 (Silent Drop)

인터넷 환경에서 클라이언트와 백엔드 서버 사이에는 수많은 네트워크 중계 장비(기업 방화벽, 가정용 공유기 NAT, AWS NAT Gateway, L4 Network Load Balancer 등)가 존재합니다.

이 장비들은 패킷을 올바른 목적지로 라우팅하기 위해 메모리에 **연결 상태 추적 테이블(Connection Tracking Table, Conntrack Table)**을 유지합니다:
```
[Conntrack Table]
Client IP:Port <---------> L4 NAT Gateway <---------> Backend IP:Port
203.0.113.10:52412        198.51.100.1:443           10.0.1.50:8080
```

그러나 방화벽의 메모리는 유한하기 때문에, 모든 중계 장비에는 **유휴 커넥션 타임아웃(Idle Timeout)**이 설정되어 있습니다 (보통 60초, 120초, 또는 AWS 기본 350초).

### 침묵의 드롭 (Silent Drop) 메커니즘
1. 사용자가 호가창을 켜두고 60초 동안 아무런 주문이나 채팅을 보내지 않습니다.
2. 중간에 위치한 방화벽/L4 장비는 생각합니다:
   *"어? 이 연결은 60초 동안 양방향으로 패킷이 하나도 안 오가네? 죽은 연결인가 보다. 메모리 아까우니 테이블에서 지워야지."*
3. **장비는 Conntrack Table에서 해당 세션 정보를 조용히 삭제(Silent Drop)합니다.**
4. **치명적인 사실은, 이 과정에서 클라이언트나 서버 어느 쪽에도 TCP FIN이나 RST 패킷을 날려주지 않는다는 것입니다!**

```
[클라이언트 OS]              [중간 L4 방화벽]              [백엔드 서버]
     │                              │                            │
     │     (60초간 트래픽 없음)     │   (60초간 트래픽 없음)     │
     │                              │                            │
     │                     [Conntrack 엔트리 소각!]              │
     │                     (아무에게도 알리지 않음)              │
     │                              │                            │
[여전히 ESTABLISHED 착각]           │                 [여전히 ESTABLISHED 착각]
(좀비 커넥션 상태)                  │                 (좀비 커넥션 상태)
     │                              │                            │
     │── (1) 사용자 주문 패킷 전송 ─>│                            │
     │                              │ (너 누구야? 매핑 없음!)   │
     │<── (2) TCP RST 강제 반환 ───│                            │
[ECONNRESET 1006 폭사!]             │                            │
```

양쪽 엔드포인트는 연결이 살아있다고 굳게 믿고 있는 **좀비 커넥션(Zombie Connection)** 상태에 빠지게 되고, 나중에 패킷을 보낼 때 비로소 방화벽으로부터 `RST`를 얻어맞고 즉사하게 됩니다.

## 3. 오해와 한계: TCP Keep-Alive는 왜 웹소켓을 구하지 못하는가?

"OS 수준의 TCP Keep-Alive 설정을 켜면 되지 않나요?"

수많은 초보 엔지니어들이 이 시도를 하다가 실패합니다. 그 이유는 2가지 치명적 한계 때문입니다:

### (1) 기본 주기의 비현실성
* 리눅스 커널의 기본 `tcp_keepalive_time`은 **7200초 (무려 2시간)**입니다.
* 방화벽의 60초 유휴 타임아웃을 막으려면 2시간은 턱없이 깁니다.

### (2) L7 리버스 프록시의 경계 차단 (Proxy Boundary Termination)
* 현대 웹 아키텍처에서는 클라이언트와 서버 사이에 Nginx, Envoy, Cloudflare, AWS ALB와 같은 **L7 리버스 프록시**가 필수적으로 위치합니다.
* L7 프록시는 TCP 연결을 2개로 물리적으로 분리합니다:
  1. `클라이언트 <---> L7 프록시` (TCP Connection 1)
  2. `L7 프록시 <---> 백엔드 컨테이너` (TCP Connection 2)
* 클라이언트 OS가 전송한 TCP 수준의 Keep-Alive 패킷은 L7 프록시의 커널에서 흡수되어 소멸할 뿐, **프록시를 뚫고 백엔드 애플리케이션으로 전달되지 못합니다.**

## 4. 진정한 구원 투수: RFC 6455 웹소켓 Ping / Pong 하트비트

웹소켓 사양(RFC 6455 Section 5.5)은 이 문제를 원천 해결하기 위해 프로토콜 레벨의 제어 프레임(Control Frame)으로 **Ping(0x9)과 Pong(0xA)**을 규정했습니다.

### (1) 동작 메커니즘
1. **주기적 Ping 발송 (예: 25초 주기)**:
   * 클라이언트 또는 서버가 유휴 타임아웃(60초)보다 충분히 짧은 간격으로 1바이트짜리 경량 Ping 프레임을 발송합니다.
   * L7 애플리케이션 페이로드이므로 모든 프록시와 방화벽을 투명하게 통과합니다.
   * 중간 방화벽은 패킷을 확인하고 **Conntrack Table의 유휴 타이머를 0초로 리셋**합니다 (세션 유지).
2. **자동 Pong 회신**:
   * 상대방 엔드포인트(브라우저나 서버)는 Ping을 수신하면 사양에 따라 동일한 페이로드를 담은 **Pong 프레임을 즉시 반사**합니다.
3. **고스트 커넥션의 능동적 조기 감지**:
   * 만약 상대방 서버가 다운되었거나 인터넷 케이블이 뽑혔다면, Ping을 보내도 Pong이 오지 않습니다.
   * `pong_timeout` 내에 응답이 없으면 클라이언트는 방화벽이 RST를 때리기 전에 **"연결이 단절되었음"을 스스로 감지**하고, 백그라운드에서 신속하게 재연결(Reconnect)을 수행합니다!

## 5. 비교 요약표

| 비교 항목 | 아무것도 안 함 (None) | TCP Keep-Alive | WebSocket Ping/Pong (RFC 6455) |
|:---|:---:|:---:|:---:|
| **동작 계층** | - | 전송 계층 (L4 TCP) | 애플리케이션 계층 (L7 WebSocket) |
| **방화벽 60초 유휴 방어** | ❌ **100% 드롭 폭사** | ⚠️ 커널 파라미터 튜닝 필요 | ✅ **완벽 방어 (주기적 리셋)** |
| **L7 프록시(ALB/Nginx) 통과** | - | ❌ **프록시 경계 차단** | ✅ **100% 투명 통과** |
| **단절 조기 감지** | ❌ 패킷 전송 전까지 불능 | ⚠️ 수십 분 소요 | ✅ **수초 내 즉시 감지 ($N$초)** |
| **실무 표준** | 안티패턴 | 백엔드 내부망 전용 | **실무 글로벌 표준 (필수 구현)** |
