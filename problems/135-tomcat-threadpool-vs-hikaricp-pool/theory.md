# 스레드 풀 vs 커넥션 풀의 불균형과 리틀의 법칙(Little's Law)

> "동시 접속자 수를 뻥튀기하겠다고 톰캣 최대 스레드를 2,000개(`max-threads: 2000`)로 늘리고 대기 큐도 5,000개로 넉넉하게 잡았습니다.  
> 그런데 세일 오픈 날, 특정 상품 재고 확인 SQL 쿼리가 살짝 느려져 평소 5ms 걸리던 쿼리가 **500ms(0.5초)**로 지연되자마자...  
> **스레드 2,000개가 전부 생성되어 CPU 100%를 찍고 메모리가 2GB나 불어나더니, 전사 서비스가 504 Gateway Timeout으로 완전히 뻗어버렸습니다!**  
> 스레드를 2,000개나 넉넉하게 줬는데 왜 서버가 더 빠르게 폭사한 걸까요?!"

---

## 1. 리틀의 법칙 (Little's Law)과 시스템 수용 한계

대기행렬 이론(Queueing Theory)의 가장 위대한 기본 법칙인 **리틀의 법칙(Little's Law)**은 시스템 내부의 부하를 다음과 같이 정의합니다:

$$L = \lambda 	imes W$$

- **$L$ (Concurrency)**: 시스템 내부에 동시에 머물고 있는 요청 수 (활성 스레드 수)
- **$\lambda$ (Arrival Rate)**: 초당 유입되는 요청 건수 (TPS, Requests per Second)
- **$W$ (Latency / Residence Time)**: 요청 1건을 처리하는 데 걸리는 평균 시간 (초)

### DB 커넥션 풀의 최대 처리량 (Max Throughput)
웹 애플리케이션에서 거의 모든 비즈니스 로직은 데이터베이스를 거칩니다.  
따라서 시스템의 최대 처리량(Throughput)은 톰캣 스레드 수가 아니라 **가장 느린 병목 자원인 DB 커넥션 풀(HikariCP)**에 의해 결정됩니다:

$$	ext{Max DB TPS} = rac{	ext{HikariCP Pool Size}}{	ext{Average Query Latency}}$$

```
+-----------------------------------------------------------------------------------+
| 쿼리 속도에 따른 DB 커넥션 풀(50개)의 실제 최대 처리량 (TPS)                      |
+---------------------+-------------------------------+-----------------------------+
| 쿼리 지연시간 ($W$) | 초당 최대 처리량 ($\lambda$)  | 비고                        |
+---------------------+-------------------------------+-----------------------------+
| 5ms (0.005초)       | 10,000 TPS                    | 평상시: 50개 커넥션으로 충분|
| 50ms (0.05초)       | 1,000 TPS                     | 부하 증가 시                |
| 500ms (0.5초)       | 100 TPS                       | 슬로우 쿼리/락 경합 발생 시 |
+---------------------+-------------------------------+-----------------------------+
```

## 2. 톰캣 스레드 2,000개 폭탄의 원리

초당 500개의 요청이 쏟아져 들어오는데 DB 쿼리가 500ms로 지연되는 순간:
- DB 커넥션 풀(50개)은 **초당 100건**밖에 처리하지 못합니다.
- 나머지 초당 400건의 요청은 DB 커넥션을 얻지 못하고 대기열에 줄을 서야 합니다.

```
[클라이언트 요청 초당 500건]
            │
            ▼
[톰캣 워커 스레드 2,000개 폭증!] ──► 스레드당 1MB 스택 메모리 점유 (2GB 소비!)
            │                        OS 컨텍스트 스위칭 폭풍으로 CPU 100% 포화!
            ▼
[HikariCP 커넥션 풀 (50개 한도)] 🔒 ──► 이미 50개 100% 소진!
            │
            ▼
[커넥션 대기열 (Hikari Connection Wait Queue)]
     │
     ├──► 30초 동안 커넥션 못 얻고 줄서서 대기...
     │
     └──► connection-timeout 초과! ──► 504 Gateway Timeout 폭발! 💥
```

### 왜 스레드를 많이 주면 서버가 죽는가?
1. **스택 메모리 낭비 (Stack Memory Overflow)**:  
   자바 스레드는 생성될 때마다 최소 1MB의 스택 메모리(`-Xss1m`)를 소비합니다. 스레드가 2,000개까지 생성되면 순수 스레드 스택으로만 **2GB의 힙 외부 메모리가 소진**되어 프로세스 메모리가 고갈됩니다.
2. **컨텍스트 스위칭(Context Switching) 지옥**:  
   8코어 서버라면 CPU 하드웨어는 동시에 8개의 스레드만 실행할 수 있습니다. 2,000개의 스레드가 CPU를 차지하려고 경쟁하면, CPU가 실제 일(비즈니스 로직)을 하는 시간보다 **스레드 레지스터를 교체(Context Switch)하는 데 CPU 90% 이상을 낭비**하여 시스템이 얼어붙습니다.
3. **가짜 가용성 (False Concurrency)**:  
   스레드 2,000개가 살아있어 봐야, DB 커넥션이 50개뿐이면 **1,950개의 스레드는 DB 커넥션 락 뒤에서 잠들어 있을 뿐**입니다!

## 3. HikariCP 창시자의 커넥션 풀 공식

HikariCP의 창시자 브렛 울드리지(Brett Wooldridge)는 수많은 벤치마크 끝에 다음과 같은 황금 공식을 제시했습니다:

$$	ext{Connections} = (	ext{CPU Cores} 	imes 2) + 	ext{Disk Spindle Count}$$

- 8코어 서버에 SSD 스토리지라면 **$8 	imes 2 + 1 = 17$개에서 30개 안팎**의 커넥션 풀이 가장 높은 TPS와 가장 낮은 지연시간을 냅니다.
- 커넥션을 1,000개씩 늘리면 DB 서버의 디스크 I/O 경합과 트랜잭션 락 경합이 폭발하여 오히려 DB 전체 처리량이 곤두박질칩니다.

## 4. 실무 아키텍처: 올바른 스레드/커넥션 조화

> "도로(DB)가 막혔을 때 입구(스레드)를 2,000대나 더 열어주면 고속도로 전체가 주차장이 된다.  
> 입구에서 차를 통제하고 초과 차량은 우회(Fast-Fail)시켜야 고속도로 위의 차들이라도 제시간에 도착한다!"

| 구성 요소 | 나쁜 설정 (장애 유발) | 좋은 설정 (안정적 고성능) |
|---|---|---|
| **톰캣 최대 스레드** | 2,000개 (과다 생성) | **50 ~ 200개** (코어 수 및 DB 능력에 맞춤) |
| **톰캣 대기 큐** | 5,000개 (지연만 폭증) | **50 ~ 100개** (초과 시 즉시 503 거절) |
| **HikariCP 풀 크기** | 50개 (스레드와 극심한 불균형) | **스레드 수의 50~100%** 수준으로 조화 |
| **Connection Timeout** | 30초 (사용자 30초 대기) | **1 ~ 3초** (빠른 실패 후 재시도 유도) |
| **장애 완충 장치** | 무제한 줄서기 | 서킷 브레이커(Resilience4j) & 429/503 Fast-Fail |
