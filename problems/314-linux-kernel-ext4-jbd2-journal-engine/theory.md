# 리눅스 커널 ext4 JBD2 저널링 아키텍처 및 무결성 복구 이론

## 1. 개요 및 배경 (Crash Consistency Problem)

파일 시스템에서 파일 생성, 수정, 삭제는 단일 원자적 연산이 아니라 여러 디스크 블록에 걸친 복합적인 갱신 작업입니다.
예를 들어 `append` 연산은 다음 3단계를 수반합니다:
1. 데이터 비트맵(Data Bitmap) 갱신: 새로운 데이터 블록 할당 마킹.
2. 아이노드(Inode) 갱신: 파일 크기 증가 및 새로운 블록 포인터 추가.
3. 데이터 블록(Data Block) 기록: 사용자 페이로드 작성.

이 중 일부만 디스크 플래터에 반영된 상태에서 전원이 차단되면, 파일 시스템 메타데이터의 상호 참조 관계가 파괴되는 **충돌 일관성 문제(Crash Consistency Problem)**가 발생합니다.

초기 파일 시스템(`ext2`, UFS)은 부팅 시 전체 디스크 블록 트리를 일일이 순회하며 검증하는 `fsck`(File System Consistency Check)를 수행했으나, 테라바이트/페타바이트 급 스토리지에서는 검사 시간이 수십 시간 이상 소요되어 시스템 가용성에 치명적인 문제를 안겼습니다.

## 2. JBD2(Journaling Block Device 2)의 설계 원칙

리눅스 커널은 파일 시스템 로직과 저널링 계층을 분리하기 위해 독립된 블록 계층 추상화 엔진인 **JBD2(`fs/jbd2/`)**를 도입했습니다. ext4는 모든 디스크 쓰기를 JBD2 핸들 인터페이스(`jbd2_journal_start`, `jbd2_journal_stop`)를 통해 수행합니다.

### 1) 트랜잭션의 4단계 수명주기
- **`T_RUNNING`**: 현재 열려 있는 활성 트랜잭션입니다. 여러 프로세스가 실행하는 VFS 시스템 콜의 수정 사항들이 버퍼 헤드(`buffer_head`) 단위로 등록됩니다.
- **`T_LOCKED`**: 트랜잭션의 용량이 다 차거나 주기적 동기화 주기(기본 5초, `commit=5`)가 도래하여 새로운 핸들의 진입을 차단한 상태입니다.
- **`T_COMMIT`**: 트랜잭션 커밋 스레드(`jbd2/sdX`)가 디스크립터 블록, 메타데이터 블록, 그리고 최종 커밋 블록을 저널 링 버퍼에 기록하는 단계입니다.
- **`T_CHECKPOINT`**: 저널 커밋이 완료되어 영속성을 확보한 후, 메인 파일 시스템의 최종 위치로 블록을 복사하기 위해 대기하는 상태입니다.

## 3. 세 가지 저널링 모드 (Journal Modes)

리눅스 ext4 마운트 옵션 `data=`에 따라 일관성과 I/O 성능 사이의 트레이드오프가 결정됩니다:

1. **`data=journal` (최고 무결성 모드)**:
   - 파일 데이터와 메타데이터를 모두 저널에 먼저 기록한 뒤 메인 파일 시스템으로 보냅니다.
   - 모든 데이터가 두 번씩 디스크에 기록되므로 I/O 대역폭이 50% 수준으로 반토막 나지만, 메타데이터와 사용자 데이터 모두 완벽한 충돌 복구를 보장합니다.
2. **`data=ordered` (리눅스 기본값)**:
   - 메타데이터만 저널에 기록하되, **저널 커밋 블록을 디스크에 쓰기 전에 해당 트랜잭션과 연관된 모든 파일 데이터 블록을 메인 파일 시스템에 먼저 플러시(Flush)**합니다.
   - 이를 통해 충돌 복구 시 파일 크기는 커졌는데 데이터 블록에는 쓰레기 값(과거 삭제된 타 사용자의 기밀 데이터)이 노출되는 제로-데이 데이터 유출 및 쓰레기 데이터 노출(Garbage Data Exposure)을 완벽하게 방지합니다.
3. **`data=writeback` (최고 성능 모드)**:
   - 메타데이터만 저널링하며, 사용자 데이터의 기록 순서는 제어하지 않습니다. 충돌 시 과거 데이터가 노출될 수 있습니다.

## 4. 취소 블록 (Revoke Block)의 필연성

저널링 파일 시스템에서 가장 간과하기 쉬운 치명적 결함은 **메타데이터 블록의 데이터 블록 재할당 레이스(Race Condition)**입니다.

1. 트랜잭션 1: 디렉토리 A가 생성되어 물리 블록 500번에 디렉토리 엔트리 메타데이터가 기록되고 저널에 커밋됨.
2. 트랜잭션 2: 디렉토리 A가 삭제됨. 블록 500번이 해제됨.
3. 트랜잭션 3: 사용자가 대용량 동영상 파일을 쓰면서 블록 500번이 데이터 블록으로 재할당되어 동영상 데이터가 기록됨.
4. 이때 시스템 충돌 발생!

만약 복구 엔진이 단순히 저널을 처음부터 끝까지 재생(Replay)한다면, 과거 트랜잭션 1의 디렉토리 메타데이터가 트랜잭션 3에서 기록된 사용자의 동영상 데이터 블록 500번을 덮어써버려 사용자 파일이 영구 파괴됩니다.

JBD2는 이를 해결하기 위해 트랜잭션 2에서 블록이 삭제될 때 **`JBD2_REVOKE_BLOCK`**을 저널에 영구 기록합니다. 복구 엔진은 스캔 패스에서 Revoke 목록을 먼저 구축한 후, 재생 패스에서 블랙리스트에 등재된 블록 번호의 재생을 원천 건너뜀으로써 메타데이터와 사용자 데이터의 충돌을 완벽하게 방어합니다.
