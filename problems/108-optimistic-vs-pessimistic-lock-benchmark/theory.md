>

## 1. 동시성 제어 2대 철학: 낙관적 락 vs 비관적 락

데이터베이스의 동시성 제어는 "충돌이 얼마나 자주 일어날 것인가?"에 대한 철학적 가정에서 출발합니다.

### 1) 낙관적 락 (Optimistic Concurrency Control, OCC)
- **가정**: "세상은 평화롭고, 두 사용자가 동시에 같은 데이터를 수정하는 일은 거의 없을 것이다."
- **메커니즘**:
  - 읽을 때 락을 전혀 걸지 않습니다 (`SELECT stock, version FROM item WHERE id = 1`).
  - 수정할 때 버전 번호를 검증합니다:
    `UPDATE item SET stock = stock - 1, version = version + 1 WHERE id = 1 AND version = 1`
  - 만약 내가 읽은 뒤 다른 놈이 먼저 버전을 2로 바꿔버렸다면, 내 UPDATE는 0행이 수정(실패)됩니다.
  - 실패 시 애플리케이션 레벨에서 트랜잭션을 롤백하고, 최신 버전을 다시 읽어 **재시도(Retry Loop)**합니다.
- **장점**: 충돌이 없을 때는 락 획득/해제 오버헤드가 0이며, 데드락(Deadlock)이 원천적으로 발생하지 않습니다.

---

### 2) 비관적 락 (Pessimistic Concurrency Control, PCC)
- **가정**: "세상은 험난하고, 내가 데이터를 보는 도중에 반드시 다른 놈이 끼어들어 수정할 것이다."
- **메커니즘**:
  - 데이터를 조회하는 그 순간부터 행 배타락(X-Lock)을 걸어 잠급니다 (`SELECT ... FOR UPDATE`).
  - 내가 트랜잭션을 커밋할 때까지 다른 어떤 트랜잭션도 이 행을 수정하거나 읽을 수 없습니다.
  - 뒤이어 도착한 스레드들은 DB 커널 레벨의 락 대기열(Lock Wait Queue)에 얌전히 줄을 섭니다.
- **장점**: 충돌(Conflict)이 0회이며, 실패 및 롤백, 재시도가 발생하지 않습니다.
- **단점**: 락을 쥐고 있는 동안 다른 트랜잭션이 대기해야 하므로 지연이 발생하며, 락 획득 순서가 꼬이면 데드락이 발생할 수 있습니다.

## 2. 경합도(Contention)에 따른 성능 임계점의 역전

많은 주니어 개발자들이 "낙관적 락은 락이 없으니 항상 비관적 락보다 빠르다"고 오해합니다.
하지만 이는 **경합도가 극도로 낮을 때(Low Contention)**만 참인 명제입니다!

```
[처리량 (TPS)]
   ▲
   │         /─── 비관적 락 (PCC): 고경합에서도 안정적인 O(N) 처리량 유지
   │        /
   │   낙관적 락 (OCC)
   │     ┌───┐  (저경합: 락 오버헤드 없어 최고 성능)
   │    /        │   /       \ 🚨 성능 절벽 (임계점 돌파 시 99% 충돌 및 재시도 폭풍으로 TPS 0 수렴)
   │  /            └─┴───────────┴────────────────────────▶ [동시 경합도 (Contention Level)]
```

### 1) 경합이 낮을 때 (Low Contention, 예: 유저별 개인 프로필 수정)
- 여러 사용자가 각자의 프로필을 수정하므로 충돌 확률이 1% 미만입니다.
- 이때 비관적 락을 쓰면 매번 불필요한 DB Row Lock을 잡고 풀며 오버헤드가 발생합니다.
- **낙관적 락이 압도적으로 우수합니다.**

### 2) 경합이 극도로 높을 때 (High Contention, 예: 선착순 100명 티켓팅, 타임딜)
- 1개의 행(Row)을 두고 1,000개의 스레드가 동시에 경합합니다.
- 낙관적 락을 쓰면:
  - 1번 시도: 1명 성공, 999명 충돌 및 롤백 -> 재시도!
  - 2번 시도: 1명 성공, 998명 충돌 및 롤백 -> 재시도!
  - 전체 DB 쿼리 수: $\sum_{i=1}^{N} i pprox rac{N^2}{2}$ (**$O(N^2)$ 쿼리 폭발 참사!**)
  - 수천 개의 스레드가 쉬지 않고 DB를 두들기며 CPU 100%, 커넥션 풀 고갈을 유발합니다.
- 반면 비관적 락을 쓰면:
  - 1,000개의 스레드가 DB 락 큐에 줄을 서서 1명씩 순차적으로 1번의 쿼리만 실행하고 빠져나갑니다.
  - 전체 DB 쿼리 수: 정확히 **$2N$ ($O(N)$)**!
  - **비관적 락이 수십~수백 배 빠르고 안정적입니다.**

## 3. 실무 아키텍처 선택 가이드

| 기준 | 낙관적 락 (OCC with Version) | 비관적 락 (PCC with FOR UPDATE) | 분산 락 (Redis / Redisson) |
|---|---|---|---|
| **적합한 상황** | 충돌 빈도가 낮은 일반 CRUD | 단일 자원에 대한 극심한 동시성 집중 | 다중 서버/MSA 분산 환경의 자원 점유 |
| **재시도 비용** | 실패 시 애플리케이션 재시도 필수 | 락 대기 후 즉시 처리 (재시도 0회) | 락 획득 실패 시 즉시 탈락(Fast-Fail) 가능 |
| **DB 부하** | 고경합 시 쿼리 $O(N^2)$ 폭증 | 락 점유로 인한 커넥션 대기 시간 증가 | DB 진입 전 Redis에서 차단하여 DB 보호 |
| **데드락 위험** | 없음 | 다중 자원 락 획득 시 발생 가능 | 분산 락 타임아웃(Lease Time)으로 방어 |
