# [ZeliJudge #017] 9시간 늦게 산 사람이 1등?: 시간대(Timezone)의 덫과 UTC 절대 시계

## 📌 문제 배경 스토리
글로벌 한정판 스니커즈 커머스 스타트업 '젤리드롭'의 신입 백엔드 개발자 젤리는 전 세계 100족 한정판 신발의 선착순 구매 이벤트를 오픈했습니다.
전 세계의 열성 팬들이 각자의 스마트폰으로 정각에 맞추어 주문을 넣었습니다:

- 🇺🇸 뉴욕의 존: `2026-09-09 02:00:00 -04:00` (현지 시각 새벽 2시)
- 🇬🇧 런던의 엠마: `2026-09-09 06:30:00 +01:00` (현지 시각 아침 6시 30분)
- 🇰🇷 서울의 철수: `2026-09-09 15:00:00 +09:00` (현지 시각 오후 3시)

젤리는 데이터베이스에서 주문 내역을 조회하여 선착순 1등부터 당첨자를 정렬할 때, 시간대(오프셋 `+09:00`, `-04:00`)를 전혀 고려하지 않고 **표기된 날짜/시간 문자열 그대로(`NAIVE`)** 오름차순 정렬했습니다:

```python
# [젤리가 작성한 순진한 선착순 정렬]
# "02:00는 새벽 2시니까 제일 빠르고, 15:00는 오후 3시니까 제일 늦네!"
orders.sort(key=lambda x: (x.date_str, x.time_str, x.order_id))
```

그 결과, 젤리의 시스템에서는 엉뚱하게 존(02:00)이 1등, 엠마(06:30)가 2등, 철수(15:00)가 꼴찌로 처리되었습니다.
하지만 실제 지구상의 절대적인 동시성(협정 세계시, UTC) 기준으로 계산하면 진실은 완전히 달랐습니다:
- **엠마 (런던)**: `06:30:00 +01:00` -> **UTC 05:30:00 (진짜 1등!)**
- **존 (뉴욕)**: `02:00:00 -04:00` -> **UTC 06:00:00 (동시 2등)**
- **철수 (서울)**: `15:00:00 +09:00` -> **UTC 06:00:00 (동시 2등)**

가장 먼저 주문한 런던의 엠마는 2등으로 밀려나 한정판 신발을 받지 못했고, 해외 커뮤니티는 *"사기 사이트다! 시차도 계산 못 하는 사이트가 어디 있냐!"* 라며 고소 사태와 환불 폭탄이 터졌습니다!

CTO는 시스템을 긴급 전면 개편하기 위해,
1. 시간대를 무시하고 표기 문자열 그대로 정렬한 **버그 시스템 (`NAIVE`)**
2. 모든 시각을 협정 세계시(UTC) 절대 초로 정규화하여 정렬한 **정상 시스템 (`UTC_NORMALIZED`)**
두 시스템의 결과를 비교 분석하여 억울하게 순위가 뒤바뀐 주문의 수를 전수 조사하라고 지시했습니다.

---

## ⚙️ 시스템 동작 규칙

각 주문은 `<order_id> <YYYY-MM-DD> <HH:MM:SS> <[+/-]HH:MM>` 형식으로 주어집니다.

### 1. 두 시스템의 정렬 기준
* **버그 시스템 (`NAIVE`)**:
  - 시간대 오프셋(`<[+/-]HH:MM>`)을 완전히 무시합니다.
  - 1차 기준: 문자열 `f"{YYYY-MM-DD} {HH:MM:SS}"`의 사전순(오름차순)
  - 2차 기준: `order_id` 사전순(오름차순)
* **정상 시스템 (`UTC_NORMALIZED`)**:
  - 각 주문의 시각을 **UTC 기준 절대 초(Timestamp)**로 정확히 변환합니다.
    - 변환 공식: `UTC = Local_Time - Offset`
    - 예: `15:00:00 +09:00` -> `15:00:00 - 9시간` = `06:00:00 UTC`
    - 예: `02:00:00 -04:00` -> `02:00:00 - (-4시간)` = `06:00:00 UTC`
  - 1차 기준: UTC 절대 시각(초) 오름차순
  - 2차 기준: `order_id` 사전순(오름차순)

### 2. 순위 불일치 주문 (`MISPLACED_ORDERS`)
- $N$개의 주문을 두 시스템으로 각각 정렬했을 때,
  $i$번째 순위($0 \le i < N$)에 위치한 `order_id`가 서로 다른 위치의 개수입니다.
- 즉, `NAIVE_RANK[i] != UTC_RANK[i]`를 만족하는 인덱스 $i$의 총합입니다.

---

## 📥 입력 형식 (Input)

- 첫째 줄에 주문의 총 개수 $N$이 주어집니다. ($1 \le N \le 100,000$)
- 둘째 줄부터 $N$개의 줄에 걸쳐 각 주문의 정보가 공백으로 구분되어 주어집니다:
  `<order_id> <YYYY-MM-DD> <HH:MM:SS> <[+/-]HH:MM>`
- `<order_id>`는 1~20자의 영문 대소문자 및 숫자로 이루어져 있습니다.
- 모든 `<order_id>`는 유일함이 보장됩니다.
- 날짜는 2000-01-01부터 2099-12-31까지 유효한 날짜이며, 오프셋은 `-12:00`부터 `+14:00` 사이의 유효한 시간대 오프셋입니다.

---

## 📤 출력 형식 (Output)

다음 형식에 맞추어 정확히 4줄을 출력합니다:
- 1번째 줄: `FASTEST UTC:<utc_1st_id> NAIVE:<naive_1st_id>`
- 2번째 줄: `MISPLACED_ORDERS:<count>`
- 3번째 줄: `TOP3_UTC:<id1> <id2> <id3>` (단, $N < 3$인 경우 존재하는 개수만큼 공백으로 구분)
- 4번째 줄: `TOP3_NAIVE:<id1> <id2> <id3>` (단, $N < 3$인 경우 존재하는 개수만큼 공백으로 구분)

---

## 💡 입출력 예제

### 예제 입력 1
```text
3
ORD_NY 2026-09-09 02:00:00 -04:00
ORD_LON 2026-09-09 06:30:00 +01:00
ORD_SEL 2026-09-09 15:00:00 +09:00
```

### 예제 출력 1
```text
FASTEST UTC:ORD_LON NAIVE:ORD_NY
MISPLACED_ORDERS:2
TOP3_UTC:ORD_LON ORD_NY ORD_SEL
TOP3_NAIVE:ORD_NY ORD_LON ORD_SEL
```

### 예제 설명 1
- **절대 시각 (UTC)**:
  - `ORD_LON`: `2026-09-09 05:30:00 UTC` (1등!)
  - `ORD_NY`: `2026-09-09 06:00:00 UTC` (2등, ID 사전순 앞섬)
  - `ORD_SEL`: `2026-09-09 06:00:00 UTC` (3등)
- **표기 시각 (NAIVE)**:
  - `ORD_NY`: `02:00:00` (1등)
  - `ORD_LON`: `06:30:00` (2등)
  - `ORD_SEL`: `15:00:00` (3등)
- 1등과 2등의 자리가 서로 뒤바뀌어 있으므로 `MISPLACED_ORDERS`는 **2**입니다.

---

### 예제 입력 2
```text
2
T1 2026-01-01 12:00:00 +00:00
T2 2026-01-01 13:00:00 +00:00
```

### 예제 출력 2
```text
FASTEST UTC:T1 NAIVE:T1
MISPLACED_ORDERS:0
TOP3_UTC:T1 T2
TOP3_NAIVE:T1 T2
```

### 예제 설명 2
- 두 주문 모두 동일한 기준시(`+00:00`)를 사용하므로, `NAIVE`와 `UTC_NORMALIZED`의 정렬 순서가 100% 일치하며 오판정이 전혀 없습니다 (`MISPLACED_ORDERS:0`).
