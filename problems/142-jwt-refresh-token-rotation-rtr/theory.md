# [JWT 보안 아키텍처: Refresh Token Rotation (RTR)과 토큰 패밀리 침해 감지]

## 1. 무상태(Stateless) JWT의 딜레마와 한계

JWT는 서버가 세션 저장소(RDBMS나 Redis)를 조회하지 않고도 서명(Signature) 검증만으로 사용자를 식별할 수 있는 강력한 장점을 제공합니다.
하지만 이 '무상태성'은 보안 관점에서 양날의 검입니다:
- **즉시 무효화 불가능**: 한 번 발급된 JWT는 만료 시간(`exp`)이 되기 전까지 서버가 강제로 회수(Revoke)하거나 무효화할 수 없습니다.
- 만약 토큰이 탈취되면, 만료될 때까지 해커에게 문을 열어준 꼴이 됩니다.

이 딜레마를 해결하기 위해 2-Token 전략이 사용됩니다:
1. **Access Token**: 15분~1시간 정도로 수명을 극단적으로 짧게 하여 탈취 시 피해 창(Window of Vulnerability)을 최소화.
2. **Refresh Token**: 2주~한 달 정도로 길게 유지하여 사용자가 매번 로그인하는 번거로움을 방지.

하지만 **"리프레시 토큰이 탈취되면 어떡할 것인가?"**라는 근본적인 문제는 여전히 남아있었습니다.

## 2. Refresh Token Rotation (RTR) 메커니즘

OAuth 2.0 Security Best Current Practice (RFC 6749 BCP)에서는 싱글 페이지 애플리케이션(SPA)이나 모바일 앱처럼 클라이언트에 안전한 시크릿 저장이 불가능한 퍼블릭 클라이언트(Public Client)에 대해 **Refresh Token Rotation (RTR)**을 강력히 권고합니다.

```text
[클라이언트]                                           [인증 서버]
     |                                                     |
     | ----- 1. POST /token (RT_1 전송) -----------------> |
     |                                                     | (RT_1 검증 & 즉시 폐기)
     |                                                     | (새 RT_2 및 새 AT_2 생성)
     | <---- 2. 응답 (AT_2, RT_2 반환) ------------------- |
     |                                                     |
```

### RTR의 핵심 원칙:
1. **1회용(One-time Use) 리프레시 토큰**:
   - 리프레시 토큰은 단 한 번만 액세스 토큰 갱신에 사용할 수 있습니다.
   - 갱신 요청이 성공하면 기존 RT는 즉시 만료되며, 반드시 새 RT가 함께 발급됩니다.
2. **토큰 수명 갱신(Sliding Window)**:
   - 유저가 활발히 서비스를 사용하는 동안에는 리프레시 토큰이 계속 새것으로 교체되므로 세션이 유지됩니다.

## 3. 자동 침해 감지 (Automatic Reuse Detection)와 토큰 패밀리

RTR만 적용하면 충분할까요? 아닙니다!
만약 해커가 네트워크 스니핑이나 XSS로 $RT_1$을 훔쳤다고 가정해 봅시다:

### 시나리오 A: 해커가 먼저 갱신하는 경우
1. 해커가 훔친 $RT_1$로 갱신 요청 $	o$ 해커가 $RT_2(H)$와 $AT_2(H)$를 획득.
2. 잠시 후 정상 유저가 자신의 $RT_1$로 갱신 요청 $	o$ 이미 쓰인 $RT_1$이 다시 들어옴!

### 시나리오 B: 유저가 먼저 갱신하는 경우
1. 유저가 $RT_1$로 갱신 요청 $	o$ 유저가 $RT_2(U)$와 $AT_2(U)$를 정상 획득.
2. 잠시 후 해커가 훔쳐둔 $RT_1$로 갱신 요청 $	o$ 이미 쓰인 $RT_1$이 다시 들어옴!

**두 시나리오 모두 공통점이 있습니다: "이미 사용 완료된(Used) 과거 세대의 리프레시 토큰이 다시 인증 서버로 전달되었다"는 사실입니다!**

정상적인 단일 클라이언트 환경에서는 이미 교체된 구형 토큰을 다시 보낼 이유가 없습니다.
따라서 **소진된 구형 RT의 재유입은 토큰 탈취 및 복제(Breach)가 일어났음을 입증하는 결정적 증거**입니다.

### 토큰 패밀리 무효화 (Token Family Revocation):
- 인증 서버는 토큰 체인(Family) 단위로 이전 세대 토큰 목록을 유지합니다.
- 사용된 토큰이 재유입되는 즉시 **침해 경보(Breach Alert)**를 발동합니다.
- 해당 패밀리에서 파생된 **현재 활성화된 모든 토큰(해커의 $RT_2$든 유저의 $RT_2$든 모두 포함)을 일괄 무효화(Blacklist)**합니다.
- 결과적으로 해커의 접근 권한이 영구 박탈되며, 정상 유저에게는 재로그인 및 보안 경고(비밀번호 변경 권유)가 전달됩니다.

## 4. 실무 아키텍처 구현 가이드

1. **Redis 기반의 토큰 패밀리 저장소**:
   - `family:{family_id}:active` $	o$ 현재 유효한 최신 RT 해시값
   - `family:{family_id}:used` $	o$ 소진된 구형 RT 해시 세트 (TTL: 리프레시 토큰 전체 만료시간)
   - `family:{family_id}:status` $	o$ `ACTIVE` 또는 `REVOKED`
2. **Access Token 블랙리스트 관리**:
   - 로그아웃이나 패밀리 침해 발생 시, 해당 유저/패밀리의 활성 AT JTI(JWT ID)를 Redis 블랙리스트에 등록 (TTL: 액세스 토큰 잔여 유효시간).
3. **네트워크 일시 지연 완충 (Grace Period)**:
   - 모바일 환경에서 불안정한 네트워크로 인해 갱신 요청이 중복 전송되는 경우를 대비하여, 실무에서는 구형 토큰 무효화 후 수 초(예: 5~10초)의 유예 기간(Grace Period)을 두고 이 시간 내의 동일 토큰 재요청은 기존 응답을 재전송하는 설계를 적용하기도 합니다.
