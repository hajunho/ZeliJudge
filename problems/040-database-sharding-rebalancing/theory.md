# 📚 기술 백서: 데이터베이스 샤딩(Sharding)과 리밸런싱 아키텍처

> **"수직 확장(Scale-up)으로 버티는 것은 언젠가 반드시 벽에 부딪힙니다. 데이터가 1억 건을 넘어서는 순간, 진정한 분산 스토리지 엔지니어링이 시작됩니다."**

단일 데이터베이스(RDB)에 데이터가 수억 건 쌓이면, 아무리 비싼 AWS r6g.16xlarge(1TB RAM) 인스턴스를 사용해도 시스템이 버티지 못합니다.
B-Tree 인덱스 크기가 서버의 물리 메모리(RAM)를 초과하는 순간, 모든 쿼리가 디스크 랜덤 I/O를 유발하며 DB는 서서히 침몰합니다.

결국 단일 DB를 여러 대의 독립된 데이터베이스로 쪼개는 **샤딩(Sharding)**이 필연적인 선택이 됩니다.
하지만 샤딩을 잘못 설계하면 **특정 샤드만 터지는 핫샤드(Hot Shard)**와 **샤드 증설 시 데이터 80%를 옮겨야 하는 대이사 참사**를 겪게 됩니다.
이 백서에서는 샤딩의 3대 파티셔닝 전략과 실무 리밸런싱 기법을 다룹니다.

---

## 1. 현실 비유: 국립중앙도서관 본관과 4개 분관

국립도서관 본관(단일 DB)에 책이 1억 권이 넘어가 건물이 붕괴될 위기에 처하자, 4개의 분관(동관, 서관, 남관, 북관 = Shard 1, 2, 3, 4)을 지어 책을 분산하기로 했습니다.

### 참사 1: 출판 연도별 범위 샤딩 (Range-Based Sharding)
* "2000년 이전 책은 동관, 2010년 이전은 서관, 2020년 이전은 남관, 2020년 이후는 북관에 두자!"
* **결과**: 사람들은 최신 베스트셀러(2024~2026년 신간)만 찾습니다.
* **북관(최신 샤드)만 대기 줄이 1km 서고 문이 부서지며 폭발(Hot Shard)**하고, 동관은 하루에 1명 방문하는 유령 건물이 되었습니다.

### 참사 2: 도서 고유 번호 모듈로 샤딩 (Modulo Hash Sharding)
* "그럼 책 번호(ISBN) % 4로 4개 관에 아주 똑같이 25%씩 나누자!"
* 4개 관에 책이 완벽하게 균등 분산되었습니다.
* 그런데 책이 더 늘어나 분관을 1개 더 지어 **5개 관**이 되었습니다!
* 번호 % 4에서 % 5로 바뀌는 순간, **기존 책의 80%($\frac{4}{5}$)를 트럭에 싣고 다른 분관으로 이사(Data Migration)보내느라 국가 물류망이 마비**되었습니다!

### 해결책: 디렉토리 기반 샤딩 (Directory / Lookup Table Sharding)
* 본관 전산실에 **"어떤 책/저자가 어느 관에 있는지" 기록된 룩업 테이블**을 둡니다.
* 5번째 분관이 생기면 책 전체를 옮기지 않고, **가장 책이 많은 분관에서 딱 필요한 만큼만 몇 개 박스를 골라 새 분관으로 이전(Selective Rebalancing)**합니다!

## 2. 샤딩(Sharding)의 3대 파티셔닝 전략 비교

| 샤딩 전략 | 동작 원리 | 장점 | 치명적 단점 | 실무 사용처 |
|:---:|---|---|---|:---:|
| **범위 기반<br>(Range-Based)** | 특정 키의 연속된 구간별 분할<br>(예: ID 1~1000만 $\to$ Shard 1) | 구현 단순, 범위 검색(`BETWEEN`) 최적화 | **최신 데이터 샤드로 트래픽이 쏠리는 핫샤드(Hot Shard) 발생** | 과거 로그 아카이빙 테이블 |
| **모듈로 해시<br>(Modulo Hash)** | $S = \text{hash}(\text{key}) \pmod K$ | 균등한 데이터 분산, 핫스팟 최소화 | **샤드 수 변경($K \to K+1$) 시 대규모 데이터 재배치($\frac{K}{K+1}$) 참사** | 샤드 수가 고정된 소규모 시스템 |
| **디렉토리 기반<br>(Directory Sharding)** | 중앙 메타데이터 매핑 테이블 관리<br>(`key -> shard_id`) | **샤드 증설 시 최소한의 선택적 이전(Selective Migration) 가능**, 핫스팟 유저 격리 가능 | 룩업 테이블 조회 오버헤드 (Redis 캐싱 필수) | **대규모 엔터프라이즈 플랫폼 표준** |

---

## 3. 샤드 증설 시 모듈로 해시의 수학적 비극: $\frac{K}{K+1}$ 재배치

샤드 $K$대에서 $K+1$대로 1대 증설할 때, 기존 데이터 중 새 위치와 이전 위치가 달라져 마이그레이션해야 하는 데이터의 비율은 수학적으로 다음과 같습니다:

$$\text{Migration Ratio} = 1 - \frac{1}{K+1} = \frac{K}{K+1}$$

* 샤드가 3대 $\to$ 4대로 증가: **기존 데이터의 75%가 이동!**
* 샤드가 4대 $\to$ 5대로 증가: **기존 데이터의 80%가 이동!**
* 샤드가 9대 $\to$ 10대로 증가: **기존 데이터의 90%가 이동!**

단 1대의 샤드를 추가했을 뿐인데 수천만~수억 건의 데이터베이스 행이 네트워크를 타고 다른 호스트로 복사되고 원본에서 삭제되어야 합니다.
이 과정에서 발생하는 디스크 I/O와 네트워크 트래픽 때문에 실서비스는 며칠 동안 점검 상태에 빠질 수밖에 없습니다.

## 4. 샤딩 도입 시 반드시 해결해야 할 3대 분산 아키텍처 재앙

샤딩을 도입하면 단일 DB 시절에는 당연했던 기능들이 모두 깨집니다:

1. **Scatter-Gather (팬아웃 쿼리 참사)**:
   * `WHERE user_id = 42`는 샤드 1개만 찌르면 됩니다 ($O(\log N)$).
   * 하지만 `WHERE title LIKE '%특가%'`처럼 **샤드 키가 없는 검색**은 모든 샤드(Shard 0~N)에 쿼리를 쏘고 메모리에서 병합해야 하므로 DB가 폭발합니다.
2. **분산 조인(Cross-Shard Join) 불가**:
   * 서로 다른 물리적 서버에 있는 테이블끼리는 RDB의 `JOIN` 문을 쓸 수 없습니다.
   * 비정규화(Denormalization)를 통해 데이터를 중복 저장하거나 애플리케이션 레벨에서 조인해야 합니다.
3. **Auto-Increment Primary Key의 무력화**:
   * 각 샤드가 각자 1, 2, 3... 번호를 매기면 전체 시스템에서 PK 충돌이 발생합니다.
   * 트위터의 **Snowflake ID**(타임스탬프 + 워커ID + 시퀀스)나 **UUID v7** 같은 글로벌 유니크 키 생성기를 도입해야 합니다.

## 5. 결론: 디렉토리 샤딩과 안정 해시(Consistent Hashing)의 융합

현대 클라우드 분산 데이터베이스(YouTube의 **Vitess**, PostgreSQL의 **Citus**, Amazon **DynamoDB**, Google **Spanner**)는:
* **가상 버킷(Virtual Buckets)**을 두고 버킷 단위로 샤드에 매핑하거나,
* **디렉토리 룩업 테이블**을 Redis/ZooKeeper에 캐싱하여,

샤드가 100대, 1,000대로 늘어나더라도 **오직 새 샤드가 감당할 $\frac{1}{K+1}$ 만큼만 정밀하게 이전**함으로써 무중단 스케일아웃을 달성합니다.
이 원리를 이해하는 엔지니어만이 테라바이트를 넘어 페타바이트급 대규모 데이터를 안정적으로 지휘할 수 있습니다.
