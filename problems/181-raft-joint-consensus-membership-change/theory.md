# Raft 분산 합의 클러스터 멤버십 변경과 공동 합의(Joint Consensus, $C_{old,new}$) 스플릿 브레인 방어

## 1. 개요: 분산 클러스터의 동적 재구성(Dynamic Reconfiguration)

실제 프로덕션 분산 시스템(etcd, Kubernetes, TiKV, HashiCorp Consul 등)은 영구히 고정된 노드로만 운영될 수 없습니다.
- 하드웨어 장애 노드를 신규 노드로 교체해야 합니다.
- 트래픽 증가로 인해 3노드 클러스터를 5노드로 스케일아웃해야 합니다.
- 데이터센터 이전(마이그레이션)을 위해 기존 5대 노드를 신규 리전 5대로 점진 교체해야 합니다.

클러스터를 중단하지 않고 라이브(Live) 상태에서 멤버십을 변경하는 것은 분산 합의 알고리즘에서 가장 까다로운 난제 중 하나입니다.
단 하나의 사소한 프로토콜 결함만으로도 **동일 클러스터에서 2명의 리더가 동시에 선출되는 스플릿 브레인(Split-Brain) 재앙**이 발생할 수 있기 때문입니다.

## 2. 참사의 근원: 나이브한 1단계 단일 설정 전환의 파멸

### 2.1 단일 전환 방식의 취약점

만약 리더가 신규 설정 $C_{new}$를 담은 로그를 생성하고 단순히 노드들에게 브로드캐스트하여 즉시 변경하도록 만든다면 어떻게 될까요?

예를 들어 3대 노드 $C_{old} = \{1, 2, 3\}$에서 5대 노드 $C_{new} = \{1, 2, 3, 4, 5\}$로 클러스터를 확장하는 상황을 가정해 봅시다:
- $C_{old}$의 과반수(Majority): 3대 중 **2대**
- $C_{new}$의 과반수(Majority): 5대 중 **3대**

```
[시간 t0]  모든 노드가 C_old = {1, 2, 3} 상태
           (리더 1이 C_new = {1, 2, 3, 4, 5} 설정 전파 시작)

[시간 t1]  비대칭 네트워크 지연 발생!
           - Node 3, 4, 5는 C_new 설정을 수신하고 즉시 적용!
           - Node 1, 2는 네트워크 지연으로 C_new를 아직 받지 못해 C_old 유지!

[시간 t2]  기존 리더 1과 3 사이의 네트워크 순단 발생 -> 선출(Election) 발발!
           - Node 1: C_old {1, 2, 3} 기준으로 투표 요청 -> {1, 2} 득표 (2/3 과반수 달성!) -> 리더 1 당선!
           - Node 5: C_new {1, 2, 3, 4, 5} 기준으로 투표 요청 -> {3, 4, 5} 득표 (3/5 과반수 달성!) -> 리더 5 당선!
```

### 2.2 결과: 스플릿 브레인과 영구적 데이터 분기 (Disaster)

- 리더 1은 클라이언트 A로부터 쓰기 요청을 받아 $\{1, 2\}$에 커밋합니다.
- 리더 5는 클라이언트 B로부터 쓰기 요청을 받아 $\{3, 4, 5\}$에 커밋합니다.
- **서로 상충하는 두 개의 트랜잭션이 동일 임기/클러스터에서 동시에 커밋되어 데이터 정합성이 영구 파괴됩니다!** (`CATASTROPHIC_SPLIT_BRAIN_TWO_LEADERS`).

## 3. 구원: Diego Ongaro의 공동 합의(Joint Consensus, $C_{old,new}$)

2014년 Diego Ongaro 박사는 박사 학위 논문(Section 6) 및 USENIX ATC '14 논문에서 이 문제를 완벽하게 해결하는 **공동 합의(Joint Consensus, $C_{old,new}$)** 프로토콜을 제안했습니다.

설정을 $C_{old}$에서 $C_{new}$로 한 번에 건너뛰지 않고, 두 설정의 과도기적 합집합인 **과도기 설정(Joint Configuration) $C_{old,new}$**를 경유하는 2단계 전이(Two-Phase Transition)를 수행합니다.

### 3.1 2단계 라이프사이클

```
[Phase 0: C_old]
       │
       ▼ (리더가 C_old,new 엔트리 생성 및 복제 시작)
[Phase 1: 공동 합의 C_old,new] ──► ⚡️ 이중 쿼럼(Dual-Majority) 필수!
       │                           (C_old 과반수 AND C_new 과반수 동시 만족)
       ▼ (C_old,new 엔트리가 이중 쿼럼으로 커밋 완료!)
[Phase 2: 최종 합의 C_new]     ──► C_new 단일 과반수만으로 커밋
       │
       ▼ (C_new 커밋 완료)
[Phase 3: 불필요한 구 노드 안전 퇴역 (Decommission)]
```

### 3.2 이중 쿼럼 (Dual-Majority / Two Quorums) 법칙

$C_{old,new}$ 상태에서 리더 선출이나 로그 엔트리 커밋 등 **모든 합의 결정은 $C_{old}$의 과반수와 $C_{new}$의 과반수를 "동시에" 만족**해야만 합니다:

$$\text{Quorum}(C_{old,new}) = \text{Majority}(C_{old}) \land \text{Majority}(C_{new})$$

$C_{old} = \{1, 2, 3\}$이고 $C_{new} = \{1, 2, 3, 4, 5\}$일 때:
- 후보자가 당선되거나 로그가 커밋되려면:
  1. $\{1, 2, 3\}$ 집합에서 **적어도 2표 이상**을 얻어야 하고, **동시에**
  2. $\{1, 2, 3, 4, 5\}$ 집합에서 **적어도 3표 이상**을 얻어야 합니다!

### 3.3 스플릿 브레인이 불가능한 수학적 증명

- $\{1, 2\}$ 그룹은 $C_{old}$의 과반수(2/3)는 만족하지만, $C_{new}$ 관점에서는 5대 중 2대(2/5)에 불과하므로 $C_{new}$ 과반수에 미달하여 탈락합니다.
- $\{3, 4, 5\}$ 그룹은 $C_{new}$의 과반수(3/5)는 만족하지만, $C_{old}$ 관점에서는 3대 중 1대(1/3, 노드 3)에 불과하므로 $C_{old}$ 과반수에 미달하여 탈락합니다.
- **결론**: 두 개의 상호 배타적인(Disjoint) 그룹이 동시에 과반수를 충족하는 것은 수학적으로 불가능하므로, 스플릿 브레인이 100% 원천 차단됩니다!

## 4. 실무 구현 시의 핵심 불변식

1. **로그 기록 즉시 활성화 (Immediate Configuration Activation)**:
   - Raft 노드는 설정 변경 엔트리($C_{old,new}$ 또는 $C_{new}$)가 **커밋될 때까지 기다리지 않고, 자신의 로컬 로그에 추가되자마자 즉시 그 설정을 활성화**합니다.
2. **리더의 퇴역 처리 (Leader Decommissioning)**:
   - 노드 교체 작업으로 인해 기존 리더가 $C_{new}$에 포함되지 않는 경우(예: $\{1, 2, 3\} \to \{2, 3, 4\}$에서 노드 1), 리더는 $C_{new}$ 엔트리가 커밋된 직후 팔로워로 자진 강등하고 안전하게 클러스터를 떠납니다.
3. **빈번한 설정 변경 금지**:
   - 이전 설정 변경($C_{old,new} \to C_{new}$)이 최종 커밋되기 전에는 새로운 설정 변경을 중첩해서 시작할 수 없습니다.
