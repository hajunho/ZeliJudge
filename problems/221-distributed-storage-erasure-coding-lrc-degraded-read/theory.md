# 문제 221 이론: 대규모 분산 스토리지 이레이저 코딩(Erasure Coding): Reed-Solomon(RS)과 로컬 복구 코드(LRC) 및 Degraded Read 테일 레이턴시 공학

---

## 1. 3중 복제(Replication) vs 이레이저 코딩(Erasure Coding) 경제학

대규모 클라우드 분산 스토리지(AWS S3, Azure Storage, Google Cloud Storage, Ceph)에서 가장 중요한 하드웨어 비용 요소는 원시 디스크 용량입니다.

### 1.1 3중 복제(3x Replication)의 한계
- **스토리지 오버헤드**: 원본 데이터 1PB를 저장하기 위해 3PB의 물리 디스크가 필요합니다 (오버헤드 200%).
- **장점**: 특정 노드가 다운되더라도 나머지 2개의 복제본 중 하나에서 원본 데이터를 즉시 1:1로 읽을 수 있어 디코딩 CPU 오버헤드가 없고 복구 읽기가 매우 단순합니다.
- **단점**: 엑사바이트(EB) 단위 인프라에서는 수천억 원의 디스크 구매 비용과 전력/상면 비용이 낭비됩니다.

### 1.2 Reed-Solomon (RS) 이레이저 코딩
- 데이터를 $k$개의 데이터 청크로 분할하고, 갈루아 체(Galois Field $GF(2^w)$) 연산을 통해 $m$개의 패리티 청크를 생성합니다.
- **스토리지 오버헤드**: $O_{\text{RS}} = \frac{k+m}{k} \times 100\%$
  - 예: $RS(10, 4) \implies \frac{14}{10} = 1.4\times$ (오버헤드 40%). 3중 복제 대비 **53%의 물리 디스크 비용을 절감**합니다.
- **내결함성(Fault Tolerance)**: 최대 $m$개의 청크가 손실되어도 임의의 $k$개 청크만 남아있으면 반데르몬드(Vandermonde) 또는 코시(Cauchy) 행렬의 역행렬을 곱하여 원본 $k$개 데이터를 100% 복원할 수 있습니다.

## 2. 분산 환경에서 Degraded Read와 테일 레이턴시(Tail Latency) 폭발

### 2.1 제프 딘의 'The Tail at Scale' (CACM 2013)
정상 상태에서 클라이언트는 자신이 원하는 데이터 청크가 저장된 노드 1곳에만 접근합니다.
그러나 드라이브 고장, 랙 점검, 백그라운드 스크러빙 등으로 인해 대상 청크 노드가 응답하지 못하면 시스템은 **손상 읽기(Degraded Read / Reconstruction Read)** 모드로 전환됩니다.

### 2.2 순서 통계량(Order Statistics)과 롱테일 증폭 수학
$RS(k, m)$에서 청크 1개를 복구하려면 **서로 다른 $k$개 노드로부터 청크를 병렬 수신**해야 합니다.
복구 읽기의 총 지연시간은 수신해야 하는 $k$개 노드 중 **가장 느린 노드의 지연시간**에 의해 지배됩니다:
$$T_{\text{degraded}} = \max(T_1, T_2, \dots, T_k) + T_{\text{decode}}$$

각 스토리지 노드가 99% 확률로 15ms 내에 응답하고, 1% 확률($p = 0.01$)로 200ms 이상의 스트래글러(Straggler) 지연을 겪는다고 가정합시다.
- 단일 노드 정상 읽기 시 스트래글러를 만날 확률: $1\%$
- $RS(10, 4)$ 복구 읽기($k=10$) 시 스트래글러를 최소 1개 만날 확률:
  $$P(\text{At least 1 straggler}) = 1 - (1 - p)^k = 1 - (0.99)^{10} = 1 - 0.9044 \approx 9.56\%$$
- 만약 고장률이나 지터 확률이 $p = 0.05$ (5%)라면:
  $$P(\text{At least 1 straggler}) = 1 - (0.95)^{10} = 1 - 0.5987 \approx 40.13\%!$$
즉, 복구 읽기의 **40% 이상이 최악의 드라이브 지연시간에 붙잡혀 서비스 SLA를 붕괴**시킵니다.

### 2.3 네트워크 증폭과 스위치 포화
청크 크기가 64MB일 때:
단 1개의 64MB 청크를 복구하기 위해 ToR 스위치를 거쳐 전송되는 네트워크 트래픽은 $10 \times 64\text{MB} = 640\text{MB}$에 달합니다 (10배 네트워크 증폭).

## 3. 로컬 복구 코드(Local Reconstruction Codes, LRC)

Microsoft Research(Cheng Huang et al., USENIX ATC 2012)는 Windows Azure Storage(WAS)의 페타바이트 운영 경험을 바탕으로 **LRC(Local Reconstruction Codes)**를 발표했습니다.

```
 [LRC(12, 2, 2) Hierarchical Parity Architecture]

   Local Group 0 (6 Data + 1 Local Parity):
   [ D0 ] [ D1 ] [ D2 ] [ D3 ] [ D4 ] [ D5 ] ───► [ L0 = D0 ^ D1 ^ ... ^ D5 ]

   Local Group 1 (6 Data + 1 Local Parity):
   [ D6 ] [ D7 ] [ D8 ] [ D9 ] [ D10] [ D11] ───► [ L1 = D6 ^ D7 ^ ... ^ D11 ]

   Global Parity (Covers ALL 12 Data Chunks):
   [ G0 ], [ G1 ] (Computed via Cauchy RS over D0..D11)
```

### 3.1 LRC의 핵심 설계 원리
실제 데이터센터 장애 통계에 따르면, **동시 드라이브 장애의 90% 이상은 '단 1개의 노드' 고장**입니다.
LRC는 단일 장애 복구를 위해 전체 $k$개를 모두 읽을 필요가 없도록, 데이터 청크를 $l$개의 로컬 그룹으로 나누고 각 그룹마다 단순 XOR 기반의 로컬 패리티($L_i$)를 둡니다.

1. **단일 장애 복구 로컬리티(Locality $r = k / l$)**:
   - $LRC(12, 2, 2)$에서 $D_1$이 고장 나면, Group 0에 속한 5개의 데이터 청크와 로컬 패리티 $L_0$ 총 **6개만 읽어서 복구**합니다.
   - 네트워크 전송량: $12 \times 64\text{MB} = 768\text{MB} \to 6 \times 64\text{MB} = 384\text{MB}$ (**50% 절감**).
   - 스트래글러 노출 확률: Group 1에 스트래글러 노드가 있더라도 전혀 접근하지 않으므로 완전히 격리됩니다.
2. **다중 장애 시 글로벌 복구(Global Reconstruction) 폴백**:
   - 만약 동일 로컬 그룹 내에서 2개 이상의 청크가 동시에 고장 나면, 로컬 패리티만으로는 풀 수 없으므로 전체 풀에서 글로벌 패리티 $G_0, G_1$을 포함한 $k=12$개를 읽어 기존 RS 방식으로 복원합니다.

## 4. 투기적 헤징 요청(Speculative Hedged Reads) 기법

스트래글러 회피를 위한 소프트웨어 최적화로 구글(Jeff Dean)이 고안한 **Hedged Requests** 패턴이 널리 사용됩니다.
- 복구에 필요한 최소 청크 수가 $k$개일 때, 클라이언트는 $k$개만 요청하는 대신 **$k+1$개(또는 여유분) 노드에 동시에 요청**을 보냅니다.
- 가장 먼저 응답을 완료한 $k$개의 패킷을 취하여 디코딩을 수행하고, 아직 응답하지 않은 가장 느린 1개의 연결은 즉시 취소(`cancel`)합니다.
- 이 기법은 단 10%의 추가 네트워크 오버헤드로 스트래글러로 인한 극단적 P99 레이턴시 스파이크를 거의 0에 가깝게 제거합니다.
