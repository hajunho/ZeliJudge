# [CS-106] 서버 메모리가 16GB인데 프로세스들이 64GB를 잡고 있어요?!: Linux 가상 메모리 오버커밋(Overcommit)과 OOM-Killer 희생양 스코어링 (`oom_score_adj`)

> **"선생님! 우리 서버 RAM이 16GB밖에 안 되는데, 프로세스들이 `malloc()`으로 총 64GB를 할당받았는데도 에러가 안 나요! 그런데 왜 새벽에 아무 에러 로그도 없이 가장 중요한 Redis 프로세스가 'Killed'라는 단어 하나만 남기고 죽었을까요?!"**
> 
> 데이터 플랫폼을 운영하는 신입 엔지니어 도현이는 서버 모니터링을 보다가 기겁했습니다.
> 16GB 물리 메모리를 탑재한 인스턴스에서 프로세스들의 가상 메모리(VIRT) 총합이 무려 64GB를 넘고 있었기 때문입니다.
> "메모리가 4배나 뻥튀기되었는데 어떻게 프로세스들이 살아있지?" 하고 신기해하던 그 순간, 회사의 메인 캐시이자 세션 스토리지인 Redis 프로세스가 `Exit Code 137 (SIGKILL)`로 돌연 즉사했습니다.
> 
> 애플리케이션 로그에는 에러 스택트레이스가 단 한 줄도 없었습니다.
> 당황한 도현이에게 인프라 아키텍트는 `dmesg -T` 명령어를 실행하여 커널 로그를 보여주었습니다:
> `Out of memory: Killed process 1420 (redis-server) total-vm:16777216kB, anon-rss:12582912kB, oom_score_adj:0`
> 
> "도현 씨, 항공사가 비행기 좌석 100개에 예약 150명을 받는 '오버부킹'을 하듯, 리눅스 커널도 메모리를 '오버커밋'해요. 하지만 승객이 전부 공항에 나타나면, 기장은 비행기를 띄우기 위해 가장 덩치 큰 승객을 비행기 밖으로 던져버립니다(OOM-Killer)."

---

## 1. 리눅스 가상 메모리 오버커밋(Memory Overcommit)이란?

프로그램이 `malloc(10GB)`을 호출한다고 해서 운영체제가 즉시 물리 RAM 10GB를 내어주는 것은 아닙니다.
대부분의 프로그램은 메모리를 넉넉하게 예약(Virtual Memory Allocation)해두고, 실제로 사용하는 양(Resident Set Size, RSS)은 훨씬 적습니다.

리눅스 커널은 메모리 활용률을 극대화하기 위해, **현재 남아있는 물리 RAM보다 훨씬 더 많은 가상 메모리 할당 요청을 승인하는 '오버커밋(Overcommit)'** 정책을 기본적으로 사용합니다.

### 커널 오버커밋 제어: `/proc/sys/vm/overcommit_memory`

1. **`0` (Heuristic Overcommit, 기본값)**:
   - 커널이 휴리스틱 알고리즘을 사용하여 "너무 황당하게 큰 요청(예: 주소 공간 전체 할당 등)"이 아니면 적당히 오버커밋을 허용합니다.
2. **`1` (Always Overcommit)**:
   - 물리 메모리가 얼마가 남았든 묻지도 따지지도 않고 모든 `malloc()` 요청을 무조건 승인합니다.
   - **Redis 공식 권장 설정**: Redis가 백그라운드 스냅샷(`BGSAVE`)을 위해 `fork()`할 때, Copy-On-Write(COW)로 인해 순간적으로 가상 메모리가 2배로 잡히는 현상이 발생합니다. 이때 `overcommit_memory = 1`이 아니면 `fork()` 자체가 `ENOMEM`으로 실패하므로, Redis는 이 설정을 강력히 요구합니다.
3. **`2` (Strict / No Overcommit)**:
   - 절대 과도한 오버커밋을 허용하지 않는 엄격한 모드입니다.
   - 가상 메모리 할당 총합은 다음 공식으로 계산되는 **커밋 한도(Commit Limit)**를 결코 넘을 수 없습니다:
     $$	ext{CommitLimit} = 	ext{Swap} + \left(	ext{RAM} 	imes rac{	ext{overcommit\_ratio}}{100}ight)$$
   - 한도를 초과하는 `malloc()` 요청은 커널이 즉시 거부하고 `ENOMEM` 에러를 반환합니다.

## 2. 참사의 순간: OOM(Out Of Memory)과 OOM-Killer

오버커밋 덕분에 평화롭게 돌아가던 서버에 위기가 닥칩니다.
프로세스들이 예약만 해두었던 가상 메모리에 실제로 데이터 쓰기(Page Touch)를 시작한 것입니다!
- 가상 페이지에 실제 데이터가 쓰이는 순간, CPU MMU의 페이지 폴트(Page Fault)가 발생하고 물리 RAM 페이지가 하나씩 소비됩니다.
- 어느 순간 물리 RAM과 스왑 공간이 $100\%$ 고갈되어, 커널조차 단 1페이지의 메모리도 확보할 수 없는 극한의 상황(**OOM, Out Of Memory**)에 도달합니다.
- 이때 시스템 전체가 굳어버리는 커널 패닉(Kernel Panic)을 막기 위해, 리눅스 커널의 최후의 보루인 **OOM-Killer**가 깨어납니다!

---

## 3. 희생양 선정 알고리즘: `oom_badness()`와 `oom_score`

OOM-Killer는 무작위로 프로세스를 죽이지 않습니다. 커널 내부 함수 `oom_badness()`를 호출하여 모든 프로세스의 **"사형 점수(oom_score, 0 ~ 1000점)"**를 채점합니다.

### 1) 기본 점수 (Base Score)
- 프로세스가 점유하고 있는 물리 메모리(RSS)가 전체 RAM에서 차지하는 비율에 비례하여 0~1000점이 부여됩니다:
  $$	ext{base\_score} = \left\lfloor rac{	ext{proc\_rss\_pages}}{	ext{total\_ram\_pages}} 	imes 1000 ightfloor$$
- 즉, **물리 메모리를 가장 많이 처먹고 있는 뚱뚱한 놈**이 가장 높은 점수를 받습니다!

### 2) 관리자의 개입: `oom_score_adj` (-1000 ~ +1000)
- 시스템 관리자는 `/proc/<pid>/oom_score_adj` 파일에 값을 써서 OOM-Killer의 사형 집행 우선순위를 직접 조정할 수 있습니다.
- 최종 점수:
  $$	ext{oom\_score} = \min(1000, \max(0, 	ext{base\_score} + 	ext{oom\_score\_adj}))$$
- **특별한 값 `-1000` (OOM_SCORE_ADJ_MIN)**:
  - 이 값이 설정된 프로세스는 점수가 무조건 `-1000`으로 처리되어 **사형 집행 대상에서 영구 면제(Immune)**됩니다!
  - 아무리 메모리를 99% 점유하고 있더라도 OOM-Killer가 절대 건드리지 않습니다 (`sshd`, `systemd`, 데이터베이스 마스터 등).
- **양수 값 (예: `+500`, `+1000`)**:
  - 메모리를 조금만 쓰더라도 OOM-Killer에게 가장 먼저 사살당하는 총알받이(Victim)로 지정할 때 사용합니다.

### 3) 처형 집행 (Execution)
- 면제되지 않은 프로세스 중 `oom_score`가 가장 높은 프로세스를 선정하여 `SIGKILL (Kill -9)` 시그널을 강제로 내리꽂습니다.
- 희생자가 죽으면서 점유하고 있던 모든 물리 메모리가 즉시 회수되어 시스템이 기적적으로 숨통을 틉니다.

## 4. 실무 핵심 요약 및 아키텍처 베스트 프랙티스

1. **핵심 데몬의 OOM 면제 설정**:
   - 데이터베이스(MySQL, PostgreSQL, Redis)나 핵심 게이트웨이가 메모리를 많이 쓴다는 이유로 OOM-Killer에게 사살당하면 서비스 전체가 마비됩니다.
   - `systemd` 서비스 유닛에 `OOMScoreAdjust=-1000`을 설정하여 커널 레벨에서 사형 면제권을 부여해야 합니다.
2. **배치/분석 프로세스의 총알받이 격리**:
   - 무거운 데이터 분석 스크립트나 배치 작업에는 `OOMScoreAdjust=500`을 주어, 메모리 부족 시 메인 웹서버 대신 배치가 먼저 희생되도록 유도합니다.
3. **컨테이너 환경(Cgroup)의 OOM 격리**:
   - 쿠버네티스 파드(Pod)에 Memory Request/Limit을 설정하면 호스트 전체가 아니라 해당 컨테이너의 cgroup 내에서만 OOMKilled가 발생하도록 장애 반경을 완벽하게 격리할 수 있습니다.
