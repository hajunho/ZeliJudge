# 세대별 가비지 컬렉션과 조기 승격의 덫 (Generational GC STW & Premature Promotion)

> **"분명히 메모리는 충분한데, 왜 서버가 10초마다 1초씩 멈춰서 타임아웃 에러를 뿜을까요?!"**  
> **"레스토랑의 냅킨 치우기 vs 창고 대청소의 비극 (Stop-The-World와 조기 승격)"**

---

## 1. 현실 세계 비유: 일회용 냅킨 치우기와 창고 대청소

손님이 끊이지 않는 대형 레스토랑의 쓰레기 처리 시스템을 상상해 봅시다.

```
[비극적인 상황: 창고에 처박힌 냅킨들 (조기 승격, Premature Promotion)]
1. 손님이 식사를 마치고 나면 테이블 위 쓰레기의 99%는 갓 쓴 일회용 냅킨과 종이컵(단기 객체)입니다.
2. 테이블 옆에는 냅킨을 임시로 모아두는 작은 쓰레기통(Survivor 영역)이 있습니다.
3. 그런데 쓰레기통이 너무 작아서 냅킨이 금방 넘쳐납니다.
4. 어리석은 지배인은 생각합니다: "쓰레기통이 꽉 찼네? 저 냅킨 뭉치를 전부 안쪽 깊은 창고(Old Generation)에 처박아 둬라!"
5. 단 1분 만에 버려져야 할 일회용 냅킨들이 장기 보관 창고(Old)에 산더미처럼 쌓입니다.
6. 결국 창고가 꽉 차자 지배인은 사이렌을 울립니다:
   "창고 대청소(Full GC)를 해야 하니 손님들은 전부 밖으로 나가세요! 30분 동안 레스토랑 영업을 전면 중단합니다!" (Stop-The-World 마비)
7. 밖에서 기다리던 손님들(HTTP 요청)은 음식을 못 먹고 떠나버리고(타임아웃), 구청 위생과(쿠버네티스)는 레스토랑을 강제 영업정지(파드 Restart)시킵니다!
```

```
[지혜로운 상황: 세대별 쓰레기 관리 (Tuned Generational GC)]
1. 지배인은 테이블 옆 쓰레기통(Survivor 영역)을 충분히 크게 마련했습니다.
2. 냅킨과 종이컵은 테이블 옆 쓰레기통 안에서 몇 분 머물다가 다음 손님이 오기 전에 홀 웨이터(Minor GC)가 0.1초 만에 비웁니다 (STW 1ms 미만, 손님은 청소하는 줄도 모름).
3. 진짜 오래 보관해야 할 식기류나 인테리어 비품(장기 객체)만 선별하여 창고(Old)에 보관하므로, 창고 대청소(Full GC)를 할 일이 몇 달에 한 번도 없습니다!
```

## 2. 약한 세대 가설 (Weak Generational Hypothesis)

자바(JVM), V8(Node.js), Go 등 현대 엔터프라이즈 런타임의 가비지 컬렉터는 컴퓨터 과학 역사상 가장 위대한 통계적 관찰에 기반합니다:

> **1. 대부분의 객체는 생성된 지 얼마 되지 않아 아주 짧은 시간 안에 죽는다 (Most objects die young).**  
> **2. 오래 살아남은 객체에서 젊은 객체로의 참조는 극히 드물다.**

웹 서버에서 생성되는 95% 이상의 객체(DTO, JSON 파싱 객체, 임시 문자열, 로컬 변수)는 HTTP 요청 1건을 처리하는 수 밀리초(ms) 사이에 쓰이고 즉시 수명을 다합니다.  
따라서 **"전체 메모리를 한 덩어리로 보고 뒤지는 무식한 청소"** 대신, 힙을 **젊은 세대(Young Gen)**와 **오래된 세대(Old Gen)**로 물리적으로 분할한 것입니다.

## 3. JVM 세대별 메모리 구조와 객체 순환 라이프사이클

```
┌─────────────────────────────────────────────────────────────┬───────────────────────────┐
│                    Young Generation                         │      Old Generation       │
│  ┌───────────────────────────┬──────────────┬──────────────┐│                           │
│  │       Eden Space          │ Survivor 0   │ Survivor 1   ││   Tenured Space (Old)     │
│  │   (신규 객체 즉시 할당)     │ (From-Space) │ (To-Space)   ││ (검증된 장기 객체 보관 구역)  │
│  └───────────────────────────┴──────────────┴──────────────┘│                           │
└─────────────────────────────────────────────────────────────┴───────────────────────────┘
```

1. **Eden 영역 할당**: 모든 `new` 객체는 가장 먼저 Eden 영역에 할당됩니다.
2. **Minor GC (Young GC)**:
   - Eden 영역이 꽉 차면 발동합니다.
   - Eden에서 아직 살아있는 극소수의 객체만 골라 Survivor 영역으로 복사(Copying)하고, 죽은 객체들은 Eden 전체를 0으로 리셋하여 순식간에 날려버립니다.
   - 스캔 범위가 매우 좁으므로 **STW 일시정지 시간이 수 밀리초(1~3ms) 이내로 극히 짧습니다**.
3. **Survivor 교대와 Age 증가**:
   - Minor GC가 돌 때마다 Survivor0과 Survivor1 사이를 번갈아 복사되며, 살아남을 때마다 객체의 **나이(Tenuring Age)**가 1씩 증가합니다.
4. **승격 (Promotion)**:
   - 나이가 임계값(`MaxTenuringThreshold`, 예: 3~15)에 도달한 진짜 장기 객체(싱글톤 Bean, 캐시 등)만 비로소 Old 영역으로 이동합니다.

## 4. 조기 승격(Premature Promotion)의 저주와 Full GC 폭풍

실무에서 성능 재앙을 일으키는 주범은 바로 **Survivor 영역의 과소 설정**입니다:

- **상황**: 대용량 트래픽이 몰려 일시적으로 Minor GC 생존 객체 크기가 Survivor 영역 용량을 초과함 (`Overflow`).
- **참사 (조기 승격)**: JVM은 나이(`age`)가 1밖에 안 된 단기 임시 객체들을 어쩔 수 없이 **Old 영역으로 강제 밀어 넣습니다(Premature Promotion)**!
- **결과**:
  - 단기 객체들은 Old 영역에 들어가자마자 1초 뒤에 사망합니다.
  - 하지만 Old 영역은 Minor GC의 수거 대상이 아니므로, 죽은 단기 객체들이 Old 영역을 쓰레기장으로 만듭니다.
  - 결국 Old 영역이 가득 차서 **Full GC (Major GC)**가 격발됩니다!
  - Full GC는 기가바이트(GB) 단위의 거대한 Old 힙 전체를 전수 조사하고 단편화를 해결하기 위해 메모리를 압축(Compaction)하므로, **수 초(1,000ms ~ 5,000ms) 동안 애플리케이션의 모든 스레드를 정지(Stop-The-World)**시킵니다.
  - 전사 HTTP 타임아웃, 마이크로서비스 연쇄 헬스체크 실패, 쿠버네티스 파드 재시작 폭풍이 이어집니다.

---

## 5. 실무 튜닝 핵심 3원칙

1. **"단기 객체는 영 영역(Young Gen) 안에서 죽게 하라!"**:
   - Survivor 영역 크기를 넉넉하게 설정하여 피크 트래픽에서도 조기 승격이 발생하지 않도록 완충 공간을 확보합니다.
2. **불필요한 대용량 임시 객체 생성 지양**:
   - `byte[]` 버퍼 재사용, 큰 JSON 문자열 통째 파싱 지양, 스트리밍 처리.
3. **최신 저지연 가비지 컬렉터 도입**:
   - G1GC, ZGC, Shenandoah GC 등 STW 정지 시간을 10ms 이하로 줄여주는 동시성(Concurrent) 수집기 활용.

> **"Full GC는 시스템의 비명이다. 힙 메모리를 무작정 늘리지 말고, 객체가 어디서 죽고 있는지 세대별 흐름을 보라."**  
> 이것이 초당 수십만 건의 결제를 10밀리초 이내로 처리하는 글로벌 금융/테크 기업의 JVM 튜닝 제1원칙입니다.
