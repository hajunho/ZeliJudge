# [ZeliJudge #021] async로 짰는데 왜 1초씩 멈춰요?: 싱글 스레드 이벤트 루프와 블로킹 I/O의 배신

## 📌 문제 배경 스토리
쇼핑몰 '젤리마켓'의 백엔드 개발자 젤리는 초당 수만 건의 트래픽을 감당하기 위해 파이썬의 고성능 비동기 웹 프레임워크인 **FastAPI**를 도입했습니다.
젤리는 비동기 프로그래밍이 마법의 은총알이라고 굳게 믿고, 모든 API 함수 앞에 `async def`를 붙였습니다:

```python
# [젤리가 작성한 비동기 API 코드]
@app.get("/api/report")
async def generate_report():
    # 젤리가 무심코 넣은 2초짜리 동기식 슬립 (또는 외부 requests.get 동기 호출)
    time.sleep(2)
    return {"status": "success"}

@app.get("/api/ping")
async def ping():
    # 0.01초 만에 끝나야 하는 초고속 핑 체크
    await asyncio.sleep(0.01)
    return {"pong": True}
```

젤리는 생각했습니다:
*"FastAPI는 비동기니까 `/api/report`가 2초 동안 쉬더라도, 다른 사용자의 `/api/ping` 요청은 백그라운드에서 알아서 0.01초 만에 쌩쌩 돌아가겠지?"*

하지만 실제 서비스가 오픈되자마자 서버 관제 화면에 빨간 불이 들어왔습니다:
1. 어떤 사용자가 엑셀 보고서 다운로드(`/api/report`)를 한 번 누른 순간,
2. 가볍게 접속한 수백 명의 일반 사용자들의 화면이 **2초 동안 완전히 멈춰서 흰 화면(White Screen)**으로 변해버렸습니다!
3. 심지어 이미 데이터베이스 조회가 다 끝나서 응답만 기다리던 결제 요청들까지 모조리 2초씩 지연되다가 타임아웃 에러를 뿜었습니다!

CTO는 머리를 감싸 쥐며 젤리를 호출했습니다:
*"젤리 씨! Python의 `asyncio`나 Node.js의 JavaScript 런타임은 **단 하나의 메인 스레드(Single Thread)**에서 동작하는 **이벤트 루프(Event Loop)** 기반이에요!"*
*"비동기 함수 안에서 `time.sleep()`이나 `requests.get()` 같은 **동기식 블로킹(Blocking) 함수**를 호출하면, **동사무소 직원이 한 명뿐인 단일 창구에서 손님이 도장 찍겠다고 창구 책상을 2초 동안 온몸으로 틀어막고 버틴 것**과 똑같습니다!"*
*"그 2초 동안 이벤트 루프는 숨이 멎어서, 다른 어떤 요청도 시작하지 못하고 이미 끝난 비동기 I/O의 완료 이벤트조차 처리하지 못한다고요!"*

CTO는 싱글 스레드 이벤트 루프에서 블로킹 작업이 전체 서버에 미치는 재앙적인 연쇄 지연을 개발팀 전원에게 시각화하여 경각심을 심어주기 위해, **이벤트 루프 블로킹 시뮬레이터**를 개발하라고 지시했습니다.

---

## ⚙️ 시스템 동작 규칙

단일 스레드로 동작하는 이벤트 루프는 시간 $T=0$부터 시작하며, 도착한 요청들을 순서대로 처리합니다.

### 1. 작업의 종류
각 요청은 작업 유형(`task_type`)과 소요 시간(`duration`)을 가집니다:

1. **`ASYNC` (비동기 협력 논블로킹 작업)**:
   - `await asyncio.sleep(duration)` 또는 논블로킹 I/O를 모방합니다.
   - 메인 스레드는 요청을 등록(dispatch)하는 즉시($0$ms) 다음 작업을 처리할 수 있습니다.
   - 실제 I/O 대기는 백그라운드에서 진행되며, 시작 시각으로부터 정확히 $duration$ 밀리초 후($t_{io\_done} = t_{start} + duration$)에 I/O가 완료됩니다.
   - **주의**: I/O가 완료되었더라도, 그 순간 메인 스레드가 `BLOCK` 작업에 의해 점유되어 있다면 완료 이벤트(응답 반환)를 처리하지 못하고 메인 스레드가 풀려날 때까지 지연됩니다!
2. **`BLOCK` (동기식 블로킹 작업)**:
   - `time.sleep(duration)` 또는 무거운 CPU 집약적 연산을 모방합니다.
   - 시작 시각부터 **정확히 $duration$ 밀리초 동안 메인 스레드를 100% 독점**합니다.
   - 이 점유 시간 동안 이벤트 루프 전체가 얼어붙으므로:
     - 새로운 요청이 도착해도 시작하지 못하고 큐에서 대기합니다.
     - 이미 백그라운드에서 I/O가 끝난 `ASYNC` 작업도 완료 응답을 보내지 못하고 블로킹이 끝날 때까지 대기합니다.

---

### 2. 이벤트 루프 스케줄링 및 완료 시각 계산

메인 스레드의 점유 종료 시각을 나타내는 변수를 $busy\_until$ (초기값 $0$)이라 합니다.

요청은 도착 시각 $t_{arrive}$ 오름차순으로 입력됩니다:

1. **작업 시작 시각 ($t_{start}$)**:
   - 메인 스레드가 비어 있어야 작업을 디스패치할 수 있습니다:
     $$t_{start} = \max(t_{arrive}, busy\_until)$$

2. **메인 스레드 점유 (`BLOCK` vs `ASYNC`)**:
   - 작업이 `BLOCK`인 경우:
     - 메인 스레드를 독점하므로 점유 종료 시각이 연장됩니다:
       $$busy\_until = t_{start} + duration$$
     - 이 작업 자체의 완료 시각:
       $$t_{finish} = busy\_until$$
     - 블로킹 구간 $[t_{start}, busy\_until)$이 형성됩니다.
   - 작업이 `ASYNC`인 경우:
     - 메인 스레드를 점유하지 않으므로 $busy\_until$은 변경되지 않습니다.
     - 백그라운드 I/O 완료 예정 시각:
       $$t_{io\_done} = t_{start} + duration$$

3. **`ASYNC` 작업의 최종 완료 시각 ($t_{finish}$)**:
   - 백그라운드 I/O 완료 시각 $t_{io\_done}$에 메인 스레드가 블로킹 중인지 확인합니다.
   - 만약 $t_{io\_done}$이 어떤 `BLOCK` 작업의 점유 구간 $[S, E)$ 내에 포함되어 있다면 ($S \le t_{io\_done} < E$):
     - 메인 스레드가 얼어붙어 있으므로 완료 콜백 처리가 블로킹 종료 시점까지 지연됩니다:
       $$t_{finish} = E$$
   - 만약 어떤 블로킹 구간에도 포함되지 않는다면(메인 스레드가 정상 가동 중):
     $$t_{finish} = t_{io\_done}$$

4. **지연 시간 ($delay$) 계산**:
   - 이상적인 환경(블로킹 방해가 전혀 없는 환경)이었다면 요청은 $t_{arrive} + duration$에 완료되었을 것입니다.
   - 따라서 블로킹으로 인해 억울하게 지연된 시간은 다음과 같습니다:
     $$delay = t_{finish} - (t_{arrive} + duration)$$

## 📥 입력 형식 (Input)

- 첫째 줄에 총 요청의 개수 $N$이 주어집니다. ($1 \le N \le 100,000$)
- 둘째 줄부터 $N$개의 줄에 걸쳐 각 요청 정보가 도착 시각 오름차순으로 주어집니다:
  `REQ <req_id> <arrive_time> <task_type> <duration>`
- `<req_id>`: 영문과 숫자로 이루어진 1~20자의 고유 요청 식별자.
- `<arrive_time>`: 요청 도착 시각 (밀리초 단위의 정수, $0 \le arrive\_time \le 10^9$).
- `<task_type>`: `ASYNC` 또는 `BLOCK`.
- `<duration>`: 소요 시간 (밀리초 단위의 양의 정수, $1 \le duration \le 10^6$).

---

## 📤 출력 형식 (Output)

- 각 요청에 대해 처리 결과를 한 줄씩 출력합니다:
  `EVENT <req_id> START:<t_start> FINISH:<t_finish> DELAY:<delay>`
- 마지막 줄에 시스템 전체 요약 통계를 출력합니다:
  `SUMMARY TOTAL:<N> MAX_DELAY:<max_delay> AVG_DELAY:<avg_delay>`
  - `<max_delay>`: 전체 요청 중 가장 큰 지연 시간 (정수).
  - `<avg_delay>`: 전체 요청의 평균 지연 시간 (소수점 둘째 자리까지 반올림 표기, 예: `0.00`, `12.34`).

---

## 💡 입출력 예시 (Example)

### 예시 입력 1
```text
3
REQ R1 0 ASYNC 100
REQ R2 10 BLOCK 200
REQ R3 50 ASYNC 20
```

### 예시 출력 1
```text
EVENT R1 START:0 FINISH:210 DELAY:110
EVENT R2 START:10 FINISH:210 DELAY:0
EVENT R3 START:210 FINISH:230 DELAY:160
SUMMARY TOTAL:3 MAX_DELAY:160 AVG_DELAY:90.00
```

### 예시 설명 1
- **R1** (`ASYNC 100`): $t=0$에 즉시 시작되어 백그라운드에서 진행됩니다. 원래 $t=100$에 완료되어야 하지만, $t=10$부터 $t=210$까지 R2의 블로킹으로 이벤트 루프가 멈춰있어 R2가 끝나는 $t=210$에야 응답을 마칩니다. (지연 $210 - 100 = 110$ms)
- **R2** (`BLOCK 200`): $t=10$에 메인 스레드를 잡고 $t=210$까지 200ms 동안 이벤트 루프를 동결시킵니다. 본인 완료 시각은 210입니다. (지연 0ms)
- **R3** (`ASYNC 20`): $t=50$에 도착했지만 메인 스레드가 블로킹 중이어서 $t=210$까지 시작조차 못 하고 대기하다가 $t=210$에 시작되어 $t=230$에 끝납니다. 원래 $50+20=70$에 끝났어야 하므로 지연은 $230 - 70 = 160$ms에 달합니다!
- 총 지연 시간 $110 + 0 + 160 = 270$ms이며, 평균 지연 시간은 $270 / 3 = 90.00$ms입니다.
