# 커넥션 풀 크기의 함정과 리틀의 법칙 (Connection Pool Sizing & Little's Law)

> **"동시 접속자가 1,000명이니까 DB 커넥션 풀도 1,000개로 늘리면 빨라지지 않을까요?!"**  
> **"요리사 4명 있는 주방에 냄비 100개 갖다 놓으면 일어나는 끔찍한 비극"**

---

## 1. 현실 세계 비유: 4명의 요리사와 냄비 100개의 참사

유명 파스타 맛집 주방에 **요리사(CPU 코어)는 딱 4명**뿐입니다.  
점심 피크 시간이 되자 주문서(트래픽)가 100장씩 쏟아져 들어왔습니다.

```
[초보 주방 매니저의 착각: Oversized Pool = 100]
매니저는 "주문이 100개니까 냄비(DB 커넥션)도 100개를 동시에 불 위에 올려야지!"라며,
주방 바닥과 화구에 냄비 100개를 빽빽하게 깔아버렸습니다.

무슨 일이 일어났을까요?
1. 요리사 4명이 냄비 100개를 관리하느라 주방을 미친 듯이 뛰어다닙니다. (CPU Context Switching 폭증!)
2. 1번 냄비 면 한번 젓고, 20번 냄비 뚜껑 열고, 50번 냄비 소금 치고, 90번 냄비 불 조절하느라, 
   정작 파스타 한 접시를 끝까지 완성하지 못합니다!
3. 요리사끼리 복도에서 계속 어깨를 부딪치고(Lock 경합), 들고 있던 올리브유를 쏟아붓습니다(Cache Thrashing).
4. 결과: 평소 1분에 10접시씩 뽑아내던 주방이, 30분 동안 단 한 접시도 완성하지 못해 
   홀에 앉아있던 손님 100명이 굶어 죽다가 전원 주문 취소하고 뛰쳐나갑니다 (DB CPU 100% 타임아웃 폭사)!
```

```
[HikariCP / 백엔드 명장의 설계: Optimal Pool = 9]
베테랑 셰프는 주방 바닥의 쓸데없는 냄비를 모조리 치우고, 딱 9개의 냄비만 화구에 올립니다:
공식: (요리사 4명 x 2) + 1 = 9개!

손님 100명의 주문서는 냄비에 바로 올리지 않고, 주문서 꽂이(대기 큐 / Wait Queue)에 꽂아둡니다.
1. 요리사 4명은 9개 냄비에만 집중합니다. 동선이 꼬이지 않고, 컨텍스트 스위칭 낭비가 0에 수렴합니다.
2. 냄비 1개당 1분 만에 완벽한 파스타가 조리되어 즉시 손님 식탁으로 나갑니다.
3. 비어있는 냄비에 대기 중이던 다음 주문서가 즉시 투입됩니다.
4. 결과: 100접시의 파스타가 10분 만에 초고속으로 전량 서빙 완료됩니다!
```

## 2. 컴퓨터 과학의 물리적 한계: CPU와 컨텍스트 스위칭

컴퓨터 하드웨어에는 타협할 수 없는 물리 법칙이 존재합니다:
- **4코어 CPU는 물리적으로 정확히 동시에 4개의 스레드만 연산할 수 있습니다.**
- 만약 DB 서버에 100개의 커넥션이 동시에 쿼리를 실행하면, OS 스케줄러는 4개의 코어 위에서 100개의 스레드를 수 밀리초마다 번갈아 교체(Time-sharing)해야 합니다.

### 컨텍스트 스위칭(Context Switching)의 파괴적 비용
1. **레지스터 저장 및 복원**: 현재 스레드의 CPU 레지스터, 프로그램 카운터(PC), 스택 포인터를 메모리에 백업하고 다음 스레드의 상태를 로드합니다.
2. **CPU 캐시 무효화 (Cache Thrashing)**: CPU 내부의 초고속 L1, L2 캐시에 들어있던 데이터가 교체되면서, 연산 속도가 수백 배 느린 메인 메모리(RAM)를 계속 뒤지게 됩니다.
3. **디스크 I/O 및 락 경합**: 수십 개의 스레드가 InnoDB 버퍼 풀과 트랜잭션 락 테이블을 동시에 수정하려 들면서 뮤텍스 스핀락(Spinlock)에 걸려 CPU가 연산은 안 하고 대기하는 데만 쓰입니다 (`sys` CPU 100%).

## 3. 리틀의 법칙 (Little's Law)과 풀 사이징

큐잉 이론(Queueing Theory)의 기초인 **리틀의 법칙**은 시스템의 동시 처리량을 설명합니다:

$$L = \lambda \times W$$

- $L$: 시스템 내부에서 동시에 실행 중인 작업 수 (커넥션 풀 크기)
- $\lambda$: 단위 시간당 처리량 (Throughput / TPS)
- $W$: 작업 하나를 완료하는 데 걸리는 평균 체류 시간 (Latency)

### 왜 커넥션을 늘리면 레이턴시($W$)가 폭증하는가?
CPU 코어 수 $C$를 초과하여 $L$을 무작정 늘리면, 시스템 처리 능력의 물리적 상한선 때문에 $\lambda$는 더 이상 증가하지 않습니다.  
오히려 컨텍스트 스위칭 페널티로 인해 시스템의 실제 처리율 $\lambda$는 급감합니다.  
방정식 $W = \frac{L}{\lambda}$에 의해, **분자($L$)는 10배 커졌는데 분모($\lambda$)는 줄어들었으니 지연 시간($W$)이 수십 배로 폭증**하는 것입니다!

## 4. PostgreSQL & HikariCP의 황금 공식

스프링 부트(Spring Boot)의 기본 커넥션 풀인 **HikariCP**의 창시자 브렛 울드리지(Brett Wooldridge)와 PostgreSQL 공식 위키는 다음 공식을 제시합니다:

$$\text{connections} = (\text{core\_count} \times 2) + \text{effective\_spindle\_count}$$

- `core_count`: DB 서버의 물리 CPU 코어 수
- `effective_spindle_count`: 디스크 I/O 채널 수 (SSD나 고속 NVMe 환경에서는 보통 `1`)

### 실제 예시:
- 4코어 SSD 서버: $4 \times 2 + 1 = \mathbf{9}$ 또는 $10$개
- 8코어 SSD 서버: $8 \times 2 + 1 = \mathbf{17}$개
- 16코어 대형 서버: $16 \times 2 + 1 = \mathbf{33}$개

> **"1만 명의 유저를 받는 서비스라도, DB 커넥션 풀은 10~20개면 충분하고도 넘칩니다."**

## 5. 실무 프로덕션 벤치마크 (HikariCP Benchmark)

실제 프로덕션 웹 애플리케이션에서 커넥션 풀 크기를 조절하며 측정한 실제 벤치마크 결과:

| 커넥션 풀 크기 | 초당 처리량 (Throughput) | 평균 응답 지연 (Latency) | DB 서버 상태 |
| :---: | :---: | :---: | :--- |
| **2,048개** | 약 20,000 TPS | **100ms 이상 (스파이크 발생)** | CPU 컨텍스트 스위칭 폭증, 불안정 |
| **96개** | 약 20,000 TPS | **2ms (50배 단축!)** | CPU 사용률 안정화, 락 경합 완화 |
| **10개 (최적)** | 약 20,500 TPS | **1.5ms (극상의 쾌적함)** | 0% 스위칭 낭비, 가장 안정적인 P99 |

### 결론:
대기열(Queue)은 DB 내부에서 스레드들이 몸싸움하게 두는 것이 아니라, **HikariCP의 가벼운 메모리 대기 큐에서 조용히 대기**시켜야 DB가 최고 속도로 쿼리를 쳐낼 수 있습니다.
