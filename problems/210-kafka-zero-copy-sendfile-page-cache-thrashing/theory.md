# 분산 스트리밍 Kafka: OS 페이지 캐시와 Linux sendfile(2) Zero-Copy vs 유저 공간 버퍼 복사 및 페이지 캐시 스래싱 방어

## 1. 개요: 카프카가 JVM 힙 메모리 대신 OS 페이지 캐시를 선택한 이유

현대 분산 메시지 브로커(Apache Kafka, Redpanda, Apache Pulsar)는 초당 수백만 건의 이벤트를 수십~수백 Gbps의 유선 속도로 지속 전달해야 합니다.

일반적인 엔터프라이즈 자바 애플리케이션은 성능 향상을 위해 JVM 힙(Heap) 내부에 거대한 인메모리 캐시를 구성하지만, 카프카의 창시자들(Jay Kreps et al.)은 **JVM 힙 캐시를 완전히 포기하고 모든 데이터를 운영체제의 페이지 캐시(Page Cache)에 위임**하는 혁신적인 설계를 선택했습니다. 그 이유는 다음과 같습니다:

1. **객체 메모리 오버헤드 (Object Memory Bloat)**:
   자바 객체는 헤더(Header) 및 메모리 정렬 패딩으로 인해 실제 원시 데이터 크기 대비 $2 \sim 4\times$ 이상의 메모리를 낭비합니다. 반면 OS 페이지 캐시는 바이트 배열(Raw Binary)을 4KB 물리 프레임에 그대로 저장하므로 메모리 밀도가 2배 이상 높습니다.
2. **가비지 컬렉션(GC) 일시정지 제거**:
   64GB 이상의 거대한 힙에서 수천만 개의 메시지 객체를 GC가 스캔하고 회수할 때 발생하는 Stop-The-World(STW) 지연은 수 초에 달합니다. 페이지 캐시는 커널 레벨에서 C 언어로 관리되므로 GC 오버헤드가 정확히 $0$입니다.
3. **프로세스 재시작 무중단 (Instant Warm-up)**:
   브로커 프로세스가 크래시되거나 롤링 업그레이드로 재시작되어도, OS 커널 메모리에 상주하는 페이지 캐시는 그대로 유지되므로 재시작 즉시 캐시 웜업(Warm-up) 없이 최고 속도를 발휘합니다.

## 2. 전통적 I/O vs 리눅스 Zero-Copy (`sendfile`) 심층 메커니즘

컨슈머가 브로커로부터 파티션 세그먼트 데이터를 읽어 네트워크로 전송받을 때 일어나는 커널 내부 동작을 비교해 봅니다:

```
[전통적 방식: read() + write() / 4회 컨텍스트 스위치, 4회 데이터 복사]
User Space    :               ┌──────────────────┐
                              │  JVM Heap Buffer │
                              └─▲──────────────┬─┘
                 CPU Copy #1    │              │  CPU Copy #2
────────────────────────────────┼──────────────┼─────────────────
Kernel Space  :   ┌─────────────┴──┐        ┌──▼─────────────┐
                  │ OS Page Cache  │        │ Socket Buffer  │
                  └─▲──────────────┘        └──┬─────────────┘
      DMA Copy #1   │               DMA Copy #2│
────────────────────┼──────────────────────────┼─────────────────
Hardware      : ┌───┴────┐                 ┌───▼────┐
                │  Disk  │                 │  NIC   │
                └────────┘                 └────────┘
```

1. **전통적 방식 (`read` + `write`)**:
   - `read()` 호출 시 User $\rightarrow$ Kernel 컨텍스트 스위치 (1)
   - 디스크에서 OS 페이지 캐시로 DMA 복사 (1)
   - 페이지 캐시에서 JVM 힙 메모리로 **CPU 메모리 복사(`memcpy`)** (2)
   - `read()` 완료 후 Kernel $\rightarrow$ User 컨텍스트 스위치 (2)
   - `write()` 호출 시 User $\rightarrow$ Kernel 컨텍스트 스위치 (3)
   - JVM 힙에서 커널 소켓 버퍼(`sk_buff`)로 **CPU 메모리 복사(`memcpy`)** (3)
   - 소켓 버퍼에서 NIC 버퍼로 DMA 복사 (4)
   - `write()` 완료 후 Kernel $\rightarrow$ User 컨텍스트 스위치 (4)
   - **총계**: **4번의 컨텍스트 스위치, 2번의 CPU 메모리 복사, 2번의 DMA 복사**.
   - $100\,\text{Gbps}$ 전송 시 CPU는 오직 `memcpy` 루프를 도느라 100% sys/usr 상태로 포화되어, 실제 처리량이 $12\,\text{Gbps}$에 갇힙니다.

```
[리눅스 Zero-Copy: sendfile(2) / 2회 컨텍스트 스위치, 2회 DMA 복사, 0 CPU Copy]
User Space    :               (데이터가 유저 공간을 전혀 거치지 않음!)
─────────────────────────────────────────────────────────────────
Kernel Space  :   ┌────────────────┐ (주소 포인터만 전달) ┌────────────────┐
                  │ OS Page Cache  ├──────────────────────►│ Socket Buffer  │
                  └─▲──────────────┘                       └──┬─────────────┘
      DMA Copy #1   │                            DMA Copy #2  │ (Scatter-Gather)
────────────────────┼─────────────────────────────────────────┼───
Hardware      : ┌───┴────┐                                ┌───▼────┐
                │  Disk  │                                │  NIC   │
                └────────┘                                └────────┘
```

2. **리눅스 Zero-Copy (`sendfile(2)` 및 Java `transferTo`)**:
   - 자바의 `FileChannel.transferTo(position, count, targetChannel)`는 리눅스의 `sendfile(2)` 시스템 콜로 직결됩니다.
   - 데이터는 JVM 유저 공간으로 전혀 올라오지 않습니다.
   - 커널은 소켓 버퍼(`sk_buff`)에 데이터 본문 대신 **페이지 캐시의 메모리 주소와 길이(Descriptor)**만 기록합니다.
   - 네트워크 카드(NIC)는 **Scatter-Gather DMA** 기능을 활용하여 OS 페이지 캐시 메모리를 직접 읽어 패킷을 조립하고 유선으로 전송합니다.
   - **총계**: **2번의 컨텍스트 스위치, 0번의 CPU 메모리 복사, 2번의 DMA 복사**.
   - CPU 사용률이 $98\%$에서 $5\%$ 미만으로 급감하며, $100\,\text{Gbps}$ 라인레이트를 완벽히 포화시킵니다.

## 3. 지연 컨슈머(Lagging Consumer)와 페이지 캐시 스래싱 (Page Cache Thrashing)

Zero-Copy를 사용하는 최적화된 브로커에서도, 수일 전 데이터나 수십 GB의 과거 데이터를 읽어 들이는 **지연 컨슈머(Lagging / Cold Consumer)**가 등장하면 파괴적인 연쇄 장애가 일어납니다:

```
[정상 상태: 핫 캐시]
Page Cache (64GB) : [파티션 0 최신][파티션 1 최신] ... [파티션 N 최신] (Hit Rate: 99%)
실시간 컨슈머     : 디스크 접근 0회, 100% 메모리 스트리밍 (지연시간: 0.1ms)

           │
           ▼ (지연 컨슈머가 128GB의 과거 데이터 일괄 조회 개시)
           │

[재앙 상태: 페이지 캐시 스래싱]
1. 커널은 과거 콜드 데이터를 읽기 위해 디스크 I/O를 수행하고 페이지 캐시 LRU에 적재.
2. 콜드 데이터(128GB)가 캐시 용량(64GB)을 초과하므로, 실시간 컨슈머가 읽고 있던
   핫 파티션 헤드 페이지들을 전부 강제 방출(Eviction)!
3. 결과: 실시간 컨슈머마저 캐시 미스(Cache Miss) 발생!
   ==> 실시간 컨슈머와 지연 컨슈머가 디스크 헤드 I/O 큐에서 동시 경합!
   ==> 디스크 읽기 큐가 폭발하고 I/O 지연시간이 0.1ms -> 48ms로 400배 폭등!
   ==> 프로듀서의 쓰기 요청 또한 I/O 병목으로 지연되며 카프카 클러스터 전체 마비!
```

## 4. 캐시 스래싱 방어 기법: `posix_fadvise(2)`와 캐시 격리

이 참사를 방지하기 위해 고성능 브로커는 과거 콜드 세그먼트를 읽을 때 리눅스 커널의 **`posix_fadvise(2)`** API를 호출합니다:

```c
#include <fcntl.h>

// 콜드 데이터를 sendfile로 전송한 직후 호출:
// "이 페이지들은 일회성 배치 읽기이므로 다시 참조하지 않는다. 즉시 캐시에서 버려라!"
posix_fadvise(fd, offset, length, POSIX_FADV_DONTNEED);
```

- **`POSIX_FADV_DONTNEED` 효과**:
  - 커널은 해당 파일 세그먼트를 디스크에서 읽어 소켓으로 보낸 직후, **페이지 캐시의 활성(Active) LRU 리스트에 잔류시키지 않고 즉시 페이지 프레임을 해제(Drop)**합니다.
  - 따라서 128GB의 대규모 콜드 데이터가 쏟아져 들어오더라도, 실시간 컨슈머들이 점유하고 있는 64GB의 핫 파티션 캐시는 **단 1바이트도 오염되거나 방출되지 않고 $99.5\%$ 적중률을 철통 방어**합니다.
  - 결과적으로 실시간 트래픽은 메모리 버스에서 초저지연($0.14\,\text{ms}$)으로, 콜드 트래픽은 NVMe 디스크 대역폭에서 격리되어 동시에 최고 속도로 흐르는 **이중 경로(Dual-Path) 스트리밍**이 완성됩니다.

## 5. 프로덕션 카프카 브로커 커널 튜닝 권장 파라미터

| 파라미터 | 권장 설정값 | 엔지니어링 근거 |
| :--- | :--- | :--- |
| `vm.swappiness` | `1` | 스왑 사용을 극도로 억제하여 페이지 캐시가 불필요하게 디스크로 스왑 아웃되는 사태 방지 |
| `vm.dirty_background_ratio` | `5` | 백그라운드 pdflush/kswapd가 조기에 더티 페이지를 디스크로 비동기 플러시하여 버스트 방어 |
| `vm.dirty_ratio` | `10` ~ `20` | 사용자 스레드가 동기식 I/O 스톨(Direct Writeback)에 빠지지 않도록 상한선 설정 |
| `SO_SNDBUF` / `SO_RCVBUF` | 커널 자동 튜닝 (`wmem_max` $16\,\text{MB}$) | 100GbE 네트워크에서 BDP(Bandwidth-Delay Product)를 완전히 채우도록 보장 |
| `transferTo` 활성화 | `true` (기본값) | Java NIO `transferTo()`를 통해 `sendfile(2)` 제로카피 무조건 활성화 |
