# 009. 캐시의 배신과 메모리 누수: LRU 캐시의 마법

* **난이도**: Lv.2 (실무 필수 / 고성능 시스템 설계)
* **카테고리**: 자료구조, LRU 캐시, 해시 맵 + 이중 연결 리스트, 메모리 관리, 시간 복잡도 O(1)
* **시간 제한**: 1.0초
* **메모리 제한**: 256 MB
* **핵심 CS 이론**: [theory.md 읽으러 가기](theory.md)

---

## 📖 실무 버그 시나리오

AI 플랫폼 백엔드 개발자 성민이는 비싼 GPU LLM 추론 비용과 데이터베이스 쿼리를 절감하기 위해 "질의응답(Q&A) 캐싱 모듈"을 개발했습니다.
성민이는 AI 코딩 툴에게 다음과 같이 요청했습니다:

> *"동일한 질문이 들어오면 DB나 LLM을 거치지 않고 메모리에서 즉시 응답하도록 파이썬 딕셔너리로 캐시를 만들어 줘."*

AI는 너무나 간결한 5줄짜리 캐시 코드를 짜주었습니다:

```python
# AI가 작성해 준 코드 (무한 증식 캐시)
cache = {}

def get_answer(query_id):
    if query_id not in cache:
        cache[query_id] = fetch_from_llm(query_id)  # 무한정 메모리에 저장!
    return cache[query_id]
```

성민이는 개발 환경에서 테스트했습니다. 두 번째 조회부터는 **0.0001초** 만에 빛의 속도로 캐시가 적중(Cache Hit)했습니다! 성민이는 기뻐하며 프로덕션에 배포했습니다.

하지만 서비스가 3일 동안 계속 가동되자 **기괴한 일이 벌어졌습니다**:

1. 수십만 명의 사용자가 제각각 고유한 UUID와 일회성 검색어를 입력하면서, `cache` 딕셔너리의 크기가 끝없이 불어났습니다.
2. 3일 전 딱 한 번 조회되고 다시는 쓰이지 않는 쓰레기 데이터들이 RAM을 꽉 채웠습니다(**메모리 누수, Memory Leak**).
3. 서버의 RAM 사용량이 8GB, 16GB를 넘어서더니, 결국 리눅스 운영체제의 저승사자인 **OOM Killer (Out of Memory Killer)**가 사전 경고도 없이 메인 백엔드 프로세스를 강제 사살(`SIGKILL`)해 버렸습니다!

성민이가 AI에게 해결책을 묻자, AI는 "용량이 차면 리스트에서 가장 오래된 것을 지우라"며 `list.pop(0)`을 쓰는 $O(N)$짜리 느려터진 코드를 내놓았습니다.

성민이의 캐시는 왜 서버를 죽였을까요?

AI는 딕셔너리의 편리함만 알았을 뿐, **"컴퓨터 메모리는 유한하며, 가장 오랫동안 안 쓴 데이터를 $O(1)$로 잘라내는 LRU(Least Recently Used) 축출 알고리즘"**을 전혀 고려하지 않았던 것입니다.

## 🎯 문제 설명

용량이 $C$개로 고정된 **LRU (Least Recently Used) 캐시**를 구현하세요.
캐시는 최대 $C$개의 `(key, value)` 쌍을 보관할 수 있으며, 다음 두 가지 명령어를 지원해야 합니다:

1. **`PUT key value`**:
   * 캐시에 `(key, value)`를 저장합니다.
   * 이미 캐시에 `key`가 존재한다면, 값을 새로운 `value`로 갱신하고 해당 키를 **가장 최근에 사용된(Most Recently Used)** 상태로 업데이트합니다.
   * 새로운 `key`이고 현재 캐시에 저장된 키의 개수가 용량 $C$에 도달했다면, **가장 오랫동안 참조되지 않은(Least Recently Used) 키를 캐시에서 영구히 삭제(Evict)**한 후 새로운 키-값을 삽입합니다.
2. **`GET key`**:
   * 캐시에서 `key`에 해당하는 `value`를 조회합니다.
   * `key`가 캐시에 존재한다면, 해당 `value`를 출력하고 해당 키를 **가장 최근에 사용된(Most Recently Used)** 상태로 업데이트합니다.
   * `key`가 캐시에 존재하지 않는다면(Cache Miss), `-1`을 출력합니다.

### ⚠️ 주의 사항
* 총 쿼리 수 $Q$는 최대 $100,000$건이며, 캐시 용량 $C$는 최대 $10,000$입니다.
* 일반 리스트(`list`)나 순차 탐색을 사용하여 LRU 순서를 관리하면 $O(Q \times C) \approx 10억\text{ 번 연산}$으로 **100% 시간 초과(TLE)** 판정을 받게 됩니다.
* 반드시 **해시 맵(Hash Map)과 이중 연결 리스트(Doubly Linked List)** 또는 언어 내장 최적화 자료구조(`collections.OrderedDict`)를 활용하여 **`GET`과 `PUT` 연산 모두 평균 $O(1)$**으로 처리해야 합니다. ([theory.md](theory.md) 참고)

## 📥 입력 형식 (Input)

* **첫째 줄**: 캐시의 최대 용량 $C$와 쿼리의 개수 $Q$가 공백으로 구분되어 주어집니다. ($1 \le C \le 10,000$, $1 \le Q \le 100,000$)
* **둘째 줄부터 $Q$개의 줄**: 각 줄에 명령어 `PUT key value` 또는 `GET key`가 주어집니다.
  * $1 \le key, value \le 1,000,000,000$ (정수)

---

## 📤 출력 형식 (Output)

* `GET` 명령어가 주어질 때마다 한 줄에 하나씩 조회된 결과값을 출력합니다.

---

## 💡 예제 1

### 입력
```text
2 6
PUT 1 10
PUT 2 20
GET 1
PUT 3 30
GET 2
GET 3
```

### 출력
```text
10
-1
30
```

### 힌트
* 용량 $C = 2$
* `PUT 1 10` $\rightarrow$ 캐시: `{1: 10}`
* `PUT 2 20` $\rightarrow$ 캐시: `{1: 10, 2: 20}` (최근: 2, 가장 오래됨: 1)
* `GET 1` $\rightarrow$ 값 `10` 반환. 1번이 조회되었으므로 1번이 가장 최근으로 승격! (최근: 1, 가장 오래됨: 2)
* `PUT 3 30` $\rightarrow$ 캐시 용량 초과! 가장 오래된 **2번 키가 축출(Evict)**됨. 캐시: `{1: 10, 3: 30}` (최근: 3, 가장 오래됨: 1)
* `GET 2` $\rightarrow$ 2번은 방금 축출되었으므로 캐시 미스! `-1` 반환
* `GET 3` $\rightarrow$ 값 `30` 반환

## 💡 예제 2 (기존 키 갱신)

### 입력
```text
2 5
PUT 1 100
PUT 2 200
PUT 1 150
PUT 3 300
GET 2
```

### 출력
```text
-1
```

### 힌트
* `PUT 1 150`을 실행할 때 1번의 값이 갱신되면서 동시에 1번이 가장 최근 사용으로 업데이트됩니다.
* 따라서 `PUT 3 300`을 넣을 때 가장 오래된 2번 키가 축출되어, `GET 2`는 `-1`이 됩니다.

---

## 🔍 채점 엣지케이스 안내
1. **$Q = 100,000, C = 10,000$ 대규모 쿼리**: $O(1)$ LRU가 아니면 100% 타임아웃
2. 캐시 용량 $C = 1$ 인 단일 슬롯 캐시
3. 동일한 키에 대해 반복적인 `PUT` 및 갱신
4. 존재하지 않는 키에 대한 대량의 `GET` 요청 (캐시 미스 연속)
