## 📖 실무 버그 시나리오

스타트업의 이커머스 백엔드 개발자 유진이는 정산 시스템에서 "주문별 총 결제 금액 계산" API를 개발했습니다.
유진이는 AI 코딩 툴에게 다음과 같이 프롬프트를 작성했습니다:

> *"주문(Order) 목록을 순회하면서, 각 주문에 딸린 주문상품(OrderItem)들의 가격과 수량을 곱해 주문별 총 결제 금액을 계산해 줘."*

AI는 다음과 같은 지극히 평범한 ORM 코드를 작성해 주었습니다:

```python
# AI가 작성해 준 코드 (치명적인 N+1 쿼리)
def calculate_order_totals(orders):
    results = []
    # 1. 주문 N건을 순회 (O(N))
    for order in orders:
        # 2. 루프 내부에서 주문상품 테이블을 매번 조건 검색 (N번 쿼리 발생!)
        # items = OrderItem.objects.filter(order_id=order.id)
        # 또는 items_db 전체에서 order_id가 일치하는 것을 매번 선형 탐색!
        total = 0
        for item in all_items:
            if item.order_id == order.id:
                total += item.price * item.quantity
        results.append((order.id, total))
    return results
```

개발 데이터베이스에서 테스트용 주문 20건을 넣고 실행했을 땐 **0.01초** 만에 완벽한 결과가 나왔습니다.
유진이는 아무런 의심 없이 프로덕션 서버에 배포했습니다.

월말 대규모 정산일, 한 달 동안 쌓인 주문 10만 건($N=100,000$)과 주문상품 10만 건($M=100,000$)이 유입되었습니다.
그리고 시스템은 **그대로 폭발했습니다**:

1. 데이터베이스 커넥션 풀(Connection Pool)이 순식간에 고갈되었습니다.
2. DB 서버의 CPU는 100%를 찍었고, 다른 모든 고객의 결제와 장바구니 API까지 모조리 504 Gateway Timeout으로 마비되었습니다.
3. 메모리에는 10만 개 주문과 10만 개 상품 객체가 한꺼번에 리스트로 적재되며 **OOM (Out of Memory)으로 웹 서버 프로세스가 강제 사살(Killed)**되었습니다!

분명 $N$과 $M$은 10만 개뿐이었는데, 왜 데이터베이스와 서버가 통째로 뻗어버렸을까요?

AI는 비즈니스 로직을 코드로 옮겨주었지만, **데이터베이스의 관계형 모델(RDBMS)과 조인(JOIN), 그리고 루프 안에서 매번 하위 데이터를 조회하는 'N+1 문제'의 파멸적인 시간 복잡도 $O(N \times M)$**를 전혀 고려하지 않았던 것입니다.

## 🎯 문제 설명

전자상거래 시스템의 $N$개의 주문(Order) 목록과 $M$개의 주문상품(OrderItem) 목록이 주어집니다.
각 주문상품은 속해있는 주문 번호 `order_id`, 단가 `price`, 구매 수량 `quantity`를 가집니다.

주어진 $N$개의 주문 순서대로, 각 주문의 **`order_id`와 해당 주문의 총 결제 금액(`total_amount`)**을 한 줄씩 공백으로 구분하여 출력하세요.

$$\text{주문 } i\text{의 총 결제 금액} = \sum (\text{price} \times \text{quantity})$$

### ⚠️ 주의 사항
* $N \le 100,000$, $M \le 100,000$ 입니다.
* 각 주문마다 주문상품 목록 전체를 일일이 훑는 $O(N \times M)$ 탐색을 수행하면 **100억 번의 연산으로 100% 시간 초과(TLE)** 판정을 받게 됩니다.
* 특정 주문에 연계된 주문상품이 단 하나도 없다면 총 결제 금액은 **0**으로 출력해야 합니다.
* 반드시 **해시 맵(Hash Map) 그룹핑 집계 또는 조인(JOIN) 원리를 활용하여 시간 복잡도 $O(N + M)$ 이내**로 해결해야 합니다. ([theory.md](theory.md) 참고)

---

## 📥 입력 형식 (Input)

* **첫째 줄**: 주문 건수 $N$과 주문상품 건수 $M$이 공백으로 구분되어 주어집니다. ($1 \le N, M \le 100,000$)
* **둘째 줄**: $N$개의 고유한 주문 번호 `order_id`가 공백으로 구분되어 주어집니다. ($1 \le \text{order\_id} \le 1,000,000,000$)
* **셋째 줄부터 $M$개의 줄**: 각 줄에 주문상품의 정보인 `order_id`, `price`, `quantity`가 공백으로 구분되어 주어집니다.
  * $1 \le \text{price} \le 1,000,000$ (정수)
  * $1 \le \text{quantity} \le 1,000$ (정수)
  * 하나의 주문에 여러 개의 주문상품이 속할 수 있습니다.
  * (어떤 주문상품의 `order_id`는 둘째 줄의 주문 목록에 존재하지 않는 취소된 주문일 수 있으며, 이 경우 무시합니다)

---

## 📤 출력 형식 (Output)

* 둘째 줄에 주어진 $N$개의 주문 순서대로, 각 주문의 `order_id`와 계산된 총 결제 금액을 공백으로 구분하여 총 $N$줄에 걸쳐 출력합니다.

---

## 💡 예제 1

### 입력
```text
3 4
101 102 103
101 1500 2
102 3000 1
101 2000 3
102 500 4
```

### 출력
```text
101 9000
102 5000
103 0
```

### 힌트
* 주문 101번: $(1500 \times 2) + (2000 \times 3) = 3000 + 6000 = 9000$ 원
* 주문 102번: $(3000 \times 1) + (500 \times 4) = 3000 + 2000 = 5000$ 원
* 주문 103번: 연계된 상품이 없으므로 0원
* 입력받은 주문 순서(101, 102, 103)대로 정확히 출력되었습니다.

* 60번 주문은 상품이 없으므로 0원입니다.

## 🔍 채점 엣지케이스 안내
1. **$N = 100,000, M = 100,000$ 대규모 데이터셋**: $O(N \times M)$ 루프 작성 시 100% 타임아웃
2. 모든 상품이 단 하나의 주문에 몰려 있는 경우 (1개 주문에 10만 개 상품)
3. $N$개의 주문에 연계된 상품이 전혀 없는 경우 (전원 0원 출력)
4. 주문 번호가 정수 최대 범위($10^9$)에 가깝게 흩어져 있어 배열 인덱스로 접근할 수 없고 반드시 해시 맵을 써야 하는 경우
