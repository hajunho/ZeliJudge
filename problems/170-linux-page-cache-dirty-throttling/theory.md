# Linux 페이지 캐시 더티 스로틀링(Dirty Throttling)과 `vm.dirty_ratio` vs 바이트 단위 튜닝 & `sync_file_range`

## 1. 개요: 리눅스 가상 메모리와 페이지 캐시(Page Cache)의 명암

리눅스 커널(Linux Kernel)은 스토리지 I/O 성능을 극대화하기 위해 여유 RAM을 파일 시스템의 읽기/쓰기 캐시로 활용하는 **페이지 캐시(Page Cache)**를 운용합니다.

애플리케이션이 `write(2)` 시스템 콜을 호출할 때, 커널은 데이터를 물리 디스크에 즉시 쓰지 않고 RAM 상의 페이지 캐시에만 복사한 뒤 즉각 반환(`return 0`)합니다. 이로 인해 `write()` 레이턴시는 물리 I/O 지연(수 밀리초)이 아닌 RAM 메모리 복사 지연(수십 마이크로초) 수준으로 초고속 처리됩니다.

이렇게 메모리에는 기록되었으나 아직 물리 디스크 블록으로 동기화되지 않은 페이지를 **더티 페이지(Dirty Pages)**라고 부릅니다.

```
[애플리케이션 (write)] ---> [RAM: 페이지 캐시 (더티 페이지 축적)] --(비동기 백그라운드 배출)--> [물리 디스크]
       |                                  ^                                                    ^
       |                                  | (메모리 축적 속도)                                  | (디스크 쓰기 대역폭)
       +==================================+====================================================+
```

## 2. 참사의 발단: `vm.dirty_ratio`와 15초 D-State 정지의 악몽

### 2.1 커널 더티 페이지 제어 임계치
리눅스 커널(`mm/page-writeback.c`)은 더티 페이지 축적을 제어하기 위해 2단계 임계치(`sysctl`)를 제공합니다:
1. **`vm.dirty_background_ratio` (기본값: 10%)**:
   - 전체 시스템 메모리의 10% 이상 더티 페이지가 쌓이면, 커널 백그라운드 플러시 스레드(`kworker/flush`)가 깨어나 디스크로 비동기 쓰기(`writeback`)를 시작합니다.
   - 이때 애플리케이션의 `write()` 호출은 전혀 블로킹되지 않고 정상 동작합니다.
2. **`vm.dirty_ratio` (기본값: 20%)**:
   - 더티 페이지 축적 속도가 물리 디스크 쓰기 대역폭을 초과하여 계속 차오르다 20% 상한선에 도달하면, 커널은 비상사태로 판단합니다.
   - **커널은 `write()`를 호출한 애플리케이션 스레드 자신을 강제로 동기식 플러싱 작업에 투입(`balance_dirty_pages_ratelimited()`)**합니다!

### 2.2 대용량 메모리 서버에서의 백분율(Ratio) 함정
과거 서버 RAM이 512MB~1GB이던 시절에는 20%가 고작 100MB~200MB에 불과했으므로 수백 밀리초 만에 디스크로 플러시할 수 있었습니다.
**하지만 64GB, 128GB, 256GB 이상의 고사양 엔터프라이즈 서버에서는 이 비율이 끔찍한 재앙이 됩니다!**

$$\text{128 GB RAM} \times 20\% = \mathbf{25.6 \text{ GB 더티 메모리!}}$$

1. 카프카(Kafka) 브로커, 엘라스틱서치(Elasticsearch), 또는 DB 백업 배치가 초당 수백 메가바이트의 쓰기를 쏟아붓습니다.
2. 25.6GB의 거대한 더티 페이지가 순식간에 페이지 캐시에 가득 찹니다.
3. 임계치를 초과하는 순간, 커널은 `balance_dirty_pages()`를 호출하여 **쓰기 작업을 수행하던 모든 유저 스레드를 `TASK_UNINTERRUPTIBLE` (D-state) 상태로 재워버립니다.**
4. SATA SSD나 클라우드 볼륨의 지속 쓰기 속도가 200 MB/s라면:
   $$\text{플러시 소요 시간} = \frac{25,600 \text{ MB}}{200 \text{ MB/s}} = \mathbf{128 \text{초!}}$$
5. 애플리케이션의 `write()` 시스템 콜이 커널 내부에서 **2분 이상 얼어붙는 초유의 참사**가 터집니다.
6. 쿠버네티스는 파드가 죽었다고 판단해 Liveness Probe 실패로 파드를 강제 재시작하고, 다른 노드로 장애가 연쇄 전파(Cascading Failure)됩니다.

## 3. 참사 2: 나이브 `fsync()` 절벽

버퍼링 I/O를 사용하는 애플리케이션이 주기적으로 데이터 지속성을 보장하기 위해 `fsync()` 또는 `fdatasync()`를 호출할 때도 동일한 참사가 발생합니다:
- 애플리케이션이 2GB 분량의 데이터를 빠르게 `write()`한 후 안심하고 `fsync(fd)`를 호출합니다.
- `fsync()`는 해당 파일에 속한 모든 더티 페이지가 물리 디스크 플래터/NAND에 안전하게 기록될 때까지 **절대로 반환하지 않습니다.**
- $2,000\text{MB} / 100\text{MB/s} = 20$초 동안 애플리케이션 스레드는 멈춰 서게 되며, P99.9 레이턴시가 수직 상승합니다.

## 4. 구원: 3대 커널 튜닝 및 아키텍처 해결책

### 4.1 바이트 단위 절대값 튜닝 (`vm.dirty_bytes`)
메모리 용량에 비례하여 기하급수적으로 커지는 백분율(`ratio`) 대신, 디스크 처리량에 맞춘 **절대 바이트 한도(`bytes`)**를 설정합니다:
```bash
# sysctl -w
vm.dirty_background_bytes = 134217728   # 128 MB (초기 백그라운드 배출 유도)
vm.dirty_bytes = 268435456              # 256 MB (최대 스로틀링 임계치)
```
- 서버 메모리가 512GB이더라도 더티 페이지는 최대 256MB까지만 차오릅니다.
- 200 MB/s 디스크 기준, 최악의 스로틀링이 발생해도 대기 시간은 **단 1.28초**로 엄격히 통제됩니다!

### 4.2 선제적 스트리밍 동기화 (`sync_file_range` / Write-Behind)
록스디비(RocksDB), 카프카, 포스트그레스큐엘(PostgreSQL) 등 고성능 스토리지 엔진은 리눅스 전용 시스템 콜인 **`sync_file_range(2)`**를 사용하여 백그라운드에서 데이터를 조금씩 디스크로 밀어냅니다.
- 데이터 64MB를 쓸 때마다 비동기 플러시 요청:
  `sync_file_range(fd, offset, 64MB, SYNC_FILE_RANGE_WRITE)`
- 이전 청크의 기록 완료 대기:
  `sync_file_range(fd, prev_offset, 64MB, SYNC_FILE_RANGE_WAIT_BEFORE | SYNC_FILE_RANGE_WRITE | SYNC_FILE_RANGE_WAIT_AFTER)`
- 페이지 캐시에 대용량 더티 페이지가 쌓이는 것을 원천 차단하므로, 추후 `fsync()`가 호출되어도 이미 데이터가 대부분 플러시되어 있어 **수 밀리초 만에 즉각 반환**됩니다!

### 4.3 Direct I/O (`O_DIRECT`)
MySQL InnoDB(`innodb_flush_method=O_DIRECT`)나 ScyllaDB 등은 OS 페이지 캐시를 완전히 우회하고 유저 버퍼에서 물리 디스크로 직접 DMA 전송을 수행합니다.
- 페이지 캐시 오버헤드 0%, 커널 D-state 스톨 0건.
- 레이턴시가 전적으로 물리 디스크의 균일한 성능에 수렴하여 예측 가능성이 극대화됩니다.

## 5. 핵심 요약 비교

| 기법 | 페이지 캐시 사용 | 스로틀링 위험성 | `fsync()` 지연 | 적합한 워크로드 |
| :--- | :--- | :--- | :--- | :--- |
| **기본 버퍼링 (`vm.dirty_ratio`)** | 최대 20% (수십 GB) | **매우 높음 (수십 초 D-State 정지)** | 최대 수십 초 동결 | 일반 데스크톱, 소형 배치 |
| **바이트 튜닝 (`vm.dirty_bytes`)** | 128MB~512MB 제한 | **낮음 (최대 1~2초 이내 통제)** | 1~2초 이내 | 일반 고사양 백엔드 서버 |
| **선제적 `sync_file_range`** | 청크 단위 순환 | **거의 없음 (지속적 유출)** | 수 밀리초 | Kafka, RocksDB, LSM 엔진 |
| **Direct I/O (`O_DIRECT`)** | 0 MB (완전 우회) | **없음 (물리 디스크 대역폭 직결)** | 즉시 반환 | MySQL InnoDB, DBMS WAL |
