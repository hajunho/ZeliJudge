# [배경 이론] 카프카 메시지 1개 재시도했을 뿐인데 왜 뒤의 100만 개가 멈춰요?!: HOL 블로킹과 논블로킹 재시도 큐 (Kafka Non-Blocking Retry & DLT)

## 1. 현실 비유: 고속도로 톨게이트 1차로와 고장 난 트럭

1차로 단일 차선(카프카 파티션, Partition)으로만 통과해야 하는 고속도로 톨게이트를 상상해 보세요.

- **차량 1번 (주문 #100)**: 결제 카드 단말기 오류(일시적 외부 API 장애)로 결제가 승인되지 않습니다.
- **차량 2번~1000번 (주문 #101~#1000)**: 카드를 정상적으로 손에 쥐고 있는 수많은 정상 고객들입니다.

### 🛑 전통적인 블로킹 재시도 (Naive In-place Retry)의 비극
톨게이트 수납원(컨슈머)이 1번 트럭을 세워두고 말합니다:  
*"손님, 카드 오류네요. 5초 뒤에 다시 긁어보고, 또 안 되면 30초 뒤에 다시 긁어봅시다."*

- 1번 차량이 톨게이트를 통과(`commitOffset`)하지 못하고 1차로를 가로막고 서 있는 동안:
- **뒤에 서 있는 2번~1000번 정상 차량 전체가 단 1미터도 전진하지 못하고 꼼짝없이 갇혀버립니다(Head-of-Line Blocking)!**
- 심지어 재시도 시간이 길어져 5분(`max.poll.interval.ms`)을 초과하면, 브로커가 컨슈머가 죽은 줄 알고 쫓아내어 전사 **컨슈머 리밸런스 폭풍(Rebalance Storm)**까지 터집니다.

## 2. 우버(Uber)와 스프링이 제시한 구원 투수: 논블로킹 재시도 토픽 (Non-Blocking Retry Topics)

우버(Uber) 엔지니어링 팀은 이 끔찍한 HOL 블로킹을 해결하기 위해 **"신속 갓길 이동(Off-ramp)"** 아키텍처를 고안했습니다 (Spring Kafka의 `@RetryableTopic` 표준).

```
[메인 토픽: orders]
  Order #1 (실패) ──► 오프셋 즉시 커밋! 갓길(Retry-1)로 이동!
  Order #2 (정상) ──► 0초 만에 즉시 정상 처리! ✅
  Order #3 (정상) ──► 0초 만에 즉시 정상 처리! ✅
       │
       ▼ (실패 메시지만 별도 지연 토픽으로 격리)
[재시도 1차 토픽: orders-retry-1] (5초 지연 대기 후 재시도)
       │  (또 실패하면?)
       ▼
[재시도 2차 토픽: orders-retry-2] (30초 지연 대기 후 재시도)
       │  (최종 실패 시)
       ▼
[사장 메시지 토픽: orders-dlt] (Dead Letter Topic, 운영자 알림 및 보관)
```

### 핵심 동작 원리
1. **메인 토픽의 논블로킹 커밋**:
   - 메인 토픽에서 주문 #1이 일시적 장애(외부 PG사 순단 등)로 실패하면, 그 자리에서 `Thread.sleep()`으로 버티지 않습니다.
   - 즉시 1차 재시도 토픽(`orders-retry-1`)으로 메시지를 발행하고, **메인 토픽의 오프셋을 즉시 커밋(Commit)**합니다.
   - 따라서 뒤따라오던 수만 개의 정상 주문(#2, #3, ...)은 **단 1ms의 지체도 없이 즉시 처리**됩니다.
2. **다단계 지연 재시도 토픽 (Tiered Delay Topics)**:
   - `orders-retry-1` 토픽을 구독하는 전용 컨슈머는 메시지의 재시도 예약 시각(`execute_at = 발행시각 + 5초`)이 될 때까지 대기했다가 재시도합니다.
   - 여기서 성공하면 정상 종료되고, 또 실패하면 2차 토픽(`orders-retry-2`, 30초 지연)으로 이관됩니다.
3. **독약 메시지 격리 (Dead Letter Topic, DLT)**:
   - 모든 재시도 횟수를 소진한 불량 메시지는 최종적으로 DLT로 이동하여 안전하게 격리됩니다.
   - 시스템 전체의 처리량을 100% 유지하면서도 단 1건의 메시지 유실도 발생하지 않습니다.

## 3. 블로킹 vs 논블로킹 트레이드오프

| 비교 항목 | 전통적 블로킹 재시도 (In-place) | 논블로킹 다단계 재시도 (Uber/Spring) |
| :--- | :---: | :---: |
| **파티션 순서성 (Ordering)** | 100% 보장 (앞 메시지가 끝나야 뒤로 감) | 메인 정상 메시지가 먼저 처리됨 (비순차 허용) |
| **전체 파이프라인 처리량** | **1개 장애에 전체 멈춤 (HOL Blocking)** | **장애 메시지만 격리되어 처리량 100% 유지** |
| **리밸런스 폭풍 위험** | 재시도 대기로 `max.poll` 초과 빈번 | 오프셋 즉시 커밋으로 리밸런스 위험 0% |
| **추천 시나리오** | 계좌 잔액 변경 등 절대 순서가 필수적인 경우 | 결제/주문/알림 등 99.9% 대다수 엔터프라이즈 API |
