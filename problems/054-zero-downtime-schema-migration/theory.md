# #054 하위 호환성 없는 DB 마이그레이션과 Expand-and-Contract 패턴 완벽 가이드

---

## 1. 개요: "서버는 무중단 롤링 배포인데 왜 DB 때문에 500 에러가 터지나요?"

현대 클라우드 네이티브 환경(Kubernetes, AWS ECS)에서는 서비스를 중단하지 않고 새 버전을 배포하기 위해 **롤링 업데이트(Rolling Update)**를 사용합니다.  
서버 인스턴스를 하나씩 죽이고 새 버전을 띄우는 방식으로, 배포 중에도 사용자는 무중단 서비스를 누릴 수 있습니다.

하지만 **데이터베이스 스키마(컬럼명, 테이블 구조)를 변경해야 하는 순간**,  
수많은 초보 엔지니어와 AI 바이브 코더들이 엄청난 재앙을 겪습니다:

```text
1. 개발자가 컬럼명을 변경하는 Flyway/Liquibase DDL 마이그레이션 스크립트를 작성함.
   ALTER TABLE users RENAME COLUMN phone TO mobile_number;
2. 배포가 시작되자마자 DB에 DDL이 먼저 실행됨.
3. 롤링 배포가 진행되는 5분 동안, 아직 살아있는 구버전(v1) 서버 파드들이
   유저 요청을 받아서 'phone' 컬럼을 조회하려다 500 에러 폭발!
   "SQLException: Column 'phone' not found"
4. 전사 결제/로그인 기능이 마비되고 롤백을 시도하지만,
   이미 DB 컬럼이 바뀌어 있어 구버전으로의 롤백조차 불가능한 '외통수'에 빠짐!
```

왜 이런 일이 발생할까요?  
**서버 애플리케이션은 점진적으로 교체할 수 있지만, 데이터베이스는 단 하나의 공유 상태(Shared State)이기 때문**입니다.  
배포 과도기에는 반드시 **구버전 코드(v1)와 신버전 코드(v2)가 동일한 DB를 동시에 바라보고 읽고 쓰는 순간**이 존재합니다.

---

## 2. 해결책: Expand-and-Contract (확장 및 수축 / Parallel Change) 패턴

세계적인 소프트웨어 아키텍트 마틴 파울러(Martin Fowler)가 정립한 무중단 스키마 마이그레이션의 절대 원칙입니다.  
한 번에 바꾸려 하지 말고, **"확장(Expand) $\to$ 공존(Dual Write) $\to$ 백필(Backfill) $\to$ 수축(Contract)"**의 4단계를 거칩니다.

```text
[단계 1: Expand (확장)]
 DB에 신규 컬럼을 추가하되, 구버전 컬럼을 절대 지우지 않습니다.
   ALTER TABLE users ADD COLUMN country_code VARCHAR(10) NULL;
   ALTER TABLE users ADD COLUMN national_number VARCHAR(20) NULL;
 * 구버전(v1) 앱은 여전히 'phone' 컬럼만 쓰므로 아무 장애도 나지 않습니다.

[단계 2: Dual Write & Fallback Read (동시 쓰기)]
 신버전(v2) 앱을 배포합니다.
 - 쓰기: 'phone'과 '신규 컬럼' 양쪽에 동시에 기록합니다 (Dual Write).
 - 읽기: 신규 컬럼이 있으면 읽고, 없으면 구버전 'phone'에서 읽습니다 (Fallback Read).
 * v1 파드와 v2 파드가 동시에 살아있어도 양쪽 모두 100% 정상 작동합니다!

[단계 3: Backfill (과거 데이터 이관)]
 백그라운드 배치 작업으로 과거에 v1이 쌓아두었던 옛날 행들의
 'phone' 데이터를 파싱하여 신규 컬럼에 차곡차곡 채워 넣습니다.

[단계 4: Contract (수축)]
 모든 서버 파드가 v2로 교체 완료된 것을 확인한 후,
 최종적으로 구버전 컬럼을 안전하게 삭제(DROP)합니다.
   ALTER TABLE users DROP COLUMN phone;
```

---

## 3. Dual Write(동시 쓰기)와 Fallback Read(대체 읽기)의 중요성

Expand-and-Contract 패턴의 핵심 심장은 **신버전(v2) 애플리케이션의 데이터 접근 계층(DAO / Repository)**에 있습니다.

### 1) Dual Write (동시 쓰기)가 필요한 이유
롤링 배포 중에는 트래픽이 라운드로빈으로 분산되므로,  
- 사용자 A의 회원가입 요청이 $v2$ 파드로 들어가서 저장됨.
- 1초 뒤 사용자 A의 마이페이지 조회 요청이 **아직 교체되지 않은 $v1$ 파드**로 들어갈 수 있습니다!
- 만약 $v2$가 신규 컬럼에만 썼다면, $v1$은 구버전 컬럼이 비어있어 사용자 정보가 누락되는 치명적 버그가 발생합니다.
- 따라서 **$v2$ 파드는 구버전 컬럼과 신버전 컬럼 양쪽 모두에 데이터를 써주어야 합니다.**

### 2) Fallback Read (대체 읽기)가 필요한 이유
신버전 $v2$ 파드가 배포되었더라도, 과거 3년 동안 가입한 수백만 명의 유저는 신규 컬럼이 `NULL`입니다.  
배치 마이그레이션(Backfill)이 다 돌기 전까지, $v2$ 파드는 신규 컬럼이 비어있으면 구버전 컬럼에서 실시간으로 파싱해서 읽어오는 방어 로직을 갖추어야 합니다.

## 4. 실무 프로덕션 DDL 주의사항 (Online DDL & Large Tables)

컬럼을 추가(`ADD COLUMN`)하거나 삭제(`DROP COLUMN`)할 때도 데이터베이스 엔진 레벨의 락(Lock)을 주의해야 합니다.

1. **메타데이터 락(Metadata Lock, MDL)**:
   - 1억 건이 넘는 거대 테이블에 `ALTER TABLE`을 날리면, 트랜잭션이 끝날 때까지 테이블 전체에 배타적 락이 걸려 서비스 전체 쿼리가 타임아웃으로 줄줄이 폭사합니다.
2. **Instant DDL 활용 (MySQL 8.0+)**:
   - `ALGORITHM=INSTANT`: 컬럼을 맨 뒤에 추가할 때는 실제 데이터 행을 재작성하지 않고 메타데이터만 0.01초 만에 갱신합니다.
3. **대규모 마이그레이션 전문 도구**:
   - `gh-ost` (GitHub 오픈소스): 별도의 섀도우 테이블(Shadow Table)을 만들고 바이너리 로그(Binlog)를 추적하여 무중단 마이그레이션을 수행.
   - `pt-online-schema-change` (Percona 툴킷): 트리거(Trigger) 기반 온라인 스키마 변경.

## 5. 요약: 무중단 DB 변경 체크리스트

| 배포 단계 | 데이터베이스 스키마 상태 | 애플리케이션 버전 | 핵심 작업 |
| :--- | :--- | :--- | :--- |
| **Phase 1** | 기존 스키마 유지 | v1 (구버전) | 평시 운영 |
| **Phase 2 (Expand)** | 신규 컬럼 추가 (`NULL` 허용) | v1 $\to$ v2 롤링 배포 | v2에 **Dual Write & Fallback Read** 적용 |
| **Phase 3 (Backfill)** | 두 컬럼 공존 | v2 100% 가동 | 과거 데이터 비동기 일괄 마이그레이션 |
| **Phase 4 (Contract)** | 구버전 컬럼 삭제 (`DROP`) | v2 (정상 운영) | 완전한 신규 스키마 전환 완료 |
