# Apache Kafka 멱등성 프로듀서(Idempotent Producer)와 정확히 한 번(Exactly-Once Semantics, EOS) 처리 아키텍처

## 1. 개요: 분산 메시징의 성배, Exactly-Once

분산 메시징 시스템(Apache Kafka, RabbitMQ, Pulsar 등)에서 메시지 전달 보장(Delivery Semantics)은 3단계로 나뉩니다:

1. **최대 한 번 (At-Most-Once)**: 메시지가 유실될 수 있지만 중복되지는 않음 (Fire-and-Forget, 로그 수집).
2. **최소 한 번 (At-Least-Once)**: 메시지가 절대 유실되지 않지만, 네트워크 재시도로 인해 **중복 메시지(Duplicate Message)가 발생할 수 있음** (카프카의 기본 동작).
3. **정확히 한 번 (Exactly-Once Semantics, EOS)**: 네트워크가 끊기고 브로커나 프로듀서가 재시작되어도, **메시지가 유실되지 않고 단 한 번만 정확히 기록/처리됨** (결제, 계좌 이체, 재고 차감의 절대적 필수 요건).

컴퓨터 과학계에서는 분산 환경(두 장군 문제, FLP 불가능성)에서 네트워크 패킷 유실을 감안할 때 완벽한 Exactly-Once는 물리적으로 불가능하다고 여겨졌습니다.
그러나 2017년, Apache Kafka는 **KIP-98 (Exactly Once Delivery and Transactional Messaging)**을 통해 프로토콜 레벨에서 이를 우아하게 달성했습니다.

## 2. 참사의 근원: 네트워크 단절과 At-Least-Once 재시도 폭풍

### 2.1 카프카의 기본 전송 사이클과 ACK 유실

```
[프로듀서 (결제 모듈)]                                         [카프카 브로커 파티션]
         |                                                                |
         | --- 1. ProduceRequest (order_101 결제, 5만원) ---------------> | (디스크 커밋 완료! Offset 42)
         |                                                                |
         | <xx 2. ProduceResponse (ACK 성공) 유실! (네트워크 깜빡임) xxx |
         |                                                                |
  (타임아웃 발생!)                                                         |
  "어라? 브로커가 응답이 없네? 결제가 안 됐나 보다. 재시도하자!"             |
         |                                                                |
         | --- 3. ProduceRequest 재전송 (order_101 결제, 5만원) --------> | (디스크 중복 커밋! Offset 43)
         |                                                                |
         | <--- 4. ProduceResponse (ACK 성공) -------------------------- |
```

### 2.2 결과: 침묵의 중복 결제(Duplicate Payment) 재앙
1. 브로커는 첫 번째 요청을 받아 디스크에 정상적으로 기록했습니다.
2. 그러나 응답 패킷(ACK)이 돌아오던 중 네트워크가 0.1초 깜빡여 패킷이 유실되었습니다.
3. 데이터 유실을 막기 위해 프로듀서의 `retries` 옵션이 켜져 있으므로, 프로듀서는 동일한 메시지를 다시 전송했습니다.
4. **치명적 결함**: 나이브한 브로커는 이것이 재시도인지 새로운 결제인지 알 길이 없습니다.
5. 브로커는 파티션 로그의 다음 오프셋(Offset 43)에 동일한 결제 요청을 또다시 추가(`append`)합니다.
6. 다운스트림 컨슈머(PG 연동 서버)는 파티션에서 두 개의 결제 이벤트를 읽어 **고객의 신용카드에서 5만 원을 두 번 긁어버립니다!**

## 3. 구원: KIP-98 멱등성 프로듀서 (Idempotent Producer)

KIP-98은 브로커와 프로듀서 간의 상태 머신 추적을 통해, **네트워크 레벨에서 아무리 재전송이 일어나더라도 브로커 디스크에는 단 한 번만 원자적으로 기록되도록 보장**합니다.

### 3.1 3대 핵심 빌딩 블록

#### 1. PID (Producer ID)
- 프로듀서가 처음 부팅되어 브로커와 핸드셰이크할 때, 브로커의 트랜잭션 코디네이터가 프로듀서에게 고유한 64비트 정수 식별자(`PID`)를 발급합니다.
- 각 프로듀서는 고유한 자신만의 주민등록번호를 갖게 됩니다.

#### 2. 파티션별 Sequence Number (단조 증가 시퀀스 번호)
- 프로듀서는 각 토픽 파티션마다 0부터 시작하여 1씩 단조 증가하는 32비트 정수 `seq_num`을 관리합니다.
- 메시지를 보낼 때마다 `(PID, partition, seq_num)` 메타데이터가 패킷 헤더에 동봉됩니다:
  $$\text{Message 1} \to \text{Seq } 0, \quad \text{Message 2} \to \text{Seq } 1, \quad \text{Message 3} \to \text{Seq } 2 \dots$$

#### 3. 브로커의 5개 인플라이트 시퀀스 윈도우 (Deduplication Window)
- 브로커는 각 파티션 메모리에 `(PID, partition)`별로 최근 성공적으로 커밋된 마지막 시퀀스 번호(`last_seq`)를 보관합니다.
- 브로커가 시퀀스 번호 $S$를 수신했을 때의 엄격한 3대 판정 규칙:

```
                  [수신된 Sequence Number (S) 검사]
                                 |
           +---------------------+---------------------+
           |                                           |
    [S == last_seq + 1]                         [S <= last_seq]                         [S > last_seq + 1]
           |                                           |                                        |
           v                                           v                                        v
     [정상 순차 메시지]                           [중복 메시지 (ACK 유실 재시도)]          [메시지 유실 / 순서 역전]
  - 디스크에 정상 커밋                          - 디스크에 절대 쓰지 않음!                  - 즉시 에러 발생!
  - last_seq = S                               - 성공 ACK만 조용히 회신                    - OutOfOrderSequenceException
  - 클라이언트에 성공 회신                       (Silent Deduplication)                    - 갭(Gap) 발생 방지
```

1. **$S == \text{last\_seq} + 1$ (정상 수신)**:
   - 정확히 순서에 맞는 다음 메시지입니다. 파티션 로그에 추가하고 `last_seq`를 $S$로 갱신합니다.
2. **$S \le \text{last\_seq}$ (중복 재전송 감지)**:
   - 프로듀서가 ACK를 못 받아 재전송한 패킷입니다.
   - **디스크에 절대 다시 쓰지 않습니다!**
   - 대신 프로듀서가 재시도를 멈출 수 있도록 **가짜가 아닌 진짜 성공 ACK를 조용히 반환**합니다. (완벽한 중복 제거)
3. **$S > \text{last\_seq} + 1$ (시퀀스 갭 발생)**:
   - 중간 번호의 메시지가 네트워크에서 증발했거나 순서가 뒤집힌 상태입니다.
   - 브로커는 즉시 `OutOfOrderSequenceException`을 던져 데이터 누락을 원천 차단합니다.

## 4. 좀비 인스턴스 격리: Epoch & Zombie Fencing

쿠버네티스 환경에서 파드가 일시적인 네트워크 파티션이나 긴 Full GC STW(Stop-The-World)로 인해 죽은 것으로 오인되어 신규 파드가 기동된 경우:
- 구 파드(Zombie Instance)가 뒤늦게 깨어나 과거의 미전송 메시지를 브로커에 쏟아부을 위험이 있습니다.
- 카프카는 이를 막기 위해 `Epoch` 번호를 도입했습니다:
  - 신규 인스턴스가 기동되면 동일한 `transactional_id`에 대해 `Producer Epoch`를 1 증가시킵니다.
  - 브로커는 구 인스턴스가 보낸 낮은 Epoch의 요청을 즉시 **`ProducerFencedException`**으로 사살(Fence)하여 데이터 오염을 완벽하게 차단합니다.

## 5. 실무 권장 프로덕션 설정

카프카 3.0부터는 멱등성 프로듀서가 기본 활성화(`default: true`)되어 있으나, 엔터프라이즈 결제/금융 파이프라인에서는 반드시 다음 4대 설정을 명시적으로 고정해야 합니다:

```properties
# 1. 멱등성 프로듀서 활성화
enable.idempotence=true

# 2. 모든 ISR 레플리카의 디스크 동기화 대기
acks=all

# 3. 네트워크 일시 장애 시 무한 재시도 (멱등성이 중복을 100% 막아주므로 안전)
retries=2147483647

# 4. 순서 보장과 파이프라이닝 성능을 동시에 달성하는 황금 윈도우 (최대 5개까지 허용)
max.in.flight.requests.per.connection=5
```
