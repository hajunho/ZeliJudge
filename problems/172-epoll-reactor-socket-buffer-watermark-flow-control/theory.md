# Epoll Reactor 패턴 소켓 송신 버퍼(SO_SNDBUF), 논블로킹 write() EAGAIN과 고/저 워터마크(High/Low Watermark) 역압(Backpressure) 제어

## 1. 개요: 비동기 고성능 서버의 숨은 시한폭탄

Netty, Nginx, Envoy, Node.js, Rust Tokio, Go 네트워크 폴러 등 현대의 모든 고성능 네트워크 서버 및 리버스 프록시는 **이벤트 드리븐 Reactor 패턴**과 리눅스의 **논블로킹 소켓 (`O_NONBLOCK`) + `epoll(7)` 다중화**를 핵심 아키텍처로 사용합니다.

이를 통해 단 몇 개의 스레드만으로 수만, 수십만 개의 동시 TCP 연결(C10K, C100K)을 0에 수렴하는 컨텍스트 스위칭 비용으로 우아하게 처리할 수 있습니다.

그러나 실무에서 비동기 서버를 구축하고 프로덕션에 투입한 수많은 엔지니어들이 전혀 예상치 못한 기괴한 참사를 마주합니다:
> *"평소엔 메모리를 200MB도 안 쓰던 Netty/Node.js API 게이트웨이가, 모바일 앱 유저들이 대용량 파일이나 비디오를 다운로드하기 시작하자마자 메모리가 1GB, 4GB, 16GB까지 폭증하더니 커널 OOM-Killer에 의해 `Exit Code 137`로 강제 사살(SIGKILL)당했습니다!"*

분명 비동기 I/O로 CPU를 아끼고 스레드 풀도 작게 유지했는데, **도대체 수 기가바이트의 메모리는 어디서 폭발한 것일까요?**

## 2. 참사의 원인: 저속 클라이언트(Slow Consumer)와 무제한 유저 버퍼링

### 2.1 커널 소켓 송신 버퍼 (`SO_SNDBUF`)와 논블로킹 `write()`
TCP 소켓을 생성하면 리눅스 커널은 해당 연결을 위해 송신 버퍼(`SO_SNDBUF`, 보통 64KB ~ 256KB)를 할당합니다.
애플리케이션이 소켓에 `write(fd, data)` 또는 `send()`를 호출할 때, 데이터는 네트워크 카드로 즉시 나가는 것이 아니라 커널의 `SO_SNDBUF`에 복사됩니다.
커널 TCP 스택은 수신자(클라이언트)가 ACK를 회신할 때까지 이 버퍼에 데이터를 보관하며, ACK가 도착하면 버퍼 공간을 비웁니다.

- **블로킹 소켓**: `SO_SNDBUF`가 꽉 차면 `write()` 시스템 콜이 블로킹되어 스레드가 잠에 빠집니다.
- **논블로킹 소켓 (`O_NONBLOCK`)**: `SO_SNDBUF`가 가득 차면 커널은 즉시 `-1`을 반환하며 `errno`를 **`EAGAIN`** 또는 **`EWOULDBLOCK`**으로 설정합니다. "지금은 소켓 버퍼에 쓸 공간이 없으니 나중에 다시 시도하라"는 뜻입니다.

### 2.2 나이브(Naive) 비동기 서버의 치명적 설계 결함
고속 업스트림(빠른 사내 백엔드 서비스, Redis, 로컬 NVMe SSD 등)에서 초당 50MB/s로 대용량 응답 데이터를 읽어옵니다.
그런데 이 데이터를 받아가는 다운스트림 클라이언트는 지하철에서 3G/LTE를 쓰는 모바일 사용자이거나, 네트워크 대역폭이 100KB/s에 불과한 저속 클라이언트(Slow Client)입니다.

```
[초고속 업스트림] --(50 MB/s 읽기)--> [비동기 프록시 서버] --(100 KB/s 쓰기)--> [저속 모바일 클라이언트]
                                     |
                          [SO_SNDBUF 64KB 가득 참!]
                                     |
                          (write -> EAGAIN 발생!)
                                     v
                       [유저 스페이스 무제한 큐에 적재]
                       (1초 후: +50MB, 10초 후: +500MB, 1분 후: +3GB!)
                                     v
                         🚨 [OOM-KILLER 사망]
```

1. 프록시 서버가 업스트림 소켓에서 `EPOLLIN` 이벤트를 감지하고 데이터를 시원하게 읽어옵니다.
2. 클라이언트 소켓에 `write()`를 날리지만, `SO_SNDBUF`(64KB)는 0.01초 만에 가득 찹니다.
3. 커널은 `EAGAIN`을 뱉습니다.
4. **치명적 실수: 나이브한 비동기 서버는 쓰지 못한 데이터를 힙 메모리의 연결 리스트나 큐(`pending_buffer`)에 담아두고, 업스트림 소켓의 `EPOLLIN` 읽기 감시를 멈추지 않습니다!**
5. 업스트림은 계속해서 수십 MB의 데이터를 쏟아붓고, 서버는 이를 고스란히 유저 메모리에 차곡차곡 쌓아 올립니다.
6. 클라이언트 단 10명이 동시에 100MB 파일을 요청하면 1GB, 100명이 요청하면 10GB의 힙 메모리가 순식간에 고갈되어 시스템 전체가 동반 폭사합니다.

## 3. 구원: 고/저 워터마크(High/Low Watermark) 역압(Backpressure) 제어

Netty의 `WriteBufferWaterMark`, Nginx의 버퍼링 제어, Envoy의 버퍼 필터, Node.js Stream의 `pause()/resume()`은 모두 **고/저 워터마크(High/Low Watermark) 기반 역압(Backpressure)**으로 이 문제를 원천 차단합니다.

### 3.1 3단계 역압 라이프사이클

```
                     [유저 버퍼 크기 (pending_user_buffer)]
   512 KB ------------------------------------------------- [🚨 OOM 임계선]
                                  :
   128 KB -------+----------------+------------------------ [High Watermark]
                /                  \
               /                    \  (소켓 비우기 진행)
              /                      \
    64 KB ---+------------------------+-------------------- [Low Watermark]
            /                                          \
           /                                            \
     0 KB +----------------------------------------------+--
          [정상 스트리밍]   [백압 발동: 읽기 정지]   [백압 해제: 읽기 재개]
```

#### 1단계: High Watermark 도달 및 업스트림 인입 중단 (Pause)
- 유저 공간 대기 큐(`pending_user_buffer`)의 크기가 **`high_watermark` (예: 128KB)**를 초과하는 순간:
  1. 채널의 쓰기 가능 상태를 `isWritable = false`로 전환합니다.
  2. **핵심: 업스트림 소켓의 읽기 감시를 즉시 해제(`epoll_ctl(EPOLL_CTL_MOD, upstream_fd, 0)` 또는 `channel.config().setAutoRead(false)`)합니다!**
  3. 업스트림 데이터를 더 이상 `read()`하지 않으므로, 업스트림 커널의 수신 윈도우(rwnd)가 0으로 줄어들고 업스트림 프로듀서도 전송을 멈추게 됩니다. (End-to-End 종단간 역압 전파)

#### 2단계: `EPOLLOUT` 이벤트 감지와 비동기 소켓 배출 (Drain)
- 클라이언트 소켓의 `SO_SNDBUF`가 가득 차서 `EAGAIN`이 발생하면, 이벤트 루프는 클라이언트 소켓에 **`EPOLLOUT`** 감시를 등록합니다.
- 클라이언트가 ACK를 보내 커널 `SO_SNDBUF`에 여유 공간이 생기면, 커널이 `EPOLLOUT` 이벤트를 발생시켜 이벤트 루프를 깨웁니다.
- 이벤트 루프는 `pending_user_buffer`에서 데이터를 꺼내 `SO_SNDBUF`의 잔여 용량만큼 non-blocking `write()`를 수행합니다.

#### 3단계: Low Watermark 도달 및 업스트림 인입 재개 (Resume)
- `EPOLLOUT` 처리를 통해 유저 버퍼가 비워지며 **`low_watermark` (예: 64KB)** 미만으로 떨어지는 순간:
  1. 채널의 쓰기 가능 상태를 `isWritable = true`로 복구합니다.
  2. **업스트림 소켓의 `EPOLLIN` 감시를 다시 등록(`setAutoRead(true)`)하여 데이터 읽기를 재개합니다!**
  3. 멈춰 있던 데이터 파이프라인이 다시 매끄럽게 흐르기 시작합니다.

## 4. 왜 단일 워터마크가 아닌 High/Low 2중 워터마크(Hysteresis)인가?

만약 워터마크를 `128KB` 단 하나만 둔다면 무슨 일이 일어날까요?
- 버퍼가 `128KB + 1B`가 됨 $	o$ 업스트림 정지 (`setAutoRead(false)`)
- 소켓으로 1바이트 씀 $	o$ `128KB`가 됨 $	o$ 업스트림 재개 (`setAutoRead(true)`)
- 업스트림에서 1바이트 읽음 $	o$ `128KB + 1B`가 됨 $	o$ 업스트림 정지
- **초당 수만 번의 `epoll_ctl` 시스템 콜이 폭발하며 CPU가 100% 포화되는 스래싱(Thrashing / Churn) 현상이 발생합니다.**

공학에서는 이를 방지하기 위해 상한선(High Watermark)과 하한선(Low Watermark) 사이에 충분한 간격(Gap)을 두는 **히스테리시스(Hysteresis, 이력 현상)**를 적용합니다.
High(128KB)에서 멈추고, Low(64KB)까지 충분히 소켓이 비워질 때까지는 재개하지 않음으로써 시스템 콜 오버헤드를 극소화하고 고성능 스트리밍을 달성합니다.
