# 이론 정리: 리눅스 커널 페이지 캐시 쓰기백과 Dirty Throttling 아키텍처

## 1. 지연 쓰기(Delayed Write)와 메모리 압박

운영체제의 I/O 서브시스템에서 디스크(HDD/SSD)의 물리적 처리 속도는 DRAM에 비해 수백 배에서 수만 배 느립니다. 애플리케이션의 `write(2)` 호출마다 동기적으로 디스크 플러시(`O_SYNC`)를 수행하면 성능이 심각하게 저하됩니다.

따라서 리눅스는 **지연 쓰기(Delayed Writeback)** 전략을 채택합니다:
1. `write(2)`는 데이터를 커널의 페이지 캐시(Page Cache)에 복사하고 즉시 리턴합니다.
2. 수정된 페이지에는 `PG_dirty` 플래그가 설정됩니다.
3. 커널은 백그라운드에서 주기적으로 혹은 메모리가 일정 수준 이상 오염되었을 때 디스크로 페이지를 내보냅니다(Flush).

## 2. 2대 핵심 임계치와 `balance_dirty_pages()`

더티 페이지가 무제한으로 쌓이면 다음 문제가 발생합니다:
- 물리 RAM 고갈로 인한 시스템 프리징 및 OOM Killer 난동.
- 정전이나 커널 패닉 시 수 기가바이트의 미기록 데이터 영구 소실.

리눅스 커널(`mm/page-writeback.c`)은 이를 제어하기 위해 2개의 핵심 수위를 정의합니다:

```
[ 전체 RAM 공간 ]
┌────────────────────────────────────────────────────────┐
│ Clean Pages / Free Memory                              │
├──────────────────────────┬─────────────────────────────┤ ◄─── dirty_ratio (예: 40%)
│ Throttling Zone          │ 사용자 프로세스 동기 블로킹!   │      balance_dirty_pages() sleep
├──────────────────────────┴─────────────────────────────┤ ◄─── dirty_background_ratio (예: 20%)
│ Async Flushing Zone      │ 백그라운드 flusher 스레드 기동│      wb_workfn / bdi_writeback
├────────────────────────────────────────────────────────┤
│ Safe Dirty Pages         │ 정상 비동기 버퍼링           │
└────────────────────────────────────────────────────────┘
```

### 1) `dirty_background_ratio` (기본값 약 10%~20%)
- 백그라운드 플러셔 데몬(`bdi_writeback`)을 깨우는 임계치입니다.
- 이 수준에 도달하면 커널은 스토리지 컨트롤러에 비동기 I/O 요청을 제출합니다.
- 사용자 애플리케이션은 아무런 방해를 받지 않고 계속 쓰기를 수행할 수 있습니다.

### 2) `dirty_ratio` (기본값 약 20%~40%)
- 사용자 프로세스가 강제로 감속(Throttling)되는 안전 하드 리밋입니다.
- 더티 페이지 수가 이 임계치를 초과하면, `write(2)`를 호출한 프로세스는 `balance_dirty_pages()` 함수에 진입하여 직접 더티 페이지를 디스크로 내보내며 `io_schedule()`로 슬립 상태에 빠집니다.
- 이를 통해 쓰기 유입 속도가 물리 디스크의 실제 배출 속도 이하로 강제 동기화됩니다.

## 3. 주기적 노화(Aging) 메커니즘 (`dirty_expire_interval`)

더티 페이지의 양이 적어서 임계치를 넘지 않더라도, 오래된 데이터가 디스크에 반영되지 않고 메모리에만 남아있으면 데이터 유실 위험이 커집니다.
- 커널은 각 페이지가 더티화된 시점(`dirty_time`)을 기록합니다.
- `dirty_expire_interval`(기본값 30초 = 3000 centiseconds)이 경과한 페이지는 백그라운드 수위와 무관하게 플러셔 스레드의 최우선 플러시 대상으로 선정됩니다.

---

## 4. 고성능 분산 시스템 및 DB 튜닝에서의 실무적 의의

- **카프카(Kafka) / 락스DB(RocksDB)**:
  - 대량의 로그를 Append-Only로 쏟아붓는 워크로드에서 `dirty_ratio`가 너무 높으면 수 기가바이트의 더티 페이지가 쌓였다가 한꺼번에 플러시되면서 수 초간 시스템 전체 I/O가 동결되는 **Write Stall Spikes**가 발생합니다.
  - 실무 엔지니어는 `/proc/sys/vm/dirty_background_ratio`를 낮게(예: 5%) 설정하여 플러시를 조기에 부드럽게 분산시키고, `dirty_ratio`를 10% 수준으로 조여 거대한 I/O 스파이크를 방어합니다.
