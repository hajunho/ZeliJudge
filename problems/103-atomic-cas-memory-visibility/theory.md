# 103. 멀티스레드로 숫자 100만 번 더했을 뿐인데 왜 결과가 매번 다르고 줄어들어요?!: CPU 메모리 가시성(Visibility)과 volatile & 원자적 CAS(Compare-And-Swap)의 세계

---

## 1. 비극의 시작: 100만이 나와야 하는데 왜 73만이 나오죠?!

스타트업 백엔드 개발자 성진이는 대규모 트래픽이 몰리는 이벤트 페이지의 실시간 방문자 수 카운터를 구현했습니다:

```java
public class EventCounter {
    private int count = 0;

    public void click() {
        count++; // 방문자 1명 증가!
    }

    public int getCount() {
        return count;
    }
}
```

테스트를 위해 10개의 스레드가 각각 10만 번씩 총 **100만 번** `click()`을 호출하도록 멀티스레드 부하 테스트를 돌렸습니다:
- 실행 1회차: `732,814`
- 실행 2회차: `654,192`
- 실행 3회차: `819,003`

**"100만 번 호출했는데 왜 30만 건 가까운 숫자가 흔적도 없이 사라진 거지?!"**

성진이는 구글링을 통해 *"멀티스레드 환경에서는 CPU 캐시 때문에 값이 동기화되지 않을 수 있으니 `volatile`을 붙여야 한다"*는 글을 보고 즉시 코드를 수정했습니다:

```java
private volatile int count = 0; // 메인 메모리에서 직접 읽고 쓴다!
```

그리고 다시 100만 번 테스트를 돌렸습니다.  
결과는... **`741,920`**!  
`volatile`을 붙였는데도 여전히 25만 건이 넘는 숫자가 증발해 버렸습니다! 도대체 왜 이런 일이 벌어진 걸까요?

## 2. 현실 비유: 교실 칠판과 두 학생의 분필 비극

교실 칠판(메인 메모리)에 현재 방문자 수 **`100`**이 분필로 적혀 있습니다:
1. **학생 A와 학생 B(스레드 2개)**가 동시에 교실 문을 열고 들어왔습니다.
2. **학생 A (LOAD)**: 칠판의 `100`을 보고 머릿속에 기억했습니다.
3. **학생 B (LOAD & STORE)**:
   - 칠판의 `100`을 보고 머릿속에서 $100 + 1 = 101$을 계산했습니다.
   - 학생 B가 재빨리 지우개로 칠판의 `100`을 지우고 **`101`**을 적었습니다!
4. **학생 A의 뒤늦은 쓰기 (STORE - 참사의 순간!)**:
   - 학생 A는 칠판이 이미 101로 바뀌었다는 사실을 모른 채, **자신이 아까 머릿속에 기억해둔 100에 1을 더한 `101`**을 칠판에 그대로 덮어써 버렸습니다!
5. **결과**:
   - 두 학생이 방문했으므로 숫자는 `102`가 되어야 마땅하지만, 칠판에는 여전히 `101`이 적혀 있습니다.
   - 학생 B의 증가분 1건이 완전히 증발한 것입니다(**갱신 분실, Lost Update**)!

## 3. 컴퓨터 과학 / 하드웨어 동시성 이론

### 1) `count++`의 물리적 실체: Read-Modify-Write (3단계 연산)
프로그래밍 언어에서는 `count++`가 단 1줄이지만, CPU 하드웨어/어셈블리 레벨에서는 **서로 분리된 3개의 기계어 명령어**로 실행됩니다:

```text
1. LOAD  EAX, [count]   ; 메인 메모리/캐시에서 레지스터 EAX로 값 읽기 (Read)
2. ADD   EAX, 1         ; CPU ALU에서 레지스터 값 1 증가 (Modify)
3. STORE [count], EAX   ; 계산된 레지스터 값을 다시 메모리에 쓰기 (Write)
```

두 스레드가 동시에 실행되면 명령어들이 뒤섞여(Interleaving), 서로의 연산 결과를 덮어쓰며 숫자가 누락됩니다.

### 2) `volatile`의 오해: 가시성(Visibility) vs 원자성(Atomicity)
- **가시성 (Visibility)**:  
  CPU 코어의 L1/L2 로컬 캐시를 우회하여, 한 스레드가 변경한 값을 다른 스레드가 **즉각적으로 메인 메모리에서 볼 수 있게** 보장합니다.
- **원자성 (Atomicity)**:  
  여러 단계로 구성된 연산이 도중에 다른 스레드에 의해 끼어들거나 쪼개지지 않고 **단일한 한 덩어리로 실행됨**을 보장합니다.
- **결론**:  
  `volatile`은 **가시성만 보장할 뿐 원자성을 전혀 보장하지 못합니다!**  
  `count`가 `volatile`이더라도 3단계(Load-Modify-Store) 연산 도중에 컨텍스트 스위칭이 일어나면 갱신 분실(Lost Update)은 100% 동일하게 발생합니다.

### 3) 해결책: 하드웨어 CAS (Compare-And-Swap)
뮤텍스(Mutex)나 `synchronized`를 쓰면 락을 걸고 푸는 과정에서 OS 컨텍스트 스위칭과 스레드 블로킹 오버헤드가 발생하여 성능이 떨어집니다.  
현대 CPU(x86, ARM)는 하드웨어 레벨에서 단 한 클럭에 실행되는 **CAS(Compare-And-Swap) 명령어(`LOCK CMPXCHG`)**를 제공합니다:

$$	ext{CAS}(V, E, N)$$
- $V$: 조작할 메모리 위치
- $E$: 내가 읽었던 예상 값(Expected Value)
- $N$: 새로 쓰려는 값(New Value)
- **원리**: $V$의 현재 값이 $E$와 일치할 때만 원자적으로 $N$으로 교체하고 `true`를 반환합니다. 중간에 다른 스레드가 먼저 값을 바꿔버려 불일치하면 아무것도 변경하지 않고 `false`를 반환합니다!

```java
// Java AtomicInteger의 무잠금(Lock-Free) 루프
public int incrementAndGet() {
    while (true) {
        int current = get();       // 1. 현재 값 읽기 (Expected)
        int next = current + 1;    // 2. 새 값 계산 (New)
        if (compareAndSet(current, next)) { // 3. CAS 시도!
            return next; // 성공 시 반환!
        }
        // 실패 시: 누군가 먼저 바꿨으므로 다시 루프를 돌며 최신 값으로 재시도!
    }
}
```

## 4. 실무 권장 아키텍처 및 교훈

1. **`volatile`은 단일 읽기/쓰기에만 사용하라**:
   - `volatile`은 플래그 변수(예: `while(!stopped)`)처럼 이전 상태에 의존하지 않는 단순 대입 연산에만 유효합니다.
2. **복합 연산(Read-Modify-Write)은 원자적 타입 사용**:
   - 카운터나 시퀀스 번호는 반드시 `AtomicInteger`, `AtomicLong`, `LongAdder`(고동시성 분산 카운터)를 사용해야 합니다.
3. **CAS의 스핀(Spin) 비용 인지**:
   - 수백 개의 스레드가 동일한 카운터에 동시에 CAS를 날리면 충돌로 인해 CPU 사용률이 치솟을 수 있습니다. 경합이 극도로 심할 때는 Java 8의 `LongAdder`처럼 코어별로 카운터를 분산시키는 셀(Cell) 기반 아키텍처를 도입해야 합니다.
