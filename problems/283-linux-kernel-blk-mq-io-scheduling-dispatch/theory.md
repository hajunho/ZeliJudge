# 이론적 배경: 리눅스 커널 blk-mq 멀티큐 아키텍처와 I/O 스케줄링

## 1. 단일 큐 블록 계층(Single Queue)의 한계와 병목

전통적인 유닉스 및 초기 리눅스 커널의 블록 계층(`request_queue_t`)은 단일 하드 디스크(HDD)를 위해 설계되었습니다.
HDD의 물리적 특성상 회전하는 플래터와 헤드의 탐색 시간(Seek Time)을 최소화하기 위해, 커널은 모든 CPU 코어에서 들어오는 bio 요청들을 단 하나의 큐에 넣고 **엘리베이터 알고리즘(Elevator Algorithm: Linus Elevator, AS, CFQ, Deadline)**을 사용하여 섹터 번호순으로 정렬했습니다.

이 구조는 다음 한계를 가집니다:
1. **전역 락 경합 (`queue_lock`)**:
   모든 CPU 코어가 I/O를 요청하거나 완료 인터럽트를 처리할 때 동일한 전역 스핀락을 획득해야 했습니다. CPU 코어가 8개, 16개, 64개로 증가할수록 락을 대기하는 스핀 시간이 실제 I/O 처리 시간보다 훨씬 길어졌습니다.
2. **하드웨어 인터페이스의 발전과의 불일치**:
   SATA/AHCI는 최대 32개의 명령 큐(NCQ)를 지원했지만 단일 컨트롤러 큐였습니다. 반면 현대의 **NVMe(Non-Volatile Memory Express)** 사양은 최대 64,000개의 하드웨어 큐와 큐당 64,000개의 엔트리를 지원합니다. 단일 큐 블록 계층은 이 엄청난 병렬성을 전혀 활용할 수 없었습니다.

## 2. blk-mq의 2단계 큐 (Two-Level Queue) 아키텍처

옌스 악스보(Jens Axboe)가 설계한 `blk-mq`는 블록 I/O 경로를 **소프트웨어 스테이징 계층**과 **하드웨어 디스패치 계층**으로 완전히 분리했습니다.

```
+-------------------------------------------------------------+
|                     User Space / POSIX I/O                  |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
| Task Plug (blk_plug) - Per-Thread Batching & Sequential Merge|
+-------------------------------------------------------------+
         |                    |                    |
+-----------------+  +-----------------+  +-----------------+
|  CPU 0 ctx      |  |  CPU 1 ctx      |  |  CPU 2/3 ctx    |
| (Software Queue)|  | (Software Queue)|  | (Software Queue)|
+-----------------+  +-----------------+  +-----------------+
         \                   /                     |
    (cpu_to_hw_map: CPU 0,1 -> hctx 0)    (CPU 2,3 -> hctx 1)
           \               /                       |
      +------------------------+      +------------------------+
      |  Hardware Queue 0      |      |  Hardware Queue 1      |
      | (blk_mq_hw_ctx / Tags) |      | (blk_mq_hw_ctx / Tags) |
      +------------------------+      +------------------------+
                  |                                |
      +------------------------+      +------------------------+
      | NVMe Submission Q 0    |      | NVMe Submission Q 1    |
      +------------------------+      +------------------------+
```

### (1) 소프트웨어 큐 (`struct blk_mq_ctx`)
- CPU 코어당 1개씩 존재하며 NUMA 노드 로컬 메모리에 할당됩니다.
- I/O 요청 생성 시 해당 CPU의 로컬 락(또는 lock-free 연산)만 필요하므로 다른 CPU의 간섭 없이 $O(1)$에 가까운 속도로 큐잉됩니다.

### (2) 하드웨어 디스패치 큐 (`struct blk_mq_hw_ctx`)
- 실제 하드웨어 컨트롤러가 제공하는 Submission Queue의 개수에 맞춰 생성됩니다.
- 토폴로지 매핑 계층(`blk_mq_queue_map`)을 통해 여러 CPU(예: CPU 0과 CPU 1)가 동일한 하드웨어 큐(`hctx 0`)를 공유할 수 있습니다.

## 3. 태스크 플러깅(`blk_plug`)과 Bio 병합 알고리즘

단일 I/O 시스템 콜마다 블록 계층 큐에 진입하는 오버헤드를 줄이기 위해, 커널 태스크는 `blk_start_plug(&plug)`를 호출하여 로컬 플러그 리스트를 생성합니다.

### 병합 조건 (Merge Conditions)
연속적인 디스크 블록을 읽고 쓰는 요청이 들어오면 기존 `struct request`에 새 `struct bio`를 합칩니다:
1. **Back Merge**:
   - `req.end_sector == bio.sector`
   - 기존 요청의 끝에 새 bio를 연결합니다.
2. **Front Merge**:
   - `bio.sector + bio.nr_sectors == req.start_sector`
   - 기존 요청의 앞에 새 bio를 연결하고 `req.start_sector`를 갱신합니다.
3. **최대 크기 제한 (`max_sectors`)**:
   - 병합 후 총 섹터 수가 드라이버의 최대 제한(`max_sectors`)을 초과하면 병합을 거절하고 새로운 요청으로 독립시킵니다.

플러그 작업이 끝나고 `blk_finish_plug(&plug)`가 호출되면 모인 요청들이 소프트웨어 큐로 일괄 플러시됩니다.

## 4. 하드웨어 태그 할당과 `sbitmap` (Scalable Bitmap)

각 하드웨어 큐는 처리할 수 있는 최대 동시 요청 수인 **`queue_depth`**를 갖습니다.
- 커널은 각 요청을 추적하기 위해 고유한 **하드웨어 태그(Hardware Tag)**를 부여합니다.
- `blk-mq`는 태그 할당의 병목을 없애기 위해 **`sbitmap` (Scalable Bitmap)** 자료구조를 사용합니다. 비트맵을 여러 개의 64비트 단어(word)로 분할하고 단어별 락을 두어 코어 간 캐시 라인 경합을 방지합니다.
- 모든 태그가 사용 중일 때 추가 요청이 발생하면 디바이스는 `BLK_STS_RESOURCE`를 반환하고, 해당 요청은 하드웨어 디스패치 리스트(`dispatch_list`)에서 대기 상태로 남습니다.
- 디바이스 인터럽트에 의해 요청이 완료(`blk_mq_complete_request`)되면 해당 태그가 `sbitmap`에 반환되어 대기 중이던 요청이 즉시 디스패치될 수 있습니다.

## 5. I/O 스케줄러: `NONE` vs `MQ-DEADLINE`

1. **`NONE` (Noop / Passthrough)**:
   - 초고속 NVMe SSD에서 CPU 사이클을 아끼기 위해 I/O 스케줄러를 완전히 비활성화하고 순수 FIFO로 하드웨어에 직결합니다.
2. **`MQ-DEADLINE`**:
   - 지연 시간에 민감한 읽기 작업이 대규모 쓰기 버스트에 의해 기아(Starvation) 상태에 빠지는 것을 방지합니다.
   - 각 요청에 만료 시간(`deadline`)을 부여합니다:
     - 읽기 만료 기한: 통상 $500\mu s$
     - 쓰기 만료 기한: 통상 $5000\mu s$ (5ms)
   - **디스패치 우선순위**:
     1. 만료 기한이 지난 요청(`deadline <= current_ts`)이 존재할 경우 가장 오래된 만료 요청부터 우선 디스패치.
     2. 만료 요청이 없을 경우 읽기 요청을 쓰기 요청보다 항상 우선 디스패치하며, 섹터 오름차순으로 정렬하여 디스크/플래시 친화적 I/O를 수행.

## 6. 알고리즘 시간 복잡도 분석

- **Bio 제출 및 플러그 병합**: 플러그 내 요청 수 $K$에 대해 $O(K)$. 일반적으로 플러그 크기는 16 이하로 유지되므로 실질적 $O(1)$.
- **소프트웨어 큐 플러시**: $O(K)$.
- **하드웨어 태그 할당 (`sbitmap`)**: 최소 가용 태그 탐색 $O(1)$.
- **MQ-DEADLINE 디스패치 정렬**: 디스패치 대기열 크기 $R$에 대해 $O(R \log R)$.
- 전반적인 시뮬레이션 복잡도는 $O(M \cdot (K + R \log R))$로, 밀리초 단위로 수만 건의 I/O를 초고속 처리합니다.
