# [CS 백서 #087] 전원이 갑자기 꺼졌는데 결제 내역이 왜 살아있죠?!: 데이터베이스 Write-Ahead Logging (WAL)과 ARIES 장애 복구

> **"새벽에 데이터센터 누전 차단기가 내려가며 DB 서버 전원이 완전히 꺼졌습니다!"**  
> 다음 날 아침 전원을 다시 켜보니, 커밋 완료된 10만 건의 결제 내역은 1원도 유실되지 않았고, 정전 순간 처리 중이던 불완전한 결제는 귀신같이 자동 롤백되어 있었습니다.  
> 디스크 쓰기 속도가 초당 수십 MB에 불과한데, 어떻게 데이터베이스는 멈추지 않고 초당 수만 건의 트랜잭션을 처리하면서도 전원 차단에 100% 무결성을 보장할까요?  
> 그 비밀은 바로 컴퓨터 과학 역사상 가장 위대한 알고리즘 중 하나인 **Write-Ahead Logging (WAL)** 과 **ARIES 복구 알고리즘**에 있습니다!

---

## 1. 현실 세계 비유: 미슐랭 레스토랑 주방의 주문서와 두꺼운 양장본 장부

고급 레스토랑 주방을 상상해 봅시다.
- **두꺼운 양장본 장부 (디스크 데이터베이스 파일)**: 손님의 테이블 번호와 주문 현황이 정갈하게 정리된 두꺼운 장부입니다. 한 페이지를 찾아서 지우고 다시 쓰려면 1분이 걸립니다(**디스크 Random I/O**).
- **메모장 주문 꼬챙이 (WAL, Write-Ahead Log)**: 요리사 앞에 있는 꼬챙이에 주문 종이를 순서대로 꽂는 곳입니다. 0.001초 만에 종이를 꽂을 수 있습니다(**디스크 Sequential Append-Only I/O**).
- **요리사의 머릿속 (RAM 버퍼 풀)**: 현재 주방 냄비에서 볶고 있는 실시간 요리 상태입니다.

### 시나리오: 정전이 터졌다!
손님이 스테이크를 주문할 때마다 요리사가 두꺼운 양장본 장부를 일일이 펼쳐서 기록한다면 손님들은 1시간 동안 음식을 기다려야 합니다.
그래서 똑똑한 수석 셰프는 이렇게 규칙을 세웁니다:

> *"손님이 주문하거나 결제할 때, 두꺼운 장부는 일단 건드리지 마라! 대신 **주문 꼬챙이(WAL)에 시간 순서대로 영수증을 먼저 꽂아둬라(Write-Ahead)**. 장부에는 한가할 때 한꺼번에 몰아서 적자(Checkpoint)!"*

갑자기 식당 전체에 정전이 발생하여 주방 불이 꺼지고 요리사 머릿속(RAM)이 새하얗게 지워졌습니다:
1. **분석 (Analysis)**: 양초를 켜고 마지막으로 장부를 정리했던 시점부터 주문 꼬챙이를 훑습니다.
   - *"이 손님은 돈을 내고 나갔군(Winner), 저 손님은 고기 굽는 도중에 정전이 나서 도망갔군(Loser)!"*
2. **역사 반복 (Redo)**: 주문 꼬챙이에 적힌 순서대로 요리를 처음부터 끝까지 그대로 다시 만들어봅니다.
   - 정전 직전의 주방 상태를 완벽하게 재현합니다.
3. **취소 롤백 (Undo)**: 돈을 내지 않고 도망간 손님의 요리는 쓰레기통에 쏟아버리고 원래 재료 상태로 장부를 되돌립니다.

이 3단계를 거치자, 식당은 손해를 1원도 보지 않고 100% 정상 영업 상태로 복구됩니다!

## 2. 컴퓨터 과학 원리: 데이터베이스 버퍼 관리와 WAL의 필연성

### (1) 디스크 I/O의 딜레마: Steal vs No-Steal, Force vs No-Force
트랜잭션이 디스크에 데이터를 기록할 때 DBMS는 두 가지 정책적 고민을 합니다:

| 정책 | 개념 | 장단점 |
| :--- | :--- | :--- |
| **Force (강제)** | 트랜잭션이 커밋될 때마다 수정된 모든 데이터 페이지를 즉시 디스크에 쓴다. | 커밋 시점에 디스크 Random I/O가 폭증하여 **성능이 파멸적으로 느려짐**. |
| **No-Force (지연)** | 커밋되어도 수정된 페이지는 RAM(Buffer Pool)에만 두고 디스크엔 나중에 쓴다. | **초고속 성능**. 하지만 커밋 직후 정전되면 데이터가 날아갈 위험! |
| **Steal (허용)** | 아직 커밋되지 않은 트랜잭션의 더티 페이지라도 메모리가 모자라면 디스크에 덮어쓴다. | 메모리 관리 효율적. 하지만 정전 시 커밋 안 된 쓰레기 데이터가 디스크에 남음! |
| **No-Steal (금지)** | 커밋되기 전에는 절대 디스크의 원본 페이지를 덮어쓰지 못하게 잠근다. | 트랜잭션이 거대해지면 메모리 부족(OOM)으로 시스템 마비. |

> 현대의 모든 상용 RDBMS (MySQL InnoDB, PostgreSQL, Oracle, SQLite)는 **`Steal + No-Force`** 정책을 채택합니다.
> 즉, **"커밋되었다고 디스크에 즉시 쓰지 않으며(No-Force), 커밋되지 않은 데이터라도 필요하면 디스크에 미리 쓸 수 있다(Steal)"**는 극단적인 고성능 정책입니다.
> 
> 그렇다면 정전 시 커밋된 데이터 유실(No-Force의 위험)과 미커밋 데이터 오염(Steal의 위험)을 어떻게 완벽히 방어할까요?
> 그 해답이 바로 **WAL (Write-Ahead Logging)** 입니다!

### (2) WAL (Write-Ahead Logging)의 핵심 원칙

1. **로그 우선 기록 원칙 (Write-Ahead Rule)**:
   - 데이터베이스 버퍼 풀에 있는 더티 페이지를 디스크에 플러시하기 전에, **그 변경사항을 기술한 WAL 로그 레코드가 디스크에 먼저 영구 기록(`fsync`)되어야 한다.**
2. **커밋 시점의 WAL 플러시**:
   - `COMMIT` 명령이 떨어지면, 수백 MB짜리 데이터 테이블을 쓸 필요 없이, 오직 수십 바이트짜리 **`COMMIT LSN` 로그 레코드 하나만 디스크에 순차 쓰기(Append-Only Sequential I/O)** 합니다.
   - 순차 I/O는 무작위 I/O보다 수백 배 빠르므로, 트랜잭션은 수 밀리초 만에 성공적으로 커밋 완료를 반환할 수 있습니다!

### (3) ARIES 3단계 장애 복구 알고리즘 (C. Mohan, 1992)

IBM의 C. Mohan 박사가 고안한 **ARIES (Algorithms for Recovery and Isolation Exploiting Semantics)** 는 관계형 데이터베이스 복구의 표준 교과서입니다.
시스템 크래시 후 부팅 시 3단계를 순차적으로 실행합니다:

```text
[Crash 시점]
          Checkpoint LSN: 10
                 │
                 ▼
WAL: ───[10: CP]───[11: START T1]───[12: UPDATE T1]───[13: COMMIT T1]───[14: START T2]───[15: UPDATE T2] ──► (CRASH!)
                                                                                                               ▲
                                                                                                               │
1. Analysis Phase (순방향 스캔) ───────────────────────────────────────────────────────────────────────────────┘
   - 마지막 Checkpoint(10)부터 끝까지 읽으며 T1은 Winner(커밋됨), T2는 Loser(미완료) 판정

2. Redo Phase (역사 반복, 순방향 재생) ───────────────────────────────────────────────────────────────────────►
   - 11번부터 15번까지의 모든 UPDATE를 차례대로 재실행! (크래시 순간의 정확한 상태 재현)

3. Undo Phase (역방향 롤백) ◄─────────────────────────────────────────────────────────────────────────────────
   - 15번부터 거꾸로 스캔하며 Loser인 T2의 UPDATE를 원래 값(Old Value)으로 역순 롤백!
```

1. **1단계: 분석 (Analysis Phase)**
   - 가장 최근의 **체크포인트(Checkpoint)** 지점부터 WAL의 끝(Crash 지점)까지 앞으로 스캔합니다.
   - 크래시 당시 커밋을 완료한 트랜잭션 집합(**Winners**)과 완료하지 못한 유령 트랜잭션 집합(**Losers**)을 분류합니다.
2. **2단계: 리두 (Redo Phase - "Repeating History")**
   - 체크포인트 이후의 모든 로그를 순방향으로 재생합니다.
   - 놀랍게도 **Loser 트랜잭션의 작업까지도 일단 그대로 다시 실행**합니다!
   - 이유: 크래시 순간의 데이터베이스 물리적 상태를 단 1비트의 오차도 없이 완벽하게 복원해야, 뒤이어 안전하게 롤백(Undo)할 수 있기 때문입니다.
3. **3단계: 언두 (Undo Phase - "Rolling Back Losers")**
   - WAL의 끝에서부터 거꾸로 역방향 스캔합니다.
   - 오직 **Loser 트랜잭션이 변경한 값들만 찾아 이전 값(Old Value)으로 원복**합니다.
   - 롤백이 끝나면 데이터베이스는 모든 유령 트랜잭션의 흔적이 완벽히 제거된, 무결한 ACID 상태로 돌아옵니다.

### (4) 체크포인트 (Checkpoint)가 필요한 이유

만약 체크포인트가 없다면 어떻게 될까요?
서버가 3년 동안 100억 개의 트랜잭션을 처리했다면, 정전 후 부팅할 때 3년 치 WAL 100억 건을 처음부터 다 읽느라 서버가 3일 동안 켜지지 않을 것입니다!
- **체크포인트(Checkpoint)** 는 주기적으로 버퍼 풀의 모든 더티 페이지를 실제 디스크 데이터 파일에 플러시하고, 현재 활성 트랜잭션 목록을 WAL에 기록합니다.
- 복구 시 엔진은 전체 로그가 아니라 **가장 최근의 체크포인트 지점까지만 거슬러 올라가면 되므로**, 복구 시간이 수 초 이내로 획기적으로 단축됩니다.
