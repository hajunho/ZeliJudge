# 리눅스 커널 AutoNUMA 스케줄러 이론 백서: NUMA Hinting Page Fault, 메모리 국지성(Locality), 그리고 task_numa_placement 무경합 태스크 스왑

## 1. NUMA 아키텍처와 인터커넥트 병목

현대 멀티소켓 x86_64 및 ARM64 서버(AMD EPYC, Intel Xeon, Ampere Altra)는 메모리 컨트롤러가 각 CPU 소켓에 직접 부착된 **NUMA (Non-Uniform Memory Access)** 구조를 가집니다:

```text
+------------------------+                        +------------------------+
|      NUMA Node 0       |                        |      NUMA Node 1       |
|  [Core 0 ... Core 63]  |                        | [Core 64 ... Core 127] |
|           │            |                        |           │            |
|     (Local 30ns)       |                        |     (Local 30ns)       |
|           ▼            |    UPI / Infinity      |           ▼            |
|   [Local DRAM Bank 0]  |◄══════════════════════►|   [Local DRAM Bank 1]  |
+------------------------+      Fabric (90ns)     +------------------------+
```

* **로컬 메모리 접근 (Local Access)**: 자기 노드의 메모리 컨트롤러를 직접 통과하므로 지연시간이 약 30ns에 불과합니다.
* **원격 메모리 접근 (Remote Access)**: 소켓 간 고속 직렬 버스(Intel UPI, AMD Infinity Fabric)를 건너야 하므로 지연시간이 3배(약 90~110ns)로 증가하며, 버스 대역폭이 포화되면 큐잉 지연이 200ns 이상으로 치솟습니다.

따라서 멀티소켓 시스템의 성능 최적화 핵심은 **"프로세스가 자주 참조하는 물리 메모리가 프로세스가 실행 중인 CPU 코어와 동일한 NUMA 노드에 머물도록 만드는 것(Memory Locality)"**입니다.

## 2. AutoNUMA의 동작 메커니즘 (`kernel/sched/fair.c`)

전통적인 정적 바인딩(`numactl`, `taskset`)은 워크로드가 동적으로 변하거나 멀티스레드 간 메모리를 공유할 때 한계가 분명합니다.
이에 안드레아 아르캉겔리(Andrea Arcangeli)와 잉고 몰나르(Ingo Molnar) 등이 주도하여 리눅스 커널 3.8에 도입한 **AutoNUMA**는 런타임에 동적으로 메모리 접근 패턴을 학습합니다:

```text
                ┌───────────────────────────────────┐
                │   task_numa_work() 백그라운드 스캔│
                └─────────────────┬─────────────────┘
                                  │
                                  ▼
                [PTE를 _PAGE_PROTNONE으로 인위적 무효화]
                                  │
                                  ▼
                ┌───────────────────────────────────┐
                │   태스크가 해당 페이지 접근 시도   │
                └─────────────────┬─────────────────┘
                                  │
                                  ▼
                [하드웨어 #PF 발생: task_numa_fault()]
                  ├── 1. 접근 CPU 노드와 페이지 물리 노드 기록
                  ├── 2. PTE 권한 정상 복원 (순간적 오버헤드 완충)
                  └── 3. 통계 갱신: task->numa_faults[node]++
                                  │
                  ┌───────────────┴───────────────┐
                  ▼                               ▼
       [페이지 마이그레이션]              [태스크 스왑 / 이주]
     migrate_misplaced_page()           task_numa_placement()
```

### 1) NUMA 힌팅 폴트 (Hinting Page Fault)
- 커널은 주기적으로 프로세스의 가상 주소 공간을 순회하며 페이지 테이블 엔트리(PTE)의 접근 권한을 일시적으로 제거(`_PAGE_PROTNONE`)합니다.
- 프로세스가 해당 페이지를 읽거나 쓸 때 가벼운 트랩(Minor Page Fault)이 발생하여 커널의 `task_numa_fault()` 루틴으로 진입합니다.
- 커널은 하드웨어 성능 카운터(PMC) 없이도 어떤 태스크가 어떤 노드의 메모리를 얼마나 집중적으로 사용하는지 완벽하게 프로파일링할 수 있습니다.

### 2) 페이지 마이그레이션 vs 태스크 마이그레이션
* **페이지 마이그레이션 (`migrate_misplaced_page`)**:
  - 소량의 핫 페이지가 잘못된 노드에 있을 때 적합.
  - 4KB 페이지를 물리적으로 복사해야 하므로 메모리 버스 대역폭을 소비.
* **태스크 마이그레이션 (`task_numa_placement`)**:
  - 프로세스의 메모리 워킹셋 전체(수백 MB~수십 GB)가 다른 노드에 있을 때, 방대한 페이지를 일일이 옮기는 대신 **스케줄러가 스레드 실행 코어만 옮기는 것(Task Migration)**이 수천 배 효율적입니다!

## 3. 무경합 양방향 태스크 스왑 (Two-Way Task Swap)

단순히 원격 접근이 많은 태스크를 다른 노드로 옮기면 심각한 **런큐 부하 불균형(Runqueue Load Imbalance)**이 발생합니다 (예: Node 0은 코어가 비고 Node 1은 과열됨).

이를 방지하기 위해 리눅스 커널의 `task_numa_compare()`는 **양방향 맞교환(Task Swap)**을 수행합니다:
* Task A (현재 Node 0)가 Node 1의 메모리를 갈망하고,
* Task B (현재 Node 1)가 Node 0의 메모리를 갈망한다면,
* 두 태스크의 코어 친화도를 서로 맞바꿔줍니다.
* **결과**:
  1. 각 노드의 실행 중인 태스크 수는 그대로 유지되므로 로드 밸런서가 개입할 필요가 전혀 없음(Zero Imbalance).
  2. 두 태스크 모두 즉시 로컬 메모리 접근(30ns)을 회복하여 시스템 전체 인터커넥트 트래픽이 즉시 소멸함!
