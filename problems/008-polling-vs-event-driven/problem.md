# 008. 끝없는 폴링과 소켓 고갈: Polling vs Event-Driven

* **시간 제한**: 1.0초
* **메모리 제한**: 256 MB
* **핵심 CS 이론**: [theory.md 읽으러 가기](theory.md)

## 📖 실무 버그 시나리오

음식 배달 플랫폼에서 실시간 배달 위치 추적 및 알림 기능을 개발하던 주니어 프론트/백엔드 개발자 민혁이는 고객 앱에서 라이더의 배달 상태(`COOKING` $\rightarrow$ `PICKED_UP` $\rightarrow$ `DELIVERED`)를 실시간으로 갱신하는 모듈을 맡았습니다.

"서버에 새로운 상태가 왔는지 어떻게 확인하지?" 고민하던 민혁이는 AI 코딩 툴에게 다음과 같이 요청했습니다:

> *"배달 상태가 `DELIVERED`(배달 완료)로 바뀔 때까지 실시간으로 감지하는 파이썬 코드를 짜줘."*

AI는 너무나 친절하게 **단기 폴링(Short Polling)** 코드를 작성해 주었습니다:

```python
# AI가 작성해 준 코드 (무한 폴링)
while True:
    status = request_server_status(order_id)  # 0.1초마다 계속 HTTP 요청!
    if status == "DELIVERED":
        show_notification("배달이 완료되었습니다!")
        break
    time.sleep(0.1)
```

개발 환경에서 휴대폰 1대로 테스트할 땐 0.1초마다 즉시 반응하며 아무런 문제가 없어 보였습니다.  
민혁이는 만족하며 프로덕션 앱에 기능을 배포했습니다.

불금 저녁 7시, **동시 배달 주문 10,000건($N=10,000$)**이 몰리자 **서버실에 비상이 걸렸습니다**:

1. 1만 대의 스마트폰이 0.1초마다 서버에 HTTP 요청을 때리니, **초당 100,000번의 HTTP 요청**이 폭격처럼 쏟아졌습니다!
2. 하지만 배달 상태는 20~30분 동안 거의 변하지 않았고, **서버가 보낸 응답의 99.99%는 "아직 배달 중입니다"라는 무의미한 빈 껍데기**였습니다.
3. TCP 핸드셰이크와 `TIME_WAIT` 소켓이 눈덩이처럼 불어나며 리눅스 서버의 소켓 포트(File Descriptor)가 완전 고갈되었습니다.
4. 웹 서버의 CPU는 빈 응답을 만들고 TCP 연결을 맺고 끊느라 100%로 타버렸고, 결국 전사 서버가 다운되었습니다.

당황한 민혁이가 AI에게 묻자, AI는 "로드 밸런서 뒤에 서버 인스턴스를 10대로 늘리세요"라는 월 수천만 원짜리 비용 폭탄 답변만 내놓았습니다.

AI는 문법대로 코드를 짜주었지만, 컴퓨터 네트워크와 운영체제의 가장 거대한 패러다임 전환인 **"바쁜 대기(Busy Waiting / Polling)의 재앙"**과 **"이벤트 기반 푸시(Event-Driven Push / epoll)"**의 본질을 전혀 이해하지 못했던 것입니다.

## 🎯 문제 설명

타임라인 상에서 발생하는 $M$개의 상태 변경 이벤트와 한 명의 관찰자(Client)가 주어집니다.
초기 시각 $t=0$에 공유 시스템의 상태 값은 $V_0$입니다.
이후 시각 $t$마다 상태 값이 $new\_value$로 변경되는 이벤트들이 발생합니다.

관찰자는 관찰 시작 시각 $T_{start}$부터 시스템 상태가 목표 값인 $TARGET$으로 변경되는 순간을 감지하고자 합니다.

동일한 상태 변경 시퀀스에 대해 **[방식 A: 주기적 폴링(Polling)]**과 **[방식 B: 이벤트 기반 푸시(Event-Driven)]** 두 가지 모델을 시뮬레이션하여 비교하세요.

---

### 방식 A: 주기적 폴링 (Short Polling)
* 관찰자는 주기 $P$ 간격으로 서버에 직접 조회 쿼리를 전송합니다:
  $$\text{조회 시각: } t = T_{start}, T_{start} + P, T_{start} + 2P, \dots$$
* 각 조회 시점의 서버 상태 값을 확인하여, 그 값이 $TARGET$과 일치하면 **즉시 감지 성공 판정을 내리고 폴링을 종료**합니다.
* 만약 동일 시각 $t$에 상태 변경 이벤트와 폴링 조회가 겹친다면, **상태 변경이 먼저 서버에 반영된 후** 폴링 조회가 값을 읽습니다.
* 관찰 시각은 $T_{max}$를 초과할 수 없습니다. 시각 $T_{max}$ 시점(포함)까지 조회를 수행했음에도 목표 값을 감지하지 못하면 조회를 중단하고 감지 실패(-1)로 처리합니다.
* **기록**: **총 전송한 폴링 요청 횟수**, **목표 값 감지 시각** (실패 시 -1)

---

### 방식 B: 이벤트 기반 푸시 (Event-Driven / Pub-Sub)
* 관찰자는 서버의 이벤트 채널을 구독(Subscribe)하고 대기합니다. (클라이언트가 쿼리를 날리지 않습니다)
* $T_{start}$ 이후(포함) 발생하는 상태 변경 이벤트 중, 시각 $T_{max}$ 이하(포함)에 발생하는 이벤트만 실시간으로 구독자에게 전송(Push)됩니다.
* 서버에서 상태가 $TARGET$으로 변경되는 이벤트가 푸시되는 바로 그 순간, 관찰자는 **지연 시간 0초 만에 즉시 감지 성공**하고 연결을 종료합니다.
* 시각 $T_{max}$까지 목표 값으로 바뀌는 이벤트가 발생하지 않으면 감지 실패(-1)로 처리합니다.
* **기록**: **총 수신한 푸시 이벤트 횟수**, **목표 값 감지 시각** (실패 시 -1)

---

## 📥 입력 형식 (Input)

* **첫째 줄**: $V_0$, $TARGET$, $T_{start}$, $T_{max}$, $P$ 가 공백으로 구분되어 주어집니다.
  * $0 \le V_0, TARGET \le 1,000,000,000$ (정수, $V_0 \ne TARGET$)
  * $0 \le T_{start} \le T_{max} \le 1,000,000,000$ (정수)
  * $1 \le P \le 1,000,000$ (정수, 폴링 주기)
* **둘째 줄**: 상태 변경 이벤트의 총 개수 $M$ ($1 \le M \le 100,000$)
* **셋째 줄부터 $M$개의 줄**: 각 줄에 이벤트 발생 시각 $time$과 변경된 새로운 값 $new\_value$가 공백으로 구분되어 주어집니다.
  * $0 \le time \le 1,000,000,000$ (정수, 시각 오름차순으로 주어짐)
  * $0 \le new\_value \le 1,000,000,000$ (정수)

---

## 📤 출력 형식 (Output)

* **첫째 줄**: [방식 A: 폴링]의 **총 폴링 요청 횟수**와 **감지 성공 시각**을 공백으로 구분하여 출력합니다. (감지 실패 시 시각은 -1)
* **둘째 줄**: [방식 B: 이벤트 푸시]의 **총 전송된 푸시 이벤트 횟수**와 **감지 성공 시각**을 공백으로 구분하여 출력합니다. (감지 실패 시 시각은 -1)

## 💡 예제 1

### 입력
```text
0 100 0 100 10
3
25 50
45 100
70 200
```

### 출력
```text
6 50
2 45
```

### 힌트
* $V_0 = 0$, 목표 $TARGET = 100$, 시작 $T_{start} = 0$, 최대 $T_{max} = 100$, 폴링 주기 $P = 10$
* **[방식 A: 폴링 (주기 10)]**:
  - $t=0$: 상태 0 $\rightarrow$ 불일치 (1회)
  - $t=10$: 상태 0 $\rightarrow$ 불일치 (2회)
  - $t=20$: 상태 0 $\rightarrow$ 불일치 (3회)
  - $t=30$: 상태 50 $\rightarrow$ 불일치 (4회)
  - $t=40$: 상태 50 $\rightarrow$ 불일치 (5회)
  - $t=50$: 상태 100 $\rightarrow$ **감지 성공!** (6회)
  - 결과: 총 6회 요청, 감지 시각 50 (실제 이벤트 $t=45$ 대비 5초 지연 발생!)
* **[방식 B: 이벤트 푸시]**:
  - $t=25$: 값 50 푸시 (1회)
  - $t=45$: 값 100 푸시 $\rightarrow$ **즉시 감지 성공!** (2회)
  - 결과: 총 2회 푸시, 감지 시각 45 (지연 시간 0초!)
* **비교**: 폴링은 6번 요청하여 5초 늦게 감지한 반면, 이벤트 푸시는 단 2번의 전송으로 0초 만에 즉각 감지!

## 🔍 채점 엣지케이스 안내
1. **$M = 100,000$ 대규모 이벤트 스트림**: 선형 탐색 대신 이진 탐색(Binary Search) 또는 투 포인터(Two Pointer)로 시뮬레이션 최적화 필요
2. $T_{max}$까지 목표 값 $TARGET$이 발생하지 않는 경우 (감지 시각 -1 출력)
3. $T_{start}$ 시점에 이미 상태 값이 $TARGET$인 경우 (과거 이벤트로 이미 $TARGET$에 도달한 상태에서 관찰을 시작한 경우 $\rightarrow$ 폴링은 $t=T_{start}$에 1회 만에 즉시 감지)
4. 이벤트 발생 시각과 폴링 시각이 정확히 일치하는 경우 (이벤트 선반영)
