# 📘 [CS 이론 #008] 끝없는 폴링과 소켓 고갈: Polling vs Event-Driven

> **"0.1초마다 서버에 물어보는 코드를 짰을 뿐인데 왜 소켓이 고갈되고 서버가 다운됐을까?"**  
> 바쁜 대기(Busy Waiting)의 비극, I/O 다중화(epoll), 그리고 웹소켓과 이벤트 루프의 탄생 배경.

---

## 1. 흔한 직관의 함정: "0.1초마다 물어보면 실시간 아니야?"

초보 개발자나 AI 코딩 도구는 "실시간 업데이트"를 구현할 때 가장 먼저 다음과 같은 코드를 작성합니다:

```python
# 가장 순진하고 위험한 단기 폴링 (Short Polling)
while True:
    status = fetch_status_from_server()
    if status == "COMPLETED":
        break
    time.sleep(0.1)  # 0.1초 쉬고 다시 물어보기
```

이 코드는 개발자 혼자 테스트할 때는 0.1초 만에 칼같이 반응하므로 마치 진짜 실시간 시스템인 것처럼 착각하게 만듭니다.  
하지만 **이 방식은 컴퓨터 네트워크 역사상 가장 비효율적이고 위험한 안티패턴 중 하나인 '단기 폴링(Short Polling)'**입니다.

---

## 2. 왜 폴링(Polling)은 서버를 파괴하는가?

사용자 10,000명이 배달 현황이나 주식 호가를 보기 위해 이 앱을 켜두었다고 가정해 보겠습니다:

```
[ 클라이언트 10,000대 ]                                        [ 백엔드 서버 ]
      │                                                              │
      │─── 0.1초마다 HTTP GET /status 요청 전송 (초당 10만 건!) ───►│ (CPU 100% 포화)
      │◄── "아직 배달 중입니다 (상태 변화 없음, 99.99%)" ────────────│
```

### 1) 99.99%의 쓰레기 트래픽 (Wasted Packets)
배달은 보통 20분~30분이 걸립니다. 상태는 30분 동안 딱 3~4번 바뀝니다.  
그런데 0.1초마다 물어보면 30분 동안 **1인당 18,000번의 HTTP 요청**을 보냅니다.  
그중 17,997번은 **"아무것도 변하지 않았다"는 쓸모없는 빈 껍데기 응답**입니다!

### 2) TCP 핸드셰이크와 소켓(File Descriptor) 고갈
HTTP 연결을 맺고 끊을 때마다 3-Way Handshake와 4-Way Handshake가 발생합니다.  
연결이 끊어진 후에도 OS는 패킷 꼬임을 방지하기 위해 **`TIME_WAIT` 상태**로 소켓을 수 분간 물고 있습니다.  
초당 10만 번씩 소켓을 열고 닫으면, **리눅스 서버가 열 수 있는 최대 파일 디스크립터(보통 65,535개 포트)가 순식간에 고갈**되어 더 이상 어떤 네트워크 연결도 받지 못하고 뻗어버립니다.

### 3) 폴링 주기의 딜레마
* **주기를 짧게 하면 (0.1초)**: 서버가 트래픽 폭격으로 즉사합니다.
* **주기를 길게 하면 (10초)**: 서버는 살지만, 배달이 끝났는데 10초 뒤에야 알림이 떠서 유저 경험이 엉망이 됩니다.

## 3. 패러다임의 대전환: "묻지 말고, 일이 생기면 나를 불러라!"

이 비효율을 해결하기 위해 컴퓨터 과학자들은 발상을 180도 뒤집었습니다:

$$\text{"클라이언트가 계속 묻지 말고(Pull), 서버에 데이터가 생겼을 때 알려주자(Push)!"}$$

이를 **이벤트 기반 아키텍처(Event-Driven Architecture)** 또는 **발행-구독(Pub-Sub) 모델**이라고 부릅니다.

```
[ 이벤트 기반 푸시 (Push) ]
클라이언트 ──[ 1. 채널 구독 (Subscribe) ]──► 서버 (대기 상태, CPU 0% 소모)
                                                 │
                                           (30분 뒤 배달 완료 이벤트 발생!)
                                                 │
클라이언트 ◄──[ 2. 배달 완료 이벤트 푸시 (Push) ]──┘ (정확히 단 1회 전송!)
```

* **폴링 방식**: 18,000번의 요청/응답, 지연 시간 발생
* **이벤트 푸시**: **정확히 단 1번의 전송, 지연 시간 0초!**

네트워크 트래픽이 99.99% 절감되고, 서버는 유휴 시간 동안 CPU를 1%도 쓰지 않습니다.

## 4. 운영체제의 혁명: select에서 epoll까지 (C10K 문제)

이벤트 기반의 원리는 웹뿐만 아니라 **운영체제 커널의 I/O 다중화(I/O Multiplexing)**에서도 똑같이 적용되었습니다.

1999년, 소프트웨어 엔지니어들은 *"단일 서버로 동시 접속자 10,000명(C10K)을 처리할 수 있는가?"*라는 거대한 벽에 부딪혔습니다.  
클라이언트 1명당 스레드 1개를 만들면(Thread-per-client), 스레드 1만 개의 스택 메모리만 수십 GB가 되어 메모리가 터졌기 때문입니다.

```
[ 과거: select / poll (폴링 방식) ]
OS 커널: "소켓 1만 개가 등록되어 있네. 1번부터 10,000번까지 하나씩 다 열어보면서 데이터 왔는지 확인해야지..." (O(N) 탐색!)

[ 현대: epoll (Linux) / kqueue (BSD/macOS) (이벤트 기반) ]
OS 커널: "데이터가 도착한 소켓만 하드웨어 인터럽트로 이벤트 큐(Ready List)에 넣어줄게. 넌 이 큐만 꺼내가!" (O(1) 즉시 반환!)
```

* 리눅스의 **`epoll`** 덕분에 서버는 1만 개의 소켓을 루프로 훑을 필요 없이, **데이터가 실제로 도착한 소켓만 $O(1)$로 즉시 처리**할 수 있게 되었습니다.
* 바로 이 `epoll`을 기반으로 만들어진 것이 바로 **Nginx**와 **Node.js의 이벤트 루프(Event Loop)**입니다!

## 5. 실무 실시간 웹 기술 비교

현대 실무에서는 요구사항에 따라 다음과 같은 이벤트 기반 기술을 선택합니다:

| 기술 | 통신 방향 | 프로토콜 | 적합한 사용 사례 |
|---|:---:|:---:|---|
| **Short Polling** | 단방향 (Pull) | HTTP | (실무 사용 비권장) 극도로 단순한 프로토타입 |
| **Long Polling** | 단방향 (Pseudo-Push) | HTTP | 웹소켓을 지원하지 않는 구형 레거시 환경 |
| **Server-Sent Events (SSE)** | **단방향 (Server $\rightarrow$ Client)** | HTTP | **알림, 주식 시세, ChatGPT 스트리밍 응답** |
| **WebSocket** | **양방향 전이중 (Full-Duplex)** | WS / WSS | **실시간 채팅, 멀티플레이어 온라인 게임, 협업 툴** |

---

## 💡 AI 바이브 코더를 위한 실무 체크리스트
1. **`while True: time.sleep()` 루프로 서버를 찌르는 코드를 당장 멈추세요.** 접속자가 늘어나는 순간 서버의 파일 디스크립터와 CPU가 타버립니다.
2. **서버가 클라이언트에게 단방향으로 실시간 데이터를 보내야 한다면 SSE (Server-Sent Events)를 쓰세요.** 웹소켓보다 훨씬 가볍고 HTTP/2와 방화벽 친화적입니다.
3. **양방향 실시간 통신이 필요하다면 무조건 WebSocket을 도입하세요.**
