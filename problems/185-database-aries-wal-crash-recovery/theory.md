# 이론 설명: ARIES 복구 프로토콜과 Steal/No-Force 버퍼 풀 관리

## 1. 버퍼 풀 아키텍처와 Steal / No-Force 정책
데이터베이스 성능의 핵심은 디스크 I/O 횟수를 최소화하는 것입니다. 트랜잭션의 읽기/쓰기는 메인 메모리의 버퍼 풀(Buffer Pool) 페이지에서 수행됩니다.

| 정책 조합 | Steal 허용 여부 | Force 강제 여부 | 장점 | 단점 및 복구 요구사항 |
| :--- | :--- | :--- | :--- | :--- |
| **No-Steal / Force** | 불허 | 필수 | 복구가 매우 단순 (Redo/Undo 불필요) | 극심한 커밋 지연, 메모리 크기 초과 트랜잭션 처리 불가 |
| **Steal / Force** | 허용 | 필수 | 메모리 한도 완화 | 여전히 커밋마다 대량 무작위 디스크 쓰기 병목, Undo 필요 |
| **No-Steal / No-Force** | 불허 | 불허 | 빠른 커밋 | 대형 트랜잭션 처리 불가, Redo 필요 |
| **Steal / No-Force (현대 표준)** | **허용** | **불허** | **최고의 트랜잭션 처리량, 유연한 메모리 활용, 초고속 커밋** | **Redo와 Undo가 모두 완벽하게 동작하는 복구 엔진 필수** |

---

## 2. ARIES 프로토콜의 핵심 3대 원칙 (C. Mohan et al.)

### 2.1 WAL (Write-Ahead Logging)
메모리의 더티 페이지가 디스크 파일로 플러시되기 전에, 해당 변경을 기술하는 로그 레코드가 비휘발성 저장장치에 먼저 쓰여야 합니다. 각 페이지 헤더에는 마지막으로 반영된 로그의 `pageLSN`이 기록되어 있어, 디스크의 페이지 상태와 WAL 로그의 진행 상황을 완벽하게 동기화할 수 있습니다.

### 2.2 Repeating History (역사의 재현)
ARIES의 가장 독창적인 설계 철학은 **"장애 시점까지 발생했던 모든 역사를 그대로 재현한다"**는 것입니다.
- 다른 구형 복구 기법들은 커밋된 트랜잭션만 골라서 Redo하려고 시도하다가 인덱스 구조 변경(SMO)이나 동시성 제어 충돌로 버그를 유발했습니다.
- ARIES는 Redo 단계에서 **커밋 여부와 상관없이 모든 변경사항(패배자 트랜잭션의 변경 포함)을 로그 순서대로 그대로 재실행**합니다.
- 이로써 데이터베이스는 장애가 발생하던 그 찰나의 메모리 상태와 100% 동일한 상태로 복원됩니다.

### 2.3 Compensation Log Record (CLR)을 통한 멱등 복구
Undo 단계에서 미커밋 트랜잭션을 롤백할 때 단순 롤백에 그치지 않고, 취소 작업 자체를 기술하는 **보상 로그 레코드(CLR)**를 로그에 기록합니다:
1. CLR은 `undo_next_lsn` 필드를 가집니다. 이 필드는 취소된 레코드의 `prev_lsn`을 가리킵니다.
2. **불변식**: CLR 자체는 절대 다시 취소(Undo)되지 않습니다.
3. 복구 도중 전원이 다시 나가서 서버가 2차, 3차 크래시를 겪더라도, 재시작 시 CLR을 만나면 `undo_next_lsn`으로 즉시 건너뛰므로 **이미 롤백된 작업을 중복해서 롤백하지 않습니다**.
4. 이 멱등성(Idempotency) 덕분에 복구 작업의 진행 시간이 보장되며 시스템이 무한 롤백 루프에 빠지지 않습니다.

## 3. DPT(Dirty Page Table)와 Redo 최적화
Redo 단계에서 전체 로그를 무조건 디스크에 다 쓸 필요는 없습니다:
1. **DPT 부재 체크**: 페이지 ID가 DPT에 없다면, 이미 크래시 전에 디스크로 완전히 플러시된 상태이므로 Redo를 건너뜁니다.
2. **recLSN 체크**: 로그의 `LSN < DPT[page_id].recLSN`이라면, 해당 변경사항은 이전 플러시에 이미 포함되었으므로 건너뜁니다.
3. **pageLSN 체크**: 디스크 페이지를 읽었을 때 `disk_page.pageLSN >= record.lsn`이라면, 디스크에 이미 최신 데이터가 반영되어 있으므로 쓰기를 건너뜁니다.

이 3중 필터링을 통해 기가바이트 단위의 거대한 WAL 로그가 존재하더라도 실제 복구 시 필요한 디스크 I/O를 수 밀리초 수준으로 최소화할 수 있습니다.
