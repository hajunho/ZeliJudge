# CS 이론 백서: TCP 4-Way Handshake, TIME_WAIT 상태와 임시 포트(Ephemeral Port) 고갈의 덫

> **"초당 1,000건 외부 결제 API를 쐈을 뿐인데, 30초 만에 `Cannot assign requested address` 에러가 터지며 서버 전체 통신이 마비되었습니다."**  
> 이 문제는 네트워크 장비 고장이 아니라, **TCP 프로토콜이 데이터를 보호하기 위해 설계한 `TIME_WAIT` 메커니즘과 단발성 소켓 남용의 충돌**에서 발생합니다.

---

## 1. 현실 비유: 1인용 공중전화 부스와 60초 소독 방역의 비극

마을에 외부와 통화할 수 있는 **1인용 공중전화 부스(임시 포트, Ephemeral Port)**가 딱 5개 있습니다.

```
[부스 30000]   [부스 30001]   [부스 30002]   [부스 30003]   [부스 30004]
```

### 시나리오 A: 단발성 호출의 비극 (단일 요청마다 전화 걸고 끊기)
손님이 도착해서 한 문장 말하고 전화를 끊습니다:
1. 손님이 전화를 끊으면(Active Close), 보건 당국은 부스 안에 혹시 남아있을지 모르는 바이러스(네트워크 지연 유령 패킷)를 없애기 위해 **부스 문을 잠그고 60초 동안 소독 방역(`TIME_WAIT`)**을 진행합니다.
2. 손님이 1초에 1명씩 와서 전화 걸고 끊기를 반복하면:
   - 1초: 30000번 부스 소독 중 (잠김)
   - 2초: 30001번 부스 소독 중 (잠김)
   - 3초: 30002번 부스 소독 중 (잠김)
   - 4초: 30003번 부스 소독 중 (잠김)
   - 5초: 30004번 부스 소독 중 (잠김)
3. **6초째 도착한 손님**:  
   마을의 모든 부스(5개)가 소독 중입니다! 손님은 공중전화 부스에 들어가지 못하고 길바닥에서 쫓겨납니다.  
   $\rightarrow$ **`OSError: [Errno 99] Cannot assign requested address` (포트 고갈 참사)**

---

### 시나리오 B: 커넥션 풀(Connection Pool)의 구원
지혜로운 손님은 부스에 들어가서 전화를 끊지 않고 계속 들고 있습니다(**Keep-Alive**):
- 첫 번째 용건을 말하고, 대기하다가 1초 뒤 두 번째 용건을 말하고, 또 1초 뒤 세 번째 용건을 말합니다.
- 부스 1개(포트 1개)로 수만 건의 용건을 소독 방역 없이 연속으로 처리합니다.
- 나머지 4개의 부스는 다른 긴급 용무를 위해 여유롭게 비어 있습니다(**Healthy**).

---

## 2. TCP 4-Way Handshake와 Active Close의 숙명

TCP 연결을 종료할 때, 양쪽 컴퓨터는 **4단계 핸드셰이크(4-Way Handshake)**를 거칩니다:

```
[클라이언트 (Active Close)]                    [서버 (Passive Close)]
          |                                              |
          | ---------- 1. FIN (종료 요청) -------------> |  (CLOSE_WAIT 진입)
          | <--------- 2. ACK (종료 접수) -------------- |
          |                                              |
          | <--------- 3. FIN (서버도 종료) ------------- |
          | ---------- 4. ACK (최종 확인) -------------> |  (CLOSED)
          |                                              |
     [TIME_WAIT] (2MSL: 약 60초간 유지!)                   |
          |                                              |
     [CLOSED] (60초 후 비로소 포트 회수)                    |
```

연결 종료를 먼저 요청한 쪽을 **Active Close**라고 부르며, 반드시 **Active Close를 시도한 쪽이 `TIME_WAIT` 상태**에 빠지게 됩니다.

## 3. `TIME_WAIT`는 도대체 왜 존재하는가? (절대 버그가 아니다!)

초보 개발자들은 "왜 소켓을 닫았는데 60초나 포트를 붙잡고 안 놔주냐! 버그 아니냐!"라며 분노합니다. 하지만 `TIME_WAIT`는 인터넷의 무결성을 지키는 핵심 안전장치입니다:

### 1) 마지막 ACK 유실 대비 (신뢰성 있는 연결 종료)
- 클라이언트가 보낸 4단계 마지막 `ACK`가 네트워크 혼잡으로 도중에 유실될 수 있습니다.
- 만약 클라이언트가 ACK를 보내자마자 포트를 닫아버린다면, 서버는 FIN에 대한 ACK를 못 받았으므로 FIN을 다시 보냅니다.
- 하지만 클라이언트는 이미 닫혔으므로 서버에 `RST`(강제 리셋)를 날리고, 서버는 "비정상 종료" 에러를 뿜으며 비명을 지릅니다.
- `TIME_WAIT`로 60초 동안 살아있어야, 서버가 FIN을 재전송했을 때 마지막 ACK를 다시 던져주며 아름답게 종료할 수 있습니다.

### 2) 지연 패킷(Ghost / Stray Packet)의 데이터 오염 방지
- 인터넷 라우터들이 혼잡할 때, 이전 연결에서 보낸 패킷이 라우터 큐에 갇혀 몇 초간 헤매는 일이 발생합니다.
- 만약 소켓이 즉시 닫히고 0.1초 뒤 동일한 포트 번호로 새로운 TCP 연결이 맺어졌다면?
- 이전 연결에서 방황하던 지연 패킷이 불쑥 새 연결에 도착하여 새 데이터와 섞여버립니다! 금융 송금 내역이 엉뚱한 결제 건에 덮어써지는 끔찍한 데이터 오염이 발생합니다.
- 패킷의 최대 수명(MSL: Maximum Segment Lifetime, 보통 30초)의 2배인 **2MSL(60초)** 동안 포트를 잠가두면, 방황하던 지연 패킷들이 자연 소멸되어 새 연결을 오염시킬 위험이 0이 됩니다.

## 4. 임시 포트(Ephemeral Port) 고갈과 `Cannot assign requested address`

리눅스 OS에서 아웃바운드 연결을 맺을 때 사용하는 **임시 포트(Ephemeral Port)** 범위는 다음과 같습니다:
```bash
$ cat /proc/sys/net/ipv4/ip_local_port_range
32768   60999
```
- 총 가용 포트 수: $60999 - 32768 + 1 = \mathbf{28,232개}$.
- 만약 외부 API를 호출하면서 `requests.get()`을 세션 없이 단발성으로 호출하면:
  - 1초에 500개 요청 $\rightarrow$ 1초에 500개 포트가 `TIME_WAIT`로 진입!
  - 28,232개 / 500개 $\approx \mathbf{56초}$!
  - **정확히 56초 만에 서버의 28,232개 임시 포트가 전량 고갈**됩니다!
- 더 이상 아웃바운드 소켓에 바인딩할 포트가 남아있지 않으므로, OS는 즉시 에러를 반환합니다:
  ```text
  OSError: [Errno 99] Cannot assign requested address (EADDRNOTAVAIL)
  ```
- 이후 들어오는 모든 결제, 로그인, 외부 통신이 100% 거부되며 전사적 장애로 이어집니다.

## 5. 실무 아키텍트의 3단계 해결책

### 1단계: HTTP Connection Pool & Keep-Alive 적용 (최우선 필수!)
단발성 소켓 생성을 멈추고, 연결을 재사용하는 커넥션 풀을 사용합니다.
- **Python**:
  ```python
  # ❌ 재앙의 코드: 매 요청마다 새 TCP 연결 + TIME_WAIT 폭증
  for url in urls:
      requests.get(url)

  #  구원의 코드: 1개 세션(풀)으로 TCP 연결 재사용
  session = requests.Session()
  for url in urls:
      session.get(url)
  ```
- **효과**: 수만 건의 요청을 단 2~4개의 TCP 포트로 처리! 3-Way Handshake와 TLS 협상 시간이 사라져 응답 속도가 10배 빨라지고, `TIME_WAIT`가 원천 발생하지 않습니다.

### 2단계: Linux 커널 파라미터 `tcp_tw_reuse` 활성화
리눅스 서버에서 다음과 같이 커널 파라미터를 튜닝합니다:
```bash
# TIME_WAIT 소켓이 1초 이상 경과되었고 타임스탬프가 유효하다면 새 아웃바운드 연결에 재사용 허용
sysctl -w net.ipv4.tcp_tw_reuse=1
sysctl -w net.ipv4.tcp_timestamps=1
```
- `tcp_tw_reuse`는 RFC 1323의 TCP 타임스탬프를 확인하여 지연 패킷의 위험이 없는 경우에만 안전하게 `TIME_WAIT` 소켓을 즉시 재사용합니다.

### 3단계: 임시 포트 범위 확장
기본 28,232개인 포트 범위를 6만 개 이상으로 확장합니다:
```bash
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
```

> ⚠️ **절대 사용 금지 경고 (`tcp_tw_recycle`)**:  
> 인터넷 블로그에 종종 `net.ipv4.tcp_tw_recycle = 1`을 켜라는 옛날 글이 있습니다. 이 옵션은 NAT(공유기/로드밸런서) 환경에서 서로 다른 클라이언트의 패킷을 무작위로 사살(Drop)하는 치명적인 참사를 유발하여 **리눅스 커널 4.12부터 완전히 삭제**되었습니다. 절대로 켜서는 안 됩니다!
