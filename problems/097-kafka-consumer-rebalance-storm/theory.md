# 097. 배치 작업 5분 돌렸을 뿐인데 왜 전사 메시지 처리가 멈추고 파티션이 핑퐁을 쳐요?!: Apache Kafka 컨슈머 리밸런스 폭풍(Consumer Rebalance Storm)과 `max.poll.interval.ms`의 배신

---

## 1. 비극의 시작: 도서관 사서와 5분 반납 타이머 비유

어느 대학교 중앙도서관에 아주 엄격한 규칙이 있습니다:
- 서가(카프카 파티션)에는 수많은 책 꾸러미(메시지 레코드)가 꽂혀 있습니다.
- 학생 3명(컨슈머 A, B, C)이 팀을 이뤄(컨슈머 그룹) 서가 책들을 나눠 읽기로 했습니다.
- 사서 선생님(카프카 브로커의 그룹 코디네이터, Group Coordinator)은 다음과 같은 규칙을 공표했습니다:
  > **"학생 여러분! 책을 한 번 빌려 가면(poll), 최대 5분(max.poll.interval.ms=300초) 안에 데스크로 돌아와서 '여기까지 다 읽었습니다!' 하고 확인 도장(commit)을 찍어야 합니다. 5분이 지나도 안 오면 여러분이 도서관에서 쓰러졌거나 튄 것으로 간주하고 도서관 전체 문을 일시 폐쇄(Rebalance)한 뒤 책을 다른 사람에게 뺏어서 넘깁니다!"**

그런데 학생 A가 빌려간 책 꾸러미 속에 **페이지가 10,000장에 달하는 초고난도 전공 서적(대용량 배치 결제 정산 메시지)**이 섞여 있었습니다!  
A는 땀을 뻘뻘 흘리며 정독하느라 **5분 10초**가 걸렸습니다.

그 10초 사이에 도서관에는 무슨 일이 벌어졌을까요?
1. **강제 퇴출 (Eviction)**:  
   사서 선생님은 시계를 보더니 **"학생 A가 5분 동안 데스크에 안 나타났다! A는 사망했다!"**며 즉시 명부에서 A의 이름을 파내버렸습니다.
2. **도서관 전체 폐쇄 (Eager Rebalance / Stop-The-World)**:  
   사서는 사이렌을 울리며 멀쩡히 다른 책을 읽고 있던 B와 C에게 소리쳤습니다:  
   *"전원 독서 중단! 자리에 있는 책 전부 데스크에 반납해라! A가 빠졌으니 책을 처음부터 다시 분배한다!"*  
   도서관 안의 모든 학생이 독서를 멈추고 멍하니 대기하게 되었습니다.
3. **독후감 파기 (`CommitFailedException`)**:  
   5분 10초가 된 순간, A가 땀을 닦으며 독후감을 들고 데스크로 뛰어왔습니다.  
   *"선생님! 저 10,000쪽 다 읽었습니다! 확인 도장 찍어주세요!"*  
   사서는 차갑게 말합니다:  
   **"너 이미 10초 전에 제명당했어. 네 책은 이미 다른 사람한테 넘어갔으니 도장 못 찍어준다!"** (`CommitFailedException`)
4. **리밸런스 폭풍의 악순환 (Rebalance Storm)**:  
   - 사서는 A가 읽던 그 무시무시한 전공책을 **학생 B**에게 넘겼습니다.
   - B는 영문도 모른 채 그 책을 펴서 읽기 시작합니다. A가 이미 다 읽었지만 도장을 못 찍었기 때문에 **처음부터 다시 읽어야 합니다(중복 처리, Duplicate Processing)!**
   - 한편 쫓겨난 A는 억울해서 **"저 다시 공부할래요!" 하고 재입실 신청(`JoinGroup`)**을 합니다.
   - A가 들어오자 도서관은 또 문을 닫고 책을 재분배합니다(**2차 폐쇄**)!
   - 그 와중에 책을 넘겨받은 B도 5분 안에 다 못 읽고 또 쫓겨납니다!
   - 도서관은 공부는 1초도 못 하고 **하루 종일 '문 닫고 책 뺏기 핑퐁'만 무한 반복**하게 되었습니다!

## 2. 컴퓨터 과학 / 분산 시스템 이론

### 1) 카프카 컨슈머 그룹과 파티션 매핑 원칙
- **파티션(Partition)**: 카프카 토픽의 수평 확장 단위이자 메시지의 엄격한 순서(FIFO)가 보장되는 큐.
- **컨슈머 그룹(Consumer Group)**: 여러 대의 컨슈머 인스턴스가 협력하여 토픽의 메시지를 병렬 처리하는 단위.
- **불변 원칙**: 한 토픽의 특정 파티션은 동일 컨슈머 그룹 내에서 **동시에 단 하나의 컨슈머 인스턴스에만 할당**될 수 있습니다 (1:1 배타적 매핑).

### 2) 하트비트 스레드(Heartbeat Thread)와 폴 스레드(Poll Thread)의 분리 (KIP-62)
카프카 0.10.1 이전에는 하트비트와 메시지 처리가 단일 스레드에서 돌아갔습니다. 이로 인해 메시지 처리가 길어지면 하트비트를 못 보내서 컨슈머가 끊기는 문제가 잦았습니다.  
이에 카프카 커뮤니티는 **두 스레드를 완전히 분리**했습니다:

| 설정 파라미터 | 담당 주체 | 역할 및 감시 대상 |
| :--- | :--- | :--- |
| `session.timeout.ms` (기본 45초) | **Heartbeat Thread** (백그라운드) | 컨슈머 프로세스의 물리적 생존 여부 (JVM 크래시, 네트워크 단절 감지) |
| `max.poll.interval.ms` (기본 300초 / 5분) | **Application / Poll Thread** (메인 루프) | 비즈니스 로직 처리의 정상 진행 여부 (무한 루프, 스레드 데드락, 처리 지연 감지) |

> **실무 함정**: 많은 초보 개발자가 "우리 컨슈머 하트비트 정상적으로 가고 프로세스도 살아있는데 도대체 왜 리밸런스가 터지죠?!"라며 혼란에 빠집니다.  
> 하트비트 스레드는 백그라운드에서 멀쩡히 돌고 있지만, **메인 스레드가 `records`를 처리하느라 다음 `poll()`을 제시간에 부르지 못하면 브로커는 컨슈머가 멈춘(Hanged) 것으로 간주하고 가차 없이 퇴출**시킵니다!

### 3) 리밸런스 프로토콜 (Rebalance Protocol)
1. **Eager Rebalance (기본/전통적 방식)**:
   - 그룹 멤버 구성에 변화가 생기면(멤버 추가, 이탈, 파티션 증설), **모든 컨슈머가 자신이 들고 있던 모든 파티션을 즉시 반납**합니다.
   - 모든 컨슈머가 메시지 처리를 멈추는 **전면 정지(Stop-The-World)**가 발생합니다.
   - 코디네이터가 새 파티션 할당표를 완성하면 그제서야 각자 할당받은 파티션에서 읽기를 재개합니다.
2. **Cooperative Sticky Assignor (협력적 스티키 리밸런스, KIP-429)**:
   - 카프카 2.4+부터 도입된 진보된 방식.
   - 전체를 멈추지 않고, **소유권이 이전되어야 하는 파티션만 선별적으로 반납**합니다.
   - 변경 없는 나머지 대다수 파티션은 리밸런스 중에도 끊김 없이 메시지를 계속 소비합니다.

### 4) `CommitFailedException`과 중복 처리의 메커니즘
컨슈머가 5분 동안 열심히 100건의 메시지를 DB에 인서트했습니다.  
그리고 `consumer.commitSync()`를 호출하는 순간:
1. 브로커는 이미 리밸런스를 진행하여 해당 파티션을 다른 컨슈머(B)에게 넘긴 상태입니다.
2. 브로커의 세대 번호(`Generation ID`)가 올라갔기 때문에, 구 세대의 커밋 요청을 거부하고 `CommitFailedException`을 던집니다.
3. 파티션을 새로 받은 B는 **A가 커밋하지 못한 마지막 오프셋부터 다시 읽기 시작**합니다.
4. 결과: **A가 이미 DB에 넣었던 100건의 데이터가 B에 의해 또다시 DB에 인서트되는 '대규모 중복 결제/데이터 오염'**이 발생합니다!

## 3. 실무 아키텍처 및 튜닝 모범 사례

1. **`max.poll.records` 튜닝**:
   - `poll()` 한 번에 가져오는 레코드 수를 줄입니다 (예: 기본 500개 -> 50개 또는 10개).
   - 레코드 1건당 평균 1초가 걸린다면 `max.poll.records=50`으로 줄여야 50초 안에 처리가 끝나 300초 제한을 넘지 않습니다.
2. **`max.poll.interval.ms` 적정값 상향**:
   - 무거운 배치나 외부 결제 PG사 API 호출이 포함되어 있다면, 최악의 지연시간을 고려하여 `max.poll.interval.ms`를 충분히 크게 늘립니다 (예: 15분~30분).
3. **비동기 워커 스레드 풀 오프로딩 (Worker Thread Pool Offloading)**:
   - `poll()` 스레드는 메시지를 가져와서 인메모리 큐(BlockingQueue)에 넣고 즉시 다음 `poll()`을 호출하여 카프카와의 연결을 유지합니다.
   - 실제 무거운 비즈니스 로직은 별도의 워커 스레드 풀(ExecutorService)이 병렬로 처리합니다.
4. **멱등성(Idempotency) 보장**:
   - 리밸런스는 분산 시스템에서 언제든 발생할 수 있으므로, 재처리되더라도 안전하도록 DB Unique 제약조건이나 멱등 키(Idempotency Key)를 반드시 적용합니다.
