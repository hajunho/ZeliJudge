# 📚 기술 백서: Sticky Session vs Redis 분산 세션 vs JWT

> **"웹 서버를 진정한 무상태(Stateless)로 만들지 못하면, 당신의 클라우드 오토스케일링(Auto-scaling)은 사상누각에 불과합니다."**

서버가 1대일 때는 프레임워크가 제공하는 기본 `HttpSession`이나 메모리 세션만으로도 로그인 기능이 완벽하게 동작합니다.
하지만 서비스가 성장하여 로드밸런서(ALB, Nginx) 뒤에 웹 서버를 2대, 3대로 늘리는 순간(Scale-out), 사용자들은 **"방금 로그인했는데 다음 페이지에서 로그인이 풀려요!"**라며 분통을 터뜨립니다.

이 백서에서는 멀티 서버 환경에서 발생하는 세션 불일치의 원인과 이를 해결하기 위한 **세션 클러스터링 4대 아키텍처의 트레이드오프**를 깊이 있게 분석합니다.

---

## 1. 현실 비유: 병원 3개 진료실과 진료 차트

종합병원에 3개의 진료실(서버 1, 서버 2, 서버 3)이 있고 입구에 안내원(로드밸런서)이 있습니다:

1. **로컬 메모리 세션 (각 의사 책상 서랍)**:
   * 환자가 1번 진료실 의사에게 접수하고 진료를 받았습니다. 의사는 진료 차트(세션)를 **자기 책상 서랍(RAM)**에 넣어두었습니다.
   * 환자가 수납을 하려고 다음 방으로 가자, 안내원은 환자를 2번 진료실로 보냈습니다.
   * 2번 의사는 자기 서랍을 뒤져보더니: *"환자분 기록이 없는데요? 다시 처음부터 접수하세요!"*
2. **Sticky Session (담당 의사 지정제)**:
   * 안내원이 환자 옷에 **"1번 의사 전용" 스티커**를 붙여주어 다음부터는 무조건 1번 방으로만 보냅니다.
   * 하지만 1번 의사가 갑자기 쓰러져 병원에 못 나오면(서버 크래시), 서랍이 잠겨 진료 차트가 통째로 증발합니다! 또한 유명한 환자들만 1번 방으로 몰려 1번 진료실만 미어터지는 **트래픽 불균형**이 발생합니다.
3. **Redis 중앙 분산 세션 (병원 중앙 전산실 차트)**:
   * 의사 개인 서랍을 치우고, 모든 환자의 진료 차트를 **병원 중앙 전산실(Redis)**에 등록합니다.
   * 환자가 1번 방으로 가든, 2번 방으로 가든, 3번 방으로 가든 전산망에서 즉시 차트를 열람합니다. 1번 방 의사가 쓰러져도 2번 방에서 즉시 진료를 이어갈 수 있습니다!
4. **JWT 무상태 토큰 (환자 목에 건 공인 전자 명찰)**:
   * 전산실을 매번 조회할 필요조차 없이, 병원장의 위조 불가 디지털 서명이 들어간 **전자 명찰(JWT)**을 환자 목에 걸어줍니다.
   * 의사들은 환자의 명찰 서명만 확인하고 즉시 진료합니다.

## 2. 왜 서버를 늘리면 세션이 풀릴까?

HTTP 프로토콜은 기본적으로 연결을 유지하지 않는 **무상태(Stateless)** 프로토콜입니다.
따라서 클라이언트의 상태를 기억하기 위해 서버는 쿠키(`JSESSIONID`, `connect.sid` 등)를 클라이언트에 주고, 서버 자신의 메모리에 세션 객체를 매핑합니다.

```text
[Client] --- (Request + Cookie: JSESSIONID=abc) ---> [Load Balancer]
                                                           |
                      +------------------------------------+------------------------------------+
                      |                                    |                                    |
            [Web Server 1 (RAM)]                 [Web Server 2 (RAM)]                 [Web Server 3 (RAM)]
          Session: abc -> User(42)              Session: (비어있음!)                  Session: (비어있음!)
```

로드밸런서는 기본적으로 모든 서버에 트래픽을 고르게 나누기 위해 **라운드로빈(Round-Robin)** 또는 **최소 연결(Least Connection)** 알고리즘을 사용합니다.
서버가 3대라면, 다음 클릭에서 세션이 유지될 확률은 고작 $\frac{1}{3}$ (33.3%)에 불과하며, 나머지 66.7%의 확률로 다른 서버로 튕겨나가 세션이 풀려버립니다!

## 3. 세션 관리 4대 아키텍처 비교

| 아키텍처 | 동작 원리 | 핵심 장점 | 치명적 단점 / 한계 | 실무 사용 권장도 |
|:---:|---|---|---|:---:|
| **Local Memory** | 서버 자체 RAM 힙 메모리에 저장 | 구현 비용 0원, 최고 속도 | 서버 2대 이상 시 세션 불일치 100% 발생, 서버 다운 시 세션 소실 | ❌ 단일 서버 외 사용 금지 |
| **Sticky Session** | L7 로드밸런서가 유저 쿠키를 보고 항상 동일 서버로 고정 라우팅 | 기존 코드 수정 없이 멀티 서버 적용 가능 | **트래픽 불균형(Hotspot)**,<br>**서버 장애/무중단 배포 시 해당 서버 유저 세션 전원 증발** | ⚠️ 과도기 임시 조치용 |
| **Redis 분산 세션** | 모든 웹 서버가 중앙 인메모리 DB(Redis)를 세션 스토리지로 공유 | **완전한 무상태(Stateless) 웹 서버**, 자유로운 오토스케일링 및 장애 복구(Failover) 무손실 | Redis 네트워크 I/O 오버헤드, Redis 단일 장애점(SPOF) 방지 클러스터 필요 | **실무 웹 서비스 표준 (Golden Standard)** |
| **JWT 무상태 인증** | 세션 저장소 없이 서명된 토큰(Token) 자체에 유저 정보를 담아 클라이언트가 소지 | **서버 저장소 0원, DB/Redis I/O 없음**, MSA/모바일 앱 최적화 | **토큰 탈취 시 즉시 무효화(블랙리스트) 불가**, 토큰 크기 증가로 네트워크 대역폭 낭비 | **MSA / 모바일 API 표준** |

## 4. Sticky Session의 2대 치명적 한계

많은 개발자들이 로컬 세션 문제를 해결하기 위해 AWS ALB에서 클릭 한 번으로 켤 수 있는 **Sticky Session(세션 고정)**을 선택합니다.
하지만 이는 다음의 2대 재앙을 필연적으로 낳습니다:

1. **트래픽 핫스팟 (Hotspot Server)**:
   * 특정 서버에 로그인한 유저들이 유독 많은 활동(헤비 유저, 크롤러 등)을 하면, 로드밸런서는 그 트래픽을 다른 한가한 서버로 분산시키지 못하고 그 서버로만 계속 몰아주어 **결국 특정 서버 1대만 CPU 100%를 치며 폭사**합니다.
2. **무중단 롤링 배포(Rolling Deploy)의 악몽**:
   * 서비스를 중단하지 않고 서버를 1대씩 교체하며 배포할 때, 교체되는 서버에 붙어있던 모든 유저는 **배포 순간 세션이 통째로 날아가 강제 로그아웃**됩니다.

## 5. Redis 분산 세션: Stateless 웹 아키텍처의 완성

Spring Boot에서는 `spring-session-data-redis` 의존성 하나만 추가하면 웹 서버의 세션 저장소를 Redis로 즉시 전환할 수 있습니다.

```mermaid
sequenceDiagram
    autonumber
    actor Client as 유저 (브라우저)
    participant ALB as 로드밸런서 (ALB)
    participant S1 as Web Server 1
    participant S2 as Web Server 2
    participant Redis as Redis Session Cluster

    Client->>ALB: POST /login (로그인)
    ALB->>S1: 라운드로빈 전달
    S1->>Redis: HSET session:abc user_id=42 (세션 저장)
    S1-->>Client: Set-Cookie: SESSION=abc; HttpOnly

    Note over Client, S2: 다음 클릭 (라운드로빈으로 S2 배정!)
    Client->>ALB: GET /profile (Cookie: SESSION=abc)
    ALB->>S2: 라운드로빈 전달
    S2->>Redis: HGET session:abc -> user_id=42
    S2-->>Client: 200 OK (프로필 정상 조회!)

    Note over S1: S1 서버 장애(Crash) 발생!
    Note over Client, S2: 다음 요청
    Client->>ALB: GET /orders (Cookie: SESSION=abc)
    ALB->>S2: 정상 서버인 S2로 전달
    S2->>Redis: HGET session:abc -> user_id=42
    S2-->>Client: 200 OK (서버가 죽어도 세션 100% 무사!)
```

## 6. 결론: 언제 Redis 세션을 쓰고, 언제 JWT를 써야 하는가?

* **Redis 분산 세션을 써야 할 때**:
  * 전통적인 웹 브라우저 기반 SSR(Spring MVC, Thymeleaf, Django 등) 서비스.
  * **보안이 극도로 중요한 금융/커머스** (관리자가 특정 사용자의 세션을 즉시 강제 종료하거나, 동시 로그인 1회 제한을 걸어야 할 때).
* **JWT를 써야 할 때**:
  * 모바일 앱(iOS, Android) 및 단일 페이지 애플리케이션(SPA: React, Vue, Next.js).
  * 서버가 수십 개로 쪼개진 **마이크로서비스 아키텍처(MSA)**에서 서비스 간 인증 상태를 Redis 조회 없이 초고속으로 전파해야 할 때.
