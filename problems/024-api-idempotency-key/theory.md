# [ZeliJudge 백서 #024] 새로고침 5번 눌렀더니 결제가 5번 됐어요?!: 멱등성(Idempotency)과 멱등키의 방패

> **"네트워크에는 '성공'과 '실패'만 있는 것이 아닙니다. 진짜 공포는 '서버는 돈을 깎았는데 응답만 유실된 알 수 없음(Unknown)' 상태입니다."**

---

## 1. 💡 비전공자 바이브 코더를 위한 현실 비유: "엘리베이터 버튼 vs 자판기 동전"

일생생활에서 멱등성(Idempotency)을 이해하는 가장 쉬운 비유는 **엘리베이터 버튼**과 **자판기**입니다:

```text
[엘리베이터 닫힘 버튼] ──> 멱등함 (Idempotent)
문이 닫히길 바라며 [닫힘] 버튼을 1번 누르든, 성격이 급해서 10번 연타하든,
문이 닫히는 최종 결과는 완벽히 똑같습니다! (시스템에 추가적인 부작용 없음)

[자판기 동전 투입구] ───> 멱등하지 않음 (Non-Idempotent)
1,000원짜리 지폐를 1번 넣으면 1,000원이 충전되지만,
5번 집어넣으면 잔액이 5,000원이 됩니다! (실행할 때마다 시스템 상태가 계속 변함!)
```

만약 결제 API가 **자판기 동전 투입구처럼 동작**한다면?  
네트워크가 불안정해서 고객이 [결제하기]를 3번 누르는 순간, 통장에서 돈이 3번 빠져나가는 끔찍한 금융 사고가 터집니다!

## 2. 🔍 컴퓨터 과학적 원리: 분산 네트워크의 3대 상태

많은 개발자가 함수 호출 결과를 성공(Success) 또는 실패(Failure)의 이분법으로 생각합니다.  
하지만 인터넷(분산 네트워크) 세상에는 **제3의 상태**가 존재합니다:

```text
[정상 상황]
클라이언트 ─── (1) 결제 요청 ───> 백엔드 서버 (DB 5만원 차감)
클라이언트 <─── (2) 성공 응답 ─── 백엔드 서버 (200 OK)

[네트워크 유실 참사]
클라이언트 ─── (1) 결제 요청 ───> 백엔드 서버 (DB 5만원 차감 완료!)
클라이언트 <─── (2) 성공 응답 ─── 💥 중간 와이파이 단절로 응답 패킷 증발!
```

- **클라이언트의 시점**: "응답이 안 오고 타임아웃 에러가 떴네? 결제가 안 됐나 보다. 다시 결제 버튼 눌러야지!" (재시도, Retry)
- **서버의 시점**: "어? 아까 결제했는데 또 결제 요청이 왔네? 또 5만 원 깎아야지!" ──> **중복 과금(Double Charge) 참사!**

## 3. 🌐 HTTP 메서드의 멱등성 표준 (RFC 7231)

| HTTP Method | 멱등성 여부 | 설명 |
|---|:---:|---|
| **`GET`** | ✅ **멱등함** | 데이터를 100번 조회해도 서버의 데이터는 변하지 않음 |
| **`PUT`** | ✅ **멱등함** | "이 데이터로 덮어써라"이므로 100번 반복해도 최종 데이터는 동일함 |
| **`DELETE`**| ✅ **멱등함** | 1번 지우든 100번 지우든 해당 데이터가 없는 최종 상태는 동일함 |
| **`POST`** | ❌ **멱등하지 않음** | 호출할 때마다 새로운 게시글/주문/결제가 계속 생성됨! |

결제나 주문처럼 시스템 상태를 변경하는 작업은 보통 `POST` 메서드를 사용합니다.  
그렇다면 `POST` 요청의 중복 실행을 어떻게 막을 수 있을까요?

## 4. 🛡️ 구원의 기술: 멱등키 (Idempotency Key)

글로벌 결제 표준(Stripe, 토스페이먼츠)은 **멱등키(Idempotency Key)** 패턴을 사용합니다:

```text
[1단계: 클라이언트의 고유 키 발급]
클라이언트: 주문 1건당 무작위 UUID v4 멱등키를 딱 하나 발급하여 헤더에 동봉
POST /api/pay
Header: Idempotency-Key: pay-9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d

[2단계: 백엔드의 멱등성 검사]
백엔드:
if 멱등키가 DB/Redis에 없는가?
    -> [FIRST_RUN]: 실제 잔액 차감 수행!
    -> 성공 응답(Body, Status)을 해당 멱등키와 함께 캐시에 저장 (TTL 24시간)
else (이미 기록된 멱등키인가?)
    -> [CACHED_REPLAY]: 🛑 실제 결제를 절대로 다시 하지 않음!
    -> 이전에 캐싱해 둔 최초 성공 응답을 그대로 즉시 반환!
```

### 왜 이 방식은 완벽한가?
- 고객이 통신 장애로 결제 버튼을 10번 연타하더라도, 브라우저는 **동일한 멱등키**를 실어 보냅니다.
- 서버는 첫 번째 요청에서만 실제로 계좌에서 돈을 깎고,
- 나머지 9번의 요청에 대해서는 **돈을 전혀 건드리지 않고 "결제 성공했습니다!"라는 아까의 영수증(캐시 응답)만 돌려줍니다.**
- 결과적으로 고객 통장에서는 정확히 1번만 결제되며, 사용자 화면에도 정상 결제 완료 화면이 뜨게 됩니다!
