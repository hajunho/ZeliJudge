# [CS-104] TCP 네이글 알고리즘(Nagle's Algorithm)과 지연된 ACK(Delayed ACK) 40ms 지연의 저주 (`TCP_NODELAY`)

> **"로컬 환경에서는 0.1ms 만에 끝나던 마이크로서비스 간 RPC 호출이, 패킷 2번 쪼개 보냈을 뿐인데 왜 칼같이 40ms씩 지연되죠?!"**
> 
> 결제 백엔드를 담당하는 신입 개발자 준호는 마이크로서비스 간 HTTP/1.1 클라이언트를 직접 구현했습니다.
> 코드를 깔끔하게 분리한다는 생각으로 `socket.write(http_headers)`를 호출한 직후 곧바로 `socket.write(json_body)`를 호출했습니다.
> 로컬 루프백 테스트에서는 아무 문제 없던 이 코드가, 사내 내부망 서버로 배포되자마자 모든 결제 승인 API의 p99 지연시간이 정확히 **40.2ms**로 치솟았습니다.
> 
> "쿼리도 0.5ms밖에 안 걸리고 네트워크 핑도 0.2ms인데, 왜 모든 요청이 귀신에 홀린 듯 40ms씩 멈춰 설까요?!"
> 네트워크 시스템 아키텍트는 씩 웃으며 Wireshark 패킷 캡처 로그를 보여주었습니다.
> "준호 씨, 컴퓨터 네트워크 역사상 가장 유명한 '두 천재의 선의가 빚어낸 40ms 데드락'에 걸리셨군요. 존 네이글(John Nagle)의 알고리즘과 버클리 소켓의 Delayed ACK가 서로를 하염없이 기다리고 있습니다."

---

## 1. 두 알고리즘의 탄생 배경과 목적

### 1) 작은 패킷의 홍수를 막아라: 네이글 알고리즘 (Nagle's Algorithm, RFC 896, 1984)
인터넷 태동기인 1980년대 초반, 유저들은 텔넷(Telnet)을 통해 원격 서버에 접속했습니다.
사용자가 키보드로 `a`라는 한 글자(1바이트)를 입력할 때마다 운영체제는 패킷을 만들어 네트워크로 전송했습니다.
- 전송할 데이터: **1 바이트**
- IP 헤더: **20 바이트**
- TCP 헤더: **20 바이트**
- 총 패킷 크기: **41 바이트** (헤더 오버헤드가 무려 97.5%!)

네트워크 회선 대역폭이 수십 Kbps에 불과하던 시절, 이런 자잘한 패킷(Small Packet / Tinygram)들이 초당 수만 개씩 쏟아지자 인터넷 라우터 버퍼가 넘쳐나며 전체 네트워크가 마비되는 **혼잡 붕괴(Congestion Collapse)**가 발생했습니다.

이에 존 네이글은 1984년 다음과 같은 혁신적인 규칙을 제안했습니다:
> **네이글 규칙 (RFC 896)**:
> "송신 버퍼에 데이터가 생겼을 때:
> 1. 모인 데이터가 **MSS(Maximum Segment Size, 보통 1460B)** 이상이면 즉시 한 세그먼트를 묶어서 전송한다.
> 2. 만약 데이터가 MSS보다 작다면:
>    - 이전에 보낸 패킷 중 **아직 상대방으로부터 확인 응답(ACK)을 받지 못한 데이터(In-Flight Data)**가 전혀 없다면 즉시 전송한다.
>    - 아직 받지 못한 ACK가 하나라도 남아있다면, 새 데이터를 즉시 보내지 말고 **버퍼에 대기(Buffering)**시킨다!"

즉, "이전 패킷의 ACK가 올 때까지 작은 패킷을 마구 쏘지 말고 한곳에 모아두라"는 지혜로운 완충 전략이었습니다.

---

### 2) 빈 껍데기 ACK를 아껴라: 지연된 확인 응답 (Delayed ACK, RFC 1122)
한편, 버클리 소켓(BSD) 구현자들은 수신 측(서버)의 오버헤드에 주목했습니다.
클라이언트가 보낸 데이터 패킷마다 서버가 매번 빈 껍데기 ACK 패킷(40바이트 헤더)을 전송하는 것은 엄청난 네트워크 대역폭 낭비였습니다.

이에 다음과 같은 Delayed ACK 최적화가 도입되었습니다:
> **Delayed ACK 규칙 (RFC 1122)**:
> "상대방으로부터 데이터 패킷을 수신했을 때:
> 1. 즉시 빈 ACK를 보내지 말고 **최대 40ms (OS에 따라 100~200ms) 동안 대기**한다.
> 2. 만약 40ms 이내에 서버가 클라이언트에게 보낼 **응답 데이터(HTTP Response 등)**가 생기면, 그 응답 패킷에 ACK 번호를 얹어서(Piggybacking) 함께 보낸다!
> 3. 만약 40ms 이내에 상대방으로부터 **두 번째 데이터 세그먼트(Full-sized segment)**가 도착하면 타이머를 취소하고 즉시 누적 ACK를 보낸다.
> 4. 40ms 동안 아무것도 오지 않으면, 타이머 만료로 인해 어쩔 수 없이 빈 ACK 패킷을 전송한다."

## 2. 악마의 결합: 40ms 교착상태 (Interlock Deadlock)

각각의 알고리즘은 네트워크 대역폭을 아끼기 위한 천재적인 발상이었습니다.
하지만 클라이언트가 데이터를 **두 번 나누어 쓰는(2-Write Pattern)** 순간, 두 알고리즘은 최악의 침묵 교착상태를 만들어냅니다.

### 40ms 참사 시나리오: `write(header); write(body);`

```
[클라이언트 (Nagle ON)]                         [서버 (Delayed ACK ON)]
       │                                                   │
       │─── 1. Header (50 bytes) 전송 ───────────────────>│ (도착!)
       │    (In-Flight 없으므로 첫 패킷은 즉시 전송)       │
       │                                                   │ "패킷 1개 왔네? 응답이나
       │                                                   │  2번째 패킷 올 때까지
       │                                                   │  40ms 동안 ACK 지연하자!"
       │                                                   │ (Delayed ACK 타이머 가동 ⏰)
       │                                                   │
       │ 2. Body (200 bytes) 쓰기 발생                     │
       │    "어? 헤더 50B의 ACK가 아직 안 왔네?"          │
       │    "그리고 바디 200B는 MSS(1460B)보다 작네?"     │
       │    "네이글 규칙에 따라 버퍼에 대기한다!"         │
       │    (전송 보류: BUFFERED)                          │
       │                                                   │
       │                  <<< 40ms 동안 침묵 >>>           │
       │    클라이언트: "서버야, 제발 ACK 좀 줘..."        │
       │    서버:       "클라이언트야, 2번째 패킷 줘..."   │
       │                                                   │
       │                                                   ⏰ 40ms 타이머 만료!
       │<── 3. Delayed ACK (빈 껍데기 패킷) ───────────────│ "에휴, 더 안 오네. ACK 보낸다."
       │                                                   │
       │ "드디어 ACK가 왔다! In-Flight 해소!"              │
       │─── 4. Body (200 bytes) 버퍼 방출 전송 ───────────>│ (도착!)
       │                                                   │
```

보시다시피, 헤더와 바디의 실제 전송 시간은 0.1ms도 안 걸렸지만, **Nagle과 Delayed ACK의 상호 대기로 인해 강제로 40ms가 증발**한 것입니다!

## 3. 실무 해결책 및 아키텍처 베스트 프랙티스

### 1) `TCP_NODELAY` 소켓 옵션 활성화 (Nagle 알고리즘 끄기)
대부분의 현대 네트워크 애플리케이션(Nginx, Netty, Redis, Node.js, gRPC 등)은 소켓을 열 때 기본적으로 `TCP_NODELAY = 1`을 설정합니다.
```c
int flag = 1;
setsockopt(sock_fd, IPPROTO_TCP, TCP_NODELAY, (char *)&flag, sizeof(int));
```
- Nagle 알고리즘을 즉시 비활성화하여, MSS 미만의 작은 패킷이라도 버퍼링 없이 즉시 네트워크 망으로 방출합니다.
- 지연시간(Latency)이 생명인 온라인 게임, 금융 HFT, RPC, 웹 서버 환경에서는 필수 설정입니다.

### 2) 단일 버퍼 병합 쓰기 (Scatter-Gather I/O & `writev`)
소켓 쓰기를 2번 호출하지 않고, 유저 공간에서 헤더와 바디를 단 하나의 연속된 버퍼로 합치거나 `writev(iov, 2)` 시스템 콜을 사용하여 1회의 세그먼트로 전송합니다.

### 3) `TCP_CORK` vs `TCP_NODELAY`
- `TCP_NODELAY`: 데이터를 모으지 말고 0초 만에 즉시 쏴라 (지연시간 최소화).
- `TCP_CORK`: 대용량 파일 전송(`sendfile`) 시 패킷이 MSS에 찰 때까지 무조건 꽉꽉 채워서 쏴라 (대역폭 효율 극대화).
