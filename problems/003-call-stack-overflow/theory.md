# 📘 [CS 이론 #003] 순진한 재귀함수의 최후: 콜 스택(Call Stack)과 메모리 구조

> **"재귀 함수는 왜 1,000번만 돌면 뻗을까? 반복문은 1억 번도 도는데?"**  
> 프로세스의 4대 메모리 영역(Code, Data, Heap, Stack)과 시스템 아키텍처의 한계.

---

## 1. 재귀(Recursion)의 치명적인 함정

많은 컴퓨터 전공 입문서와 AI 코딩 도구는 재귀 함수를 사랑합니다. 코드가 수학 공식처럼 짧고 우아해 보이기 때문입니다.

```python
# 우아해 보이지만 서비스 다운을 유발하는 재귀 코드
def dfs(node):
    for child in node.children:
        dfs(child)
```

하지만 이 코드는 **실무 프로덕션 환경의 시한폭탄**입니다.  
폴더 구조나 트리 데이터가 일직선으로 길어져 깊이(Depth)가 1,000단계를 넘어서는 순간, 파이썬은 다음 에러를 뿜으며 즉시 중단됩니다:

```text
RecursionError: maximum recursion depth exceeded
```

반복문(`for`, `while`)은 1억 번을 돌아도 절대 터지지 않는데, **왜 재귀 함수는 고작 1,000번 만에 컴퓨터를 항복시키는 걸까요?**  
그 비밀은 운영체제(OS)가 프로세스에 제공하는 **'메모리 구조'**에 있습니다.

---

## 2. 운영체제와 프로세스의 4대 메모리 영역

프로그램이 실행되어 프로세스(Process)가 되면, OS는 메모리(RAM)를 크게 4개 영역으로 나누어 할당합니다:

```
┌────────────────────────────────────────────────────────┐ 높은 메모리 주소 (0xFFFFFFFF)
│                 스택 영역 (Stack)                      │ ──┐
│      함수 호출 프레임, 지역 변수, 반환 주소              │   │ 아래로 자람 (보통 1MB ~ 8MB 제한!)
├────────────────────────────────────────────────────────┤   ▼
│                          │                             │
│                          ▼                             │
│                                                        │
│                          ▲                             │
│                          │                             │
├────────────────────────────────────────────────────────┤   ▲ 위로 자람 (수 GB ~ 수십 GB 가용!)
│                  힙 영역 (Heap)                        │ ──┘
│        동적 할당 객체 (Python List, Dict, Object 등)    │
├────────────────────────────────────────────────────────┤
│                 데이터 영역 (Data / BSS)               │
│               전역 변수(Global), 정적 변수             │
├────────────────────────────────────────────────────────┤
│                 코드 영역 (Code / Text)                │
│                 컴파일된 기계어 명령어                   │
└────────────────────────────────────────────────────────┘ 낮은 메모리 주소 (0x00000000)
```

1. **코드(Code) 영역**: 실행할 기계어 명령어가 읽기 전용으로 저장되는 곳
2. **데이터(Data) 영역**: 프로그램 전체에서 공유하는 전역 변수가 저장되는 곳
3. **힙(Heap) 영역**: 프로그래머가 동적으로 생성하는 데이터(파이썬의 리스트, 딕셔너리, 인스턴스 등)가 저장되는 곳. **컴퓨터의 RAM 크기만큼(수 GB ~ 수십 GB) 광활하게 쓸 수 있습니다.**
4. **스택(Stack) 영역**: **함수 호출과 관련된 임시 정보**가 저장되는 곳. **OS가 각 스레드당 보통 1MB(Windows) ~ 8MB(Linux) 정도로 극도로 비좁게 제한**해 둡니다.

---

## 3. 함수를 호출할 때 일어나는 일: 스택 프레임(Stack Frame)

함수 `A()`가 함수 `B()`를 호출할 때, 컴퓨터는 `B()`가 끝나고 다시 돌아갈 주소와 `B()` 내부의 지역 변수들을 기억해야 합니다.  
이를 위해 스택 메모리에 하나의 상자(**스택 프레임, Stack Frame**)를 차곡차곡 쌓아 올립니다:

```
[ 함수 호출 시 스택 메모리 상태 ]
│                                    │
├────────────────────────────────────┤
│ dfs(node=4) : 지역변수, 반환주소    │ ◄── 맨 위
├────────────────────────────────────┤
│ dfs(node=3) : 지역변수, 반환주소    │
├────────────────────────────────────┤
│ dfs(node=2) : 지역변수, 반환주소    │
├────────────────────────────────────┤
│ dfs(node=1) : 지역변수, 반환주소    │
├────────────────────────────────────┤
│ main()                             │
└────────────────────────────────────┘
```

함수가 반환(`return`)되면 스택 프레임이 제거(Pop)되면서 메모리가 반환됩니다.  
하지만 **재귀 함수는 자식 호출이 끝나기 전까지 이전 부모의 스택 프레임이 절대로 제거되지 않습니다.**

만약 트리의 깊이가 100,000단계라면?  
스택 프레임 10만 개가 1MB 남짓한 좁은 스택 메모리에 쏟아져 들어오며, 스택 영역의 바닥을 뚫고 지나가는 **'스택 오버플로우(Stack Overflow)'**가 발생합니다.

## 4. `sys.setrecursionlimit()`을 쓰면 프로세스가 즉사하는 이유

AI에게 *"재귀 깊이 에러가 나요"*라고 물어보면 단골로 추천하는 코드가 있습니다:

```python
import sys
sys.setrecursionlimit(1000000)  # 재귀 제한을 100만으로 늘린다?
```

파이썬의 기본 재귀 한도가 1,000인 이유는 파이썬이 느려서가 아닙니다.  
**OS의 물리적 C-스택 메모리가 터지기 전에 파이썬 인터프리터 차원에서 소프트웨어적으로 안전하게 에러를 던져 프로세스를 보호하는 방화벽**입니다.

이 방화벽을 강제로 해제하면 어떻게 될까요?  
파이썬 인터프리터(CPython)는 C 언어로 작성된 프로그램입니다. C-레벨에서 실제 하드웨어 스택 메모리 한계(1MB~8MB)를 넘어서는 순간, OS 커널은 경고도 없이 해당 프로세스에 강제 종료 시그널을 보냅니다:
* Linux: **`Segmentation Fault (core dumped)`**
* Windows: **`0xC00000FD (STATUS_STACK_OVERFLOW)`**

`try...except` 문으로 감싸도 잡을 수 없습니다. 프로세스가 즉사(Crash)하여 서버가 바로 내려갑니다.

## 5. 구원투수: 힙(Heap)을 쓰는 명시적 스택(Explicit Stack)

그렇다면 깊이가 10만, 100만 단계를 넘나드는 대규모 트리나 그래프는 어떻게 탐색해야 할까요?  
답은 **"OS의 비좁은 시스템 콜 스택(1MB)을 버리고, 광활한 힙(Heap) 메모리(수십 GB)를 쓰는 반복문으로 전환하는 것"**입니다.

파이썬의 일반 `list`는 힙(Heap) 메모리에 할당됩니다:

```python
# [해결책] 시스템 스택 대신 힙 메모리 리스트를 활용한 반복문 DFS
def traverse_with_heap_stack(root, weights, adj):
    total_cost = 0
    # 스택에 (노드 번호, 부모 노드, 현재 깊이) 저장
    # 이 stack 리스트는 수십 GB 용량의 '힙(Heap) 메모리'에 저장됩니다!
    stack = [(root, 0, 1)]
    
    while stack:
        curr, parent, depth = stack.pop()
        total_cost += depth * weights[curr]
        
        for neighbor in adj[curr]:
            if neighbor != parent:
                stack.append((neighbor, curr, depth + 1))
                
    return total_cost
```

### 왜 이 방식은 안전할까요?
* 함수를 새로 호출하지 않으므로 **OS 콜 스택 프레임은 오직 `traverse_with_heap_stack` 단 1개**만 유지됩니다.
* 10만 개의 데이터는 모두 힙 메모리에 얹히므로, 메모리가 넉넉하여 스택 오버플로우가 물리적으로 일어날 수 없습니다.
* 함수 호출 오버헤드(Call/Return 오버헤드)가 사라져 **실행 속도도 2~5배 이상 빨라집니다.**

## 6. 보너스 CS 상식: 꼬리 재귀 최적화 (TCO, Tail Call Optimization)

어떤 언어들(Scala, Elixir, Scheme 등 함수형 언어)은 재귀 함수를 작성해도 컴파일러가 자동으로 반복문(Loop) 코드로 변환해 주는 **꼬리 재귀 최적화(TCO)**를 지원합니다.

> **파이썬 창시자 귀도 반 로섬은 왜 파이썬에 TCO를 넣지 않았을까요?**  
> 귀도는 *"TCO를 적용하면 스택 프레임이 덮어씌워져 사라지기 때문에, 버그가 발생했을 때 상세한 스택 트레이스(Stack Trace)를 볼 수 없어 디버깅이 어려워진다"*는 철학으로 파이썬에 TCO 도입을 명시적으로 거부했습니다.  
> **따라서 파이썬에서는 개발자가 직접 명시적 스택이나 반복문을 작성해야 합니다.**

1. **재귀 함수를 기본값으로 쓰지 마세요.** 깊이가 1,000을 넘을 가능성이 1%라도 있는 데이터(트리, 그래프, 파일 경로 순회, 대댓글 등)는 무조건 `while` 루프와 명시적 스택/큐로 작성하세요.

3. **너비 우선 탐색(BFS)을 쓸 때는 `collections.deque`를 쓰세요.** 일반 `list.pop(0)`은 $O(N)$이지만 `deque.popleft()`는 $O(1)$입니다.
