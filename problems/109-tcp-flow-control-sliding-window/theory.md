# [CS-109] 수신자가 숨넘어가는데 계속 쐈더니 패킷이 통째로 증발해요?!: TCP 흐름 제어(Flow Control) 슬라이딩 윈도우와 제로 윈도우 프로브(Zero Window Probe)

> **"선생님! 10Gbps 초고속 전용선인데, 대용량 파일을 전송하다가 전송 속도가 갑자기 0KB/s로 곤두박질치더니 멈춰버렸어요! 와이어샤크(Wireshark)를 켜보니 `TCP ZeroWindow`와 `TCP ZeroWindowProbe`라는 시뻘건 경고가 화면을 가득 채우고 있어요!"**
> 
> 고성능 파일 전송 데몬을 개발하던 신입 네트워크 엔지니어 현우는 이상한 병목을 마주했습니다.
> 송신 측 서버는 초당 수백 메가바이트의 데이터를 뿜어낼 준비가 되어 있었고, 네트워크 회선 대역폭도 넉넉했습니다.
> 하지만 수신 측 서버가 데이터베이스 저장 및 압축 작업으로 인해 CPU 100%를 치며 데이터를 천천히 읽자, 몇 초 지나지 않아 전송이 완전히 올스톱되었습니다.
> 
> "회선도 널널하고 송신 서버도 쌩쌩한데 왜 패킷 전송이 0으로 멈출까요?!"  
> 시니어 네트워크 아키텍트는 칠판에 슬라이딩 윈도우 다이어그램을 그리며 말했습니다.
> "현우 씨, 아무리 주방장(송신자)이 요리를 1초에 한 접시씩 만들어도, 손님 테이블(수신 버퍼)에 빈 접시 놓을 자리가 없으면 요리를 내보낼 수 없어요. 수신자가 '제발 그만 보내요, 자리가 없어요!(Zero Window)'라고 비명을 지른 겁니다."

---

## 1. 혼잡 제어(Congestion Control) vs 흐름 제어(Flow Control)

네트워크를 공부할 때 가장 많이 혼동하는 두 개념입니다:

1. **혼잡 제어 (Congestion Control, `cwnd`)**:
   - 대상: 송신자와 수신자 사이에 놓인 **"네트워크 망(라우터, 스위치, 중계 회선)"**
   - 목적: 네트워크 도로망이 패킷 정체로 마비되지 않도록 전송량을 조절 (Slow Start, AIMD 등).
2. **흐름 제어 (Flow Control, `rwnd`)**:
   - 대상: 데이터를 받는 **"수신자(Receiver)의 소켓 수신 버퍼(Receive Buffer)"**
   - 목적: 수신 측 애플리케이션의 처리 속도가 느려서 수신 버퍼가 오버플로우(Overflow)되어 패킷이 쓰레기통으로 버려지는 것을 원천 방지.

---

## 2. 슬라이딩 윈도우(Sliding Window)와 수신 윈도우(`rwnd`)

TCP는 흐름 제어를 위해 **슬라이딩 윈도우(Sliding Window)** 알고리즘을 사용합니다.

```
[수신 측 소켓 수신 버퍼 (Total Buffer = 4000 Bytes)]
┌──────────────────────────────┬──────────────────────────────┐
│  도착했으나 아직 앱이 안 읽음  │    현재 비어있는 수용 공간     │
│       (2500 Bytes 점유)      │      (rwnd = 1500 Bytes)     │
└──────────────────────────────┴──────────────────────────────┘
```

1. **윈도우 통보 (Window Advertisement)**:
   - 수신자는 송신자에게 ACK 패킷을 보낼 때마다, TCP 헤더의 `Window Size` 필드에 자신의 현재 수용 가능한 잔여 공간 크기인 **`rwnd` (Receive Window)**를 적어서 보냅니다.
2. **송신 윈도우 제한**:
   - 송신자는 수신자로부터 확인받지 못한 채 네트워크에 띄울 수 있는 미확인 바이트의 총합을 `rwnd` 이하로 엄격히 제한합니다:
     $$	ext{LastByteSent} - 	ext{LastByteAcked} \le 	ext{rwnd}$$
   - 송신 윈도우가 0이 되면 송신자는 추가 데이터 송신을 즉시 중단하고 대기합니다.

## 3. 제로 윈도우(Zero Window)와 침묵의 교착상태(Deadlock)

수신 측 애플리케이션이 무거운 연산으로 인해 소켓 수신 버퍼에서 데이터를 전혀 읽어가지 않으면, 버퍼가 100% 꽉 차는 순간이 발생합니다.
- 수신자는 송신자에게 **`rwnd = 0` (TCP ZeroWindow)**을 통보합니다.
- 송신자는 이 알림을 받고 즉시 패킷 전송을 전면 중단합니다.

### 악마의 시나리오: 윈도우 갱신(Window Update) 패킷 유실 참사
```
[송신자 (Sender)]                                       [수신자 (Receiver)]
       │                                                         │
       │<─── 1. ACK (rwnd = 0) "버퍼 꽉 찼음! 전송 중단해!" ──────│ (수신 버퍼 100% 포화)
       │    (송신 전면 중단: Window Closed)                       │
       │                                                         │ (앱이 2000B를 읽음!)
       │                                                         │ (버퍼에 2000B 여유 발생)
       │    <<< 2. Window Update (rwnd = 2000) 패킷 유실! 💥 >>> │
       │    (네트워크 노이즈/라우터 혼잡으로 패킷 소멸)             │
       │                                                         │
       │                   <<< 영구 교착상태 발생 >>>             │
       │ 송신자: "윈도우 열릴 때까지 기다려야지..."                 │ 수신자: "왜 데이터가 더 안 오지?"
       │ (영원히 대기)                                            │ (영원히 대기)
```
- TCP의 순수 ACK 패킷은 그 자체로는 ACK를 요구하지 않으므로, 이 갱신 패킷이 유실되면 양쪽이 서로를 하염없이 기다리는 **영구 교착상태(Deadlock)**에 빠집니다!

## 4. 구원 투수: 지속 타이머(Persist Timer)와 제로 윈도우 프로브(Zero Window Probe)

TCP 설계자들은 이 치명적인 교착상태를 깨뜨리기 위해 기막힌 해결책을 마련했습니다:

### 지속 타이머 (Persist Timer)
- 송신자는 `rwnd = 0` 통보를 받는 그 순간 **지속 타이머(Persist Timer)**를 가동합니다.

### 제로 윈도우 프로브 (Zero Window Probe, ZWP)
- 타이머가 만료되면 송신자는 수신자에게 **1바이트짜리 작은 정찰병 패킷(Zero Window Probe)**을 강제로 전송합니다.
- **수신자의 의무**: 수신자는 유효한 패킷을 받았으므로, 현재 자신의 최신 윈도우 상태를 담은 **ACK를 무조건 회신**해야 합니다!
- 만약 수신자 버퍼에 여전히 여유가 없다면 다시 `rwnd = 0`이 올 것이고, 송신자는 지속 타이머를 재가동합니다.
- 수신자 버퍼에 여유가 생겼다면 회신된 ACK에 `rwnd = 2000`이 담겨 올 것이므로, 송신자는 즉시 슬라이딩 윈도우를 열고 정상 전송을 재개합니다!

## 5. 실무 아키텍처 베스트 프랙티스

1. **소켓 수신 버퍼 튜닝 (`SO_RCVBUF`)**:
   - 고속 대용량 트래픽 환경에서는 OS 기본 수신 버퍼(예: 128KB)가 쉽게 고갈되므로, BDP(Bandwidth-Delay Product)에 맞게 `SO_RCVBUF`를 적절히 상향 조정해야 합니다.
2. **논블로킹 비동기 I/O (Reactive / Netty)**:
   - 수신 측 애플리케이션이 I/O 스레드에서 무거운 CPU 연산이나 DB 블로킹 작업을 하지 않고, 워커 풀로 즉시 오프로딩하여 수신 버퍼를 상시 비워두어야 Zero Window 병목을 예방할 수 있습니다.
