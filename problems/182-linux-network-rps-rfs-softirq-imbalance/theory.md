# Linux 네트워크 멀티코어 수신 스케일링: RSS, RPS, RFS와 softirq 불균형 아키텍처

## 1. 개요: 100Gbps 시대의 리눅스 네트워크 스택 병목

현대 데이터센터의 네트워크 대역폭은 1Gbps에서 10Gbps, 40Gbps, 100Gbps, 심지어 400Gbps로 급격히 발전했습니다. 100Gbps 링크에서 최소 크기 패킷(64바이트 이더넷 프레임)이 전송될 때, 초당 패킷 처리량(Packet Per Second, PPS)은 **약 1억 4,880만 PPS (148.8 Mpps)**에 달합니다.
이는 패킷 1개당 처리 시간이 **약 6.7 나노초(ns)** 이내여야 함을 의미합니다.

단일 최신 CPU 코어의 클록 주파수가 3~4GHz라 할 때, 6.7ns는 고작 20~30 CPU 사이클에 불과합니다. 함수 호출 한 번, 캐시 미스(L3 캐시 40~60사이클, DRAM 접근 200사이클) 한 번만으로도 패킷 처리 기한을 넘기게 됩니다. 따라서 단일 CPU 코어로는 100Gbps는커녕 10Gbps의 라인 레이트(Line Rate)조차 처리할 수 없으며, **멀티코어 CPU로의 완벽한 수신 부하 분산(Multi-core Inbound Load Balancing)**이 필수적입니다.

그러나 멀티코어로 패킷을 분산하는 과정에서 다음과 같은 치명적인 엔지니어링 문제들이 발생합니다:
1. **하드웨어 인터럽트 및 softirq 편향(CPU Core Imbalance)**
2. **패킷 역순 전달(Packet Out-of-Order Delivery)로 인한 TCP 처리량 붕괴**
3. **코어 간 캐시 핑퐁(Inter-core Cache Ping-Pong) 및 메모리 버스 경합**

리눅스 커널은 이를 해결하기 위해 하드웨어 가속(RSS)과 소프트웨어 수신 스케일링(RPS, RFS, aRFS) 기술을 발전시켜 왔습니다.

## 2. 리눅스 네트워크 수신 경로 (RX Path)의 두 단계: HardIRQ vs SoftIRQ

네트워크 카드(NIC)에 패킷이 도착하여 유저스페이스 소켓 버퍼로 전달되기까지의 수신 경로는 다음과 같습니다:

```
+-----------------------------------------------------------------------------------+
| 1. 패킷 도착 (NIC RX FIFO)                                                        |
+-----------------------------------------------------------------------------------+
                                         |
                                         v (DMA)
+-----------------------------------------------------------------------------------+
| 2. 호스트 RAM의 RX Ring Buffer (디스크립터 링)에 sk_buff 메모리 쓰기               |
+-----------------------------------------------------------------------------------+
                                         |
                                         v (MSI-X Interrupt)
+-----------------------------------------------------------------------------------+
| 3. 하드웨어 인터럽트 (Top-Half ISR)                                               |
|    - CPU의 정상 실행 중단                                                         |
|    - 인터럽트 확인(ACK) 및 인터럽트 비활성화                                      |
|    - NAPI 구조체 스케줄링 (napi_schedule(&adapter->napi))                         |
|    - NET_RX_SOFTIRQ 소프트 인터럽트 플래그 세팅 (raise_softirq(NET_RX_SOFTIRQ))     |
+-----------------------------------------------------------------------------------+
                                         |
                                         v (Context: ksoftirqd/X or irq_exit)
+-----------------------------------------------------------------------------------+
| 4. 소프트 인터럽트 (Bottom-Half: NET_RX_SOFTIRQ)                                   |
|    - napi_poll() 루틴 실행                                                        |
|    - budget (보통 300 또는 64개 패킷)만큼 링 버퍼에서 skb를 인출                   |
|    - netif_receive_skb() 호출                                                     |
|      - [RPS/RFS 적용 지점]: 대상 CPU 결정 및 IPI(Inter-Processor Interrupt) 전송  |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
| 5. 네트워크 계층 처리 (IPv4/IPv6, iptables, TCP/UDP 스택)                         |
|    - 체크섬 검증, 라우팅 테이블 조회                                              |
|    - TCP 상태 머신, 시퀀스 번호 검증, 소켓 수신 큐(sk_receive_queue)에 skb 적재   |
+-----------------------------------------------------------------------------------+
                                         |
                                         v (wake_up_interruptible)
+-----------------------------------------------------------------------------------+
| 6. 유저 애플리케이션 수신 (epoll_wait -> recv / read)                             |
|    - 커널 공간 skb 데이터를 유저 버퍼로 복사 (copy_to_user)                      |
+-----------------------------------------------------------------------------------+
```

### Top-Half와 Bottom-Half의 분리 이유
하드웨어 인터럽트 핸들러(Top-Half)가 실행되는 동안에는 해당 CPU의 다른 인터럽트가 마스킹(차단)됩니다. 복잡한 TCP 패킷 파싱, 방화벽 규칙 검사, 세션 트래킹을 Top-Half에서 수행하면 시스템 전체가 멈추므로, Top-Half는 최소한의 작업(NAPI 스케줄링)만 하고 즉시 종료되며, 실제 패킷 디코딩은 Bottom-Half(`NET_RX_SOFTIRQ`)에서 비동기적으로 수행됩니다.

## 3. 멀티코어 분산 기법 비교: RSS, RPS, RFS

### 3.1 하드웨어 멀티큐: RSS (Receive Side Scaling)
고성능 NIC(Intel, Mellanox, Broadcom 등)는 하드웨어 레벨에서 복수 개의 독립적인 RX 링 버퍼(Queue)를 지원합니다.
- **Toeplitz 해시**: NIC 하드웨어가 패킷 헤더의 4-튜플(Source IP, Dest IP, Source Port, Dest Port)을 추출하여 Toeplitz 해시를 계산합니다.
- **RETA (Redirection Table)**: 해시값의 하위 N비트를 인덱스로 사용하여 RETA 테이블을 참조하고, 패킷을 특정 하드웨어 큐(예: RX Queue 0~7)로 전달합니다.
- **MSI-X 벡터 분산**: 각 RX 큐는 전용 MSI-X 하드웨어 인터럽트 라인을 가지며, `/proc/irq/<irq_num>/smp_affinity`를 통해 각 큐의 인터럽트를 서로 다른 CPU 코어로 1:1 매핑할 수 있습니다.

```
       [ 패킷 4-튜플 ]
              |
              v (하드웨어 Toeplitz Hash)
        [ RETA Table ]
       /      |       \
      v       v        v
  [Queue 0] [Queue 1] [Queue 2]
     |         |         | (MSI-X IRQ)
     v         v         v
  [Core 0]  [Core 1]  [Core 2]
```

### 3.2 소프트웨어 RSS 에뮬레이션: RPS (Receive Packet Steering)
가상화 환경(AWS EC2 초기 인스턴스, virtio-net)이나 단일 하드웨어 큐만 지원하는 저가형 NIC에서는 하드웨어 RSS를 사용할 수 없습니다. 이 경우 단일 코어(보통 Core 0)가 모든 하드웨어 인터럽트를 전담하므로 CPU 1개가 100% 포화됩니다.

이를 구제하기 위해 리눅스 커널 2.6.35에 도입된 것이 **RPS**입니다.
- 단일 하드웨어 인터럽트를 받은 Core 0의 드라이버가 `netif_receive_skb()`를 실행할 때, 소프트웨어로 4-튜플 해시(`skb_get_hash()`)를 계산합니다.
- 대상 코어로 지정된 CPU의 백로그 큐(`input_pkt_queue`)에 패킷을 넣고, **IPI (Inter-Processor Interrupt)**를 날려 해당 코어의 `NET_RX_SOFTIRQ`를 깨웁니다.
- **장점**: 멀티큐 하드웨어가 없어도 수신 프로토콜 스택 처리를 전 코어로 분산할 수 있습니다.

### 3.3 치명적 결함: 단순 라운드로빈(Round-Robin)과 TCP 패킷 역순(Out-of-Order) 재앙
RPS를 구현할 때 "가장 이상적인 부하 분산은 코어들에게 패킷을 순서대로 골고루 나누어주는 라운드로빈"이라고 착각하기 쉽습니다. 하지만 이는 **네트워크 스택의 대참사**를 부릅니다:

```
[클라이언트] ----(Seq 1, 2, 3, 4 송신)----> [NIC]
                                              |
                   +--------------------------+--------------------------+
                   | (Round-Robin 분배)                                  |
                   v                                                     v
              [Core 0] (Seq 1, 3 처리)                              [Core 1] (Seq 2, 4 처리)
                   | (다른 작업으로 지연 발생)                           | (빠르게 처리 완료)
                   v                                                     v
               [TCP 스택] <---------------- Seq 2 도착 (Seq 1 없음!)
                                            -> 즉시 Dup ACK 발생!
               [TCP 스택] <---------------- Seq 4 도착
                                            -> 2번째 Dup ACK!
               [TCP 스택] <---------------- Seq 1 지연 도착 (Out-of-Order)
```

1. **TCP Fast Retransmit 발동**: 동일한 TCP 연결의 패킷들이 서로 다른 코어에서 병렬 처리되면 코어별 스케줄링 지터로 인해 도착 순서가 뒤바뀝니다.
2. 수신측은 구멍(Hole)이 뚫린 패킷을 보고 **3회의 중복 ACK(Duplicate ACK)**를 발생시킵니다.
3. 송신측은 실제 패킷 유실이 없음에도 불구하고 패킷이 망실되었다고 판단하여 **빠른 재전송(Fast Retransmit)**을 수행하고, 혼잡 윈도우(CWND)를 절반 이하로 강제 축소(`ssthresh = cwnd / 2`)합니다.
4. 결과적으로 네트워크 링크가 아무리 널널해도 실제 TCP 전송률은 1/10 수준으로 폭락합니다.

따라서 모든 네트워크 수신 조향(RSS, RPS)은 반드시 **"동일한 4-튜플(플로우)의 패킷은 항상 동일한 코어로 보내는 해시 기반 플로우 고정(Flow Affinity)"** 규칙을 엄격히 준수해야 합니다.

## 4. 캐시 지역성과 RFS (Receive Flow Steering)

### 4.1 RPS의 숨은 한계: 캐시 미스와 인터-코어 버스 트래픽
해시 기반 RPS로 동일 플로우를 Core 1에 고정했다고 가정합시다.
그런데 정작 유저스페이스에서 해당 소켓의 `read()` 시스템 콜을 호출하는 웹 서버 프로세스(예: Nginx 워커 스레드)는 OS 스케줄러에 의해 **Core 3**에서 돌고 있다면 어떻게 될까요?

1. **Core 1**: softirq가 패킷 헤더와 페이로드를 읽어 소켓 버퍼에 기록 (Core 1의 L1/L2 D-Cache에 적재됨).
2. **Core 3**: 유저 애플리케이션이 소켓 버퍼를 읽기 위해 메모리 접근 (`copy_to_user`).
3. Core 3의 L1/L2 캐시에는 해당 데이터가 없으므로 **L1/L2 Cache Miss** 발생.
4. CPU 캐시 일관성 프로토콜(MESI/MOESI)에 의해 Core 1의 L2 캐시 라인을 인터커넥트 버스(UPI/QPI)를 통해 Core 3로 복사해오는 **Cross-Core Cache Invalidation 및 전송 오버헤드** 발생.
5. 메모리 버스 지연으로 인해 패킷당 처리 시간이 $10\,\mu\text{s}$에서 $50\,\mu\text{s}$ 이상으로 5배 급증합니다.

### 4.2 RFS: 소켓-코어 완벽 일치 (Zero-Copy Cache Locality)
**RFS**는 패킷을 단순히 4-튜플 해시 코어로 보내는 대신, **"해당 소켓을 현재 읽고 있는 애플리케이션 스레드가 있는 코어"**로 패킷을 조향합니다.

리눅스 커널은 두 개의 해시 테이블을 유지합니다:
1. **`rps_sock_flow_table` (글로벌 소켓 플로우 테이블)**:
   - 유저 애플리케이션이 소켓에 대해 `recvmsg()`, `read()`, `epoll_wait()`을 호출할 때마다, 커널은 현재 CPU 코어 ID를 이 테이블에 업데이트합니다 (`sock_rps_record_flow()`).
2. **`rps_dev_flow_table` (NIC 디바이스별 플로우 테이블)**:
   - 드라이버가 패킷을 수신했을 때 `rps_sock_flow_table`을 조회하여 애플리케이션이 실행 중인 코어를 찾아냅니다.
   - 단, 패킷 역순을 방지하기 위해 직전 코어의 큐가 완전히 비워진 것을 확인한 후에만 코어를 전환합니다.

이로 인해 **softirq를 처리하는 코어와 유저 애플리케이션 스레드가 동일한 코어로 통합**되어, 패킷 데이터가 **L1/L2 캐시에 완벽히 보존(Cache Hit 100%)**되며 지연시간이 극적으로 단축됩니다.

## 5. 엔지니어링 실무 진단 및 튜닝 체크리스트

리눅스 프로덕션 서버에서 네트워크 멀티코어 병목을 진단하고 해결하기 위한 가이드입니다:

### 1. 인터럽트 불균형 진단 (`/proc/interrupts`)
```bash
watch -d -n 1 "cat /proc/interrupts | grep -E 'eth|mlx|ens'"
```
- 특정 CPU 코어(예: CPU 0)의 인터럽트 카운터만 급격히 증가하고 다른 코어는 0에 가깝다면 하드웨어 IRQ 불균형입니다.

### 2. softnet 통계 진단 (`/proc/net/softnet_stat`)
```bash
cat /proc/net/softnet_stat
```
각 열(Column)의 의미:
- **1열**: 총 처리된 패킷 프레임 수
- **2열 (dropped)**: 백로그 큐가 가득 차서 드랍된 패킷 수 (`core_softirq_capacity` 초과)
- **3열 (time_squeeze)**: budget(보통 300) 내에 패킷을 다 비우지 못하고 softirq 핸들러가 강제 양보한 횟수

### 3. RPS 설정 (예: 4개 코어 0, 1, 2, 3으로 분산)
비트마스크 `f` (2진수 `1111` = 코어 0, 1, 2, 3):
```bash
echo "f" > /sys/class/net/eth0/queues/rx-0/rps_cpus
```

### 4. RFS 활성화
글로벌 엔트리 수(보통 32768)와 큐당 엔트리 수 설정:
```bash
echo 32768 > /proc/sys/net/core/rps_sock_flow_entries
echo 32768 > /sys/class/net/eth0/queues/rx-0/rps_flow_cnt
```
