# [CS 백서 #088] 멀티스레드로 바꿨더니 왜 10배나 느려져요?!: CPU 캐시 라인(64바이트)과 거짓 공유(False Sharing)의 덫

> **"성능을 높이려고 단일 스레드 카운터를 4개 스레드 병렬 카운터로 바꿨습니다. 뮤텍스(Lock)도 전혀 안 썼는데, 왜 4배 빨라지기는커녕 10배나 느려졌을까요?!"**  
> Go, Java, C++, Rust로 고성능 병렬 시스템을 구축하던 개발자들이 가장 큰 충격을 받는 순간입니다.  
> 원인은 소프트웨어 코드에는 락이 없지만, **CPU 하드웨어 레벨에서 64바이트 캐시 라인을 서로 뺏고 빼앗기며 버스 핑퐁(Bus Bouncing) 전쟁**을 벌이고 있었기 때문입니다.  
> 이를 컴퓨터 과학에서 **거짓 공유(False Sharing)** 라고 부릅니다!

---

## 1. 현실 세계 비유: 한 장의 도화지를 나눠 쓰는 4명의 화가

4명의 천재 화가(CPU 코어 4개)가 각자 맡은 그림을 그리고 있습니다.
- 사장님이 각자에게 개인 스케치북을 준 게 아니라, **커다란 전지 1장(64바이트 캐시 라인)** 을 주고 각자 모퉁이 4군데에 그림을 그리라고 했습니다.
- 화가 A는 왼쪽 위에, 화가 B는 오른쪽 위에, 화가 C는 왼쪽 아래에, 화가 D는 오른쪽 아래에 그림을 그립니다.
- 각자 완전히 다른 그림을 그리고 있으므로 논리적으로는 충돌할 이유가 없습니다.

### 참사의 시작: "내가 붓을 댈 땐 아무도 손대지 마!"
그런데 전지(도화지)의 규칙이 이상합니다:
- 도화지에는 딱 1명의 화가만 붓을 댈 수 있습니다(**캐시 일관성 프로토콜, MESI**).
- 화가 A가 왼쪽 위에 점 하나를 찍으면, 도화지가 통째로 화가 A의 손으로 날아옵니다.
- 그 순간 그림을 그리려던 화가 B, C, D는 도화지를 뺏겨 작업을 멈추고 멍하니 기다려야 합니다(**Cache Invalidation & Miss**).
- 이번엔 화가 B가 점 하나를 찍자, 도화지가 화가 B에게로 뺏겨옵니다. 화가 A는 그리던 손을 멈춰야 합니다.
- 결국 4명의 화가는 1초에 수천 번씩 **도화지를 이리저리 뺏고 빼앗기느라(Cache Bouncing)** 정작 그림은 단 한 획도 제대로 긋지 못하고 하루를 날려버립니다!

### 해결책: 각자에게 전지 1장씩 따로 줘라!
- 사장님이 화가 각자에게 전지를 1장씩 따로 주었습니다(**64바이트 캐시 라인 패딩**).
- 도화지를 뺏길 일이 없어진 4명의 화가는 쉬지 않고 동시에 붓질을 하여, 작업 속도가 **정확히 4배(100% 병렬화)** 로 빨라졌습니다!

## 2. 컴퓨터 과학 원리: CPU 캐시 계층 구조와 MESI 프로토콜

### (1) 캐시 라인 (Cache Line)과 64바이트의 물리적 제약
현대 CPU(Intel, AMD, ARM)는 메모리(RAM)에서 데이터를 읽거나 쓸 때 바이트(1Byte) 단위로 작업하지 않습니다.
메모리 버스의 대역폭 효율을 위해 반드시 **64바이트(Cache Line)** 단위로 뭉텅이로 묶어서 L1/L2 캐시로 퍼 올립니다.

```text
[메모리 주소 (0 ~ 63 Byte)] ──► 캐시 라인 0 (Cache Line 0, 64 Bytes)
┌──────────────┬──────────────┬──────────────┬──────────────┬──────┐
│  count[0]    │  count[1]    │  count[2]    │  count[3]    │ ...  │
│  (8 Bytes)   │  (8 Bytes)   │  (8 Bytes)   │  (8 Bytes)   │      │
└──────────────┴──────────────┴──────────────┴──────────────┴──────┘
       ▲              ▲              ▲              ▲
       │              │              │              │
    Core 0         Core 1         Core 2         Core 3
 (Thread 0 수정) (Thread 1 수정) (Thread 2 수정) (Thread 3 수정)
```

- 개발자는 `count[0]`과 `count[1]`이 서로 다른 독립된 변수라고 생각합니다.
- 하지만 CPU 하드웨어의 눈에는 **둘 다 동일한 64바이트 상자(Line 0) 안에 담긴 데이터**일 뿐입니다!

---

### (2) MESI 캐시 일관성 프로토콜 (Cache Coherence Protocol)

여러 코어가 각자의 L1 캐시를 가질 때, 데이터의 정합성을 보장하기 위해 CPU 하드웨어는 버스 스누핑(Bus Snooping) 기반의 **MESI 프로토콜**을 작동시킵니다.
캐시 라인은 4가지 상태 중 하나를 갖습니다:

| 상태 | 의미 | 설명 |
| :---: | :--- | :--- |
| **M (Modified)** | 수정됨 (더티) | 이 코어만 최신 수정본을 독점하고 있음. 메모리와 불일치. |
| **E (Exclusive)** | 독점적 깨끗함 | 이 코어만 읽기 전용으로 독점하고 있음. 메모리와 일치. |
| **S (Shared)** | 공유됨 | 여러 코어가 이 캐시 라인을 동시에 읽기 전용으로 캐싱 중. |
| **I (Invalid)** | 무효화됨 | 데이터가 더 이상 유효하지 않음 (캐시 미스 발생). |

#### 쓰기 충돌과 무효화 폭풍 (Invalidation Storm):
1. **Core 0**이 `count[0]`을 수정하려고 합니다:
   - 캐시 버스에 **`BusUpgr` (또는 `BusRdX`)** 신호를 브로드캐스트합니다:  
     *"이 캐시 라인을 가진 놈들은 전부 데이터를 버려라!"*
   - 동일한 캐시 라인을 가지고 있던 **Core 1의 캐시 상태가 강제로 `I (Invalid)`로 강등**됩니다.
2. 1나노초 뒤, **Core 1**이 `count[1]`을 수정하려고 합니다:
   - 자신의 캐시가 `I (Invalid)` 상태이므로 **L1 캐시 미스**가 발생합니다!
   - Core 1은 파이프라인을 멈추고(Stall), Core 0에게 최신 캐시 라인을 메모리로 플러시하라고 요청한 뒤 다시 가져옵니다.
   - Core 1이 쓰기를 시도하면서 다시 `BusRdX`를 쏘아 **Core 0의 캐시 라인을 `I (Invalid)`로 파괴**합니다!
3. 이 악순환이 무한 반복되며 코어들은 연산은 못 하고 **L1 캐시 라인을 핑퐁하며 버스에서 수백 사이클씩 대기**합니다.

---

### (3) 레이턴시 비용 비교 (Cache Latency Impact)

| 연산 유형 | 소요 클럭 사이클 (Cycles) | 체감 속도 비유 |
| :--- | :---: | :---: |
| **L1 캐시 적중 (Cache Hit)** | **~1 ~ 4 사이클** | 눈 깜빡임 (0.5초) |
| **L2 캐시 적중** | **~12 사이클** | 커피 한 모금 (2초) |
| **L3 캐시 적중** | **~40 사이클** | 화장실 다녀옴 (1분) |
| **거짓 공유 캐시 미스 & 버스 무효화 (Bus Bouncing)** | **~100 ~ 300 사이클** | 100미터 달리기 (20분) |
| **메인 메모리(RAM) 접근** | **~200 ~ 400 사이클** | 해외여행 (반나절) |

거짓 공유가 발생하면 1사이클에 끝나야 할 덧셈 연산 1개가 **100~200사이클의 버스 대기 지연**으로 둔갑합니다.
스레드를 4개로 늘렸는데 성능이 10배~50배 추락하는 이유가 바로 여기에 있습니다!

## 3. 실무 해결책: 캐시 라인 패딩 (Cache Line Padding)

해결 방법은 물리적으로 변수들을 **서로 다른 64바이트 캐시 라인에 격리**시키는 것입니다.

### (1) 수동 패딩 (Padding Array)
```c
// [False Sharing 발생] - 64바이트 1개 라인에 인접
struct BadCounters {
    int64_t count0; // 8 bytes
    int64_t count1; // 8 bytes (동일 캐시 라인!)
};

// [캐시 라인 패딩 적용] - 64바이트 단위 격리
struct GoodCounters {
    int64_t count0;       // 8 bytes
    char pad0[56];        // 56 bytes 더미 패딩 -> 총 64 bytes (Line 0)
    int64_t count1;       // 8 bytes (Line 1로 분리!)
    char pad1[56];        // 56 bytes 더미 패딩 -> 총 64 bytes
};
```

### (2) 언어별 공식 어노테이션 및 정렬 지시자
- **C/C++**: `alignas(64) int64_t count;`
- **Java**: `@jdk.internal.vm.annotation.Contended` (JVM이 자동으로 128바이트 패딩 삽입)
- **Go**: 구조체 필드 사이에 `_ [56]byte` 패딩 배열 삽입
- **Rust**: `#[repr(align(64))]`

이 56바이트의 빈 공간(더미 데이터) 하나가, 수억 원짜리 64코어 서버의 병렬 처리 성능을 100배 끌어올리는 기적을 만듭니다!
