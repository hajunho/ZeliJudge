# 📚 기술 백서: 분산 카운터(Distributed Counter)와 샤디드 카운터

> **"RDBMS에서 가장 비싼 연산은 '단 하나의 행(Row)을 수만 명이 동시에 수정하려고 줄서는 것'입니다."**

초당 수만 명이 시청하는 라이브 스트리밍이나 대형 커뮤니티에서 '좋아요(하트)', '조회수', '티켓 잔여 수량'을 관리할 때 가장 흔히 저지르는 실수가 바로 **단일 컬럼 UPDATE (`UPDATE post SET count = count + 1 WHERE id = 1`)**입니다.

이 쿼리는 로직상 완벽해 보이지만, 대규모 트래픽이 몰리는 순간 데이터베이스를 즉사시키는 흉기로 돌변합니다.
이 백서에서는 행 락 경합(Row Lock Contention)의 원리와 인스타그램/유튜브가 이를 극복하기 위해 사용하는 **샤디드 카운터(Sharded Counter)**의 설계 원리를 다룹니다.

---

## 1. 현실 비유: 경기장 1개 회전문 vs 16개 분산 게이트

10만 명이 입장하는 월드컵 경기장을 상상해 보십시오:

### 참사: 출입문이 1개뿐인 경기장 (단일 카운터)
* 문지기 1명이 서서 관객이 올 때마다 회전문을 열고 계수기(Clicker)를 딸깍 누릅니다 (`UPDATE ... likes = likes + 1`).
* 1명이 문을 통과하는 동안 다음 사람은 문 앞에서 기다려야 합니다(**행 배타락: Row Exclusive Lock**).
* 10만 명이 문 하나 앞에 몰려들자 끔찍한 압사 사고가 발생하고, 30초 넘게 기다리다 지친 9만 5천 명은 "입장 포기(Lock Wait Timeout)"로 집에 돌아갑니다.
* 결과: 관중석에 앉은 사람은 10만 명인데 계수기에는 **고작 50명**만 찍히는 대참사가 발생합니다!

### 해결책: 16개의 분산 게이트 (샤디드 카운터)
* 입구에 16개의 독립된 게이트(`Gate 0` ~ `Gate 15`)를 뚫어놓습니다!
* 관객들은 주민번호 끝자리에 따라 16개 게이트로 흩어져 들어갑니다 ($slot = user\_id \pmod{16}$).
* 16명의 문지기가 동시에 각자의 계수기를 딸깍 누릅니다.
* 락 경합이 $\frac{1}{16}$로 줄어들어 10만 명이 병목 없이 순식간에 통과합니다!
* 전광판에 총 관객 수를 띄울 때는? **16개 게이트의 숫자를 더하기(`SUM`)**만 하면 끝납니다!

## 2. 단일 행 배타락(X-Lock)의 직렬화 병목

MySQL의 InnoDB나 PostgreSQL 등 현대 RDBMS는 원자적(Atomic) 데이터 수정을 보장하기 위해 대상 행(Row)에 **배타적 락(Exclusive Lock, X-Lock)**을 획득합니다.

```text
[Transaction 1] ---> [Lock Row #1] ---> [Read 42] ---> [Write 43] ---> [Commit & Release Lock]
                            | (락 점유 중 대기!)
[Transaction 2] ------------+---------------------------------------> [Lock Row #1 획득] ---> ...
[Transaction 3] ----------------------------------------------------> [대기열...]
...
[Transaction 10,000] ------------------------------------------------> [innodb_lock_wait_timeout 초과! 롤백!]
```

* **물리적 한계**: 아무리 빠른 최신 NVMe SSD와 CPU를 장착해도, 단일 행에 대한 락 획득 $\to$ 메모리 수정 $\to$ WAL 기록 $\to$ 락 해제 사이클은 초당 **1,000 ~ 2,000 TPS**가 한계입니다.
* **초당 1만 건 폭주 시 발생하는 3대 재앙**:
  1. **Lock Wait Timeout**: 대기열 뒤에 선 트랜잭션들이 50초(기본값) 타임아웃을 맞고 대량 롤백되어 500 에러 발생.
  2. **Deadlock 폭발**: 여러 트랜잭션이 다른 자원과 맞물리며 교착 상태를 일으켜 강제 롤백.
  3. **CPU 자멸 (Context Switching)**: 수천 개의 스레드가 락을 얻으려고 `Sleep`과 `Wakeup`을 반복하며 CPU 사용률이 100%로 치솟아 전체 DB가 마비됨.

## 3. 샤디드 카운터(Sharded Counter) 아키텍처

샤디드 카운터는 카운터 1개를 물리적으로 **$S$개의 독립된 행(슬롯)**으로 쪼개는 기술입니다.

### 1) 테이블 스키마 설계
```sql
CREATE TABLE post_like_shards (
    post_id BIGINT NOT NULL,
    slot_id INT NOT NULL,
    like_count BIGINT NOT NULL DEFAULT 0,
    PRIMARY KEY (post_id, slot_id)
);
```

### 2) 쓰기 분산 (Write: $O(1)$)
좋아요를 누를 때마다 $S$개의 슬롯 중 하나를 무작위 또는 사용자 ID 기반으로 선택하여 UPDATE합니다:
```sql
-- S = 16 슬롯인 경우:
UPDATE post_like_shards 
SET like_count = like_count + 1 
WHERE post_id = :post_id 
  AND slot_id = (:user_id % 16);
```
* 서로 다른 슬롯을 찌르는 트랜잭션들은 **서로 다른 행 락을 획득하므로 완벽하게 병렬(Parallel)로 실행**됩니다!
* 락 경합 확률이 정확히 $\frac{1}{S}$로 줄어들어, 쓰기 처리량이 $S$배로 확장(Scale-out)됩니다.

### 3) 읽기 집계 (Read: $O(S)$)
총 좋아요 수를 조회할 때는 16개 슬롯의 합계를 구합니다:
```sql
SELECT SUM(like_count) 
FROM post_like_shards 
WHERE post_id = :post_id;
```

## 4. 샤디드 카운터의 트레이드오프

모든 분산 아키텍처에는 대가가 따릅니다:

| 항목 | 단일 카운터 (Single) | 샤디드 카운터 (Sharded) |
|:---:|:---:|:---:|
| **쓰기(Write) 성능** | ❌ 초당 1~2천 건 병목, 락 경합 폭발 | ⭕ **$S$배 확장 (초당 수만~수십만 건 병렬 처리)** |
| **읽기(Read) 비용** | ⭕ 단 1개 행 조회 ($O(1)$) | ⚠️ $S$개 행 조회 후 합산 ($O(S)$) |
| **스토리지 용량** | ⭕ 게시글당 1개 행 | ⚠️ 게시글당 $S$개 행 |
| **적합한 사용처** | 조회가 많고 쓰기가 드문 일반 게시판 | **실시간 라이브, 핫딜, 인기 SNS의 핫스팟 카운터** |

> **실무 꿀팁:**  
> 읽기 비용 $O(S)$조차 부담스럽다면, 클라이언트는 **Redis 캐시**에서 읽고, 백그라운드 워커가 1초마다 DB의 $S$개 슬롯을 `SUM`하여 Redis에 캐싱하는 **CQRS / Write-Back 패턴**과 결합하면 쓰기와 읽기 성능을 모두 극한으로 끌어올릴 수 있습니다!
