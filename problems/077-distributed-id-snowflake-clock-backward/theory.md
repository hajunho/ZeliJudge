# CS 백서: 분산 유일 ID 생성과 트위터 스노우플레이크 (Twitter Snowflake ID & Clock Backward Defense)

> **"UUID를 기본키(PK)로 썼더니 데이터가 100만 건 넘어가자마자 DB 쓰기 속도가 10배 느려졌어요!  
> 게다가 서버 시계가 1초 뒤로 돌아갔더니 DB에서 Primary Key Duplicate 에러가 터져 주문이 유실됐습니다!"**  
> — 분산 마이크로서비스 환경에서 고유 ID를 설계하다 인덱스 단편화와 시계 역행으로 밤을 샌 데이터 엔지니어의 절규

## 1. 현실 비유: 전국 1,024개 지점 은행의 번호표 기계와 거꾸로 간 벽시계

전국에 1,024개 지점을 가진 초대형 은행이 있습니다.  
고객이 방문할 때마다 창구에서 겹치지 않는 고유한 번호표(ID)를 뽑아줘야 합니다.

```
[동네 구멍가게: Auto Increment]
  1번, 2번, 3번... ──▶ 지점이 1개일 땐 문제없지만, 전국 1024개 지점으로 늘어나면 지점마다 1번이 겹침!
                       중앙 본점 1곳에 전화해서 번호 받아오게 했더니 전화통에 불나서 전국 업무 마비 (SPOF)!

[미련한 무작위 외계어: UUID v4]
  "a8098c1a-f86e-11da-bd1a-00112444be1e" ──▶ 36자리 외계어 번호표!
  손님들이 번호표를 읽지도 못하고, 은행 장부(B-Tree 인덱스)에 무작위 위치로 끼워 넣느라 장부 책장이 찢어짐 (Page Split)!

[트위터 스노우플레이크: 64비트 스마트 압축 번호표]
  [현재시각 41비트] + [지점/창구번호 10비트] + [순번 12비트] = 64비트 정수 딱 1개!
  시간순으로 차곡차곡 증가하므로 장부 맨 끝에 0.001초 만에 순서대로 기록됨 (Append-only)!
```

1. **Auto Increment의 한계**:
   - 데이터베이스 1대일 때는 1씩 올라가는 정수 ID가 최고였습니다.
   - 하지만 서버가 수십 대, DB가 샤딩(Sharding)되는 분산 환경에서는 노드 간에 번호가 충돌하거나, 단 1대의 시퀀스 발급기에 트래픽이 몰려 전체가 다운됩니다 (Single Point of Failure).

2. **UUID v4의 재앙 (B-Tree 인덱스 단편화)**:
   - "충돌이 안 난다"는 말만 듣고 128비트 랜덤 문자열(UUID v4)을 데이터베이스 기본키(PK)로 썼습니다.
   - 관계형 데이터베이스의 Clustered Index(B-Tree)는 키 값의 순서대로 디스크에 데이터를 저장합니다.
   - 무작위 UUID가 들어오면, 정렬된 B-Tree의 한가운데를 비집고 들어가느라 기존 페이지를 둘로 쪼개는 **페이지 스플릿(Page Split)**이 끝없이 발생합니다.
   - 디스크 단편화가 극심해지고 쓰기 성능이 1/10 토막 납니다.

3. **트위터 스노우플레이크(Snowflake)의 우아함**:
   - 2010년 트위터(X) 엔지니어링 팀은 초당 수십만 건의 트윗에 순서가 있고(Monotonic), 겹치지 않는 ID를 부여하기 위해 64비트 정수 포맷을 고안했습니다:
     - **41비트 타임스탬프**: 밀리초 단위 시간 (약 69년간 사용 가능). 앞부분이 시간이므로 **자연스럽게 단조 증가**하여 B-Tree 맨 끝에 순차 삽입됩니다.
     - **10비트 노드 ID**: 데이터센터 ID(5비트) + 워커 노드 ID(5비트) = 총 1,024개 분산 서버에서 독립 발행.
     - **12비트 시퀀스 번호**: 같은 밀리초 안에 들어온 요청을 0부터 4095까지 순차 부여.
   - 중앙 서버 조율(Coordination)이나 락(Lock) 없이도 노드당 밀리초당 4,096개, 초당 409만 개의 ID를 초고속 발급합니다!

4. **비극의 반전: NTP 시계 역행(Clock Backward) 참사**:
   - 그런데 서버의 벽시계는 완벽하지 않습니다. 윤초(Leap Second)가 발생하거나, 분산 서버 시계를 맞춰주는 **NTP(Network Time Protocol)** 데몬이 서버 시계를 과거로 2ms 되돌렸습니다!
   - 순진한 스노우플레이크 생성기는 "어? 지금이 100ms네?" 하고 방금 2ms 전에 이미 발급했던 타임스탬프와 똑같은 ID를 다시 생성해 버립니다.
   - 동일한 Primary Key가 발급되어 데이터베이스에서 **중복 키 에러(Duplicate Key Error)**가 터지고 결제/주문 데이터가 유실됩니다.
   - **견고한 스노우플레이크(Robust Snowflake)**는 시계 역행을 감지했을 때 과거 시간으로 되돌아가지 않고, **가상 시간(Virtual Clock)을 유지**하거나 시계가 정상화될 때까지 안전하게 대기하여 단 1건의 충돌도 허용하지 않습니다!

## 2. 컴퓨터 과학 이론: 64비트 비트 구조와 시계 역행 방어

### 1) 64비트 비트 레이아웃
```
 1 bit   41 bits (Timestamp)            10 bits (Node)   12 bits (Sequence)
┌─────┬───────────────────────────────┬────────────────┬─────────────────┐
│  0  │  Delta Milliseconds from Epoch │  Machine Node  │  0 ~ 4095       │
└─────┴───────────────────────────────┴────────────────┴─────────────────┘
  ▲                   ▲                       ▲                 ▲
부호(양수)      기준시간 경과 ms             데이터센터+워커      동일 ms 내 순번
```

- **비트 연산 공식**:
  $$\text{ID} = ((\text{timestamp} - \text{EPOCH}) \ll 22) \mid (\text{node\_id} \ll 12) \mid \text{sequence}$$

### 2) 시계 역행(Clock Drift / Backward) 방어 알고리즘
- 분산 서버 환경에서 서버 시계는 네트워크 지연, 가상화 오버헤드, NTP 조정으로 인해 1~5ms 정도 뒤로 튀는 현상이 빈번합니다.
- **알고리즘 비교**:
  1. **Naive Engine**:
     - `current_time < last_timestamp`인 경우에도 그대로 ID를 생성합니다.
     - $\implies$ 과거에 이미 발급했던 ID가 재생성되어 **PK 중복 충돌** 발생!
  2. **Robust Engine (가상 시간 유지 & 모노토닉 보장)**:
     - 시계 역행 감지: $\Delta = \text{last\_timestamp} - \text{current\_time} > 0$
     - 역행 폭이 허용 한도($\le \text{MAX\_TOLERABLE\_MS}$) 이내인 경우:
       - 타임스탬프를 과거로 되돌리지 않고 `last_timestamp`를 그대로 유지합니다.
       - 시퀀스를 계속 증가시켜 동일 ms 버킷에서 안전하게 ID를 발급합니다.
       - 만약 시퀀스(4095)가 소진되면, `last_timestamp`를 인위적으로 1ms 전진시켜(가상 틱 전진) 단조 증가성을 영구히 유지합니다.
     - 결과: 시계가 아무리 요동쳐도 이전에 발급한 어떤 ID보다 무조건 큰 값이 생성되며 충돌률 0.00%를 보장합니다.
