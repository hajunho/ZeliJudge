# 데이터베이스 데드락과 대기 그래프 사이클 탐지 (Database Deadlock & Wait-For Graph Cycle Detection)

> **"분명히 트랜잭션 2개만 돌렸는데, 왜 쇼핑몰 DB 전체가 50초 동안 멈출까요?!"**  
> **"외나무다리의 두 마리 염소 비유 vs 대기 그래프(Wait-For Graph)와 희생자 롤백의 기적"**

---

## 1. 현실 세계 비유: 외나무다리의 두 고집불통 염소

폭이 좁아서 한 번에 한 마리만 지나갈 수 있는 긴 외나무다리가 있습니다.

```
[비극적인 상황: 교착 상태 (Deadlock)]
1. 염소 A는 왼쪽에서 출발하여 다리 가운데까지 걸어왔습니다 (자원 R1 점유).
2. 염소 B는 오른쪽에서 출발하여 다리 가운데까지 걸어왔습니다 (자원 R2 점유).
3. 이제 염소 A는 건너가기 위해 염소 B가 비켜주길 기다립니다 (자원 R2 대기).
4. 염소 B 역시 건너가기 위해 염소 A가 비켜주길 기다립니다 (자원 R1 대기).
5. 둘 다 고집이 세서 먼저 비켜줄 생각이 전혀 없습니다!
```

이 상태를 컴퓨터 과학에서는 **교착 상태(Deadlock, 데드락)**라고 부릅니다.  
다리 관리자가 없다면 두 염소는 탈진해 쓰러질 때까지(타임아웃 50초!) 버티고 서 있을 것이며, 다리 양쪽 끝에는 건너가려는 수백 마리의 양떼(DB 커넥션 풀)가 갇혀 다리 전체가 완전히 마비됩니다.

이때 지혜로운 다리 관리자가 나타나 대기 상태를 종이에 그려봅니다(대기 그래프):  
**"염소 A $\to$ 염소 B $\to$ 염소 A"** 라는 순환 고리(Cycle)를 발견하자마자, 관리자는 둘 중 짐이 가볍고 덜 걸어온 염소 B(희생자, Victim)를 번쩍 들어 뒤로 물립니다(Rollback).  
그 순간 염소 A가 무사히 다리를 건너고, 다리 전체의 통행이 0.01초 만에 정상화됩니다!

## 2. 코프만 4대 조건 (Coffman Conditions)

데드락은 다음 4가지 물리적 조건이 **동시에 성립할 때만** 발생합니다:

| 조건 | 설명 | 실무 DB 비유 |
| :--- | :--- | :--- |
| **1. 상호 배제 (Mutual Exclusion)** | 한 번에 한 프로세스(트랜잭션)만 자원을 점유할 수 있음. | 쓰기 배타락(X-Lock, `SELECT FOR UPDATE`) |
| **2. 점유와 대기 (Hold and Wait)** | 최소 하나의 자원을 쥔 채, 다른 자원을 얻기 위해 대기함. | 테이블 1의 락을 쥔 채, 테이블 2의 락을 요청 |
| **3. 비선점 (No Preemption)** | 다른 트랜잭션이 쥔 자원을 강제로 뺏을 수 없음. | 상대방 트랜잭션이 커밋/롤백하기 전엔 락 강탈 불가 |
| **4. 환형 대기 (Circular Wait)** | 프로세스들이 꼬리를 물고 원형으로 서로의 자원을 기다림. | $T_1 \to T_2 \to T_3 \to T_1$ (사이클 형성) |

## 3. 실무 데이터베이스에서의 데드락 참사

MySQL InnoDB, PostgreSQL 등 관계형 데이터베이스에서 가장 흔히 터지는 실무 사고입니다:

```sql
-- [트랜잭션 1: 주문 결제]
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 101; -- 101번 행 락 획득
-- (0.1초 뒤)
UPDATE products SET stock = stock - 1 WHERE id = 102; -- 102번 행 락 대기 (블로킹!)

-- [트랜잭션 2: 묶음 할인 이벤트]
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 102; -- 102번 행 락 획득
-- (0.1초 뒤)
UPDATE products SET stock = stock - 1 WHERE id = 101; -- 101번 행 락 대기 (블로킹!)
```

### 데드락 탐지기가 없을 때 일어나는 재앙 (Naive Timeout)
- 만약 DB 엔진이 단순히 타임아웃(`innodb_lock_wait_timeout = 50s`)에만 의존한다면, 두 트랜잭션은 50초 동안 아무것도 하지 못하고 멈춰 섭니다.
- 초당 수백 건의 주문이 유입되는 쇼핑몰이라면, 50초 동안 5,000개 이상의 DB 커넥션이 락 대기열에 묶여 커넥션 풀이 전멸(Starvation)하고 전사 500 에러가 터집니다.

## 4. 대기 그래프(Wait-For Graph)와 즉시 탐지 알고리즘

현대 엔터프라이즈 DB(InnoDB, Postgres 등)는 백그라운드 스레드로 **대기 그래프(Wait-For Graph)**를 유지합니다:

```
    ┌─────────────────────────────┐
    │                             ▼
[Tx 1 (id:101 점유)] ──대기──> [Tx 2 (id:102 점유)]
```

### 1) 그래프 구성
- **정점(Vertex)**: 현재 실행 중인 활성 트랜잭션 ($T_1, T_2, \dots$)
- **유향 간선(Directed Edge $T_a \to T_b$)**: $T_a$가 원하는 자원을 현재 $T_b$가 점유하고 있어 대기 중임을 의미.

### 2) 사이클 탐지 (Cycle Detection with DFS)
- 락 요청이 블로킹될 때마다 또는 주기적으로 DFS(깊이 우선 탐색)를 수행합니다.
- 탐색 경로 상에서 이미 방문 중인(`VISITING`) 노드를 다시 만나면 **환형 대기(사이클)**가 성립한 것입니다.

### 3) 희생자 선정 (Victim Selection)과 즉시 롤백
- 사이클이 발견되면 사이클에 연루된 트랜잭션 중 **"가장 롤백 비용이 적은(Undo log 양이 적거나 변경한 행 수가 적은) 트랜잭션"**을 희생자(Victim)로 지정합니다.
- 희생자 트랜잭션에 즉시 에러(`ERROR 1213: Deadlock found when trying to get lock; try restarting transaction`)를 던지며 강제 롤백합니다.
- 희생자가 쥐고 있던 락이 즉각 해제되므로, 살아남은 트랜잭션은 50초를 기다리지 않고 **단 1밀리초 만에 즉시 락을 얻고 통과**합니다!

## 5. 실무 데드락 방지 3대 수칙

1. **락 획득 순서의 정렬 (Consistent Lock Ordering)**:
   - 여러 행을 수정할 때는 반드시 Primary Key 순서(`ORDER BY id ASC`)로 정렬한 뒤 락을 획득하면 환형 대기(Circular Wait)가 물리적으로 불가능해집니다.
2. **트랜잭션 범위 최소화 (Keep Transactions Short)**:
   - 트랜잭션 내부에서 외부 API 호출이나 긴 비즈니스 로직을 배제하여 락을 쥐고 있는 시간 자체를 줄입니다.
3. **애플리케이션 계층의 재시도(Retry) 메커니즘**:
   - 데드락 에러(1213)는 버그라기보다는 동시성 시스템의 자연스러운 현상이므로, 애플리케이션에서 지수 백오프로 1~2회 재시도하도록 설계합니다.

> **"데드락을 무서워해서 타임아웃 뒤에 숨지 마라. 그래프를 그려 사이클을 끊어내는 것이 고성능 동시성의 비결이다."**  
> 이것이 관계형 데이터베이스 엔진이 초당 수만 건의 동시 트랜잭션을 처리하는 핵심 원리입니다.
