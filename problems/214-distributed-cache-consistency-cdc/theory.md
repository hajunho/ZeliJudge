# Problem 214 심층 이론: 분산 캐시 일관성(Distributed Cache Consistency)과 Cache-Aside 동시성 레이스 컨디션 및 CDC 기반 트랜잭셔널 무효화

## 1. 분산 환경에서 캐시와 데이터베이스 일관성의 본질적 난제

고성능 분산 백엔드 아키텍처에서 관계형 데이터베이스(MySQL, PostgreSQL)의 디스크 I/O 병목을 해소하고 읽기 처리량을 극대화하기 위해 인메모리 분산 캐시(Redis, Memcached)를 배치하는 것은 표준적인 엔지니어링 관례입니다.

이때 가장 널리 사용되는 디자인 패턴이 **Cache-Aside(지연 로딩 / Look-Aside)** 패턴입니다:
- **읽기(Read)**: 애플리케이션이 먼저 캐시를 확인하여 적중(HIT)하면 즉시 반환하고, 미적중(MISS)하면 데이터베이스를 조회한 뒤 캐시에 적재(Backfill)하고 반환합니다.
- **쓰기(Write)**: 애플리케이션이 데이터베이스에 데이터를 갱신하고, 캐시의 해당 키를 무효화(삭제)합니다.

그러나 관계형 데이터베이스와 분산 캐시는 **서로 다른 물리 시스템이며 분산 트랜잭션(2-Phase Commit, 2PC)으로 묶여있지 않습니다.**  
2PC를 적용하면 Redis의 밀리초 이하 초고속 응답성이 완전히 파괴되므로, 두 저장소는 필연적으로 **이중 쓰기(Dual-Write)** 문제와 동시성 레이스 컨디션(Race Condition)에 직면하게 됩니다.

## 2. Cache-Aside 패턴의 4대 동시성 레이스 컨디션과 장애 유형

### 2.1 "캐시를 먼저 삭제하고 DB를 갱신하면 안 되나요?" (선 삭제 후 갱신의 참사)
많은 초급 엔지니어들이 "캐시를 먼저 지우면 안전하겠지"라고 생각하지만, 이는 가장 치명적인 레이스 컨디션을 유발합니다:

```
Thread A (쓰기: 잔액 5000 -> 8000)             Thread B (동시 읽기)
┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
│ 1. redis.delete("balance") 성공!      │     │                                      │
│                                      │     │ 2. get("balance") -> Cache MISS!     │
│                                      │     │ 3. DB 조회 -> 옛날 값 5000 읽음!       │
│ 4. DB UPDATE balance = 8000 COMMIT!  │     │                                      │
│                                      │     │ 5. set("balance", 5000) 캐시 적재!   │
└──────────────────────────────────────┘     └──────────────────────────────────────┘
===> 결과: DB에는 8000원, Redis 캐시에는 옛날 값 5000원이 영구적으로 잔류!
```

### 2.2 "DB를 먼저 갱신하고 캐시를 삭제하면 완벽한가요?" (지연된 읽기 미스 레이스)
"DB 갱신 후 캐시 삭제"는 선 삭제보다 훨씬 안전하지만, 다음과 같은 타이밍에서 여전히 레이스 컨디션이 성립합니다:

```
Thread A (읽기 미스)                          Thread B (동시 쓰기)
┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
│ 1. Cache MISS 발생!                   │     │                                      │
│ 2. DB 조회 시작 (옛날 값 1000 읽음)    │     │                                      │
│    (네트워크/복제 지연으로 20ms 소요)   │     │                                      │
│                                      │     │ 3. DB UPDATE value = 2000 COMMIT!    │
│                                      │     │ 4. redis.delete("key") (이미 캐시 비어있음)│
│ 5. DB 조회 완료!                      │     │                                      │
│ 6. set("key", 1000) 캐시 적재!       │     │                                      │
└──────────────────────────────────────┘     └──────────────────────────────────────┘
===> 결과: Thread B가 캐시를 삭제했음에도 불구하고, Thread A가 나중에 도착하여
     옛날 값 1000을 캐시에 덮어써 버림! 캐시와 DB가 영구히 불일치!
```

### 2.3 이중 쓰기 네트워크 장애 (Dual-Write Network Failure)
- 1단계: 애플리케이션이 MySQL에 트랜잭션을 정상 커밋합니다.
- 2단계: 애플리케이션이 Redis에 `DEL key`를 요청하는 순간, 일시적인 네트워크 순단(Socket Timeout), Redis OOM, 또는 애플리케이션 Pod 강제 종료(OOMKill)가 발생합니다.
- 결과: DB는 변경되었으나 캐시는 삭제되지 않아, 만료 시간(TTL)이 다할 때까지 영구히 오염된 데이터가 서비스됩니다.

### 2.4 DB 복제 지연(Replication Lag)에 의한 캐시 재오염
Master DB에 쓰기가 완료되고 캐시를 삭제했더라도, 뒤이어 유입된 읽기 요청이 아직 동기화되지 않은 Slave(Replica) DB에서 옛날 데이터를 읽어 캐시에 다시 채워 넣는 복제 지연 참사가 발생합니다.

## 3. 지연된 이중 삭제 (Delayed Double Delete) 패턴

지연된 이중 삭제(Delayed Double Delete)는 위 레이스 컨디션을 완화하기 위해 고안된 실무적 기법입니다:

```
[지연된 이중 삭제 동작 흐름]

1. 1차 캐시 삭제: redis.delete(key)
2. 데이터베이스 갱신: db.update(key, new_value)
3. 비동기 지연 대기: Sleep (예: 500ms ~ 1000ms 또는 지연 큐 메시지 발송)
4. 2차 캐시 삭제: redis.delete(key)
```

### 3.1 해결 원리
- 1차 삭제와 DB 갱신 사이에 침투한 동시 읽기 요청이 DB의 옛날 데이터를 읽어 캐시에 채워 넣더라도(위 참사 1, 2번),
- 일정 시간(예: 500ms) 후에 실행되는 **2차 캐시 삭제가 그 오염된 캐시 엔트리를 다시 날려버립니다.**
- 따라서 최종적으로 캐시는 비워지며, 이후의 읽기 요청은 최신 DB 데이터를 조회하여 캐시를 올바르게 복구합니다(최종 일관성, Eventual Consistency).

### 3.2 지연된 이중 삭제의 한계와 구조적 취약점
1. **지연 시간(Sleep Window) 산정의 모호함**:
   - 지연 시간은 반드시 `(DB 읽기 지연시간 + 복제 지연시간 + 네트워크 RTT)`보다 커야 합니다.
   - 만약 DB 슬로우 쿼리나 락 대기로 인해 읽기가 1,500ms 걸렸는데 지연 삭제 타이머가 500ms로 설정되어 있다면, 2차 삭제가 먼저 끝나버려 **캐시가 다시 오염되는 현상을 막을 수 없습니다.**
2. **일시적 불일치 윈도우(Inconsistency Window)**:
   - 2차 삭제가 실행되기 전까지의 수백 밀리초 동안 사용자들은 옛날 데이터를 조회하게 됩니다.
3. **스레드 풀 고갈 및 비동기 복잡도**:
   - `Thread.sleep()`은 서버 스레드를 점유하므로 RabbitMQ/Redis 지연 큐 등 별도의 비동기 인프라를 구축해야 하는 운영 복잡도가 발생합니다.

## 4. 트랜잭셔널 CDC(Change Data Capture) 기반 캐시 무효화 (Enterprise Standard)

넷플릭스(Netflix), 메타(Meta), 우버(Uber), 카카오 등 대규모 트래픽을 다루는 글로벌 빅테크 기업들은 애플리케이션의 이중 쓰기를 완전히 제거하고, **데이터베이스의 트랜잭션 로그를 기반으로 캐시를 무효화하는 CDC 아키텍처**를 표준으로 사용합니다.

```
[트랜잭셔널 CDC 기반 캐시 무효화 아키텍처]

Client (쓰기)
   │
   ▼ 1. 오직 DB만 갱신! (Dual-Write 원천 제거!)
┌──────────────────────────┐
│ MySQL / PostgreSQL DB    │
│ (InnoDB Binlog / WAL 기록)│
└────────────┬─────────────┘
             │ 2. 트랜잭션 커밋 완료 후 로그 스트리밍 (Debezium / Canal)
             ▼
┌──────────────────────────┐
│ Apache Kafka Topic       │ ◄── 최소 1회 전송(At-least-once) 및 오프셋 순서 보장!
└────────────┬─────────────┘
             │ 3. 캐시 무효화 컨슈머 (Cache Invalidation Consumer)
             ▼
┌──────────────────────────┐
│ Redis Cluster            │ ◄── redis.delete(key) 실행!
└──────────────────────────┘
```

### 4.1 핵심 동작 메커니즘

1. **이중 쓰기(Dual-Write)의 원천 제거**:
   - 비즈니스 애플리케이션 코드는 Redis 삭제를 직접 호출하지 않습니다. 오직 DB 트랜잭션만 성공시키면 됩니다.
   - 따라서 네트워크 타임아웃이나 서버 크래시로 인한 캐시 삭제 누락 문제가 100% 소멸합니다.

2. **트랜잭션 커밋 보장 (Commit-Only Invalidation)**:
   - CDC(Debezium)는 데이터베이스에 **실제로 커밋된 트랜잭션의 Binlog만 읽어 들입니다.**
   - DB 트랜잭션이 롤백되었는데 캐시만 지워지거나 오염되는 참사가 원천 차단됩니다.

3. **버전/타임스탬프 기반 역주행 방어 (Version Gate / Stale Put Rejection)**:
   - 읽기 요청이 DB에서 데이터를 읽어올 때의 트랜잭션 버전(LSN / Version ID)을 함께 추적합니다.
   - 만약 읽기 미스 응답이 늦게 도착하여 캐시에 쓰려고 할 때, 이미 DB 버전이 그보다 앞서 있다면(`db_version > read_version`), **캐시 적재를 즉시 폐기(Discard)**합니다.
   - 이를 통해 아무리 느린 슬로우 쿼리가 뒤늦게 도착하더라도 캐시를 오염시킬 수 없습니다.

4. **카프카의 신뢰성 보장 (At-least-once & Retry)**:
   - Redis가 다운되거나 장애가 발생하더라도, 카프카 컨슈머는 오프셋을 커밋하지 않고 재시도(Retry)하여 Redis가 복구되는 즉시 누락 없이 캐시를 삭제합니다.

## 5. 3대 캐시 일관성 아키텍처 종합 비교

| 비교 항목 | 나이브 Cache-Aside (`NAIVE_CACHE_ASIDE_UPDATE`) | 지연된 이중 삭제 (`DELAYED_DOUBLE_DELETE`) | 트랜잭셔널 CDC 무효화 (`TRANSACTIONAL_CDC_CACHE_INVALIDATION`) |
| :--- | :--- | :--- | :--- |
| **캐시 삭제 주체** | 애플리케이션 비즈니스 코드 | 애플리케이션 비즈니스 코드 (2회) | 독립된 CDC 컨슈머 (Kafka 기반) |
| **이중 쓰기 실패 위험** | **매우 높음** (네트워크 에러 시 영구 불일치) | 완화됨 (2차 삭제가 보완) | **원천 차단** (Kafka 신뢰성 전송) |
| **동시 읽기 미스 오염** | **영구 오염 발생** | 최종 삭제로 해소 (단, 지연 윈도우 존재) | **버전 게이트로 완전 차단 (오염 0%)** |
| **DB 슬로우 쿼리 내성** | 취약 | **취약** (지연 시간 초과 시 재오염) | **완벽 내성** (버전 불일치 시 Discard) |
| **최종 일관성 보장** | 미보장 | 부분 보장 (타이머 의존) | **100% 보장** |
| **도입 복잡도** | 매우 단순 | 보통 (비동기 지연 큐 필요) | 높음 (Kafka + Debezium 인프라 필요) |
| **업계 채택 사례** | 소규모 단순 웹 서비스 | 중간 규모 백엔드 시스템 | 넷플릭스, 우버, 메타, 대형 핀테크/이커머스 |
