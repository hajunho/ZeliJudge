# [배경 이론] 42KB짜리 압축 파일 하나 풀었을 뿐인데 왜 디스크 1TB가 꽉 차서 서버가 뻗어요?!: 압축 폭탄(Zip Bomb / 42.zip)과 Zip Slip(경로 순회) 방어

## 1. 현실 비유: 마법의 텐트와 100만 평의 경기장

택배 기사님이 여러분의 원룸(서버 디스크)에 **손바닥만 한 상자(42KB ZIP 파일)** 하나를 배달했습니다.
상자 겉면에는 *"간편 원터치 텐트"*라고 적혀 있습니다.

- **방심한 순간 (Naive Extraction)**:
  - *"상자가 이렇게 쪼그마니까 아무 문제없겠지!"* 하고 원룸 방 한가운데서 상자 끈을 풀었습니다(`zipfile.extractall()`).
  - 그 순간 상자 안에서 텐트가 펴지기 시작하는데, 원룸 벽을 뚫고, 아파트를 부수고, 온 동네를 덮치더니 **서울월드컵경기장 100개 크기(4.5 페타바이트, 4,500,000 GB)**로 팽창합니다!
  - 원룸은 벽돌 하나 남기지 않고 완전히 으스러졌고(디스크 용량 100% 포화 `No space left on device`), 집주인(운영체제)은 질식사(OS 커널 패닉)했습니다!

이 엽기적인 마법 상자가 바로 컴퓨터 보안 역사상 가장 유명한 서비스 거부(DoS) 공격 무기인 **압축 폭탄 (Zip Bomb, 또는 Decompression Bomb)**입니다.

---

## 2. 왜 압축 폭탄이 가능할까? (DEFLATE 알고리즘의 맹점)

ZIP 파일이 사용하는 표준 압축 알고리즘인 **DEFLATE (LZ77 + 허프만 코딩)**는 "동일한 데이터의 반복"을 압축하는 데 기형적으로 특화되어 있습니다.

예를 들어, 숫자 `0`이 **10억 개(1GB)** 연속으로 적힌 파일을 압축한다고 가정해 봅시다:
- 원본: `00000000...` (1,000,000,000 바이트)
- DEFLATE 압축: *"0이라는 글자가 10억 번 반복됨"*이라는 메타데이터 단 몇 바이트로 압축!
- 결과: 단 **수 킬로바이트(KB)**짜리 압축 파일이 완성됩니다! 압축 비율이 무려 **1,000,000 : 1**에 달합니다.

### 전설의 `42.zip`
1996년에 제작된 전설적인 압축 폭탄 `42.zip`은 단 **42,374 바이트(약 42KB)**에 불과하지만:
- 16개의 중첩 ZIP 파일이 5단계 깊이(Recursive Nesting)로 들어있으며,
- 모든 압축을 완전히 해제하면 무려 **4.5 페타바이트 (4.5 PB = 4,500,000 GB)**의 데이터가 쏟아져 나옵니다.
- 아무리 테라바이트급 클라우드 서버라도 수 초 만에 디스크와 메모리가 100% 포화되어 즉사합니다.

## 3. 또 하나의 악마: Zip Slip (경로 순회 덮어쓰기 공격)

압축 파일 안에는 파일 내용뿐만 아니라 **파일의 상대 경로(Relative Path)**도 함께 저장됩니다.

해커가 악의적으로 파일명을 다음과 같이 조작하여 ZIP 파일을 만듭니다:
```text
../../../../../../../../etc/passwd
../../../../../../../../app/server.py
```

백엔드 개발자가 아무런 검증 없이 `archive.extractall('/tmp/uploads')`를 실행하면:
- 대상 파일이 `/tmp/uploads` 안에 풀리지 않고, `../`를 타고 올라가 **서버의 핵심 시스템 파일(`server.py`, `authorized_keys`)을 덮어써 버립니다!**
- 이로 인해 해커가 원격으로 서버를 장악(Remote Code Execution, RCE)할 수 있게 됩니다.

## 4. 안전한 압축 해제 5대 방어 수칙 (Secure Decompressor)

AI 코딩 도구가 짜준 `extractall()` 코드를 그대로 쓰면 백도어와 DoS 공격에 100% 무방비로 노출됩니다.  
실무에서는 다음 **5가지 방어선**을 반드시 구축해야 합니다:

1. **최대 압축 해제 누적 바이트 제한 (`max_uncompressed_bytes`)**:  
   스트리밍 방식으로 압축을 풀며 누적 해제 크기가 임계값(예: 100MB)을 넘어서는 순간 즉시 프로세스를 강제 중단합니다.
2. **압축 비율 검사 (`max_ratio = size / compressed_size`)**:  
   개별 파일의 압축 해제 비율이 비정상적으로 높으면(예: 100:1 또는 200:1 이상) 압축 폭탄으로 간주하고 즉각 거부합니다.
3. **최대 파일 개수 제한 (`max_file_count`)**:  
   아카이브 내에 지나치게 많은 수(예: 1,000개 이상)의 파일이 들어있는 경우 파일 시스템 inode 고갈을 방지하기 위해 차단합니다.
4. **중첩 압축 깊이 제한 (`max_depth`)**:  
   ZIP 파일 안에 또 다른 ZIP 파일이 중첩된 경우 최대 깊이(예: 2단계)를 제한하여 `42.zip` 식의 재귀 폭발을 차단합니다.
5. **Zip Slip 정규화 경로 검증 (Canonical Path Check)**:  
   추출될 최종 목적지 절대 경로가 허용된 대상 디렉터리(`target_dir`) 내부로 정확히 한정되는지(`os.path.commonpath`) 반드시 검사하여 상위 디렉터리 탈출을 원천 차단합니다.\n
