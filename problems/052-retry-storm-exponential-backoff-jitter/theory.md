# #052 재시도 폭풍(Retry Storm)과 지수 백오프 + 지터(Exponential Backoff with Jitter) 완벽 가이드

---

## 1. 개요: "서버가 잠깐 느려졌을 뿐인데 왜 영원히 안 켜지나요?"

마이크로서비스 아키텍처(MSA)를 운영하다 보면 누구나 한 번쯤 마주하는 공포스러운 시나리오가 있습니다:

> "DB에 1초 동안 슬로우 쿼리가 발생해서 일시적으로 503 에러가 떴습니다.  
> 그런데 1초 뒤에 슬로우 쿼리가 끝났음에도 불구하고,  
> **초당 1,000건이던 트래픽이 순식간에 5,000건, 10,000건으로 폭증**하면서  
> 서버 CPU가 100%에 갇혀 영원히 재기동되지 못하고 시스템 전체가 셧다운되었습니다."

원인은 바로 클라이언트와 마이크로서비스 간에 심어놓은 **"무지성 재시도(Naive Retry)"** 로직 때문입니다.  
서버가 힘들어해서 잠깐 숨을 고르려는 찰나에, 수천 대의 클라이언트가 **"어? 실패했네? 다시 해!"**라며  
동시에 재시도 패킷을 들이부어 서버를 물고문하듯 익사시키는 현상,  
이를 **재시도 폭풍(Retry Storm)** 또는 **트래픽 증폭(Traffic Amplification)**이라고 부릅니다.

---

## 2. 재시도 전략의 진화와 동기화 파동의 덫

```text
[1] 무지성 즉시 재시도 (Immediate Retry)
   요청 ──(실패)──> 즉시 재시도 ──(실패)──> 즉시 재시도 ──(실패)──> 영구 폭사!
   💥 문제점: 트래픽이 3~5배로 순간 증폭되어 장애 중인 서버를 즉시 사살함.

[2] 고정 간격 백오프 (Fixed Delay Backoff)
   t=10s : 1,000명 동시 실패!
   t=12s : 1,000명이 정확히 2초 뒤에 "동시에 다시 돌진!" ──> 💥 2차 폭발!
   t=14s : 남은 800명이 또 정확히 2초 뒤에 "동시에 다시 돌진!" ──> 💥 3차 폭발!
   💥 문제점: "동기화 파동(Synchronization Waves)" 발생!
             트래픽이 주기적인 거대 쓰나미(Spike) 형태로 서버를 공명 강타함.

[3] 지수 백오프 + 완전 지터 (Exponential Backoff with Full Jitter)
   t=10s : 1,000명 동시 실패!
   t=11s ~ 18s : 1,000명이 주사위를 굴려 각자 제각각의 시각(1s, 2.3s, 4.1s, 7.8s...)에 분산 재시도!
   ✅ 결과: 트래픽 스파이크가 완전히 사라지고 일정한 수평선(Flattening)으로 평탄화됨!
            서버 수용 한계(Capacity) 이하로 부드럽게 유입되어 100% 복구 성공!
```

### 왜 고정 백오프(Fixed Backoff)는 실패하는가? (공명과 동기화 현상)
물리학에서 군인들이 다리를 건널 때 발을 맞춰 행진하면 다리가 붕괴하듯(공명 현상),  
네트워크에서도 수천 대의 독립된 클라이언트가 **동일한 딜레이($\Delta t = 2초$)**를 가지면  
장애 시점의 충격파가 2초 주기로 계속 재생산됩니다.  
서버가 간신히 복구되어 기동되는 바로 그 시점에 2초 주기 쓰나미가 덮치면, 서버는 복구되자마자 즉시 다시 죽습니다.

## 3. AWS 공식 추천: 지수 백오프와 지터(Jitter) 알고리즘

AWS의 수석 아키텍트 Marc Brooker는 기념비적인 논문 **"Exponential Backoff And Jitter"**에서  
재시도 스파이크를 없애기 위한 3가지 지터 알고리즘을 제안했습니다.

### 1) No Jitter (순수 지수 백오프)
$$t_{sleep} = \min(cap, base \times 2^{attempt})$$
간격은 점점 넓어지지만, 동일 시점에 실패한 클라이언트들끼리는 여전히 동기화 스파이크가 발생합니다.

### 2) Full Jitter (완전 지터 - ⭐ 가장 권장됨!)
$$temp = \min(cap, base \times 2^{attempt})$$
$$t_{sleep} = \text{random}(0, temp)$$
- **원리**: 지수적으로 증가하는 상한선($temp$) 내에서 **완전 무작위 균등 분포**로 대기 시간을 선택합니다.
- **효과**:
  - 클라이언트들의 재시도 시점이 시간 축 전체로 가장 넓고 고르게 퍼집니다.
  - 서버의 순간 초당 요청 수(Peak RPS)를 가장 극적으로 낮춰줍니다.
  - AWS SDK(Java, Python Boto3, Go 등)의 기본 내장 재시도 알고리즘입니다.

### 3) Equal Jitter (동등 지터)
$$temp = \min(cap, base \times 2^{attempt})$$
$$t_{sleep} = \frac{temp}{2} + \text{random}(0, \frac{temp}{2})$$
최소 대기 시간 절반을 보장하면서 나머지 절반을 무작위로 흔듭니다.

### 4) Decorrelated Jitter (탈상관 지터)
이전 대기 시간($prev$)을 기반으로 다음 대기 시간을 결정합니다:
$$t_{sleep} = \min(cap, \text{random}(base, prev \times 3))$$

## 4. 실무 프로덕션 재시도 모범 사례 (Best Practices)

지터를 적용하는 것 외에도, 실무 분산 시스템에서는 다음과 같은 방어막을 반드시 함께 구축해야 합니다:

### 1) 재시도 예산 (Retry Budget - Envoy / Finagle 표준)
서버가 완전히 쓰러졌을 때는 지터를 적용해도 결국 재시도 요청이 서버를 압박합니다.  
따라서 클라이언트/프록시 레벨에서 **"재시도 요청은 전체 정상 트래픽의 10%를 넘을 수 없다"**는 룰을 강제합니다.
- 토큰 버킷 알고리즘을 사용하여, 정상 요청이 10번 성공할 때마다 재시도 토큰 1개를 충전합니다.
- 장애 상황에서 토큰이 고갈되면 재시도를 즉시 중단하고 클라이언트에 빠른 실패(Fail-Fast)를 반환합니다.

### 2) 멱등성(Idempotency) 보장 없는 요청은 재시도 금지!
- **안전한 재시도**: GET, HEAD, PUT, DELETE (멱등한 HTTP 메서드)
- **위험한 재시도**: `POST /api/v1/payments/charge` (결제 승인)
  - 네트워크 타임아웃이 났을 때 "서버에서 결제가 됐는데 응답만 안 온 건지", "결제 전에 끊긴 건지" 알 수 없습니다.
  - 멱등키(`Idempotency-Key: UUID`) 헤더 없이 무작정 재시도하면 고객 계좌에서 돈이 2번 출금되는 치명적 금융 사고가 발생합니다!

### 3) 서킷 브레이커(Circuit Breaker)와의 완벽한 앙상블
- 클라이언트 개별의 지수 백오프는 **"일시적이고 국소적인 순단(Transient Glitch)"**을 해결합니다.
- 만약 서버가 30초 이상 장기 장애에 돌입했다면, 백오프로 버티지 말고 **서킷 브레이커가 회로를 열어(OPEN) 0초 만에 요청을 차단**해야 합니다.
