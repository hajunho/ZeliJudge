# [배경 이론] SSD 믿고 DB 돌렸더니 6개월 만에 SSD가 사망하고 속도가 100배 느려졌어요?!: SSD 낸드 플래시 블록 지우기(Erase-Before-Write)와 쓰기 증폭(Write Amplification Factor, WAF) & 가비지 컬렉션(GC)

## 1. 현실 비유: 연필과 지우개의 물리적 비극

여러분에게 **공책 1권(SSD)**이 주어졌습니다. 그런데 이 공책에는 아주 고약한 마법의 물리 법칙이 걸려 있습니다.

- **글씨 쓰기(Program / Write)**:
  - 연필로 **한 줄(페이지, Page 4KB)**씩 아주 정밀하고 빠르게 쓸 수 있습니다.
- **글씨 지우기(Erase)**:
  - 하지만 지우개는 너무나 거대해서, 글씨를 한 줄만 지울 수 없습니다.
  - 지우개를 한 번 문지르면 **페이지 128줄이 묶인 책 한 권 전체(블록, Block 512KB~4MB)가 통째로 지워집니다!**
- **덮어쓰기(Overwrite)의 저주**:
  - 이미 글씨가 적힌 3번 줄을 고쳐 쓰고 싶습니다. 하지만 연필로 쓴 글씨 위에 겹쳐 쓸 수는 없습니다.
  - 지우개로 3번 줄만 싹 지울 수도 없습니다(책 128줄 전체가 지워지니까요!).
  - 결국 어떻게 해야 할까요?
    1. 3번 줄에 **빨간 펜으로 "이 내용은 무효(Invalid)!"**라고 빗금을 긋습니다.
    2. 공책의 **새 빈 줄(Free Page)**을 찾아 3번 줄의 새 내용을 새로 적습니다(Out-of-place Write).
    3. 공책에 빈 줄이 다 떨어지면?
       살아있는 멀쩡한 글씨들을 새 공책으로 일일이 베껴 적은 뒤(Copy), 헌 공책 전체를 지우개로 빡빡 문질러 지웁니다(Garbage Collection)!

이 기형적인 물리 법칙 때문에, 여러분은 **단 4KB짜리 글자 1개를 고쳤을 뿐인데, 공책 내부에서는 수십~수백 KB의 글자를 베껴 쓰고 지우느라** 손목(플래시 메모리 소자 수명)이 너덜너덜해집니다.

## 2. 왜 SSD에서는 덮어쓰기(In-place Overwrite)가 불가능한가?

HDD는 자성 입자를 회전시키며 그 자리에 즉시 새 데이터를 덮어쓸 수 있습니다.  
하지만 SSD의 **NAND 플래시 메모리**는 전자를 플로팅 게이트(Floating Gate)나 차지 트랩(Charge Trap)에 가두는 반도체 소자입니다.

```
[NAND Flash의 비대칭적 물리 단위]
┌────────────────────────────────────────────────────────┐
│ Block (소거 Erase 단위: 128~512 Pages, 약 2MB~8MB)     │
│  ┌──────────┬──────────┬──────────┬──────────┬───────┐ │
│  │ Page 0   │ Page 1   │ Page 2   │ Page 3   │ ...   │ │
│  │ (4KB)    │ (4KB)    │ (4KB)    │ (4KB)    │       │ │
│  └──────────┴──────────┴──────────┴──────────┴───────┘ │
│  ▲ 읽기/쓰기(Program) 단위                              │
└────────────────────────────────────────────────────────┘
▲ 지우기(Erase) 단위: 고전압으로 전자를 일괄 방출해야 함!
```

- **Program 단위 (Page, 4KB)**: 1을 0으로 바꾸는 전하 충전.
- **Erase 단위 (Block, 수 MB)**: 0을 1로 되돌리려면 수만 볼트의 고전압을 가해 블록 내 모든 셀의 전자를 한꺼번에 방출해야 함!
- 따라서 **"지우지 않고는 덮어쓸 수 없다(Erase-Before-Write)"**는 물리적 제약이 발생합니다.

## 3. FTL (Flash Translation Layer)과 가비지 컬렉션(GC)

SSD 컨트롤러 내부의 임베디드 OS인 **FTL**은 이 문제를 감추기 위해 마법을 부립니다:
1. 논리 주소(LPA)와 물리 주소(PPA) 매핑 테이블을 둡니다.
2. 데이터 수정 시 기존 물리 페이지를 `INVALID`로 마킹하고, 다른 빈 페이지에 씁니다(Out-of-place Update).
3. 빈 페이지가 바닥나면 **가비지 컬렉션(GC)**을 실행합니다:
   - 유효 페이지(Valid Page)가 적고 무효 페이지(Invalid Page)가 많은 희생양 블록(Victim Block)을 선정.
   - 희생양 블록의 유효 페이지들을 다른 빈 블록으로 복사(Relocation).
   - 희생양 블록 전체를 소거(Erase)하여 100% 빈 블록으로 재탄생!

## 4. 쓰기 증폭 (Write Amplification Factor, WAF)

가비지 컬렉션 과정에서 유효 페이지를 복사하느라, **호스트(사용자)가 쓴 데이터보다 실제 플래시 메모리에 기록된 물리적 데이터 양이 훨씬 더 많아지는 현상**을 **쓰기 증폭(Write Amplification)**이라고 합니다.

$$	ext{WAF} = rac{	ext{플래시 메모리에 실제로 쓰여진 총 데이터 양}}{	ext{호스트(OS/DB)가 쓰기를 요청한 데이터 양}}$$

- 가장 이상적인 상태: $	ext{WAF} = 1.0$ (불필요한 복사 쓰기 0)
- 무작위 쓰기(B-Tree)가 심한 최악의 상태: $	ext{WAF} = 3.0 \sim 10.0$ 이상!

### WAF가 폭증할 때 생기는 재앙
1. **SSD 속도 급락**: 쓰기 요청을 처리해야 할 SSD가 백그라운드에서 유효 페이지 복사와 블록 소거를 하느라 디스크 I/O 응답 시간이 수백 밀리초로 치솟습니다.
2. **SSD 조기 사망**: 낸드 플래시 셀은 소거 횟수(P/E Cycle, 보통 TLC 기준 1,000~3,000회)에 물리적 한계가 있습니다. WAF가 5배면 SSD의 물리적 수명이 1/5로 단축됩니다!

## 5. 실무에서의 해결책

1. **TRIM 명령어**:  
   OS에서 파일을 삭제할 때 SSD에 *"이 논리 페이지는 더 이상 안 쓰니 INVALID로 쳐도 돼!"*라고 알려주어, GC 시 불필요한 복사를 사전에 막아 WAF를 극적으로 낮춥니다.
2. **오버프로비저닝 (Over-Provisioning, OP)**:  
   전체 저장 공간의 10~28%를 유저에게 공개하지 않고 순수 GC 작업용 예비 블록으로 할당하여 GC 효율을 극대화합니다.
3. **순차 쓰기 아키텍처 (LSM-Tree / Kafka)**:  
   MySQL B-Tree처럼 무작위 위치를 덮어쓰지 않고, 무조건 끝에 덧붙이는(Append-Only) 순차 쓰기를 수행하여 블록 단위로 한꺼번에 무효화되도록 설계합니다.\n
