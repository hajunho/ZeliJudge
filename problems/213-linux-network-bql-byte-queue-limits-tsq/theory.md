# Problem 213 심층 이론: 리눅스 커널 BQL(Byte Queue Limits)과 TSQ(TCP Small Queues)를 통한 드라이버 링 버퍼블로트(Bufferbloat) 방어와 초저지연 네트워킹

## 1. 리눅스 커널 패킷 송신 경로의 계층 구조

리눅스 운영체제에서 애플리케이션이 `write()`, `send()`, `sendfile()` 등의 시스템 콜을 호출하여 데이터를 네트워크 카드로 보낼 때, 패킷은 여러 계층의 대기열(Queue)을 통과합니다:

```
[리눅스 네트워크 송신 스택의 3단계 큐잉 구조]

1. 소켓 계층 (Socket Layer)
   - struct sock: sk_write_queue (소켓 송신 버퍼)
   - TCP 슬라이딩 윈도우, 혼잡 제어(Cubic, BBR), 세그멘테이션(TSO/GSO)
   │
   ▼ [TSQ: net.ipv4.tcp_limit_output_bytes 로 Qdisc 유출량 통제!]
2. 트래픽 제어 계층 (Qdisc / Traffic Control)
   - pfifo_fast, fq(Fair Queueing), fq_codel, cake
   - 플로우별 큐 분리, 패킷 페이싱(Pacing), 스케줄링
   │
   ▼ [BQL: netdev_tx_sent_queue 로 하드웨어 링 유출량 통제!]
3. 드라이버 및 디바이스 계층 (NIC Driver & Hardware)
   - ndo_start_xmit() 드라이버 핸들러
   - 하드웨어 TX Ring Buffer (DMA 서술자/Descriptor 배열: 512 ~ 4096개)
   - 물리 계층(PHY) 및 전송 선로 (Wire)
```

각 계층은 고유한 버퍼를 가지고 있으며, 하위 계층으로 내려갈수록 **커널의 소프트웨어적 제어력(Reordering, Cancellation, Prioritization)**이 급격히 상실됩니다.

## 2. 드라이버 링 버퍼블로트(Bufferbloat)의 치명적 메커니즘

엔지니어들이 자주 저지르는 대표적인 실수는 패킷 드롭(`tx_dropped`)을 방지하겠다는 의도로 `ethtool` 명령을 통해 하드웨어 링 버퍼를 최대로 늘리는 것입니다:
```bash
$ sudo ethtool -G eth0 tx 4096 rx 4096
```

### 2.1 하드웨어 링 버퍼의 "블랙박스(Black Box)" 특성
1. **커널 제어권 상실**: 패킷(`struct sk_buff`)이 하드웨어 링 버퍼(TX Ring Descriptor)로 전달되어 물리 메모리 주소(DMA Address)가 매핑되는 순간, 커널 TCP 스택은 이 패킷을 취소하거나 회수하거나 우선순위를 바꿀 수 없습니다.
2. **엄격한 하드웨어 FIFO**: NIC 컨트롤러는 디스크립터 링에 등록된 순서대로 패킷을 선로로 방출합니다.
3. **거대한 잠재 지연시간**:
   - 디스크립터 4,096개에 표준 MTU(1500 바이트) 또는 TSO 세그먼트(최대 64KB)가 채워지면, 하드웨어 링에는 **수 메가바이트(MB)**의 데이터가 쌓이게 됩니다.
   - 100Mbps 선로에서 600KB의 패킷이 링에 적재될 경우, 이를 비워내는 데 무려 **$48\,\text{ms}$**가 소요됩니다.
   - 1Gbps 선로라 하더라도 1.2MB가 적재되면 **$10 \sim 20\,\text{ms}$**의 지연이 발생합니다.

### 2.2 두부 차단(Head-of-Line Blocking)과 대참사
동일한 호스트에서 대용량 데이터 전송(DB 백업, 동영상 업로드)이 진행되는 동안, 쿠버네티스의 파드 헬스체크(Liveness Probe HTTP 호출, 수백 바이트), SSH 키 입력, DNS 쿼리 등 초저지연이 생명인 작은 패킷들이 생성됩니다.
- 이 긴급 패킷들이 하드웨어 링 버퍼에 도달했을 때, 이미 링 버퍼 앞단에는 수백~수천 개의 벌크 패킷이 가득 차 있습니다.
- 결과적으로 100바이트짜리 헬스체크 패킷이 하드웨어 링에서 $40 \sim 50\,\text{ms}$ 동안 갇히게 되고, 헬스체크 타임아웃이 발생하여 멀쩡한 파드가 연쇄 재시작되는 참사가 벌어집니다.
- 또한, TCP ACK 패킷의 왕복 시간(RTT)이 수십 배로 왜곡되어 TCP 혼잡 제어 알고리즘이 비정상적으로 동작하게 됩니다.

## 3. BQL (Byte Queue Limits, Linux 3.3+)

2011년 톰 허버트(Tom Herbert)가 설계한 **BQL**은 네트워크 드라이버 계층에서 동작하며, 하드웨어 링 버퍼에 패킷이 과도하게 쌓이는 것을 방지하는 동적 피드백 알고리즘입니다.

```
[BQL의 동작 사이클]

           [ Qdisc 계층 ]
                 │
                 ▼ ndo_start_xmit()
  ┌───────────────────────────────┐
  │ netdev_tx_sent_queue(bytes)   │
  │ bytes_in_flight += bytes      │
  │ if (bytes_in_flight >= limit) │ ──► netif_stop_queue() (Qdisc 일시 정지!)
  └──────────────┬────────────────┘
                 │
                 ▼
  ┌───────────────────────────────┐
  │ NIC 하드웨어 TX Ring Buffer    │
  │ (DMA 전송 수행)               │
  └──────────────┬────────────────┘
                 │
                 ▼ (TX 인터럽트 완료 발생)
  ┌───────────────────────────────┐
  │ netdev_tx_completed_queue()  │
  │ bytes_in_flight -= bytes      │
  │ if (하드웨어 유휴/기아 발생)     │ ──► limit 증가 (선로 대역폭 포화 보장)
  │ elif (과도한 큐 잔류 발생)      │ ──► limit 축소 (버퍼블로트 즉시 억제)
  │ netif_wake_queue() 호출       │ ──► Qdisc 전송 재개
  └───────────────────────────────┘
```

### 3.1 왜 '패킷 수'가 아닌 '바이트 수(Bytes)'인가?
기존의 링 버퍼는 디스크립터 개수(예: 4096개)로 한도를 정했습니다. 그러나 패킷의 크기는 64바이트(ACK)부터 64,000바이트(TSO/GSO)까지 1,000배 이상 차이가 납니다.
- 4096개의 64바이트 패킷 = 256 KB
- 4096개의 64KB TSO 패킷 = 256 MB!
따라서 디스크립터 개수 기준은 물리적 전송 시간과 아무런 상관이 없습니다. BQL은 실제 선로를 통과하는 **물리 바이트(Bytes)** 단위로 대기열을 관리합니다.

### 3.2 BQL의 동적 한도 적응 원리
- **기아(Starvation) 감지**: 이전 인터럽트 주기 동안 하드웨어 링이 완전히 비어 전송 선로가 놀았을 경우, 처리량 손실을 막기 위해 `limit`을 1 MTU씩 증가시킵니다.
- **버퍼블로트(Over-buffering) 감지**: 인터럽트가 발생했는데도 하드웨어 링에 아직 전송되지 못한 잔여 바이트가 많다면, `limit`을 줄여 하드웨어 링 체류 시간을 항상 **$1\,\text{ms}$ 미만**으로 유지합니다.

## 4. TSQ (TCP Small Queues, Linux 3.6+)

BQL의 도입으로 하드웨어 드라이버 링의 크기는 수 킬로바이트(약 3KB~6KB)로 줄어들었습니다. 그러나 커널 개발팀은 또 다른 문제를 발견했습니다:
> **"하드웨어 링을 줄였더니, 소켓이 뿜어내는 수백 개의 패킷들이 Qdisc 계층으로 고스란히 밀려 올라가 Qdisc를 팽창시켰다!"**

이를 해결하기 위해 에릭 뒤마제(Eric Dumazet)는 TCP 계층에 **TSQ(TCP Small Queues)**를 도입했습니다.

```
[TSQ의 소켓 레벨 페이싱과 추월 보장 원리]

Bulk TCP Socket                                     Interactive Socket (SSH / Probe)
┌────────────────────────┐                          ┌────────────────────────┐
│ sk_write_queue (500KB) │                          │ sk_write_queue (100B)  │
│ sk_wmem_alloc: 3,000B  │                          │ sk_wmem_alloc: 0B      │
└───────────┬────────────┘                          └───────────┬────────────┘
            │                                                   │
   [TSQ 검사: 3000 >= 3000]                                     │ [TSQ 통과: 100 < 3000]
   ==> TSQ_THROTTLED!                                          │ ==> 즉시 Qdisc로 유출!
   (소켓 전송 잠금! 버퍼에 머무름)                                    │
                                                                ▼
                                                    [Linux FQ Qdisc]
                                                    대화형 패킷이 벌크를 즉시 추월!
                                                                │
                                                                ▼
                                                    [BQL 하드웨어 TX 링 (3KB)]
                                                    0.14 ms 만에 선로 방출!
```

### 4.1 소켓 메모리 추적 (`sk_wmem_alloc`)
각 TCP 소켓은 자신이 Qdisc 및 드라이버 계층으로 내려보낸 바이트 합계를 `sk->sk_wmem_alloc`에 기록합니다.

### 4.2 TSQ 제한 임계값 (`net.ipv4.tcp_limit_output_bytes`)
- 기본값: 대략 `2 * MSS` (약 3,000 ~ 4,000 바이트) 또는 최대 128KB.
- 만약 `sk_wmem_alloc >= tcp_limit_output_bytes`라면, TCP 스택은 해당 소켓의 `tcp_write_xmit()`을 즉시 중단하고 소켓에 `TSQ_THROTTLED` 플래그를 세팅합니다.
- 패킷들은 소켓의 유저/커널 송신 버퍼(`sk_write_queue`)에 머무르게 됩니다.

### 4.3 인터럽트 기반 언스로틀링 (Unthrottling)
1. 하드웨어 NIC가 패킷 전송을 완료하면 TX 인터럽트가 발생합니다.
2. 커널이 `kfree_skb()`를 실행하며 메모리를 해제합니다.
3. 소켓의 `sk_wmem_alloc`이 차감되고, 임계값 밑으로 내려가면 TSQ 완료 핸들러(`tcp_tsq_handler` / `tsq_tasklet`)가 소켓을 깨워 다음 1~2개 패킷을 Qdisc로 밀어 넣습니다.

## 5. BQL과 TSQ의 유기적 결합이 선사하는 가치

1. **소켓 버퍼 체류의 결정적 이점**:
   패킷이 하부 계층(Qdisc나 드라이버 링)으로 내려가지 않고 소켓 버퍼에 머물러 있으면, TCP 스택은 최신 ACK 정보와 혼잡 신호를 반영하여 패킷을 재스케줄링하거나 드롭할 수 있습니다.
2. **FQ(Fair Queueing)와의 시너지**:
   벌크 플로우가 하위 계층에 단 2개의 패킷만 올려두고 있으므로, 갑자기 유입된 SSH나 쿠버네티스 헬스체크 패킷은 수천 개의 큐를 기다릴 필요 없이 즉시 Qdisc 선두로 배치되어 $0.1 \sim 0.2\,\text{ms}$ 만에 선로로 나갑니다.
3. **선로 대역폭 100% 포화 유지**:
   BQL이 인터럽트 간격 동안 선로가 절대 굶지 않도록 최소한의 바이트를 정밀하게 공급하므로, 처리량 저하 없이 지연시간을 99% 단축시킵니다.
