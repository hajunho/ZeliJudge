# [CS-105] 대용량 파일 읽었더니 메모리가 0B인데 디스크에서 바로 읽혀요?!: Linux 가상 메모리 파일 매핑 `mmap`과 페이지 캐시 Zero-Copy

> **"선생님! 10GB짜리 데이터베이스 인덱스 파일을 열었는데, 프로세스 메모리(RSS)가 0MB로 찍혀요! 그런데 파일 안의 데이터를 배열처럼 즉시 읽고 쓸 수 있는 게 말이 되나요?!"**
> 
> 검색 엔진 백엔드를 개발하는 주니어 엔지니어 태우는 10GB짜리 역색인(Inverted Index) 파일을 메모리로 불러와 초고속 검색을 구현하려 했습니다.
> 기존 방식대로 `file.read()`를 호출하자마자 서버 메모리가 순식간에 10GB 폭증하더니 리눅스 OOM-Killer에 의해 프로세스가 즉사(Exit Code 137)당했습니다.
> 
> 멘토는 혀를 차며 코드 한 줄을 수정해 주었습니다:
> `mapped_data = mmap.mmap(file.fileno(), 0, access=mmap.ACCESS_READ)`
> 
> 그러자 기적이 일어났습니다! 프로세스의 물리 메모리 사용량(RSS)은 0KB로 유지되는데, `mapped_data[102400]`처럼 마치 메모리 배열을 다루듯 파일의 모든 위치를 0.001ms 만에 읽어낼 수 있었습니다.
> 
> "메모리에 올리지도 않았는데 어떻게 메모리 포인터로 읽히죠?!"  
> 시니어 아키텍트는 화이트보드에 가상 메모리와 페이지 테이블을 그리며 말했습니다.
> "태우 씨, 도서관에서 1만 페이지짜리 백과사전을 볼 때 책 전체를 가방에 다 쑤셔 넣고(Read 버퍼) 다니나요? 아니면 서가 번호표(가상 메모리 주소)만 쥐고 있다가, 읽고 싶은 페이지만 쏙 펼쳐서 책상(RAM)에 올려놓고(Page Fault) 보나요?"

## 1. 기존 `read()`/`write()` 시스템 콜의 치명적 한계: 이중 복사(Double Copy)

전통적인 파일 I/O 방식인 `read()`와 `write()`는 CPU와 메모리에 심각한 오버헤드를 발생시킵니다.

```
[디스크 (Storage)]
       │
       │  (1) DMA Copy: 디스크 -> 커널 페이지 캐시
       ▼
[커널 페이지 캐시 (Kernel Page Cache)]
       │
       │  (2) CPU Copy: 커널 버퍼 -> 유저 프로세스 힙 버퍼 (치명적 병목!)
       ▼
[유저 프로세스 메모리 (User Space Buffer)]
```

1. **이중 복사 (Double Copy)**: 데이터가 RAM 안에 커널 페이지 캐시와 유저 프로세스 힙 메모리라는 두 개의 서로 다른 공간에 중복 저장됩니다. 10GB 파일을 읽으면 메모리 20GB가 낭비됩니다!
2. **빈번한 컨텍스트 스위칭**: 파일의 일부분을 읽을 때마다 유저 모드와 커널 모드를 오가는 시스템 콜 인터럽트가 발생하여 수천 번의 CPU 사이클이 낭비됩니다.
3. **가비지 컬렉션(GC) 폭탄**: 수 기가바이트의 바이트 배열이 힙(Heap)에 생성되면서 JVM이나 언어 런타임의 GC STW(Stop-The-World)를 유발합니다.

## 2. 가상 메모리 파일 매핑: `mmap`의 마법

`mmap` (Memory Map)은 파일을 메모리 버퍼로 '복사'해 오는 것이 아니라, **파일의 디스크 블록을 프로세스의 가상 주소 공간(Virtual Address Space)에 1:1로 직접 연결(Mapping)**해 주는 운영체제 커널 기능입니다.

```
[유저 프로세스 가상 주소 공간 (Virtual Address Space)]
   0x1000 ~ 0x1FFF ───────┐ (가상 페이지 매핑: 초기 물리 RAM 할당 0B!)
   0x2000 ~ 0x2FFF ───┐   │
                      │   │
                      │   │ Page Fault 발생 시 4KB 페이지만 직접 로드
                      ▼   ▼
        [물리 RAM / 커널 페이지 캐시 (Page Cache)]
                      │   ▲
                      │   │ DMA Transfer (Zero-Copy)
                      ▼   │
               [하드디스크 / SSD 파일]
```

### 1) 지연 할당 (Lazy Allocation)과 0B 메모리의 비밀
- `mmap()` 시스템 콜을 호출하는 그 순간에는 물리 메모리(RAM)를 단 1바이트도 할당하지 않습니다.
- 단지 커널의 가상 메모리 영역(VMA, Virtual Memory Area)에 "이 주소 범위는 디스크 파일의 이 오프셋에 대응된다"는 장부(메타데이터)만 기록합니다.
- 따라서 100GB 파일을 `mmap` 해도 프로세스의 실제 물리 메모리 점유량(RSS, Resident Set Size)은 **0B**입니다!

### 2) 요구 페이징 (Demand Paging)과 페이지 폴트 (Page Fault)
- 프로그램이 `mapped_data[4096]`을 읽으려고 특정 메모리 주소에 접근합니다.
- CPU 내부의 **MMU(Memory Management Unit)**가 페이지 테이블을 조회하지만, 해당 가상 페이지에 아직 물리 RAM 프레임이 연결되어 있지 않음을 발견합니다.
- CPU는 즉시 **페이지 폴트(Page Fault, x86 인터럽트 #14)** 예외를 발생시키고 제어권을 커널로 넘깁니다.
- 커널의 페이지 폴트 핸들러는 해당 파일 오프셋의 **정확히 4KB(1개 페이지)** 크기만 디스크에서 읽어 커널 페이지 캐시(물리 RAM)에 로드하고 페이지 테이블을 연결합니다.
- 이후 동일한 페이지에 대한 모든 읽기/쓰기는 커널을 거치지 않고 **하드웨어 MMU를 통해 물리 RAM에서 0.0001ms 만에 직접 실행(Zero-Copy Cache Hit)**됩니다!

### 3) 더티 페이지 (Dirty Page)와 `msync`
- 가상 메모리에 값을 쓰면(`mapped_data[10] = 'A'`), 해당 페이지만 **더티(Dirty, 변경됨)** 상태로 표시됩니다.
- 프로세스는 디스크 쓰기 완료를 기다리지 않고 메모리에 쓴 뒤 즉시 다음 작업을 진행합니다.
- 변경된 내용은 백그라운드에서 리눅스 커널의 플러셔 스레드(`flusher/pdflush`)가 비동기로 디스크에 반영하거나, 사용자가 명시적으로 `msync(MS_SYNC)`를 호출하여 즉시 동기화할 수 있습니다.

## 3. 실무 아키텍처 활용 사례

1. **Apache Kafka의 초고속 I/O**:
   - 카프카 브로커는 메시지 로그 파일을 `mmap` 및 `sendfile`을 통해 다룹니다.
   - JVM 힙 메모리를 전혀 쓰지 않고 OS 커널의 페이지 캐시만을 사용하므로, GC 부담이 0이며 OS의 메모리 관리 및 프리페치(Read-ahead) 혜택을 100% 누립니다.
2. **Lucene / Elasticsearch (`mmapfs`)**:
   - 수십~수백 기가바이트의 역색인 파일(`.doc`, `.tim`, `.tip`)을 `mmap`으로 매핑하여, JVM 힙을 작게 유지하면서도 OS 레벨에서 핫(Hot) 인덱스를 RAM 캐시에 상주시켜 밀리초 단위 검색을 달성합니다.
3. **SQLite & RocksDB**:
   - 데이터베이스 파일과 B+Tree 노드를 `mmap` 주소로 직접 포인팅하여 불필요한 시스템 콜 오버헤드와 버퍼 복사를 제거합니다.
