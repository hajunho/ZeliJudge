# 깊이 있는 컴퓨터 과학: 리눅스 epoll I/O 멀티플렉싱, 엣지 트리거와 썬더링 허드 방어

## 1. 리눅스 I/O 멀티플렉싱 진화: select/poll에서 epoll로

초기 유닉스의 `select()`와 `poll()`은 파일 디스크립터(FD) 집합 전체를 사용자 공간에서 커널로 복사하고, 매 호출마다 $O(N)$으로 모든 소켓을 선형 탐색해야 했습니다.
리눅스 2.6에 도입된 **`epoll`**은 다음 세 가지 인터페이스로 $O(1)$ 이벤트 통지를 달성했습니다:
1. `epoll_create1()`: 커널 내부 레드-블랙 트리(RB-Tree)와 준비 큐(Ready List)를 갖는 epoll 인스턴스 생성.
2. `epoll_ctl()`: 모니터링할 소켓 등록/수정/삭제. 커널 콜백 함수(`ep_poll_callback()`)가 등록되어 소켓에 데이터가 도착하면 즉시 준비 큐에 삽입.
3. `epoll_wait()`: 준비 큐에 쌓인 활성 FD만 $O(K)$ ($K$는 실제 준비된 소켓 수) 속도로 반환.

## 2. Level-Triggered (LT) vs Edge-Triggered (ET)

### 2.1 Level-Triggered (수평 트리거, 기본값)
- 소켓 수신 버퍼에 읽지 않은 데이터가 남아있는 한, `epoll_wait()`을 호출할 때마다 해당 FD가 계속해서 활성 상태로 반환됩니다.
- 프로그래밍이 직관적이며 버그 발생 위험이 낮습니다.
- **단점**: 이미 처리 중인 소켓이 `epoll_wait()`에 반복 노출되므로, 멀티스레드 환경에서 불필요한 이벤트 통지와 시스템 호출 오버헤드가 발생합니다.

### 2.2 Edge-Triggered (엣지 트리거, `EPOLLET`)
- 수신 버퍼에 새로운 데이터가 도착하여 상태 전이(State Transition: 0바이트 -> 양수 바이트)가 일어나는 그 '순간(Edge)'에만 단 1회 이벤트를 발생시킵니다.
- `epoll_wait()`이 동일 FD를 중복 보고하지 않으므로 커널-유저 공간 컨텍스트 스위칭이 최소화됩니다.
- **치명적 위험 (Socket Starvation / Data Trapped)**:
  - 애플리케이션이 `read()` 시스템 콜을 호출하여 수신 버퍼의 일부만 읽고 반환할 경우, 버퍼에 남은 잔여 데이터는 새 패킷이 들어올 때까지 절대 통지되지 않습니다.
  - 클라이언트는 응답을 기다리고, 서버는 epoll 이벤트가 안 와서 멈춰 있는 **교착 상태(Deadlock/Hang)**가 발생합니다.
- **해결 원칙**: 반드시 소켓을 비블로킹(`O_NONBLOCK`)으로 설정하고, `read()`가 `EAGAIN` 또는 `EWOULDBLOCK` 에러를 반환할 때까지 루프를 돌며 버퍼를 비워야 합니다.

## 3. 썬더링 허드 (Thundering Herd) 문제와 `EPOLLEXCLUSIVE`

### 3.1 썬더링 허드 현상
Nginx나 Netty와 같은 고성능 서버는 멀티코어 확장을 위해 여러 개의 워커 프로세스/스레드를 띄웁니다.
- 모든 워커가 단일 리슨 소켓(`listen_fd`)을 감시할 때, 신규 클라이언트 연결 1개가 들어오면 대기 중인 모든 워커가 한꺼번에 깨어납니다.
- 단 하나의 워커만이 `accept()`에 성공하고, 나머지 모든 워커는 허탈하게 다시 수면 상태로 돌아갑니다.
- 이는 막대한 CPU 컨텍스트 스위칭 낭비와 캐시 라인 무효화(Cache Invalidation)를 초래합니다.

### 3.2 리눅스 커널의 해결책 진화
1. **`SO_REUSEPORT` (Linux 3.9+)**:
   - 각 워커 프로세스가 동일 포트에 대해 독립적인 리슨 소켓을 바인드하고, 커널이 수신 SYN 패킷의 4-튜플 해시를 기반으로 워커에 연결을 분배.
2. **`EPOLLEXCLUSIVE` (Linux 4.5+)**:
   - `epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev)` 등록 시 `EPOLLEXCLUSIVE` 플래그를 설정.
   - 신규 연결 이벤트가 발생했을 때 커널의 웨이크업 큐(`autoremove_wake_function`)에서 **단 1개의 대기 스레드만 배타적으로 깨움**.
   - 썬더링 허드로 인한 CPU 오버헤드를 0으로 제거.

## 4. 바운디드 드레인 (Bounded Drain)과 공평 스케줄링 (Fair Yield)

`EAGAIN`이 나올 때까지 무한 루프로 `read()`를 호출하면 엣지 트리거의 데이터 트랩은 막을 수 있지만, 대용량 트래픽을 쏟아붓는 특정 소켓이 워커 스레드의 CPU 시간을 독점하여 다른 수천 개의 소켓이 응답 지연을 겪는 **소켓 간 기아(Inter-Socket Starvation)**가 발생합니다.

- **바운디드 드레인 패턴**:
  - 루프 1회당 최대 읽기 바운드(예: 64KB)를 설정.
  - 바운드를 초과하면 읽기를 잠시 중단하고, 해당 소켓을 사용자 공간의 대기 큐에 등록한 뒤 다음 소켓으로 공평하게 양보.
  - 이로써 엣지 트리거의 고성능과 C100K 다중 연결의 공평성(Fairness)을 동시에 보장할 수 있습니다.
