# 리눅스 ext4 파일 시스템과 JBD2 저널링 아키텍처 심층 분석

## 1. 개요: 파일 시스템 크래시 일관성(Crash Consistency) 문제

현대 운영체제에서 파일에 데이터를 추가(Append)하거나 수정하는 간단한 `write()` 시스템 콜은 물리 디스크 레벨에서 여러 개의 서로 다른 블록을 갱신하는 복합 작업입니다:
1. **데이터 블록 (Data Block)**: 유저가 쓴 실제 바이트.
2. **아이노드 (Inode)**: 파일 크기(`i_size`), 블록 포인터/익스텐트 트리(Extent Tree), 수정 시각(`mtime`).
3. **데이터 블록 비트맵 (Data Block Bitmap)**: 어떤 디스크 블록이 새로 점유되었는지 추적.
4. **아이노드 비트맵 (Inode Bitmap)**: 신규 파일인 경우 아이노드 할당 여부.

```
[User write("Hello")]
        │
        ├──> [Data Block]            (Disk Sector 1048576)
        ├──> [Inode Block]           (Disk Sector 2048)
        └──> [Block Bitmap]          (Disk Sector 4096)
```

이 블록들은 물리 디스크의 서로 다른 섹터에 위치하므로, 하드웨어적으로 동시에 원자적(Atomic)으로 쓰일 수 없습니다.  
만약 블록 1만 디스크에 쓰이고 블록 2, 3이 쓰이기 직전에 **서버 전원이 차단(Power Cut / Kernel Panic)**된다면 파일 시스템은 심각한 불일치(Inconsistency) 상태에 빠집니다.

### 과거의 해결책과 한계: `fsck`
초기 파일 시스템(ext2)은 재부팅 시 디스크 전체를 순회하며 메타데이터를 검증하는 `fsck`(File System Consistency Check)를 실행했습니다.  
그러나 수 테라바이트~수십 테라바이트의 현대 스토리지 환경에서 디스크 전체를 스캔하는 것은 **수 시간에서 수십 시간이 소요**되어 엔터프라이즈 서비스의 무중단 가용성을 완전히 파괴합니다.

## 2. JBD2(Journaling Block Device 2)와 트랜잭션 수명 주기

이 문제를 해결하기 위해 데이터베이스의 WAL(Write-Ahead Logging) 기법을 운영체제 커널에 도입한 것이 **ext3/ext4의 저널링 서브시스템인 JBD2**입니다.  
JBD2는 디스크의 전용 원형 버퍼 공간(Journal Area)을 두고, 모든 변경 사항을 트랜잭션 단위로 묶어 관리합니다:

```
+-------------------------------------------------------------------------+
|                        JBD2 Transaction Lifecycle                       |
|                                                                         |
|  1. Running     : 유저의 쓰기 요청을 현재 메모리 트랜잭션에 지속 누적     |
|  2. Committing  : 저널 디스크 영역에 디스크립터 블록 및 메타데이터 기록 |
|  3. Flushed     : 하드웨어 배리어(FLUSH CACHE)로 물리 플래시 강제       |
|  4. Checkpoint  : 저널에 기록된 내용을 실제 파일 시스템 블록으로 덮어씀 |
+-------------------------------------------------------------------------+
```

정전이 발생하더라도 재부팅 시 저널 영역의 몇 메가바이트만 순차 스캔하여 커밋된 트랜잭션만 재생(Replay)하므로, **단 1~2초 만에 완벽한 크래시 복구가 완료**됩니다.

## 3. ext4의 3대 저널 모드 심층 비교

리눅스 커널 ext4는 성능과 안전성의 상충 관계(Trade-off)에 따라 3가지 저널 모드를 제공합니다.

### 3.1 `data=writeback` (최대 성능, 치명적 무결성 결함)
- **작동 원리**: 오직 메타데이터(아이노드, 비트맵)만 저널에 기록하며, 실제 데이터 블록이 디스크에 기록되는 순서는 전혀 통제하지 않습니다.
- **치명적 참사: 쓰레기 데이터 누출 (Stale Data Exposure)**:
  1. 유저가 파일에 8KB 데이터를 씁니다.
  2. JBD2가 파일 크기가 8KB 늘어났다는 메타데이터를 저널에 커밋합니다.
  3. 실제 데이터 블록이 디스크 플래터/NAND 플래시에 쓰이기 전에 정전이 발생합니다.
  4. 재부팅 후 저널 리플레이가 실행되면 파일 크기는 8KB로 정상 확장되어 있습니다.
  5. 그러나 실제 블록에는 유저 데이터가 쓰이지 않았으므로, **디스크의 해당 섹터에 이전에 저장되어 있던 이전 삭제 파일의 조각(다른 사용자의 개인정보, 암호화 키, 세션 토큰) 또는 널 바이트(`0x00`)가 그대로 노출**됩니다.
  6. 이는 심각한 데이터 파손뿐만 아니라 치명적인 보안 정보 유출(Security Vulnerability)로 이어집니다.

### 3.2 `data=journal` (최대 안전, 극심한 성능 병목)
- **작동 원리**: 메타데이터뿐만 아니라 **유저의 실제 데이터 블록까지 전부 저널 영역에 먼저 기록**합니다.
  - 1차 쓰기: 유저 데이터 + 메타데이터 -> 저널 영역에 기록.
  - 2차 쓰기: 저널 커밋 후 실제 파일 시스템 블록으로 데이터 복사.
- **치명적 병목: 2배 쓰기 증폭 (2.0x Write Amplification)**:
  - 10GB 데이터를 쓰면 디스크에는 총 20GB의 물리 쓰기가 발생합니다.
  - 디스크 I/O 대역폭과 IOPS가 정확히 절반으로 깎이며, 플래시 메모리 기반 NVMe/SATA SSD의 수명(TBW)이 2배 빠른 속도로 닳아 없어집니다.

### 3.3 `data=ordered` (리눅스 커널 기본값, 황금률의 아키텍처)
- **작동 원리**: 메타데이터만 저널에 기록하지만, **엄격한 순서 제어(Ordering Invariant)**를 강제합니다:
  $$\text{Flush User Data Blocks to Disk} \longrightarrow \text{Hardware Barrier} \longrightarrow \text{Commit Metadata to Journal}$$
- **구원 원리**:
  1. 유저 데이터 블록이 메인 스토리지 디스크에 물리적으로 기록 완료될 때까지, JBD2는 해당 트랜잭션의 커밋 블록(Commit Record)을 저널에 절대 쓰지 않습니다.
  2. 데이터 플러시 전 정전 발생 시: 저널에 커밋 블록이 없으므로 재부팅 시 트랜잭션이 전량 폐기(Rollback)되어 파일 크기는 늘어나지 않습니다 (쓰레기 데이터 노출 원천 차단).
  3. 저널 커밋 후 정전 발생 시: 데이터 블록이 이미 물리 디스크에 기록되었음이 100% 보장되므로 메타데이터 리플레이 후 완벽한 데이터가 보존됩니다.
  4. 데이터는 단 1번만 디스크에 쓰이므로 **데이터 쓰기 증폭률은 정확히 1.0x**를 유지합니다.

## 4. 디스크 캐시와 하드웨어 플러시 배리어 (`barrier=1`)

현대 HDD와 SSD는 자체 온보드 휘발성 DRAM 캐시(보통 512MB~2GB)를 내장하고 있습니다.  
운영체제가 디스크에 쓰기 명령을 보내면, 드라이브 컨트롤러는 실제 자기 디스크나 NAND 셀에 쓰기 전에 캐시에만 넣고 "쓰기 완료(Write Complete)"를 보고할 수 있습니다(Write-back 캐시).

```
[OS Kernel] --- Write Data ---> [SSD DRAM Cache] --- (아직 플래시 안 됨!)
[OS Kernel] --- Write Commit -> [SSD DRAM Cache] --- (정전 발생! 캐시 휘발!)
```

만약 하드웨어 플러시 배리어가 꺼져 있다면(`nobarrier`), 컨트롤러가 메타데이터 커밋 블록을 데이터 블록보다 먼저 물리 플래시에 써버릴 수 있어 `data=ordered` 모드에서도 순서가 역전되어 데이터가 깨질 수 있습니다.  
따라서 리눅스 커널은 `barrier=1` 옵션을 통해 SCSI `SYNCHRONIZE CACHE` 또는 ATA `FLUSH CACHE EXT` 명령을 전송하여, 온보드 캐시의 데이터가 물리 미디어에 안전하게 기록되었음을 확인한 후 다음 단계로 진행합니다.

## 5. ext4 3대 저널 모드 종합 비교

| 비교 항목 | `data=writeback` | `data=ordered` (기본값) | `data=journal` |
|---|---|---|---|
| **저널 기록 대상** | 메타데이터만 | **메타데이터만 (순서 보장)** | 데이터 + 메타데이터 |
| **데이터 쓰기 증폭률** | **1.0x** | **1.0x** | **2.0x (심각한 병목)** |
| **정전 시 데이터 안전성** | **쓰레기 데이터/널 노출 위험** | **100% 무결점 (이전 상태 or 완성)** | 100% 무결점 |
| **디스크 I/O 처리량** | 최상 | **우수 (최적 균형)** | 최하 (50% 이하 추락) |
| **SSD 수명 영향** | 정상 | **정상** | **수명 2배 단축** |
| **추천 사용처** | 임시 캐시 디스크 (`/tmp`) | **데이터베이스, 결제 원장, 일반 OS** | 극도의 무결성 요구 특수 환경 |
