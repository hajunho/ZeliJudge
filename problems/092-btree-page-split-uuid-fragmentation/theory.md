# CS 이론 백서: B+Tree 리프 페이지 분할(Page Split)과 UUID v4 무작위 단편화(Internal Fragmentation)

> **"보안에 좋대서 무심코 `UUID.randomUUID()`를 DB 기본키(PK)로 박았다가, 데이터 100만 건 넘어가면서 서비스 전체가 멈췄습니다."**  
> 데이터베이스 성능 문제의 80%는 쿼리 튜닝이 아니라 **디스크 물리 저장 구조와 인덱스 정렬의 불일치**에서 발생합니다.

---

## 1. 현실 비유: 도서관 서가와 무작위 번호 책의 비극

당신이 국립 중앙도서관의 사서라고 상상해 보세요. 도서관 서가의 각 칸(페이지, Page)에는 **책이 딱 4권**만 꽂힐 수 있습니다. 그리고 책들은 반드시 **'청구기호(Primary Key)' 순서대로 엄격하게 정렬**되어 있어야 합니다.

```
[서가 0] : [ 1번 책 | 2번 책 | 3번 책 | 4번 책 ]  (가득 참!)
```

### 시나리오 A: 연도순 책 (Sequential Insert - Auto-Increment ID / UUID v7)
매일 새로 출판되는 책들의 번호가 `5번, 6번, 7번, 8번...` 순서대로 들어옵니다.
- 사서는 이미 꽉 찬 [서가 0]을 건드릴 필요가 없습니다.
- 옆에 새로운 **[서가 1]**을 하나 가져다 놓고, 그곳에 5번, 6번, 7번, 8번 책을 차례대로 꽂기만 하면 됩니다(**Right-Append Optimization**).
- **결과**: 모든 서가가 빈틈없이 100% 꽉 찹니다(**Fill Factor ~ 100%**). 사서는 항상 맨 마지막 서가만 만지므로 발걸음(디스크 I/O)이 거의 필요 없습니다.

---

### 시나리오 B: 무작위 번호 책 (Random Insert - UUID v4)
이번에는 보안을 챙긴다며 책 번호가 완전 무작위(예: `23번, 871번, 2번, 45번, 12번...`)로 들어옵니다.
- 이미 `[ 10번 | 30번 | 50번 | 70번 ]`으로 꽉 차 있는 서가 한가운데에 `35번 책`이 도착했습니다.
- 청구기호 순서를 지키려면 **30번과 50번 사이에 책을 억지로 쑤셔 넣어야** 합니다!
- 하지만 서가에는 빈 공간이 단 1밀리미터도 없습니다.
- 사서는 눈물을 머금고 서가의 책 절반(50번, 70번)을 빼내어, 새로 가져온 빈 서가로 옮겨 담습니다(**50/50 Page Split**).
```
[서가 0] : [ 10번 | 30번 | 35번 | (빈칸) ]   --> 채움률 75%
[서가 1] : [ 50번 | 70번 | (빈칸) | (빈칸) ]  --> 채움률 50%
```
- 다음 날, 또 무작위로 책이 들어오면 서가 이곳저곳을 쪼개느라 모든 서가가 2~3권씩만 꽂힌 채 절반이 텅텅 비어버립니다(**내부 단편화 40~50%**).
- 도서관 건물은 서가로 꽉 차서 터져나가고, 사서는 1권 꽂으려고 도서관 동관 서관을 미친 듯이 뛰어다니다가 쓰러집니다(**랜덤 디스크 I/O 폭증**)!

## 2. RDBMS 스토리지 엔진의 물리적 현실: Clustered Index와 B+Tree

MySQL InnoDB, SQL Server, Oracle 등 대부분의 관계형 데이터베이스는 **클러스터드 인덱스(Clustered Index)** 구조를 사용합니다.

```
       [ B+Tree 루트 노드 ]
           /         \
   [ 브랜치 노드 ]    [ 브랜치 노드 ]
     /        \        /        \
 [Leaf 0] <-> [Leaf 1] <-> [Leaf 2]  <-- 실제 데이터 행(Row)이 저장된 16KB 디스크 페이지
```

1. **테이블 데이터 자체가 곧 B+Tree의 잎(Leaf) 노드**:
   - 테이블의 실제 모든 레코드(모든 컬럼 데이터)는 별도의 파일이 아니라, **Primary Key 순서대로 정렬된 B+Tree 리프 페이지 안에 물리적으로 저장**됩니다.
   - InnoDB의 기본 리프 페이지 크기는 **16KB**입니다.
2. **리프 페이지 간 양방향 연결 리스트(Doubly Linked List)**:
   - 각 16KB 페이지는 이전 페이지(`prev`)와 다음 페이지(`next`)의 물리 디스크 포인터를 가지고 있어, 정렬 순회(`ORDER BY pk`, `BETWEEN A AND B`)를 초고속으로 수행합니다.

## 3. 페이지 분할(Page Split)이 일으키는 3대 대참사

### 1) 쓰기 증폭(Write Amplification)과 디스크 I/O 폭풍
- 순차 키 삽입 시에는 맨 마지막 페이지만 수정되므로 16KB 페이지 하나가 꽉 찰 때까지 메모리에서만 작업합니다.
- 하지만 무작위 키(UUID v4) 삽입 시, **16KB 페이지가 꽉 찰 때마다 분할(Split)**이 일어납니다.
  1. 새 16KB 페이지 물리 할당
  2. 기존 페이지 레코드의 50%를 새 페이지로 메모리 복사
  3. B+Tree 부모 브랜치 노드에 새로운 라우팅 키 등록 (부모 노드도 꽉 차면 연쇄 분할!)
  4. 양방향 링크 포인터 갱신 및 두 페이지 모두 Dirty 마킹 후 디스크 플러시
- 레코드 1건 INSERT하려다 수십 KB의 디스크 쓰기가 연쇄 폭발합니다.

### 2) 내부 단편화(Internal Fragmentation)와 스토리지 낭비
- B+Tree는 균형을 유지하기 위해 50/50 분할을 기본으로 합니다.
- 무작위 키 인입 시 정상적인 정상상태(Steady State)에서의 **평균 페이지 채움률(Fill Factor)은 약 67%** (최악의 경우 50%)로 급락합니다.
- 즉, **디스크 용량의 33% ~ 50%가 허공(Unused Space)**으로 낭비됩니다. 순차 키로 100GB면 충분할 테이블이 UUID v4를 쓰면 150GB ~ 200GB로 부풀어 오릅니다.

### 3) 버퍼 풀(Buffer Pool) 쓰래싱과 캐시 미스(Cache Miss)
- DB 서버의 RAM에는 자주 쓰이는 페이지를 올려두는 **버퍼 풀(InnoDB Buffer Pool)**이 있습니다.
- 순차 삽입 시에는 방금 쓴 맨 끝 페이지만 계속 접근하므로 **버퍼 풀 캐시 적중률(Hit Rate)이 99.9%**에 달합니다.
- 반면 무작위 UUID v4는 B+Tree 전체에 걸쳐 균등하게 흩어져 있는 수십만 개의 리프 페이지 중 아무 곳이나 무작위로 찌릅니다.
- 버퍼 풀(RAM)에 없는 페이지를 디스크에서 읽어오고(`Buffer Pool Miss`), 다른 페이지를 디스크로 내쫓는(`Eviction`) 과정이 무한 반복되며 **디스크 I/O 100% 병목(Thrashing)**에 걸립니다.

## 4. UUID v4 vs Sequential UUID (UUID v7, TSID) 비교

| 구분 | UUID v4 (Random) | UUID v7 (Time-Ordered) / TSID | BIGINT AUTO_INCREMENT |
| :--- | :--- | :--- | :--- |
| **생성 방식** | 122비트 완전 무작위 난수 | 48비트 밀리초 타임스탬프 + 74비트 난수 | 1씩 단조 증가하는 64비트 정수 |
| **정렬 특성** | **전혀 정렬되지 않음 (Chaos)** | **시간 순서대로 완벽 정렬 (Monotonic)** | **완벽 순차 정렬** |
| **B+Tree 삽입 위치** | 전체 리프 페이지에 무작위 침투 | **항상 B+Tree 맨 오른쪽 끝에 추가** | **항상 맨 오른쪽 끝에 추가** |
| **페이지 분할 빈도** | **극도로 빈번 (50/50 Split)** | **거의 없음 (Right-Append Split)** | **거의 없음 (Right-Append Split)** |
| **페이지 채움률** | **50% ~ 67% (심각한 단편화)** | **95% ~ 99% (초고밀도 저장)** | **~ 100% (최고 효율)** |
| **보안/유추 방지** | 유추 불가 (완벽) | 타임스탬프 유추 가능하나 뒤 74비트 난수로 충돌/추측 방어 | 다음 ID 유추 쉬움 (IDOR 취약점 위험) |
| **분산 환경 생성** | DB 중앙 락 없이 각 서버에서 즉시 생성 | DB 중앙 락 없이 각 서버에서 즉시 생성 | DB 단일 락 필요 (분산 샤딩 시 병목) |

> **실무 결론**:  
> "보안과 분산 생성을 위해 UUID가 필요하다면, 절대로 무작위 **UUID v4**를 클러스터드 인덱스 PK로 쓰지 마라!  
> 반드시 2024년 공식 표준이 된 **RFC 9562 UUID v7**이나 **TSID (Time-Sorted Unique Identifier)**를 사용하라!"

## 5. 이미 망가진 B+Tree를 치유하는 법: OPTIMIZE TABLE (Defragmentation)

이미 UUID v4로 인해 수십 GB의 빈틈(단편화)이 생긴 테이블은 어떻게 고칠까요?
- MySQL: `OPTIMIZE TABLE my_table;` 또는 `ALTER TABLE my_table ENGINE=InnoDB;`
- PostgreSQL: `VACUUM FULL my_table;` 또는 `REINDEX TABLE my_table;`
- **동작 원리**:
  1. 기존의 단편화된 B+Tree 리프 페이지들을 순서대로 쭉 읽습니다.
  2. 새로운 임시 파일에 레코드들을 **100% 가득 찬 연속 페이지**로 빈틈없이 차곡차곡 재패킹(Re-pack)합니다.
  3. 작업 완료 후 기존 파일을 날리고 새 파일로 스왑합니다.
  4. **효과**: 테이블 디스크 크기가 30~50% 줄어들고, 연속된 디스크 블록 배치로 Full Scan 및 Range Scan 속도가 수배 빨라집니다.
  5. **주의점**: 테이블 전체를 다시 쓰는 작업이므로 막대한 디스크 공간(여유 공간 100% 필요)과 I/O 부하가 발생합니다.
