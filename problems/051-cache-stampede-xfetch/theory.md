# #051 캐시 스탬피드(Cache Stampede)와 분산 락 vs stale-while-revalidate 완벽 가이드

---

## 1. 개요: "캐시를 달았는데 왜 트래픽이 몰릴 때 DB가 죽나요?"

Redis나 Memcached 같은 인메모리 캐시를 도입하는 가장 큰 목적은 **"비싼 DB 쿼리를 줄여서 대규모 트래픽을 감당하는 것"**입니다.  
많은 개발자들이 가장 흔하게 사용하는 패턴은 **Look-Aside (Cache-Aside)** 패턴입니다:

```python
# 전형적인 초보자의 Cache-Aside 코드
data = redis.get("hot_deal_product_123")
if data is None:
    # 🚨 캐시가 만료된 그 순간, 동시 접속자 1만 명이 일제히 여기로 진입합니다!
    data = db.select_expensive_product_info(123)
    redis.setex("hot_deal_product_123", 600, data)
return data
```

평소에는 캐시 히트율이 99%를 기록하며 DB CPU 사용률도 1~2%로 매우 평화롭습니다.  
하지만 **캐시 유효시간(TTL 10분)이 딱 끝나는 바로 그 1밀리초의 순간**,  
초당 5,000건의 트래픽이 들어온다면 어떤 일이 벌어질까요?

5,000개의 모든 웹 서버 스레드가 동시에 `data is None`을 확인하고,  
**동일한 무거운 쿼리를 들고 DB로 동시에 돌진**합니다.  
이 현상을 **캐시 스탬피드(Cache Stampede)**, **썬더링 허드(Thundering Herd)**, 또는 **도그파일 효과(Dogpile Effect)**라고 부릅니다.

---

## 2. 캐시 스탬피드가 전사 DB를 파괴하는 메커니즘 (Cascading Failure)

```text
[동시 요청 5,000건]
       │
       ▼ (캐시 TTL 만료 순간!)
[Redis: MISS!] 
       │
       ├─────────────────────────────────────────┐
       ▼                                         ▼
[DB 커넥션 풀 100개 즉시 고갈]           [4,900개 스레드 커넥션 락 대기]
       │                                         │
       ▼ (슬로우 쿼리 발생, 0.05초 -> 5초로 지연)  ▼
[뒤이어 들어온 2만 건 요청도 전부 DB로 돌진] ──> [DB CPU 100% & 메모리 OOM]
                                                 │
                                                 ▼
                                        [🔥 전사 서비스 마비]
```

1. **커넥션 풀(HikariCP) 고갈**: 웹 서버마다 할당된 DB 커넥션 20~30개가 0.01초 만에 꽉 찹니다.
2. **슬로우 쿼리 유발**: 동일한 쿼리 수백 개가 DB 엔진의 버퍼 풀과 CPU를 장악하여, 평소 50ms 걸리던 쿼리가 5초, 10초로 급격히 느려집니다.
3. **연쇄 폭사(Cascading Collapse)**: 쿼리가 끝나야 캐시를 채우는데, 쿼리가 10초 동안 안 끝나니  
   그 10초 동안 새로 들어온 수만 건의 요청도 죄다 DB로 직행하여 DB 프로세스가 완전히 기절(Crash)합니다.

## 3. 해결책 1: Mutex 분산 락 (Single-Flight 패턴)

가장 직관적인 해결책은 **"캐시가 없더라도, DB에는 딱 1명만 들어가게 하자"**입니다.

```text
[동시 요청 5,000건] ──> 캐시 MISS
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
       [1번 요청: 락 획득!]           [2~5,000번 요청: 락 획득 실패]
               │                             │
       (DB 조회 & 캐시 갱신)               (잠시 대기 후 캐시 읽기)
               │                             │
               └──────────────┬──────────────┘
                              ▼
                      [모두 최신 캐시 수신!]
```

### 1) Go 언어의 `singleflight.Group`
Go 표준 라이브러리 준공식 패키지에는 이 문제를 풀기 위한 예술적인 도구가 내장되어 있습니다:
```go
var g singleflight.Group

v, err, _ := g.Do(key, func() (interface{}, error) {
    // 5,000개의 고루틴이 동시에 호출해도,
    // 이 함수는 오직 최초의 1개 고루틴만 실행합니다!
    return db.QueryExpensiveData(key)
})
```
나머지 4,999개의 고루틴은 채널(Channel)을 통해 첫 번째 고루틴이 가져온 결과를 그대로 공유받습니다.

### 2) Spring Boot의 `@Cacheable(sync = true)`
스프링 캐시 추상화에서도 동기화 옵션을 제공합니다:
```java
@Cacheable(value = "popularProducts", key = "#id", sync = true)
public ProductDto getProduct(Long id) {
    // 다중 스레드가 접근해도 단일 스레드만 실행되도록 락이 걸립니다.
    return productRepository.findById(id).orElseThrow();
}
```

### 3) Redis 분산 락 (`SETNX`)
여러 대의 분산 서버 간에 캐시 스탬피드를 막으려면 Redis의 원자적 분산 락을 사용합니다:
- `SET lock:product:123 "token" NX PX 5000`
- 락을 획득한 서버만 DB를 조회하고 캐시를 갱신한 뒤 락을 해제합니다.
- 락을 획득하지 못한 다른 서버들은 50ms 대기 후 다시 Redis 캐시를 조회합니다.

## 4. 해결책 2: stale-while-revalidate (RFC 5861)

Mutex 락은 DB 쿼리 수를 1개로 줄여주지만,  
**"락을 획득한 1번 요청이 DB 쿼리를 마칠 때까지(50ms~100ms) 대기하던 손님들은 여전히 레이턴시 지연을 겪는다"**는 단점이 있습니다.

초당 수만 건의 웹 트래픽에서는 p99 지연시간(Tail Latency Spike)을 없애는 것이 핵심입니다.  
이때 사용하는 궁극의 무기가 바로 **`stale-while-revalidate`**입니다.

```text
[요청 도착] ──> 캐시 TTL 만료 확인!
                    │
       ┌────────────┴────────────┐
       ▼                         ▼
 [사용자 응답]            [백그라운드 비동기 작업]
 "방금 만료된 과거 데이터       "조용히 DB에 가서 새 데이터를
  (Stale Data)라도 1ms 만에     가져와 다음 손님을 위해
  즉시 받아 가세요!"           캐시를 갱신해 둘게!"
```

- **동작 원리**:
  - 캐시가 만료되었더라도, 완전히 쓰레기 데이터가 아니라면 **기존 데이터를 즉시 1ms 만에 반환**합니다.
  - 동시에 백그라운드 워커(Worker) 스레드가 비동기로 DB 쿼리를 실행하여 조용히 캐시를 최신화합니다.
- **장점**:
  - 사용자 체감 지연시간이 항상 **1ms**로 일정하게 유지됩니다 (스파이크 0건!).
  - Cloudflare, Fastly 같은 글로벌 CDN과 최신 프론트엔드 프레임워크(Next.js SWR, TanStack Query)가 기본 채택하고 있습니다.

## 5. 해결책 3: 확률적 조기 만료 (XFetch 알고리즘)

ACM 논문(Vattani et al., 2015)에서 제안되고 Redis 공식 레퍼런스 아키텍처에 등재된 최첨단 수학적 기법입니다.

### 핵심 아이디어: "캐시가 0초로 떨어지는 순간 자체를 없애자!"
캐시 유효시간이 아직 남아있더라도, **남은 시간이 줄어들수록 확률적으로 백그라운드 갱신을 트리거**합니다:

$$\Delta - \beta \times \delta \times \ln(rand()) \le 0$$

- $\Delta$: 캐시 만료까지 남은 시간 ($expire\_time - current\_time$)
- $\delta$: 해당 쿼리를 수행하는 데 소요되는 계산 비용 ($compute\_time$)
- $\beta$: 갱신 적극성 가중치 ($\beta > 0$, 기본값 1.0)
- $rand()$: $(0, 1]$ 사이의 균등 난수

트래픽이 많을수록 캐시 만료 직전에 누군가 한 번은 이 확률적 주사위 조건에 걸리게 되고,  
그 사용자가 캐시가 만료되기 전에 미리 캐시를 연장해 둡니다.  
결과적으로 **캐시 미스(MISS) 상태가 영구히 발생하지 않는 마법**이 일어납니다!

## 6. 캐시 스탬피드 3대 전략 종합 비교

| 비교 항목 | 무방비 Cache-Aside (NAIVE) | Mutex 분산 락 (MUTEX) | stale-while-revalidate (STALE) |
| :--- | :--- | :--- | :--- |
| **캐시 만료 시 DB 쿼리** | **수천 개 동시 폭주 (위험!)** | **정확히 1개로 제한** | **정확히 1개로 제한** |
| **만료 구간 사용자 지연** | 느림 (모두 DB 쿼리 대기) | 보통 (1명은 DB 쿼리, 나머지는 대기) | **초고속 (전원 1ms 즉시 반환)** |
| **데이터 신선도** | 항상 최신 | 항상 최신 | 찰나의 순간 과거 데이터 노출 가능 |
| **적합한 유즈케이스** | 트래픽이 거의 없는 내부 백오피스 | 금융 잔액, 재고 잔여 수량 등 엄격한 정합성 | **홈 화면 배너, 실시간 랭킹, 상품 상세, 뉴스 피드** |
