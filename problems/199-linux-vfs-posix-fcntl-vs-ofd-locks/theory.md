# 리눅스 VFS 파일 잠금: POSIX fcntl의 묵시적 잠금 해제와 Open File Description (OFD) 락 심층 분석

## 1. 개요: 유닉스 VFS 3단계 추상화와 파일 잠금의 역사

리눅스 가상 파일 시스템(VFS)은 파일 접근을 관리하기 위해 3단계의 계층 구조를 사용합니다:

```text
[Process Descriptor Table]       [System-wide Open File Table]        [VFS Inode Table]
┌────────────────────────┐      ┌─────────────────────────────┐      ┌─────────────────┐
│ Task A (PID 100)       │      │ struct file (OFD 1)         │      │                 │
│   fd 3 ────────────────┼─────>│   - f_pos, f_flags, f_count │─────>│ struct inode    │
│   fd 4 ─────────┐      │      └─────────────────────────────┘      │  - i_size       │
│                        │                                           │  - i_mode       │
│ Task B (PID 200)│      │      ┌─────────────────────────────┐      │  - i_flock list │
│   fd 3 ─────────┼──────┼─────>│ struct file (OFD 2)         │─────>│                 │
│                 │      │      └─────────────────────────────┘      └─────────────────┘
│                 └──────┼─────────────────────────────────────────────┘
└────────────────────────┘
```

1. **파일 디스크립터(File Descriptor, `fd`)**: 각 프로세스의 파일 디스크립터 테이블의 정수 인덱스.
2. **오픈 파일 설명자(Open File Description, `struct file`)**: `open()` 시스템 콜마다 커널에 생성되는 객체로, 현재 파일 오프셋(`f_pos`), 접근 모드, 참조 카운트를 보유.
3. **아이노드(`struct inode`)**: 디스크 상의 실제 물리적 파일을 가리키는 유일한 메타데이터 객체.

이 3단계 구조에서 **"잠금(Lock)의 소유권을 어디에 바인딩할 것인가?"**에 대한 설계 차이가 30년간 수많은 소프트웨어 엔지니어들을 괴롭힌 버그의 근원입니다.

## 2. POSIX `fcntl(2)` 레코드 잠금의 치명적 설계 결함

1980년대 초 POSIX 표준 위원회가 레코드 잠금(`F_SETLK`)을 설계할 당시에는 **멀티스레드(Multithreading) 개념이 존재하지 않았습니다**. 모든 병렬성은 독립된 프로세스(PID)로만 구현되었습니다.

이로 인해 POSIX 락은 잠금의 소유자를 **`(PID, inode)` 쌍**으로 정의했습니다.

### 2.1 묵시적 잠금 해제(Silent Lock Drop)의 메커니즘
리눅스 커널의 파일 닫기 루틴인 `filp_close()`는 다음과 같이 동작합니다:

```c
// Linux kernel fs/locks.c
void locks_remove_posix(struct file *filp, fl_owner_t owner) {
    // owner는 프로세스의 파일 테이블 (즉, PID에 바인딩됨)
    // 이 프로세스가 해당 inode에 대해 소유한 *모든* POSIX 락을 순회하며 일괄 제거!
}
```

이 규칙으로 인해 다음과 같은 참사가 발생합니다:
1. 프로세스 내 워커 스레드 1이 `fd_1 = open("data.db")`을 열고 특정 레코드에 배타적 쓰기 잠금(`F_WRLCK`)을 획득합니다.
2. 동일 프로세스 내의 무관한 스레드 2(또는 타사 로깅 라이브러리, 플러그인)가 내부적으로 `fd_2 = open("data.db")`을 열어 헤더만 읽은 후 `close(fd_2)`를 호출합니다.
3. **커널은 `close(fd_2)`를 처리하면서, 스레드 1이 `fd_1`으로 획득했던 배타 락을 조용히 지워버립니다!**
4. 스레드 1은 락이 풀린 사실을 전혀 통지받지 못하며, 파일은 잠금 없는 무방비 상태로 노출됩니다.
5. 다른 프로세스가 즉시 해당 영역에 쓰기를 수행하여 데이터베이스 파일이 산산조각 납니다.

### 2.2 스레드 간 상호 배제 불가
동일한 프로세스 내의 두 스레드가 서로 다른 fd로 동일한 바이트 범위에 `F_SETLK`를 호출하면, 커널은 같은 PID가 락을 갱신하는 것으로 간주하여 **에러 없이 즉시 성공**시킵니다. 즉, 프로세스 내부의 스레드 간에는 동시성 제어가 전혀 불가능합니다.

## 3. `flock(2)` vs `fcntl(2)`의 딜레마

| 특성 | BSD `flock(2)` | POSIX `fcntl(2)` |
| :--- | :--- | :--- |
| **잠금 소유권** | `struct file` (오픈 파일 설명자) | `(PID, inode)` |
| **무관한 fd close 영향** | **안전함** (해당 fd만 닫힘) | **❌ 치명적** (모든 락 증발) |
| **바이트 범위 잠금 (Record Lock)** | **❌ 불가능** (파일 전체만 잠금) | **지원** (start, length) |
| **스레드 간 상호 배제** | 지원 (`open`을 따로 호출한 경우) | **❌ 불가** (동일 PID는 충돌 안 함) |

개발자들은 "안전하지만 파일 전체를 잠가 성능이 붕괴하는 `flock`"과 "정밀한 바이트 잠금이 되지만 언제 풀릴지 모르는 시한폭탄 `fcntl`" 사이에서 고통받았습니다.

## 4. 리눅스 3.15의 해법: Open File Description (OFD) 락

2014년 커널 엔지니어 Jeff Layton은 두 잠금의 장점만을 결합한 **Open File Description (OFD) 락**을 리눅스 3.15에 도입했습니다 (`fcntl` 플래그: `F_OFD_SETLK`, `F_OFD_SETLKW`, `F_OFD_GETLK`).

### 4.1 OFD 락의 핵심 원리
- **소유권 바인딩**: 잠금이 `PID`가 아닌 **오픈 파일 설명자(`struct file`)**에 직접 묶입니다.
- **`close()` 안전성**: 해당 잠금을 생성한 파일 디스크립터가 닫힐 때만 락이 해제됩니다. 동일 프로세스 내의 다른 fd를 수백 번 열고 닫아도 **OFD 락은 100% 안전하게 유지**됩니다.
- **스레드 간 상호 배제**: 동일 프로세스 내의 두 스레드가 각각 `open()`을 호출하여 별도의 `struct file`을 가진 경우, 서로의 OFD 잠금은 정상적으로 충돌하여 안전한 상호 배제가 이루어집니다.
- **바이트 범위 정밀성**: 파일의 특정 파티션(예: SQLite의 4KB B-Tree 페이지) 단위로 병렬 동시 잠금을 완벽히 지원합니다.

```c
struct flock fl = {
    .l_type   = F_WRLCK,
    .l_whence = SEEK_SET,
    .l_start  = 4096,
    .l_len    = 4096,
    .l_pid    = 0, // OFD 락에서는 반드시 0이어야 함
};
// Linux 3.15+ OFD 락 호출
fcntl(fd, F_OFD_SETLK, &fl);
```

## 5. 프로덕션 시스템 적용 사례

### 5.1 SQLite WAL (Write-Ahead Logging) 엔진
SQLite 3.8.7부터 리눅스 환경에서 OFD 락(`SQLITE_ENABLE_LOCKING_STYLE`)을 적극적으로 지원합니다:
- 여러 스레드가 동시에 WAL 프레임(Frame)을 읽고 쓰는 과정에서, 임시 커넥션이 닫히더라도 메인 트랜잭션의 락이 해제되지 않아 무결점 동시성을 보장합니다.

### 5.2 QEMU / KVM 가상 디스크 이미지 락
QEMU는 여러 VM 인스턴스가 실수로 동일한 원시 디스크 이미지(`.qcow2`, `.raw`)를 동시에 열어 파괴하는 것을 방지하기 위해 OFD 락을 사용합니다. 프로세스 내부 스레드 모델에서도 안전하게 이미지 무결성을 지켜냅니다.
