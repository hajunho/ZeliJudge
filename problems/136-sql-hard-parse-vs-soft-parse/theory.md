# SQL 하드 파싱 vs 소프트 파싱과 바인드 변수(Bind Variable)의 기적

> "사용자별 주문 상세 조회 API를 만들면서 아무 생각 없이 파이썬 f-string으로 SQL을 조립했습니다:  
> `query = f\"SELECT * FROM orders WHERE user_id = {user_id}\"`  
> 개발계에서는 인덱스 덕분에 0.5ms 만에 초고속으로 조회되길래 뿌듯해하며 배포했는데...  
> **동시 접속자 1,000명이 몰리자마자 쿼리 실행 시간은 0.5ms인데 DB 서버의 CPU가 100%로 치솟고, Shared Pool 메모리가 터지며 전사 결제 DB가 멈췄습니다!**  
> 인덱스도 잘 타고 쿼리도 단순 PK 조회인데, 도대체 왜 DB CPU가 100%로 불타버린 걸까요?!"

---

## 1. 데이터베이스 엔진 내부의 SQL 3단계 라이프사이클

개발자가 DB로 `SELECT ...` SQL 텍스트를 전송하면, RDBMS(오라클, MySQL, PostgreSQL) 엔진은 결과를 반환하기까지 내부적으로 3단계를 거칩니다:

```
[클라이언트 SQL 전송] ──► [1. 파싱 (Parse)] ──► [2. 최적화 (Optimize)] ──► [3. 실행 (Execute)]
                                │                         │                          │
                                ├── 문법 검사 (Syntax)    └── 수십 가지 실행 계획    └── 인덱스/테이블 블록
                                ├── 권한 검사 (Semantic)      비용 계산 (CBO)            실제 읽기 및 반환
                                └── 캐시 조회 (Lookup)        (CPU 연산 폭발! 🔥)
```

1. **파싱 (Parse)**: SQL 문법이 올바른지, 테이블과 컬럼이 존재하는지, 사용자 권한이 있는지 검사합니다.
2. **최적화 (Optimize)**: **CBO(비용 기반 옵티마이저)**가 인덱스를 탈지, 풀 테이블 스캔을 할지, 어떤 조인 방식(Nested Loop vs Hash)을 쓸지 수많은 경로의 비용을 수학적으로 계산하여 **최적의 실행 계획(Execution Plan)**을 수립합니다. (엄청난 CPU 연산 소모!)
3. **실행 (Execute)**: 확정된 실행 계획에 따라 실제 디스크/버퍼 풀 블록을 읽고 반환합니다.

---

## 2. 하드 파싱 (Hard Parse) vs 소프트 파싱 (Soft Parse)

최적화(Optimize) 단계는 고도의 수학적 알고리즘을 수행하므로 **CPU를 극단적으로 많이 소모**합니다.  
따라서 DB 엔진은 한 번 컴파일한 실행 계획을 **라이브러리 캐시(Library Cache / Shared Pool)**라는 메모리 공간에 저장해 두고 재사용하려 합니다.

```
+-----------------------------------------------------------------------------------+
| 하드 파싱 vs 소프트 파싱 비교                                                     |
+---------------------+-------------------------------+-----------------------------+
| 구분                | 하드 파싱 (Hard Parse)        | 소프트 파싱 (Soft Parse)    |
+---------------------+-------------------------------+-----------------------------+
| 동작 방식           | 캐시에 실행 계획이 없어 문법  | 캐시에 동일한 SQL이 존재하  |
|                     | 검사, 의미 검사, 최적화(CBO), | 여 기존 실행 계획을 즉시    |
|                     | 코드 생성을 전부 처음부터 수행| 재사용 (최적화 단계 건너뜀) |
+---------------------+-------------------------------+-----------------------------+
| CPU 소모량          | 극도로 높음 (수 밀리초 소요)  | 거의 0에 수렴 (0.01ms 이하) |
+---------------------+-------------------------------+-----------------------------+
| 락/래치 경합        | 새 플랜 등록을 위해 라이브    | 읽기 락만 잠깐 확인 후 통과 |
|                     | 러리 캐시 래치/뮤텍스 획득    |                             |
+---------------------+-------------------------------+-----------------------------+
```

## 3. 리터럴 SQL(문자열 결합)의 비극: 100% 하드 파싱 지옥

DB 엔진은 라이브러리 캐시에서 SQL을 찾을 때 **SQL 텍스트 문자열 전체의 해시값(SQL ID)**을 키로 사용합니다.  
즉, **공백 하나, 대소문자 하나, 리터럴 숫자 하나만 달라도 완전히 다른 쿼리로 인식**합니다!

```sql
-- 개발자가 f-string으로 전송한 리터럴 쿼리들:
SELECT * FROM orders WHERE user_id = 1001; -- SQL ID: a1b2c3 (하드 파싱!)
SELECT * FROM orders WHERE user_id = 1002; -- SQL ID: d4e5f6 (완전히 다른 SQL! 하드 파싱!)
SELECT * FROM orders WHERE user_id = 1003; -- SQL ID: g7h8i9 (완전히 다른 SQL! 하드 파싱!)
```

### 무슨 일이 벌어질까?
1. **CPU 100% 고갈 (CBO 연산 폭풍)**:  
   1,000명의 고객이 조회를 요청하면, DB 엔진은 똑같은 로직인데도 **1,000번의 하드 파싱을 수행**하며 CPU가 100% 포화됩니다.
2. **라이브러리 캐시 래치 경합 (Library Cache Latch Contention)**:  
   1,000개의 서로 다른 1회용 실행 계획을 라이브러리 캐시에 집어넣으려고 수많은 DB 프로세스가 메모리 래치(Latch) 뒤에 줄을 서며 극심한 병목이 발생합니다.
3. **공유 풀 메모리 고갈 (Shared Pool Churn)**:  
   1회용 쿼리 플랜들이 캐시 메모리를 꽉 채우고, 메모리가 부족해지자 기존 캐시를 강제로 축출(Eviction / Churn)하면서 DB 메모리가 산산조각 납니다 (오라클의 경우 악명 높은 `ORA-04031: unable to allocate bytes of shared memory` 에러 발생!).

## 4. 바인드 변수 (Bind Variable / PreparedStatement)의 구원

해결책은 너무나 우아하고 간단합니다.  
리터럴 값 대신 **바인드 변수(`?` 또는 `:user_id`)**를 사용하는 것입니다:

```sql
SELECT * FROM orders WHERE user_id = ?; -- 바인드 변수 사용!
```

1. **최초 1회 요청 (`user_id = 1001`)**:  
   캐시에 없으므로 최초 1회만 하드 파싱을 수행하고 실행 계획을 라이브러리 캐시에 등록합니다.
2. **이후 수만 번의 요청 (`user_id = 1002`, `1003`, `1004`...)**:  
   SQL 텍스트 템플릿이 완벽하게 일치하므로, **100% 소프트 파싱(캐시 적중)**으로 최적화 단계를 통째로 건너뛰고 0.01ms 만에 실행 계획을 꺼내옵니다!
3. **결과**:
   - DB CPU 사용률이 **90% 이상 급감**합니다.
   - 라이브러리 캐시 메모리 사용량이 수천 분의 1로 줄어듭니다.
   - 값과 SQL 구조가 분리되므로 악명 높은 **SQL 인젝션(SQL Injection)** 공격이 물리적으로 불가능해집니다!

## 5. 실무 아키텍처 진단표

- **`hard_parse_ratio_pct`**: 전체 쿼리 중 하드 파싱 비율. OLTP 시스템에서는 **1% 미만**이어야 정상입니다.
- **`soft_parse_ratio_pct`**: 소프트 파싱(캐시 적중) 비율. **99% 이상**을 유지해야 고성능 DB입니다.
- **`overall_verdict`**:
  - `HARD_PARSE_STORM_CPU_EXHAUSTION`: 리터럴 쿼리 남발로 하드 파싱 폭풍이 발생하여 DB CPU가 마비된 상태.
  - `SHARED_POOL_THRASHING_LRU_CHURN`: 1회용 플랜이 캐시 용량을 초과하여 대량의 캐시 축출(Eviction)이 발생한 상태.
  - `OPTIMAL_BIND_VARIABLE_REUSE`: 바인드 변수 재사용으로 90% 이상 소프트 파싱을 달성한 최적의 상태.
