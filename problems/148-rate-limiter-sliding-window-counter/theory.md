# [분산 처리율 제한(Rate Limiting) 아키텍처: 고정 윈도우의 경계 트랩과 슬라이딩 윈도우 카운터]

## 1. Rate Limiting이 필요한 이유

DDoS 공격 방어, 크롤러 차단, 서비스 티어별 쿼터(Quota) 제한, 마이크로서비스 연쇄 과부하(Cascading Failure) 방지를 위해 모든 엔터프라이즈 API 게이트웨이(Kong, Nginx, AWS WAF, Envoy)는 **처리율 제한(Rate Limiting)**을 필수로 탑재합니다.

---

## 2. 4대 Rate Limiter 알고리즘 비교

| 알고리즘 | 메모리 복잡도 | 트래픽 버스트 제어 | 경계선 2배 스파이크 | 실무 평가 |
|:---|:---:|:---:|:---:|:---|
| **고정 윈도우 (Fixed Window)** | $O(1)$ | ❌ 취약 | 💥 **최악 (2배 뚫림)** | 단순 카운터, 프로덕션 비추천 |
| **토큰 버킷 (Token Bucket)** | $O(1)$ | ⭕ 버스트 허용 | ⭕ 방어 | AWS, Stripe 표준 알고리즘 |
| **슬라이딩 로그 (Sliding Log)** | $O(N)$ (메모리 폭발) | ⭕ 완벽 제어 | ⭕ 방어 | 모든 타임스탬프 저장, 메모리 비용 과다 |
| **슬라이딩 윈도우 카운터 (Sliding Counter)** | $O(1)$ | ⭕ 완벽 제어 | ⭕ **방어 (100% 안전)** | Cloudflare 표준, 최고 효율 |

---

## 3. 고정 윈도우(Fixed Window)의 경계선 트랩 (Boundary Trap)

고정 윈도우는 시간을 0~60초, 60~120초와 같이 정적인 블록으로 나눕니다.

```text
  윈도우 1 (00:00 ~ 00:59)            윈도우 2 (01:00 ~ 01:59)
[─────────────── 100건 ──]       [── 100건 ───────────────]
                   ▲                 ▲
                 00:59초            01:01초
                   └─── 단 2초간 200건 폭주! ───┘
```
- 공격자가 윈도우가 끝나기 직전(59초)에 한도치(100건)를 쏟아붓고, 윈도우가 바뀌자마자(01초) 다시 100건을 쏟아부으면 **허용 한도의 정확히 2배 트래픽이 2초 만에 백엔드로 관통**합니다.

---

## 4. 슬라이딩 윈도우 카운터(Sliding Window Counter)의 우아한 수학

Cloudflare 엔지니어링 팀이 고안한 슬라이딩 윈도우 카운터는 **이전 윈도우와 현재 윈도우 단 2개의 정수 카운터**만으로 슬라이딩 윈도우를 근사합니다.

### 핵심 공식:
현재 시간 $t$가 현재 윈도우에서 $weight$ 만큼 경과했을 때, 롤링 윈도우(최근 1분간)의 추정 요청 수는:
$$	ext{Estimated} = 	ext{Count}(W_{prev}) 	imes (1 - weight) + 	ext{Count}(W_{curr})$$

```text
          ├────── 최근 60초 슬라이딩 윈도우 ──────┤
          │                                      │
[─── 이전 윈도우 (Count=100) ───][─── 현재 윈도우 (Count=1) ───]
          │◄──── (1 - 1/60) ────►│◄────── 1/60 ─────►│
                 가중치 98.3%            가중치 100%
```

- $t = 61$초 시점:
  - $weight = (61 - 60) / 60 = 1/60$
  - 이전 윈도우의 잔여 가중치 $= 59/60 pprox 98.3\%$
  - 추정 요청 수 $= 100 	imes rac{59}{60} + 0 = 98.3$건
  - 따라서 신규 요청이 들어오면 $98.3 + 1 = 99.3 \le 100$이므로 1건만 통과되고, 그 뒤의 요청들은 **즉시 `429 Too Many Requests`로 차단**됩니다!

### 장점:
1. **메모리 절약**: 요청마다 타임스탬프를 보관하는 슬라이딩 로그(Redis Sorted Set)와 달리, 유저당 단 2개의 카운터(8바이트)만 사용하므로 수천만 유저도 메모리 부담 없이 커버합니다.
2. **원자적 Lua 스크립트**: Redis에서 단일 Lua 스크립트로 $O(1)$ 원자적 검증 및 증가가 가능합니다.
