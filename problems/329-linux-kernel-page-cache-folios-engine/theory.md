# 리눅스 커널 페이지 캐시 폴리오 (Page Cache Folios) 이론 백서

## 1. 등장 배경 및 `struct page`의 한계

리눅스 커널은 1990년대 초창기부터 4KB 크기의 물리 메모리 프레임을 추적하기 위해 `struct page` 구조체를 사용해 왔습니다. 
그러나 현대 시스템 환경에서 세 가지 치명적인 문제가 발생했습니다:

1. **테일 페이지 혼란 (Tail Page Ambiguity)**:
   - 복합 페이지(Compound Page / Transparent Huge Page) 도입 이후, 2MB 대형 페이지는 1개의 헤드 페이지와 511개의 테일 페이지로 구성됩니다.
   - 함수 인자로 `struct page *`를 넘기면 수신자는 이 페이지가 단독 4KB 페이지인지, 아니면 대형 페이지의 테일인지 알 수 없었습니다.
   - 이를 해결하기 위해 커널 전역에서 수시로 `compound_head(page)` 매크로를 호출해야 했고, 이는 L1/L2 CPU 캐시 라인 오염과 분기 예측 실패를 초래했습니다.
2. **XArray (Radix Tree) 탐색 오버헤드**:
   - 페이지 캐시에서 2MB 데이터를 읽을 때, 전통적인 방식은 512개의 4KB 페이지 각각에 대해 XArray 검색과 페이지 잠금(`lock_page()`)을 수행했습니다.
   - 이는 거대한 트리 순회 오버헤드와 락 경합을 유발했습니다.

---

## 2. 폴리오 (`struct folio`)의 혁신적 설계

매튜 윌콕스는 리눅스 5.16에서 **`struct folio`**를 제안했습니다:
- **불변식(Invariant)**: `struct folio` 포인터는 **절대로 테일 페이지를 가리키지 않습니다**.
- 즉, 폴리오는 항상 독립적인 단일 4KB 페이지이거나, 복합 페이지(Compound Page)의 헤드 페이지를 가리킵니다.
- 컴파일러 수준에서 타입 안전성(Type Safety)을 보장하여 런타임 `compound_head()` 호출을 0으로 제거합니다.

## 3. 대형 폴리오 (Large Folios)와 페이지 캐시 성능

페이지 캐시(`mm/filemap.c`)가 대형 폴리오를 지원함으로써 얻는 이점은 다음과 같습니다:

1. **XArray 다중 슬롯 단일 등록**:
   - Order-2(16KB) 폴리오는 4개의 슬롯을, Order-4(64KB) 폴리오는 16개의 슬롯을 차지하지만, XArray에는 단 1개의 헤드 엔트리만 저장됩니다.
   - 검색 시 16번의 트리 하향 탐색 대신 단 1번의 탐색으로 64KB 전체의 참조를 획득합니다.
2. **잠금 및 상태 전이 비용 절감**:
   - `folio_lock()`과 `folio_unlock()`이 64KB당 1회만 발생하므로, 락 획득/해제 사이클이 16배 감소합니다.
   - `folio_mark_dirty()` 역시 1회만 호출되어 `nr_dirty` 카운터 원자적 연산 경합이 대폭 줄어듭니다.
3. **분할(Splitting)과 자르기(Truncation)**:
   - 메모리 회수(Reclaim)나 파일 축소(`truncate`) 시, 경계선에 걸친 대형 폴리오는 `folio_split()`을 통해 하위 차수 또는 Order-0 단일 페이지로 안전하게 분할된 뒤 해제됩니다.
