# [배경 이론] 웹소켓 백프레셔와 송신 버퍼 하이/로우 워터마크 (WebSocket Backpressure & Buffer Watermark)

## 1. 현실 비유: 고속 수로와 꽉 막힌 수도꼭지 (느린 수신자의 저주)

대형 가상화폐 거래소나 실시간 스포츠 중계 서버를 상상해 보세요.
초당 수천 개의 비트코인 체결가 변동을 10,000명의 유저에게 웹소켓(WebSocket)으로 실시간 브로드캐스팅합니다.

- **초고속 유저 (Fast Consumer)**:
  - 기가 인터넷에 연결된 데스크톱 유저는 서버가 쏘는 족족 패킷을 바로바로 읽어갑니다.
- **거북이 유저 (Slow Consumer)**:
  - 지하철을 타고 터널을 지나가는 모바일 3G 유저는 네트워크가 극도로 느려 초당 1KB도 채 받지 못합니다.

만약 서버가 아무 생각 없이 `for client in clients: client.send(price)` 루프를 돈다면 무슨 일이 벌어질까요?

1. 거북이 유저의 스마트폰 수신 버퍼가 가득 차면서 TCP 수신 윈도우가 0이 됩니다 (`rwnd = 0`).
2. 서버의 OS TCP 소켓 송신 버퍼(`SO_SNDBUF`)도 순식간에 꽉 찹니다.
3. 더 이상 네트워크 카드로 보낼 수 없게 된 메시지들이 **서버 애플리케이션 메모리(Netty 송신 큐, JVM 힙 메모리)에 수십만 개씩 쌓이기 시작**합니다!
4. **결과**: 거북이 유저 몇 명 때문에 서버 메모리가 수십 GB로 폭증하여 **OOM Killer로 거래소 서버 전체가 다운**되고 10,000명 전원의 연결이 끊어지는 대참사가 발생합니다.

---

## 2. 해결책: 하이 워터마크(High Watermark)와 로우 워터마크(Low Watermark)

Netty나 고성능 비동기 웹소켓 엔진은 이 문제를 해결하기 위해 **채널 버퍼 워터마크(Buffer Watermark)** 메커니즘을 사용합니다.

```
[송신 큐 메모리 크기 (Buffer Bytes)]
   ▲
   │
   │  [Hard Limit] max_capacity (128 KB) ──► 강제 연결 종료 (Slow Consumer Eviction)
   │
   │  [High Watermark] (64 KB) ───────────► isWritable = false (백프레셔 발동! 쓰기 중단/드롭)
   │     ▲
   │     │  (안전 구간 / 버퍼 드레인 대기)
   │     ▼
   │  [Low Watermark] (32 KB) ────────────► isWritable = true (쓰기 재개!)
   │
   └──────────────────────────────────────────────────────────► 시간
```

### 1) 하이 워터마크 (High Watermark)
- 아직 네트워크로 전송되지 못하고 애플리케이션 송신 큐에 쌓인 바이트 수가 `high_watermark` (예: 64KB)를 초과하는 순간:
  - 채널의 쓰기 가능 상태가 거짓(`isWritable = false`)으로 전환됩니다.
  - 서버는 이 클라이언트에게 무차별 메시지 전송을 멈추거나 백프레셔 정책을 적용해야 합니다.

### 2) 로우 워터마크 (Low Watermark)
- 클라이언트가 데이터를 조금씩 읽어가서 송신 큐 크기가 `low_watermark` (예: 32KB) 미만으로 충분히 배수(Drain)되었을 때:
  - 비로소 채널의 쓰기 가능 상태가 참(`isWritable = true`)으로 복구됩니다.
- **왜 하이와 로우를 분리할까요? (히스테리시스, Hysteresis)**
  - 기준선이 1개뿐이라면 64KB 경계에서 `true` $\leftrightarrow$ `false`가 초당 수천 번 핑퐁을 치며 막대한 CPU 컨텍스트 스위칭 오버헤드가 발생하기 때문입니다.

---

## 3. 실무 백프레셔(Backpressure) 처리 4대 정책

송신 큐가 차서 `isWritable = false`가 되거나 한계에 도달했을 때, 실무에서는 다음 4가지 전략 중 하나를 선택합니다:

1. **`DISCONNECT` (강제 퇴출 / Slow Consumer Eviction)**:
   - 버퍼가 최대 한도(`max_capacity`)를 넘어서면, 서버 메모리를 보호하기 위해 해당 느린 클라이언트와의 연결을 즉시 강제 종료(`WebSocket Close 1008 Policy Violation`)합니다.
   - 금융/채팅 서버에서 다른 수만 명의 정상 유저를 보호하기 위한 표준 정책입니다.
2. **`CONFLATE` (최신 데이터 덮어쓰기)**:
   - 주식/코인 현재가처럼 "중간 과거 데이터는 버려도 되고 오직 최신 값만 중요한 경우":
   - 큐에 이미 동일한 키(`BTC-USDT`)의 메시지가 있다면, 새 메시지로 그 자리를 덮어써서(In-place Replace) 큐가 불필요하게 커지는 것을 원천 차단합니다.
3. **`DROP_OLDEST` (오래된 데이터 드롭)**:
   - 버퍼 공간이 부족할 때 큐의 가장 앞(오래된 메시지)을 버리고 최신 메시지를 넣습니다.
4. **`DROP_LATEST` (새 데이터 드롭)**:
   - 버퍼가 차 있을 때 새로 들어오는 메시지를 조용히 폐기(Drop)합니다.
