# TCP Zero Window 교착 상태, Persist Timer 탐침과 바보 윈도우 증후군 (SWS) 방어

## 1. 개요: TCP 흐름 제어(Flow Control)와 슬라이딩 윈도우

인터넷 프로토콜 스택에서 TCP(Transmission Control Protocol, RFC 793)는 신뢰성 있는 바이트 스트림 전송을 보장합니다. 이때 송신자가 수신자의 수신 능력을 초과하여 패킷을 쏟아붓지 못하도록 조절하는 핵심 메커니즘이 바로 **흐름 제어(Flow Control)**입니다.

- **혼잡 제어(Congestion Control, `cwnd`)**: 네트워크 라우터와 링크의 대역폭 포화를 방지하기 위해 송신자가 자체 계산하는 윈도우.
- **흐름 제어(Flow Control, `rwnd` / `rcv_wnd`)**: 수신자의 소켓 수신 버퍼(`SO_RCVBUF`)가 넘치지 않도록, 수신자가 매 ACK 헤더의 `Window` 필드(16비트, 윈도우 스케일링 옵션 지원)에 기록하여 송신자에게 알리는 가용 수신 버퍼 크기.

송신자는 다음 조건을 만족하는 범위 내에서만 데이터를 전송할 수 있습니다:
$$\text{FlightSize} = \text{SND.NXT} - \text{SND.UNA} \le \min(\text{CWND}, \text{SND.WND})$$

```
+-------------------------------------------------------------------------------+
|                       TCP 수신 버퍼 구조 (Receive Buffer)                     |
+-------------------------------------------------------------------------------+
|   수신 완료 & 앱 미수신 (Buffer Used)        |     가용 수신 윈도우 (rcv_wnd)   |
|============================================|---------------------------------|
| [Byte 0 ~~~~~~~~~~~~~~~~~~~~~~~~ Byte 2000] | [Byte 2001 ~~~~~~~~~ Byte 4000] |
+-------------------------------------------------------------------------------+
                 ^                                            ^
                 | 애플리케이션 `read()` 소비 시 우측으로 이동 | 송신자 데이터 도착 시 좌측으로 축소
```

## 2. 제로 윈도우(Zero Window)와 영구 교착 상태(Deadlock)의 공포

### 2.1 제로 윈도우의 발생
수신 애플리케이션(예: 데이터베이스 벌크 인서트, 디스크 I/O 병목, GC 일시 정지)의 데이터 소비 속도가 송신 속도보다 느리면, 수신 버퍼가 100% 꽉 차게 됩니다.
이때 수신자는 송신자에게 **`rcv_wnd = 0`**을 담은 ACK를 보냅니다. 이를 **제로 윈도우(Zero Window)**라고 부릅니다.
송신자는 제로 윈도우를 수신하는 즉시 새로운 데이터 전송을 일시 중단해야 합니다.

### 2.2 침묵의 교착 상태 (The Silent Deadlock Trap)
이후 수신 애플리케이션이 버퍼의 데이터를 읽어가면서 공간이 생겼다고 가정해 봅시다.
1. 수신자는 이제 데이터를 받을 수 있으므로, 새로운 윈도우 크기(예: `rcv_wnd = 2000`)를 담은 순수 ACK 패킷인 **윈도우 갱신(Window Update ACK)**을 전송합니다.
2. **그러나 순수 ACK(페이로드가 없는 ACK)는 시퀀스 번호를 소비하지 않으며, 상대방이 이에 대해 다시 ACK를 보내지 않습니다.**
3. 만약 네트워크 혼잡이나 스위치 큐 오버플로우로 인해 **이 윈도우 갱신 ACK 패킷이 유실(Drop)**된다면 어떻게 될까요?

```
[송신자 (Sender)]                                       [수신자 (Receiver)]
       |                                                       |
       |  rcv_wnd = 0 (Zero Window)                            |
       | <---------------------------------------------------- | (수신 버퍼 가득 참)
       |                                                       |
   (전송 중단!)                                             (앱이 2000B 읽음)
       |                                                       |
       |       Window Update (rcv_wnd = 2000) [X PACKET DROP!] |
       |       X < - - - - - - - - - - - - - - - - - - - - - - |
       |                                                       |
       |                                                       |
 (윈도우 열리기만을                                       (송신자가 데이터 보내기만을
  기다리며 무한 대기)                                       기다리며 무한 대기)
       |                                                       |
       +==================== [영구 교착 상태: DEADLOCK] ============+
```

송신자는 윈도우가 0인 줄 알고 마냥 기다리고, 수신자는 이미 윈도우를 열어줬으니 송신자가 데이터를 보내기만을 기다립니다.
**두 종단 간에 단 1바이트도 오가지 않는 영구적인 교착 상태(Deadlock)**에 빠지게 됩니다!

## 3. 구원 1: 지속 타이머(Persist Timer)와 제로 윈도우 탐침(ZWP)

RFC 793은 이 치명적인 교착 상태를 타파하기 위해 **지속 타이머(Persist Timer)**와 **제로 윈도우 탐침(Zero Window Probe, ZWP)**을 규정했습니다.

### 3.1 지속 타이머 동작 원리
- 송신자가 `rcv_wnd = 0`을 수신하고 미전송 데이터(`unsent > 0`)가 존재하면, 즉시 지속 타이머(초기값: RTO 수준, 예: 100ms~200ms)를 가동합니다.
- 지속 타이머가 만료될 때까지 윈도우 갱신이 오지 않으면, 송신자는 수신자에게 **1바이트의 페이로드를 담은 제로 윈도우 탐침(Zero Window Probe, ZWP)** 패킷을 강제로 전송합니다.
- 수신자는 윈도우가 0이더라도 이 1바이트 탐침 패킷에 대해 **반드시 현재의 `rcv_wnd`를 담은 ACK를 응답**해야 합니다.
  - 만약 여전히 버퍼가 0이라면: 수신자는 탐침을 버리거나 버퍼 여유에 따라 처리하고 `rcv_wnd = 0` ACK를 보냅니다. 송신자는 지속 타이머를 지수 백오프(Exponential Backoff: $RTO 	imes 2, 4, 8 \dots$)하며 다음 탐침을 준비합니다.
  - 만약 버퍼가 열렸는데 이전 Window Update가 유실되었던 것이라면: 수신자의 ACK에 열려있는 최신 윈도우 크기(`rcv_wnd > 0`)가 실려 오므로, **유실되었던 윈도우 정보가 복구되어 교착 상태가 즉각 해소**됩니다!

## 4. 참사 2: 바보 윈도우 증후군 (Silly Window Syndrome, SWS)

제로 윈도우를 해결하자 또 다른 네트워크 재앙이 찾아왔습니다. 1982년 David D. Clark이 RFC 813에서 밝혀낸 **바보 윈도우 증후군(Silly Window Syndrome, SWS)**입니다.

### 4.1 SWS의 발생 메커니즘
1. 수신 버퍼가 가득 차서 `rcv_wnd = 0`이 되었습니다.
2. 수신 애플리케이션이 키보드 입력이나 단말기 스트림 등으로 인해 버퍼에서 **단 1바이트(또는 10바이트)**만 소비했습니다.
3. 순진한 수신자가 신나서 송신자에게 `rcv_wnd = 10`이라고 알립니다.
4. 송신자 역시 기다렸다는 듯이 **10바이트 페이로드**를 담은 TCP 세그먼트를 쏩니다.
5. IP 헤더(20B) + TCP 헤더(20B) = 총 40바이트의 헤더를 붙여서 단 10바이트를 보냅니다!
   $$\text{헤더 오버헤드 비율} = \frac{40}{40 + 10} = 80\%!$$
6. 이 과정이 무한 반복되면서 기가비트 초고속 네트워크가 초당 수만 개의 10바이트 극소 패킷들로 뒤덮이고, 대역폭과 라우터 CPU가 헤더 파싱에 낭비되어 전체 전송 효율이 곤두박질칩니다.

## 5. 구원 2: SWS의 양방향 회피 알고리즘

SWS를 완벽히 막기 위해서는 수신자와 송신자 양쪽 모두에 가드레일이 필요합니다.

### 5.1 수신자 측 방어: 클라크 알고리즘 (Clark's Algorithm)
수신자는 버퍼에 쥐꼬리만 한 여유 공간이 생겼다고 해서 경솔하게 윈도우를 열어주지 않습니다.
수신자는 가용 버퍼 공간이 다음 임계치에 도달할 때까지 **계속해서 `rcv_wnd = 0`을 광고**합니다:
$$\text{광고 가능 조건: } \text{가용 공간} \ge \min\left(\text{MSS}, \; \frac{\text{전체 수신 버퍼 크기}}{2}\right)$$
충분한 크기(최소 1 MSS 또는 버퍼 절반)의 공간이 확보되었을 때만 비로소 일괄적으로 큰 윈도우를 광고합니다.

### 5.2 송신자 측 방어: RFC 1122 송신자 SWS 회피 알고리즘
수신자가 클라크 알고리즘을 구현하지 않아 작은 윈도우를 광고하더라도, 현명한 송신자는 전송을 스스로 유예(Stall)해야 합니다.
송신자는 다음 **3가지 조건 중 하나 이상을 충족할 때만** 세그먼트를 전송합니다:
1. **전체 MSS 전송 가능**: 전송할 데이터가 1 MSS 이상이고, 가용 윈도우(`snd_wnd`)가 1 MSS 이상인 경우.
2. **최대 윈도우의 절반 이상**: 전송할 데이터 크기가 지금까지 수신자가 광고했던 최대 윈도우(`max_advertised_wnd`)의 절반 이상인 경우.
3. **잔여 데이터 전송 및 미확인 세그먼트 전무**: 송신 대기 중인 모든 데이터를 한 번에 보낼 수 있고, 네트워크상에 아직 ACK를 받지 못한 미확인 패킷(In-flight)이 전혀 없거나 Nagle 알고리즘 조건을 통과한 경우.

이 조건을 만족하지 못하면 송신자는 작은 윈도우가 열려 있어도 전송을 보류(`SWS_AVOIDANCE_STALL`)하고 더 큰 윈도우가 열릴 때까지 기다립니다.

## 6. 핵심 알고리즘 및 RFC 표준 정리

| :--- | :--- | :--- | :--- |
| **Persist Timer & ZWP** | RFC 793, RFC 1122 | 윈도우 갱신 ACK 유실로 인한 영구 교착(Deadlock) | 윈도우 0 상태에서 타이머 만료 시 1바이트 강제 탐침 전송 및 수신자 윈도우 강제 갱신 유도 |
