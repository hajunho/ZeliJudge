# 데이터베이스 마스터-슬레이브 복제 지연(Replication Lag)과 Read-Your-Own-Writes 일관성

> **"글 작성 완료를 눌렀는데 방금 쓴 글이 목록에 안 보여요! 새로고침(F5)을 3번 누르니까 1초 뒤에 나타납니다!"**  
> 데이터베이스 읽기 부하 분산을 위해 Master-Slave(Primary-Replica) 복제 구조를 도입한 백엔드 팀이 반드시 마주치는 대표적인 분산 데이터 일관성 결함이 바로 **Read-Your-Own-Writes (Write-After-Read) 일관성 위반**입니다.

---

## 1. 실무 참사 시나리오

스타트업 백엔드 개발자 젤리(Zeli)는 서비스 트래픽이 급증하자 DB 병목을 해소하기 위해 AWS RDS Aurora의 **Read Replica(읽기 전용 복제본)**를 2대 증설했습니다:
- **Master(Primary) DB**: 모든 쓰기 트랜잭션(`INSERT`, `UPDATE`, `DELETE`) 전담.
- **Replica(Slave) DB 1, 2**: 모든 조회 쿼리(`SELECT`)를 라운드로빈으로 분산 처리.

배포 후 DB CPU는 안정권으로 내려왔지만, 고객센터(CS)에 이상한 문의가 빗발치기 시작했습니다:
- *"프로필에서 닉네임을 변경하고 '저장'을 눌렀는데, 마이페이지로 이동하니 옛날 닉네임이 그대로 떠요!"*
- *"게시판에 글을 등록했는데 목록에 안 보여서 글이 안 써진 줄 알고 똑같은 글을 3번 연속으로 올렸어요!"*
- *"방금 결제했는데 주문 목록에 '주문 내역이 없습니다'라고 나와서 결제가 취소된 줄 알고 재결제했습니다!"*

놀랍게도 1~2초 뒤에 화면을 새로고침하면 방금 쓴 데이터가 정상적으로 나타납니다!

---

## 2. 왜 이런 일이 발생할까? (비동기 복제와 Replication Lag)

Master-Slave 복제는 성능을 위해 대부분 **비동기 복제(Asynchronous Replication)** 방식으로 동작합니다:

```
[비동기 복제 아키텍처와 시차]

클라이언트                    Master DB                        Replica DB
   │                             │                                 │
   │ 1. WRITE (게시글 등록)       │                                 │
   ├────────────────────────────>│                                 │
   │                             │ 2. 트랜잭션 커밋 및 Binlog 기록   │
   │ 3. 200 OK (등록 성공)        │                                 │
   │<────────────────────────────┤                                 │
   │                             │ 4. Binlog 네트워크 비동기 전송   │
   │                             ├────────────────────────────────>│ (Relay log 기록)
   │ 5. READ (방금 쓴 글 조회)    │                                 │
   ├─────────────────────────────┼────────────────────────────────>│ ⚠️ 아직 재생 안 됨!
   │                             │                                 │ (Replication Lag)
   │ 6. 404 Not Found (글 없음!) │                                 │
   │<────────────────────────────┼─────────────────────────────────┤
   │                             │                                 │ 7. SQL 스레드가 재생 완료!
```

1. 클라이언트가 Master DB에 데이터를 쓰고 커밋(`Commit`)을 완료합니다.
2. Master DB는 즉시 클라이언트에게 성공(200 OK) 응답을 반환합니다.
3. 동시에 Master는 변경 내역인 **바이너리 로그(Binary Log / Binlog)**를 네트워크를 통해 Replica로 전송합니다.
4. Replica의 I/O 스레드가 이를 받아 릴레이 로그(Relay Log)에 쓰고, **SQL 워커 스레드가 이벤트를 순차적으로 재생(Replay)**하여 자신의 스토리지에 반영합니다.
5. 이 네트워크 전송, 디스크 I/O, 슬레이브의 쿼리 락 경합 등으로 인해 **수십 ms에서 수 초에 달하는 복제 지연(Replication Lag)**이 발생합니다!
6. 클라이언트가 쓰기 성공 직후 목록 페이지로 리다이렉트되어 Replica로 `SELECT`를 날리면, **아직 슬레이브에 트랜잭션이 반영되지 않아 방금 쓴 데이터가 보이지 않는 Stale Read 참사**가 터집니다.

## 3. Read-Your-Own-Writes (Write-After-Read) 일관성이란?

분산 시스템과 데이터베이스 이론(Martin Kleppmann의 *DDIA* 5장)에서 정의하는 핵심 일관성 모델입니다:

> **Read-Your-Own-Writes Consistency**:  
> 사용자가 직접 수정한 데이터는, **그 수정을 가한 사용자 본인이 조회할 때는 항상 최신 상태(자신의 변경 사항이 반영된 상태)로 보여야 한다**는 보장.

- **타인(Other Users)의 관점**:
  - 다른 사용자가 작성한 글이나 프로필은 몇 백 ms 정도 늦게 보여도 서비스 이용에 큰 지장이 없습니다 (최종 일관성 / Eventual Consistency 허용).
- **작성자 본인(Author)의 관점**:
  - 자신이 방금 입력하고 저장한 데이터가 즉시 보이지 않으면 시스템이 고장 났다고 인지하여 중복 요청을 유발하고 결제 사고로 이어집니다 (강한 일관성 / Strong Consistency 필수).

## 4. 3대 해결 전략 비교

### 1. `NAIVE_REPLICA_ONLY` (문제의 단순 무식 전략)
- 모든 `SELECT`를 무조건 Replica로 보냄.
- 복제 지연이 0.1초라도 있으면 쓰기 직후 조회 시 100% `STALE_READ_ANOMALY` 발생.
- 심각한 사용자 경험 훼손.

### 2. `SESSION_MASTER_PINNING` (세션 기반 마스터 핀닝 윈도우)
- 사용자가 쓰기(`INSERT/UPDATE/DELETE`)를 수행하면 세션이나 쿠키, 로컬 스토리지에 **마지막 쓰기 시각($T_{\text{write}}$)**을 기록합니다.
- 이후 일정 시간($T_{\text{pin}}$, 예: 2초) 동안 해당 사용자의 모든 조회 요청을 **강제로 Master DB로 라우팅**합니다.
- **장점**: 구현이 매우 단순하며 Spring Boot `AbstractRoutingDataSource`나 Rails Multi-DB에서 널리 쓰임.
- **단점**: 쓰기가 잦은 사용자가 많으면 읽기 쿼리가 마스터로 몰려 Master DB CPU가 치솟을 수 있음.

### 3. `CAUSAL_GTID_CONSISTENCY` (GTID 인과적 일관성 대기 및 적응형 폴백)
- Master에서 트랜잭션을 커밋할 때 단조 증가하는 고유 트랜잭션 번호인 **GTID(Global Transaction Identifier)**(예: `1052`)를 발급받아 클라이언트 응답 헤더나 세션에 담아둡니다.
- 클라이언트가 Replica로 조회를 날릴 때 자신이 요구하는 최소 GTID($G_{\text{needed}}$)를 함께 전달합니다.
- **Replica 검사**:
  1. 슬레이브의 적용된 GTID $G_{\text{applied}} \ge G_{\text{needed}}$이면: **이미 최신 상태! 슬레이브에서 즉시 읽기 수행**.
  2. $G_{\text{applied}} < G_{\text{needed}}$이면:
     - MySQL의 `SELECT WAIT_FOR_EXECUTED_GTID_SET('...', timeout)`을 호출하여 슬레이브가 따라잡을 때까지 잠시 대기(예: 최대 0.5초).
     - 시간 내에 따라잡으면 **슬레이브에서 읽기 수행 (마스터 부하 0%)**.
     - 타임아웃이 초과되면 **Master DB로 안전하게 폴백(Fallback)**하여 최신 데이터 조회.
- **장점**: 슬레이브가 이미 따라잡았거나 금방 따라잡는 대부분의 경우 마스터 부하를 유발하지 않으면서 100% 일관성을 보장하는 최고 효율의 아키텍처.
