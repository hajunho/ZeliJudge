# 오프셋 페이징의 덫과 커서 기반 페이징 (OFFSET Pagination Bottleneck vs Keyset Cursor Pagination)

> **"게시판 1페이지는 0.01초 만에 뜨는데, 왜 10만 페이지는 30초 동안 멈출까요?!"**  
> **"100만 쪽 백과사전 앞에서 99만 장을 손으로 넘기는 참사 vs 책갈피(Cursor) 꽂고 직행하기"**

---

## 1. 현실 세계 비유: 100만 쪽 백과사전 넘기기

두께가 100만 쪽에 달하는 거대한 역사 백과사전에서 50만 1쪽부터 20쪽 분량의 글을 읽으려고 합니다.

```
[비극적인 방식: OFFSET 페이징]
1. 독자는 1쪽부터 시작해서 "1, 2, 3, 4, ... 500,000"까지 손가락으로 50만 장을 한 장 한 장 세어가며 넘깁니다.
2. 50만 장을 넘기느라 손가락에 쥐가 나고 1시간이 걸렸습니다.
3. 드디어 50만 1쪽부터 50만 20쪽까지 20장을 재미있게 읽었습니다.
4. 다음 장(50만 21쪽)을 읽으려고 책을 넘기려는데...
   다시 책을 덮고 1쪽부터 50만 20장까지 처음부터 다시 세기 시작합니다!
```

```
[지혜로운 방식: Cursor (Keyset) 페이징]
1. 독자는 방금 읽은 마지막 페이지(Cursor: 50만 쪽)에 책갈피를 딱 꽂아둡니다.
2. 다음번 글을 읽을 때는 1쪽부터 셀 필요 없이, 책갈피가 꽂힌 곳(WHERE id < last_id)을 0.001초 만에 펼칩니다.
3. 1페이지든 100만 페이지든 언제나 눈 깜짝할 사이에 20장만 읽고 덮습니다!
```

이것이 바로 전 세계 수많은 웹 서비스가 무심코 쓰는 **오프셋(OFFSET) 페이징이 데이터가 쌓일수록 데이터베이스를 폭사시키는 근본 이유**입니다.

---

## 2. 왜 `OFFSET`은 데이터가 많아질수록 느려지는가?

우리가 흔히 작성하는 SQL 페이징 쿼리를 살펴봅시다:

```sql
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000;
```

### 데이터베이스 엔진 내부에서 일어나는 일 ($O(N + M)$)
1. DB 엔진은 마법처럼 100만 번째 위치로 바로 점프할 수 없습니다.
2. B-Tree 인덱스 또는 테이블에서 정렬 순서대로 **1,000,020개의 행을 디스크에서 메모리로 전부 퍼 올립니다**.
3. 그리고 앞의 **1,000,000개의 행을 CPU로 하나하나 카운트하며 버립니다(Discard)**.
4. 마지막에 남은 20개의 행만 클라이언트에 반환합니다.
5. **결과**: 페이지 번호가 커질수록 읽고 버리는 행 수($\text{OFFSET}$)가 무한정 늘어나 디스크 I/O가 폭증하고 DB CPU가 100%로 마비됩니다.

---

## 3. 더 끔찍한 실무 버그: 데이터 드리프트 (Data Drift)

오프셋 페이징은 성능 저하뿐만 아니라 **데이터의 중복 노출과 누락**이라는 치명적인 정합성 결함을 안고 있습니다:

```
[상황: SNS 피드에서 사용자가 1페이지(글 1~20번)를 읽고 있는 사이, 새 글 5개가 등록됨]
- 사용자가 스크롤을 내려 2페이지(LIMIT 20 OFFSET 20)를 요청합니다.
- 새 글 5개가 맨 위에 추가되면서 기존 글들의 순번이 5칸씩 뒤로 밀렸습니다!
- 그 결과, 1페이지 맨 끝에서 이미 보았던 16~20번 글 5개가 2페이지 맨 앞머리에 또다시 중복 노출됩니다!
- 반대로 글이 삭제되면 특정 글이 건너뛰어져 영영 보이지 않는 누락 버그가 발생합니다.
```

---

## 4. 해결책: 커서 기반 페이징 (Keyset Pagination)

커서 기반 페이징은 "몇 개를 건너뛸지(OFFSET)"를 묻지 않고, **"마지막으로 본 데이터가 무엇인지(Keyset Cursor)"**를 조건절에 명시합니다:

```sql
SELECT * FROM orders 
WHERE id < 1000021 
ORDER BY id DESC 
LIMIT 20;
```

### B-Tree 인덱스 레인지 탐색 ($O(\log N + M)$)
1. DB 엔진은 B-Tree 루트 노드에서 이진 탐색으로 `id = 1000021`의 리프 노드 위치를 단 $\lceil \log_2 N \rceil$번(1억 건이어도 단 27번!) 만에 직행합니다.
2. 그 위치부터 오름차순/내림차순으로 **딱 20개의 리프 노드 레코드만 읽고 즉시 쿼리를 종료**합니다.
3. 앞의 100만 개를 읽을 필요가 전혀 없으므로, **1페이지든 1억 페이지든 응답 시간이 항상 0.001초로 고정**됩니다!
4. 도중에 새로운 글이 수만 건 등록되더라도 커서(`last_id`) 이후의 데이터만 읽으므로 **데이터 중복이나 누락이 수학적으로 불가능**합니다.

---

## 5. 두 페이징 전략 종합 비교

| 비교 항목 | 오프셋 페이징 (OFFSET Pagination) | 커서 페이징 (Keyset / Cursor Pagination) |
| :--- | :--- | :--- |
| **시간 복잡도** | $O(\text{OFFSET} + \text{LIMIT})$ (뒤로 갈수록 선형 증가) | $O(\log N + \text{LIMIT})$ (항상 일정) |
| **디스크 I/O** | 수백만 건을 읽어서 버림 (I/O 낭비 심각) | 요청한 LIMIT 개수 페이지만 정확히 읽음 |
| **데이터 정합성** | 신규 데이터 삽입/삭제 시 중복 노출 및 누락 발생 | 삽입/삭제가 일어나도 100% 무결성 유지 |
| **적합한 UI/UX** | 전통적인 번호형 페이지네이션 (`[1] [2] [3] ...`) | 모바일 앱 무한 스크롤(Infinite Scroll), 피드, 대량 API |

> **"뒤 페이지를 읽겠다고 앞 페이지를 전부 읽어 버리는 바보짓을 멈춰라. 책갈피(Cursor)를 꽂는 순간 1억 건의 데이터베이스도 0.001초 만에 열린다."**  
> 이것이 인스타그램, 트위터, 쿠팡 등 대규모 글로벌 트래픽을 감당하는 빅테크 기업의 무한 스크롤 아키텍처의 비밀입니다.
