# 이론 백서: 분산 NoSQL Dynamo/Cassandra: Consistent Hash 토큰 링, vnode 데이터 편중 및 힌티드 핸드오프(Hinted Handoff) 폭풍

## 1. 개요 및 배경 (Background)

2007년 아마존(Amazon)이 발표한 **Dynamo 논문**과 이를 오픈소스로 발전시킨 **Apache Cassandra** 및 **ScyllaDB**는 단일 장애점(SPOF)이 없는 마스터리스(Masterless, Peer-to-Peer) 분산 NoSQL 데이터베이스의 시대를 열었습니다.

마스터리스 시스템은 중앙 집중식 리더(Raft의 Leader나 RDBMS의 Primary) 없이, 클러스터 내의 모든 노드가 대등한 자격으로 클라이언트의 읽기/쓰기 요청을 수신하는 **코디네이터(Coordinator)** 역할을 수행합니다.

이러한 고가용성 구조를 지탱하는 양대 핵심 축은 다음과 같습니다:
1. **일관된 해싱(Consistent Hashing) 기반 토큰 링**: 데이터를 클러스터 노드들에 수평 분할(Sharding)하는 메커니즘.
2. **힌티드 핸드오프(Hinted Handoff)**: 일시적으로 다운된 레플리카 노드가 존재하더라도 쓰기 가용성을 보장하기 위해 코디네이터가 미전송 뮤테이션을 임시 보관했다가 사후 전달하는 비동기 복구 메커니즘.

그러나 토큰 링 구성(Vnodes)과 힌트 전달 정책(Throttling)을 부적절하게 운영할 경우, 노드 간 데이터 불균형으로 인한 핫스팟 디스크 고갈과 복구 노드를 향한 **힌티드 핸드오프 폭풍(Handoff Storm)**으로 인한 클러스터 연쇄 마비 장애가 발생합니다.

## 2. 일관된 해싱(Consistent Hashing)과 가상 노드(Vnodes)

### 2.1. 고전적 단일 토큰(Single Token) 방식의 한계
초기 카산드라(0.x~1.1)에서는 물리 노드 1대당 링 상의 토큰 1개만을 수동으로 할당했습니다.
- 해시 공간($[-2^{63}, 2^{63}-1]$)에 노드들이 임의의 토큰 위치를 가질 때, 각 노드가 소유하는 토큰 범위(Token Range)는 극도로 불균등합니다.
- 확률론적으로 6대 노드 클러스터에서 최대 점유 노드와 최소 점유 노드의 데이터 비율 차이는 **5배 이상(Skew Ratio > 5.0)** 벌어질 수 있습니다.
- 특정 노드만 디스크 사용량이 85%에 육박하여 디스크 풀(Full) 장애를 겪고, 해당 노드의 JVM GC 정체(STW)로 전체 쿼리 지연이 악화되는 핫스팟 문제가 필연적으로 발생합니다.
- 노드 추가/제거 시에도 오직 인접한 이웃 노드 하나만 데이터 이동 부하를 전담해야 하는 심각한 확장성 병목이 존재했습니다.

### 2.2. 가상 노드(Virtual Nodes, Vnodes)의 도입
카산드라 1.2부터 도입된 **Vnode** 아키텍처(`num_tokens = 128` 또는 `256`)는 물리 노드 1대가 링 상의 여러 가상 토큰 위치를 무작위로 소유하도록 만듭니다.

```
 [Single Token Ring: num_tokens = 1]          [Vnode Ring: num_tokens = 128]
        (Node 1)                               (N1)   (N2)   (N3)   (N1)
       /        \                             /    \ /    \ /    \ /    \
   (N3)          (N2)                      (N3)    (N1)   (N2)   (N3)   (N2)
   - 큰 불균형 (25% vs 5%)                  - 대수의 법칙으로 완전 균등화
   - 핫스팟 및 OOM 유발                     - 점유 편차(CV) < 5% 달성
```

- **대수의 법칙(Law of Large Numbers)**: 노드당 가상 토큰 수가 64~128개 이상으로 증가하면, 통계적으로 각 물리 노드가 소유하는 토큰 구간의 총합이 수학적 기댓값($1/N$)에 수렴합니다.
- 점유율 변동 계수(Coefficient of Variation, CV)가 $35\%$ 이상에서 $3\sim 5\%$ 이하로 급감하여 클러스터 디스크 및 부하가 완벽히 평준화됩니다.
- 신규 노드 추가 시 클러스터의 **모든 기존 노드가 조금씩 데이터를 쪼개어 전달**하므로 리밸런싱 속도가 비약적으로 향상됩니다.

## 3. 힌티드 핸드오프(Hinted Handoff) 메커니즘

### 3.1. 쓰기 동작과 힌트 생성
$RF=3$ (Replication Factor) 및 $CL=\text{QUORUM}$ (2개 노드 응답 필요) 설정에서:
1. 클라이언트가 특정 키에 대한 쓰기를 코디네이터 노드로 발행합니다.
2. 코디네이터는 토큰 링에서 해당 키를 저장할 3개의 복제 노드($R_1, R_2, R_3$)를 결정합니다.
3. 만약 $R_1, R_2$는 정상이지만 $R_3$가 일시적 네트워크 단절로 응답하지 못한다면:
   - 코디네이터는 $R_1, R_2$로부터 성공 ACK를 받아 총 2개의 복제본에 기록했으므로 $CL=\text{QUORUM}$을 만족하여 **클라이언트에게 즉시 쓰기 성공을 응답**합니다.
   - 동시에 코디네이터는 $R_3$에게 보내지 못한 뮤테이션 데이터를 로컬 디스크의 힌트 디렉토리(`hints/`)에 **힌트(Hint)** 파일로 기록합니다.

### 3.2. 힌트 유효 기간 (`max_hint_window_in_ms`)
만약 대상 노드가 영구적으로 사망했거나 수일 동안 살아나지 못한다면, 코디네이터 노드의 디스크가 끝없이 쌓이는 힌트 파일로 인해 가득 차는 2차 장애가 발생할 수 있습니다.
- 따라서 커널/설정 레벨에서 최대 힌트 저장 윈도우(`max_hint_window_in_ms`, 기본 3시간)를 둡니다.
- 노드가 다운된 지 3시간이 초과되면 코디네이터는 해당 노드를 위한 힌트 저장을 완전히 중단합니다.
- **부작용 (Silent Data Loss)**: 3시간 이후 노드가 복구되면, 3시간 동안의 업데이트가 힌트로 전달되지 못하므로 해당 노드는 구버전(Stale) 데이터를 보관하게 됩니다. 이는 사후에 수동으로 `nodetool repair`(안티-엔트로피 머클 트리 복구)를 돌려야만 일관성이 회복됩니다.

## 4. 힌티드 핸드오프 폭풍(Hinted Handoff Storm)과 노드 플래핑

### 4.1. 장애 전개 과정
수 분간의 일시적 장애(스위치 리부팅, 긴 풀 GC) 후 $R_3$가 살아났을 때 가장 위험한 현상이 일어납니다:

```
 [Coordinator 1] ──► (1,000 Hints) ──┐
 [Coordinator 2] ──► (1,000 Hints) ──┼──► [Recovered Replica R3]
 [Coordinator 4] ──► (1,000 Hints) ──┤      - MutationStage Queue (Max: 1000)
 [Coordinator 5] ──► (1,000 Hints) ──┘      - 4,000건 동시 유입!
                                            - Queue Overflow ──► Packet Drop!
                                            - CPU 100%, GC STW ──► 다시 DOWN! (Flapping)
```

1. 클러스터의 가십(Gossip) 프로토콜을 통해 $R_3$의 상태가 `UP`으로 전환됩니다.
2. 클러스터 내의 모든 코디네이터 노드들이 일제히 보관 중이던 수천~수만 건의 힌트를 $R_3$로 전송하기 시작합니다.
3. **쓰기 큐 포화 및 드롭**:
   - $R_3$의 커밋로그 쓰기 스레드 풀인 `MutationStage`는 초당 처리 능력과 큐 크기(기본 1000~2000)에 한계가 있습니다.
   - 쓰로틀링이 없는 환경(`hint_throttle_kb_per_sec = 0`)에서는 큐가 즉시 가득 차고 초과 힌트가 무차별적으로 폐기(`MutationDrop`)됩니다.
4. **노드 플래핑 (Flapping)**:
   - 과도한 I/O와 메모리 압박으로 $R_3$의 응답 시간이 수 초 이상 지연되면 다른 노드들의 피어 감시(Failure Detector)에 의해 $R_3$가 다시 `DOWN`으로 마킹됩니다.
   - 다운되면 힌트 전송이 멈추고, 잠시 후 $R_3$가 숨을 돌려 다시 `UP`이 되면 또다시 힌트 폭풍이 쏟아지는 무한 플래핑 루프에 갇히게 됩니다.

## 5. 완화 기술 및 프로덕션 엔지니어링 권장사항

### 5.1. 힌트 스트리밍 쓰로틀링 (`hinted_handoff_throttle_in_kb`)
- 코디네이터 노드가 단일 타겟 노드로 힌트를 전송할 때 사용하는 대역폭을 토큰 버킷으로 엄격히 제한합니다.
- 프로덕션 권장값: 노드당 `1024 ~ 2048 KB/s`.
- 쓰로틀링을 적용하면 복구 노드의 정상 트래픽 처리 능력을 침해하지 않으면서 백그라운드에서 대기열을 부드럽게 소각(Drain)할 수 있습니다.

### 5.2. 백프레셔(Backpressure) 기반 힌트 전송 일시 중지
- 수신 노드의 `MutationStage` 대기 큐 깊이나 커밋로그 지연이 임계치(예: 큐 50% 이상)를 초과하면 코디네이터에게 백프레셔 신호를 보내어 힌트 전송을 일시 중지(Backoff)시킵니다.

### 5.3. 적정 Vnode 수 산정
- 너무 작은 Vnode(`num_tokens < 16`): 데이터 편중 발생.
- 너무 큰 Vnode(`num_tokens > 256`): 노드 간 연결 수 및 가십 메시지 오버헤드 폭증, `nodetool repair` 수행 시간 증가.
- 최신 카산드라(4.0+) 권장값: **`num_tokens = 16 ~ 128`**.
