# [배경 이론] 새벽에 통계 쿼리 한 번 돌렸더니 왜 전사 결제 쿼리가 디스크로 떨어져 DB가 뻗어요?!: MySQL InnoDB 버퍼 풀 오염(Buffer Pool Pollution)과 Midpoint LRU 2계층 캐시 알고리즘

## 1. 현실 비유: 특급 도서관의 열람실 책상과 하루살이 방문객

국립 중앙도서관의 최고 인기 열람실에 **책상(버퍼 풀, Buffer Pool)**이 딱 10개 있습니다.

- **평화로운 시간**:
  - 매일 수천 명의 고시생들이 가장 중요한 법전, 의학 서적 10권(핫 데이터, 결제/주문 인덱스)을 책상 위에 펴두고 0초 만에 빠르게 읽습니다.
  - 책을 서고(디스크)에서 찾으러 갈 필요가 없어 도서관은 빛의 속도로 돌아갑니다.

- **참사의 새벽 (캐시 오염, Cache Pollution)**:
  - 새벽 3시, 마케팅 부서 직원이 도서관에 들어와 외칩니다:
    *"서고 3층에 있는 고대 만화책 1,000권(통계 풀 스캔, `SELECT * FROM users`) 전부 한 페이지씩 훑어볼게요!"*
- **전통적인 LRU(Least Recently Used) 책상의 비극**:
  - 전통적 LRU는 책을 읽을 때마다 **무조건 책상 맨 앞자리**에 올리고, 가장 오래된 책을 서고로 쫓아냅니다.
  - 직원이 만화책 1,000권을 차례로 읽는 동안, 매일 쓰이던 소중한 법전과 의학 서적 10권이 **전량 서고로 쫓겨나고(Eviction)**, 책상 10개는 방금 딱 1초 보고 다시는 안 볼 쓰레기 만화책들로 가득 차버립니다!
  - 아침 9시, 고시생(실제 유저 결제 요청)들이 몰려오자 책상이 텅 비어 모든 책을 서고(디스크 I/O)에서 일일이 찾아오느라 도서관 문이 닫혀버립니다(DB 다운)!

## 2. 왜 전통적인 단순 LRU는 데이터베이스에서 실패하는가?

알고리즘 교과서에 나오는 고전적인 LRU 캐시는 **"최근에 참조된 데이터는 가까운 미래에 다시 참조될 가능성이 높다(시간 지역성, Temporal Locality)"**는 가정에 기반합니다.

하지만 데이터베이스 실무 환경에서는 이 가정이 산산조각 납니다:
1. **풀 테이블 스캔 (Full Table Scan / Index Scan)**:  
   배치 정산, 대규모 통계 쿼리, 악성 쿼리는 수백만~수천만 건의 데이터를 '단 한 번' 순차적으로 읽고 버립니다.
2. **캐시 오염 (Cache Pollution)**:  
   일회성 대량 데이터가 버퍼 풀의 진짜 핫(Hot) 페이지들을 전부 쫓아내어, 정작 실시간 서비스 트랜잭션의 캐시 적중률(Hit Ratio)이 99%에서 0%로 곤두박질치는 현상입니다.

## 3. MySQL InnoDB의 구원: Midpoint Insertion LRU (2계층 LRU)

MySQL InnoDB 스토리지 엔진은 이 문제를 완벽하게 해결하기 위해 **LRU 리스트를 2개의 구역으로 분할한 Midpoint LRU 알고리즘**을 사용합니다 (`innodb_old_blocks_pct`, `innodb_old_blocks_time`).

```
[InnoDB 2계층 Midpoint LRU 리스트 구조]
Head (MRU)                                         Tail (LRU)
 ┌─────────────────────────┬─────────────────────────┐
 │   Young Sublist (5/8)   │    Old Sublist (3/8)    │
 │ (진짜 Hot 페이지 보호 구역) │ (신규 페이지 격리 수용소)   │
 └─────────────────────────┴─────────────────────────┘
                           ▲
                  [Midpoint 삽입 지점]
```

### 1) 중간 삽입 (Midpoint Insertion)
- 새로 디스크에서 읽어 들인 페이지는 리스트의 맨 앞(Head)이 아니라, 정확히 Young과 Old의 경계인 **Midpoint(Old Sublist의 헤드)**에 삽입됩니다.
- 풀 테이블 스캔으로 수백만 페이지가 쏟아져 들어와도, 이 페이지들은 **하위 3/8 영역(Old Sublist) 내에서만 회전하며 조용히 꼬리(Tail)로 밀려나 축출**됩니다!
- 상위 5/8 영역에 있는 소중한 결제/주문 페이지들은 털끝 하나 다치지 않고 안전하게 보존됩니다!

### 2) 시간 기반 승급 방어 (`innodb_old_blocks_time`)
풀 스캔을 수행할 때 한 페이지 내의 여러 행(Row)을 연속으로 읽기 때문에, 몇 밀리초(ms) 사이에 동일 페이지가 여러 번 참조될 수 있습니다.  
만약 단순히 "두 번 참조되었다"고 Young 영역으로 올려준다면 여전히 풀 스캔에 뚫리게 됩니다.

이를 방지하기 위해 InnoDB는 **시간 창(Time Window, 기본 1000ms)**을 둡니다:
- 페이지가 Old 영역에 처음 들어온 시점(`first_access_time`)으로부터 **최소 1000ms(1초) 이상 체류한 이후에 다시 참조**되어야만, *"아! 너는 잠깐 스쳐 지나가는 통계 스캔이 아니라, 진짜 오랜 시간 반복해서 찾는 핫 페이지구나!"*라고 인정받아 Young Sublist의 헤드로 승급(Promote)됩니다!
- 1000ms 이내에 수십 번 읽히는 연속 참조는 승급되지 않고 무시됩니다.

이 정교한 2계층 시간 기반 LRU 구조 덕분에, MySQL InnoDB는 대규모 배치 통계 작업이 백그라운드에서 아무리 풀 스캔을 돌아도 실시간 핵심 서비스 쿼리를 0ms 메모리 캐시로 철통 보호할 수 있습니다.\n
