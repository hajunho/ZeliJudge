# 데이터베이스 샤딩과 팬아웃 병목 (Database Sharding & Scatter-Gather Fan-out)

> **"DB를 16대로 쪼개어 샤딩(Sharding)했는데, 왜 단일 DB일 때보다 10배나 느려졌을까요?!"**  
> **"100개 서랍장을 전부 열어보는 멍청한 집사(Scatter-Gather) vs 서랍 번호로 직행하는 스마트 집사(Targeted Routing)"**

---

## 1. 현실 세계 비유: 100개의 서랍장과 고객 영수증 찾기

거대한 전자제품 백화점에 고객 100만 명의 영수증이 쌓이자, 창고 매니저는 **100개의 서랍장(DB Shard 0~99)**을 사서 영수증을 분산 보관하기로 했습니다.

```
[잘못된 샤딩 전략: 생성 날짜(created_date) 기준 샤딩]
매니저는 아무 생각 없이 "영수증 발행 날짜별로 100개 서랍에 나눠 넣자!"라고 결정했습니다.

어느 날 고객 철수(User ID = 42)가 찾아와 요청합니다:
"제가 과거에 결제했던 모든 영수증 목록을 보여주세요!"

무슨 일이 일어났을까요?
1. 창고 직원은 철수가 몇 년 몇 월 몇 일에 물건을 샀는지 전혀 모릅니다!
2. 결국 매니저는 확성기로 소리칩니다: 
   "직원 100명 전원 각자 자기 서랍 열고 철수 영수증 찾아!" (Scatter-Gather / Fan-out = 100!)
3. 100개의 서랍장 문이 동시에 쾅쾅 열리고 100명의 직원이 서랍을 샅샅이 뒤집어엎습니다.
4. 그중 98개 서랍에는 철수 영수증이 1장도 없는데, 헛수고를 하느라 다른 손님 업무를 전혀 보지 못합니다.
5. 심지어 100명 중 가장 손이 느린 직원 1명이 서랍을 다 뒤질 때까지 철수는 카운터에서 10분 동안 기다려야 합니다 (Long-tail 병목)!
```

손님 1,000명이 동시에 영수증을 달라고 하면 어떻게 될까요?  
직원 100명이 10만 번 서랍을 열고 닫다가 과로로 쓰러지고, 백화점 창고 문이 닫힙니다!

```
[올바른 샤딩 전략: 사용자 ID(user_id) 기준 코로케이션 샤딩]
베테랑 매니저는 비즈니스의 90%가 "고객별 주문 조회"라는 점을 간파하고, 서랍을 고객 번호로 분류했습니다:
공식: hash(user_id) % 100 = 42번 서랍장!

고객 철수(User ID = 42)가 오자, 매니저는 딱 1명의 직원에게만 지시합니다:
"42번 서랍으로 가서 철수 영수증 한 묶음 바로 꺼내와!" (Targeted Single-Shard / Fan-out = 1!)

결과:
1. 오직 42번 서랍만 열렸고, 1초 만에 영수증을 꺼내왔습니다.
2. 나머지 99개의 서랍과 직원들은 단 0.1초도 방해받지 않고 다른 99명의 고객 요청을 동시에 처리했습니다!
3. 고객이 1,000명이 와도 서랍장에 골고루 분산되어 처리량(TPS)이 정확히 100배로 선형 확장(Linear Scaling)됩니다!
```

## 2. 샤딩(Sharding)의 목적과 본질

샤딩은 단일 데이터베이스 서버(Scale-up)의 CPU, 메모리, 디스크 한계를 극복하기 위해 데이터를 여러 대의 독립된 물리 DB 노드에 쪼개어 저장하는 **수평 분할(Horizontal Partitioning)** 기술입니다.

### 샤딩의 대원칙:
> **"샤딩은 대부분의 쿼리가 단 1개의 샤드(Single Shard)만 찔러야 성공한다."**

만약 샤드 키(Shard Key)를 잘못 고르면, 쿼리 하나를 처리하기 위해 수십 대의 샤드에 일제히 쿼리를 뿌리고 취합하는 **스캐터-게더(Scatter-Gather / Fan-out)** 지옥에 빠지게 됩니다.

---

## 3. 스캐터-게더(Scatter-Gather)의 3대 치명적 재앙

샤딩 환경에서 `WHERE` 조건절에 샤드 키가 없으면, 샤딩 라우터(ShardingSphere, Vitess, Citus)는 쿼리를 모든 샤드로 팬아웃(Fan-out)시킵니다:

```
                  [ Client Query: WHERE user_id = 42 ]
                                  |
                        [ Sharding Router ]
                        /     |     |     \  (Broadcast / Scatter!)
                       v      v     v      v
                    [Shard 0][Shard 1][Shard 2][Shard 3]  (모든 샤드 CPU/IO 100% 폭사)
                       \      |     |      /
                        v     v     v     v
                  [ Gather, Merge, Sort in Router Memory ]
                                  |
                            [ Response ]
```

1. **시스템 리소스 $N$배 낭비**:
   - 샤드가 16대라면, 단 1건의 쿼리를 위해 16대의 DB 서버가 동시에 CPU와 디스크 I/O를 소모합니다.
   - 단일 DB보다 전체 시스템 처리량(TPS)이 오히려 1/16로 토막 납니다.
2. **롱테일 레이턴시(Long-Tail Latency)의 저주**:
   - 전체 쿼리 완료 시간은 **모든 샤드 중 가장 느린 샤드의 응답 시간**에 종속됩니다:
     $$\text{Total Latency} = \max(T_1, T_2, \dots, T_N)$$
   - 샤드 중 단 1대만 디스크 I/O 스파이크나 GC 지연이 발생해도 전체 사용자 화면이 멈춥니다.
3. **분산 정렬 및 페이징 오버헤드 (Distributed Pagination)**:
   - `ORDER BY date LIMIT 10 OFFSET 1000`을 날리면, 16개 샤드가 각각 1,010건씩 읽어서 라우터로 보내야 하므로 라우터 메모리가 OOM으로 폭사합니다.

## 4. 샤드 키(Shard Key) 선정의 3대 황금 원칙

샤딩을 설계할 때 가장 먼저 고려해야 할 3가지 원칙입니다:

### 1) 높은 카디널리티 (High Cardinality)
- 유니크한 값의 종류가 충분히 많아야 데이터가 특정 샤드로 쏠리지 않고 균등하게 분산(Uniform Distribution)됩니다.
- **나쁜 예**: `gender` (남/여 2종류 $\to$ 샤드 2개만 일하고 나머지 14개 놀음), `status` (활성/비활성).
- **좋은 예**: `user_id`, `account_id`, `uuid`.

### 2) 쿼리 격리성 (Query Isolation / Targeted Routing)
- 서비스 전체 트래픽의 80~90%를 차지하는 핵심 OLTP 쿼리가 샤드 키를 `WHERE` 조건에 포함하도록 설계해야 합니다.
- 이커머스/SNS는 유저 중심(User-centric)이므로 `user_id`로 샤딩해야 사용자의 주문, 장바구니, 프로필 조회가 **단 1개의 샤드로 직행(Fan-out = 1)**합니다.

### 3) 코로케이션 (Colocation / Co-sharding)
- 서로 자주 `JOIN`되는 부모-자식 테이블(예: `users`와 `orders`)을 **동일한 샤드 키(`user_id`)**로 샤딩하여 같은 물리 샤드 인스턴스에 나란히 저장합니다.
- 네트워크를 타고 다른 샤드의 테이블과 조인하는 **분산 크로스 샤드 조인(Distributed Cross-Shard Join)**을 원천 차단합니다.

---

## 5. 실무 비교 요약

| 점검 항목 | Date-Based 샤딩 (Naive) | User-Based 코로케이션 샤딩 (Optimal) |
| :--- | :--- | :--- |
| **사용자 주문 조회 (`WHERE user_id`)** | **전체 $S$개 샤드 팬아웃 (Scatter-Gather)** | **단 1개 샤드 직행 (Targeted Single-Shard)** |
| **샤드 쿼리 소모량** | 쿼리당 $S$회 소모 (CPU 낭비 극심) | **쿼리당 1회 소모 (최소 리소스)** |
| **샤드 추가 시 성능** | 샤드가 늘어날수록 팬아웃 비용 증가로 악화 | **샤드가 늘어날수록 완벽한 선형 확장 (Linear Scale)** |
| **테일 레이턴시** | 가장 느린 샤드에 끌려다님 ($\max(T_i)$) | **단일 노드 로컬 속도로 즉시 응답** |
| **분산 조인** | 불가능 (네트워크 셔플 필요) | **동일 샤드 내 초고속 로컬 조인 가능** |
