# DB 쿼리 1개가 조금 느려졌을 뿐인데 왜 전사 카프카 컨슈머가 올스톱되고 메시지가 무한 복제돼요?!: 카프카 컨슈머 리밸런스 폭풍(Kafka Consumer Rebalance Storm)과 max.poll.interval.ms & 협력적 스티키 리밸런싱(Cooperative Sticky Rebalance)

> "주문 이벤트를 처리하는 카프카 컨슈머 서버 3대를 운영하고 있습니다.  
> 평소에는 1초에 수천 건씩 시원하게 메시지를 빼가며 잘 돌고 있었습니다.  
> 그런데 특정 주문 건에서 결제 PG사 API 지연과 DB 슬로우 쿼리가 발생해 **메시지 1건을 처리하는 데 약 5분이 소요**되었습니다.  
> 그러자마자... **갑자기 전사 카프카 컨슈머 3대의 메시지 처리가 일제히 얼어붙고(Stop-The-World), 방금 결제 완료된 500건의 주문이 다른 서버에서 처음부터 다시 실행되어 유저들에게 결제가 중복 승인되는 초대형 금융 참사**가 터졌습니다!  
> 메시지 1건이 늦어졌을 뿐인데 왜 멀쩡하던 다른 서버들까지 멈추고 결제가 무한 중복 복제된 걸까요?!"

## 1. 전설의 카프카 리밸런스 폭풍 (Rebalance Storm)

아파치 카프카(Apache Kafka)를 실무 프로덕션 환경에 처음 도입한 개발팀이 가장 높은 확률로 경험하는 악몽이자, 중복 결제와 전사 파티션 먹통을 유발하는 1위 범인은 바로 **"카프카 컨슈머 리밸런스 폭풍(Consumer Rebalance Storm)"**입니다.

이 장애가 발생하는 근본적인 이유는 카프카가 컨슈머의 생사(Liveness)를 감지하는 독특한 **이중 스레드 아키텍처(KIP-62)**와, 고전적 **조급한 리밸런싱(Eager Rebalancing)**의 동작 방식 때문입니다.

---

## 2. KIP-62: 하트비트 스레드 vs 폴(Poll) 스레드의 분리

카프카 0.10.1 이전에는 하트비트 전송과 메시지 처리가 단일 스레드에서 이루어져, 메시지 처리가 조금만 길어져도 브로커가 "컨슈머가 죽었다"고 착각하는 문제가 있었습니다.  
이를 해결하기 위해 KIP-62에서 **하트비트 전송과 메시지 처리를 2개의 독립된 스레드로 분리**했습니다:

```
[카프카 컨슈머 프로세스]
   │
   ├── (1) 백그라운드 Heartbeat Thread ──► 브로커에게 주기적으로 "나 살아있어!" 핑 전송 (session.timeout.ms: 45초)
   │
   └── (2) 메인 메시지 처리 Poll Thread ──► poll()로 500개 레코드 가져와 for 루프로 비즈니스 로직 수행
```

### 🚨 새로운 함정: `max.poll.interval.ms` (기본값: 300,000ms = 5분)
- 백그라운드 하트비트 스레드가 아무리 정상적으로 하트비트를 보내고 있더라도,
- **메인 스레드가 `poll()`을 호출한 뒤 다음 `poll()`을 호출할 때까지 걸린 시간이 `max.poll.interval.ms`(5분)를 1ms라도 초과하면?**
- 카프카 브로커(Group Coordinator)는 다음과 같이 판단합니다:  
  *"하트비트는 오지만 메인 워커 스레드가 데드락에 걸렸거나 무한 루프에 빠져 일을 안 하고 있구나! 이 녀석을 컨슈머 그룹에서 강제 퇴출(Kick Out)시키고 파티션을 다른 서버에 넘겨야겠다!"*

## 3. 리밸런스 폭풍과 무한 중복 결제의 메커니즘

배치 크기 `max.poll.records = 500` 설정 상태에서 500개의 메시지를 가져와 순차 처리하던 중, 100번째 메시지에서 350초(5분 50초)짜리 DB 슬로우 쿼리가 터졌다고 가정해 봅시다:

```
[컨슈머 c1]
   │
   ├── 500개 메시지 poll() 인입 (Offset 0 ~ 499)
   ├── Offset 0 ~ 99번까지 100개 정상 처리 완료 (DB 저장 & 결제 완료)
   ├── Offset 100번 처리 중... (DB 락/외부 API 지연으로 350초 소요!)
   │
   ⏱️ 300초 경과! (max.poll.interval.ms 한도 초과!)
   │
[Group Coordinator (브로커)]
   │
   ├── "c1 응답 없음! 컨슈머 c1 강제 퇴출! 🚨 리밸런싱(Rebalance) 발동!"
   │
[전사 컨슈머 그룹 (c1, c2, c3)]
   │
   ├── 💥 Stop-The-World! Eager 리밸런싱으로 인해 모든 컨슈머의 모든 파티션 강제 회수!
   ├── c1이 처리 중이던 파티션 0이 컨슈머 c2에게 재할당!
   │
[컨슈머 c2]
   │
   ├── 파티션 0 할당받고 poll() 호출
   ├── c1이 100번까지 처리했지만 커밋(Commit)을 못 날리고 쫓겨났으므로,
   │   마지막 커밋 오프셋은 여전히 [0번]!
   │
   ├── 😱 c2가 Offset 0번부터 500개를 처음부터 다시 poll()!
   ├── 💥 Offset 0 ~ 99번 결제 로직이 또다시 중복 실행! (이중 결제 참사 발생!)
   ├── 그리고 Offset 100번 지연 메시지(Poison Pill)를 만나 또 350초 동안 멈춤!
   │
   ⏱️ 또 300초 초과! ──► c2 강제 퇴출! ──► 또 리밸런싱! ──► c3에게 재할당!
   │
[무한 연쇄 리밸런스 폭풍 (Rebalance Cascade Storm)]
전사 컨슈머가 5분마다 차례대로 폭사하고, 앞의 정상 메시지 수백 개가 무한 중복 실행됨!
```

## 4. 리밸런싱 프로토콜의 진화: Eager vs Cooperative Sticky

### ① 고전적 Eager Rebalance (조급한 리밸런싱)
- 리밸런스가 시작되면 컨슈머 그룹의 **모든 컨슈머가 자신이 쥐고 있던 모든 정상 파티션을 강제로 반납(Revoke)**해야 합니다.
- 리밸런싱이 끝날 때까지 수 초~수십 초 동안 **전사 메시지 처리가 100% 동결(Stop-The-World)**됩니다.

### ② Cooperative Sticky Assignor (KIP-429, 협력적 스티키 리밸런싱)
- Apache Kafka 2.4+부터 도입된 혁신적 프로토콜입니다.
- **문제가 된 컨슈머의 파티션만 핀포인트로 회수**하고, 문제없는 다른 컨슈머들은 자신이 처리하던 파티션을 **멈춤 없이 계속 처리**합니다 (Zero STW).
- 전체 파티션이 한꺼번에 멈추는 재앙을 방어합니다.

## 5. 실무 엔지니어링 3대 처방전

### ① `max.poll.records` 현실화 (가장 중요!)
- 카프카의 기본 `max.poll.records`는 **500개**입니다.
- 메시지 1건당 최악의 경우 1초가 걸린다면 500초(8.3분)가 걸려 무조건 `max.poll.interval.ms`(5분)를 초과합니다!
- **공식**: $	ext{max.poll.records} 	imes 	ext{p99 처리 시간} < 	ext{max.poll.interval.ms} 	imes 0.5$
- 무거운 외부 API/DB 처리를 한다면 `max.poll.records = 10 ~ 50`으로 과감하게 줄여야 합니다.

### ② `max.poll.interval.ms` 상향
- 배치 처리가 길어질 수밖에 없는 대용량 작업이라면, `max.poll.interval.ms`를 10분~30분(600,000ms ~ 1,800,000ms)으로 넉넉하게 늘려 불필요한 퇴출을 막아야 합니다.

### ③ 독약 메시지(Poison Pill) 격리와 사장 큐(DLQ, Dead Letter Queue)
- 특정 메시지가 예외나 타임아웃을 유발해 반복적으로 리밸런스를 일으키는 경우, 최대 재시도 횟수(`max_delivery_attempts`, 보통 3회)를 초과하면 해당 메시지를 **DLQ(Dead Letter Queue) 토픽으로 격리**하고 오프셋을 전진시켜야 파티션 전체가 동결되는 연쇄 폭풍을 끊을 수 있습니다.
