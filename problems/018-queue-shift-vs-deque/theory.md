# [ZeliJudge CS 백서 #018] 롤러코스터 대기열과 50억 번의 발걸음: list.pop(0) vs collections.deque

> **"맨 앞사람 한 명이 나갔다고 해서, 뒤에 선 10만 명이 전부 짐을 싸서 앞으로 한 걸음씩 이사할 필요는 없다."**

## 🎢 1. 일상 비유: 롤러코스터 대기열과 게이트 팻말

어느 초대형 테마파크에 10만 명의 손님이 롤러코스터를 타기 위해 1열로 줄을 길게 늘어섰습니다.
두 명의 놀이공원 알바생이 대기열을 관리하는 방식입니다:

* **알바생 A (비효율적인 list.pop(0))**:
  - 맨 앞 1번 손님이 롤러코스터에 탑승하자마자 메가폰을 잡고 외칩니다:
    > *"맨 앞자리 비었습니다! 뒤에 계신 **99,999명 손님 여러분, 전부 짐 들고 앞으로 한 발자국씩 걸어서 이동하세요!**"*
  - 다음 손님이 타자 또 외칩니다:
    > *"앞자리 비었습니다! 뒤에 계신 **99,998명 손님 여러분, 다시 한 발자국씩 앞으로 이동하세요!**"*
  - 손님들은 롤러코스터를 타기도 전에 수만 걸음을 걷다가 지쳐 쓰러집니다.
* **알바생 B (최적화된 collections.deque)**:
  - 손님들에게 외칩니다:
    > *"손님 여러분, 힘들게 걷지 마시고 **자기 자리에 편안하게 그대로 서 계세요!**"*
  - 그리고 알바생은 손에 든 **'입장 탑승구 팻말(포인터)'을 2번 손님 앞으로 슥 한 칸 옮깁니다.**

이것이 바로 파이썬의 기본 `list`와 `collections.deque`가 컴퓨터 메모리를 다루는 결정적 차이입니다.

## 🧱 2. 동적 배열(Dynamic Array)의 메모리 물리 구조

파이썬의 `list`는 내부적으로 C 언어의 **동적 배열(Dynamic Array)**로 구현되어 있습니다.
동적 배열의 가장 큰 특징은 **"메모리 상에 모든 원소가 빈틈없이 연속(Contiguous)으로 붙어 있다"**는 점입니다:

```text
[RAM 메모리 주소]
  0x1000 : [userA] (인덱스 0)
  0x1008 : [userB] (인덱스 1)
  0x1010 : [userC] (인덱스 2)
  0x1018 : [userD] (인덱스 3)
```

### 왜 list[i] 조회는 초고속 O(1)인가?
메모리가 따닥따닥 붙어 있기 때문에, 1,000번째 원소를 찾을 때 하나씩 셀 필요 없이 수학 공식 `시작주소 + (1000 * 8바이트)`로 1번 만에 주소를 계산해 찾아갈 수 있습니다.

### 하지만 맨 앞 원소(pop(0))를 빼면 무슨 일이 벌어질까?
`0x1000` 번지에 있던 `userA`가 빠져나가면 배열의 첫 자리에 구멍(공백)이 생깁니다.
배열은 연속성을 유지해야 하므로, CPython 인터프리터는 C 언어의 `memmove()` 함수를 호출하여 **뒤에 있는 모든 원소를 왼쪽 메모리로 한 칸씩 복사해서 이동(Memory Shift)**시킵니다:

```text
userA 삭제 직후:
  [ 빈자리 ] <- [userB] <- [userC] <- [userD]  (모든 원소가 왼쪽으로 복사 이동!)
```

원소가 $N$개일 때, `pop(0)` 1번을 수행하면 **$N - 1$번의 메모리 복사 이동**이 강제로 발생합니다 ($O(N)$).

## 🧮 3. 가우스 덧셈의 저주: 왜 50억 번인가?

10만 명($N=100,000$)의 대기열에서 손님들을 차례대로 모두 `pop(0)`으로 내보낸다고 상상해 봅시다:
- 첫 번째 손님 퇴장: 뒤에 선 99,999명 이동
- 두 번째 손님 퇴장: 뒤에 선 99,998명 이동
- ...
- 99,999번째 손님 퇴장: 뒤에 선 1명 이동
- 100,000번째 손님 퇴장: 0명 이동

총 메모리 복사 이동 횟수는 다음과 같습니다:
$$\text{Total Shifts} = \sum_{i=1}^{N-1} i = \frac{(N-1) \times N}{2} = \frac{99,999 \times 100,000}{2} = 4,999,950,000 \approx \mathbf{50\text{억 번!}}$$

현대 고성능 컴퓨터 CPU가 1초에 수행할 수 있는 연산은 약 $10^8$번(1억 번) 내외입니다.
즉, 단순한 대기열 10만 명을 비우는 데 **순수 CPU 연산만 최소 50초 이상** 걸리며, 서버는 즉시 응답 불가(Timeout) 상태로 뻗어버립니다 ($O(N^2)$).

## 🚀 4. 구원투수: collections.deque의 비밀

파이썬 표준 라이브러리인 `collections.deque`(Double-Ended Queue)는 메모리를 다르게 관리합니다.
연속된 하나의 거대한 배열 대신, **64개 단위의 작은 블록(청크)들이 앞뒤로 사슬처럼 엮인 이중 연결 리스트(Doubly Linked List)** 구조를 가집니다.

```text
[블록 1] <---> [블록 2] <---> [블록 3]
```

### deque.popleft()의 원리:
1. 맨 앞 원소를 뺄 때, 뒤에 있는 수만 개의 원소를 복사해서 당기지 않습니다!
2. 블록 내부의 **'시작 인덱스 포인터'만 1 증가**시키고 끝납니다.
3. 블록 안의 64개 원소가 모두 비워지면 그 작은 블록 하나만 메모리에서 해제하고 다음 블록으로 연결 사슬을 넘깁니다.

결과적으로, 대기열에 10만 명이 있든 1,000만 명이 있든 **원소 시프트는 정확히 0회**이며, 항상 단 1번의 연산인 **$O(1)$**로 즉시 완료됩니다!

## 🏆 5. 실무 가이드: list vs deque 선택 공식

| 상황 / 요구사항 | 추천 자료구조 | 이유 |
| :--- | :--- | :--- |
| 임의의 인덱스 조회 빈번 (`arr[42]`, `arr[999]`) | **`list`** | 메모리 연속성 덕분에 $O(1)$ 초고속 인덱싱 지원 |
| 선입선출(FIFO) 큐, 대기열, 작업 큐 | **`collections.deque`** | `append()`와 `popleft()` 모두 $O(1)$ 보장 |
| 너비 우선 탐색 (BFS 알고리즘) | **`collections.deque`** | 그래프 탐색 시 노드 큐의 $O(1)$ Dequeue 필수 |
| 최근 $K$개 항목만 유지하는 버퍼 | **`collections.deque(maxlen=K)`** | 용량 초과 시 오래된 원소 자동 $O(1)$ 축출 |

> **"파이썬 코드에서 `queue.pop(0)` 또는 `queue.insert(0, val)`을 적는 순간, 당신은 서버에 50억 번의 지옥 행군을 명령하고 있는 것이다. 큐가 필요하다면 무조건 `from collections import deque`를 선언하라!"**
