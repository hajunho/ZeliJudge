> **"컨슈머 팟 한 대 롤링 배포했을 뿐인데, 왜 3분 동안 전사 메시지 처리가 멈췄을까요?!"**  
> **"의자 뺏기 놀이(Eager Rebalance)의 비극 vs 자기 자리를 지키는 협력적 스티키 할당(Cooperative Sticky)"**

## 1. 현실 세계 비유: 사무실 의자 뺏기 놀이 vs 조용한 자리 양보

12명의 직원(컨슈머)이 12개의 전담 모니터(파티션)를 보며 고객 주문을 실시간으로 처리하고 있는 콜센터가 있습니다.

```
[구버전 Eager Rebalance (의자 뺏기 놀이)]
새로운 신입 직원 C13이 사무실 문을 열고 들어왔습니다.

팀장이 갑자기 호루라기를 삑-! 붑니다:
"전원 하던 일 즉시 멈추고(Stop-The-World), 의자에서 일어나서 복도로 나가세요!" (Revoke All Partitions)

기존 12명의 직원은 고객 통화를 강제로 끊고 복도로 쫓겨납니다.
복도에서 13명이 다 모일 때까지 수 분 동안 대기합니다. (JoinGroup & SyncGroup 지연)
그리고 제비뽑기를 해서 다시 자리에 들어갑니다.

황당한 점은, 방금 앉아있던 자리로 다시 돌아갈 확률이 매우 높은데도, 
책상 위 서류를 전부 치우고 다시 까느라 3분 동안 회사 콜센터 전화가 올스톱되었습니다!
```

더 끔찍한 재앙은 지금부터입니다.  
**쿠버네티스(K8s) 환경에서 컨슈머 팟 10대를 순차 롤링 배포**하면 어떻게 될까요?
1. 팟 1번 재시작 $\to$ **전원 복도로 퇴출! (30초 정지)**
2. 팟 1번 들어옴 $\to$ **전원 복도로 퇴출! (30초 정지)**
3. 팟 2번 재시작 $\to$ **전원 복도로 퇴출! (30초 정지)**  
$\dots$  
결과: 배포가 끝날 때까지 10분 넘게 전사 메시지 처리가 마비되는 **리밸런싱 폭풍(Rebalance Storm)**이 몰아치고, 카프카 랙(Consumer Lag)은 수천만 건으로 폭증하여 서버가 폭사합니다!

```
[모던 Cooperative Sticky Rebalance (협력적 스티키 할당)]
신입 직원 C13이 들어오자, 팀장이 조용히 귓속말을 합니다:
"기존 12분은 하던 일 0.1초도 멈추지 마시고 계속 통화하세요." (Zero Downtime)
"단, 가장 많은 모니터를 보던 C1님만 모니터 1개만 조용히 신입에게 넘겨주세요." (Cooperative Revocation)

결과: 11명의 직원은 단 1초의 중단도 없이 계속 일했고, 딱 1개의 모니터만 조용히 이관되었습니다!
```

## 2. Apache Kafka의 파티션 할당과 리밸런싱 메커니즘

### 1) 컨슈머 그룹과 파티션
카프카에서 토픽의 파티션들은 컨슈머 그룹 내의 컨슈머들에게 1:N으로 배정됩니다.  
- 파티션 $N$개, 컨슈머 $M$개일 때, 각 컨슈머는 대략 $N/M$개의 파티션을 전담하여 소비합니다.
- 그룹 내 컨슈머의 수가 바뀌면(스케일아웃, 스케일인, 크래시, 네트워크 순단), 파티션을 다시 공평하게 나누는 **리밸런싱(Rebalance)**이 일어납니다.

### 2) Eager Rebalance의 치명적 결함 (Kafka 2.3 이전 기본값)
과거 카프카의 기본 할당자(`RangeAssignor`, `RoundRobinAssignor`)는 **Eager Rebalance 프로토콜**을 따랐습니다:

```
[Eager Rebalance의 3단계 Stop-The-World]
1. Revoke Phase: 모든 살아있는 컨슈머가 자신이 소유한 모든 파티션을 일제히 반환 (Revoke All!)
2. Join & Sync Phase: 모든 컨슈머가 그룹 코디네이터(브로커)에 재참여 요청 (메시지 소비 완전 중단)
3. Assign Phase: 백지상태에서 파티션을 처음부터 끝까지 다시 분배
```

- **Stop-The-World 다운타임**: 리밸런싱 시간 동안 그룹 전체의 파티션 소비가 100% 올스톱됩니다.
- **캐시 무효화 및 오버헤드**: 컨슈머 메모리에 캐싱해 둔 데이터(로컬 상태, DB 커넥션, 배치 버퍼)가 모조리 날아가고, 새 파티션을 받으면 처음부터 오프셋을 읽고 캐시를 다시 워밍업해야 합니다.
- **파티션 뒤섞기(Shuffle)**: 원래 자기가 잘 처리하고 있던 파티션이 엉뚱한 컨슈머로 넘어가 버립니다.

## 3. 혁신: KIP-429 협력적 스티키 리밸런싱 (Cooperative Sticky)

아파치 카프카 커뮤니티는 2019년 **KIP-429**를 통해 혁신적인 **협력적 스티키 할당자(`CooperativeStickyAssignor`)**를 도입했습니다.

### 1) 두 가지 핵심 철학
1. **협력적(Cooperative)**:  
   전체 파티션을 일괄 반환하지 않고, **소유권 이전이 반드시 필요한 파티션만 선별적으로 반환**합니다.  
   이동하지 않는 파티션은 리밸런싱 도중에도 단 0.1초도 멈추지 않고 계속 소비됩니다!
2. **스티키(Sticky)**:  
   파티션을 재배치할 때 **기존에 담당하던 컨슈머에게 가능한 한 그대로 유지**시킵니다.  
   파티션의 소유권 변경을 수학적으로 최소화합니다.

### 2) 비교 지표: Eager vs Cooperative Sticky

| 비교 항목 | Eager Rebalance | Cooperative Sticky |
| :--- | :--- | :--- |
| **파티션 반환 방식** | **모든 컨슈머의 모든 파티션 일괄 반환 (Revoke All)** | **초과 보유 컨슈머의 일부 파티션만 선별 반환** |
| **리밸런싱 중 메시지 소비** | **전면 중단 (Stop-The-World)** | **영향받지 않는 파티션은 100% 무중단 소비** |
| **K8s 롤링 배포 시** | 리밸런싱 폭풍 $\to$ Consumer Lag 폭증 $\to$ 장애 | **Lag 증가 없이 부드럽게 무중단 롤링 완료** |
| **파티션 이동 횟수(Migrations)** | 매우 높음 (전체 재셔플) | **이론상 최소치 (Minimal Transitions)** |
| **로컬 캐시 보존율** | 0% (모두 증발) | **80~95% 이상 보존** |

## 4. 실무 프로덕션 권장 설정 (Kafka Consumer)

스프링 부트(Spring Boot)나 카프카 클라이언트 설정 시 기본값을 반드시 점검해야 합니다:

```properties
# 최신 카프카 프로덕션 표준 설정
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# 하트비트 세션 타임아웃 (너무 짧으면 찰나의 GC 멈춤에도 리밸런싱 유발)
session.timeout.ms=45000
heartbeat.interval.ms=15000
max.poll.interval.ms=300000
```

> **"카프카 컨슈머의 `CooperativeStickyAssignor` 단 한 줄 설정이,  
> 당신의 쿠버네티스 롤링 배포 시간을 10분에서 30초로 단축시키고 Consumer Lag 장애를 99% 영구 박멸합니다."**
