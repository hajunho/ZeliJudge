# Raft 분리 노드 재선출 스톰(Re-election Storm)과 Pre-Vote 프로토콜

## 1. 개요: 분산 합의 알고리즘과 Raft의 리더 중심 아키텍처

현대 분산 시스템(Kubernetes의 `etcd`, TiDB의 `TiKV`, CockroachDB, Kafka의 `KRaft`)은 고가용성과 강한 일관성(Linearizable Consistency)을 보장하기 위해 **Raft 분산 합의 알고리즘(Raft Consensus Algorithm)**을 표준으로 채택하고 있습니다.

Raft는 복잡한 Paxos 대비 이해 가능성(Understandability)을 최우선 목표로 설계되었으며, 그 핵심은 **강력한 단일 리더(Strong Leader)** 모델입니다:
- 클러스터 내에는 특정 임기(Term) 동안 오직 **단 하나의 합법적인 리더(Leader)**만이 존재합니다.
- 모든 클라이언트의 읽기/쓰기 요청은 리더를 통해서만 처리되며, 리더는 복제 로그(Replicated Log)를 팔로워(Follower)들에게 단방향으로 전파(`AppendEntries`)합니다.
- 리더는 주기적으로 빈 `AppendEntries` 메시지인 **하트비트(Heartbeat)**를 브로드캐스트하여 자신의 리더십 권한(Leader Lease)을 갱신하고, 팔로워들의 선출 타이머(Election Timer)가 만료되지 않도록 억제합니다.

```
+-----------------------------------------------------------------------+
|                     Raft 기본 3상태 머신 (Standard Raft)              |
+-----------------------------------------------------------------------+
|                                                                       |
|      +------------------+   선출 타이머 만료    +-------------------+   |
|      |                  | --------------------> |                   |   |
|      |     FOLLOWER     |                       |     CANDIDATE     |   |
|      |                  | <-------------------- |                   |   |
|      +------------------+    더 높은 Term 발견   +-------------------+   |
|               ^                                           |           |
|               |                                           | 과반수 투표 |
|               |         더 높은 Term 발견                  | 획득 성공  |
|               +-------------------------------------------+           |
|                               |                           |           |
|                               v                           v           |
|                     +---------------------------------------+         |
|                     |                LEADER                 |         |
|                     +---------------------------------------+         |
+-----------------------------------------------------------------------+
```

## 2. 참사의 발단: 표준 Raft의 치명적 취약점 - 분리 노드 재선출 스톰

Diego Ongaro의 Stanford 박사 학위 논문(*"Consensus: Bridging Theory and Practice"*, Section 9.6)에서는 오리지널 Raft 논문(USENIX ATC '14)에 기술된 표준 규칙이 특정 네트워크 장애 상황에서 **전체 클러스터를 마비시키는 치명적인 리더 축출 스톰(Disrupted Node Re-election Storm)**을 유발한다고 경고합니다.

### 2.1 Raft의 불변 규칙: 고임기(Higher Term) 우선 원칙
표준 Raft 명세(Section 5.1)는 다음과 같은 절대적인 규칙을 정의합니다:
$$\text{If an incoming RPC request or response has } T > \text{currentTerm}:$$
$$\text{currentTerm} \gets T, \quad \text{role} \gets \text{FOLLOWER}, \quad \text{votedFor} \gets \text{null}$$

이 규칙은 이전 리더가 네트워크 단절에서 복구되었을 때, 신규 선출된 최신 리더에게 즉시 복종하도록 강제하는 필수적인 안전장치입니다. **그러나 이 규칙이 네트워크 단절 노드와 결합하면 재앙으로 돌변합니다.**

### 2.2 비대칭 네트워크 파티션(Asymmetric Network Partition) 참사
클라우드 인프라(AWS/GCP/Kubernetes)에서는 가상 브릿지 고장, 스위치 포트 단방향 패킷 드랍, 방화벽(iptables/ebpf) Conntrack 누락 등으로 인해 **"단방향 통신만 가능한 비대칭 파티션"**이 빈번하게 발생합니다.

```
 [Leader: node1] --- (하트비트 전송 불가 / 패킷 드랍) ---> [node5] (인바운드 먹통)
       |                                                    |
       | <============= (RequestVote 송신 가능!) ============+ (아웃바운드 정상)
       v
 [Followers: node2, node3, node4] (정상 작동 중)
```

1. **상황**: 5대 노드 중 `node1`이 정상 리더이고 `node2, node3, node4`와 정상 통신 중입니다. `node5`의 네트워크 수신(Inbound) 인터페이스만 고장나서 하트비트를 받지 못하지만, 송신(Outbound)은 정상입니다.
2. **선출 타이머 만료**: `node5`는 하트비트를 받지 못하므로 선출 타이머(예: 150ms)가 만료됩니다.
3. **무차별 Term 인플레이션**:
   - `node5`는 즉시 자신의 Term을 1에서 2로 증가시키고 `CANDIDATE`로 변환합니다.
   - `node5`는 모든 피어(`node1 ~ node4`)에게 `RequestVote(term=2)`를 브로드캐스트합니다.
4. **정상 리더의 강제 폐위(Demotion)**:
   - 멀쩡히 클라이언트 트래픽을 처리하던 `node1`이 `node5`의 `RequestVote(term=2)`를 수신합니다.
   - $2 > 1$이므로, `node1`은 즉시 리더십을 박탈당하고 **`FOLLOWER`로 강제 강등**됩니다!
   - 클러스터의 활성 리더가 사라집니다!
5. **투표 불발과 선출 루프**:
   - `node5`는 인바운드가 먹통이므로 동료들의 투표 응답을 받지 못해 과반수를 얻지 못하고 실패합니다.
   - 클러스터에 리더가 없으므로 클라이언트의 모든 쓰기 요청은 `NO_LEADER` 에러를 뿜으며 거부됩니다.
   - 150ms 뒤 `node5`의 선출 타이머가 또 만료됩니다 $\to$ 이번엔 `term=3`으로 올리고 또 브로드캐스트!
   - 클러스터는 영원히 새로운 리더를 안정적으로 유지하지 못하고 무한 재선출 지옥에 빠집니다.

### 2.3 소수 파티션 격리 후 재결합 스톰(Minority Reconnection Storm)
비대칭 파티션이 아니더라도, 단순 네트워크 순단으로 소수 노드(`node4, node5`)가 잠시 고립된 경우에도 동일한 참사가 터집니다:
- 과반수(`node1, node2, node3`)는 정상적으로 쿼리를 처리하며 `term=1`을 유지합니다.
- 고립된 `node4`는 하트비트가 오지 않으므로 매 선출 주기(150ms, 300ms, 450ms...)마다 타임아웃되어 `term`을 2, 3, 4, 5로 폭발적으로 인플레이션시킵니다.
- 잠시 후 네트워크 파티션이 정상 복구(Heal)되어 `node4`가 클러스터에 복귀하는 순간:
  `node4`가 던진 `term=5` 메시지를 받은 합법적인 리더 `node1`은 즉시 리더 자리를 빼앗기고 팔로워로 전락합니다.
- 멀쩡하던 서비스가 **"네트워크가 복구되는 순간" 갑자기 수 초간 중단되는 역설적인 장애**가 발생합니다.

## 3. 구원: Pre-Vote 프로토콜 (Diego Ongaro Dissertation Section 9.6)

이 문제를 해결하기 위해 고안된 기법이 바로 **Pre-Vote 프로토콜(Pre-Vote Protocol)**입니다.

```
+-----------------------------------------------------------------------+
|                    Pre-Vote 확장 상태 머신 (Pre-Vote Raft)             |
+-----------------------------------------------------------------------+
|                                                                       |
|      +------------------+  선출 타이머 만료   +--------------------+     |
|      |     FOLLOWER     | -----------------> |   PRE_CANDIDATE    |     |
|      |                  |                    | (Term 증가 금지!)  |     |
|      +------------------+                    +--------------------+     |
|               ^                                        |              |
|               | PreVote 거부                           | PreVote 과반수 |
|               | (원상 복귀)                            | 획득 성공     |
|               +----------------------------------------+              |
|                                                        |              |
|                                                        v              |
|                                              +--------------------+   |
|                                              |     CANDIDATE      |   |
|                                              | (공식 Term 증가!)  |   |
|                                              +--------------------+   |
|                                                        |              |
|                                                        | 과반수 투표  |
|                                                        | 획득 성공    |
|                                                        v              |
|                                              +--------------------+   |
|                                              |       LEADER       |   |
|                                              +--------------------+   |
+-----------------------------------------------------------------------+
```

### 3.1 Pre-Vote의 핵심 원리
1. **신규 상태 도입 (`PRE_CANDIDATE`)**:
   선출 타이머가 만료되었을 때, 노드는 곧바로 `term`을 올리고 `CANDIDATE`가 되지 않습니다. 대신 가상 후보 상태인 **`PRE_CANDIDATE`**로 전환합니다.
2. **Term 보존 및 가상 임기 질의**:
   노드는 자신의 실제 `currentTerm`을 증가시키지 않습니다. 가상의 차기 임기($\text{targetTerm} = \text{currentTerm} + 1$)를 담아 피어들에게 사전 투표(`PreRequestVote`)를 요청합니다.
3. **수신 노드의 2단계 검증 게이트**:
   `PreRequestVote`를 수신한 피어 노드는 다음 **두 가지 조건**을 모두 만족할 때만 사전 투표를 승인합니다:
   - **조건 1: 리더 임대(Leader Lease / Heartbeat Recency) 검증**
     수신 노드가 최근 `election_timeout` 이내에 현재 합법적인 리더로부터 유효한 하트비트를 수신한 상태라면, **Pre-Vote를 단호히 거부(REJECT)**합니다!
     *(이유: 현재 리더가 멀쩡히 살아있으므로, 새로운 선출은 클러스터에 불필요한 혼란을 초래하는 소음일 뿐입니다.)*
   - **조건 2: 로그 완전성(Log Completeness) 검증 (Raft Section 5.4.1)**
     후보의 로그가 수신 노드의 로그보다 최소한 동등하거나 더 최신이어야 합니다.
     $$\text{candLastTerm} > \text{recvLastTerm} \quad \lor \quad (\text{candLastTerm} == \text{recvLastTerm} \land \text{candLastIndex} \ge \text{recvLastIndex})$$
4. **자문적 성격(Advisory Semantics)**:
   Pre-Vote를 승인하거나 거부하더라도, 수신 노드의 실제 `currentTerm`이나 `votedFor`는 **절대로 변경되지 않습니다.**
5. **과반수 획득 시에만 정식 출마**:
   오직 피어들의 **과반수(Majority)**로부터 Pre-Vote 승인을 얻어낸 경우에만, 클러스터가 실제로 리더를 필요로 하고 자신이 당선될 자격이 있음을 확신하고 정식 `CANDIDATE`로 승격하여 실제 `currentTerm`을 증가시키고 본 선출(`RequestVote`)을 시작합니다.
   과반수를 얻지 못하면 조용히 `FOLLOWER`로 복귀합니다.

## 4. 표준 Raft vs Pre-Vote Raft 동작 비교

| 장애 시나리오 | 표준 Raft (Standard Raft) | Pre-Vote Raft (Diego Ongaro 9.6) |
| :--- | :--- | :--- |
| **비대칭 파티션 (1대 인바운드 먹통)** | 고립 노드가 주기적으로 Term 증가 후 본투표 요청 $\to$ **멀쩡한 리더가 폐위되어 클러스터 마비** | 고립 노드의 PreVote가 피어들의 리더 임대 검증에 걸려 **전원 거부 $\to$ 리더 100% 보존** |
| **소수 파티션 장기 격리 후 복귀** | 격리 동안 부풀려진 거대 Term($T=5$) 메시지 도착 $\to$ **복귀 순간 리더 강제 폐위 및 재선출 다운타임** | 격리 동안 PreVote 실패로 Term($T=1$) 보존 $\to$ **복귀 시 리더의 하트비트를 받고 무혈 흡수** |
| **낙후된 로그 노드의 재선출 시도** | 고임기 메시지로 인해 기존 리더 폐위 $\to$ 이후 본투표는 로그 부족으로 낙선 $\to$ **불필요한 리더십 공백** | PreVote 단계에서 로그 검증 실패로 사전 차단 $\to$ **기존 리더와 클러스터에 0ms 영향** |
| **진짜 리더 장애 (Crash/Partition)** | 팔로워 선출 타이머 만료 후 선출 돌입 $\to$ 신규 리더 선출 | 모든 팔로워의 리더 임대가 만료된 상태이므로 **PreVote 과반 승인 $\to$ 지체 없이 신규 리더 선출** |

## 5. 엔터프라이즈 분산 시스템의 실제 적용

1. **Kubernetes & etcd**:
   `etcd`는 v3.4부터 Pre-Vote 플래그(`raft.PreVote = true`)를 기본 활성화했습니다. 대규모 쿠버네티스 클러스터에서 노드 네트워크 깜빡임이나 kubelet 재시작 시 컨트롤 플레인의 etcd 리더가 핑퐁 치며 API Server 응답이 지연되던 현상을 원천 차단했습니다.
2. **PingCAP TiKV (Distributed HTAP Database)**:
   TiKV는 수천 개의 Raft 그룹(Multi-Raft)을 구동합니다. 단 하나의 노드가 순간적으로 GC STW(Stop-The-World)를 겪거나 패킷 손실이 발생했을 때 수백 개 리전(Region)의 리더가 일제히 폐위되는 대참사를 방지하기 위해 Raft Engine 레벨에서 Pre-Vote를 필수로 강제합니다.
3. **CockroachDB & Apache Ratis**:
   Raft 리더 리스(Leader Lease)와 Pre-Vote를 결합하여 불필요한 선출을 99.99% 억제하고, 네트워크 분할 환경에서도 0-Downtime Linearizable Read/Write를 달성합니다.
