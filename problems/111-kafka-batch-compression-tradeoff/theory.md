# [배경 이론] 카프카 배치 압축 알고리즘 트레이드오프: GZIP vs Snappy vs LZ4 vs Zstandard

## 1. 현실 비유: 택배 포장 센터와 화물 트럭의 전쟁

대형 이커머스 물류 센터에서 매일 수천만 개의 택배 상자를 전국으로 발송한다고 상상해 보세요.

- **방법 1: 압축 없이 그냥 박스에 담아 보내기 (`none`)**
  - 포장 작업자(CPU)는 상자에 물건 넣고 테이프만 붙이면 되므로 **초당 수천 개를 초고속으로 처리**합니다.
  - 하지만 상자 부피가 너무 커서 화물 트럭(네트워크 대역폭)이 몇 개 싣지도 못하고 가득 차 버립니다.
  - 고속도로 요금과 트럭 대여비(네트워크 비용, AWS 데이터 전송 비용)가 수억 원씩 청구됩니다.

- **방법 2: 초강력 진공 압축기로 공기를 싹 빼서 보내기 (`gzip`)**
  - 상자 부피가 70~80%나 줄어들어 트럭 한 대에 어마어마한 양을 실을 수 있습니다. 트럭 운송료는 극적으로 절감됩니다.
  - 하지만 진공 압축기를 돌리는 데 **전력과 시간(CPU 소모와 압축 지연 시간)**이 너무 많이 듭니다. 포장대 앞에서 대기 줄이 길어지고 물류 센터 전체 작업 속도가 곤두박질칩니다.

- **방법 3: 번개처럼 빠른 경량 압축기 (`snappy` / `lz4`)**
  - 진공 압축기만큼 극적으로 줄어들지는 않지만(40~60% 감소), 압축 속도와 압축 해제 속도가 눈 깜짝할 새(초당 수백 MB)에 끝납니다.
  - 포장 작업자(CPU)도 지치지 않고 트럭 적재량(네트워크 대역폭)도 2배 이상 늘어납니다. 현대 엔터프라이즈 카프카 파이프라인에서 가장 널리 쓰이는 표준 방식입니다.

- **방법 4: 상황에 따라 세기를 조절하는 스마트 압축기 (`zstandard` / `zstd`)**
  - 메타(Facebook)에서 개발한 차세대 알고리즘입니다. 압축 레벨(1~22)을 조절하여 "LZ4급 초고속"부터 "GZIP을 능가하는 고압축"까지 자유롭게 튜닝할 수 있습니다.

## 2. 카프카의 핵심 설계: 배치(RecordBatch) 단위 압축

많은 초보 개발자가 **"카프카는 메시지 하나를 보낼 때마다 그 메시지를 압축한다"**고 오해합니다.  
하지만 카프카 프로듀서는 **레코드(Record) 개별 압축이 아니라 배치(RecordBatch) 단위로 압축**합니다.

```
[프로듀서 RecordAccumulator 메모리 버퍼]
  +-------------------------------------------------------+
  | Record #1 (JSON: {"userId": 101, "event": "click"})  |
  | Record #2 (JSON: {"userId": 102, "event": "view"})   |
  | Record #3 (JSON: {"userId": 103, "event": "click"})  |
  +-------------------------------------------------------+
                            │
                            ▼ (batch.size 또는 linger.ms 도달 시)
  +───────────────────────────────────────────────────────+
  |              RecordBatch 통째로 일괄 압축              |
  |  LZ4 / Snappy / GZIP / ZSTD 알고리즘 사전(Dictionary)   |
  |  공통 JSON 키 ("userId", "event", "click") 중복 제거  |
  +───────────────────────────────────────────────────────+
                            │
                            ▼ (네트워크 전송)
                        [카프카 브로커]
```

### 왜 배치 단위로 압축해야 할까요?
1. **압축 사전(Dictionary) 효율성 극대화**:
   - 50바이트짜리 단일 JSON 메시지를 압축하면 압축 알고리즘 헤더 오버헤드 때문에 **오히려 크기가 60바이트로 늘어나는 현상(Negative Compression)**이 발생합니다.
   - 하지만 16KB~1MB 크기의 배치로 모아서 압축하면 `"timestamp"`, `"service_id"`, `"user_agent"` 등 수많은 중복 키와 텍스트가 거대한 하나의 사전으로 묶여 압축 효율이 기하급수적으로 증가합니다.
2. **네트워크 패킷 헤더 오버헤드 감소**:
   - 단일 레코드마다 TCP 패킷을 쏘는 대신, 고밀도로 압축된 단 하나의 대형 TCP 세그먼트로 전송하므로 네트워크 왕복(RTT) 및 패킷 오버헤드가 급감합니다.

## 3. 종단간 압축(End-to-End Compression)과 Zero-Copy

카프카의 경이로운 처리량(Throughput) 비결 중 하나는 **종단간(End-to-End) 압축 아키텍처**입니다.

```
[프로듀서]                 [카프카 브로커]                  [컨슈머]
   │                              │                            │
 1. 압축 수행 (CPU 소모)            │                            │
   │                              │                            │
   ├─── 압축된 RecordBatch 전송 ───►│                            │
   │                              │ 2. 브로커는 압축을 풀지 않음!   │
   │                              │    (Zero-Copy sendfile로   │
   │                              │     OS Page Cache에 기록)  │
   │                              │                            │
   │                              ├─── 압축된 채로 그대로 전송 ───►│
   │                              │                            │ 3. 컨슈머가 직접 압축 해제
   │                              │                            │    (CPU 소모)
```

- 프로듀서가 한 번 압축하면, 브로커는 **그 압축을 절대 풀지 않고 바이트 그대로 디스크와 OS 페이지 캐시에 씁니다**.
- 컨슈머가 데이터를 읽어갈 때도 브로커는 CPU를 쓰지 않고 리눅스 커널의 `sendfile()` Zero-Copy 시스템 콜을 사용해 네트워크 카드로 바로 쏩니다.
- 실제 압축 해제는 데이터를 최종 소비하는 컨슈머가 수행합니다.

## 4. 실무 최악의 장애: 브로커 리컴프레션(Broker Recompression Hazard)

브로커의 토픽 설정에는 `compression.type`이 있습니다. 이 설정의 기본값은 `producer`입니다.  
`producer`로 설정되어 있으면 프로듀서가 보낸 압축 포맷을 브로커가 존중하여 그대로 보관합니다.

### 💥 대참사 시나리오: 브로커 코덱 강제 변경
인프라 관리자가 "디스크 용량을 아끼겠다"며 브로커 설정을 `compression.type=gzip`으로 강제 변경했다고 가정해 봅시다.  
그런데 수백 대의 프로듀서 애플리케이션은 기본값인 `snappy`나 `lz4`로 메시지를 쏘고 있습니다.

1. 브로커가 프로듀서로부터 `Snappy`로 압축된 배치를 수신합니다.
2. 브로커는 디스크에 `Gzip`으로 저장해야 하므로, **Snappy 압축을 브로커 CPU로 직접 풉니다(Decompress)**!
3. 그리고 브로커 CPU를 풀가동하여 **Gzip으로 다시 압축(Recompress)**합니다!
4. **결과**:
   - 브로커 CPU 점유율 100% 폭발!
   - 브로커가 프로듀서의 요청을 처리하지 못해 타임아웃 발생!
   - 파티션 리더가 죽고 ISR(In-Sync Replicas)이 붕괴하는 연쇄 장애 발생!

> **실무 황금률**: 특별한 사유가 없는 한 브로커의 `compression.type`은 반드시 `producer`로 유지해야 합니다.

## 5. 압축 알고리즘 4대장 정량 비교 요약

| 알고리즘 | 압축률 (JSON 기준) | 압축 속도 (CPU 소모) | 압축 해제 속도 | 추천 사용 시나리오 |
| :--- | :---: | :---: | :---: | :--- |
| **`none`** | 0% (원문 그대로) | 없음 (CPU 0) | 없음 | 로컬 개발 환경, 네트워크 대역폭이 무제한인 내부망 |
| **`snappy`** | 약 40~50% 감소 | 매우 빠름 (CPU 최저) | 매우 빠름 | CPU 리소스가 극히 제한된 마이크로서비스 프로듀서 |
| **`lz4`** | 약 50~60% 감소 | 빠름 (CPU 낮음) | **초고속 (압축의 2~3배)** | **카프카 실무 표준 (Default 권장)**, 고처리량 스트리밍 |
| **`gzip`** | **약 70~80% 감소** | 매우 느림 (CPU 극심) | 느림 | 네트워크 대역폭 비용이 극도로 비싼 해외 리전 간 전송 |
| **`zstd`** | **약 70~85% 감소** | 보통 (레벨 조절 가능) | 빠름 (GZIP의 3배 이상) | 대용량 로그 수집 파이프라인, 아카이빙 토픽 |
