# [ZeliJudge #023] A는 B를 기다리고 B는 A를 기다린다: 데드락(Deadlock)과 락 획득 순서의 저주

## 📌 문제 배경 스토리
핀테크 스타트업 '젤리페이'의 백엔드 개발자 젤리는 동시성 버그(Race Condition)를 막기 위해 데이터베이스 트랜잭션 락(Lock)을 도입했습니다.
젤리는 사용자 간 계좌 이체 API를 만들면서 다음과 같이 아주 단순하게 코드를 작성했습니다:

```python
# [젤리가 작성한 단순 계좌 이체 락 획득 코드]
def transfer_money(from_account, to_account, amount):
    # 1. 돈을 보내는 사람 계좌 락 획득
    acquire_lock(from_account)
    # 2. 돈을 받는 사람 계좌 락 획득
    acquire_lock(to_account)
    
    # 송금 처리 진행...
    deduct(from_account, amount)
    add(to_account, amount)
    
    release_lock(to_account)
    release_lock(from_account)
```

젤리는 생각했습니다:
*"보내는 사람 잠그고, 받는 사람 잠그고 돈 옮기면 완벽히 안전하잖아? 동시성 이슈 끝!"*

하지만 월급날 저녁, 젤리페이 서버가 **CPU 사용률 0% 상태로 돌처럼 굳어버렸습니다**:
* 사용자 철수(`ACC_A`)가 영희(`ACC_B`)에게 10,000원을 송금하려 함:
  1. 철수 트랜잭션: `ACC_A` 락 획득 성공! ──> 이제 `ACC_B` 락을 얻으려 대기 중...
* 정확히 같은 순간, 영희(`ACC_B`)가 철수(`ACC_A`)에게 5,000원을 송금하려 함:
  2. 영희 트랜잭션: `ACC_B` 락 획득 성공! ──> 이제 `ACC_A` 락을 얻으려 대기 중...

결과:
- 철수는 영희가 쥔 `ACC_B`를 기다리고, 영희는 철수가 쥔 `ACC_A`를 기다리며 영원히 멈췄습니다!
- 에러 로그도 발생하지 않고 CPU도 돌지 않지만, 모든 후속 계좌 이체 요청이 대기 큐에 무한정 쌓이며 전국의 은행 거래가 올스톱되는 **데드락(Deadlock, 교착 상태)** 참사가 터졌습니다!

CTO는 긴급 점검 회의에서 화이트보드에 큰 화살표를 그리며 외쳤습니다:
*"젤리 씨! 자원을 획득하는 순서가 무질서하면 꼬리에 꼬리를 무는 **원형 대기(Circular Wait)**가 생겨 데드락이 필연적으로 발생합니다!"*
*"이 참사를 영구적으로 해결하는 가장 우아한 컴퓨터 과학적 해법은 **글로벌 락 정렬(Global Lock Ordering)**입니다!"*
*"누가 누구에게 송금하든 상관없이, 항상 **자원 ID의 사전순(오름차순)으로 작은 쪽 자원을 먼저 잠그고 큰 쪽 자원을 나중에 잠그도록 규칙을 강제**하면, 그래프의 모든 간선이 단방향(DAG)으로만 흘러 사이클이 100% 원천 봉쇄됩니다!"*

CTO는 트랜잭션 락 설계의 안정성을 평가하기 위해,
1. 개발자가 작성한 순서 그대로 락을 획득했을 때 데드락 발생 여부를 판별하는 `NAIVE` 정책
2. 모든 락을 오름차순으로 정렬하여 획득함으로써 데드락을 원천 차단하고 최장 대기 체인을 계산하는 `ORDERED` 정책
두 정책을 대조 분석하는 **데드락 탐지 및 방지 분석 엔진**을 구현하라고 지시했습니다.

---

## ⚙️ 시스템 동작 규칙

$N$개의 트랜잭션이 주어지며, 각 트랜잭션은 2개의 서로 다른 자원에 대해 순차적으로 락을 획득하려 합니다:
`TX <tx_id> <res_from> <res_to>`

---

### 1. NAIVE 정책 (무질서한 락 획득)
- 트랜잭션이 입력받은 순서 그대로 `<res_from>` 락을 먼저 점유(Hold)한 상태에서 `<res_to>` 락을 획득 대기(Wait)합니다.
- 자원 간 방향성 대기 간선 `<res_from> -> <res_to>`가 형성됩니다. (동일한 방향의 중복 간선은 1개로 취급)
- **사이클 탐지 (Cycle Detection)**:
  - 자원 이름의 오름차순(사전순)으로 노드들을 방문하며 DFS를 수행합니다.
  - 탐색 중 현재 탐색 경로 상에 있는 노드(방문 중인 조상 노드)로 향하는 역방향 간선(Back-Edge)을 발견하면 **사이클(데드락)**이 발생한 것입니다.
  - 최초로 발견된 사이클에 포함된 자원(노드)의 개수를 $K$라 할 때:
    `NAIVE: DEADLOCK CYCLE:<K>`
  - 사이클이 전혀 존재하지 않는다면:
    `NAIVE: SAFE`

---

### 2. ORDERED 정책 (글로벌 락 획득 순서 강제)
- 모든 트랜잭션의 락 획득 순서를 두 자원 이름의 사전순(오름차순)으로 강제 정렬합니다:
  $$u = \min(res\_from, res\_to), \quad v = \max(res\_from, res\_to)$$
- 모든 트랜잭션은 항상 $u$를 먼저 획득하고 그 뒤에 $v$를 획득합니다. ($u \to v$)
- 정렬 후 생성된 방향 간선 집합(중복 제거)으로 유향 비순환 그래프(DAG)를 구성합니다.
  - 모든 간선이 $u < v$ 사전순 증가 방향으로만 흐르므로, **사이클은 절대로 발생할 수 없습니다 (100% SAFE 보장).**
- **최장 락 의존 체인 (Max Chain)**:
  - 트랜잭션들이 락을 획득하기 위해 순차적으로 기다려야 하는 가장 긴 의존 경로의 간선(Edge) 개수를 계산합니다:
    $$MAX\_CHAIN = \max_{path} (\text{간선 수})$$
    (간선이 없으면 0)
- 출력 형식:
  `ORDERED: SAFE MAX_CHAIN:<len>`

---

## 📥 입력 형식 (Input)

- 첫째 줄에 총 트랜잭션의 개수 $N$이 주어집니다. ($1 \le N \le 100,000$)
- 둘째 줄부터 $N$개의 줄에 걸쳐 각 트랜잭션 정보가 주어집니다:
  `TX <tx_id> <res_from> <res_to>`
- `<tx_id>`: 1~20자의 영문 알파벳과 숫자, 언더스코어로 구성된 고유 식별자.
- `<res_from>`, `<res_to>`: 1~20자의 영문 알파벳과 숫자, 언더스코어로 구성된 자원 식별자 (`<res_from> != <res_to>`).

---

## 📤 출력 형식 (Output)

- 정확히 두 줄을 출력합니다:
  - 첫째 줄: `NAIVE: DEADLOCK CYCLE:<K>` 또는 `NAIVE: SAFE`
  - 둘째 줄: `ORDERED: SAFE MAX_CHAIN:<len>`

---

## 💡 입출력 예시 (Example)

### 예시 입력 1
```text
2
TX T1 ACC_A ACC_B
TX T2 ACC_B ACC_A
```

### 예시 출력 1
```text
NAIVE: DEADLOCK CYCLE:2
ORDERED: SAFE MAX_CHAIN:1
```

### 예시 설명 1
- `NAIVE`: `ACC_A -> ACC_B`와 `ACC_B -> ACC_A`가 서로를 대기하여 2개 노드로 이루어진 맞물림 사이클이 발생해 데드락이 터집니다.
- `ORDERED`: 두 트랜잭션 모두 `min(A, B) = ACC_A`를 먼저 잠그고 `ACC_B`를 잠그도록 정렬되므로, 유일한 간선 `ACC_A -> ACC_B` (체인 길이 1)만 남아 안전하게 순차 실행됩니다.

---

### 예시 입력 2
```text
3
TX T1 RES_1 RES_2
TX T2 RES_2 RES_3
TX T3 RES_3 RES_1
```

### 예시 출력 2
```text
NAIVE: DEADLOCK CYCLE:3
ORDERED: SAFE MAX_CHAIN:2
```

### 예시 설명 2
- `NAIVE`: `RES_1 -> RES_2 -> RES_3 -> RES_1`의 3개 자원 원형 대기 루프가 발생하여 데드락이 됩니다.
- `ORDERED`: T3의 락 순서가 `RES_1 -> RES_3`으로 정렬되면서 간선들이 `RES_1 -> RES_2 -> RES_3` 및 `RES_1 -> RES_3`이 되어 사이클이 완전히 해체됩니다. 최장 체인은 `RES_1 -> RES_2 -> RES_3`의 간선 2개입니다.
