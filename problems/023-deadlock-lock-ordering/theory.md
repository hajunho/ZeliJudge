# [ZeliJudge 백서 #023] A는 B를 기다리고 B는 A를 기다린다: 데드락(Deadlock)과 락 획득 순서의 저주

> **"CPU는 0%이고, 에러 로그는 단 한 줄도 안 뜨는데, 전 세계의 결제 API가 멈췄습니다. 두 스레드가 서로의 양보만을 영원히 기다리고 있기 때문입니다."**

---

## 1. 💡 비전공자 바이브 코더를 위한 현실 비유: "외나무다리의 두 염소"

폭이 좁아서 딱 한 마리만 지나갈 수 있는 외나무다리 한가운데서 두 염소가 마주쳤습니다:

```text
[왼쪽 염소 철수] ───> 🐐 ── 충돌! ── 🐐 <─── [오른쪽 염소 영희]
```

- 철수: *"네가 먼저 뒤로 물러서야 내가 지나가지!"* (영희의 양보를 기다림)
- 영희: *"너야말로 먼저 뒤로 물러서야 내가 지나가지!"* (철수의 양보를 기다림)

두 염소 모두 한 발자국도 물러서지 않고 뿔을 맞댄 채 버티다가 **결국 다리 위에서 둘 다 굶어 죽었습니다.**

컴퓨터 시스템에서도 똑같은 비극이 벌어집니다:
- 스레드 1: 자원 A를 쥐고 자원 B를 기다림.
- 스레드 2: 자원 B를 쥐고 자원 A를 기다림.
- 두 스레드는 상대방이 락(Lock)을 풀어주기만을 영원히 기다리며 멈춰버립니다.  
  이것이 바로 **데드락(Deadlock, 교착 상태)**입니다!

---

## 2. 🔍 데드락 발생의 4대 필요조건 (Coffman Conditions)

1971년 에드워드 코프먼(Edward G. Coffman) 박사는 데드락이 발생하려면 다음 **4가지 조건이 동시에 만족**되어야 함을 증명했습니다:

| 조건 | 설명 | 현실 비유 |
|---|---|---|
| **1. 상호 배제 (Mutual Exclusion)** | 자원은 한 번에 한 스레드만 독점 가능 | 화장실 칸은 1명만 사용 가능 |
| **2. 점유와 대기 (Hold and Wait)** | 하나를 쥔 채로 다른 자원을 달라고 대기 | 화장실 열쇠를 쥔 채 휴지를 달라고 버팀 |
| **3. 비선점 (No Preemption)** | 남이 쥐고 있는 자원을 강제로 뺏을 수 없음 | 남이 쥔 열쇠를 강제로 뺏으면 폭력죄 |
| **4. 원형 대기 (Circular Wait)** | 꼬리에 꼬리를 무는 환형 대기 고리 형성 | A는 B를, B는 C를, C는 A를 기다림 |

> 💡 **핵심 정리**:  
> 위 4가지 조건 중 **단 하나라도 깨뜨리면(Break), 데드락은 수학적으로 절대로 발생할 수 없습니다!**

## 3. 🛡️ 구원의 기술: 원형 대기 파괴 (Global Lock Ordering)

실무에서 상호 배제나 비선점을 깨는 것은 매우 어렵습니다 (데이터 정합성이 깨지기 때문).  
따라서 엔지니어들이 사용하는 가장 우아하고 강력한 무기는 바로 **4번 '원형 대기'를 원천 파괴하는 것**입니다.

### 해법: "자원 ID가 작은 놈부터 무조건 먼저 잠가라!"

누가 누구에게 송금하든 상관없이, 항상 **자원의 고유 ID(계좌 번호, 식별자)의 사전순(오름차순)**으로 락을 획득하도록 강제합니다:

```python
# ❌ [취약한 코드]: 입력받은 순서대로 락 획득 (데드락 발생!)
def transfer(from_acc, to_acc):
    lock(from_acc)
    lock(to_acc)

# ✅ [안전한 코드]: 글로벌 락 정렬 (데드락 100% 원천 봉쇄!)
def transfer(from_acc, to_acc):
    first_lock  = min(from_acc, to_acc)  # 작은 ID 먼저!
    second_lock = max(from_acc, to_acc)  # 큰 ID 나중에!
    
    lock(first_lock)
    lock(second_lock)
```

### 왜 이 방법은 100% 안전한가? (위상 정렬의 마법)
- 모든 트랜잭션이 항상 작은 자원($u$)에서 큰 자원($v$)으로만 락을 요청하므로 ($u < v$),
- 자원 할당 그래프의 모든 화살표는 **오직 오른쪽(순방향)으로만 흐르는 유향 비순환 그래프(DAG)**가 됩니다!
- 오른쪽으로만 흐르는 그래프에서는 뒤로 되돌아오는 역방향 간선이 물리적으로 존재할 수 없으므로, **원형 대기(사이클)가 영구히 소멸**합니다!

## 4. 🚀 바이브 코더를 위한 실무 생존 가이드

### 1) 데이터베이스 다중 행 UPDATE 시 정렬 필수!
MySQL/PostgreSQL에서 여러 행을 한꺼번에 수정할 때 ID를 정렬하지 않으면 DB 데드락이 터집니다:

```sql
-- ❌ 위험: 순서 없이 무작위로 잠금 (동시 실행 시 Deadlock!)
UPDATE accounts SET balance = balance - 100 WHERE id IN (105, 12, 88);

-- ✅ 안전: 항상 기본키(PK) 오름차순으로 정렬하여 잠금!
-- 애플리케이션 단에서 [12, 88, 105] 순서로 정렬 후 순차 쿼리 실행
```

### 2) 분산 락 (Redis Redlock 등)
마이크로서비스에서 상품 재고와 쿠폰을 동시에 잠글 때도 키 이름을 알파벳순으로 정렬하여 락을 획득해야 서버 전체의 정지를 막을 수 있습니다.
