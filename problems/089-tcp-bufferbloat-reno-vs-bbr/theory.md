# [CS 백서 #089] 와이파이로 다운로드만 걸면 왜 핑이 1000ms로 치솟아요?!: 네트워크 버퍼블로트(Bufferbloat)와 TCP 혼잡 제어 (Reno vs Google BBR)

> **"집에서 동생이 스팀 게임 다운로드를 시작하자마자, 제 롤(LoL) 핑이 15ms에서 900ms로 치솟고 줌(Zoom) 화상회의가 멈춰버렸습니다!"**  
> 대부분의 사람들은 "인터넷 대역폭(속도)이 부족해서 느려졌다"고 착각합니다.  
> 하지만 측정해 보면 100Mbps 회선에서 다운로드는 90Mbps로 쌩쌩 잘 돌아가고 있습니다. 대역폭은 충분한데 내 패킷의 지연시간(Latency)만 60배 폭증한 것입니다.  
> 원인은 네트워크 장비의 거대한 버퍼와 구시대적 손실 기반 TCP 알고리즘이 결합해 만들어낸 현대 인터넷의 고질병, **버퍼블로트(Bufferbloat)** 였습니다!

---

## 1. 현실 세계 비유: 고속도로 톨게이트와 1,000대짜리 대형 주차장

서울에서 부산으로 가는 고속도로를 상상해 봅시다.
- **물리적 도로 지연시간 ($RTprop$)**: 차가 막히지 않을 때 서울에서 부산까지 시속 100km로 달리는 순수 주행 시간 (예: 2시간).
- **병목 톨게이트 처리량 ($BtlBw$)**: 톨게이트가 시간당 통과시킬 수 있는 최대 차량 수 (예: 시간당 100대).
- **대역폭-지연 곱 (BDP, Bandwidth-Delay Product)**:
  $$\text{BDP} = BtlBw \times RTprop = 100\text{대/시간} \times 2\text{시간} = 200\text{대}$$
  즉, 고속도로 위에 차가 정확히 200대 있을 때, 도로가 100% 꽉 차면서도 차가 1초도 막히지 않고 시속 100km로 달릴 수 있는 **완벽한 이상적 상태(Kleinrock's Optimal Point)** 입니다!

### (1) 구시대의 비극: 손실 기반 Reno/Cubic과 거대 주차장 (Bufferbloat)
한국도로공사에서 "차가 길가에 버려지는 일(패킷 손실)을 막겠다"며 톨게이트 바로 앞에 **1,000대짜리 대형 주차장(라우터 버퍼)** 을 만들었습니다.
- **Reno 알고리즘**:
  - Reno는 톨게이트 용량(BDP)을 알지 못합니다. 오직 **"차가 갓길에 버려지지 않는 한 계속 고속도로로 차를 밀어 넣는다!"**는 단순 무식한 규칙을 따릅니다.
  - 고속도로 파이프 용량(200대)이 꽉 찼는데도 차를 300대, 500대, 1,000대 계속 밀어 넣습니다.
  - 넘쳐난 차들은 톨게이트 앞 1,000대짜리 주차장(버퍼)에 꼬리에 꼬리를 물고 줄을 섭니다.
- **게이머의 비극**:
  - 이때 게이머가 앰뷸런스(게임 조작 패킷, PING)를 타고 톨게이트를 지나가려 합니다.
  - 하지만 주차장 앞에 1,000대의 트럭(다운로드 패킷)이 꽉 들어차 있어, 앰뷸런스도 주차장 맨 뒤에서 **10시간 동안 줄을 서서 기다려야(Queuing Delay)** 톨게이트를 빠져나갈 수 있습니다!
  - 이것이 바로 **버퍼블로트(Bufferbloat: 버퍼가 퉁퉁 부어오른 현상)** 입니다.

### (2) 구원의 혁신: Google BBR (Bottleneck Bandwidth and RTT)
2016년 구글이 개발한 **BBR** 은 패킷 손실을 혼잡의 지표로 보지 않습니다:
- BBR은 네트워크의 물리적 두 가지 핵심 변수를 실시간으로 지속 측정합니다:
  1. **$BtlBw$ (병목 대역폭)**: 톨게이트가 시간당 처리할 수 있는 최대 속도.
  2. **$RTprop$ (최소 왕복 지연시간)**: 차가 없을 때 도로를 주파하는 순수 물리 지연.
- BBR은 네트워크에 보내는 패킷 수(Inflight)를 정확히 **$\text{BDP} = BtlBw \times RTprop$** 에 맞추어 조절(Pacing)합니다.
- **결과**:
  - 주차장(라우터 버퍼) 대기 차량 수: **0대!**
  - 패킷 유실: **0건!**
  - 고속도로는 100% 가득 차서 달리고, 앰뷸런스(게임 핑)는 대기시간 0초로 톨게이트를 시속 100km로 무정차 통과합니다!

## 2. 컴퓨터 과학 원리: TCP 혼잡 제어의 패러다임 전환

### (1) 손실 기반 혼잡 제어 (Reno/Cubic)의 한계

```text
[Reno의 톱니파 패턴 (Sawtooth Wave)]
CWND
 │             /│             /│ ◄── 버퍼가 터져 패킷이 드롭될 때까지 무한정 증가!
 │            / │            / │
 │           /  │           /  │
 │   /\     /   │   /\     /   │
 │  /  \   /    │  /  \   /    │ ◄── 패킷 드롭 발생 시 절반으로 급감(Multiplicative Decrease)
 └──┴───┴─┴─────┴──┴───┴─┴─────┴──► Time
```

1. **Slow Start**: 패킷 손실이 없으면 매 RTT마다 `CWND`를 2배씩 기하급수적으로 늘립니다.
2. **Congestion Avoidance**: `ssthresh`에 도달하면 선형적으로 1씩 계속 늘립니다.
3. **버퍼블로트 발생**: 파이프가 꽉 찼는데도(`Inflight > BDP`) 패킷 드롭이 발생할 때까지 계속 늘려 라우터 큐를 가득 채웁니다.
4. **대기 지연 폭발**:
   $$\text{전체 지연시간} = \text{기본 물리 지연}(RTprop) + \frac{\text{라우터 큐에 쌓인 패킷 수}}{\text{대역폭}(BtlBw)}$$
   버퍼가 거대할수록 지연시간이 수십 배에서 수백 배까지 팽창합니다.

---

### (2) 모델 기반 혼잡 제어 (Google BBR)의 혁신

BBR은 **클라인락의 최적 동작 지점(Kleinrock's Optimal Operating Point)** 을 추구합니다.

```text
대역폭 / 지연시간
  ▲
  │ (Throughput) ─────────────── 병목 대역폭 도달 (최대 속도 유지)
  │             /
  │            /
  │           / ◄── BBR 동작점 (Inflight = BDP)
  │          /      [버퍼 큐 = 0, 지연 = 최소, 대역폭 = 최대]
  │         /
  │────────/───────────────────── 기본 지연시간 (RTprop) 유지
  │                           /
  │                          /  ◄── Reno 동작점 (버퍼가 꽉 찰 때까지 지연 폭증)
  └─────────────────────────┴────► Inflight Bytes
              ▲             ▲
             BDP       BDP + Buffer
```

- BBR은 네트워크 파이프를 가득 채우되(`Inflight = BDP`), **라우터 버퍼에는 단 1개의 패킷도 줄세우지 않는 것**을 목표로 합니다.
- 유튜브(YouTube) 트래픽에 BBR을 적용한 결과, 전 세계 사용자들의 **버퍼블로트 지연시간이 평균 30%~50% 감소**했고, 모바일 망에서는 지연시간이 수천 ms에서 수십 ms로 안정화되었습니다.

## 3. 실무 엔지니어의 핵심 교훈

1. **대형 버퍼의 역설**:
   - 메모리가 싸졌다고 공유기나 스위치의 버퍼를 무작정 늘려놓으면, 패킷 유실은 줄어들지만 지연시간이 파멸적으로 치솟는 버퍼블로트가 발생합니다.
2. **SQM (Smart Queue Management) & FQ-CoDel**:
   - 공유기 펌웨어(OpenWrt 등)에서 **Cake** 나 **FQ-CoDel** 같은 지능형 큐 관리 알고리즘을 켜면, 다운로드 패킷과 게임/화상회의 패킷을 서로 다른 큐로 분리하여 핑 폭증을 완벽히 막을 수 있습니다.
3. **리눅스 BBR 활성화**:
   - 고성능 웹 서버나 스트리밍 서버에서는 기본 Cubic 대신 BBR을 활성화하는 것이 표준 권장사항입니다:
     ```bash
     sysctl -w net.ipv4.tcp_congestion_control=bbr
     ```
