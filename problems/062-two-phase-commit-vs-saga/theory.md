# 분산 트랜잭션의 2PC 블로킹 지옥과 Saga 보상 트랜잭션 (Two-Phase Commit vs Saga Pattern)

> **"결제 서버 하나 뻗었을 뿐인데, 왜 쇼핑몰 전체 주문 DB가 꽁꽁 얼어붙어 마비됐을까요?!"**  
> **"MSA에서 2PC(Two-Phase Commit)를 쓰면 전사 DB가 줄줄이 인질로 잡히는 이유"**

---

## 1. 현실 세계 비유: 4명의 여행 약속과 코디네이터 방전 참사

친구 4명(코디네이터 A, 친구 B, C, D)이 이번 주말 1박 2일 제주도 여행을 가기로 했습니다.

```
[방식 1: 2PC (Two-Phase Commit) 방식]
코디네이터 A: "얘들아, 이번 주말 제주도 갈 거지? 갈 수 있으면 다른 약속 일체 잡지 말고 대기해!" (Phase 1: Prepare)
친구 B: "응! 다른 약속 다 거절하고 비워둘게." (로컬 락 획득)
친구 C: "응! 주말 스케줄 비웠어." (로컬 락 획득)
친구 D: "응! 나도 대기 중!" (로컬 락 획득)
```

그런데 바로 그 순간, **코디네이터 A의 스마트폰이 배터리 방전으로 꺼져버렸습니다! (Coordinator Crash)**

친구 B, C, D는 어떻게 될까요?
- 다른 약속을 잡을 수도 없습니다 (A가 표를 예매했을지도 모르니까요).
- 그렇다고 제주도로 출발할 수도 없습니다 (최종 확정 연락을 못 받았으니까요).
- 주말 내내 꼼짝없이 방구석에 갇혀 인생의 황금 같은 주말을 날려버립니다 (**Indoubt State & 영구 블로킹**).
- 심지어 다른 친구 E, F가 와서 "주말에 영화나 볼래?" 해도 "나 A 연락 기다려야 해서 안 돼"라며 거절당합니다 (**후속 트랜잭션의 Lock Timeout 폭사**).

```
[방식 2: Saga 패턴 (보상 트랜잭션) 방식]
친구들은 약속을 동시에 묶어두지 않고, 각자 할 일을 순차적으로 진행합니다:
1. 친구 B가 KTX 예매 완료 (로컬 커밋, 락 즉시 반환)
2. 친구 C가 호텔 예약 완료 (로컬 커밋, 락 즉시 반환)
3. 친구 D가 렌터카 예약 시도 -> "앗, 렌터카 전량 매진!" (실패 발생)
```

Saga 방식에서는 누군가 기절해서 모두가 얼어붙는 일 따위는 없습니다.  
대신, 실패가 발생하면 지금까지 했던 일들을 차례대로 되돌리는 **보상 트랜잭션(Compensating Transaction)**을 실행합니다:
- 친구 C: 호텔 무료 취소 버튼 클릭! (환불 완료)
- 친구 B: KTX 취소 수수료 없이 반환! (환불 완료)

결과: **아무도 락(Lock)에 묶여 멍때리지 않았고, 다른 사람들의 주말 약속을 방해하지도 않았으며, 최종적으로 모든 상태가 깨끗하게 원상 복구(Eventual Consistency)되었습니다!**

## 2. 모놀리식 ACID의 천국 vs MSA 분산 트랜잭션의 지옥

### 1) 과거의 모놀리식 (단일 DB)
과거 하나의 거대한 RDBMS(Oracle, MySQL)를 쓸 때는 트랜잭션이 너무나 쉬웠습니다.
```sql
BEGIN TRANSACTION;
  INSERT INTO orders ...;      -- 주문 생성
  UPDATE stocks SET qty = qty - 1; -- 재고 차감
  UPDATE users SET balance = balance - 10000; -- 결제
COMMIT; -- 원자성(Atomicity) 100% 보장!
```
DB 엔진 하나가 알아서 롤백과 커밋을 책임져 주었기 때문입니다.

### 2) 마이크로서비스(MSA)의 등장과 파편화
MSA에서는 서비스마다 독자적인 물리 DB를 가집니다:
- **주문 서비스** $\to$ Order DB
- **재고 서비스** $\to$ Inventory DB
- **결제 서비스** $\to$ Payment DB / 외부 PG사(토스, 카카오페이, 나이스페이)

이제 하나의 `COMMIT`으로 묶을 수 있는 단일 DB가 존재하지 않습니다!  
이때 수많은 주니어 개발자나 설계자들이 *"분산 환경에서도 2PC(XA)를 쓰면 ACID를 유지할 수 있지 않나요?"*라는 치명적인 유혹에 빠집니다.

## 3. 2PC(Two-Phase Commit)의 구조와 치명적 한계

2PC는 코디네이터(Coordinator)와 참여자(Participant) 간에 2단계로 합의를 진행합니다:

```
[Phase 1: Prepare]
Coordinator ---- "PREPARE" (재고 1개 락 걸고 준비해!) ----> Inventory DB
Coordinator ---- "PREPARE" (잔액 1만원 락 걸고 준비해!) --> Payment DB
Inventory DB -- "VOTE_COMMIT" (락 걸었음, 커밋 준비 끝!) --> Coordinator
Payment DB ---- "VOTE_COMMIT" (락 걸었음, 커밋 준비 끝!) --> Coordinator

[Phase 2: Commit]
Coordinator ---- "GLOBAL_COMMIT" ------------------------> Inventory DB
Coordinator ---- "GLOBAL_COMMIT" ------------------------> Payment DB
```

### 왜 2PC는 실무 MSA에서 사실상 "금지 기술"인가?

1. **코디네이터 블로킹 참사 (Coordinator Crash & Indoubt State)**:
   - 코디네이터가 Phase 1에서 모든 참여자의 `VOTE_COMMIT`을 받은 직후 크래시되거나 네트워크가 끊기면,
   - 참여자 DB 노드들은 **"커밋을 해야 할지, 롤백을 해야 할지" 알 수 없는 Indoubt 상태**에 빠집니다.
   - DB는 데이터 정합성을 위해 잡고 있던 **Row Lock을 영원히 풀지 못합니다.**
   - 그 결과, 같은 상품이나 같은 유저를 조회/수정하려는 수천 개의 다른 트랜잭션들이 줄줄이 `Lock Wait Timeout`으로 터지며 쇼핑몰 전체가 마비됩니다.
2. **극단적인 성능 저하 (Throughput 저하)**:
   - 네트워크 왕복(RTT)이 수십 ms씩 걸리는 동안 DB 트랜잭션과 커넥션을 계속 쥐고 있어야 하므로, 시스템 처리량이 단일 DB 대비 1/100 토막 납니다.
3. **외부 API 연동 불가능**:
   - 카카오페이, 네이버페이, 카드사 등 외부 결제사는 2PC의 `PREPARE` 인터페이스를 제공하지 않습니다!

## 4. 모던 아키텍처의 해답: Saga 패턴 (보상 트랜잭션)

1987년 프린스턴 대학의 헥터 가르시아-몰리나(Hector Garcia-Molina) 교수가 제안한 Saga 패턴은 **"분산 락을 아예 버리고, 최종 일관성(Eventual Consistency)을 취하자"**는 패러다임의 전환입니다.

### 1) 핵심 동작 메커니즘
- 긴 분산 트랜잭션을 로컬 트랜잭션의 체인으로 분할합니다: $T_1 \to T_2 \to T_3 \dots$
- 각 로컬 트랜잭션은 실행 즉시 자기 DB에 **로컬 커밋하고 락을 즉시 반환**합니다. (분산 락 0개!)
- 만약 도중에 $T_k$가 실패하면, 이미 커밋된 이전 단계들을 되돌리기 위해 **보상 트랜잭션(Compensating Transaction)** $C_{k-1} \dots C_1$을 역순으로 실행합니다.

```
[정상 흐름 (Happy Path)]
[T1: 주문 생성 (PENDING)] -> [T2: 재고 차감 (-1)] -> [T3: 결제 승인 (-10,000)] -> [T4: 주문 확정 (CONFIRMED)]
  (각 단계 즉시 로컬 커밋 & 락 반환!)

[실패 흐름: 결제(T3)에서 잔액 부족/PG 오류 발생]
[T1: 주문 PENDING] -> [T2: 재고 차감] -> [T3: 결제 실패!]
                                             |
                                 (역순 보상 트랜잭션 시작)
                                             v
[주문 취소 (CANCELLED)] <- [C2: 재고 원복 (+1)] <- [C3: 보상 없음 (미과금)]
```

### 2) 2PC vs Saga 실무 비교

| 비교 항목 | 2PC (Two-Phase Commit) | Saga 패턴 (보상 트랜잭션) |
| :--- | :--- | :--- |
| **일관성 모델** | 강한 일관성 (Strong ACID) | 최종 일관성 (BASE / Eventual Consistency) |
| **분산 락 (Locking)** | 필수 (Phase 1~2 동안 락 유지) | **없음 (0초 락, 즉시 로컬 커밋)** |
| **코디네이터 장애 시** | **전사 DB 영구 락 블로킹 마비** | **락 없음, Saga Log로 무중단 복구** |
| **시스템 처리량(TPS)** | 매우 낮음 (수십 TPS 한계) | **매우 높음 (수만 TPS 확장 가능)** |
| **외부 결제사 연동** | 불가능 (PG사가 지원 안 함) | **완벽 지원 (환불 API가 곧 보상 트랜잭션)** |
| **롤백 방식** | DB 엔진의 Physical Rollback | 애플리케이션의 Semantic Rollback (보상 쿼리) |

---

## 5. 결론: 분산 시스템을 지탱하는 진리

> **"네트워크는 언제든 끊어질 수 있고, 서버는 언제든 죽을 수 있다."**  
> 완벽한 만장일치를 강요하는 2PC는 장애 상황에서 모두를 공멸로 이끕니다.  
> 모던 대규모 시스템(넷플릭스, 쿠팡, 우버, 아마존)이 100% Saga 패턴과 이벤트 기반 아키텍처(Event-Driven Architecture)를 채택하는 이유입니다.
