# 분산 합의(Raft)와 쿼럼(Quorum) 과반수 & 스플릿 브레인(Split-Brain) 방어

## 1. 분산 시스템의 악몽: 스플릿 브레인 (Split-Brain)

### 1.1 통신이 끊긴 배와 두 명의 선장
승무원 5명이 탄 대형 유람선이 있습니다.  
폭풍우가 몰아치며 배의 통신선이 끊겨 선미(노드 1, 2, 3)와 선수(노드 4, 5)가 완전히 단절되었습니다.

만약 두 구역 모두에서 "내가 선장이다!" 하고 각각의 선장을 뽑는다면 어떻게 될까요?
- 선미의 선장 1: "암초를 피해 **우현(오른쪽)**으로 전속력 회항하라!"
- 선수의 선장 2: "항로를 따라 **좌현(왼쪽)**으로 전속력 회항하라!"

배가 반으로 찢어지며 탑승객 전원이 수장되고 맙니다.

```text
[네트워크 파티션으로 쪼개진 클러스터]
  ┌──────────────┐                  ┌──────────────┐
  │ 노드 1, 2, 3 │  (네트워크 단절)  │   노드 4, 5  │
  │   (3대 그룹)  │ <=== X X X ===>  │  (2대 그룹)   │
  └──────────────┘                  └──────────────┘
         │                                 │
   과반수(3표) 확보!                 과반수(3표) 미달!
   합법적 리더 선출 및 정상 쓰기      ★ 쓰기 거절 (스플릿 브레인 방어)
```

이것이 바로 Kubernetes(etcd), ZooKeeper, Kafka(KRaft), TiDB 등 분산 데이터베이스에서 가장 두려워하는 **스플릿 브레인 (Split-Brain, 분할 뇌)** 참사입니다.

네트워크 장애(Network Partition)로 클러스터가 두 동강 났을 때, 양쪽 서브넷이 모두 리더를 세우고 클라이언트의 쓰기 요청을 제각각 수락한다면 동일한 키에 서로 다른 데이터가 덮어써져 데이터베이스가 영구적으로 파괴됩니다.

## 2. 왜 클러스터 노드는 항상 홀수(3, 5, 7)로 구성해야 하는가?

주니어 엔지니어들이 가장 많이 저지르는 실수 중 하나는 **"서버 4대로 하면 2대씩 짝이 맞아서 더 안정적이지 않나요?"**라며 짝수 노드로 구성하는 것입니다.

### 2.1 과반수 쿼럼(Majority Quorum) 수학 공식
분산 합의 알고리즘(Paxos, Raft)에서 모든 결정(리더 선출, 로그 커밋)은 반드시 **과반수(Majority Quorum)**의 동의를 얻어야 합니다:

$$Q = \left\lfloor \frac{N}{2} \right\rfloor + 1$$

허용 가능한 최대 장애 노드 수(Fault Tolerance, $F$):
$$F = \left\lfloor \frac{N - 1}{2} \right\rfloor$$

| 노드 수 ($N$) | 과반수 쿼럼 ($Q$) | 허용 장애 노드 수 ($F$) | 비고 |
|:---:|:---:|:---:|:---|
| **3대** | **2표** | **1대** | 1대 죽어도 2대로 정상 서비스 유지 |
| **4대** | **3표** | **1대** | **3대와 동일하게 1대만 죽어도 끝! (비용 낭비)** |
| **5대** | **3표** | **2대** | 2대 죽어도 3대로 정상 서비스 유지 |
| **6대** | **4표** | **2대** | **5대와 동일하게 2대만 죽어도 끝! (비용 낭비)** |

### 2.2 4대 노드의 비극: 2대:2대 단절 참사
4대 노드로 구성된 클러스터에서 스위치 장애로 네트워크가 2대 vs 2대로 절반으로 쪼개졌다고 가정해 봅시다:
- 과반수 쿼럼 $Q = \lfloor 4/2 \rfloor + 1 = 3$표가 필요합니다.
- 하지만 왼쪽 그룹(2대)도 2표, 오른쪽 그룹(2대)도 2표밖에 얻지 못합니다.
- **결과**: 양쪽 모두 과반수를 채우지 못해 **새 리더를 선출할 수 없고, 모든 쓰기 요청이 거절되어 전사 서비스가 100% 마비**됩니다!
- 반면 5대 노드였다면 3대 vs 2대로 나뉘어, 3대 쪽이 과반수(3표)를 확보하여 무중단으로 서비스를 지속합니다.

## 3. Raft 스플릿 브레인 방어 메커니즘

### 3.1 쿼럼 검증 기반 쓰기 커밋 (Quorum-based Commit)
리더 노드가 클라이언트로부터 `WRITE <key> <value>` 요청을 받으면:
1. 리더는 자신이 현재 통신할 수 있는 활성 노드 수(`reachable_nodes`)를 확인합니다.
2. 만약 `reachable_nodes < Q`라면:
   - 리더는 자신이 네트워크 파티션의 **소수파(Minority) 구역에 고립되었음**을 감지합니다.
   - **즉시 쓰기 요청을 거절(`REJECTED_NO_QUORUM`)**하여 고립된 유령 리더가 엉뚱한 데이터를 쓰는 것을 원천 차단합니다!
3. 만약 `reachable_nodes >= Q`라면:
   - 과반수 노드에 로그를 복제하고 안전하게 커밋(`COMMITTED`)합니다.

### 3.2 네트워크 복구(Heal)와 단일 원천 복원
네트워크 파티션이 해소되면:
1. 더 높은 임기(Term)와 최신 커밋 로그를 가진 다수파 리더의 데이터가 소수파 노드들로 전파(Log Replication)되어 클러스터 전체가 100% 동일한 상태로 수렴합니다.
2. 고립되었던 옛 리더는 즉시 일반 팔로워(Follower)로 강등됩니다.
