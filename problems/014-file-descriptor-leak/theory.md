## 🚻 1. 일상 비유: 백화점 공중화장실과 자동 스프링 도어

어느 대형 백화점 1층에 화장실이 있습니다.
백화점 손님은 수천 명인데, 화장실 칸은 딱 **10개**뿐입니다.

* **정상적인 손님**: 칸에 들어가서 문을 잠그고 볼일을 본 뒤, 나올 때 **문을 활짝 열어두고(`close()`)** 나옵니다. 그럼 다음 손님이 바로 들어가서 쓸 수 있습니다.
* **비정상적인 손님 (Exception 발생)**: 볼일을 보다가 갑자기 배탈이 심하게 나서 기절해버렸습니다. 손님은 문을 안에서 걸어 잠근 채 꼼짝도 하지 못합니다.

만약 손님 10명이 차례대로 들어가서 모두 기절해버렸다면(에러 발생으로 `close()` 건너뜀) 어떻게 될까요?
화장실 10칸의 문이 모조리 잠겨버려, 밖에서 기다리던 **1,000명의 손님은 단 한 명도 화장실에 들어가지 못하고 백화점 전체에 대참사**가 벌어집니다!

이때 화장실 관리자가 도입한 기적의 장치가 바로 **"자동 비상 스프링 도어 (`with` 문)"**입니다:
> *"손님이 제 발로 걸어나오든, 안에서 기절하든, 불이 나든 상관없다! 손님의 볼일 스코프(Scope)가 끝나는 순간 **기계가 물리적으로 문을 강제로 활짝 열어제낀다!**"*

이것이 바로 파이썬의 **컨텍스트 매니저(`with` 문)**가 개발자를 구원하는 방식입니다.

## 💻 2. 운영체제(OS)의 관점: 파일 디스크립터(File Descriptor)란?

컴퓨터를 잘 모르는 바이브 코더는 `open('file.txt')`을 단순히 "파이썬 안에서 파일 글자 읽는 거겠지"라고 생각합니다.
하지만 운영체제(OS)의 커널(Kernel) 관점에서 이것은 매우 거대한 시스템 자원 할당입니다.

### 유닉스/리눅스의 대원칙: "모든 것은 파일이다 (Everything is a file)"
리눅스 서버에서 운영체제는 다음 모든 것을 **정수 번호(숫자)** 하나로 관리합니다:
1. 하드디스크/SSD의 실제 파일
2. 사용자의 웹 브라우저 접속을 받는 **네트워크 TCP 소켓**
3. 데이터베이스(MySQL, Redis) 연결 커넥션
4. 프로세스 간 통신 파이프(Pipe)
5. 터미널 표준 입출력 (0: stdin, 1: stdout, 2: stderr)

이 정수 번호를 바로 **파일 디스크립터(File Descriptor, 줄여서 FD)**라고 부릅니다.

```text
[OS 커널의 파일 디스크립터 테이블]
  FD 0 : 키보드 표준 입력 (stdin)
  FD 1 : 화면 표준 출력 (stdout)
  FD 2 : 표준 에러 출력 (stderr)
  FD 3 : 유저 A의 결제 소켓 연결
  FD 4 : 데이터베이스 연결 풀 #1
  FD 5 : 젤리가 연 temp_001.bin  <-- close 안 하고 에러 나면 영구 점유!
  FD 6 : 젤리가 연 temp_002.bin  <-- close 안 하고 에러 나면 영구 점유!
  ...
  FD 1023 : 젤리가 연 temp_999.bin
  [한도 초과!! 1024번째는 더 이상 자리가 없음!!]
```

### 왜 FD 누수(Leak)가 터지면 서버 전체가 마비될까?
리눅스는 안정성을 위해 한 프로세스가 열 수 있는 FD 개수를 기본값으로 **1024개 (`ulimit -n`)** 정도로 제한합니다.

만약 파일 처리 코드에서 에러가 터져 `f.close()`를 건너뛰는 일이 1,000번 반복되면:
1. 새 이미지 파일도 열리지 않습니다.
2. **새로운 사용자의 HTTP/웹소켓 접속(소켓 FD)도 생성되지 않습니다!**
3. **데이터베이스 쿼리를 날릴 DB 커넥션(소켓 FD)도 열리지 않습니다!**

결국 `OSError: [Errno 24] Too many open files` 라는 단 한 줄의 에러와 함께, 수억 원짜리 서버가 아무런 요청도 받지 못하는 식물인간 상태가 되어버립니다.

## 🔄 3. RAII와 Context Manager: with 문의 동작 원리

프로그래밍에서 **"자원을 획득(Acquisition)했으면 무조건 해제(Release)해야 한다"**는 원칙을 **RAII(Resource Acquisition Is Initialization)**라고 부릅니다.

과거에는 이를 위해 복잡한 `try ... finally` 문을 썼습니다:

```python
# [과거의 번거로운 방식]
f = open("data.txt")
try:
    risky_work(f)
finally:
    f.close() # 무슨 에러가 터져도 finally는 무조건 실행된다!
```

하지만 매번 5줄씩 코드를 쓰는 것은 너무 귀찮고, 실수로 빼먹기 쉽습니다.
파이썬은 이를 단 1줄로 우아하게 해결하기 위해 **Context Manager 프로토콜**을 발명했습니다:

```python
# [현대적 파이썬의 표준 정석]
with open("data.txt") as f:
    risky_work(f)
```

### 파이썬 내부에서 벌어지는 일 (`__enter__` 와 `__exit__`)
파이썬 인터프리터는 `with` 문을 만나면 내부적으로 다음과 같이 번역하여 실행합니다:

```python
manager = open("data.txt")
f = manager.__enter__()  # 1. 파일 열고 FD 획득!

try:
    risky_work(f)        # 2. 작업 수행 (여기서 에러가 터지든 말든!)
finally:
    manager.__exit__()   # 3. ★ 예외가 나든 정상 종료되든 100% 무조건 FD 닫기!
```

`risky_work()` 안에서 0으로 나누기(`ZeroDivisionError`)가 터지든, 사용자가 강제로 연결을 끊든, 심지어 `return`으로 함수를 중간에 탈출하든 상관없이, 파이썬 인터프리터는 **코드 블록을 벗어나는 찰나에 `__exit__`을 실행하여 운영체제에 FD를 즉시 반환**합니다.

## 🛡️ 4. 바이브 코더가 꼭 기억해야 할 실무 수칙

파일뿐만이 아닙니다. **"열고 닫아야 하는 모든 시스템 자원"**에는 반드시 `with` 문을 써야 합니다!

1. **파일 I/O**: `with open(...) as f:`
2. **네트워크 HTTP 요청**: `with aiohttp.ClientSession() as session:`
3. **데이터베이스 트랜잭션**: `with db.connection() as conn:`
4. **동시성 뮤텍스 락**: `with thread_lock:`

> **"코드에서 `open()`, `acquire()`, `connect()` 같은 단어가 보이면, 무조건 앞에 `with`를 붙여라. 그것이 당신의 야근과 회사의 서버를 구원하는 유일한 방패다."**
