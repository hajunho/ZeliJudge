# [ZeliJudge #014] 닫히지 않는 문과 사라진 손잡이: 파일 디스크립터(FD) 누수와 with 문의 구원

## 📌 문제 배경 스토리
AI 스타트업 '젤리랩스'의 신입 백엔드 개발자 젤리는 이미지 생성 및 분석 API 서버를 구축했습니다.
사용자가 이미지를 업로드하거나 생성을 요청할 때마다 서버는 임시 작업 파일을 디스크에 열어 데이터를 처리합니다:

```python
# [젤리가 작성한 이미지 처리 함수]
def process_image(task_id):
    f = open(f"temp_{task_id}.bin", "wb")
    
    # 이미지 디코딩 및 AI 신경망 추론
    result = run_heavy_ai_inference(f)
    
    f.close() # 작업 끝났으니 닫아야지!
    return result
```

젤리는 생각했습니다:
*"파일 열어서 작업 다 하고 마지막에 `f.close()` 꼼꼼하게 적어줬으니 완벽해!"*

하지만 서버 배포 후, 평화는 몇 시간을 넘기지 못했습니다.
사용자가 이미지를 다운로드하다가 와이파이가 끊기거나(`ConnectionResetError`), 금지된 프롬프트를 입력하여 안전 필터 에러(`SafetyFilterException`)가 터질 때마다 `run_heavy_ai_inference()` 함수가 중간에 예외를 뿜으며 튕겨나갔습니다.
그리고 그때마다 **마지막 줄에 적어둔 `f.close()`는 영영 실행되지 못했습니다.**

결국 서비스 런칭 4시간 만에 서버 전체가 뻗어버렸습니다:
```text
OSError: [Errno 24] Too many open files
```
새로운 파일도 열리지 않고, 데이터베이스(DB) 연결도 끊어지고, 심지어 새로운 사용자의 웹 접속(TCP 소켓)조차 모두 거부되었습니다! 서버를 강제로 재부팅할 때까지 모든 서비스가 올스톱되는 초대형 재앙이었습니다.

긴급 호출된 시스템 아키텍트는 분노했습니다:
*"젤리 씨! 리눅스 운영체제는 한 프로세스가 동시에 열 수 있는 **파일 손잡이(File Descriptor, FD)** 개수를 엄격히 제한(예: 1024개)합니다! 중간에 에러가 터졌다고 문을 안 닫고 도망치면 그 손잡이가 커널에 영구히 묶여서 새 파일도, DB도, 네트워크 통신도 다 마비된다고요! 파이썬의 **`with` 문(Context Manager)**을 쓰면 예외가 터져 죽더라도 OS가 문을 쾅 닫아준다는 걸 모릅니까?!"*

CTO는 이 사태를 재현하고 검증하기 위해,
1. 수동 `close()`에 의존하여 에러 발생 시 FD를 누수시키는 **위험한 시스템 (`NAIVE`)**
2. 컨텍스트 매니저 `with`를 사용하여 에러 발생 시에도 FD를 100% 회수하는 **안전한 시스템 (`SAFE_WITH`)**
두 시스템의 파일 디스크립터 점유 상태와 고갈 실패 횟수를 대조 분석하는 시뮬레이터를 개발하라고 지시했습니다.

---

## ⚙️ 시스템 동작 규칙

운영체제(OS)는 프로세스에 최대 $MAX\_FD$개의 파일 디스크립터(FD)를 제공합니다.

### 1. 두 시스템의 라이프사이클 처리 차이
* **수동 종료 시스템 (`NAIVE`)**:
  - `START <task_id>`:
    - 현재 열려 있는 파일 수가 $MAX\_FD$ 미만이면: 새로운 파일 열기에 성공하여 해당 태스크에 FD를 1개 할당합니다.
    - 이미 $MAX\_FD$개의 파일이 열려 있다면: **FD 고갈(`Too many open files`)로 열기 실패!** 이 태스크의 파일 열기는 실패(`FAIL`)로 처리되며, 태스크는 FD를 얻지 못합니다.
  - `SUCCESS <task_id>`:
    - 태스크가 정상 완료되어 `f.close()`가 정상 실행됩니다. 해당 태스크가 잡고 있던 FD를 해제하여 운영체제에 반환합니다. (열기 실패했던 태스크라면 아무 일도 일어나지 않습니다.)
  - `CRASH <task_id>`:
    - 태스크 실행 도중 치명적인 예외가 터집니다! `f.close()`에 도달하지 못하므로, **해당 태스크의 FD는 반환되지 않고 영구히 누수(Leak)**되어 계속 열린 상태로 남습니다.
* **컨텍스트 매니저 시스템 (`SAFE_WITH`)**:
  - `START <task_id>`:
    - 현재 열려 있는 파일 수가 $MAX\_FD$ 미만이면: 파일 열기에 성공하여 FD를 1개 할당합니다.
    - 이미 $MAX\_FD$개의 파일이 열려 있다면: 열기 실패(`FAIL`)로 처리됩니다.
  - `SUCCESS <task_id>`:
    - `with` 블록을 정상 탈출하면서 `__exit__`이 호출되어 FD가 즉시 안전하게 반환됩니다.
  - `CRASH <task_id>`:
    - `with` 블록 내부에서 예외가 터져 비정상 탈출하더라도, **파이썬 인터프리터가 `__exit__`을 반드시 실행하여 FD를 100% 안전하게 즉시 반환**합니다!

### 2. 상태 조회 (`STATUS`)
- 현재 시점에서 두 시스템의 상태를 다음 형식으로 한 줄에 출력합니다:
  `STATUS NAIVE:[OPEN=<open_cnt>,FAIL=<fail_cnt>] SAFE:[OPEN=<open_cnt>,FAIL=<fail_cnt>]`
  - `<open_cnt>`: 현재 운영체제에서 열려 있는(점유 중인) 총 FD 개수
  - `<fail_cnt>`: 지금까지 `START` 요청 시 FD가 꽉 차서 실패한 태스크의 누적 횟수

---

## 📥 입력 형식 (Input)

- 첫째 줄에 운영체제의 최대 가용 FD 수 $MAX\_FD$ ($1 \le MAX\_FD \le 10,000$)와 쿼리의 총 개수 $Q$ ($1 \le Q \le 100,000$)가 공백으로 구분되어 주어집니다.
- 둘째 줄부터 $Q$개의 줄에 걸쳐 다음 4가지 명령 중 하나가 주어집니다:
  - `START <task_id>`
  - `SUCCESS <task_id>`
  - `CRASH <task_id>`
  - `STATUS`
- `<task_id>`는 공백 없는 1~20자의 영문 대소문자 및 숫자로 구성되어 있습니다.
- `SUCCESS` 또는 `CRASH` 명령의 `<task_id>`는 이전에 반드시 `START`된 적이 있는 태스크임이 보장되며, 이미 종료된 태스크에 대해 중복 명령은 주어지지 않습니다.

---

## 📤 출력 형식 (Output)

- `STATUS` 명령이 주어질 때마다 지정된 규격으로 한 줄씩 출력합니다.

---

## 💡 입출력 예제

### 예제 입력 1
```text
3 10
START t1
CRASH t1
START t2
START t3
START t4
STATUS
SUCCESS t2
CRASH t3
STATUS
START t5
```

### 예제 출력 1
```text
STATUS NAIVE:[OPEN=3,FAIL=1] SAFE:[OPEN=3,FAIL=0]
STATUS NAIVE:[OPEN=2,FAIL=1] SAFE:[OPEN=1,FAIL=0]
```

### 예제 설명 1
- $MAX\_FD = 3$으로 최대 3개까지만 파일을 열 수 있습니다.
- `t1`이 시작되고 `CRASH`로 비정상 종료되었습니다:
  - `NAIVE`는 `close()`를 놓쳐서 `t1`의 FD가 열린 채 방치(Leak)됩니다 (열린 수: 1).
  - `SAFE`는 `with` 문 덕분에 `t1`의 FD가 닫혀 회수됩니다 (열린 수: 0).
- 이어 `t2`, `t3`, `t4`가 차례로 시작됩니다:
  - `NAIVE`는 `t1`(누수), `t2`, `t3`로 이미 3개가 꽉 찼기 때문에, `t4`를 열려고 할 때 `Too many open files`로 **실패(FAIL 1회)**합니다!
  - `SAFE`는 `t1`이 닫혔으므로 `t2`, `t3`, `t4` 모두 정상적으로 열립니다 (OPEN: 3, FAIL: 0).
- 첫 번째 `STATUS`:
  - `NAIVE:[OPEN=3,FAIL=1] SAFE:[OPEN=3,FAIL=0]`
- 이후 `t2`는 성공(`SUCCESS`), `t3`는 에러(`CRASH`)가 발생했습니다:
  - `NAIVE`는 `t2`만 닫히고 `t3`는 누수되어 여전히 2개(`t1`, `t3`)가 열려 있습니다.
  - `SAFE`는 `t2`, `t3` 모두 닫혀서 `t4` 1개만 열려 있습니다.
- 두 번째 `STATUS`:
  - `NAIVE:[OPEN=2,FAIL=1] SAFE:[OPEN=1,FAIL=0]`
