## 📖 실무 버그 시나리오

스타트업의 백엔드 주니어 개발자 수진이는 "인기 아이돌 콘서트 한정판 티켓팅(선착순 100석)" 예매 시스템을 개발했습니다.
수진이는 AI 코딩 툴에게 다음과 같이 요청했습니다:

> *"1초에 수천 명이 동시에 몰리니까 가장 빠른 비동기(`async/await`) 방식으로 티켓 예매 API를 짜줘."*

AI는 다음과 같은 직관적이고 깔끔한 비동기 코드를 제안했습니다:

```python
# AI가 작성해 준 위험천만한 코드
async def book_ticket(user_id, count):
    global remaining_tickets
    
    # 1. 잔여 좌석 확인 (Read)
    if remaining_tickets >= count:
        # 결제 PG사 통신 및 DB 조회 지연 (네트워크 I/O)
        await asyncio.sleep(0.05)
        
        # 2. 좌석 차감 (Write)
        remaining_tickets -= count
        return "예매 성공"
        
    return "매진"
```

수진이는 개발 환경에서 5번 연속으로 직접 예매 버튼을 눌러보았습니다. 100석에서 정확히 차감되어 완벽하게 동작했습니다. 만족한 수진이는 시스템을 오픈했습니다.

티켓 오픈 시각인 저녁 8시 정각, **단 0.1초 만에 2,000명의 동시 클릭**이 쏟아졌습니다.
그리고 1초 뒤, **모니터링 대시보드에 빨간 경고등이 켜지며 대참사가 터졌습니다**:

```text
[ALERT] 티켓 총 수량: 100장
[ALERT] 발송된 예매 성공 문자: 480명
[ALERT] 현재 잔여 티켓 수량: -380장 (음수!)
```

100석짜리 소극장에 480명이 예매에 성공해 결제까지 완료된 것입니다!  
회사는 380명에게 전액 환불과 함께 1인당 10만 원의 보상 쿠폰을 지급해야 했고, 수진이는 징계 위원회에 회부되었습니다.

수진이는 억울했습니다. 분명 `if remaining_tickets >= count:`라는 확인 코드를 넣었는데, **어떻게 잔여 좌석이 마이너스(-380)가 될 수 있었을까요?**

AI는 비동기 문법을 화려하게 구사했지만, 컴퓨터 과학의 가장 기본 원리인 **"경쟁 상태(Race Condition)"**와 **"원자성(Atomicity)"**을 완전히 무시했던 것입니다.

## 🎯 문제 설명

공유 자원(한정판 티켓 재고)의 초기 수량 $S$와 $N$개의 예매 요청 트랜잭션이 주어집니다.
각 트랜잭션 $i$는 도착 시각 $T_i$, 잔여 좌석 확인부터 차감까지 걸리는 소요 시간 $D_i$, 그리고 예매를 원하는 티켓 수량 $C_i$로 구성됩니다.

이 동일한 요청 흐름을 **[방식 A: AI의 무방비 비동기 코드]**와 **[방식 B: 엔지니어의 뮤텍스(Mutex Lock) 동기화 코드]** 두 가지 방식으로 시뮬레이션하여 그 차이를 비교 분석하세요.

---

### 방식 A: 무방비 경쟁 상태 (Naive Race Condition)
락(Lock)이 전혀 없는 상태로, 각 요청은 도착하자마자 즉시 독립적으로 실행됩니다.
1. 트랜잭션 $i$는 자신의 도착 시각 $T_i$에 메모리의 현재 티켓 잔여량(`current_stock`)을 읽습니다(**Read**).
2. 만약 $T_i$ 시점의 `current_stock` $\ge C_i$라면, 이 트랜잭션은 **"승인"**으로 판정하고 처리를 진행합니다. (만약 부족하면 즉시 "거절"되고 종료됩니다)
3. 소요 시간 $D_i$가 지난 시각 $T_i + D_i$에 실제로 티켓을 차감(**Write**)합니다:
   $$\text{current\_stock} \leftarrow \text{current\_stock} - C_i$$
   *(다른 트랜잭션이 이미 티켓을 깎아 잔액이 부족해졌더라도 이미 승인 판정을 받았으므로 무조건 차감하여 잔여 수량이 음수가 될 수 있습니다!)*
4. **동일 시각 이벤트 우선순위**: 동일한 시각 $t$에 어떤 트랜잭션의 차감(Write)과 다른 트랜잭션의 도착/확인(Read)이 동시에 발생한다면, **차감(Write)이 먼저 완료되어 메모리에 반영된 후** 도착한 트랜잭션의 확인(Read)이 일어납니다.

---

### 방식 B: 뮤텍스 상호 배제 (Mutex Lock / Critical Section)
공유 자원에 단 하나의 트랜잭션만 접근할 수 있도록 락(Lock)을 걸어 데이터 정합성을 완벽하게 보장합니다.
1. 모든 트랜잭션은 도착 시각 $T_i$ 순서대로 **FIFO 대기 큐(Queue)**에 등록됩니다. (도착 시각이 같다면 입력으로 먼저 주어진 트랜잭션이 큐의 앞에 섭니다)
2. 뮤텍스 락이 비어있다면, 큐 맨 앞의 트랜잭션이 락을 획득합니다.
   * 락 획득 시각 $Start_i = \max(T_i, \text{이전 트랜잭션의 락 해제 시각})$
3. **락을 획득한 바로 그 순간의 최신 잔여 티켓 수량**을 확인합니다:
   * **잔여량 $\ge C_i$ 인 경우**:
     * **"승인"** 판정.
     * $D_i$ 시간 동안 락을 점유하며 처리한 뒤, 시각 $Start_i + D_i$에 티켓을 차감(`stock -= C_i`)하고 락을 해제(Release)합니다.
   * **잔여량 $< C_i$ 인 경우**:
     * **"거절"** 판정.
     * 티켓이 부족하므로 기다리지 않고 **즉시(소요 시간 0) 락을 해제**하여 다음 대기자에게 넘깁니다. (락 해제 시각 = $Start_i$)
4. 모든 트랜잭션의 처리가 완료되는 최종 시각(마지막 트랜잭션 종료 시각)을 구합니다.

---

## 📥 입력 형식 (Input)

* **첫째 줄**: 초기 티켓 재고 수량 $S$와 예매 요청 건수 $N$이 공백으로 구분되어 주어집니다. ($1 \le S \le 100,000$, $1 \le N \le 100,000$)
* **둘째 줄부터 $N$개의 줄**: 각 줄에 $i$번째 트랜잭션의 도착 시각 $T_i$, 소요 시간 $D_i$, 요청 수량 $C_i$가 공백으로 구분되어 주어집니다.
  * $0 \le T_i \le 1,000,000,000$ (정수, 도착 시각 순으로 오름차순 정렬되어 주어짐)
  * $1 \le D_i \le 1,000,000$ (정수)
  * $1 \le C_i \le 1,000$ (정수)

---

## 📤 출력 형식 (Output)

* **첫째 줄**: [방식 A]의 **승인된 총 요청 건수**와 **최종 남은 잔여 티켓 수량**을 공백으로 구분하여 출력합니다.
* **둘째 줄**: [방식 B]의 **승인된 총 요청 건수**, **최종 남은 잔여 티켓 수량**, 그리고 **모든 처리가 종료된 최종 시각**을 공백으로 구분하여 출력합니다.

## 💡 예제 1

### 입력
```text
10 3
0 10 6
2 10 5
5 10 3
```

### 출력
```text
3 -4
2 1 20
```

### 힌트
* **초기 재고**: 10장
* **[방식 A: 무방비]**
  - $t=0$: 요청 1 도착 (요청량 6). 현재 재고 10 $\ge$ 6 이므로 **승인**. $t=10$에 차감 예정.
  - $t=2$: 요청 2 도착 (요청량 5). 아직 요청 1이 차감하기 전이므로 현재 재고는 여전히 10 $\ge$ 5! **승인**. $t=12$에 차감 예정.
  - $t=5$: 요청 3 도착 (요청량 3). 현재 재고 여전히 10 $\ge$ 3! **승인**. $t=15$에 차감 예정.
  - $t=10$: 요청 1 차감 $\rightarrow$ 재고 $10 - 6 = 4$
  - $t=12$: 요청 2 차감 $\rightarrow$ 재고 $4 - 5 = -1$ (재고 초과!)
  - $t=15$: 요청 3 차감 $\rightarrow$ 재고 $-1 - 3 = -4$
  - 결과: 승인 3건, 최종 재고 -4 (초과 예매 참사 발생!)
* **[방식 B: 뮤텍스]**
  - $t=0$: 요청 1이 락 획득. 재고 10 $\ge$ 6 이므로 **승인**. $t=10$까지 처리 후 재고는 4가 되고 락 해제.
  - $t=10$: 요청 2가 대기하다가 락 획득. 현재 최신 재고는 4인데 요청량은 5! 재고 부족으로 **즉시 거절**되고 락 해제 ($t=10$).
  - $t=10$: 요청 3이 락 획득. 현재 재고 4 $\ge$ 3 이므로 **승인**. $10 + 10 = 20$ 시각까지 처리 후 재고는 1이 되고 락 해제.
  - 결과: 승인 2건 (요청 1, 3), 최종 재고 1, 모든 처리 종료 시각 20.
  - *(데이터 정합성이 100% 보장됨!)*
