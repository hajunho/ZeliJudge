# 📘 [CS 이론 #004] 비동기의 배신과 계좌 복사 버그: Race Condition & 원자성

> **"비동기(async)로 빠르게 만들었는데 왜 잔액이 마이너스가 되고 돈이 복사될까?"**  
> 모든 백엔드 엔지니어가 평생 싸워야 할 가장 무서운 유령, 경쟁 상태(Race Condition)와 동시성 제어.

---

## 1. 흔한 착각: "비동기(Async) = 만병통치약?"

AI 코딩 툴에 익숙해진 주니어 개발자들은 *"동시 요청이 많으면 `async/await`나 멀티스레드를 쓰면 된다"*고 막연히 생각합니다.  
하지만 **동시성(Concurrency)을 다루는 기술은 칼날과 같아서, 올바른 제어 장치 없이 쓰면 데이터베이스와 회사의 잔고를 순식간에 절단냅니다.**

실제 핀테크, 커머스, 티켓팅 사이트에서 매년 수없이 발생하는 **'돈 복사 버그'**와 **'초과 예매 사고'**의 99%는 비동기 문법을 몰라서가 아니라, **경쟁 상태(Race Condition)**를 방어하지 못해서 발생합니다.

---

## 2. 참사의 원인: Check-Then-Act 패턴의 함정

수진이의 코드를 다시 살펴보겠습니다:

```python
# 1. 잔여 좌석 확인 (Check / Read)
if remaining_tickets >= count:
    # 2. 다른 작업 (네트워크 통신, 결제 대기 등)
    await asyncio.sleep(0.05)
    
    # 3. 좌석 차감 (Act / Write)
    remaining_tickets -= count
```

이 패턴을 컴퓨터 과학에서는 **'Check-Then-Act (확인 후 행동)'** 안티패턴이라고 부릅니다.

### 무슨 일이 벌어졌을까요? (Interleaving의 악몽)
시간 축을 마이크로초($\mu s$) 단위로 쪼개어 두 유저의 요청을 살펴보겠습니다:

```
시간(t)     유저 A (요청량 6)                      유저 B (요청량 5)                      메모리 잔여 좌석
─────────────────────────────────────────────────────────────────────────────────────────────
t = 0.00   "남은 표 몇 장이지?" (Read)                                                  10장
t = 0.01   "10장 남았네! 6 >= 10 통과!"                                                  10장
t = 0.02                                         "남은 표 몇 장이지?" (Read)            10장
t = 0.03                                         "10장 남았네! 5 >= 10 통과!"            10장
t = 0.05   [결제 완료 후 차감] (Write)                                                  4장 (10 - 6)
t = 0.06                                         [결제 완료 후 차감] (Write)           -1장 (4 - 5) 💥
```

유저 B가 잔여 좌석을 확인할 때(t=0.02), 유저 A는 아직 표를 차감하지 않았습니다.  
결국 **유저 A와 B 모두 "표가 10장 남아있다"는 과거의 거짓된 상태를 보고 둘 다 결제 승인을 받아버린 것**입니다!

이처럼 **둘 이상의 작업이 공유 자원(Shared Resource)에 동시에 접근할 때, 실행 순서나 타이밍에 따라 결과가 달라지는 비정상적인 상태**를 **경쟁 상태(Race Condition)**라고 부릅니다.

## 3. 원자성(Atomicity): "한 입에 삼키거나, 아예 안 먹거나"

파이썬에서 `remaining_tickets -= count`라는 코드는 단 한 줄입니다.  
그렇다면 이 한 줄은 안전할까요? **절대 아닙니다.**

CPU는 이 한 줄을 다음과 같이 **3개의 분리된 기계어 연산**으로 쪼개어 실행합니다:
1. **LOAD**: 메모리에서 `remaining_tickets`의 값을 CPU 레지스터로 읽어온다.
2. **SUB**: 레지스터 값에서 `count`를 뺀다.
3. **STORE**: 계산된 결과를 다시 메모리 주소에 덮어쓴다.

CPU가 1번(LOAD)을 실행하고 3번(STORE)을 실행하기 직전에 다른 스레드로 컨텍스트 스위칭(Context Switching)이 일어나면, 단 한 줄의 연산조차 데이터가 오염됩니다.

> **원자적 연산(Atomic Operation)이란?**  
> 더 이상 쪼갤 수 없는(Indivisible) 연산을 뜻합니다.  
> 중간에 다른 어떤 스레드나 인터럽트도 끼어들 수 없이 **"전부 완벽히 실행되거나, 아예 하나도 실행되지 않는(All or Nothing)"** 상태를 보장해야 비로소 데이터가 안전합니다.

## 4. 구원투수: 상호 배제(Mutex)와 임계 구역(Critical Section)

공유 자원을 안전하게 지키기 위해 엔지니어들이 고안한 핵심 메커니즘이 바로 **상호 배제(Mutual Exclusion $\rightarrow$ 줄여서 Mutex)**입니다.

```
[ 화장실 비유 (Mutex Lock) ]
화장실(공유 자원)은 단 1칸뿐입니다.
문 앞에 단 1개뿐인 '열쇠(Lock)'가 걸려 있습니다.
1. 사람이 들어가면 문을 안에서 잠급니다 (Acquire Lock).
2. 볼일을 보는 동안(Critical Section) 다른 사람들은 밖에서 줄을 서서 기다립니다 (Wait / Block).
3. 볼일이 끝나고 나올 때 문을 열어줍니다 (Release Lock).
4. 다음 대기자가 비로소 열쇠를 쥐고 들어갑니다.
```

* **임계 구역(Critical Section)**: 공유 데이터(재고, 계좌 잔액)를 읽고 쓰는 위험한 코드 영역.
* **뮤텍스(Mutex)**: 임계 구역에 오직 한 번에 단 하나의 스레드/트랜잭션만 진입하도록 강제하는 동기화 도구.

```python
# [해결책] 비동기 락(asyncio.Lock / Mutex)을 적용한 안전한 코드
lock = asyncio.Lock()

async def book_ticket_safe(user_id, count):
    global remaining_tickets
    
    # 1. 락 획득 대기 (다른 요청은 여기서 줄을 서서 멈춤)
    async with lock:
        # 2. 락을 얻은 '바로 그 순간'의 최신 잔여량 확인 (원자성 확보)
        if remaining_tickets >= count:
            await asyncio.sleep(0.05)
            remaining_tickets -= count
            return "예매 성공"
        return "매진"
```

## 5. 실무에서의 트레이드오프: 락과 성능의 딜레마

*"그럼 모든 곳에 락(Lock)을 걸면 되는 거 아닌가요?"*  
여기서 엔지니어링의 위대한 딜레마가 찾아옵니다:

* **락을 걸지 않으면**: 초당 수만 건을 처리하지만, 데이터가 걸레짝이 되어 회사가 망합니다.
* **락을 과도하게 걸면**: 데이터는 100% 안전하지만, 모든 요청이 1줄로 서서 기다리므로(직렬화 병목) 시스템이 거북이처럼 느려집니다.

이를 해결하기 위해 실무에서는 다양한 고도화 기법을 사용합니다:
1. **비관적 락(Pessimistic Lock)**: DB `SELECT ... FOR UPDATE`로 레코드에 직접 락을 거는 방식 (충돌이 빈번할 때 적합).
2. **낙관적 락(Optimistic Lock)**: 락을 걸지 않고 `version` 번호를 두어, 저장할 때 버전이 바뀌었으면 재시도하는 방식 (충돌이 드물 때 초고속).
3. **Redis 분산 락(Redlock)**: 여러 대의 서버 인스턴스가 단일 공유 메모리(Redis)를 통해 원자적 연산(`SETNX`)으로 락을 조율.
4. **원자적 쿼리(Atomic Query)**: `UPDATE stock SET count = count - 1 WHERE id = 1 AND count >= 1;` 처럼 데이터베이스 엔진 내부의 단일 원자적 쓰기를 활용.

## 💡 AI 바이브 코더를 위한 실무 체크리스트
1. **`if 잔액 >= 요청: 잔액 -= 요청` 패턴을 당장 버리세요.** 확인(Read)과 변경(Write)이 분리된 코드는 트래픽이 몰리는 순간 무조건 마이너스 잔액을 만듭니다.
2. **비동기(`async`)는 동기화(Lock)를 대신해주지 않습니다.** 오히려 동시 요청의 인터리빙 타이밍을 극대화시켜 버그 발생 빈도를 100배 높입니다.
3. **돈, 재고, 포인트에는 무조건 락(DB 비관적 락, Redis 분산 락, 또는 원자적 차감 쿼리)을 거세요.**
