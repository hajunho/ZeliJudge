# [CS 백서 #086] 새벽 3시 백업만 돌면 Redis가 왜 죽어요?!: Linux fork(), Copy-On-Write (COW)와 메모리 폭증(Memory Spike)

> **"새벽 3시마다 알람이 울려요. 트래픽도 평소의 절반인데 Redis 컨테이너가 갑자기 뻗어버립니다!"**  
> 모니터링을 확인해보니 CPU는 멀쩡한데, 메모리가 60%에서 순식간에 100%를 돌파하더니 Linux 커널의 OOM-Killer가 `redis-server`를 `SIGKILL (kill -9)`로 즉사시켰습니다.  
> 원인은 바로 백그라운드 데이터 백업(`BGSAVE`)이 도는 동안 발생한 **Linux `fork()` 시스템 콜과 Copy-On-Write (COW) 페이지 폴트의 폭풍**이었습니다!

---

## 1. 현실 세계 비유: 1,000장 서류철과 빨간 펜의 비극

회사 사무실에 1,000페이지짜리 고객 장부(메모리)가 있습니다. 사장님이 백업 담당 신입사원에게 지시합니다:
> *"지금 이 순간의 장부 내용을 그대로 스냅샷 찍어서 창고(디스크)에 파일로 저장해둬라."*

### 방식 A. 무식한 전체 복사 (Eager Copy)
- 1,000페이지를 복사기 위에 올려놓고 한 장씩 다 복사합니다.
- 복사하는 30분 동안 사장님도 손님 주문을 전혀 받지 못하고 멍하니 기다려야 합니다(**서버 멈춤, Stop-the-World**).

### 방식 B. 똑똑한 지연 복사: Copy-On-Write (COW)
- 사장님은 신입사원에게 복사본 서류철 껍데기(가상 메모리 페이지 테이블)만 쥐여주고 이렇게 말합니다:
  > *"원본 장부를 그냥 창고로 들고 가서 읽어라. 복사기는 안 쓴다. 단, **둘 중 누구든 장부에 빨간 펜을 대고 한 글자라도 고치려고(Write) 하는 순간에만**, 그 페이지 딱 1장만 복사기로 복사해서 각자 가져가라!"*
- 복사기를 돌릴 필요가 없으니 0.001초 만에 백업 작업이 시작되고 사장님은 즉시 손님 주문을 계속 받을 수 있습니다!

### 참사의 시작: 1,000페이지에 쏟아진 빨간 펜 세례
- 신입사원이 창고에서 원본 장부를 평화롭게 읽고 있는데, 마침 새벽에 야간 할인 이벤트가 터져 손님들이 장부 곳곳의 고객 포인트와 주문 내역을 수정하기 시작합니다.
- 손님이 1페이지를 수정하자 복사기가 1장을 복사합니다.
- 손님이 2페이지를 수정하자 또 1장을 복사합니다.
- 결국 손님들이 장부 1,000페이지를 골고루 건드리자, 복사기가 1,000장을 전부 복사해내며 **사무실 바닥에 종이 1,000장이 새로 쌓여 천장까지 차오릅니다!**
- 건물이 무게를 견디지 못하고 무너져(OOM Killer 출동), 사장님과 손님, 사무실 전체가 압사당하고 맙니다!

## 2. 컴퓨터 과학 원리: Linux fork()와 가상 메모리

### (1) fork() 시스템 콜과 페이지 테이블 공유
Linux/Unix 계열 운영체제에서 프로세스가 `fork()`를 호출하여 자식 프로세스를 생성하면, 커널은 부모 프로세스의 물리 메모리(RAM)를 통째로 복제하지 않습니다.
대신 **가상 메모리 주소와 물리 메모리를 연결해 주는 매핑 표(Page Table)** 만 복제합니다.

```text
[부모 프로세스 (Redis Main)]               [자식 프로세스 (Redis BGSAVE)]
   가상 페이지 P0, P1, P2 ...                가상 페이지 P0, P1, P2 ...
          │                                        │
          └───────────────┬────────────────────────┘
                          ▼
            [물리 메모리 (RAM Frames)]
            ┌──────────────────────────┐
            │ Frame 100: Page 0 (R/O)  │ ◄── 두 프로세스가 동일한 물리 메모리를
            │ Frame 101: Page 1 (R/O)  │     "읽기 전용(Read-Only)"으로 공유!
            │ Frame 102: Page 2 (R/O)  │
            └──────────────────────────┘
```

- 부모와 자식은 동일한 물리 메모리 프레임을 가리키며, 커널은 이 페이지들을 **읽기 전용(Read-Only)** 으로 플래그를 변경합니다.
- 덕분에 메모리가 100GB인 Redis라도 `fork()`는 수 밀리초(ms) 만에 완료됩니다.

---

### (2) 쓰기 시점의 반전: 하드웨어 페이지 폴트 (MMU Page Fault)

자식 프로세스가 디스크에 데이터를 쓰는 동안, 부모 프로세스(Redis 메인 스레드)에 클라이언트의 쓰기 명령(`SET`, `INCR`, `HSET`, `DEL`)이 들어옵니다.

1. 부모 프로세스가 읽기 전용으로 잠긴 페이지(예: `P0`)에 쓰기를 시도합니다.
2. CPU 내부의 **MMU(Memory Management Unit)** 가 하드웨어 보호 인터럽트인 **페이지 폴트(Page Fault)** 를 발생시킵니다.
3. 운영체제 커널의 페이지 폴트 핸들러가 출동합니다:
   - *"아, 이 페이지는 부모와 자식이 공유 중인 COW(Copy-On-Write) 페이지구나!"*
4. 커널은 빈 물리 메모리 프레임을 새로 할당하고, 원본 4KB 페이지의 데이터를 **그대로 복사(Deep Copy)** 합니다.
5. 새로 복사된 물리 페이지를 부모의 페이지 테이블에 연결하고 **쓰기 가능(Read/Write)** 으로 변경합니다.
6. 자식 프로세스는 여전히 원본 물리 페이지(스냅샷 시점의 과거 데이터)를 바라보고, 부모는 새로 복제된 독립 물리 페이지에 변경사항을 기록합니다.

```text
[부모 쓰기 발생 후]
부모 가상 P0 ──► [새 물리 Frame 200 (R/W)] (수정된 최신 데이터) -> +4KB 물리 메모리 증가!
자식 가상 P0 ──► [원래 물리 Frame 100 (R/O)] (스냅샷 시점의 과거 데이터)
```

### (3) 메모리 스파이크(Memory Spike)와 OOM Killer

만약 백그라운드 세이브(`BGSAVE`)가 도는 수십 초 ~ 수 분 동안 부모 프로세스가 보유한 페이지의 상당수가 수정된다면 어떻게 될까요?

$$\text{피크 물리 메모리} = \text{기존 메모리} + (\text{수정된 페이지 수} \times \text{페이지 크기})$$

- 8GB RAM 서버에서 Redis가 평소 5GB(62.5%)를 사용 중이었다고 가정해 봅시다.
- 새벽 할인 이벤트로 인해 전체 키의 80%가 갱신되면, 5GB 중 4GB 분량의 페이지가 복제됩니다.
- 결과: $5\text{GB} + 4\text{GB} = 9\text{GB}$의 물리 메모리가 필요해집니다!
- 물리 RAM(8GB)을 초과하는 순간, Linux 커널의 **OOM Killer (Out-of-Memory Killer)** 가 기동하여 시스템 전체를 살리기 위해 가장 메모리를 많이 먹고 있는 프로세스(`redis-server`)에 `kill -9`를 전송하여 즉사시킵니다.

### (4) 치명적인 증폭기: Transparent HugePages (THP)의 재앙

리눅스 커널 2.6.38부터 도입된 **THP (Transparent HugePages)** 기능은 TLB(Translation Lookaside Buffer) 미스를 줄이기 위해 기본 페이지 크기인 **4KB 대신 2MB(2,048KB)** 단위로 메모리를 할당합니다.

일반적인 연산에서는 성능이 좋아지지만, **Redis의 COW 환경에서는 상상초월의 재앙**이 됩니다!

| 구분 | 표준 페이지 (Standard Page) | Transparent HugePages (THP) |
| :--- | :--- | :--- |
| **페이지 단위 크기** | **4 KB** | **2,048 KB (2 MB)** |
| **8바이트 카운터 1개 수정 시** | 4 KB 물리 메모리 복제 | **2,048 KB (2 MB) 물리 메모리 복제** |
| **메모리 복제 오버헤드** | 기준선 (1x) | **무려 512배 증폭!!** |
| **COW 지연시간 (Latency)** | 4KB 복사 (수 마이크로초) | 2MB 복사 (수 밀리초 $\to$ 이벤트루프 블로킹) |

단 1개의 작은 키만 수정해도 커널이 2MB 전체를 통째로 복제하므로, 메모리가 순식간에 기하급수적으로 폭증하며 메인 스레드의 지연시간(Latency)도 수십 배 튀게 됩니다.
이것이 바로 Redis 공식 문서와 부팅 로그에서 **"WARNING you have Transparent Huge Pages (THP) support enabled in your kernel. This will create latency and memory usage issues with Redis."** 경고를 띄우며 비활성화를 강제하는 이유입니다.

## 3. 실무 엔지니어의 골든 룰 & 트러블슈팅

1. **메모리 50% 룰 (Memory Headroom)**:
   - Redis 인스턴스의 메모리 사용량(`maxmemory`)은 물리 서버 RAM의 **50%~60% 이하**로 제한해야 BGSAVE 도중 100% 페이지가 오염되어도 OOM을 피할 수 있습니다.
2. **Transparent HugePages (THP) 반드시 끄기**:
   ```bash
   echo never > /sys/kernel/mm/transparent_hugepage/enabled
   ```
3. **Linux Overcommit 설정**:
   ```bash
   sysctl vm.overcommit_memory=1
   ```
   - 기본값(`0`)인 경우, 커널이 "메모리가 2배로 늘어날 수도 있으니 fork 자체를 거절"하여 BGSAVE가 실패합니다. `1`로 설정해야 COW를 믿고 fork를 허용합니다.
4. **쓰기 부하가 적은 시간대로 스냅샷 분산**:
   - 트래픽 피크 타임에 RDB 스냅샷 저장을 피하거나, 읽기 전용 복제본(Replica Node)에서만 BGSAVE를 수행하도록 아키텍처를 분리합니다.
