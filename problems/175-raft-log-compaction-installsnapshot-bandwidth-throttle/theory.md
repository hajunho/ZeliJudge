# Raft 로그 컴팩션(Log Compaction)과 스냅샷 스트리밍 대역폭 스로틀링(InstallSnapshot Throttling)

## 1. 개요: Raft 분산 합의와 로그 무한 팽창의 딜레마

Raft 분산 합의 알고리즘(Diego Ongaro 논문)에서 모든 상태 변경 요청은 순차적인 **추가 전용 로그(Append-Only Log)**로 기록됩니다.

실제 상용 분산 시스템(etcd, Kubernetes, TiKV, CockroachDB, Consul)에서 분당 수만 건의 트랜잭션이 지속적으로 유입되면, 수일 내에 로그의 크기가 수십~수백 기가바이트로 팽창합니다:
1. **디스크 용량 고갈**: 물리 디스크 공간이 부족해져 클러스터 전체가 쓰기 불가 상태에 빠집니다.
2. **노드 재부팅 지연 (Replay Storm)**: 노드가 재시작될 때 처음부터 수천만 개의 로그를 리플레이하여 메모리 상태를 복구하느라 기동 시간이 수십 분~수 시간으로 지연됩니다.

따라서 Raft는 이미 과반수에 의해 커밋되고 상태 머신에 적용된 과거 로그들을 주기적으로 압축하여 상태 머신의 현재 스냅샷(Snapshot)으로 대체하고 과거 로그를 디스크에서 삭제하는 **로그 컴팩션(Log Compaction, 논문 Chapter 7)**을 필수적으로 수행합니다.

```
+-------------------------------------------------------------------------------+
|                        Raft 로그 컴팩션 (Log Compaction)                      |
+-------------------------------------------------------------------------------+
|                                                                               |
| [과거 로그 삭제 (Truncated)]               [활성 로그 버퍼 (Active WAL)]      |
| Index: 1 ... 99                           Index: 100 101 102 103 ...          |
| +---------------------------------------+ +---------------------------------+ |
| | Snapshot (last_index: 99, term: 1)    | | Entry(100) Entry(101) ...       | |
| +---------------------------------------+ +---------------------------------+ |
|                                                                               |
+-------------------------------------------------------------------------------+
```

## 2. 장애의 근원: 느린 팔로워(Slow Follower)와 InstallSnapshot 폭풍

### 2.1 델타 로그 복제 불가능 상황의 도래
정상적인 상황에서 리더는 팔로워의 `nextIndex`에 맞춰 차이점(Delta)에 해당하는 로그 엔트리만 `AppendEntries` RPC로 가볍게 전송합니다.
그러나 특정 팔로워가 일시적인 네트워크 지연, GC 정지, 또는 디스크 I/O 병목으로 인해 뒤처져 있는 동안, **리더가 로그 컴팩션을 수행하여 해당 팔로워가 필요로 하는 로그를 디스크에서 이미 삭제해 버린 경우(`follower.nextIndex < leader.firstLogIndex`)**가 발생합니다.

리더는 더 이상 과거 로그를 가지고 있지 않으므로 델타 전송이 원천적으로 불가능하며, **자신의 전체 상태 머신을 통째로 덤프한 거대한 스냅샷을 전송하는 `InstallSnapshot` RPC**를 발동해야 합니다.

### 2.2 대역폭 무제한 스냅샷 폭풍과 하트비트 질식(Starvation) 참사
스냅샷의 크기는 수백 메가바이트에서 수십 기가바이트에 달합니다.
만약 리더가 이 거대한 스냅샷을 대역폭 제어 없이 네트워크로 쏟아붓는다면:
1. **리더 NIC(네트워크 카드) 송신 대역폭 100% 포화**:
   - 스냅샷 청크들이 TCP 소켓 버퍼와 스위치 큐를 가득 채웁니다.
2. **하트비트 패킷 드랍 및 지연**:
   - 멀쩡히 트래픽을 처리하고 있던 다른 건강한 팔로워들에게 보내야 하는 주기적 하트비트(`AppendEntries` 빈 패킷)가 네트워크 큐 뒤로 밀리거나 드랍됩니다.
3. **연쇄 선출 타임아웃(Cascading Election Timeout) 및 리더 강제 폐위**:
   - 건강한 팔로워들은 리더가 죽었다고 판단하여 선출 타임아웃을 발동하고, 고임기 `RequestVote`를 난사합니다.
   - 합법적인 리더가 폐위되고, 새 리더 선출을 위한 스플릿 보트(Split-Vote)와 재선출 스톰이 발생하며 클러스터 전체가 수 분간 마비됩니다.

## 3. 구원: 2대 엔터프라이즈 스냅샷 엔지니어링 해법

### 3.1 스냅샷 스트리밍 대역폭 스로틀링 (`snapshot_throttle_bytes_per_tick`)
고성능 분산 합의 엔진(etcd, TiKV `snap-max-write-bytes-per-sec`)은 스냅샷 전송 채널에 **누수 버킷(Leaky Bucket) 또는 토큰 버킷 속도 제한기**를 적용합니다:
- 매 틱마다 전송할 수 있는 스냅샷 데이터의 최대 바이트 상한(예: 4KB/s 또는 50MB/s)을 엄격히 제한합니다.
- 스냅샷 전송 트래픽이 항상 하트비트 유실 임계치 미만으로 유지되므로, 느린 팔로워가 대용량 스냅샷을 복구받는 중에도 **건강한 노드들과의 하트비트 통신은 100% 무지연으로 보장**됩니다.

### 3.2 잔여 안전 로그 마진 (`trailing_log_margin`)
리더가 컴팩션을 수행할 때 `applied_index`까지의 모든 로그를 즉시 잘라내는 것은 위험합니다.
대신 커밋 및 적용된 최신 인덱스 뒤에 일정 개수(예: 10,000건)의 로그를 안전 마진으로 WAL에 남겨둡니다:
$$\text{compact\_index} = \max(0, \; \text{applied\_index} - \text{trailing\_log\_margin})$$
- 30초~1분 정도의 짧은 네트워크 깜빡임이나 일시적 지연을 겪은 팔로워는 재접속 후에도 여전히 리더의 WAL에 남아있는 로그를 통해 **값비싼 스냅샷 전송 없이 초고속 저비용 델타 `AppendEntries`만으로 즉시 캐치업**할 수 있습니다.

## 4. 핵심 아키텍처 비교 요약

| 구분 | 나이브 즉시 삭제 & 무제한 스냅샷 | 안전 마진 + 대역폭 스로틀링 (etcd / TiKV 표준) |
| :--- | :--- | :--- |
| **로그 삭제 기준** | `applied_index`까지 즉시 전원 삭제 | `applied_index - trailing_log_margin` 보존 |
| **일시 지연 노드 재접속 시** | 100% 거대 스냅샷 전송 강제 | 잔여 마진 내에서 가벼운 델타 로그 복제 |
| **스냅샷 전송 속도** | 대역폭 100% 무제한 폭주 | 정밀 청크 단위 대역폭 스로틀링 |
| **하트비트 채널 안정성** | **네트워크 포화로 하트비트 유실 $\to$ 리더 폐위 참사** | **하트비트 채널 완전 보호 $\to$ 클러스터 100% 가용성 유지** |
| **실제 적용 시스템** | 초보적 Raft 구현체 | **etcd, Kubernetes etcd, TiKV, CockroachDB, Kafka KRaft** |
